# 核心文本暴露了哪些 schema 缺口

**最明确的结构未覆盖项收敛为一类：GPU 执行与外部供给、调用者之间的依赖没有可引用的端点，直接证据是 MLA F18、Sparse F05。更广泛的问题是动作语义没有收束成可复用的短定义。这两项值得优先改 schema_docs；现有证据尚未证明必须新增固定字段，也未证明这些必要事实只能靠长文表达。**

跨调用物理存储、host 观察和全设备等待还有真实的表达边界，但目前不足以统统升级为 Pipeline IR 必须内置的语言。外部别名、warp 内协作、跨 dispatch 复制也应分别处理，不能合并成“缺很多字段”。

依据是原审计的 **193 份有稿 YAML、10 份 dispatch、5,875 个文本组、182 条机制 finding**。本轮复核全部 finding，重点重判原来的 **79 条非 none 候选：6 条 missing_field_or_event、50 条 open_semantics、17 条 representation_cost、6 条 unresolved**。这是机制复核，不是重新给 5,875 组分成四个互斥类别；一条 finding 或一个字段都可能混合多个事实。原统计、原标注和样本保持不变。

| 应处理的议题 | 本轮判断 | 建议落点 |
| --- | --- | --- |
| 外部供给、caller 入口与后继消费的依赖 | **明确缺少结构端点**；先补统一边界语义，再判断是否需要逐实例连接端点 | DOC0 的执行边界、DOC4 的事件/启动/交接 |
| 动作的输入与结果组成、capture、完成与读取退休保证 | **核心语义分散在自由定义中**；优先统一语义与短绑定，固定字段待同源验证 | DOC5 动作与契约，DOC6 原语绑定 |
| 跨调用物理分配、复用、host 观察状态 | **范围及证据待收束**；只保留影响当前设计的身份、版本与先决条件 | DOC0/3/4 的状态边界；暂不建通用 host 状态机 |
| 外部对象身份、原地写回、允许写集 | 必要但通常可很短；现行规范明确交给 meaning/math，**不是当前扩字段的首要理由** | DOC1 给统一短写规则与示例 |
| role 内部展开、跨节点局部定义与谓词复用 | 主要是**表示成本**；与“现有语言不能表达核心设计”分开 | DOC5 粒度规则、DOC0 复用规则 |

## 判定标准：必要文本不等于不可压缩文本

沿用用户的四类区分，先把长段拆成事实，再问：

1. 删掉以后，是否允许不同的计算、读写副作用、资源寿命、工作分配或并行关系？只有实现 API 名不同，不足以证明丢了核心。
2. 这个事实是否已经存在于当前有效设计或规范定义中？存在则是可删的重复。
3. 能否给出**现行合法结构的具体替代**？改个动作名、把文字搬进 math/strategy、发明未定义符号，不算结构替代。
4. 若不能，缺的是一个结构关系，还是一个可以统一定义的原语语义？二者都可能值得改 docs，改法不同。
5. 这个事实是否属于本仓库要保留的设计范围？不能为了忠实抄录 wrapper，顺带把所有 host 实现都升级为 Pipeline IR。

因此，“唯一且不能删除”只证明必须保留那个事实，**不证明原段落不能短写，也不证明必须新增一个字段**。这里的动作语义指 Design 的 `info.verb`，与定义外部任务的顶层 Contract 不同。

## 1. 最强结构候选：外部依赖的入口与出口

**缺的关系：某个输入/元数据已由外部供给者准备好，设备计算才可读取；本次请求的相关设备工作结束后，调用者后续工作才可消费。**

现行 [DOC4](rules/schema_docs/4.design.work_schedule.md:275) 将 phase 身份绑定到计算 kernel 的工作提交；[事件规则](rules/schema_docs/4.design.work_schedule.md:309)要求事件为 `<phase>.<milestone>`，并明确 `start_after` 约束设备开始、不要求 host 阻塞。它能连接图内已有 phase，却没有 caller 或非计算供给者的合法端点。虚构一个没有计算的 GPU phase，不是修复。

**Sparse F05：调用者与旁路计算之间的 fork/join。** [当前文本和 flow](inputs/extract_sparse/probe_hidden_packed.yaml:298) 的最小关系是：

```text
caller 先前工作 → probe、prefix
probe 完成 → remainder
prefix、remainder 完成 → caller 后续工作
```

这只是关系示意，不是新 YAML 语法。当前 flow 明确写出的只有 `probe.kernel_done → remainder`。删掉正文后，side stream 抢读旧输入，或 caller 提前读未写完的输出，都没有被剩余内部图排除。给 remainder 增加 `prefix.kernel_done` 会额外串行化两段，不能代替边界 join。这里必须保留的是输入可见性、两段完成与后继消费的关系，具体 event API 名可交给实现。

**MLA F18：Geo 的外部准备与主核入口。** [当前策略](inputs/extract_mla/root.yaml:321)说明：metadata 经 D2H 后由 host 建 Geo 表，再上传，主 stream 等上传就绪。这里须收窄原审计的反例：[Contract](inputs/extract_mla/root.yaml:114)及[Geo 定义](inputs/extract_mla/root.yaml:299)已经要求使用当前 metadata，不能把“防止重用旧 Geo”算作这段正文独占的信息。真正未入结构的是 **side 上传完成 → 整个 main grid 才可启动**；允许 main 提前启动、到读表时再等待，仍可能计算同一正确值，却改变驻留与重叠窗口。录图时执行的 host 前缀也不能写成每次 replay 都重新执行。

**确定需要补清的是边界语义，固定字段仍有两条候选路线。** 一条是在 DOC0/4 统一定义请求的入口/后继排序义务，以及外部供给在指定计算开始前就绪的前提；另一条是让外部就绪、调用前驱与后继成为可逐实例连接的端点。若第一条已经完整、简短地覆盖样例，就不必增加字段。当前只排除了已有字段，尚未排除这种未来的共享约定；因此不能把“现有端点缺失”升级为“新增字段已被证明不可避免”。

两条路线都必须区分“后续设备工作已被正确排序”与“CPU 已等待完成”，并明确入口作用于哪些提交、何时允许延后读取。不能统一加成“全部输入 ready 后才允许任意工作开始”的屏障，也不要求把 D2H、Python 排序、H2D 都建成带 GPU worker 的 phase。

修订是否成功，要同时通过这两个反例：Sparse 保留 prefix/remainder 的重叠机会，且 caller 不会早读；MLA 保留外部上传完成到整个 grid 启动的下界，不能用核内读前等待替代。仅让检查器接受一个新事件名不够。

## 2. 最广泛的 docs 问题：动作接口与保证过于开放

十个算子的审计都有这类事实。原 W/T/R 的 **1,571/2,424 组含非 FORMAL 核心信息**是背景范围，不能当作本项缺口数，更不能当作不可删比例。

[DOC5:78–98](rules/schema_docs/5.design.tile_pipeline.md:78) 明确要求动作定义补充上游推不出的输入、结果和原语保证；[DOC5:123](rules/schema_docs/5.design.tile_pipeline.md:123)把 `info.verb` 定义为一句契约。这使实例必须自己解释组合动作。规则要求“不复述”，但对反复出现的作用模式没有足够共用定义。

| 核心事实 | 删除后的问题 | 应收束什么 |
| --- | --- | --- |
| 合成对象究竟包含哪些值、某次动作还读了什么 | 同一个动作名可被实现成不同的搬运或计算 | 优先引用已定义的数学值/视图；确为执行组合时，给一次明确组成与引用 |
| capture 得到独立副本，源槽可归还，副本继续存活 | 可能过早覆盖源槽，或被迫延长源槽占用、失去重叠 | 共用捕获/保留语义；实例只绑定来源、结果及必要存活边界 |
| 原语先读旧操作数、再写同址结果 | 仅有按序 done 不能排除旧值尚未读完便覆盖 | 共用有适用条件的读写保证，再由 Realization 绑定提供保证的原语 |
| 一次完成覆盖哪些动作/读者/事务 | 把局部到达当全部就绪，或把发射当读完 | 精确定义保证的对象与范围；已有事件和边负责连接它 |

代表性定位：模板 GDN F09/F10 的 capture 与组合对象；模板 FA4 prefill F13–F15、QSA F06、MLA F09/F11/F12 的读写与驻留保证；GEMM F09/F10 的组完成；FMHA F12、MoE F08 的复合动作。完整筛查与反例见[动作复核](gap_review/action_review.md)。

**这里有真实的 schema 设计问题，但当前证据首先支持“缺少共用的语义定义”，不支持“缺一大套动作字段”。** 例如 `release`、`async_ordered_completion`、`resource.view` 都已经有明确语义。需要说明 release 等到哪个读者/原语，不等于缺了 `read_done` 事件。

建议先在 DOC5 给少量作用模式及完整短例，明确哪些保证已由通用动作提供、哪些必须在实例绑定、哪些跨角色前驱必须入图；DOC6 只固定提供保证的实现条件。新增共用定义只有被规范真实定义、能按名称解析时才算压缩，不能把长段换成另一个不透明名称。若一个同源完整样例仍反复需要难以引用的输入/结果/作用域关系，再评估小量固定字段。

原子插入/扫描等并发算法可以需要简短算法定义；native 近似可以需要数值语义与来源限制。缺少每种操作的专用字段，并不自动构成语言缺陷。

## 3. 需要收束边界，暂不直接扩语言

**跨调用状态与物理存储。** GDN F16、Sparse F06，以及 QSA F10、MLA F10、MoE F07/F15 暴露：逻辑值的寿命、底层分配的共享身份、host 读到的版本、前请求的未完成写入是不同的事实。

这里有一个必须纠正的推断：**现有 retention 并非只能写 invocation。** [DOC3](rules/schema_docs/3.design.math_reshape.md:100)用逻辑实例定义保留范围，MoE 已有 [`keep_value device_module`](inputs/extract_moe/init_no_scan_direct.yaml:52)。真正不能从它推出的是物理 owner、分配别名、跨请求完成边；[DOC4:341](rules/schema_docs/4.design.work_schedule.md:341)也明确 `storage: global` 不规定物理地址或分配器所有权。

应保留的最小事实可能是：“这些请求共享同一底层存储，只有满足某种顺序才能复用”，或“这次选择使用录制时的值/最终一次实际观察”。但 grow-only 分配策略、L2 查询缓存、全部 Python cache 状态是否都是 Pipeline IR 核心，需要另判。GDN 缺跨 stream 协议、Sparse/MoE 的旧 host mirror 竞争也不能通过新增字段擅自补成安全保证。

**建议先要求：** 对影响当前选择、读写版本或复用安全的外部状态，写一次身份与前提；普通 allocator/cache 实现细节留给实现交接或来源说明。只有在确定的调用域内，存在两种满足现有定义但有不同核心行为的存储绑定，并且短边界定义无法区分时，才升级为通用物理存储/生命周期结构。

**MoE F25 的全设备 host 等待。** 实际源码在建表后执行全设备同步，不能拿 `tables.kernel_done` 等价替代；另一 stream 的长任务会造成不同 host 返回时间。但“完整 operator 的 host 耗时”与“该计算流水线所需的依赖”不是同一范围。该事实应保留，是否内置全设备 host completion 事件属于范围决策，不与 Sparse 的输出正确性边界一起自动批准。

**外部对象身份与写集。** 模板 GDN F03 的 `O` 必须写入并返回原 `output`，返回一份同值新张量不等价。shape/dtype 中的属性 ref 不表达存储身份；整个对象的 binding 则可引用已有的外部对象，不能一概说 ref 没有身份能力。但这些引用不自动定义返回关系、允许写集或跨请求事件。[DOC1:41](rules/schema_docs/1.contract.algorithm_requirement.md:41)已明确把原地写回交给 meaning，现有[模板短句](inputs/template_gdn_prefill/root.yaml:29)就写得很紧凑。先统一“对象身份、允许写域、旧值是否读取”的短写方式，其他地方引用；没有理由仅因它是自然语言，就立刻新建大型 ABI 子语言。

## 4. 必须从“缺字段”清单排除的项目

| 项目 | 已有答案或正确归类 |
| --- | --- |
| 模板 FA4 decode F06 的 zero→reduce-add 等待；QSA F09 的条件 PV 退休等待 | 已有 `waits_for`、条件 repeat、成员引用；属于未使用现有结构。QSA 展开较长另计表示成本 |
| “源已读完、目标写仍在途” | 已有 release；不能以缺 `@read` 为由扩事件表 |
| 参数、分块、槽数、局部视图和若干简单 compute/produce | 已有表达式、binding、partition、resource.view、通用动作；需迁回结构或删除复述 |
| warp 内分工、变化的子集协作、slice 独立推进 | 多数可细化角色/动作/域，尚未证明无法表达；先比较完整展开的表示成本与设计粒度 |
| 跨 dispatch 的局部共同定义、重复 when 派生式 | 真正的复用成本；当前 from_parent 仅整区且不继承 when。不能直接删除各节点的唯一定义，也不能算第 4 类核心关系无法表达 |
| descriptor/PageIndex/mini-chunk 的复用依据不足，host mirror 竞态，空 when、混稿 | 来源缺口或产物缺陷。新增字段不能产生缺失的事实或修复源实现 |
| 模板 GDN F11 的通知流身份 | 未证明换通知流会改变核心依赖或一阶成本；不恢复此前已撤回的缺事件判断 |
| 数学公式、数值求值次序、近似未知界、硬件原语来源 | 必要的定义或限制；文本长度与缺字段无直接对应关系 |

这也解释了为什么“完全去掉文字后不能复现”不能单独证明 schema 的结构要扩张：某些文字正在定义算法或原语，而不是藏着缺失的执行关系。应要求它短、唯一、可引用，保留真正属于定义的内容。

## 原六条 missing_field_or_event 的最终分流

| 原 finding | 本轮结论 | 原标签不能直接证明什么 |
| --- | --- | --- |
| template_gdn_prefill F03 | 外部身份/写集需短而统一的定义；暂不要求新字段 | 没有 alias 字段，不等于大量文字无法压缩 |
| extract_gdn F16 | 跨调用物理存储与选择状态的范围决策 | 不能把 retention 误读成只支持单次调用，也不能把全部 cache 实现都当核心 |
| extract_mla F18 | **纳入外部供给就绪的结构候选** | 缺边界端点，不等于已排除共享边界约定或需要完整 host 计算图 |
| extract_sparse F05 | **纳入 caller fork/join 的结构候选** | 不能用额外 GPU 内部等待改变原重叠关系；是否需要逐实例端点仍与共享约定比较 |

## 为什么 issue 通道没有自动拦住这些问题

规范本来就给了合规出口：[DOC5:96](rules/schema_docs/5.design.tile_pipeline.md:96)要求动作语义写进 verb，[DOC4:380](rules/schema_docs/4.design.work_schedule.md:380)允许说明字符串承载结构未表达的规则，[DOC1:41](rules/schema_docs/1.contract.algorithm_requirement.md:41)要求外部原地关系写进 meaning。

[REVIEW:69](rules/schema_extract/REVIEW.md:69)在现有规则不适配、缺失或冲突时提框架候选；[REVIEW:20–22](rules/schema_extract/REVIEW.md:20)同时要求保留必要动作语义，且不要求自然语言变成可执行代码。于是“能写进合法正文”并不必然触发候选。**没有 issue 不能证明结构完备，也不能据此断言 agent 故意绕过规范。**

建议补充的触发条件是：**一个身份、读写作用、参与者或时序事实决定核心设计，其唯一定义却依赖开放正文时，先检查现有结构和共用语义；两者都不能承载，就列出删除反例与缺少的最小关系。** 重复出现的作用模式提出共用定义建议，真正的关系缺口才提出结构候选；数学公式本身、合理的简短算法/原语定义不因此成为违规或阻塞项。这项检查可由 worker、reviewer 或未来精简角色执行，不能只让精简角色负责删字。

## 下一步应改什么

1. **DOC0/4：先设计最小调用边界。** 用 Sparse 和 MLA 两份完整同源样例比较“统一边界约定”与“可引用端点”，要求保住等待位置、可见性与重叠，不增加原来没有的等待。
2. **DOC5/6：同时收束动作定义。** 从组合输入、capture 和读取退休选少量共用模式，实例只写差异与绑定。比较总表示长度时计入新增规范定义，不能只看 YAML 变短。
3. **DOC1：提供短而唯一的外部副作用写法。** 先解决重复和职责，不立即扩 ABI 字段。
