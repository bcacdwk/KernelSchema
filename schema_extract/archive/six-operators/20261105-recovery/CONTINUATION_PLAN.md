# 六算子后续组织与派发方式

> 归档说明：六算子恢复阶段的历史记录。正文中的运行状态、预算、命令和分工对应记录时点，不作为新的执行授权。 [归档索引](../../README.md)。

2026-11-05。依据[处置评估](README.md)、两个全新上下文 xhigh 子代理的[运行控制建议](organization_control.md)和[算子工作建议](organization_content.md)，Supervisor 采用以下组织方式。本页是派发方案，本轮没有启动真实提取、清算、迁移或桥接开发。

**主代理保持唯一全局 Supervisor；每个独立工作包使用新的 xhigh 子代理；同时最多推进两个工作包。** 每包通常只涉及一个算子的一个明确范围，共享桥接单列工程包。任务有可验收结果即结束会话，空位补下一项，不必等同批全部结束。GDN 已交付，不占持续工作位置。

| 角色 | 负责事项 | 交付依据 |
| --- | --- | --- |
| 主代理 / 全局 Supervisor | 任务 prompt、实际运行控制命令、固定来源与目标版本、预算、hold、恢复/重启选择、输出目录、验收和用户沟通 | 核对实际产物、差异、权威状态及必要证据；共享控制有一个决策入口 |
| 新的任务子代理 | 一个算子/范围的源码核定、维护计划、修订准备；或指定隔离目录中的桥接工程 | 明确产物路径、摘要、具体结论、验证、剩余问题和下一步；不直接写运行状态、批准或历史发布目录 |
| 每个 run 的 Runner 及其 worker/reviewer | Runner 持唯一写锁派发、检查、合入和发布；worker 写许可产物；reviewer 独立审当前有效全文 | 正式阶段回执、检查与 P6；外层代理报告不能代替批准，worker/reviewer 不再委派代理 |

两个工作包是外层调度约定，不是两个模型调用的上限。当前和三个旧 Runner 的 P5 都会为全部就绪节点派发调用，没有现成固定并发槽位（`tools/stages.py:182`、`tools/runner.py:1275,1315`）。初期只放行一条真实提取 run，另一工作包用于准备或工程；这仍不限制该 run 内 P5 的调用数。后续根据实际服务和调用占用决定是否开放第二条 run。若需要硬并发上限，另行明确调度维护范围，不虚构 CLI 参数，也不拿 resume --scope 当限流器。

首先派发两个具体工作包：

| 工作包 | 输入与许可范围 | 完成条件 |
| --- | --- | --- |
| 旧语义桥接候选及离线保稿验证 | 三条当前 run 的原锁/冻结规则、2.4.1 实际基线、维护协议；在隔离目录开发与定向验证。FMHA 的 29 个有效节点、14 个有写作历史节点作为重点保稿样本；不控制真实 run | 交付候选目录与摘要、逐旧基线完整差异、原稿/批准依赖/预算保留证据、request/drain/prepare/apply 验证和已知限制。达到“可独立评审”，不自行认证兼容 |
| Sparse P1 任务域核定 | 最新 8f1be03a… run 的 source lock、metadata/scope、input/reference、当前 root；只核定两个 scale 与 sinks 的有效域，不改运行稿 | 逐项说明是否有材料支持比构造器更宽的接口，给证据、保留或纠正结论、准确字段及全树影响。若材料不足，说明尚缺的具体定义；本结果供 Supervisor 制定维护计划，不作为 P1 批准 |

选择先核定 Sparse，是因为它可能影响整树的共同前提；MLA/GEMM 已有明确、局部的修订问题，不需要再做一轮全面诊断。Sparse 核定结束后，其位置立即依次交给新的 MLA、GEMM 修订准备代理，不等待桥接完成。准备只做固定来源描述、少量问题规格、目标路径和正式任务卡；准备就绪再创建 run，避免排队等待先消耗墙钟。

桥接工程交件后，该位置换一个全新代理独立审阅完整差异和验证证据。共用的是实现与验证方法，兼容记录必须逐 run、逐冻结基线绑定，不能一张证明覆盖 2.2.7/2.2.9/2.2.10。兼容报告的最终 basis 使用旧调用结算后的实际 checkpoint；候选目标进入评审后保持固定，不边改边应用。桥接若无法保持原语义，就记录不兼容范围和实际代价，由 Supervisor 调整路线，不反复扩大成通用迁移平台。

正式推进顺序：

1. **MLA 是优先启动的小型新任务。** 从固定原来源准备新输出目录，直接按当前 extract 流程交付；随后处理 GEMM。两项内容只需有限修正，但工具没有已发布 v2 的 seed/import/原地 revise 通道，因此不先人工完成一次全文修补批准，再重复跑新 extract。旧稿是阅读参考，不能承诺机械继承；新结果仍须当前 P6。小任务实际成功只能证明当次服务及相应交付流程，不能证明旧 run 迁移。
2. **旧任务的首次正式迁移优先 Sparse。** 前提是任务域已核定、旧调用已结清、对应旧语义桥接已独立认证。先复核共享前提与计划，再按父依赖完成八节点任务。FMHA 则先完成更充分的离线保稿验证，随后采用其单独认证的桥接迁移，保护 29 个有效节点和各自草稿。这细化了上一轮“优先 FMHA 验证保稿通路”的建议：优先用于验证资产保留能力，真实迁移先从较小任务开始。
3. **MoE 在桥接成本可判断、前一项释放资源后接入。** 保留默认 scope、P1 和完整 root 候选，先完成 P2–P4 的默认可达计划。不能把旧 60 节点套作当前计划，也不预先承诺新节点数。桥接适用则接续；明确不划算时再选择 full-restart，并保留其从 P1 重审、预算不重置的含义。
4. **GDN 继续使用 2.2.7 六节点正式版本。** 不恢复旧 run，也不为了调度对称新增一次提取。

正式维护对每个 scope 分别选择 keep/review/patch/reextract：完整候选先审，有据问题才改；残稿保持自己的 raw 并继续写作。P1 或父节点变化先处理影响范围，再进入后代；换父走显式迁移。外层任务完成不等于算子完成，最终状态以当前完整计划、P6 及实际发布/export 为准。已发布的小修与未完成 run 的连续修订分别走其合法入口。

共享控制由主代理逐步提交并核对结果：旧调用清算、全局 hold 与各 run 的暂停、实际 checkpoint、升级、语义修订、预算追加和启动。同一 run 的这些变更不重叠；全局 hold 释放前落实其他任务的暂停并检查控制结果，不因只想启动 MLA 而放行旧批次。历史 HTTP 403 配额错误尚不能证明现在仍失败或已恢复；不另发探测调用，用服务信息与首个实际任务的结果判断，持续同类错误时不批量重试。模型/配置变更也不能通过不存在的 resume 参数完成。

给每个新代理的输入卡只包含：本次目标与 run/lineage，source/rules/executor 身份和路径，checkpoint、当前阶段及精确 scope，必要问题/源码锚点，可写位置，交付物、验收和停止条件。输出卡包含：结论及证据、产物路径/摘要、实际修改与验证、未决事项、下一动作及启动条件。后继代理读取这张卡和必要文件，不复制整段聊天；正式 reviewer 仍由 Runner 按协议清除历史批准暗示，接收当前规范、产物、源码及本轮许可的问题范围。

每次独立委派换新代理；Runner 内同一正式写作步骤的连续产出和 checkpoint 恢复仍遵循既定角色协议，不因换外层代理重置次数、旧批准或预算。阶段、来源、父依赖或许可范围变化时，重新限定工作包；不能仅靠换代理扩大修改范围。主代理负责核对关键证据和异常，不再重复已经完成的六算子全面审计。

实际运行后的调度调整：MLA 已交付、GEMM/Sparse 稳定运行后，Supervisor 允许在两条实际提取之外增加一个有限的只读计划评估包，提前准备 FMHA 后续动作，以减少空槽后的等待。该代理不启动模型提取、不改运行状态、不取得全局控制；真实 Runner 仍最多两条，独立任务仍使用新 xhigh 会话。此调整只影响就绪材料准备，不改变原 source/config、审批或预算规则。
