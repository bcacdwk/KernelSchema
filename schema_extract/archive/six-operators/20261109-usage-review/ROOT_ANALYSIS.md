# 单个 root 的成本与流程复盘

这次排除 P5 分支数量、P4 整树计划和 P6 整树终审，直接查看 root.yaml。按本轮用户提供的 gpt-6-astra 单价、30 分钟缓存写入情景，近期一个 **P3 root Design 写作—首次批准闭环**通常约 **$13–16、20–29 分钟 CLI**；GDN 有一次语义退修，为 **$24.79、38.8 分钟**。加上所选 P1 Contract 工作后，每 root 为 **$19.05–31.08、32.0–52.4 分钟 CLI**。

主要开销来自多轮模型交互中的上下文读写。单 root 的 Runner 处理在已记录数据中较小；Reviewer 的占比本身没有证明其工作多余，但首审遗漏后又整轮回修，以及跨调用缓存首轮未命中，存在具体改进线索。

## 怎样统一比较单位

不能按日志的 `node=root` 直接求和：P2/P4/P6 也使用这个标签，但承担路径划分或整树工作。

- **核心 P3**：每算子取最近的非 maintenance P3 `run＋规则版本`，从本组首条尝试到第一个实际被 Runner 接收的 Reviewer approve。期间的失败、提案被拒、语义退修都计入。首次批准后的重开单列。
- **P1 Contract**：按同样方法选最近的非 maintenance P1，单列费用，便于看到完整 root 的必要前提。P1 和 P3 可能跨规则版本；不能把二者相加描述成一次从空文件开始的实验。
- **P2**：选 root 代表路径及 dispatch 草案，是前置工作，但混有此次暂不讨论的划分方法论，因此不并入主表。P4/P5/P6、子代理与 Supervisor 同样排除。
- **不是六算子都在 2.5.0 从零提取的对照实验**：GDN/FMHA 最近普通 root 写作仍是 2.2.7，Sparse 的 2.5.0 root 是有限维护，已另列；MoE/Sparse 的所选 P1 Worker 直接复核了已有字节。一些 P3 也从旧稿开始。统一的是单节点阶段闭环，不是源码复杂度或全新稿程度。文末另列六算子同为 2.2.2 的对照口径。

调用 token、缓存与价格沿用[总消耗复盘](README.md)的逐会话去重结果，输出已含 reasoning，缓存读/写已包含在输入中。以下全部是日志记录折算，不是账单。

## 公共上下文复用：有事实，但还不能确定底层原因

所选 P3 尝试中，有正增量的 **15 次调用首个用量响应，cached_input_tokens 全部为 0**；包含新会话和同会话续跑。它们的首轮缓存写入共 782,375 token，按给定单价约 $9.78。整个 P3 样本的输入缓存读取比例仍达 93.5%，因此整体高命中率不能证明跨 Worker/Reviewer 或跨次恢复已经有效复用公共前缀。

具体例子：

- MLA 首轮 Worker、Reviewer 各有 9 个包含规范读取的工具调用，涉及相同的 8 个规范路径。两边各出现两次输出截断；Reviewer 首先合读公共约定、数学改写、Contract 与模板文档，出现截断后又单独读取数学改写。这是可直接观察的重复材料加载和阅读往返。
- MoE root 的 Worker/Reviewer 分别使用 32/31 个工具调用，首次输入分别约 19.5k/21.6k，首轮缓存读均为零；整个闭环有 65 次模型响应、8.57M 累计输入。成本没有依赖 154 个派生节点才能出现。
- 同会话续修也可能重新冷读大量历史：GDN 首次退修后 Worker 的首轮输入 221,359 token、Reviewer 的首轮输入 203,580 token，缓存读均为零；MLA 后续回修两边首轮约 195k/193k，仍为零。

原始记录足以说明这些调用没有报告跨次首轮缓存读取，但不能确定原因是缓存键、TTL、网关行为、请求前缀变化还是调度。不能直接承诺“固定前缀就能省掉全部费用”。可优先核对冻结规范和源码材料能否采用稳定内容与定位结构复用，保留 Reviewer 独立判断，而不把 Worker 的结论当成审阅结论。

工具统计按实际工具输入中出现的路径/命令识别；一个调用可能混读规范和源码。`root_trace_index.json` 的输出字符量不是精确规范 token 量，未用于给单个文档分摊美元费用。

## Runner 校验：单 root 暂无小时级开销证据

不只看所选样本，重构以来所有 **127 条 P1/P3 root 尝试**，CLI 合计 **13.82 小时**，Runner 已记处理合计仅 **7.18 分钟**，约占 CLI＋处理的 **0.86%**。这和上一份全流程报告的 15.4 小时处理时间是不同范围。

近期首次 P3 样本中，GDN/MLA/GEMM/Sparse/FMHA 的 Worker＋Reviewer 处理为 3–16 秒，MoE 为 103 秒。MoE 的执行绑定/历史核验值得单独定位，但记录不能把这 103 秒全部归因于 YAML 检查函数。Runner 的处理桶还包含回执核对、输入/checkpoint 核对和状态提交；派发前准备、模型内部工具时间未完全拆项，因此这不是完整 CPU profile。

重复运行 checker 确实存在：MLA 首次 P3 Worker 在写作过程中调用 4 次 checker，Reviewer 又调用 1 次，Runner 接收两边结果时各调用一次，共观察到 7 次。Worker 中间多次检查伴随真实修改，不能全部称为冗余；Reviewer 对不变稿的自检和 Runner 自动检查存在重复，但从当前 root 数据看，省去这部分不足以解释几十分钟和数百万输入 token。

## 工具层轻量优化评估

本轮讨论约定：保留 schema 设计和提取阶段的基本方法，暂不处理 dispatch/分支数量；优先评估工具中能明确减少重复输入或机械工作的局部修改。

随后由一个全新上下文的 xhigh 子代理独立评估，再由另一个全新上下文的 xhigh 子代理实现，主代理验收。本轮最终只采纳下面两项输入组织调整，工作树版本为 **2.5.1**；diff、Reviewer 优先和机械检查事实暂缓。独立评估指出，Reviewer 的 revise 在接近既有退修限额时会进入裁决，不能保证简单回到 Worker；因此角色切换没有纳入本补丁。

验收：提取工具的 **97 项离线测试全部通过**；主代理另用六组真实产物和冻结输入，对照旧/新提示生成器，确认差异仅在调度投影与文档清单，来源、身份、权限、证据要求、预算和传入对象不变。补齐了一处原有测试 mock 缺少的 rules.files，原语义边界断言与 runtime 生产逻辑保持原样。AGENTS.md、25 份 run 状态和 Supervisor 记录的哈希未变；未升级旧 run 或恢复提取。这里只验证输入结构与边界，没有新的模型费用/速度实测。

### 已实施：裁剪 root 提示中的调度历史

修改前，`tools/prompts.py` 默认把 `relevant_nodes` 设为所有节点，仅在 P5 收窄。P1/P3 的 worker 因而可能收到全量 plan、node_approvals、reviewed_artifacts，以及 reopening 中再次嵌入的 previous_plan。这些主要供 Runner/P4 调度使用，root 写作已由当前 root、dispatch、问题和固定证据界定。

2.5.1 只对 P1/P3 投影模型输入：保留当前 root 身份、授权、nonce、实际问题及证据、必要的前置材料；保留当前 dispatch 可读入口，将历史计划和其他节点批准留在 Runner 账目。P1 的全算子共享 Contract 来源范围没有收窄。Reviewer 继续不接收旧批准结论。不改变真实计划、任何节点或其批准状态。

对历史 prompt 作一次离线字段投影，保留其他正文不变：

| 提示样本 | 原始字节 | 投影后字节 | 减少 |
| --- | ---: | ---: | ---: |
| FMHA P3 回修 Worker | 118,575 | 32,146 | 72.9% |
| FMHA P3 回修 Reviewer | 55,961 | 26,967 | 51.8% |
| GEMM P3 回修 Worker | 56,713 | 43,745 | 22.9% |
| MLA P3 回修 Worker | 32,845 | 32,005 | 2.6% |

这是输入字节的确定性减少，不是实测美元或延迟的节省比例。正常首稿原本没有大块历史，其收益较小。实施时必须确认保留下来的来源/证据/权限字段完整；仅投影提示，不改冻结历史账目。

### 已实施：标明已嵌入文档，消除重复读取要求

`tools/prompts.py` 已嵌入当前阶段页，Reviewer 还嵌入完整 `schema_extract/REVIEW.md`；`tools/stages.py:read_specs()` 又把 REVIEW.md 列入待读材料。2.5.1 通过 provided_documents 明确本次已提供全文的路径，提示中的 read_specs 只列尚未提供的材料；stages.read_specs 的完整阅读要求保持原样。Worker 没有被标记为已收到 REVIEW.md；P5 仍需读取外部 03_root.md。依据、条款和审阅要求保留完整，不生成另一套摘要规范。

局部回修附加有界 diff 和变更字段的候选暂缓：已有问题与产物锚点，额外定位收益尚未验证，而给普通 Reviewer 提供前后稿会改变目前不提供旧版本历史的输入约定。此次未实现。

### 暂缓：仅对上游变化后的 P3 复核考虑 Reviewer 优先

普通阶段切换在 `tools/stages.py:_approve()` 中固定将 P2 后继设为 P3 worker；`tools/runner.py:_begin_reopen()` 会使目标及后续阶段失效。因此 FMHA 的 P1 修复即使没有改变 Design，仍再次经过 P3 Worker→Reviewer。

可评估的最窄例外是：当前不是首次 P3，也不是问题直接要求修复 P3；存在可核验的旧 P3 完整批准；规则、来源和 root 代表路径未变；Design/Realization 的旧稿与当前稿一致；只是上游 Contract 修改触发后继复核。此时先给 Reviewer 当前完整稿和当前前提，由其重新作出独立判断；approve 正常推进，revise 再交 Worker。首次创作、直接 P3 修复、正文变化、来源或规则变化、证据不足继续按原路径。

这是小范围的控制流程调整，不能称为纯提示优化。必须覆盖回执、只读权限、候选、generation、计数、预算和旧 run 兼容性测试；不能根据执行结束后“Worker 没改字节”的事实直接推导所有未来 Worker 均可跳过。旧批准只用于 Runner 判定已有完整稿，不能代替新批准或作为 Reviewer 的结论提示。

### 低优先级：单 root 校验与缓存命中

单 root 的已记录处理仅占约 0.86%，暂没有依据新增跨调用校验缓存或调整大范围历史验证。可先明确提供同一稿、同一规则下由 Runner 生成的纯机械检查事实，帮助 Reviewer 避免自行重复运行 checker；不混入旧语义审阅结论，Runner 的接收检查保持有效。

静态材料放前、动态调用身份放后，可以作为缓存命中的小实验，但当前首轮零缓存的原因未确认。不能把提示重排、跨角色会话共用或新建缓存系统当作已证明的修复。尤其不共用 Worker/Reviewer 推理会话，不因历史批准、文本未变或 checker 成功自动批准当前语义。
