# Design 整区派生引用：实施设计

> 归档说明：已落地于 2.5.0 的设计与实施记录；现行语言和接口以公共规范及工具协议为准。 [归档索引](../README.md)。

日期：2026-11-05。实现版本：**2.5.0**，已完成代码、文档与整合验证。本文记录最终语言、公共接口和工作流契约；[聚合问题](../../issues/archive/extract_workflow/design-region-derivation.json)已按本范围解决。[问题记录](../../issues/archive/DESIGN_REGION_DERIVATION.md)保留 2.4.1 调查基线及 `DRD-01`—`DRD-10` 编号。正式 semantic revision 采用能力已验证，真实历史 run 和已发布产物未自动迁移或转换。

## 1. 决策与问题对应

| 问题 | 本次决定 | 主要落点 |
| --- | --- | --- |
| DRD-01 | 引用内容在使用节点上下文中绑定，三区域组合仍完整检查；父 `when` 不构成子前提 | 第 2、3、5 节 |
| DRD-02 | 仅直接父、同名整区、显式引用，可传递；root 全部本地；realization 本地 | 第 2 节 |
| DRD-03 | 统一 raw/effective API、真实来源诊断、完整来源身份与防漂移 | 第 3、4 节 |
| DRD-04 | 首次无稿生成引用；已有稿保留；内容来源与审批依赖分别表达 | 第 3、5、8 节 |
| DRD-05 | provider 审定义，子节点审有效绑定与适用性；当前来源图驱动证据 | 第 5 节 |
| DRD-06 | 换父留下显式迁移记录，由 worker 合法改稿并独立重审 | 第 6 节 |
| DRD-07 | 普通 P5 可重开非 root 实际 provider；独立状态转换，不借全局 reopen | 第 7、8 节 |
| DRD-08 | plan 保持七字段，ID 稳定，difference 比较有效 Design，选择条件独立 | 第 2、5 节 |
| DRD-09 | 新语义随 2.5.0 冻结；旧 run 沿原规则恢复，采用新语义走正式修订 | 第 9 节 |
| DRD-10 | 先保留真实变体，再选择共享表达；不承诺节点数或文本压缩比 | 第 2、5、10 节 |

`provider` 是某区域最终保存本地完整定义的节点；`consumer` 是当前使用该区域的节点。两者可以相同。`raw` 指保存的 YAML，`effective` 指仅展开 Design 引用后的任务视图。有效视图不等于已经完成结构、关系或人工适用性验证。

## 2. 语言边界

每个节点的 `design.math_reshape`、`design.work_schedule`、`design.tile_pipeline` 必须分别采用以下二选一：现有完整本地映射，或**恰好只有一个字段**的 `{from_parent: <直接父 ID>}`。`from_parent` 与现有对象 `ref:`、符号 `bind:` 含义不同；同一区域不能混用引用和本地字段。

```yaml
meta_data:
  # 其余 metadata 按现行要求填写
  dispatch:
    id: child
    parent: parent_node
    when: "本节点独立的选择条件"
design:
  math_reshape: {from_parent: parent_node}
  work_schedule: {from_parent: parent_node}
  tile_pipeline: {from_parent: parent_node}
```

引用 ID 必须与该文件 **raw** `meta_data.dispatch.parent` 一致，不能取 plan 的新 parent 偷换原文含义。普通 schema 已有的“省略 parent 时默认 root”规则可以保留，按该默认值核对引用；extract 始终显式写 parent。父节点同名区域若也引用其父，则沿该链找到本地 provider。root 的三区域必须本地定义。

不允许缺省继承、字段覆盖、patch、指定非直接祖先、兄弟引用、跨目录引用或别名库。更换一部分内容时，worker 应从有效视图取出**整个区域**落地本地，再修改；不能在引用旁附加覆盖字段。三区域都引用可以合法，但仍须有 P4 已确认的真实设计、实现或选择依据，不能制造冗余 dispatch。

引入内容在子节点的 root Contract、符号、参数、调度 phase/worker、资源和事件环境中解析。例如继承的数学 `bind` 可以绑定子节点本地调度参数；继承 pipeline 必须与子节点当前的 launch、handoff、role、资源及事件闭合。引用不携带父节点 `when`、`meta_data`、版本或 `realization`；这些全部由当前节点负责。父关系表示设计来源，不表示选择条件包含关系，各 `when` 仍在完整 root Contract 域内独立求值。

## 3. 统一解析 API 与来源身份

在 `schema_template/tools/design_resolution.py` 实现解析与来源模型，由 `schema.py` 暴露公共入口。`yaml_source.load/loads` 和 extract `load_yaml` 继续只读 raw，不隐式展开、不写回文件。

### 3.1 返回模型

| 名称 | 契约 |
| --- | --- |
| `RegionOrigin(provider, chain)` | provider 为节点 ID；chain 按使用者到本地 provider 排列并包含两端。本地区域为 `[node]`，传递引用如 `[child, parent, provider]` |
| `ResolvedTask.raw_task` | 原始任务，节点 ID → 原始文档值 |
| `ResolvedTask.effective_task` | 节点 ID → 展开三区域后的文档值；保留各节点本地 metadata/realization，root 仍是任务 Contract 的保存处 |
| `ResolvedTask.origins[node][region]` | 三区域各自的 `RegionOrigin` |
| `ResolvedTask.dependency_nodes[node]` | root、自身及该节点三区域实际引用的所有中间节点与 provider 的去重闭包 |
| `ResolvedTask.source_files` | 节点 ID → 实际来源 `Path`，保留 `.yaml`/`.yml` 后缀 |
| `ResolvedTask.source_hashes` | 节点 ID → raw 文件字节 SHA256 |
| `ResolvedTask.documents` | 节点 ID → 原始 `yaml_source.Document`，用于真实位置与原始值查询 |
| `source_manifest(node)` | 从该节点来源闭包投影得到的“任务目录相对文件名 → raw SHA256”映射 |
| `effective_identity(node)` | 以下规范化来源身份的 SHA256；不承诺语义等价 |

`effective_identity` 对以下内容作确定性序列化并散列：`format: kernel_schema.design_resolution.v1`、节点 ID、按文件名排序的 `source_manifest(node)`、按区域名规范化的 provider/chain。绝对目录名不进入身份。同一来源字节或链发生变化，即使展开值恰好相同，也形成不同身份；子 raw 未变而 provider 改变时身份同样变化。序列化只涉及字符串与来源结构，不用浮点数编码 Design。

内容来源闭包与审批依赖用途不同：一个全部本地的子节点仍需 root 和自己，但没有因未引用而被纳入内容来源的中间祖先；审批、调用依赖及失效继续保守使用**全部祖先文件摘要**。不能拿较小的来源闭包放松现有审批依赖。

### 3.2 入口与验证次序

| 入口 | 行为与返回 |
| --- | --- |
| `schema.resolve_directory(directory)` | 返回 `ResolvedTask`；只核对可展开包络、文件/节点身份、父链、区域引用及环，不运行完整字段与关联检查 |
| `schema.validate_resolved_file(filename, *, notices=None, source_hashes=None, skip_hardware=False)` | 完整检查并返回 `(directory, ResolvedTask)`；沿用指定文件所在目录的整任务检查语义 |
| `schema.validate_file(...)` | 保持 `(directory, task)` 旧形状，task 改为 `effective_task` |
| `schema.validate_directory(...)` | 保持 task 旧形状，返回 `effective_task` |
| `schema.validate_standalone_file(...)` | 继续完整检查单文档；交付文档必须所有区域本地且自身带 Contract，无兄弟文件依赖 |

完整检查顺序为：raw 结构（区域允许“完整本地或精确引用”）→ 父/引用目标与环 → effective 关联检查。继承部分在 consumer 的环境中执行原有跨区规则，硬件检查策略保持现有约定。`source_hashes` 输出参数继续按节点 ID 返回读取的 raw 摘要，不能改成有效身份以免破坏旧调用者。

只解析入口须容忍尚未填写的 `when` 和未完成的本地区域正文，使首稿、普通改稿和查看有效内容可用；容忍不等于批准缺失结构。身份矛盾、非法引用或引用/父链环仍须报错，不能猜测目标或退回复制。完整检查继续拒绝未完成稿。

父链检测与引用解析使用迭代遍历；读取、provider 查找及中间展开可在**一次调用内**缓存。最终 effective 各节点之间，以及 effective 与 raw 之间均不能共享可变对象；修改一个视图不能污染其他节点。不要增加跨调用展开缓存。

沿用 `CapacityError`/工具容量错误（exit 2），不能把容量耗尽报告成 schema 非法。总展开预算常量为 `design_resolution.MAX_RESOLVED_UNITS = 10_000_000`，累计复制的数据值、来源 chain 条目和依赖闭包记录，在大规模分配前收费。现有 `yaml_source.MAX_EXPANDED_NODES = 100000` 的单文件规则不降低；总预算按其 100 倍设置，测试可降低常量验证边界。深链、扇出共享和正常样例均须覆盖，不能仅限制递归深度或单文件大小。

### 3.3 extract 冻结适配

在 `schema_extract/tools/artifacts.py` 提供 `schema_for(parser_root)` 和 `resolve_workspace(directory, *, parser_root)`。前者从 `parser_for(str(parser_root)).__package__ + ".schema"` 加载相同冻结规则包的公共 schema 模块；后者调用其 `resolve_directory` 并将读取/解析失败转换为现有 extract 错误，返回该包的 `ResolvedTask`。完整检查消费者通过 `schema_for(...).validate_resolved_file` 获取验证结果。

standalone、receipts、prompts 共用该适配，不分别写 resolver，也不能 import 当前仓库的 resolver 替代 run 的冻结版。`parser_root` 来自本次调用的 `resolve_context`/rules lock；不以当前工具安装位置覆盖它。

## 4. 只读视图、诊断与派生产物

### 4.1 有效视图

新增固定 stdout 入口：

```sh
python3 -B schema_template/check_yaml.py --show-effective path/to/node.yaml
```

调用只解析入口，不写文件。成功输出 JSON envelope：`format: kernel_schema.effective_view.v1`、`validation: not_run`、`node`、`effective_yaml`、`origins`、`source_files`、`effective_identity`。这里 `source_files` 是该节点的 `source_manifest`，不是绝对 Path 对象。`effective_yaml` 字符串包含本节点引用展开后的全部 Design、本地 metadata/realization 和 root Contract，未完成的本地字段原样保留；使用保留 Decimal 与标量类型的 YAML 输出并回读核对，避免普通 JSON 数字转换损失精度。成功解析不能打印 `Valid` 或声称已验证。

worker 可以据此落地一个完整区；该视图及其虚拟行号不能作为源码或产物证据。证据必须回到实际 raw 文件。严格 standalone 仍另走完整检查、输出全部 local 的独立文档并单独验证，不能以此只读入口替代交付验证。

### 4.2 诊断和输出

effective 规则错误保留 consumer 字段路径与组合上下文。若字段来自继承区域，用 provider 的原始文档查询真实行列和值，同时展示 consumer 的引用位置和完整 chain；缺失字段也不能伪造一个 consumer 行号。非法 `from_parent`、父身份或引用形状错误直接定位 raw 出错处。诊断的定位转译由公共来源模型支持，不改写原始 `Document.positions`。

`pipeline_graph.analyze` 直接消费 effective 节点。`GraphOutput` 继续保留旧 `source`、`source_sha256` 所有权字段，并新增该节点完整 source manifest、effective identity、origins。生成前和原子发布前均复查 manifest **所有文件**；任一中间引用或 provider 漂移均拒绝发布，不能只检查 child SHA。

standalone 的 `.source.json` 升级为 `schema_extract.standalone.v2`，记录同样的来源闭包、origins、有效身份和交付文件摘要。生成前与发布前均复查全部来源；输出仍位于任务目录外，保留现有原子发布与相同内容复用约束。导出的文档离开原目录后必须能独立读和检查。旧 PNG、旧来源回执和历史产物不批量重写；原始任务树与 standalone 是两种分开发布的产物。

## 5. P2/P4 规划、P5 写作与审阅

P2/P4 先识别真实 workload、设计、实现及选择分支，再决定哪些定义适合共享。plan 固定为 `id/file/parent/workload/difference/selection/evidence` 七字段，不增加引用策略字段。`difference` 比较有效 Design，必要时说明 Design 相同而实现/选择不同的事实依据，不能仅写“改为引用”。ID 随真实路径稳定，不因 ref/local 转换、参数表达或微实现修订改名；parent 必须设计接近且有证据，不自动换父追求压缩。

`Store.start_node` 首次确无任何自己的稿件时，从父的 metadata 模板构造本节点：移除 Contract、父 realization，设置自己的版本 1、显式 id/parent、空 `when`，把三区域写成指向直接父的引用。对于任何已有草稿、重试稿、已批准稿或可恢复稿，完整保留自己的 raw，只刷新当前只读祖先，不能自动改成引用或改为 local。raw 修改按现有 `_versions` 规则增加版本；依赖变化导致的有效身份变化不伪造 child raw 版本增长。

审阅职责如下：

| 范围 | 必须审阅的内容 |
| --- | --- |
| provider 的本地定义 | 本区域的源码/规范推导及其在 provider 中的正确性 |
| 子节点 `differences` | 相对直接父有效 Design 的真实变化和实现/选择依据 |
| 子节点 `inherited_design` | 共享内容在本次选择域、参数与名称绑定、跨区接口和 realization 下成立 |
| 子节点 `walkthrough` | 使用完整有效 Design，覆盖输入到输出、launch/producer/事件、handoff 及资源闭合 |
| P6 | 当前共有定义按文件读一次；逐节点覆盖有效绑定、选择域与局部差异，以及全部待复查范围 |

继续隐藏历史 verdict、批准结论及旧交接；父批准不能证明子节点适用。审阅当前共用定义不要求子节点反复复述相同的通用源码推导，但每次消费的语义环境必须覆盖。

P5 reviewer 的必要产物文件证据为 `source_manifest(child) ∪ source_manifest(direct_parent)`，再并入 root、child、direct parent 的文件。证据还须覆盖中间引用 raw 行与实际 provider 本地定义 raw 行，不能只引用文件名或 effective 输出。P6 仍覆盖最终全部产物。

调用机器元数据使用 `design_resolution`、`provider_reopen_targets`，只从当前提交/调用 workspace 的来源图生成，不从旧批准推断。坏草稿导致解析失败时，普通修稿仍可获得诊断和保守的全祖先文件集合；无法可靠确定的 provider 不进入 targets。最终有效性和 reopen 资格不能由这个降级路径放宽。

## 6. 状态转换一：P4 换父与显式迁移

| 步骤 | 状态与职责 |
| --- | --- |
| 1. 安装新 plan | `install_plan` 比较旧/新 parent；为换父节点记录 `node.identity_migration`：old/new parent、old checkpoint、current plan revision、reason。保留旧 raw、版本、批准历史与旧 checkpoint |
| 2. 失效和排队 | 沿现有 `plan_impact` 使旧树、新树相关后代失效。换父节点必须交 worker 做迁移，即使旧稿曾完整；相关调用由 generation/fence 退休。预算和已用裁决账本保留 |
| 3. 准备 workspace | `start_node` 刷新新祖先，保留自己的 raw。旧 parent/raw refs 可以暂时与新 plan 不符，必须显示迁移诊断。旧 checkpoint 在当前 workspace 外提供只读恢复线索，不把旧祖先添加为额外任务 YAML |
| 4. worker 迁移 | worker 显式修改本节点 parent，并逐区选择指向新直接父，或从旧 checkpoint 的有效视图落地整个 local 区域；保持原版本演进。解析器不得自动 retarget |
| 5. 独立批准 | 按新 plan、新父依赖和新有效身份完成检查与独立 reviewer 批准；此前不能恢复旧批准。新身份获批后才清理迁移标记，历史记录仍保留 |

plan 改动不能授权 P4 修改子 YAML，也不能授权子 worker 改祖先。maintenance 继续使用已封存的精确写范围；若 parent/ref 或落地区域不在范围内，报告缺少的 scope，由既有机制修订范围，不能自动扩权。仅父内容变化而未换父时不创建换父标记，沿既有祖先摘要和保守后代失效重审。

## 7. 状态转换二：普通 P5 修复实际 provider

### 7.1 入口与资格

沿用 reopen 四字段：`{issue_id, target: 'P5:<id>', reason, evidence}`。只对普通 P5 的 normal 调用开放非 root provider 目标；P6、maintenance、adjudicate/signoff 不新增此入口。原有 P1—P4/external 路由保持。树/parent 问题回 P4，代表路径回 P2，root Design/when 回 P3，Contract 回 P1。

`receipt_schema`/proposal schema 动态枚举当前可信 `provider_reopen_targets`，但枚举只作调用约束。`validate_receipt` 必须从**提交 workspace** 重新解析并确认：目标是当前有效、非 root 的严格祖先，且确实是 child 至少一个引用区域的 local provider；目标和引用链仍符合当前 plan/依赖身份。子节点本地已落地的区域不能再据此重开旧 provider。

请求必须有针对该 provider 区域的当前产物锚点，以及固定源码新发现或具体转录/规范纠错证据；现有 `evidence` 继续索引 source evidence，产物锚点由 artifact evidence/issue scope 关联到实际定义区域。无关区域证据或“在子上下文不适用”不足以重开 provider：后者由 child 改本地区域。有效视图的虚拟位置不计证据。

### 7.2 转换与闭环

| 步骤 | 状态与职责 |
| --- | --- |
| 1. 保存请求稿 | 通过现有身份、写范围与证据校验后，先保存请求节点自己的 raw 草稿/合法变更，再启动 provider 修复；不能丢掉请求稿 |
| 2. 建立记录 | Runner 新增独立 `_begin_provider_reopen`；复用 `reopen_requests` 保存扩展记录，目标 `node.provider_reopen` 挂记录 key。记录请求者、provider、区域/chain、来源身份、旧 generation/批准/草稿与原因锚点 |
| 3. 重开 provider | provider `generation += 1`；清当前 approval、approved_generation、approved_sha256、merged，保留 history、draft、last approval，进入 worker。原因和定位锚点必须送到目标 worker |
| 4. 失效后代 | provider 的后代保守 `generation += 1`、清有效审批和 merged。完整稿进入 reviewer，未完成稿进入 worker，均等待当前父批准；换父标记等必须改稿的约束优先。兄弟及 P1—P4 不变 |
| 5. 重审恢复 | provider 新 generation 必须取得新的独立批准，即使修复后字节相同，也不能 restore 旧批准。close 记录绑定这次新批准，再按父先子后的现有调度恢复后代独立审阅 |

不得设置全局 `state.reopening`，该路径会切换上游阶段并阻塞普通 P5 调度。provider 修复使 P6 的当前资格/批准失效，相关 generation/fence 更新，但 P6 启动次数、调用预算、重试、裁决与签收计数不重置。其他 P5 分支仍可按现有条件继续。

循环键绑定 `provider + stable issue_id + 固定 source evidence identities`，证据身份沿用 source ID、path、SHA、行区间，不含 note、quote 或 provider 新版本。相同问题不能通过改文案或 provider 升版再次购买重开机会；失败、已用和关闭记录继续保留。若后续合法 P4 删除目标，修复记录退休并保留历史，不悬挂不可调度目标。

## 8. 在途结果、串行合入与最终整树要求

父变化、换父和 provider 修复均通过现有 generation/fence 使受影响在途结果变为 stale。旧依赖下的稿件不能直接采用，旧 generation 的批准也不能恢复。首版不新增自动 late 候选 checkpoint；保留原 attempt/workspace 和明确恢复线索，当前 worker 可在新依赖与合法写范围下显式采用其中内容，再走正常版本和审阅。

P5 串行合入保留完整 raw merged 树，仍只允许替换候选节点文件。为避免被失效后代的旧 raw/ref 卡住，完整 schema 检查在**独立受控临时目录**运行，集合为“当前有效节点 + 本次候选 + 它们的全部祖先”，按当前 plan 取闭包并记录本次检查集合及文件摘要。临时目录不在 worker workspace，不产生额外任务 YAML；完整 merged 树仍保留计划文件集合与所有旧稿。

maintenance 的候选父节点若与其已批准 raw SHA 不同，其后代在本次检查中已使用不同依赖，须在取闭包前排除并记录为 `superseded_dependents`；不能等到批准后的状态失效才排除，否则旧子绑定会阻塞父修复。父候选批准后，后代通过统一失效逻辑增加 generation、保稿并重新排队，P6 当前资格同步失效。检查记录包含 `checked_nodes`、`checked_files` 和被排除的后代，完整 merged 树仍保留全部文件。

只有本次候选和当前有效集合获得这次检查的有效性结论；尚待换父/重审的旧子稿继续无效，其旧 parent/ref 不能阻塞无关候选，也不能因为保留在 merged 树中被算作已通过。串行合入前继续核对候选固定依赖与最新祖先，不能用子集检查绕过写权限、计划身份或依赖漂移。

上述 P5 检查闭包同时用于普通流程和 maintenance。P6、ready 和 publication 始终要求**整树完整有效**。P6 保持 `revision_scope`、`affected_nodes`、`pending_rechecks` 与独立审阅/签收；来源变化按保守后代关系加入复查，不增加 P5 target。P6 发现 parent 需要改变仍回 P4，不能在字段补丁中偷偷换父。

## 9. 版本、冻结与发布边界

2.5.0 同时发布语言文档、检查器/解析器、视图/图/standalone、阶段审阅说明与 extract 状态/回执工具。旧全 inline YAML 仍合法，不做强制转换。raw SHA/version、来源有效身份、审批 generation 和规则 revision 各有用途，不能相互替代。

旧 frozen run 正常恢复时继续使用原规则与执行语义，不自动获得引用或 provider reopen 能力。采用本设计必须经过已有 semantic revision/maintenance 及对应适用性审阅；旧 checkpoints、receipts、审批历史和预算原样保留。不能把新语言和审批含义伪装为 compatible runtime 修复，也不能由当前仓库模块旁路冻结规则解释旧输入。

`design_region_derivation.v1` 能力标识纳入冻结执行器身份；compatible runtime 登记和恢复都拒绝跨越此语义边界。显式为 standalone 选择尚无公共 resolver API 的旧规则树时，调用该规则树自己的完整 exporter 和检查器，保留其 v1 来源回执；不将当前 resolver 或 writer 混入旧导出，也拒绝缺失或不一致的旧 exporter。

首次实施不迁移真实历史 run，不自动去重已有算子树，不批量重写 PNG/standalone。最终发布原始引用树，standalone 按需要单独生成并带 v2 来源回执。

验证集中于四条可复现路径，并补充所涉及模块现有检查；无需为每个段落再建一份验收账本：

1. **引用及全部消费者。** root → provider → 中间引用 → child，child 更改本地参数使继承区在子环境绑定；完整检查、真实 provider/child 诊断、effective view、图和 standalone 使用相同有效 Design/来源。覆盖 local 与传递引用、精确引用形状拒绝、环、无别名、总容量及 Decimal 回读；生成中更改中间引用/provider 必须拒绝发布，standalone 移离原目录仍可完整检查。

3. **provider 修复。** 普通 P5 从当前链请求实际非 root provider，以定义区域产物锚点和固定源码/纠错证据通过动态 schema 与提交重算；请求稿保存、provider worker 获得原因、新审批关闭记录、后代顺序恢复。验证兄弟和 P1—P4 不动、P6 资格失效而计数保留、同问题重复请求/伪造目标/无关区域/P6 或 maintenance 请求均拒绝；字节相同不能恢复旧批准。
4. **冻结规则与正式采用。** 用旧冻结上下文恢复 inline run，确认仍走旧语义；再经正式 semantic revision 采用 2.5.0，确认 schema、prompts、receipt、standalone 都来自同一 rules root。旧 checkpoint/receipt/预算不变，新语义不能经当前 repo import 或 compatible runtime 偷渡，原始树与 standalone 分开发布。
