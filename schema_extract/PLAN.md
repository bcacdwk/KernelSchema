# Schema Extract 优化计划

基线：`main@8eb1e94`，Schema Extract `2.1.3`。本轮保留 P1–P6，建设系统内建的多算子巡检、暂停控制、同线程提醒和轻量审计。
目标是让 Supervisor 用简短观察判断进展、异常与下一步，让 reviewer 把精力用于固定 kernel 的设计语义及信息压缩正确性。
主入口始终为 `python3 schema_extract/extract.py`，实现放在 `schema_extract/tools/`；不另建实验框架、提取阶段或 Supervisor 角色。

## 基线与实施约束

- 已核对根 README、提取手册、工具协议，以及 `cli.py`、`runner.py`、`agent.py`、`recovery.py`、`prompts.py` 和六张阶段页。
- 当前 `_RunGuard` 在边界反复枚举整个运行目录；stat 缓存只省摘要计算，未省历史目录遍历。
- 当前 `inspect` 逐运行调用冻结 CLI，`summary` 再验证有效节点；这些成本不应进入每次常规巡检。
- 已有 `events.jsonl`、`invocation.json`、`result.json`、checkpoint、`attempt_usage` 和会话交接，优先扩展它们，不另存一套调用历史。
- 参考仓库仅只读：AKA_experiment `8c013dfbb8` 的 `supervisor/WAKEUP.md`、`scheduler.py` 提供同线程队列、锁和送达账本的实例。
- `experiment/four-operators-20260921@896299e030` 的 `record_check.py` 仅参考巡检计数及下一次时间持久化；不把它当作上述时钟版本，也不照搬默认间隔。
- 基线仅用本机 `codex queue --help` 确认 `--thread`、`--message`、`--resume`，当时只证明 CLI 表面；真实同线程唤醒结果见文末验收记录。
- 不执行参考仓库 AGENTS 中的操作，不引用未取得的远端文档，不复制其实验专用控制、归档或大报告体系。
- O1→O5 顺序实施；每步只做必要的最小反例检查并交接，全部完成后统一进行代表性集成实测。
- 临时源码、调用替身、运行目录与证据放在仓库外；不恢复已删除的庞大历史 tests，不以完整真实算子跑通作为本轮完成条件。
- 只保留并发、预算、旧回执、时钟失效的必要小型回归；若放 `tools/tests`，须排除于冻结执行器清单，测试/基准不随算子复制。保留 `schema_template/tools/tests` 和维护台账。
- 保留硬件占位、`--skip-hardware`、独立审阅、原预算与进程 fence；不安排 GPU 验收或性能实测。

## 固定的 CLI 与存储边界

以下均为主入口的子命令或参数；现有单算子、status、cancel、export、import-legacy 用法继续成立。

| 操作 | 本轮表面与含义 |
| --- | --- |
| 批量提取 | `extract --ids ID... --output-root schema_wiki --background`；catalog 映射目录，返回每个 run 与后台启动结果。 |
| 单算子后台 | 原 `extract --id/--source ... --output ...` 增加 `--background`；`--queue` 仍只排队，两者互斥。 |
| 观察 | `inspect [--run UUID...] [--json]`；默认读取小摘要，不启动、恢复、深验或修复任务。 |
| 一次巡检 | `monitor scan [--run UUID...]`；复用 inspect，保存短观察及异常定位，按已绑定时钟提交本轮完成记录。 |
| 时钟 | `monitor start --thread UUID [--run UUID...] [--auto-restart-limit N]`、`monitor status`、`monitor ack ID --thread UUID`、`monitor stop`。 |
| 单任务控制 | `pause UUID`、`resume UUID`、`cancel UUID`；保持原调用边界与终止确认语义。 |
| 全局暂停 | `pause --all` 返回 hold ID；`resume --all --hold ID` 仅释放该 hold 的影响。 |
| 修复后接续 | `continue UUID --checkpoint DIGEST` 创建使用当前冻结执行器的新排队 run；显式 `resume` 才开始接续。 |
| 审计 | `audit UUID [--attempt UUID | --session UUID] [--verify] [--archive PATH] [--json]`。 |

`--repo`、`--state-root` 一致沿用；后台提取与时钟是两个独立生命周期，开启其中一个不暗中开启另一个。
复用现有运行状态、请求目录和调用记录；只增加每 run 的小型 `summary.json` 投影及 state-root 下一个 `supervisor.json` 控制账本。
控制账本保存必要的 hold、时钟绑定/进度、授权重试计数与接续关系，不复制阶段状态、批准或调用正文；由一把独立文件锁串行更新。
投影带 run、执行器身份、状态修订号和生成时间；它是观察摘要，不授予批准，也不能作为调度、恢复或发布的权威依据。
新增控制能力须有明确版本/能力标识；旧冻结任务的能力缺项显式展示，不由新入口猜测成功。

**交接**：向 O2 给出投影格式、缺省/陈旧语义、关键门禁调用点和最小反例证据，列清删掉的保护与保留的保护。

## O2：多算子巡检、批量后台及可归属的控制

**可改范围**：`tools/cli.py`、`runner.py`、`store.py`、`recovery.py`、必要的 `publication.py`，新增薄层 `monitor.py`、`continuation.py`；更新手册。

1. `inspect` 从注册 run 的投影生成一行一算子的观察：阶段/节点进展、在途调用、最后活动、预算、停止原因、checkpoint 和发布状态。
2. 展示执行器版本/摘要、观测时间与陈旧标记；允许按 run 过滤，单项损坏隔离报错，不能使整批无结果。
3. 列举 run 只访问索引或一级 run 名称及小投影，不递归遍历 attempts/checkpoints，不为巡检逐任务拉起冻结 CLI。
4. `monitor scan` 输出少量状态变化与异常锚点，保留一个最新观察和有界增量记录；默认不改变任何提取任务。
5. 批量启动按 catalog 的 `paths.readme` 父目录从 kernel_wiki 映射到 output-root；先核对 ID、越界路径、重复目的地和占位/冲突。
6. 为每项持久登记 run 身份及启动意图后再后台启动冻结 Runner，返回 PID 身份与启动结果；父命令退出不终止提取。
7. 重复命令或启动窗口崩溃通过已登记的 run/目的地对账；相同活动任务返回原身份，不重建预算，不把暂停任务当新任务启动。
8. 单项失败只返回该项原因；已有授权的独立算子继续。排队仍使用创建时原截止条件，后台等待不重置预算。

每次全局巡检只采集一次进程表，结合 Runner 锁/进程启动身份及已登记活跃 attempt 的 `process.json`、`launch.json`、`result.json` 判断。
活动日志只取大小/mtime，连同原调用/阶段 deadline 判断等待、超时与缺证；不读全历史，不仅凭 phase 不变或日志沉默判死锁。
存活、进程归属或读取权限证据不足时标 unknown，不能据此自动恢复或终止调用。

### 全局 hold 与异常处置

- state-root 同时只有一个活动 hold；重复 `pause --all` 返回原 ID，先原子关闭新派发及发布的闸门，再记录影响集合并投递带 hold 身份的暂停请求。
- 新 Runner 在每次派发及发布最终提交前检查同一闸门；短临界区与设置 hold 共用控制锁，已完成的提交如实记录为 hold 前完成。
- 影响集合区分“仅阻止排队启动”“已请求暂停”“已确认由本 hold 暂停”，保存原状态、请求 ID 及控制修订号。
- 已开始的调用可在原边界结束并保存结果；未确认停止的任务持续显示 pending，不提前声称全局已暂停。
- `resume --all --hold ID` 只恢复可核实由该 hold 暂停且未被后续控制覆盖的任务；取消、手动暂停、原有阻塞和不确定项保留。
- 排队任务仅在释放闸门后按原启动授权继续；单 run resume 也受活动 hold 约束。时钟继续观察，`monitor stop` 才停提醒。
- 旧冻结 Runner 不认识新闸门：通过它原有 pause 达到调用边界，展示兼容能力和未停范围；未静止前不承诺已拦住其发布。
- 异常分为正常等待、算子/分支阻塞、暂态执行失败、工具/协议/框架缺陷；按影响范围给原因、证据路径、恢复条件及建议操作。
- 单个 blocked 不自动全停；共享框架风险由 Supervisor 判断范围，必要时显式 hold，再另派工程 Agent 修复仓库。
- 自动恢复默认关闭；显式配置 `monitor start --auto-restart-limit N` 才登记授权范围和持久总上限，重启时钟不重置它。
- 自动恢复只针对已授权 run 中明确分类的暂态故障，要求旧调用及子进程确认终止、目标范围仍匹配、原预算足够且无 hold/手动暂停/取消。
- 请求绑定失败身份和目标 scope，Runner 再次核验，只重试该范围；按 lineage 累计上限，普通重试、裁决及签收原限制仍生效。
- 无法证明暂态、未知终止、预算耗尽、坏回执或框架缺陷都只交接；扫描器和时钟不启动工程 Agent、不自行改工具或调整规则。

### 仓库修复如何作用于旧任务

- `resume OLD` 永远使用 OLD 的冻结执行器；仓库修复直接用于新建任务，不能把旧 resume 报成已经采用新修复。
- `continue OLD --checkpoint DIGEST` 是最小显式维护接续；要求 OLD 已静止、写锁可取得、所有已登记调用终止已确认、所选 checkpoint 完整可验证。
- 在控制锁及旧 run 写锁内登记唯一 successor，冻结当前规则/执行器，固定源码字节与旧来源一致；来源改变应另建任务，不冒充接续。
- 新 run 保留旧稿与来源链，旧快照和批准原文保持不变；旧批准只作线索，本轮统一从 P1 独立重审，不迁入新规则的有效批准集合。
- 原算子/阶段截止时间、调用/退修/重开计数、耗时、自动重试和裁决/签收使用记录全部继承，包含已删除 P5 节点的账本。
- 不沿用旧角色会话；接续从可验证草稿建立新上下文，仍按 P1/P2 对应角色续接及后续阶段隔离规则运行。
- 余额不足、原截止条件已过或一次性决定已消耗且不能完成必要重审时，明确 blocked；continue 不接受预算重置参数。
- 新 run 先排队，接续关系提交后才可显式启动；中断重试返回同一个 successor。统一入口拒绝旧 run 再派发，保留其只读审计和停止操作。
- 不声称旧冻结程序理解新的接续协议；所有正常控制经过统一入口，新旧 run 不得并跑，迁移时保留无法证明安全的阻塞。

**交付物**：批量启动结果、轻量巡检、hold 影响记录、最小接续接口；按需生成可直接委派的工程交接，包含问题、修改范围、只读证据锚点、冻结身份、最小复现入口及恢复条件。
**最小验收**：两个合成 run 覆盖重复启动、一个 block 不全停、hold 与发布竞争、手动暂停/取消保留；接续验证同源、无旧批准、含删除节点预算及过期阻塞。
**交接**：向 O3 给出扫描调用和唯一控制账本；向工程修复者给出旧执行器边界及明确采用修复的 successor 身份，不能只报仓库 commit。

## O3：同线程持久化时钟

**可改范围**：`tools/monitor.py`、`cli.py`，必要的独立时钟模块和手册；沿用 O2 的控制账本，不建立第二套提取状态机。

1. `monitor start --thread UUID` 显式绑定真实 Supervisor 线程，启动单实例后台时钟；时钟只读时间、控制记录并投递消息，不执行提取或创建 Agent。
2. 开启时完成首次轻量 scan 并记录检查号 0；其后前三个间隔各为 300 秒，第 3 次到期扫描完成后改为 1,800 秒。
3. 下一次时间从本次成功扫描提交时刻计算：示意为首次、+5、+5、+5、随后每 30 分钟；错过时只处理一轮，不补发积压轮次。
4. 同一代际的周期计数持久保存；未持有本轮 accepted 身份的手动 scan 只观察，不消耗到期轮次、不重置前三轮，也不产生额外提醒。
5. 到期消息要求先 `monitor ack ID --thread UUID`；accepted=true 才进行该轮 scan，原子登记观察、完成号和下一次到期时间，然后结束当前对话轮次。
6. accepted=false 时结束该提醒的处理；不用对话内 sleep、倒计时轮询或临时新闹钟维持周期。
7. 稳定提醒 ID 由绑定代际、检查号、到期时间生成；队列超时、重启或有界重送沿用相同 ID，不生成第二个巡检任务。
8. ack 在控制锁内做一次性状态转换，校验线程、代际、启用状态、当前 ID 与到期条件；过期、错线程、重复、已停用均拒绝。
9. scan 的周期提交绑定已接受的 ID，重复提交幂等；崩溃后可从已登记的同轮结果完成下一次时间提交，不再次推进计数。
10. ack 后尚无完成记录的崩溃显示 acknowledged_unfinished；同线程显式 `monitor scan` 可续完已接受轮次，不靠重复 ack 再授予处理权。
11. 使用 `codex queue --thread UUID --message TEXT --resume` 投递到绑定线程，记录队列响应中的消息身份；不得用 `codex exec` 替代唤醒。
12. 发送前持久登记尝试，失败/不确定送达最多 3 次、间隔至少 120 秒；成功入队后等待 ack，不按分钟重复提醒。
13. 发送成功但落盘前崩溃允许同 ID 有界重送，由 ack 去重；上限耗尽或入队后长期无 ack 显示 needs_attention，不无限唤醒。
14. 时钟持有进程级文件锁，身份包含 PID 与启动时间；重复 start 检查真实锁和身份，不能只凭 PID 文件另起实例。
15. `monitor status` 展示 enabled、线程/代际、PID/存活/心跳、当前提醒、发送次数、ack、最近扫描及下一次时间。
16. 主机或 app-server 重启后明确展示时钟停止、逾期或送达不确定；显式 start 恢复持久进度，不假称仅有状态文件就仍在运行。
17. stop 先停用并推进代际，旧消息随即失效，再结束时钟；不暂停、取消或恢复任何提取任务。
18. 换线程使用 stop/start，保留已完成周期和重试账本，旧线程消息失效；重新收到有效 ack 才标记该线程唤醒已验证。

**交付物**：一个后台时钟、短消息/ack 协议、可读状态及重启处理说明；保留“scan→登记下一次→退出”的单轮边界。
**最小验收**：假时钟和队列替身覆盖 300/300/300/1800、手动扫描、重复/过期 ack、发送窗口崩溃、单实例和 3 次上限，不真实设置闹钟。
**交接**：向 O4 提供检查号、提醒 ID、消息 ID 与时间锚点；真实退出对话后同线程收到提醒并 ack 的统一实测已完成，见文末记录。

## O4：轻量 token、时间、会话审计与封存

**可改范围**：`tools/agent.py`、`recovery.py`、`runner.py`、`store.py`、`cli.py`，新增薄层 `audit.py`；更新工具协议与手册。

1. 从现有 CLI events 提取提供者实际报告的 usage，保存到本 attempt 的 result；记录字段来源和是否完整，不要求模型估计 token。
2. 分开 input、cached input、output；cached 是 input 的组成部分，不能与总 input 再相加。不具备可靠语义的 usage 保留原值及未知标记。
3. 缺少 usage、失败调用、截断事件均记 unknown/partial，不记作 0，不据可见 token 宣称完整账单或美元费用。
