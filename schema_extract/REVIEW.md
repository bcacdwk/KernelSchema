# Reviewer：当前文档的独立验收

Reviewer 对当前产物截至本阶段已完成的全部内容负责，依据本次冻结的 schema_docs 核实表达完整、自洽、处于正确层级，且无需历史上下文即可理解。前序批准和检查器通过不免除此责任；依靠隐含定义、正文改写结构或旧稿补充含义的产物不能放行。

这是 worker 自查与 reviewer 独立验收共用的方法。阶段页说明应完成的内容，调用中的 `purpose/mode` 决定本轮操作；可写范围取阶段权限、`writable_files` 与本轮字段授权的交集。维护任务不因阅读普通阶段页而获得推进、重开或扩大修改的权限。

## 当前产物先行

先读当前规范、当前 YAML 和当前索引，再按具体问题核对固定源码。用当前产物建立自己的理解，不以交接、退修经过、旧版本或前序批准解释其中缺失的定义。普通 reviewer 提示不提供这些历史内容；裁决所列候选各自作为完整的当前候选阅读，不能用另一候选补齐它。

可以分段、分文件阅读并保存进度，但批准前必须完成本阶段范围内的有效全文审阅，包括引用、复制和本轮未修改的内容。同一当前共用定义可按实际 provider 文件读一次；每个使用节点的选择域、参数绑定、跨区接口及 realization 仍逐一审阅。回执、阶段进度和审计证据保存在 YAML 之外。源码引用用于核实来源；属于 YAML 的计算与设计定义应在所属字段或规范允许的当前引用中可读，不能靠打开源码才补全。填写或审阅一段前，读取当前 `rules_root/schema_docs` 中对应的字段、分层与语义规则。

当前创作格式由 root 定义共享 Contract；派生节点各 Design 区域完整本地定义或按[整区规则](../schema_docs/0.common.md#design-整区引用)显式引用直接父的同名区域，可传递到实际本地 provider。当前来源链是阅读依赖，历史批准不能补充定义或证明适用；不允许隐式继承、兄弟或外部定义。只读有效视图可辅助理解，证据仍来自当前 raw 的引用行与 provider 原文。单文件交付视图由正式工具完整检查、展开全部引用并补入 Contract。

## 四项判断

1. **独立理解。** 从当前已完成内容解释本阶段的任务或设计。核对输入、输出、符号、条件和引用的定义能在当前产物及规范允许的明确依赖中找到；发现需要历史解释的地方，定位缺项。
2. **分层正确。** 每项定义和决定由所属层负责。Contract 定义任务，数学层定义计算、精度与保留，调度层定义工作与提交，流水线层定义角色、依赖与资源，实现交接只补充必要的实现条件。下层不能借理由补入或改写上层决定。
3. **全文一致。** 对照正文、公式和结构。每种改变提交集合、参与成员、物化或事件存在性的条件，都检查其不同情形；不能把未提交、没有工作和已执行动作的 no-op 混为一谈。无数据效果的已声明动作仍有事件，不能由正文取消。依[参数与结构的分组规则](../schema_docs/0.common.md#参数变化与结构变化)核对各个实际情形，既不以少建节点为由合并不相容结构，也不把可合法参数化的数量变化逐项拆开。
4. **内容必要。** 文字承担本字段允许的定义、约束或解释。数学公式、必要策略、动作契约、当前设计理由及影响理解的来源限制应保留；退修过程、待办、历史批准、“沿用上一版”等记录，以及重复定义应删除或移至回执。不要因为文本提到限制或未知事实，就把按规范保留的来源缺口判成杂事。

依[结构与扩展](../schema_docs/0.common.md#结构与扩展)区分填写实例与修改语言：具名对象、开放取值、自定义动作及数学记法按各字段规则使用；新增固定字段、封闭取值或未定义记法属于规范变更，不能自行采用。旧稿、源码写法或检查器接受都不授予扩展权限。不要求自然语言都变成可执行代码，也不按关键词或篇幅判定好坏；语义正确、必要信息齐备就直接通过，不要求找问题或增加篇幅。

涉及录图时按[计算执行实例](../schema_docs/0.common.md#plan-与计算执行实例)核对提交和事件；涉及条件等待时按[动作与契约](../schema_docs/5.design.tile_pipeline.md#动作与契约)及[索引窗口](../schema_docs/5.design.tile_pipeline.md#依赖的索引窗口)核对跨 role 前驱，既不将其藏在正文，也不为其他条件补加等待。

## 各阶段覆盖范围

| 阶段 | 必须重新审阅的当前内容 |
| --- | --- |
| P1 | root 的元数据与算法 Contract；Design 可为未完成草稿。 |
| P2 | P1 已完成内容、当前 root 选择条件与 dispatch 草案；不要求未写的 Design。 |
| P3 | 完整 root：元数据、算法 Contract、各层 Design 和适用的 Realization；结合当前 dispatch 草案核对范围。 |
| P4 | 完整 root 与当前 dispatch 计划；尚未生成的分支不作已完成设计验收。 |
| P5 | 当前分支的完整有效 Design、共享 Contract 和独立选择条件，实际 provider 定义及引用链；审定相对直接父有效 Design 的差异，以及共享内容在本节点的适用性。 |
| P6 | 全部当前节点与索引；共用定义按实际文件读一次，每个节点各层的有效绑定、选择域、局部差异及待复查范围均覆盖，再核对全树一致性。 |

硬件占位及 GPU 边界沿用提取约定，不能把这项豁免扩展到其他字段。全文表达审阅与源码复核分开：前者每次覆盖上述范围；后者围绕当前差异、风险和疑点回查，不要求每阶段重新完成整个源码审计。

P1/P2 允许的未完成 Design 不豁免本阶段元数据、Contract 或路径草案的完整性；尚未完成本阶段的 partial 草稿不能获批。P3/P5 在当前节点中贯通输入到全部输出，不能只挑一个情形就忽略改变结构的其他分支。

### 共用定义与使用节点

provider 的审阅负责本地定义的源码/规范推导及其在 provider 中的正确性。子节点的 `differences` 比较自己与直接父的有效 Design，引用语法变化本身不算设计差异；`inherited_design` 判断共用定义在本次选择域、名称与参数绑定、三区域组合和本地 realization 下是否成立。`walkthrough` 使用完整有效 Design 贯通输入到所有输出，覆盖 launch、生产者、事件、handoff 及资源闭合。子节点无需重述同一通用推导，但不能把父批准当作这些适用性的证据。realization 与反馈不继承；当前 Contract/有效 Design 之外仍必要的实现约束，即使与父相同，也须在本节点显式填写。

P5 必需产物证据覆盖 `source_manifest(child) ∪ source_manifest(direct_parent)`，再并入 root、child 和直接父文件。批准还须对 child 和直接父分别逐区域检查每条引用 chain 的全部节点：该 consumer 自己的 `from_parent` raw 行、所有中间引用 raw 行及实际 provider 本地定义 raw 行。每文件一个任意锚点不足以覆盖这些要求；同一真实范围可同时满足多项要求，无需重复列相同锚点。文件名或有效视图虚拟位置不能代替 raw 证据。P6 仍覆盖最终全部产物。调用的 `design_resolution` 与 `provider_reopen_targets` 来自当前 workspace 的来源图；坏草稿的解析诊断和保守祖先列表只用于继续修稿，不授予 provider 重开资格或批准。

## 源实现缺陷与设计分流

发现源 kernel 正确性问题时，按 schema_docs 的抽象边界判断它是否妨碍确定设计。固定源码的声明、容量预算、生产消费、使用点等共同支持同一完整设计，且无需重新决定算法、精度、数据版本、逻辑依赖、角色、提交、容量、生命周期或复用策略时，边界之外的实现偏差不阻塞提取。保留缺陷事实和证据，继续完成有据的 Design；无需先确定损坏后的实际值，除非它仍影响某项设计决定。不能只凭作者意图或“修一行即可”作此判断。

具体地址或同步指令的落实偏差不自动等于设计改变；关键是逻辑依赖和资源策略是否已有来源依据。缺少生产者、需要无依据的新依赖、增加缓冲或改变共享复用的修复不能借此放行，也不能删去源码已明确的计算提交或副作用、凭数学正确性另选算法。必须猜测或改变上述设计决定才能完成时，指出具体关系和缺失依据，阻塞受影响范围；当前产物写错或漏写已知设计则退修。

源实现问题在现有 `issues`、`source_evidence` 和 `summary` 中定位、说明影响及继续或阻塞的依据，由 Supervisor 按需登记 kernel issue；worker/reviewer 不写台账，也不把它冒充 `framework_candidates`。缺陷详情留在回执和 issue，YAML 保留设计必需约束及必要的一句来源限制，不把坏地址或错误复用写成 `realization.require/forbid`。TMEM 等计算资源、完整数据对象的容量与生命周期、数据和复用依赖仍须表达，不能与返回基址槽等实现元数据一起省略。可继续不等于可批准残稿：完整 Design、四项文档判断、全部必需文件及源码锚点和现有门禁仍须满足；Schema 批准不证明源 kernel 已正确。

修复 kernel、运行 GPU 测试或取得实测结果不属于本轮 worker/reviewer 的职责，也不是上述有据设计继续提取的先决条件。

## 来源缺项

按缺口对当前阶段的实际影响判断，不要求 P1 提前完成 Design。当前所需的任务数学、IO、副作用、参考入口和设计关系有依据，而外部验收器的公式、相对误差基准、归一化或检查路由未提供时，依[验收来源记录](../schema_docs/1.contract.algorithm_requirement.md#固定实现提取中的验收记录)在对应 `tolerance` 中保留已知判据与明确限制，说明未采用默认简写解释。用 `issues.kind=source_gap` 记录缺项、来源、为何不影响当前提取及补齐途径；它不是新增的 YAML 字段，也不写入 `golden_reference.gap`。

只影响外部测试通过边界的缺口不阻塞提取；本阶段内容完整时可 `complete/approve` 并保留 issue。后续审阅确认已知事实未遗漏、未知内容未被当作设计或数值保证、限制仍在交付中，不因比较器仍未补齐再次阻塞。计算、精度转换、输出副作用或依赖必须靠猜测才能表达时，指出具体关系和缺失依据，阻塞受影响范围；来源已明而产物写错或漏写则退修。

## 发现问题与批准

审阅范围大于修改权限。定位具体文件/字段、规则、影响、证据及修改要求，再按本轮模式处理：普通调用仅在提供 `reopen_targets` 时可申请上游重开；维护调用按明确字段安排有限修补，越界问题交 Supervisor 追加有依据的计划；裁决和签收只用本轮允许的出口。不要在下层用补充说明修补上层，也不要因上游已经通过就忽略问题。

普通 P5 normal 调用还可按可信 `provider_reopen_targets` 请求 `P5:<id>`，目标须为当前引用链上的实际非 root 本地 provider。请求须有该定义区域的当前产物锚点，以及固定源码新发现或具体转录/规范纠错依据；关联 issue 的 `scope` 同时含 provider 真实文件名和 `design.<区域>`，其 `evidence` 与 `reopen.evidence` 至少相交一项本次源码索引。reopen 与 blocked 一样，至少有一条有效 issue 须填写非空 `recovery_condition`，见[回执协议](tools/README.md#普通-p5-的-provider-修复)。仅在子上下文不适用时，由 child 落地整个本地区域修订。Runner 在提交 workspace 重新核实资格；P6、maintenance、裁决和签收没有此入口。计划或直接父选择错误回 P4；子节点 `when` 在本节点修正；root Design/when 回 P3，Contract 回 P1。

先判断能否按现有规则表达。确有不适配、缺失或冲突时，在 `framework_candidates` 给出跨运行稳定的小写字母数字及 `-_` 短 ID，`scope/summary` 指出规范文件/小节或工具、具体反例、现有写法为何不足及最小建议；`evidence` 引用本次已读源码。当前产物问题另用 `issues/artifact_evidence` 定位。交 Supervisor 处理，不写台账；正式接续采用新的冻结规则前仍按现行规范工作，不边提候选边采用新语义。依靠自造规则才能读通的产物不能批准；没有必要建议时填 `[]`，可选候选不扣住正确产物。

批准时，在现有 conclusions 中分别填写以下四项简短、针对当前内容的判断：

- `document_self_contained`：当前定义和允许的依赖足以独立理解。
- `document_layering`：各层定义权明确，没有下层补改上层。
- `document_consistency`：结构、正文及改变执行关系的情形一致。
- `document_relevance`：保留必要设计内容，未混入历史过程和无关记录。

这些判断引用当前产物的 artifact_evidence，来源 evidence 可为 `[]`；源码忠实性的阶段结论仍须来源依据。Runner 要求四项结论及本阶段全部必需文件的产物锚点，不接受只有“之前已审”或检查器退出码的批准。它只能核对提交范围和证据绑定，语义判断由 reviewer 负责。

`revise/blocked` 至少有一条具体且有依据的 issue，`blocked` 另须恢复条件。若只针对当前产物的提交格式、规范表达，按[回执证据分流](tools/README.md#回执与短交接)使用 `submission_format` 或 `schema_conformance`：`scope` 独立写全产物的相对文件名（可接字段/行号），引用该文件实际内容的 `artifact_evidence`，来源 `evidence` 可为 `[]`；其他文件、同名片段或旧目录别名不能代替。不要把源码缺口、缺陷、转录、计算、数值或选择问题改称文档问题来省略源码依据。证据分类与引文支持仍须核实；reviewer 各种结论均须覆盖必需产物并提供实际源码证据，上游重开也不适用这项单条 issue 的豁免。

发现问题时给出具体文件/字段、违背的规则、影响及可执行修改要求；无需为了填写四项批准结论伪装已完成审阅。修订后的文件重新承担上述全部验收要求，反馈本身不成为 YAML 的额外语义。

连续语义维护默认把完整旧稿先交独立 reviewer；`review` 可直接通过，只有有据问题才按明确范围修补并独立 `verify`。已有证据和授权的 `patch/reextract` 按本次任务执行，祖先更新不授权用父 Design 覆盖节点自己的 raw。换父须 worker 显式迁移 parent/ref 或落地整个区域，再独立重审；超出已封存 fields 时报告缺少的 scope，不自动扩权。字段边界限制 worker 修改，不缩减 reviewer 对本阶段有效全文和当前共享前提的职责。尚未完成的普通草稿继续原作者逻辑步骤，维护不能代替其完成或批准。

保留旧稿与采纳旧批准是两件事。`keep` 可仅表示保存内容和账本；只有 Runner 验证了独立适用性评估，覆盖规则变更和问题、确认内容未变且依赖兼容，旧批准才可成为当前有效前提。被派发的 reviewer 仍须独立审阅本轮完整范围，不能以旧批准或 `keep` 标签作通过理由。P6 始终需要当前语义上下文中的新终审。
