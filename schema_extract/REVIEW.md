# Reviewer：当前文档的独立验收

Reviewer 对当前产物截至本阶段已完成的全部内容负责，依据本任务适用的 `schema_docs` 核实表达完整、自洽、分层正确，且无需历史上下文即可理解；前序批准和检查器通过不免除此责任。阶段调用实际装配的完整审阅细则见[角色审阅页](prompt/roles/reviewer.md)（同时供 worker 自查），执行门禁见[工具协议](tools/README.md)。

## 当前产物先行

Runner 先保存 worker 原稿、整体规范化、核验文件/字段权限与来源并严格重读，reviewer 始终只读审阅落地后的当前 raw（裁决中的各候选也须各自完整可读）。先从适用规范、当前 YAML 和 `dispatch.md` 独立建立理解，再核对固定源码，最后用过程回执反查知识去向；过程记录与展开视图不能补足 raw 缺失定义或证明来源适用。批准前须完成本阶段有效全文审阅（含 [Design 整区引用](../schema_docs/0.common.md#design-整区引用)来源闭包、未改内容及[目录差额记录](../schema_docs/0.common.md#局部记录与完整方案)）；同一当前共用定义可读一次，每个使用节点的范围、绑定、跨区接口和本地 `REALIZATION` 仍分别核实。

## 四项判断

1. **独立理解。** 当前已完成内容及明确允许的依赖足以解释任务、具体设计或记录；输入、输出、符号、条件和引用均可定位，依赖历史解释属于缺项。
2. **分层正确。** Contract 定义任务，数学层定义计算、精度与保留，调度层定义工作与提交，流水线层定义角色、依赖和资源，Realization 只补必要实现条件；下层不改写上层，目录不覆盖 YAML。
3. **全文一致。** 一份 YAML 表达一套具体方案，贯通尺寸、尾块、空工作及改变提交、成员、物化或事件存在性的情形，区分未提交、无工作与仍有事件的 no-op，按[差异规则](../schema_docs/0.common.md#参数变化与结构变化)不拼接不相容机制。
4. **内容必要。** 保留必要数学、策略、动作契约、设计理由及影响理解的来源限制；过程状态留在回执记录，正式范围中的研究取舍与合规来源缺口照实保留。

[结构与扩展](../schema_docs/0.common.md#结构与扩展)、录图/调用前缀及跨 role 条件等待的核对细则见[角色审阅页](prompt/roles/reviewer.md#四项判断)与对应 `schema_docs`。

## 各阶段覆盖范围

| 阶段 | 必须独立审阅的当前内容 |
| --- | --- |
| P1 | 任务元数据、共享算法 Contract、逐输出验收材料，以及有据执行单元与所需存储名/范围的最小登记；Design 可未完成，不批准 root 代表选择。 |
| P2 | P1 已完成内容、机制概览、root 来源与初步范围、拟完整集合和记录线索；核实影响选择的有据疑点及调查止点。 |
| P3 | 完整具体 root 的元数据、Contract、Design 和必要 Realization，结合当前目录草案核对承担范围。 |
| P4 | 完整 root、目录、相关现有基线与有限未来计划；核对材料是否支持已定差异、保留依据与已知知识去处，未来内容只审计划。 |
| P5 | 本节点有效全文、共享 Contract、实际来源闭包和使用上下文；核实实质差异、完整输入到输出关系及新事实影响。 |
| P6 | 全部最终完整设计与正式记录；核对含 root 至多十份、每份独特价值、实际基线、共享适用性、机制去向与真实范围。 |

硬件最小登记、starter 占位与 GPU 豁免边界见 [P1 硬件占位](prompt/phases/01_contract.md#第-3-段硬件占位)。完整设计的保留/降级判据（独特主机制保留完整 YAML，参数/局部/已知组合降为 `dispatch.md` 记录，无新增信息合并或删除）及共用定义与使用节点的核对要求见[角色审阅页](prompt/roles/reviewer.md#完整设计的保留与降级)。另行授权的限域评议只覆盖实际核实对象，不代替正式阶段批准。

## 源实现缺陷与设计分流

发现源 kernel 正确性问题时，若固定源码已有依据支持同一完整抽象 Design，无需猜测或重定算法、精度、数据版本、逻辑依赖、角色、提交、容量、寿命或复用策略，则记录缺陷证据并继续提取（不把坏地址或错误复用写成 `REALIZATION.Require/Forbid`，也不省略计算资源、对象寿命与依赖）；必须猜测或改变上述设计决定时阻塞受影响范围，产物漏写或写错已知设计则退修。源缺陷由 Supervisor 按需登记，不冒充框架问题，也不免除完整 Design、四项判断与适用检查；Schema 批准不证明源 kernel 正确。详见[角色审阅页](prompt/roles/reviewer.md#源实现缺陷与设计分流)。

## 来源缺项

当前任务数学、IO、副作用、参考入口和设计关系有据，仅缺外部验收器的组合公式、相对误差基准、归一化或检查路由时，按[验收来源记录](../schema_docs/1.contract.algorithm_requirement.md#固定实现提取中的验收记录)在对应 `Golden_reference.Tolerance` 保留已知判据与明确限制（不套用默认简写，不挪入 `Gap`），本阶段完整时可批准并保留问题记录。计算、精度、输出副作用或依赖须靠猜测时阻塞具体范围；已知事实遗漏或写错则退修。详见[角色审阅页](prompt/roles/reviewer.md#来源缺项)。

## 发现问题与批准

批准须分别覆盖四项判断并锚定当前 raw，源码忠实性结论与非纯文档问题须附固定源码证据；退修或阻塞须给出具体有据问题，阻塞和返回还须写明恢复条件，回执编码见[工具协议](tools/README.md#回执与短交接)。正文错漏由有权阶段修定义；机制或代表取舍有误回 P2，已定代表的登记或安排变化回 P4，共享 Contract 错误回 P1，provider 定义错误回定义所在的 P3/P5，普通记录按 P3→P4、P5→P6 汇集落实；规则确有缺失或冲突时通过 `framework_candidates` 独立核实确认（详见[角色审阅页](prompt/roles/reviewer.md#发现问题与批准)）。

当前 run 的限域维护保留固定身份、草稿和已用次数：完整候选可先独立审阅，有据问题由授权 worker 按显式文件/字段修补后再审，未完成稿继续普通写作；来源身份变化后仅在机械证明定义、Contract 与完整使用上下文不变时保留原批准适用性，否则独立复审，且每次新派 reviewer 仍审本阶段完整范围，最终交付须经新的 P6。裁决补丁由 Runner 应用、规范化并严格检查后，交全新 reviewer 一次签收最终 raw（未签收改稿不形成批准）；直接选择已审阅且不再变化的规范候选无需新增签收（见[裁决协议](tools/README.md#定点返回与一次裁决)）。
