# P4：dispatch 定稿

本页将路径草案变成可据以派发节点的计划。

以下准入、推进与重开用于普通提取；`maintenance` 只执行本次任务，写入还受调用的文件/字段授权限制，不能据本页扩大范围。

## 准入与应读材料

P3 完整 root 已通过检查与独立审阅，P1、P2 的放行仍有效。Runner 提供已审 root、dispatch 草案、P3 短交接、固定 host 选择入口、当前计划修订与可写范围。首次 P4 新开一对 worker/reviewer；因新证据重开时读取受影响节点、现有清单和重开原因，继续原计数与预算。

worker 可沿 P3 短交接定位；reviewer 先按[当前文档验收](../REVIEW.md)读完整 root 与当前索引，再依[节点与索引规则](../../schema_docs/0.common.md#派生节点与-dispatch)核对 host 路由及各路径实际入口。索引格式见本页最小示例，树和节点数由固定源码决定。

## worker：可写范围与操作

可修改 `dispatch.md`，并通过回执提交结构化节点清单。root 和已审派生 YAML 只读；不提前创建 P5 节点，不把运行计划历史、退修或完成数写进索引。不允许直接修改 Runner 状态。

1. 据真实 root 设计和 host 路由重审分组，沿用[计算执行实例](../../schema_docs/0.common.md#plan-与计算执行实例)的录图与执行边界；同一套参数能覆盖的设计保留在一个节点，真实设计、实现或选择差异才支持并存路径。先识别这些事实，再决定共享表达。每个节点确定稳定 ID、预期文件名、直接父节点、workload、相对父节点有效 Design 的变化和选择依据；Design 相同时说明真实实现/选择依据，不能只写“改为引用”。
2. 明确 `parent` 是直接设计来源，可供 P5 显式引用同名整区；条件在共享契约全域独立求值，父子 `when` 不构成包含关系。选父须设计接近且有证据，不自动换父追求压缩。ID 不随 ref/local 转换、参数或微小实现修订更名。派生精确条件由 P5 写入各 YAML，选择依据在清单中足够定位对应 host 分支及必要派生量。
3. 用中文定稿 `dispatch.md`，按下面的固定表格保存当前树的直接父关系、各节点相对链接、workload、设计差异和选择理由；表格逐项取自本次 plan。精确条件和版本以 YAML 为准；尚未生成的计划内文件允许暂缺，P5 完成后由 P6 核对实有链接。索引只写稳定的设计与覆盖事实，“待 P5 生成”“当前缺文件”等临时阶段说明留在回执，避免随索引进入交付。只有 root 的任务也保留选择理由和实际覆盖缺口，不重复流水线正文或通用规范。
4. 回执仍提供 `id/file/parent/workload/difference/selection/evidence` 七字段清单，root 的 `parent` 为空；不增加引用策略字段。该清单供 Runner 校验和调度，不新建另一份项目配置或由 worker 写运行状态。`evidence` 是本回执 `source_evidence` 的索引，至少包括 host 依据。

索引从以下标题和表头开始，root 在首行，其余行按 ID 排序；单元格中的 `\` 和 `|` 分别转义为 `\\` 和 `\|`，换行写成 `<br>`。直接父列的 root 使用 `无`。Runner 确定性核对整张表格；不另写一份可能与它矛盾的树。表格结束后空一行，后文包含一个 `## 覆盖缺口` 节；允许在表格与该节之间插入必要说明，不因段落位置增加修复调用。覆盖缺口节必须有自己的正文，没有已知缺口也明确写明，不能由节前说明或另一节代替。比如 host 对未对齐输入的拒绝必须保留，不能据一条路径推断 fallback。

```markdown
# 路径索引

| 节点 | 直接父 | workload | 相对父差异 | 选择依据 |
| --- | --- | --- | --- | --- |
| [root](root.yaml) | 无 | plan.root.workload | plan.root.difference | plan.root.selection |

## 覆盖缺口

据本次源码核实的具体缺口和影响范围。
```

重开 P4 时列明新增、删除、换父或受条件变化影响的节点及证据，交 Runner 更新计划修订和有效结论。要改选代表路径、root Design/条件或共享 Contract 时，按[计划修订入口](../tools/README.md#并行合入与计划修订)回对应阶段，不能在 P4 顺手改 root。已知覆盖不足如实保留，不虚构 fallback；其他缺项和硬件边界沿用[总览](../../EXTRACT_SCHEMA.md#来源缺项与验收边界)。

换父时 Runner 保存 `identity_migration`，记录 old/new parent、旧 checkpoint、计划修订和原因，保留旧 raw、版本及审批历史；受影响旧新后代失效，在途结果按 generation/fence 退休。该节点必须交 worker 显式迁移，不能仅凭旧完整稿恢复批准。P4 只改 plan/索引，不自动改子 YAML 或 retarget 引用；P5 worker 按新 parent 逐区选择引用新父或从旧 checkpoint 落地完整旧定义。新身份独立获批后清迁移标记，预算、计数和历史保留。maintenance 超出原字段范围时先报告缺少的 scope，不自动扩权。

## reviewer：放行门槛

按[当前文档验收](../REVIEW.md)覆盖完整 root 及当前计划；尚未生成的节点不作已完成设计验收。发现只读 root 的问题按本轮模式交回，不因 P3 已批准而跳过。

独立对照 host 路由和已审 root，确认整棵树以必要节点保留真实设计、实现与选择差异，直接父节点提供有据的设计起点。每个条目的 workload、有效差异和选择依据足以让新 worker 精确接手；共享不掩盖提交、生产消费或事件拓扑差异。覆盖缺口保持真实，清单与索引相同，root 文件未被越权改写。

调用的 `plan` 是当前 worker 提交的清单，重开和维护复核也据此审阅；批准时返回相同的节点语义。自己的 `source_evidence` 顺序和 `evidence` 编号独立，不必复制 worker 的局部编号。重开时可从 `current_node_artifacts` 读取现有节点，直接审阅其内容是否仍适用；不提供此前批准结论作为阅读前提。

Runner 对 complete/approve 检查唯一 root、ID 与文件身份唯一、父节点存在、无环且所有节点可达，并核对已审 root 的身份。多节点计划要求已有 root 的 `meta_data.dispatch.when` 非空，不能等 P5 创建节点后才发现。P4 不要求尚不存在的分支 YAML 通过检查；Runner 对 root 复用有效 P3 凭据，不免除本轮完整文档审阅。普通调用中，root 身份或代表路径问题回 P2，现有 root 的 Design/when 缺失或错误回 P3；维护调用按本次有限任务反馈越界问题。P4/P5 无权改 root，不能获得必要上游修复时明确阻塞，不派发子节点。

## 回执与下一位

按[回执约定](../tools/README.md#回执与短交接)提交经审阅的节点清单、划分与选父依据、覆盖缺口及影响范围。reviewer 的 P4→P5 短交接保留路径入口和各分支待核实的差异。

Runner 验证后保存当前计划，立即为直接父节点已审并合入的节点启动 [P5](05_branch.md)，每节点全新一对 worker/reviewer。没有派生节点时跳过 P5，仍由 [P6](06_final.md) 的新 reviewer 终审。
