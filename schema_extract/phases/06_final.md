# P6：全算子终审

本页审阅完整任务目录，只有终审通过才可达到 `ready`。

本页描述普通终审；维护完成后仍须回到当前语义上下文中的 P6，不能用维护批准代替终审。本轮 `mode` 决定普通审阅、一次裁决或独立签收的出口，写入受调用的文件/字段授权限制。

## 准入与应读材料

Runner 确认当前计划的全部节点与当前有效、已合入节点集合相同，且 P1–P4 放行仍有效；规则接续后的旧批准须已通过当前适用性验证。reviewer 使用本次 source/rules/executor 绑定、当前计划、`dispatch.md`、完整任务 checkpoint 和固定来源入口；前序批准、交接和旧稿不作为其初始上下文。单 root 任务也必须进入 P6，旧 P6 批准不能跨语义修订直接沿用。

先启动全新 reviewer，尚不启动 worker。按[当前文档验收](../REVIEW.md)读取最终 raw 定义及引用链，理解所有节点的完整有效 Design，再按具体问题核对固定源码。同一当前共用定义按实际 provider 文件读一次；每个节点的有效参数/名称绑定、独立选择域、跨区接口、局部差异、realization 和待复查范围仍须覆盖。可以分批阅读，不依赖历史批准，也不能只看 when 或差异。共同准则见[节点与索引规则](../../schema_docs/0.common.md#派生节点与-dispatch)和[检查边界](../../schema_template/README.md#校验边界)。

## reviewer：先审与放行门槛

依[当前文档验收](../REVIEW.md)覆盖全目录，包括未修改内容及改变执行结构的各类情形；源码复核按变化、风险和疑点深入。

1. 对照计划检查实有文件：唯一 `root.yaml`、所有计划内节点和 `dispatch.md` 均在；ID 唯一、parent 存在、树无环且全部可达，索引树与 YAML 一致，节点链接可打开。目录没有未计划的备份或草稿 YAML。索引正文须与实有交付一致；发现“待 P5 生成”“当前缺文件”等过期阶段说明时，按索引修改范围退修清理，保留真实的来源与覆盖缺口。
2. 对照 host 核查包含 root 和中间节点在内的独立 `when`，检查互斥与完整契约域覆盖；精确条件以 YAML 为准。已知源码覆盖不足明确记录实际范围，不能靠收窄 Contract、虚构节点或 fallback 掩盖。源实现缺陷按[设计分流](../REVIEW.md#源实现缺陷与设计分流)复核，不能把已登记问题误作原 kernel 正确或提取完成的证明。
3. 核对各节点与当前共享 Contract、真实 provider/chain 和索引一致，raw 引用及本地定义可定位，全部有效层面完整；按[来源缺项](../REVIEW.md#来源缺项)确认验收记录忠实、限制随交付保留且未被用作保证。跨节点条件或共用内容不一致时深入复查受影响的源码关系；其他节点可不重复完整源码审计，但仍须完成有效全文表达及适用性审阅。硬件与 GPU 边界沿用 [P1](01_contract.md#第-3-段硬件占位)。
4. Runner 接收终审结论时自动用冻结检查器执行 `--skip-hardware`，扫描最终目录直属全部 YAML，退出 `0` 并通过上述语义审阅才放行；`1` 为产物失败，`2` 为工具或环境问题。reviewer 需要定位问题时可按调用中的命令自检。节点早先各自通过不代替这次全目录检查，检查通过也不代替选择条件、来源与未决项审阅。

不需修改时，reviewer 直接返回终审结论。需改动时，给出证据、具体文件/字段、修改要求及受影响节点，由 Runner 启动 worker；不自行越过已定计划修改产物。退修、一次裁决及裁决亲自改稿后的独立签收统一按[手册规则](../tools/README.md#退修与裁决)执行。

P6 没有普通 P5 的 `P5:<provider>` 重开入口；按本轮 `revision_scope`、`affected_nodes` 和 `pending_rechecks` 处理派生定义及保守后代复查，独立审阅/签收照常。需要换 parent 时回 P4，不在字段补丁中换父。先前 P5 的有效子集检查只服务暂态合入，不能代替本阶段全树检查。

## worker：按需加入与可写范围

只有 reviewer 明确提出修改、Runner 派发后，才启动 P6 的全新 worker。读取本页、当前 checkpoint、退修意见、受影响节点的有效结论和相关源码；按需回到对应规范或 [P3 的逐段方法](03_root.md#节点逐段方法)。

仅可修改 Runner 本次明确列出的任务 YAML/索引及字段；一般修订限于终审发现的问题。不得编辑源码、规范、检查器或运行状态，不把获得终审任务等同于整树任意改写权。按实际内容更新版本、沿引用复查受影响节点，再交 Runner 检查完整目录。需要改共享 Contract、root 设计/条件或树计划时，按[计划修订规则](../tools/README.md#并行合入与计划修订)先重开对应阶段，由 Runner 重评有效集合；重新满足 P6 准入后再终审。

## 回执与下一位

`revision_scope` 为 `[{path, fields}]`，`fields` 使用点分字段路径；`affected_nodes` 列出受影响节点 ID。退修必须给出范围：`dispatch.md` 使用 `["*"]`，派生 YAML 可限域修改 `design`、`realization`、`meta_data.source`、`meta_data.dispatch.when` 下的字段。worker 原样保留授权范围并随内容提高版本。Runner 将受影响后代加入 `pending_rechecks`，批准/签收必须逐项覆盖；root、共享 Contract 或树变化走上游重开。终审派发及放行前都验证有效回执、Runner 门禁、checkpoint 与实际内容一致。

按[回执约定](../tools/README.md#回执与短交接)提交树和链接、条件互斥/覆盖、引用与未决项结论，附必要源码依据和实际检查。若修改，给出影响范围及重新核对的节点，无需新增固定终审报告或 schema 状态字段。

`tree` 结论中的文件数量、父关系、链接和拓扑属于当前产物事实，由完整 `artifact_evidence` 和 Runner 的全树检查支持，来源 `evidence` 可为 `[]`。选择、覆盖、来源及未决项等语义结论仍须引用实际支持它们的固定源码，不用不相干的源码索引代替产物证据。

Runner 验证当前上下文的最终结论并保存已审 checkpoint 后才记录 `ready`。发布或导出前再次确认来源、规则、执行绑定及有效回执/产物一致，且无未结算调用、待处理语义修订、drain 或维护屏障，再按[交付规则](../README.md#恢复与交付)原子发布；`ready` 不等于已发布。目标冲突保留双方并向 Supervisor 报告。不能放行时保存草稿、阻塞原因与恢复条件，不把草稿当正式完成。
