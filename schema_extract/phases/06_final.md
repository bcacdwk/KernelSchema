# P6：全算子终审

本页审阅完整任务目录，只有终审通过才可达到 `ready`。

## 准入与应读材料

Runner 确认当前计划的全部节点与当前有效、已合入节点集合相同，且 P1–P4 放行仍有效。输入包括当前计划修订、`dispatch.md`、完整任务 checkpoint、固定 host 来源、各节点有效结论与未决项。单 root 任务也必须进入 P6。

先启动全新 reviewer，尚不启动 worker。reviewer 先读索引、各 YAML 的选择条件、host 选择源码和有效节点结论，再按具体不一致回查实现与规范，不无差别重做所有节点提取。共同准则见[节点与索引规则](../../schema_docs/0.common.md#派生节点与-dispatch)和[检查边界](../../schema_template/README.md#校验边界)。

## reviewer：先审与放行门槛

1. 对照计划检查实有文件：唯一 `root.yaml`、所有计划内节点和 `dispatch.md` 均在；ID 唯一、parent 存在、树无环且全部可达，索引树与 YAML 一致，节点链接可打开。目录没有未计划的备份或草稿 YAML。
2. 对照 host 核查包含 root 和中间节点在内的独立 `when`，检查互斥与完整契约域覆盖；精确条件以 YAML 为准。已知源码覆盖不足明确记录实际范围，不能靠收窄 Contract、虚构节点或 fallback 掩盖。源码已知缺陷和提取尚未完成要区分，关键未知仍须给出恢复条件。
3. 核对各节点依赖的共享 Contract、来源、选择条件与审阅内容仍一致；引用能定位实际对象和版本，未决项的处理与有效结论相符。硬件原样占位与 GPU 排除沿用 [P1](01_contract.md#第-3-段硬件占位)，不把该区纳入收尾。
4. 对最终整个任务目录运行已实现的检查器，从仓库根目录执行，替换为实际 root 路径：

```sh
python3 schema_template/check_yaml.py --skip-hardware path/to/task/root.yaml
```

检查扫描同目录直属全部 YAML，退出 `0` 后再结合上述人工结论放行；`1` 为产物检查失败，`2` 为参数、工具或环境问题，分别记录并处理。节点早先各自通过不代替本次全目录检查，检查通过也不代替选择条件、来源与未决项审阅。

不需修改时，reviewer 直接返回终审结论。需改动时，给出证据、具体文件/字段、修改要求及受影响节点，由 Runner 启动 worker；不自行越过已定计划修改产物。退修、一次裁决及裁决亲自改稿后的独立签收统一按[手册规则](../README.md#退修与裁决)执行。

## worker：按需加入与可写范围

只有 reviewer 明确提出修改、Runner 派发后，才启动 P6 的全新 worker。读取本页、当前 checkpoint、退修意见、受影响节点的有效结论和相关源码；按需回到对应规范或 [P3 的逐段方法](03_root.md#节点逐段方法)。

仅可修改 Runner 本次明确列出的任务 YAML/索引及字段；一般修订限于终审发现的问题。不得编辑源码、规范、检查器或运行状态，不把获得终审任务等同于整树任意改写权。按实际内容更新版本、沿引用复查受影响节点，再检查完整目录。需要改共享 Contract、root 设计/条件或树计划时，按[计划修订规则](../README.md#并行合入与计划修订)先重开对应阶段，由 Runner 重评有效集合；重新满足 P6 准入后再终审。

## 回执与下一位

按[回执约定](../README.md#回执与短交接)返回当前计划与实有文件、树和链接核对、条件互斥/覆盖、引用及未决项结论，附必要源码锚点和最终检查命令/退出码。若修改，列出实际文件、影响范围及重新核对的节点；框架候选放 `framework_candidates`。无需新增固定终审报告或 schema 状态字段。

Runner 验证最终结论并保存已审 checkpoint 后才记录 `ready`，再按[交付规则](../README.md#恢复与交付)向指定目录原子发布；目标冲突保留双方并向 Supervisor 报告。不能放行时保存草稿、具体阻塞原因与恢复条件，由 Supervisor 补充外部输入或处理工具问题，不能把草稿当正式完成。
