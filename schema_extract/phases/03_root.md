# P3：root 设计

本页完成 root 的 Design 和适用的 Realization；其中“节点逐段方法”也供 P5 使用。

## 准入与应读材料

P1 共享 Contract 和 P2 dispatch 草案已通过。Runner 提供已审 root 草稿、dispatch 草案、P2 短交接、选定路径的固定源码入口和本次可写范围。P3 新开一对独立 worker/reviewer。

先读上述产物和[公共引用规则](../../schema_docs/0.common.md#来源与证据)，再沿选定路径读取 host、launch 与实现；按下面的段落分别读取规范 3–6，不要求预读全部源码或规范。创建、修订和检查操作查[模板说明](../../schema_template/README.md)。

## worker：可写范围

只可修改 `root.yaml` 的 `design`、必要的 `realization` 及随实际内容修订递增的 `meta_data.version`。共享 Contract、来源、root 选择条件、dispatch 草案及其他文件只读。当前任务页不足以授权修改先前已定的前提；新证据需要改动这些内容时，在回执定位问题，由 Runner 按[计划修订规则](../tools/README.md#并行合入与计划修订)重开对应阶段。

如果本轮定位信息明确说明由 Runner 重开 P3，并授权复核现有 root 条件，可一并修订 `meta_data.dispatch.when`；Contract、source、dispatch ID/parent 仍只读，改选代表路径先回 P2。来源明确的转录差异可按手册用当前产物锚点和已读源码请求重开上游，不需要寻找无关的新源行。

## 节点逐段方法

本节第 4–7 段用于当前节点。每段围绕本段问题读取源码，写入、保存并回查后再进入下一段；复杂段可用 `continue` 分轮完成。下层发现当前允许范围内的上层有误时，先改唯一定义，再复核下游。已有决定直接引用；事实、代价和源码缺陷保持原样，不在 schema 中优化或修补实现。硬件与 GPU 边界沿用 [P1](01_contract.md#第-3-段硬件占位)，证据缺项按[总览规则](../../EXTRACT_SCHEMA.md#来源缺项与验收边界)记录。

### 第 4 段：数学改写

读取[数学改写规范](../../schema_docs/3.design.math_reshape.md)。对照共享 Contract，追踪实际求值、舍入、状态推进和物化，将变化写成从输入到全部输出的数学关系。会改变数值行为的协作关系深入源码核实，再抽象为分组、映射或递推；数学区不写线程布局、屏障编号或指令组织。留给下游确定的参数按规范绑定。

写完 `design.math_reshape`，沿公式核对值的定义、精度路径、初末状态与寿命。用可核对的量同时表达收益和代价，包括实际执行的掩码、补齐与辅助计算；算法名称和源码注释不能代替公式或证据。

### 第 5 段：工作调度

读取[工作调度规范](../../schema_docs/4.design.work_schedule.md)。从一份完整的可分配工作出发，回看 launch、工作索引、循环与领取逻辑，写清输入、局部遍历、产物和执行者，再确定 phase、映射、分配、提交与交接。数据块描述整份工作，不把每线程 fragment 当作 worktile；辅助计算和部分结果合并也须有实际执行者。

写完 `design.work_schedule`，核对所有数学计算都有工作归属，局部归约未被误拆为独立工作，生产区域能覆盖消费区域。phase、launch 和 handoff 的关系须与实际调用链相符。

### 第 6 段：微流水线

读取[微流水线规范](../../schema_docs/5.design.tile_pipeline.md)。在已确定的工作边界内，追踪影响推进与重叠的值和状态，包括主数据缓冲、寄存器预取、辅助统计量与工作领取协议。沿产生、保留、发布、全部读取、覆盖或重置的关系划分动作，再落实执行角色、重复索引、依赖和资源视图。分别核实操作发射、数据可读和存储可覆盖的保证，将同步调用还原为所保护的关系。

写完 `design.tile_pipeline`，检查首轮、稳态、末轮、未取得工作和终止路径，并追到相邻工作及跨调用状态。既确认下一份工作何时可开始，也确认前一份工作的哪些读取或写回仍继续。被丢弃或没有消费者的值若仍发生求值、搬运或状态更新，应如实保留；源码未排空的流水不能在 schema 中隐含重置。

### 第 7 段：实现交接

读取[实现交接规范](../../schema_docs/6.realization.md)。对源码中的实现选择做删除测试：替换它会破坏哪项既定语义或执行关系，或有什么具体成本理由需要交接？`realization` 只保留上游尚未表达的必要条件与有依据的选择，不因“源码使用了它”就列为硬要求；没有新增内容时省略本区。

原语顺序、近似误差和容量判断须有匹配版本的依据。已有实验或替代反馈仅能支持实际覆盖的版本与路径，不虚构实验，不把某次实现记录自动升级为设计保证。

最后选本节点适用范围内的一例具体调用，将各层从输入连到全部输出，核对符号、工作、资源和事件引用，并回查关键决定的源码或资料依据。记录具体输入条件、主线定位和未决问题；这是一轮源码对照，不要求 GPU 运行。

## reviewer：放行门槛

Runner 接收完成/批准时自动用冻结检查器执行 `--skip-hardware`，退出 `0` 才放行；`1` 的输入诊断交当前修改者，`2` 的工具或环境问题单独记录。需要定位问题时可按调用中给出的命令自检，不要求两个角色重复运行。检查扫描同目录直属全部 YAML，P3 工作目录不应混入其他草稿。

独立沿 Contract、P2 路径和固定源码贯通上述具体调用：数学改写与数值路径对应实际求值，全部输出有工作归属，局部动作的依赖、寿命与复用对应真实执行。特别核对跨迭代、相邻工作和末轮仍在继续的读取或写回；压缩不能漏掉或补造同步。必要实现条件、引用与适用范围足以解释计算、访存和重叠的主要因果，重复决定及不影响理解的细节可删。按[检查器未覆盖的语义](../../schema_template/README.md#校验边界)审阅，确认只读字段未改。

## 回执与下一位

按[回执约定](../tools/README.md#回执与短交接)提交具体调用的贯通结论、关键源码依据、实际检查与未决项。reviewer 的 P3→P4 短交接保留已定设计及理由、影响派生树的发现和后续入口。

Runner 保存有效放行后，启动 [P4](04_dispatch_plan.md) 的全新 worker/reviewer。P4 从完整已审 root 定稿路径树，不从旧会话猜测设计。
