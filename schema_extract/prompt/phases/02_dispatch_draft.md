# P2：机制识别与代表选择

本页建立足以选择具体 root 和其他完整代表的机制概览。先理解固定实现的主要设计，再进入逐份写作；不先展开所有 selector 取值与配对。

## 准入与应读材料

P1 的任务元数据和共享 Contract 已通过。准备当前 root 草稿、固定 host 与实现入口、任务适用范围及本次写入范围。worker 与 reviewer 均使用本阶段的独立新会话；本次调用提供当前材料和已定前提。

worker 从当前草稿接续；reviewer 按[当前文档验收](../roles/reviewer.md)先读共享 Contract 和 dispatch 草案，再沿固定入口核对机制与选择依据。文件、身份和差异记录遵守 [common](../../../schema_docs/0.common.md#派生节点与-dispatch)，本页只说明如何取得足够事实。

## worker：可写范围与操作

可写 `dispatch.md` 草案，以及与 root 代表身份相关的 `META_DATA.Source`、`META_DATA.Dispatch` 和实际内容修订的版本。共享 Contract 与 Design 不在本阶段修改范围；不创建其他完整 YAML，不改源码或运行状态。

1. 从任务材料和 host 入口固定本次实现范围，核对参数归一、主要入口族、实际可进入的实现以及拒绝或限制的范围。共同 Contract、来源实现范围与本次记录范围分别判断。
2. 沿有区分性线索的入口追踪主计算与物化、输出形成或归并负责者、主要工作分配及主协作关系。用实际调用、模板实参与函数体确定当前实例，入口注释只作导航。候选跨多个计算段时，分别说明各段采用的机制，再整体判断完整设计价值；不能用一个配置族名掩盖实际混合。只深入到能回答这些问题的接口，函数、文件、shape、kernel 或 launch 的数量均不是设计数量。
3. 对已有线索提示的相互作用定向核实，例如数值表示改变、输出生产者变化、状态版本、跨工作寿命或完成关系。涉及录图、缓存、验证或拒绝前缀时，区分记录结构与实际提交，核对已发生的计算和副作用；host 顺序不能证明设备工作已完成。提交含义见 DOC4 的[提交身份](../../../schema_docs/4.design.work_schedule.md#提交身份与字段)和[调用边界](../../../schema_docs/4.design.work_schedule.md#调用边界)。
4. 按[差异判断](../../../schema_docs/0.common.md#参数变化与结构变化)给已识别机制确定去处：拟完整代表、参数/局部/组合记录、已研究但不完整展开的独立方案、来源限制，或仍须解决的具体疑点。不把尚未理解的机制直接归为参数，也不为互不作用的轴展开全部配对。
5. 从真实源码实例选择一套具体 root，使其主要接口明确、便于理解和比较。它无需最复杂、最通用或成为其他设计的祖先；不能拼接不同模式构造虚拟基线。发现候选可以超过十个，选定的拟完整交付集合含 root 必须不超过十个，每份说明独特的完整设计价值。
6. 在 dispatch 草案保存实现范围、主要机制与依据、root 选择、拟完整代表及保留理由、轻量记录线索和具体未知边界。轻量线索先定位相关代表与源码中的值或协作关系，尚未写出的对象名可以暂拟；P4 再依真实完整基线落实正式记录。只链接实际存在的文件；未来文件用普通文本文件名并标明“仅计划”，未来对象和共享均待正文落实。核对 root 的实际来源与初步承担范围；完整 Design 和自身 `when` 在 P3 写实。

未选中的已研究独立方案保留名称、独特机制、范围或出处及取舍理由，不改称参数以回避上限。“未研究”表示仍缺少判断机制和去处的事实；“已研究但未完整展开”表示已有取舍依据，只未交付完整正文，二者不能互换。若用户明确要求逐套完整交付的独立方案确实超过十份，才交 Supervisor 处理具体目标冲突；普通候选过多先按任务价值取舍。

### 调查止点

已能有据区分主要机制、判断记录去处并选定真实代表，且没有会动摇当前选择的重要疑点时，可以停止。普通参数明细、完整动作列表和所有源码行无需提前读完。

继续深入必须有实际入口、调用、数值、工作分配或协作线索。源码已提示可能改变主要值、输出归属、分配、完成或跨工作寿命的机制时，须解决这项疑点，或明确来源不足及受阻判断；不能用泛泛的“未覆盖”放行。可用源码尚未读到、数值或同步关系尚未推清时，先点明下一段需要核实的关系并继续调查，不把研究未完成称为来源缺项。仅因仍有未读代码，不推定必须发现另一套设计。不影响当前主张的未读细节如实限定，后续按需回查。

共享任务事实有误回 [P1](01_contract.md)，不能通过缩小 Contract 降低设计数量。来源缺项及硬件边界沿用[提取总览](../../../EXTRACT_SCHEMA.md#来源缺项与验收边界)。

## reviewer：放行门槛

独立理解 P1 已完成内容、当前 root 的来源与承担范围、dispatch 草案，再从实际入口到输出核对所选实例及有区分性的源码线索。worker 的调查记录帮助定位，不能限定 reviewer 能发现的问题或代替独立止点判断。判断主计算、输出形成、分配和协作是否足以支持代表选择；当前 YAML 计划是否为具体方案，参数、局部差额及组合是否有合理去处。

按[完整设计的保留与降级](../roles/reviewer.md#完整设计的保留与降级)逐项审定候选；可由参数、局部或组合记录表达的差额须降级，不能仅凭不同配置保留完整任务。拟完整集合含 root 不超过十份，每份有独立价值；重要且有据的选型疑点已解决，或明确阻塞受影响选择。草案可读，实际链接有效，未来内容仅获计划认可，不作为已完成定义或共享证明。P2 不批准 root 的完整 Design，也不因它尚未完成要求完整 YAML 检查通过；本阶段自己的草案必须完整。

## 回执与下一位

plan 只登记已选完整集合，每项为 `{id, instance}`；instance 定位具体调用或模板实例。含 root 不超过十项，不能用泛配置族名代替实例。详细机制、差异、取舍理由和证据放在目录及现有 conclusions/evidence/handoff。

在既有回执与 P2→P3 短交接中保留选择理由、关键入口、记录线索、范围和待核实问题，不新增固定报告。回执编码见[工具协议](../operations/response.md)。

放行后进入 [P3](03_root.md)，新开一对 worker/reviewer。worker 按已选实例逐段写 root，reviewer 从当前产物独立建立理解。
