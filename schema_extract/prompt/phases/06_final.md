# P6：全算子终审

本页独立审阅全部当前完整设计与目录记录。先由全新 reviewer 审阅，确需修改时才加入 worker；终审通过才可达到 `ready`。

## 准入与应读材料

P1–P4 前提仍成立，当前选定的完整设计均已完成并独立审阅，实有集合与当前计划一致。准备最终任务目录、完整实际来源、固定源码、适用规则，以及 P2/P4 已识别机制和 P5 新事实的既有记录。单 root 任务也进入本阶段；维护批准或旧 P6 结论不能代替当前终审。

reviewer 按[当前文档验收](../roles/reviewer.md)先读最终 raw 定义、实际引用和目录，从产物独立理解全部有效内容，再用过程记录反查知识去向与待补项。历史批准、旧稿和交接不能补齐最终定义。同一共用定义可按当前实际文件读一次，每个使用节点的范围、绑定、数值、跨区接口和必要 Realization 仍完整覆盖。

## reviewer：先审与放行门槛

全文审阅包含未修改内容；源码复核围绕差异、风险和有据疑点深入。按 [common 的完整集合与记录规则](../../../schema_docs/0.common.md#派生节点与-dispatch)逐项核对：

1. 实有完整集合、目录和当前计划一致，root 唯一，总数含 root 不超过十份；按[保留与降级判据](../roles/reviewer.md#完整设计的保留与降级)核对每份实际内容是否支持已定差异与保留依据。不留未计划的草稿或备份 YAML，不为共享用途增加无独立价值的节点，不将额外完整方案藏在其他目录、扩展名或“历史”中继续交付。
2. 每份均为一套具体、完整的设计，从共同输入贯通到全部输出。参数、局部差额及已有组合已在合适位置记录，没有为少建文件拼接不相容主机制，也没有把多个配置塞进一份 YAML。相同整区按实际 `from` 共享，整个引用图无环；来源与 raw 定义可定位，全部使用上下文成立。
3. 从 P2/P4 的已识别机制和 P5 交接的新事实反查最终去处：完整 YAML、正式变体记录，或有据说明的未展开独立方案/来源边界。每项重要新事实必须已有去处或说明为何不进入当前交付；这项核对不要求新增永久台账。
4. 每条正式记录与实际完整基线及其中已有对象对应，差异、联动、条件和依据成立。组合直接定位完整基线，不依赖层层组合或默认任意配对，不宣称笔记已经成为完整 schema。清理仅计划的未来链接、待绑定对象和临时阶段说明；保留真实的研究取舍和范围限制。
5. 各设计的实际 `when`、来源实现范围、目录收录范围和共同 Contract 分清。范围可以重叠或留空白，root 没有隐式兜底；原任务明确要求的交付范围仍须满足。不能靠缩小 Contract、虚构 fallback 或把原 selector/样本覆盖当作最大成立域掩盖缺口。
6. 核对[来源缺项](../roles/reviewer.md#来源缺项)与[源实现缺陷](../roles/reviewer.md#源实现缺陷与设计分流)：已知验收事实完整，未知内容未被用作保证，限制随最终交付保留。硬件占位和 GPU 边界沿用 [P1](01_contract.md#第-3-段硬件占位)。
7. 完成覆盖最终全目录的适用结构检查，按 `--read-only --skip-hardware` 政策跳过硬件。早先各节点通过不能代替本次全目录检查，检查通过也不能代替全文、来源、条件和记录语义的独立审阅。

无需修改时直接给出终审结论。需要补记录或修正文时，提供证据、具体文件/字段、修改要求及影响范围，交按需 worker 处理，再独立审阅最终全部内容。不能用 P5 没有目录写权限解释最终缺项，也不能自行改稿后替代独立验收。

机制识别或代表取舍须纠正时，先按 REVIEW 的[返回分工](../roles/reviewer.md#发现问题与批准)回 P2，再由 P4 按需落实受影响的集合、目录和依赖；只改变已定代表的登记、依赖或写作安排时回 P4。root 定义错误回 P3，其他完整设计的定义错误超出本阶段授权时交相应 P5，共享 Contract 错误回 P1。相应修复和独立审阅完成后重新满足 P6 准入，未受影响稿件保留；普通记录与明确授权的限域修稿按本阶段处理。

## worker：按需加入与可写范围

reviewer 明确提出修改并确定范围后，才启动新的 P6 worker。读取当前完整产物、具体反馈和必要来源；写作按需使用 [P3 的逐段方法](03_root.md#节点逐段方法)。

只改本次明确列出的任务文件与字段。普通参数、局部、组合及未展开独立候选的记录增补和实际共享摘要，由本 worker 集中更新 `dispatch.md`；正文修订限于明确授权范围。不得修改源码、规范、检查器或运行状态，不把终审任务视为全部文件的任意改写权。随实际内容更新版本，复查真实使用者和依赖该基线的记录，再提交全目录检查与独立终审。

## 回执与下一位

在既有回执中保留完整集合、设计价值、记录去向、实际条件、来源与未决项结论，以及必要证据和实际检查。修改时说明影响与已重新核对内容，不新增固定终审报告或 schema 状态字段。回执及受限写入的编码见[工具协议](../operations/response.md)。

全部验收通过后才能作为正式交付；`ready` 不等于已发布，实际状态与发布操作见[恢复交接](../operations/recovery.md)。最终文件、来源和有效审阅须一致。无法通过时保留草稿、具体阻塞原因及恢复条件，不把未完成稿当正式成果。
