# row_softmax_fp32_v1 acceptance

The ABI is `kernel.py::Model(torch.nn.Module)`, constructed as `Model()`.
`forward(self, x, out)` supports `x=` and `out=` and returns the exact `out`
object after writing its original output region. The complete domain and side
effects are in [contract.yaml](contract.yaml); neither a design nor a candidate
may narrow that domain or weaken these checks.

Both tensors are contiguous CUDA FP32 on one device, with shape `(M,N)`,
stride `(N,1)`, `requires_grad=False`, any legal storage offset, `M in {1,32}`
and `N in {128,1024}`. They have distinct storage. `x` is finite in `[-20,20]`.
Out-of-domain shape, dtype, layout or aliasing is rejected by preparation/the
trusted adapter, not counted as an in-domain failure. Calls use inference mode,
eager execution and a single call stream; CUDA Graph and concurrent streams are
outside this Task. A prepared Model must recompute when legal `x` changes.

Before each call, retain the objects and live original storages/backings;
record storage offset, shape, stride, dtype and device. Save all `x` bytes and
backing guard bytes, and poison the original `out` region. Compute golden from
the saved pre-call FP32 input after promotion to CPU FP64:

```
z = FP64(x_before)
g[i,j] = exp(z[i,j] - max_k z[i,k]) / sum_k exp(z[i,k] - max_l z[i,l])
```

Reject every NaN/Inf output, then require **every** element to satisfy
`abs(FP64(actual)-g) <= 2e-6 + 2e-5*abs(g)`. Read actual values from the
**retained original output backing**, not only from the post-call `out` view.
Check return identity, original out storage/view, full write, x bytes and
storage/view, and all bytes outside the authorized out region independently.
In particular, `out.set_(correct_tmp); return out` fails even if the Python
object and numerical values appear correct. Never copy a returned tensor into
out, normalize offsets, suppress candidate exceptions or repair its side effects.

[inputs.json](inputs.json) enumerates exactly 4 shapes × 9 instances = 36 cases.
Each has one NaN-poison call and one `-123.0`-poison call: **72 basic calls**.
Per shape the instances are random seeds 17 and 23; constants -20, 0 and 20;
alternating extremes; a row-specific single peak; near-equal values; and a
row-permuted ramp. Random values use the locked torch CPU Generator, freshly
`manual_seed(seed)` for each instance, and FP32 `-20 + 40*torch.rand((M,N),
generator=g, dtype=torch.float32, device='cpu')`. Record actual input-byte
digests and torch identity; a seed alone does not identify generated bytes.

Seed 23 has x offset 3 and out offset 5 for both poison values, **within** those
72 calls. Other cases use the explicitly declared offsets in inputs.json.
The guard lengths and patterns there are fixture choices that instantiate the
Task's canary requirement; they do not restrict supported legal offsets.

An additional state-reuse trace reuses one Model, one x storage and one out
storage for two existing legal cases. Between calls the host overwrites the
same x storage, captures a fresh before snapshot and re-poisons the same out.
The selected cases and order are in inputs.json. These two calls are reported
separately and do not change the 36-case/72-call basic accounting.

Minimum rejected candidates include returning a new tensor without writing
out, writing out but returning its clone, replacing out storage, writing only
the first row or omitting the last column, mutating x, and violating tolerance.
FP16 reduction, external softmax and omitted max subtraction are judged against
the **current Schema**. Removing max need not overflow this finite input domain;
a numerical pass cannot establish R0 fidelity.

Build, correctness, coverage and fidelity are independent hard checks. The
complete timing recipe is in [timing.md](timing.md). Complete measurements have
performance status pass; the soft goal is reported separately as met/unmet.
A slower candidate can be completed if all hard requirements pass. A missing
required check remains unknown/not_run and cannot qualify a candidate.

This material set has no GPU/model qualification. A finite set of passing cases
would establish finite evidence, not a proof over all legal real inputs or all
device memory. The public FP32 baseline is not the FP64 oracle and its V0 pass
would not establish compliance with the selected Schema.
