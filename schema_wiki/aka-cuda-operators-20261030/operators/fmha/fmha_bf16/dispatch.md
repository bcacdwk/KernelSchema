# fmha_bf16

本文件是 fmha_bf16 的设计目录。[root](root.yaml) 保存唯一共享 Contract 与一份完整 Design，是默认阅读入口；[split_kv_prefill](split_kv_prefill.yaml)、[mma_sync_decode](mma_sync_decode.yaml)、[tc_prefill_cpasync](tc_prefill_cpasync.yaml) 是与之并列的三份完整设计；三份非 root 文件的 `Dispatch.id` 与四份各自的 `Dispatch.when`、精确参数与修订号以其正文为准。“变体与组合”中每条记录都直接定位这四份 YAML 里已有的数学符号、step、role 与存储对象，只写差额与依据，不改变任何基线的取值或 `when`。

## 范围

**任务要求实现的范围**：root.yaml 共享 Contract 的整个有效域——THD varlen BF16 query、HND 分页 KV、七组 (head_count, kv_head_count, head_dim)、bottom-right causal 与左窗口掩码、可选 sinks、可选 base-2 lse，out 必填并就地写入。

**固定实现实际覆盖的范围**（默认构建、默认环境；solution.py 的 `Model.__init__` 注明实验 knob 在评测中不设置，规划只由 shape 推导）：

- host 入口 `Model.forward` 只在 out 已给、`kv_layout == 'HND'`，且 o_sf_scale / o_sf_vec_size / kv_cache_sf / multi_ctas_kv_counter_buffer / skip_softmax_threshold_scale_factor / use_fp16_softmax / uses_spcompress 全为 None 时进入快路径；其余组合进 `_forward_slow` 并逐条 `ValueError` 拒绝，没有任何回退计算。快路径再校验 dtype（q/k/v/out 为 bf16、lse/sinks 为 fp32、三个索引张量为 contiguous int32）、head-dim 轴单位步长、page_size 为 2 的幂、heads % kv_heads == 0、out/lse 形状，以及 return_lse 为真时 lse 必须存在。
- launch 几何全部由 host 规划并缓存（`Model._plan`，key 为 shape 与标志元组），不读设备张量、不做 device sync；因此 `tiles_ub = total_m // m_tile + batch_count` 带 batch_count 个 slack tile，设备端 `map_tile` 依 cu_seqlens_q 重算真实 tile，并以 `ok == false` 丢弃空 tile。
- 调用方的 workspace_buffer 完全未被使用。split-KV 的 FP32 部分结果放在实现自持的 `Model._ws`（fp32，按需增长、跨调用复用），fused combine 的计数放在自持的 `Model._cnt`（int32，torch.zeros 分配，获胜 CTA 复位自己的槽）。batch_size 与 enable_pdl 不参与计算，cum_seq_lens_kv 只作为缓存条目的身份 pin。
- 设备侧要求 compute capability ≥ 10.0 才构建 tcgen05 库；`fmha_tc.cu` 构建、初始化或 ABI 校验失败时 `_tc` 为 None，规划改走 warp-level mma.sync 内核（此时才可能出现 m_tile 64 的 prefill）。
- host launch 链本身是被测延迟的一部分：编译扩展 fmha_ext.cu 用 slot 记住已打包的 FmhaParams、launcher 函数指针、可选 combine 函数指针与两个 host tensormap，重复同 key 调用只需一次扩展调用；tcgen05 库可通过注册的函数指针自行调用 mma.sync 侧的 `fmha_combine_only`（`_c_in_c`），使一次 split prefill 的两次提交只花一次 host 调用。CUDA graph 录制与重放存在但默认关闭（FMHA_GRAPH、FMHA_EXT_GRAPH 默认 0）；tier-0/tier-1 缓存以对象身份加 data_ptr 双重校验，只决定由哪条链发起同样的 launch，不改变设备工作。
- 执行单元：本目录选定的四份设计只使用 thread / warp / cta（P1 已登记，含 register / smem / tmem 存储名），都不使用 cluster；默认关闭的 2-CTA cluster 与 multicast 方案若日后入选，须先回 P1 登记 cluster 单元。

**本次记录范围**：只记录默认构建下真实可达的机制。默认打开的编译期机制（FMHA_TMA、FMHA_TILE_FOLD、FMHA_TC_PRO2、FMHA_TC_PAGEPRE、FMHA_IMMMAC、FMHA_LDRED、FMHA_IMM_D64、FMHA_CHAIN1、FMHA_EXP_FFMA2、FMHA_PACK2_LSUM、FMHA_PACK2_MUL；FMHA_TC_PAIRMAX 只作用于已被 NH1 行分割取代的 NH2 列分割，默认路径下不生效）属于各设计流水线内部的既有决定，不单独成设计。默认关闭、或在默认构建中被更高优先分支抢先而不可达的 knob 方案，集中在下文“已研究但未完整展开的独立方案”；来源与测量的未核实处集中在“具体未知边界”。

**主要机制与依据**（固定 10 个用例的 NCU 记录已逐 shape 与 `_plan`／`fmha_tc_run`／`fmha_run` 的门控手工核对一致，可直接作为实例证据）：

- GQA/MQA M-packing：所有内核把 (token, group 内 head) 打包为 M 行，`head = kv_head * group + row % group`、`q_idx = row / group`；m_tile 与 tiles_ub 都以打包行计数。
- tile 映射与切分：`map_tile` 由 cu_seqlens_q 前缀和定位 request，并按 causal/window 推出该 tile 的 KV 区间 [lo, hi)；`split_range` 在 splits_ub > 1 时按 tile 自身长度切块，向上取整到 n_tile，并可加“统一工作量”的 chunk 下限。
- 在线 softmax 全程在 base-2 域：`qk_scale2 = bmm1_scale * log2(e)`、exp2、`lse = m + log2(l)` 即 Contract 要求的 base-2 lse；sinks 由稳定的 base-2 logaddexp（`sink_adjust`）在 epilogue 合入并同时缩放输出；lazy O rescale 在 `msafe - mbase < lazy_thresh`（默认 16）时跳过 O 缩放，P 与 l 同基故代数恒等。
- 两条主计算载体：tcgen05（`tcgen05.mma` 把 S/P/O 放在 TMEM，KV 由 bulk-tensor box 或 cp.async 分页搬运）与 warp-level `mma.sync.aligned.m16n8k16`（寄存器累加，KV 由 cp.async 或 bulk-tensor box 搬运）。两者的分页寻址与 SW128 atom-major smem 布局相同。
- 输出形成有三种：主内核直接写 out/lse；主内核写 FP32 部分结果、由独立提交的 `fmha_combine` 归并（PDL 启动，producer 侧 `cudaTriggerProgrammaticLaunchCompletion`，consumer 侧 `cudaGridDependencySynchronize`）；decode 的 fused 变体由每个 (tile, kv_head) 最后到达的 CTA 经 `atomicAdd` 计数获胜后，在内核内调用同一个 `combine_tile`（见“decode 的内核内 fused 归并”记录）。
- 工作分配：grid = (kv_head, tiles_ub, splits_ub)；causal 时 tc 内核反转 tile 序（`tile = tiles_ub - 1 - tile_y`，默认开）形成跨 head 的全局 LPT 序，mma.sync 内核不反转；FMHA_TILE_FOLD（默认开）在 tiles_ub > 65535 时把 tile 折进 grid.z 并由 tc 内核的 `grid_pos` 以 `gridDim.z > splits_ub` 解码，但它只实现在 tcgen05 launcher 与 tc 内核中，且在 Contract 声明的几何与长度域内不会触发（见“grid 映射与 tile 序”记录）。

### 已研究但未完整展开的独立方案

以下方案均已确认机制与可达性，但未交付完整 schema；不称其为参数或局部变化。

- `fmha_tc_main8`（256 线程、8 个 softmax warp 的 NH2 列分割，行最大值经 smem 交换加命名 barrier，无专职控制 warp）：仅在 host 没有 tensormap 时对 d128/d256/d64-NT64 生效（即编码失败），或默认关闭的 FMHA_TC_WS=0／FMHA_TC_EARLY／FMHA_TC_W8_D64 下生效。取舍理由：默认构建没有稳定可达子域，机制上是 root 流水线的“专门化之前”一代。
- `fmha_tc_main8mc`（cluster (1,2,1) 的 multicast 配对，相邻两个 m_tile 128 的 CTA 共享一次 TMA 取数，故一次取数服务 2 × 128 = 256 行；rank0 经 mapa 远端 arm rank1 的 barrier）与其 DH2 变体（配对两个 256 行 tile，一次取数服务 512 行）：默认关闭（FMHA_MC2、FMHA_DH2_MC2 = 0）。取舍理由：默认不可达，且需要 P1 尚未登记的 cluster 执行单元。
- `fmha_tc2`（2-CTA cluster tcgen05 prefill，m_tile 256，`__cluster_dims__(2,1,1)`）：库仅在 FMHA_TC2=1 时构建，默认 `_tc2` 为 None，规划中的 use_tc2 恒假。取舍理由：出厂配置不可达，且同样需要 cluster 登记。
- `fmha_tc_dta`（576 线程、两个 256 线程 softmax 组交替使用两个 S 缓冲、控制 warp 提前两个 stage 预热 QK）：默认关闭，且源码自述实测被否（v1 单控制 warp ×1.56-1.69，v2 双控制 warp ×1.28-1.30）。
- NH4 的 d64 NT128 tile（`fmha_tc_main8ws` 的 NH = 4，544 线程；及 CSPLIT-NH4 576 线程）：knob 默认打开，但 launcher 先判 bit29（NH1），d64 NT128 恒走 NH1，故默认构建不可达。
- TMA_LATE 的选择性实例（FMHA_TC_TLSEL，bit24）：knob 默认打开，但默认构建中不可达——d256 侧 host 因 cs_d256_ok 为真而不置 bit24；d128 NT64 侧只对 splits_ub > 1 置位，而同一形态下 bit29（NH1）与 bit26（CSPLIT）必然置位且 launcher 先判这两者。取舍理由：源码记录其 A/B 为赢（d256 c6 ×0.976-0.985、split-d128 c9 ×0.985），但被更高优先的 NH1/CSPLIT 分支取代，没有剩余可达子域。
- `fmha_main` 的 m_tile 64 prefill（warp-level mma.sync，warp 按 M 分割成 16 行组）：只有 tcgen05 库不可达时才会被规划（FMHA_M16_MAX = 64 使 `total_m <= 64 * batch_count` 的形状一律走 m_tile 16）。取舍理由：属环境/构建失败的退路，记为来源限制而非交付设计。
- tail-split（FMHA_TAILSPLIT，bit30：只切分最重的尾部 tile，把 chunk_floor 抬到最长 tile 范围的约 3/4，未切分 tile 直接写 out/lse 并让 combine 跳过）：默认关闭。它是唯一按设备端 `active == 1` 而非 host 的 splits_ub == 1 判定直接写回的形态（见“不切分时的直接写回”记录）。
- 其余默认关闭的发射顺序／预取深度／数值打包实验：QKFIRST、QKEARLY、wave dephase、PGDEEP、E2E、PACK2_RMAX、DEC_QK4、DEC_QKSHARE、DEC_PIPE、DEC_PACK2、balanced per-tile splits（chunk_target）、TILES_EST、WS_WSYNC。其中数项在源码注释里带有“实测并否决”的结论。

### 具体未知边界

- `_plan` 的门控组合只按代表性形状手工推演（固定 10 例已逐例复算并与 NCU 内核名核对一致），未对 shape_range 全域做穷举枚举。不影响交付：各节点的 `when` 由同一份规划代码写出，上述记录已定位每个门控，剩余只是正文中的取值展开。
- tensormap 编码在目标设备上是否真的可能失败（`rc_enc != 0` → kp/vp 归零 → 退回 cp.async／main8 内核），来源只按异常处理、没有实测样本。若它是真实运行条件，`fmha_tc_main8` 就成为可达设计，需回 P2 补选择；当前按来源限制记录，不为其补造设计。
- fused combine 依赖计数缓冲在调用之间保持为零：`Model._cnt` 由 torch.zeros 分配、获胜 CTA 复位自己的槽，源码没有其他重初始化。若某次 launch 在 atomicAdd 与复位之间被放弃，后续调用可能选错获胜者。mma_sync_decode 的 `when` 以 `splits_ub * m_tile * dv > 24576` 排除 fused 形态，其正文因此不写计数缓冲，这是正确的分工；这项跨调用状态依赖由“变体与组合”中“decode 的内核内 fused 归并”记录按资源初态、寿命与失败后果完整承载（评测的 restore 不覆盖它），不影响其余三份设计的成立条件。
- root 的 `when` 与本目录的波次、DH2、NH4 条件都引用多处理器数，而共享 Hardware_specification 的 Device/Architecture 仍是 P1 占位；各节点沿用同一占位量，不在此补造硬件数值。
- NCU 记录来自被认证构建；其内核名与 grid 与当前固定源码的 dispatch 一致（已逐例核对），可作为实例证据，但绝对耗时属另一环境的测量（该设备多处理器数为 148），本次提取不据其做硬件结论。

## 完整设计

含 root 共四份完整设计，非 root 三份，均在 common 的十份上限内；每份保留一项其他份无法表达的完整设计价值（输出形成链、主计算载体与工作划分、主协作组织）。

| 设计 | 具体机制与保留理由 | 关系 |
| --- | --- | --- |
| [root](root.yaml) | tcgen05 warp-specialized prefill：m_tile = 128 打包行，一个 CTA 负责一个 (kv_head, m-tile) 的整段可见 KV。角色为 TMA_LEAD 控制 warp（分页 bulk-tensor box 发射、mbarrier arm、page 表预取）、MMA_LEAD 控制 warp（KV/P 等待、全部 `tcgen05.mma` 发射与 commit，保持 PV(s) 先于 QK(s+1) 的承载性顺序）、以及 NH1 行分割的 4 个 SOFTMAX warp（128 行、每线程一行、整段 n_tile 列在寄存器内，TMEM 融合 load-reduce 取行最大值，exp2 后把 P 打包回按 stage 奇偶双缓冲的 TMEM 区，lazy O rescale）。存储为 smem 的 q_smem 加 SB = 2 的 k_ring/v_ring，TMEM 的 s_tmem｜p_tmem｜o_tmem 共 256 列；splits_ub == 1，SOFTMAX 的 epilogue 直接写 bf16 out 与 base-2 lse。实例：`fmha_tc.cu::fmha_tc_main8ws<D=128, NT=64, SB=2, MINB=2, TMA=true, QKFIRST=false, QKEARLY=false, NH=1, TL=false, CS=true, DH=1, MC=false>`（192 线程、100 992 B 动态 smem、2 CTA/SM），由 `fmha_tc_run` 的 bit26+bit29 分支在 d128/n_tile 64 且已编码 tensormap 时启动。splits_ub == 1 且不翻 DH2 的可达见证：batch 1、q 1500、kv 1500、heads 16/kvh 4、d128、causal → tiles_ub 47、base_blocks 188 ≥ causal 波次目标（一个驻留波 = 多处理器数，实测设备 148）故不切分，且 tiles256 × kv_head = 96 不足一个波次故 m_tile 保持 128（同一模板实例在固定用例 9 以 splits_ub = 4 出现，那一形态属 split_kv_prefill）。保留理由：认证构建 prefill 侧的主机制，且是 tcgen05 流水线最简完整形态（单段 KV、无部分结果、无第二次提交），适合作阅读与比较入口。 | 阅读入口，保存唯一 Contract |
| [split_kv_prefill](split_kv_prefill.yaml) | 同一套 warp-specialized tile 流水线，但把 tile 的 KV 区间按 `split_range` 切到 grid.z：每个 CTA 只算一段，把 FP32 的 O 行与 (mbase, l) 写入实现自持的部分结果缓冲 part_o/part_ml，触发 `cudaTriggerProgrammaticLaunchCompletion`，再由第二次提交的 `fmha_combine` 按 `exp2(m_s - m*)` 权重归并，写出 bf16 out 与 base-2 lse。实例：与 root 同一模板实例 `fmha_tc.cu::fmha_tc_main8ws<128,64,2,2,true,false,false,1,false,true,1,false>` 在 splits_ub > 1 的调用 + `fmha_kernel.cu::fmha_combine<PDL=true>`（256 线程，grid = (kv_head, tiles_ub, combine_z)，combine_z 由 float4 通道数与 2 × 多处理器数推出）。combine 的链式方式是跨库注册：host 用 `fmha_tc_set_combine` 把 mma.sync 库的 `fmha_combine_only` 地址登记进 tcgen05 库，`fmha_tc_run` 在主内核之后直接调用该指针（`_c_in_c` 为真），一次 host 调用发两次提交；注册不可用时改由 host `_launch` 发第二次调用。固定用例 9 实测 main grid 8×9×4、combine grid 8×9×5。保留理由：部分结果加跨内核归并改变了输出的生产者、增加了一个工作轴与一次提交，按 common 的差异判断属需要完整方案的新整体设计，不能记为参数。 | 与 root 并列；主循环机制同源，输出形成链不同 |
| [mma_sync_decode](mma_sync_decode.yaml) | 短 query（decode/MTP）路径，位于 fmha_kernel.cu：m_tile = 16 打包行（一个 tile 可以就是单 token 的整个 head group），warp 按 N 分割——NSL = n_tile/16 个 16 列 KV 片，head_dim 256 时再分 NDV = 2 个 dv 半区并重复计算 QK；每个 warp 对自己的 KV 片独立跑在线 softmax 并持有私有 FP32 O 累加器，epilogue 先在 smem 做跨 warp 归并（各 warp 的 (m, l) → m*、`sc = exp2(m_w - m*)`、`l = Σ l_w sc_w`、`O = Σ O_w sc_w`），再走与 split_kv_prefill 相同的部分结果 + `fmha_combine` 归并。KV 由 STAGES 级 cp.async 16B 单元分页搬运，或在 `max_kv_len >= 8 * n_tile` 时由 bulk-tensor box 加每槽 mbarrier 搬运。实例：`fmha_kernel.cu::fmha_main<DQ=128, DV=128, MT=16, NT=64, STAGES=3, WNSPLIT=true, FUSE=false, MINB=1, TMA=true>`（128 线程 = 4 warp）+ `fmha_combine<PDL=true>`，固定用例 5 实测 main grid 1×9×16、combine grid 1×9×2；head_dim 256 用 8 warp（256 线程），用例 2 实测 splits 37。combine 的链式方式与 split_kv_prefill 不同：它不经跨库注册，而是 `fmha_run` 在同一库内原生调用 `fmha_combine_only`（splits_ub > 1 且非 m_tile 16 的 fused 形态），host 同样只发一次调用。工作序以函数体 `tile = blockIdx.y` 为准（源码注释声称 causal 反转，实现没有）。保留理由：主计算载体（warp-level `mma.sync.aligned.m16n8k16`）、工作划分（N 分割而非行归属）与输出形成（跨 warp smem 归并）都不同，且规划器把 `total_m <= 64 * batch_count` 的形状一律交给它（固定 10 例中的用例 2、3、5、8），是这些短 query 形状的唯一覆盖。 | 与 root 并列，独立方案；部分结果布局与 `combine_tile` 同 split_kv_prefill，但两节点各自本地定义 |
| [tc_prefill_cpasync](tc_prefill_cpasync.yaml) | 非 warp-specialized 的 tcgen05 prefill：128 线程、每线程一打包行，TMEM 的 S｜P｜O 流水线与 root 同族，但没有生产者/消费者角色划分——KV 由全部 128 线程协作以 cp.async 16B 单元分页搬运（默认 loader 每 16B 单元各自做一次 page 表 `__ldg` 与 int64 步长链），而全部 `tcgen05.mma` 只由 thread 0 发射，整个 CTA 在每个 stage 边界以 `__syncthreads()` 汇合；不使用 tensormap，KV 就绪由 cp.async commit-group 计数证明——stage 循环内为 `cp.async.wait_group (SB >= 3 ? 2 : 1)`、序幕为 `(SB >= 3 ? 2 : 0)`，故所选 SB = 3 实例的等待深度为 2（源码另有 `WAITN = 2 * SB - 3` 常量与文件头注释，全文件未被任何等待引用，SB = 3 时它给 3 而与实现不符，正文以函数体为准）；只有 QK/PV 的完成仍走 `tcgen05.commit` 加 mbarrier 握手。实例：`fmha_tc.cu::fmha_tc_main<D=64, NT=128, SB=3, TMA=false>`，由 `fmha_tc_run` 末尾无 tensormap 的 d64/NT128 分支启动（d64 的 W8 位默认关闭，故不落 main8）。默认构建下的可达条件：d64 prefill 且 n_tile 保持 128（CS-NH1-d64 的 n_tile 翻转被门控掉，即 window_left >= 0 或每 split 的估计 chunk < 2048 keys），同时 host 不编码 tensormap（splits_ub > 1，或 tiles_ub × kv_head_count > 2 × 多处理器数使 NH4 门控失效，而 FMHA_TC_D64_TMA 默认关闭）。splits_ub == 1 的可达见证：batch 1、q 4096、kv 4096、heads 12/kvh 12、d64、causal、window_left 1023 → tiles_ub 33、base_blocks 396 ≥ causal 波次目标故不切分，窗口使 n_tile 翻转门控不成立，且 396 > 2 × 148（实测设备多处理器数）使 NH4 门控失效，故 host 不编码 tensormap。保留理由：主协作组织不同（单链发射 + CTA 屏障，而非专职 warp + mbarrier 握手），且是该子域的唯一覆盖；无法围绕 root 的既有 role 与存储说清，不构成局部记录。 | 与 root 并列，独立方案；`when` 保守取 splits_ub == 1，切分形态见“非 specialized prefill 加 split-KV”记录 |

三份非 root 文件的 `Dispatch.id` 与四份各自的 `Dispatch.when`、精确参数与修订号以 YAML 正文为准；本表摘要只固定实例、主要机制与保留理由。

## 变体与组合

本节八条记录按类型标注，每条直接定位 [root](root.yaml)、[split_kv_prefill](split_kv_prefill.yaml)、[mma_sync_decode](mma_sync_decode.yaml)、[tc_prefill_cpasync](tc_prefill_cpasync.yaml) 中已有的对象；同一变化适用于多个基线时并列链接，共同差额只写一次。记录不修改任何基线的参数或 `when`，实施某项变化时以其正文为准并自行核对本处列出的联动。

### DH2 双 M 半区（局部）

- 基线：[root](root.yaml) 的 `DESIGN.Tile_pipeline::MAIN` 角色 SOFTMAX／TMA_LEAD／MMA_LEAD 与存储 q_smem、k_ring、v_ring、s_tmem、p_tmem、o_tmem，以及 `DESIGN.Work_schedule::MAIN.Decomposition`（m_tile、tiles_ub）和 `REALIZATION.Require` 中 Item 为 `DESIGN.Tile_pipeline::MAIN.SOFTMAX` 的那条（256 TMEM 列、192 线程、100 992 B 动态 smem、最少 2 CTA/SM）。
- 差异与联动：m_tile 由 128 变 256，一个 CTA 内两个互相独立的 128 行半区共享同一条 K/V 流。q_smem 翻倍为 `128 · 2 · D · 2` 字节；SOFTMAX 由 4 warp 增至 8 warp，warp 0-3 拥有行 0-127、warp 4-7 拥有行 128-255，CTA 线程 192 → 320；每半区有自己的 s_tmem｜p_tmem｜o_tmem 与 qk/pv/sfree/pre barrier 组，TMEM 由 256 列升到 512 列，MINB 由 2 降为 1（smem 133 760 B，1 CTA/SM）。Work_schedule 侧 tiles_ub 改为 `total_m // 256 + batch_count`，grid.y 随之减半，Partition 与 Worker_count 同变；TMA_LEAD 与 MMA_LEAD 的每 stage 取数与发射不变，故 KV 流量按 MAC 减半。数学仍是 root 的 base-2 在线 softmax 与 lazy rescale，行状态按半区独立。若叠加切分（FMHA_DH2_SPLITS，默认关闭），归并按 128 行半 tile 走，combine 的 grid.y = tiles × halves。
- 条件与依据：d128 NT64、splits_ub == 1、window_left < 0、`(total_m // 256 + batch_count) * kv_head_count >= 多处理器数`、`total_m // 256 + batch_count <= 65535`；实例 `fmha_tc.cu::fmha_tc_main8ws<128,64,2,1,true,false,false,1,false,true,2,false>`，由 `fmha_tc_run` 中唯一接受 m_tile 256 的分支启动。固定用例 1 与 7 实测走此路径（NCU grid 分别为 (8,50,1) 与 (8,33,1)，block 320），源码同作业 A/B 记录 c1 ×0.9254、c7 ×0.986-0.989，out 与 lse 逐位相同。窗口 prefill 被显式排除：源码记录带左窗口时全掩码前导 stage 的 lazy-rescale 状态轨迹（mbase 由 -inf 落 0）依 tile 几何而变，range sweep shape 4 实测 1-2 bf16 ulp 的 out 漂移与 6.4% 的 lse ulp 漂移，故窗口形状不得声称与 root 逐位相同。

### grid 映射与 tile 序（参数）

- 基线：[root](root.yaml) 的 `DESIGN.Work_schedule::MAIN.Mapping` 与 `Schedule`（Partition 的 kv_head、tile_y，`Schedule.Strategy` 中的 `tile = tiles_ub-1-tile_y`，Worktile_order）以及 `Flow.Launch`。
- 差异与联动：默认关闭的 FMHA_GRIDORDER = 2（dispatch bit14）交换两轴，使 tile 落在 gridDim.x、kv_head 落在 gridDim.y，tile 成为最快轴，以便在评测的逐次 L2 驱逐下让并发窗口只含一个 kv_head 的 KV；该模式 tile 走 x（上限 2^31），不需要折叠。默认打开的 FMHA_TILE_FOLD 只在 tiles_ub > 65535 时把 tile 折进 grid.z（grid = (kv_head, ceil(tiles_ub / fold), splits_ub · fold)），设备端 `grid_pos` 以 `gridDim.z > splits_ub` 识别并还原 (tile, split)。两者都只实现在 tcgen05 launcher `fmha_tc_run` 与 tc 内核的 `grid_pos`；mma.sync 侧 `fmha_run` 恒为 grid = (kv_head, tiles_ub, splits_ub)，既不折叠也不反转 tile 序（函数体取 `tile = blockIdx.y`，注释里的 LPT 说法与实现不符），这一点由 [mma_sync_decode](mma_sync_decode.yaml) 的 `DESIGN.Work_schedule::MAIN.Schedule.Strategy` 与 `Worktile_order` 按自己的调度写实。三者都只是 block→工作的排列，每 tile 的计算、输出与提交次数不变。
- 条件与依据：源码把折叠说成合规必需，举的角是 batch 32 × q 8192 × heads 32/kvh 1（total_m 8 388 608 → tiles_ub 65 568 > gridDim.y 的 65535 上限），但该 heads/kv_heads 组合不在 Contract 的七组几何内；按声明域（total_q ≤ 16384、group ≤ 16）total_m ≤ 262 144，m_tile 128 时 tiles_ub ≤ 2 080、m_tile 256 时 ≤ 1 056、m_tile 16 时 ≤ 16 416，故 fold 在 Contract 域内恒为 1，grid 与未折叠逐位相同（源码亦称 fold > 1 蕴含 splits_ub == 1，故不影响归并）。因此折叠按“默认打开但在本 Contract 域内不触发的既有保护”记录，不作为任何节点的必要工作分配机制。反转的取舍依据是源码 A/B：causal 的 1:T 工作梯度下反转为赢，非 causal 的双峰混合实测回退（c4 .2315 → .3021），故 root 只在 causal 时反转。

### tile 几何与占用参数（参数）

- 基线：[root](root.yaml) 的 `DESIGN.Work_schedule::MAIN.Decomposition.Strategy`（m_tile = 128、n_tile = 64、tiles_ub）、`DESIGN.Tile_pipeline::MAIN.Storage` 各区的 shape／depth／total_size，与 `REALIZATION.Require` 中 Item 为 `DESIGN.Tile_pipeline::MAIN.SOFTMAX` 的那条（256 TMEM 列、192 线程、100 992 B 动态 smem、最少 2 CTA/SM）。
- 差异与联动：同一 warp-specialized tcgen05 流水线在其他 (head_dim, n_tile) 上的实例化——d64 NT64（MINB 2、2 CTA/SM、192 线程；固定用例 4，splits_ub = 2 故另带 combine）、d64 NT128（MINB 1、1 CTA/SM、192 线程；用例 0）、d256 NT64（MINB 1、1 CTA/SM、192 线程；用例 6）。联动集中在三处预算：TMEM 列数 = `2 · n_tile + head_dim`（s_tmem 占 n_tile 列、p_tmem 的两个奇偶缓冲共占 n_tile 列、o_tmem 占 head_dim 列），不超过 256 才申请 256 列并可能 2 CTA/SM，否则申请 512 列并退到 1 CTA/SM；动态 smem = `fmha_tc_smem` = Q 的 `128 · DH · D · 2` + KV 环的 `SB · 2 · n_tile · D · 2` + 128 B barrier 区 + 跨 warp 交换尾部（d ≥ 128 或 8-warp 形态 2304 B，NH4 形态 4352 B）+ `n_tile · 4` 的 page 表尾部；MINB 与每线程寄存器预算共同决定实际驻留，Storage 各区的 total_size 随之改写。KV 环深度 SB = 2（默认关闭的 FMHA_DH2_SB 只在 DH2 下给 3 或 4）。d64 的 n_tile 由 host 在 128 与 64 之间选择：仅当 window_left < 0 且每 split 的估计 chunk ≥ 2048 keys 时翻到 64，翻转后 splits_ub 不变（want 与各 cap 在此门控成立的区间内都与 n_tile 无关）。
- 条件与依据：`fmha_tc_init` 的实例化列表、`fmha_tc_smem` 与 `fmha_tc_run` 的各分支给出实际组合；固定 10 例覆盖其中大部分——tcgen05 侧用例 0（d64 NT128 MINB1）、4（d64 NT64 MINB2）、6（d256 NT64 MINB1）、1 与 7（d128 NT64 DH2 MINB1，见上一条记录）、9（d128 NT64 MINB2 的切分形态，属 [split_kv_prefill](split_kv_prefill.yaml)），mma.sync 侧用例 2（d256 decode，8 warp，STAGES 3）、3 与 5（d128 decode，4 warp，STAGES 3）、8（d64 decode，4 warp，STAGES 4）。decode 侧的同类参数（STAGES：d64 为 4、d128/d256 为 3；NWARP：4，d256 为 8 且 NDV = 2 重复计算 QK；n_tile：64，32 只在默认关闭的 FMHA_D256_NT32／FMHA_DEC_D256W4 下出现；`fmha_smem` = `m_tile · D · 2 + STAGES · n_tile · (D + DV) · 2`，m_tile 16 时再与跨 warp 归并暂存取大者并留 TMA 对齐余量）由 [mma_sync_decode](mma_sync_decode.yaml) 自己的 `DESIGN.Work_schedule::MAIN.Decomposition.Strategy`（m_tile 16、n_tile 64、3 个 KV stage）、`DESIGN.Tile_pipeline::MAIN.Storage`（q_smem、三槽 k_ring/v_ring、q_frag／s_frag／p_frag／o_reg、覆盖在已排空 KV 环上的 merge_smem）与 `REALIZATION.Require` 中 128 线程／103 552 B 动态 smem 的那条写实，与本条并列。

### decode 的内核内 fused 归并（局部）

- 基线：[mma_sync_decode](mma_sync_decode.yaml) 的 `DESIGN.Work_schedule` 两步 `MAIN`／`COMBINE`、`Flow.Launch` 的两次提交与 `Flow.Handoff` 的 o_chunk／m_star／l_chunk，`DESIGN.Tile_pipeline::MAIN.MAIN` 的 `store:partials` 与 `signal:launch_trigger`，以及 `DESIGN.Tile_pipeline::COMBINE.MAIN` 的 `compute:row_stats`／`compute:split_weight`／`compute:o_sum`／`store:outputs`。
- 差异与联动：取消 COMBINE 这次提交——`Flow.Launch` 只剩 MAIN 一项，`Flow.Handoff` 三条随之消失；部分结果仍写进同一 o_chunk／m_star／l_chunk 缓冲，但只由本内核读取。`store:partials` 之后插入一次 `__threadfence()` 加 CTA 汇合，由 thread 0 对 `counters[tile * kv_head_count + kv_head]` 做 `atomicAdd(..., 1)`，读到 `active - 1` 的 CTA 获胜；`signal:launch_trigger` 不再需要。获胜 CTA 在自己的内核内执行与 COMBINE 相同的 `combine_tile` 归并，实参取 zrank 0、zsplit 1、row0 0，即一个 CTA 覆盖该 (tile, kv_head) 的全部行与全部通道，因此 `compute:split_weight` 的 64 块窗口循环与 `store:outputs` 的表达式照常成立，只是执行者换成主内核自己的线程数（固定用例中为 128）与已排空的 KV 环 smem，而不是独立的 256 线程 grid；落选 CTA 立即退出。联动还包括：FUSE 必须是独立模板实例——源码记录把 `combine_tile` 内联进非 fuse 实例会在 `__launch_bounds__(256)` 下溢出寄存器，改 `__noinline__` 则每个调用点都 IMA；launcher 只在 m_tile 16 且 fuse 位（`_pad2 & 4`）打开时跳过第二次提交。
- 条件与依据：m_tile 16、splits_ub > 1 且 `splits_ub * m_tile * dv <= 24576`（FMHA_FUSE_MAX 默认值）。固定用例 3（main grid 4×16×5）与用例 8（main grid 2×30×4）的 NCU 记录只有 `fmha_main<..., FUSE=true, ...>` 一个内核、没有任何 combine 内核；用例 2（splits 37、dv 256 → 151 552）与用例 5（splits 16、dv 128 → 32 768）超过阈值走独立 COMBINE，两者的 NCU 记录都出现 `fmha_combine`。计数缓冲的初态与寿命是本记录成立的必要条件：`Model._cnt` 只在缺失、容量不足或换设备时由 torch.zeros 分配 `max(tiles_ub * kv_head_count, 4096)` 个 int32，此后跨调用复用且不再初始化；设备端唯一的清零动作是获胜 CTA 的 thread 0 把自己那一槽写回 0，所以“每槽在一次完整归并后回到零”完全依赖上一次调用跑完。评测的 restore 不覆盖它：若某次 launch 在 atomicAdd 与获胜者复位之间被放弃，该槽留下脏计数，后续同 (tile, kv_head) 的调用要么提前选出获胜者（归并读到尚未写完的部分结果），要么再也读不到 `active - 1`（该 tile 不写 out/lse）。mma_sync_decode 的 `when` 以 `splits_ub * m_tile * dv > 24576` 排除本形态，其正文因此不含计数缓冲，这项跨调用状态依赖作为来源限制由本记录承载。

### 不切分时的直接写回（局部）

- 基线：[split_kv_prefill](split_kv_prefill.yaml) 与 [mma_sync_decode](mma_sync_decode.yaml) 的两步结构——`DESIGN.Work_schedule` 的 `MAIN`／`COMBINE`、`Flow.Launch`、`Flow.Handoff`，以及各自 `DESIGN.Tile_pipeline::MAIN` 中写部分结果的动作（`SOFTMAX::store:o_part`／`store:ml_part`／`signal:grid_trigger` 与 `MAIN::store:partials`／`signal:launch_trigger`）；同一差额在 tcgen05 prefill 侧已由 [root](root.yaml) 完整表达（只有 `MAIN` 一步、`Flow.Launch` 单项、无 `Handoff`，`SOFTMAX` 的 `compute:epilogue` 直接写 out/lse）。
- 差异与联动：host 规划给出 splits_ub == 1 时，`split_range` 直接返回整段 [lo, hi) 且 active = 1，grid.z = 1；MAIN 的 epilogue 改走直接写回分支——按 `inv = bmm2_scale / l`（有 sinks 时再乘 `sink_adjust` 给出的 os）写 bf16 `out_result`，并写 `lse_result = m + log2(l)`，即 root 的 `DESIGN.Math_reshape::Value scale, sinks and output writeback` 与两个切分节点的 `Cross-chunk merge` 在 active = 1 时的同一组表达式。部分结果不写、COMBINE 不提交，`Handoff` 与 PDL 的触发／等待全部消失，实现自持的 `Model._ws` 也不分配（ws_floats = 0）。判定量是 host 的 splits_ub，不是设备端每个 tile 自己的 active：默认构建下（bit30 关闭）active == 1 的 tile 在 splits_ub > 1 的 launch 中仍然写 part_o/part_ml 并由 COMBINE 归并。
- 条件与依据：base_blocks = tiles_ub × kv_head_count 不低于波次目标即不切分（decode 侧 2 × 多处理器数，base_blocks < 32 时 4 × 多处理器数，d64 用 240；tc prefill 侧 causal 用一个波次、非 causal 用两个），或长度 cap 把 splits 压回 1（见“split 策略取值”）。root 与 tc_prefill_cpasync 的 `when` 已各自把 splits_ub == 1 写成条件，本记录只服务于两个切分节点的 `when` 边界与 epilogue 分支。唯一按设备端 active 判定直接写回的形态是默认关闭的 tail-split（bit30，同时让 combine 对 active == 1 的 tile 直接返回），已在“已研究但未完整展开的独立方案”中记录。

### split 策略取值（参数）

- 基线：[split_kv_prefill](split_kv_prefill.yaml) 的 `DESIGN.Work_schedule::MAIN.Decomposition.Strategy`（chunk、tiles_ub）、`Mapping.Strategy` 的 active、`DESIGN.Math_reshape::Per-tile key window, split chunks and stage grid` 中绑定 `splits_ub`／`chunk`／`active` 的符号，与 `DESIGN.Work_schedule::COMBINE.Decomposition.Strategy`（nch、c_lo／c_hi、per_z）；[mma_sync_decode](mma_sync_decode.yaml) 的 `DESIGN.Math_reshape::Per-tile key window, split chunk and stage grid` 中绑定 `split_count`／`chunk_floor` 的符号、`DESIGN.Work_schedule::MAIN.Schedule.Strategy` 与 `COMBINE.Mapping.Strategy` 的 per_z；[root](root.yaml) 的 `Dispatch.when` 只用到“不切分”这一侧的判据。
- 差异与联动：这些取值全部由 host 的 `Model._plan` 决定。波次目标：decode 2 × 多处理器数，base_blocks < 32 时 4 × 多处理器数，d64 用 240；tc prefill causal 用一个波次并配合整波填充 `want = (2 × 多处理器数 + base_blocks // 2) // base_blocks`，非 causal 用两个波次；其余情形 `want = ceil_div(target, base_blocks)`。上限三个：`max_kv_len // (2 * n_tile)`、`max_kv_len // 512`（host 侧 `Model._chunk_floor`，只服务于这个上限）与 splits_cap 64，另有仅 base_blocks ≤ 2 的 decode 才启用的 wavefill 把有效上限抬到 `min(128, max(64, ceil_div(多处理器数, base_blocks)))`；`splits_ub = min(want, 各上限)`。combine 的通道分块 `combine_z = min(64, max(ceil_div(nch_max, 8), min(z_par, nch_max)))`，其中 `nch_max = ceil_div(m_tile * dv / 4, 256)` 按满 tile 的行数算，`z_par = ceil_div(2 × 多处理器数, tiles_ub × kv_head_count)`；host 这行旁的注释“device MAXI=8”已陈旧，设备端 `combine_tile` 的 `MAXI` 为 4，即每线程每组处理 4 个 float4 通道块，通道分块以函数体为准（split_kv_prefill 的 `COMBINE.Mapping.Strategy` 中 `g_count` 按 4 个块一组即此值）。设备端 `FmhaParams.chunk_floor` 是另一个量：它取 host 的 `chunk_floor_keys`（默认 1280 keys），`split_range` 用它把每块抬到统一工作量，`FmhaParams.chunk_round` 即 n_tile；两个同名概念不要混写。
- 条件与依据：`Model._plan` 中每个取值都附有源码同作业 A/B 记录；固定用例的 splits_ub——2 的 37、5 的 16、9 的 4、4 的 2、3 的 5、8 的 4——与 combine_z（用例 2 为 4、用例 5 为 2、用例 9 为 5；用例 3、8 为 fused 无 combine）都可由这些公式复算并与 NCU grid 一致。两处只有推导依据、没有实测样本。其一，combine_z 是按满 tile 的 `m_tile * dv` 规划的矩形上界，而 combine 内部每个 tile 用自己的 mrows 算 `nch = ceil_div(mrows * dv / 4, 256)`、`per_z = ceil_div(nch, combine_z)`，故尾部 channel slice 可以完全没有输出工作：用例 9 的 combine grid 为 8×9×5，满行 tile 的 nch = 16、per_z = 4，slice 4 的 c_lo = 16 已达上界，通道循环一次都不进（该 CTA 仍推导 tile 几何、等 producer 并算行统计，但不写 out/lse），而最后一个 tile 只有 1 行、nch = 1，只有 slice 0 非空。其二，设备端 chunk_floor 只在 `tiles_ub * min(splits_ub, ceil_div(eff, chunk_floor_keys)) >= 多处理器数` 时保留、否则归零以防饿死机器（eff 为 max_kv_len，有左窗口时取 `min(max_kv_len, window_left + 1 + max_q_len)`）：用例 9 的 `9 × 4 = 36 < 148` 与用例 4 的 `20 × 2 = 40 < 148` 都使其归零，故 tcgen05 切分侧 floor 生效的子域（split_kv_prefill 的 `chunk` 取 floor 那一支）在固定 10 例中没有实测样本；decode 侧只有用例 2（`16 × 26 = 416 >= 148`）保留 1280，有实测覆盖。

### KV 搬运方式互换（局部）

- 基线：[mma_sync_decode](mma_sync_decode.yaml) 的 `DESIGN.Tile_pipeline::MAIN.Storage` 中三槽 k_ring／v_ring 与 `MAIN` 角色的 `load:kv`／`await:kv_ready`（所选实例是 bulk-tensor box 形态），及其 `REALIZATION.Require` 中 `cp.async.bulk.tensor.4d` 那条；[tc_prefill_cpasync](tc_prefill_cpasync.yaml) 本身已是 cp.async 形态（`MAIN` 角色的 `load:key`／`load:value` 与 `REALIZATION.Require` 中 16 字节 `cp.async.cg` 单元那条）；[root](root.yaml) 的 `TMA_LEAD::load:key`／`load:value` 固定为 bulk-tensor 形态。
- 差异与联动：以 cp.async 16B 单元的分页 gather（默认 loader 每单元各自做一次 page 表 `__ldg` 加 int64 步长链，就绪由 commit-group 计数证明：每 stage 的 key 与 value 发射点各闭一个 group、即使为空也闭，等待深度固定为 2）替代 bulk-tensor box（每 `R = min(n_tile, page_size)` 行段解析一个 page、发射覆盖该段的 box，以每槽 mbarrier 的 expect_tx 证明就绪）。两者写入同一个 SW128 atom-major smem 布局（`amo`／`swz`），故 k_ring／v_ring 的 shape、depth 与 mma 的 smem descriptor、数值路径都不变；变的是 `load:*` 的 execution_mode、`await:kv_ready` 的证明方式（mbarrier 相位 → `cp.async.wait_group`）与 `REALIZATION.Require` 中相应的指令及 `fence.proxy.async` 位置。源码另有两个被实测否决的 cp.async 变体（warp 协作广播行基址、page 常驻 smem）。
- 条件与依据：decode 只在 `max_kv_len >= 8 * n_tile` 时编码 tensormap（源码记录 b5 边界：14.5 µs TMA vs 12.0 µs cp.async），stage 数很少时 cp.async 更省；固定 10 例的四个 decode 用例（2、3、5、8）max_kv_len 都远超 `8 * n_tile`，故 cp.async 形态在 decode 侧只有推导依据、没有实测样本。tcgen05 侧 tensormap 编码失败也会退回 cp.async 内核（该失败是否真实发生见“具体未知边界”）。

### 非 specialized prefill 加 split-KV（组合）

- 基线：[tc_prefill_cpasync](tc_prefill_cpasync.yaml) 的 `DESIGN.Tile_pipeline::MAIN`（单角色、thread 0 独发、每 stage CTA 屏障）与 [split_kv_prefill](split_kv_prefill.yaml) 的 `DESIGN.Work_schedule`（`MAIN` 的 split 分区与 chunk、`COMBINE` 步、`Flow.Launch` 的两次提交、`Flow.Handoff`）及其 `DESIGN.Tile_pipeline::COMBINE`。
- 差异与联动：两者接口相容——同一 `FmhaParams`、同一设备端 `split_range` 与部分结果布局（part_o／part_ml，行内步长 `round_up(splits_ub, 4)`）、同一 `combine_tile`；tcgen05 launcher 对任何 splits_ub > 1 的分支都在主内核之后调用同一个注册的 combine 指针。组合只需把 split_kv_prefill 的 grid.z 切分、部分结果 epilogue（以 `store:o_part`／`store:ml_part` 加 PDL 触发代替直接写 out/lse）与 COMBINE 步接到 tc_prefill_cpasync 的 tile 流水线上：其 `load:key`／`load:value`／`matmul:*` 与 softmax 链一字不改，只在 `Pipe` 入口加 `split < active` 判定。tc_prefill_cpasync 自身的 `when` 因此保守限定 splits_ub == 1，本组合不改动其正文。
- 条件与依据：默认可达子域为 d64 prefill、n_tile 保持 128（window_left >= 0，或每 split 的估计 chunk < 2048 keys）且 splits_ub > 1——此时 NH4 门控因 splits_ub > 1 失效，d64 NT128 的 tensormap 不编码（FMHA_TC_D64_TMA 默认关闭），launcher 落到无 tensormap 的 `fmha_tc_main<64,128,3>` 分支并在其后调用 combine。见证：batch 1、q 512、kv 8192、heads 8/kvh 2（group 4）、d64、causal → total_m 2048、tiles_ub 17、base_blocks 34 < 148，整波填充给 `want = (2 × 148 + 17) // 34 = 9`，caps 为 32／16／64 → splits_ub = 9；估计 chunk = (8192 − 256) // 9 = 881 < 2048 故 n_tile 保持 128；splits_ub > 1 使 NH4 门控失效 → 无 tensormap → `fmha_tc_main<64,128,3>` 加 `fmha_combine`。固定 10 例未覆盖该组合：两个 d64 prefill 用例都编码了 tensormap，用例 0 因 splits_ub == 1 且 `tiles_ub × kv_head = 204 <= 2 × 148` 走 warp-specialized 的 d64 NT128 分支，用例 4 因 n_tile 翻到 64 走 warp-specialized 的 d64 NT64 分支（NCU 实测 `fmha_tc_main8ws<64,64,2,2,...>` 加 `fmha_combine`）。依据为 `_plan` 与 `fmha_tc_run` 的门控推导。
