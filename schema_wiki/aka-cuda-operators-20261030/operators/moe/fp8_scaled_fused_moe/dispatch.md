# fp8_scaled_fused_moe

## 范围

**实现范围。** 固定实现是 `candidate/solution.py::Model.forward` 编译并加载 `candidate/moe_kernel.cu`，经单一 C ABI 入口 `moe_launch`（24 指针 + 13 整数 + stream）驱动的多 kernel 主机派发链。Python 侧只做参数归一（dtype/contiguous）、契约守卫、按 shape 键分配工作缓冲，并在第二次相同 (shape, 指针) 调用后录制 CUDA 图供后续重放；图只重用启动序列，仍从当前输入内存重算，不缓存数据结果。所有设备工作都在这一条链内，没有别的调用者可见副作用。

**冻结配置。** `MOE_CFG` 默认 -2 → `_pick_cfg` 返回 -1，即启发式派发，`moe_launch` 内全部 `cfg ==` 覆盖分支都不生效；`MOE_TUNE` 默认 1340710926，置位为 {1,2,3,13,15,16,19,21,22,23,24,25,26,27,30}；`MOE_PDL` 默认 1；`MOE_TSTORE`/`MOE_MTMAX`/`MOE_DBG` 默认 0；图重放默认开启。本次收录只覆盖该默认配置在冻结域（`token_count` 1..8192、`top_k`=8、四组几何）内实际启动的 kernel 与模板实例；`Rmax = token_count * top_k`。

**默认派发下实际可进入的链。** 逐条按 `moe_launch` 的 wmode 判定与四个几何元组核对，并用 performance/ncu 各 shape 的实际 kernel 名与模板实参交叉验证：

| 条件 | wmode | 链（节点顺序） | 承担设计 |
| --- | --- | --- | --- |
| I ∈ {768,1536} 且 Rmax > 256 | 39 | 路由前缀 → `umma_gemmPT7<1,…>` → `act_kernel2<true>` → `umma_gemmPT7<2,…>` → `finalize_kernel` | [root](root.yaml) + 局部/参数记录（H ≠ 2048 时含 finalize 分区记录） |
| I ∈ {768,1536} 且 Rmax ≤ 256 | 60 | `umma_gemmSK<1,true,true>`（含内核内路由）→ `moe_fixup<4,true>` → `umma_gemmPT7<2,…>` → `finalize_kernel` | [split_k_decode](split_k_decode.yaml) |
| I = 256 且 Rmax ≥ 1024 | 36 | 同 wmode39，但 G1 恒为 QUEUE 实例、G2 为 n1fast 实例 | [root](root.yaml) + ds-major 局部记录 + finalize 分区记录 |
| I = 256 且 16 ≤ Rmax < 1024 | 60 | 同 wmode60；Rmax ≤ 256 用内核内路由，256 < Rmax < 1024 用独立 `routing_fused` 节点 | [split_k_decode](split_k_decode.yaml) + 非 RFS 路由前缀记录 |
| I = 256 且 Rmax < 16（tokens = 1） | 0 | `routing_fused` → `gemm_kernel<3,64,256,256,4>` → `gemm_kernel<2,64,128,256,4>` → `finalize_kernel` | [mma_sync_fused](mma_sync_fused.yaml) |

路由前缀本身按 Rmax 分派：≤3072 用单 CTA `routing_fused`，>3072 用 `routing_count` + `routing_ss`。G1 的领取方式按 Rmax 分派：wmode39 在 [1024,16384) 与 ≥49152 用 QUEUE，在 (256,1024) 与 [16384,49152) 用静态条带（同一实例 `umma_gemmPT7<1,false>`）；wmode36 恒 QUEUE。G2 默认恒为静态条带，仅 Rmax ≥ 49152 转 QUEUE。这些分派都是主机配置选择，不写进任一 YAML，逐条见“变体与组合”。

**不进入本次收录的源码内容。** 三类，均据源码事实说明，不改称参数：

- 需要非默认 `MOE_CFG`/`MOE_TUNE` 才能启动的机制，其中结构上独立、本次未交付完整 schema 的有：`umma_gemmPF`（bit6 FUSE1/FUSE2，成对列 GEMM1 内融合 QDQ1/SwiGLU/QDQ2，消除 pre_code 往返与 act 节点）；PF（bit29，act 移到侧流并用 per-mt 标志与 G1 流水，`act_kernel2f`）；AP（bit20，`act_kernel2p` + 标志步调的 G2，源码记录为已否决：持久 G2 占满寄存器导致死锁）；FIXL2（bit14，把 fixup 融进 SK 并用 per-(mt,nblo) 计数器）。它们的取舍依据来自源码注释记录的实测结论，不是本提取的判断。其余为实例化/调度旋钮（bit17 的 PM64、N1D 与 SK 的 S4 k 块级分阶段、bit18 的 PE 与 SK 的 TB、bit7 GRIDCAP 与 pre_code 窗口、bit11 act 窗口、bit28 GQ 与 fixup 的 w2 预取、bit12 DEEP-T/BN128、bit29-in-wmode37 RFT、bit31 act_kernel2m、MOE_TSTORE 的 TMA 存储尾部），默认不可达。
- 冻结域内不可达的 wmode：1/2（需 H%256≠0）、6/16/18/28/30/31/33/34/35/37/40/41/42（需非默认 cfg，或 256<I<512、I%256≠0 等域外几何）；对应 `umma_gemm`、`umma_gemmT`、`umma_gemmW` 家族在默认配置下不启动。
- 定义了但全源码无启动点的死代码：`umma_gemm2`/`umma_gemm2T`（cta_group::2、`__cluster_dims__(2,1,1)`）、`umma_gemmP`、`umma_gemmPT`、`zero_detect`、`finalize_kernel8`、`act_kernel`（v1）。因此集群层级没有登记进 Contract 的 `Execution`；`routing_scan` + `routing_scatter` 仅在非默认 bit9 下启动。

**共享的主机机制。** 主机提交框架对三份设计一致：PDL 可用（`MOE_PDL=1` 且 CC ≥ 9）时，需要提交属性的节点经 `moe_launch_pdl` 以 `programmaticStreamSerializationAllowed` 启动，不可用时全部退回普通启动；CUDA 图录制/重放与按键失效；按 shape 键的工作缓冲生命周期；窗口带才触发的 persisting-L2 预留与释放。设备侧提交形态按链不同：root（wmode39）与 split_k_decode（wmode60）的全部节点经 `moe_launch_pdl` 启动并按各自 pdl 实参执行 `griddepcontrol.wait/launch_dependents`；mma_sync_fused（wmode0）的两个 `gemm_kernel` GEMM 节点为普通 `<<<>>>` 启动（签名无 pdl 形参、体内无 griddepcontrol），提交与启动由流序保证，该链中 routing_fused 与 finalize 仍经 `moe_launch_pdl`。各节点在自己的 `Work_schedule.Flow` 写实自己的启动列表（S 路径没有 launch_ready 提前边，各边界按 kernel_done 粒度写实），共同事实记录一次见“PDL 链与 CUDA 图重放”条目。

**构建分支事实。** `_build()` 仅在设备能力为 (10,3) 时用 `-gencode=arch=compute_103a,code=sm_103a` 启用 tcgen05；否则定义 `MOE_NO_UMMA`，`ensure_attrs` 不置 `g_umma_ok`，`moe_launch` 强制 wmode 0，全部带宽都落到 mma.sync S 路径。验收材料记录实测设备为 NVIDIA L20D、CC 10.3、build_target 10.3a、148 SM，故 UMMA 分支为真；这只是分支归属事实，不构成硬件能力或容量结论，Device/Architecture 仍按硬件占位豁免保持为空。

**核实边界与剩余未知。** root 带的实现细节已逐项核实并落进 root.yaml，需要沿正文理解时按以下定位：阶段屏障构成（stage_full 258 = 256 个 per-thread copy 到达 + 每宏阶段 2 次 bulk 字节数通告；mma_done = 1、promo_done = 8）、512 列 tmem 双缓冲复用窗口与三条 Released 边在 GEMM1/GEMM2 的 `sync_init`、REALIZATION.Require 与 `Waiting.Released`；128B 交织与行索引 XOR swizzle 在 REALIZATION.Prefer；QUEUE 取票守卫（`macro_bound > g + 2`）与票的可见性顺序在 GEMM1 的 `claim_first`/`fetch_ticket`/`adopt_bound` 与 `store:pre_block` 收尾 rendezvous；路由双前缀（行基址与瓦片基址）在 Rewrite “Route grouping into expert row blocks” 的 row_base/tile_base；`mt_max` 类主机上界只服务非持久网格，root 的持久 148 CTA 不用它，ACT 的主机上界在其 Mapping（grid 用 ceil_div(token_count·route_count, 16)，可超过 worktile 数）；描述符字段编码属实现层，不影响任何已定设计决定。另两份设计的实现细节同样已逐项核实并落进各自 YAML：[split_k_decode](split_k_decode.yaml) 的分段自适应（源码 `sk_s_eff` 同一纯函数在 SK 与 fixup 两侧求值，上界为主机 split_bound）与部分和段跨度在 Math_reshape Rewrite “Split-K segmentation of FC1”（split_bound/split_count/split_k_blocks，pre_partial 按 split_bound 段 × token_count·route_count 行跨距定尺）与 `Tile_pipeline.Step.SK1.MAIN` 的 `store:pre_partial`；[mma_sync_fused](mma_sync_fused.yaml) 的 64 行瓦片、配对 up/gate 双 QDQ 组与每行 4 线程的归约范围在 Rewrite “FC1 output QDQ inside the producing tile”、“Clamped SwiGLU and second QDQ in the tile” 与 `Tile_pipeline.Step.GEMM1.MAIN` 的 `qdq1_amax`/`qdq1_scale`/`qdq1_codes`/`act_quant`，GemmCfg 偏移算术落在其 GEMM1/GEMM2 的 Storage 账与 REALIZATION.Require（183104/109108 字节）。剩余未知只是覆盖与来源边界，均随交付如实标注：非 RFS 带（256 < Rmax < 1024 且 I = 256）与 S 路径没有 scored ncu 样本，归属以源码派发条件为准；外部验收器的公式与归一化未提供，root 的 `Golden_reference.Tolerance` 保留来源记录；硬件区沿用占位豁免，Device/Architecture 为空。

## 变体与组合

### 多块路由前缀（局部）

- 基线：[root](root.yaml) 的 `Work_schedule.Step.ROUTE` 与 `Tile_pipeline.Step.ROUTE.MAIN`——单 CTA（Member warp[0:32] = 1024 线程），slot_cache 每线程 8 个寄存器槽缓存专家 id，histogram/cursor/scan_state 在 smem，一次全局遍历后 `compute:prefix` 做双前缀、`store:rows` 散射（源码实例 `routing_fused`）。
- 差异与联动：Rmax > 3072 时 ROUTE step 整体换成两个节点。`routing_count`：NB = min(64, ceil(Rmax/1024)) 块 × 1024 线程，smem 直方图后平写 `hist[b*E+e]`（hist 无需 memset）。`routing_ss`：同 NB 块，每块冗余归约 hist 得到全局总数与自身独占基址，在 smem 跑同一双前缀（确定性 → 各块结果一致），block0 发布完整的 routing_tables 与清零的 ticket_counter（源码 meta[0..2E+6)），再以 smem `base[]` 作原子游标散射。Rewrite “Route grouping into expert row blocks” 的 row_token/row_expert/row_of_route/routing_tables 布局与含义不变，下游 step 无需改动；需要主机 hist 缓冲（64×256 int，`_scratch` 已含）；`Flow.Launch` 层面 count 只 trigger、ss wait+trigger（root 的 ROUTE 是链头只 trigger）。专家内行序仍是原子序（内部事实：FIN 按 row_of_route 聚集，输出不受影响）。
- 条件与依据：默认门限 3072（源码 prof102 记录的 crossover 标定值）；bit8 → 4096、bit10 → 8192、bit9 → 退回 `routing_scan` + `routing_scatter` 三节点，均非默认。该选择只依赖 Rmax 与是否 RFS：默认下即 wmode 39/36 的 Rmax > 3072 带；wmode60 的非 RFS 带（256 < Rmax < 1024）与 wmode0（Rmax < 16）仍用单 CTA 形式。

### wmode60 非 RFS 带的独立路由前缀（局部）

- 基线：[split_k_decode](split_k_decode.yaml) 的 RFS 链头形态——`Work_schedule.Step.ROUTE`（SK 网格每个 worker 用 `routing_fused256` 私有重算、worker 0 单写者发布）、`Work_schedule.Step.SK1` 与 `Work_schedule.Flow.Launch` 的首条 `{step: [ROUTE, SK1], order: per_worker}`（SK 为链头，其 REALIZATION.Require 记明链头提交既无入口 wait 也无启动授权），以及 [root](root.yaml) 的 `Work_schedule.Step.ROUTE`——独立路由节点就是与 root ROUTE 相同的单 CTA `routing_fused` 源码实例。
- 差异与联动：256 < Rmax < 1024（默认派发下仅 I = 256 进入该带）时 RFS 门（`Rmax <= 256`）为假，链前恢复独立路由节点：`routing_fused`（1×1024，链头只 trigger）产出与 root ROUTE 相同的 row_token/row_expert/row_of_route/routing_tables；SK 不再是链头——pdl 由 0 变 1（入口 wait、末尾 trigger），smem 由 UMMA_FR_SMEM（218368，含 ROUT 区）回到 UMMA_T_SMEM（203528），Rfuse 实参为 0，SK 从全局 meta/row_token 读取而不用内核内路由的 smem 副本；`moe_fixup`/G2/FIN 与 RFS 形态完全相同。专家内行序回到原子序（内部事实：FIN 按 row_of_route 聚集，输出不受影响）；ZEL 仍不适用（wmode60 不在其门内），与本目录 ZEL 条目一致。
- 条件与依据：RFS 门为 bit15（默认开）∧ wmode60 ∧ Rmax ≤ 256 ∧ 非 FIXL2；源码 v91-SKDSM 记录明确“RFS 保持 R ≤ 256 界，中间带保留独立路由节点”。该带在冻结域内可达（tokens 33..127 且 I = 256），无 scored ncu 样本，归属以源码派发条件为准；与“多块路由前缀”条目无关（Rmax < 1024 ≤ 3072，恒为单 CTA 形式）。

### GEMM1 静态条带（局部）

- 基线：[root](root.yaml) 的 GEMM1 动态领取——`Work_schedule.Step.GEMM1.Schedule.Worker_assignment`（`Refill: ticket_counter`、`Exit: [ticket_exhausted]`）与 `Tile_pipeline.Step.GEMM1.MAIN` 的 `claim_first`/`fetch_ticket`/`adopt_bound` 及 ticket_state 存储：线程 0 对 ROUTE 清零的 ticket_counter 原子取票，仅在宏阶段守卫 `m == fc1_k_blocks/2 - 2 and macro_bound > g + 2` 成立时预取 t+2 的票（该守卫同时承担“末持有瓦片不取死票”与“seed 子情形中途取票自禁用”两个作用）；票与宏上界存 ticket_state，经 `store:pre_block` 的收尾 rendezvous 发布，`adopt_bound` 在每 worktile 尾重载并据其判定 ticket_exhausted；瓦片总数低于 148 时 `claim_first` 以自身索引 seed（单瓦片上界，零原子、无 pull）；effective_row_tiles = 0 时在取票前整体退出（源码实例 `umma_gemmPT7<1,true>`）。
- 差异与联动：wmode39 在 Rmax ∈ (256,1024) 与 Rmax ∈ [16384,49152) 两段改用 `umma_gemmPT7<1,false>`，即把 GEMM1 的领取换成与 root GEMM2 同型的静态条带：`Preassigned {start: worker_id, stride: 148}`、`Exit: [assigned_done]`，宏上界由自身条带瓦片数 × fc1_k_blocks/2 导出，blockIdx.x ≥ 瓦片总数直接退出；不读 ticket_counter，无 `fetch_ticket`/`adopt_bound`/ticket_state（`claim_first` 退化为条带自算，相当于 QUEUE 的 seed 形态推广到任意条带长度）。瓦片分解 (mt, nb)、stage_ring 宏阶段流水、`qdq1` 尾部与 pre_code/pre_scale 存储完全相同，输出按位相同，只有 CTA→瓦片次序不同（源码记录：偏斜路由下静态条带有尾部不均）。ROUTE 仍会清零 ticket_counter，但该实例不读。
- 条件与依据：适用面是 wmode39 的 (256,1024) 与 [16384,49152) 两段。QUEUE 门为 bit5、bit28、Rmax ≥ 49152 或 Rmax ∈ [1024,16384)，默认 tune 下前两位为假，故 (256,1024) 落入 else 分支启动同一静态实例；该带由解码带分派 `(Rmax > 256 && I >= 512) ? 39` 进入（tokens 33..127 且 I ∈ {768,1536}，在 shape_range 的 tokens 1..8192 之内）。bit5/bit28 可在任意 Rmax 强制 QUEUE（非默认）；同一分派对 wmode36 不成立（其 G1 恒 QUEUE）。固定套件只实证了 [16384,49152) 段（ncu/9.csv 的 Rmax=32768），(256,1024) 段没有 scored 样本，其归属以源码派发条件为准。

### GEMM2 动态队列（局部）

- 基线：[root](root.yaml) 的 GEMM2 静态领取与直存——`Work_schedule.Step.GEMM2.Schedule.Worker_assignment`（`Preassigned {start: worker_id, stride: 148}`、无 Refill）与 `Tile_pipeline.Step.GEMM2.MAIN` 的 `store:c2_block`（32B 全扇区直存、无 CTA 暂存）、`load:a_block`（线程 0 bulk box 取 act 连续行，GA2；源码实例 `umma_gemmPT7<2,false,false,true,true>`）。
- 差异与联动：Rmax ≥ 49152 时 G2 改用 `umma_gemmPT7<2,true,false,false,true>`：领取换成 GEMM1 式票口机制，票口用 ticket_counter 的第二字（源码 meta[2E+5]；root 的 ROUTE 已把两字都清零），即 root GEMM1 的 Refill/`fetch_ticket`/`adopt_bound`/ticket_state 机制套用到 GEMM2 的 (mt, hb) 瓦片序列；且 `store:c2_block` 放弃 32B V8ST，c2 存储回到每线程 16B uint4 直存；`load:a_block` GA2、宏阶段流水、尾部与数值都不变（按位相同，只是瓦片次序）。
- 条件与依据：Rmax ≥ 49152 且 bit12 未置位——默认 tune 未置 bit12，故该项在 Contract 域内（Rmax ≤ 65536）可达；bit12 置位则关闭。wmode36 明确排除（其 G2 走 n1fast 静态，见 ds-major 条目）。

### 中间缓冲体量相关的存储提示与 L2 窗口（参数）

- 基线：[root](root.yaml) 的 c2 体量 ≤ 24MB：GEMM2 `store:c2_block` 走直存路径（32B V8ST、plain 存储），FIN 的 `load:c2_rows` 用 plain 读（源码 `finalize_kernel<false>`，STHR = 24MB），Math_reshape 符号 route_result。设备侧判据分两处且基准不同：G2 的 `strm2` 用实际有效行数 Rvalid（`meta[2E+2]·Ntot·2 > STHR`），FIN 的 `strm` 用上界 `T·topk·H·2 > STHR`（与主机 c2b 同基准，与 Rvalid 无关）；主机侧 LP2/窗口判据用 c2b = Rmax·H·2。root 带内三者都在 24MB 以下、行为无差别，故这些判据不进 root 的 YAML、只记录于本条目；稀疏路由下 Rvalid 判据与上界判据可以分叉，任何节点写实 FIN 的存储提示条件时必须用 T·topk·H·2。同一 24MB 门限也管 pre_code（Math_reshape 符号 pre_code/pre_scale）：root 带内 GEMM1 的 `store:pre_block` 是 plain 16B 存储、ACT 的 `compute:act_chunk` 是 plain 读（源码 `strm` 为假）。
- 差异与联动：按 c2b 分带，全部由几何决定，bit30/bit27 在默认 tune 中。(24MB,48MB]：LP2 实例把 G2 的 STHR 抬到 48MB（`store:c2_block` 仍是直存 plain），FIN 换 `finalize_kernel<true>`；源码记录该带必须用 48MB 立即数而非 ~0ull，否则常量折叠会剪掉暂存路径并触发寄存器溢出。> 48MB：`strm2` 为真，`store:c2_block` 改走 smem 暂存回读的 16B `__stcs` 存储（stageb 两个 [128][128] 相位 + 每相位 `__syncthreads`），FIN 的 `strm`（按 T·topk·H·2 判，非 Rvalid）为真 → `load:c2_rows` 用 `__ldcs`。(48MB,80MB]：persc2 令 G2 换 PW 实例（plain 存储）并由 `moe_launch_pdl_w` 在该次启动上挂 c2 的 persisting L2 访问窗口（hitRatio = 56MB 上限 / c2b，missProp = streaming）；FIN 的启动不带窗口，但 G2 已把命中的 route_result 行标记为 persisting，其聚集读因此命中 L2。窗口带还带来主机侧副作用：`ensure_l2pers` 用 `cudaDeviceSetLimit` 预留 ≤56MB，无窗口的 eager 启动会 `cudaCtxResetPersistingL2Cache` 并把限额释放为 0；两者都不能在图捕获中执行。lp2 且 bit27 时另有 c2 窗口挂在 G2 与 FIN 两次启动上的组合。pre_code 侧是同族但独立的判据，只与 Rvalid·2I 有关、不涉及 c2b：Rvalid·2I > 24MB 时 GEMM1 的 `store:pre_block` 改 `__stcs` 逐出优先存储，ACT 侧按同一判据（读 ZEL 门控后的 Rvalid）把 pre_code 读改 `__ldcs`。计分 cases 3/5/9 的 Rvalid·2I 为 25..101MB，都在该带内；源码记录其后果是 act 需从 DRAM 重流约 100MB（bit7 的 pre_code 窗口即为此而设，非默认）。存储提示不改实例选择、分区与数值。
- 条件与依据：bit7（pre_code 窗口）、bit11（act 窗口）非默认；bit20/bit28 相关的 AP、fixup 预取见“不进入本次收录的源码内容”。存储提示与窗口只改缓存行为，不改数值。[split_k_decode](split_k_decode.yaml)（Rmax ≤ 256）与 [mma_sync_fused](mma_sync_fused.yaml)（Rmax < 16）带内 c2b 与 Rvalid·2I 都远小于 24MB，两份 YAML 因此都不含这些判据；ds-major 带（H=7168、Rmax ≥ 1024）会跨带，按本条目与 ds-major 条目组合使用。

### I = 256（nm == 1）的 ds-major 带（局部）

- 基线：[root](root.yaml) 全份设计（ROUTE、GEMM1、ACT、GEMM2、FIN 五个 step 与全部 Rewrite 沿用）。
- 差异与联动：几何 (H=7168, I=256, E=256) 且 Rmax ≥ 1024 → wmode36。差异集中在两个 step：GEMM1 在所有 Rmax 都用 QUEUE 实例（root GEMM1 的票口机制不受 [1024,16384) 带限制），column_tiles = 2·I/256 = 2。GEMM2 因 K = I = 256 → fc2_k_blocks = 2、每 worktile 只有 1 个宏阶段（nm = 1），改用 n1fast 实例 `umma_gemmPT7<2,false,true,true,true,false,false,true,true>`（N1FAST + V8ST + GA2 + N1S + N1O）：瓦片坐标状态放 smem 环（N1S）而非基线实例的奇偶寄存器；瓦片边界不走共享 epilogue，而是先捕获瓦片坐标，`store:c2_block` 直接 32B V8ST 存储（超 STHR 用 `st.global.cs.v8`，见存储提示分带条目），存储之后再 refill 下一票（N1O，与 root GEMM1 的“先取票后存储”次序相反），最后才做 `master_reset`；不用 scratch 暂存、无相位 `__syncthreads`。QDQ 组仍 quant_block = 128 宽、k 序不变 → 按位相同；Math_reshape 的 bm 仍 128。其余三个 step 的沿用各有条件：ACT 的公式与 16 行块分区对 intermediate_size 一般成立（I = 256 → act_rounds = 1，`Worker_count` 取 ceil_div(T·R, 16)）；ROUTE 在 Rmax > 3072 时按“多块路由前缀”记录换成 `routing_count` + `routing_ss` 两节点（case 4 的 ncu/4.csv 即此形态），Rmax ≤ 3072 时仍是 root 的单 CTA 形式；FIN 的分区、worktile 形状与 worker 数在 H = 7168 下按“finalize 分区随 hidden_size 的适配”记录取 chunk 形（实测 grid 3584）。
- 条件与依据：仅 nm == 1（I = 256）成立，源码记录 QUEUE-at-nm==1 在 wmode36 不被使用；空路由形状要付 QUEUE 空转点名开销（源码记录的已知边界）。同族非默认项：bit12 BN128 G1（column_tiles 2→4、STAGES_U 4→6、TBUFS 4、半列 warp 跳过 LDTM 但保留 promo_done 到达）、bit20 QVG（nm==1 用 QUEUE）、bit17 N1D（除法自由的瓦片状态）。

### finalize 分区随 hidden_size 的适配（参数）

- 基线：[root](root.yaml) 的 `Work_schedule.Step.FIN`——`Decomposition.Partition.token_tile`（size token_count、tile 2）、`Worktile` 的两行形状（Invariant `route_row`/`route_weight_block` 为 [{token: 2}, {route: route_count}]，Iteration `route_result_rows` 与 Target `output_block` 为 [{token: 2}, {hidden: hidden_size}]）、`Mapping.Worker_count` = ceil_div(token_count, 2) 与 `Worktile_order`；其 `Decomposition.Strategy` 自注 “two full rows at hidden_size = 2048”，`when` 也固定 hidden_size = 2048，故该登记在自身域内成立。并列基线：[split_k_decode](split_k_decode.yaml) 的 `Work_schedule.Step.FIN`（`output_chunk`）与 [mma_sync_fused](mma_sync_fused.yaml) 的 `Work_schedule.Step.FIN`（`chunk_tile`）——同一源码实例，两份 YAML 已按下述一般 chunk 形登记。
- 差异与联动：hidden_size ≠ 2048 时机制不变——仍是一个线程服务一个 16 通道 chunk、按路由槽升序 fma32 归约、就地把 BF16 写回调用者缓冲，`zero_flag` 分支与 `await:grid_dep` 照旧，`Tile_pipeline.Step.FIN.MAIN` 的动作与等待一字不改；变的只是分区轴、worktile 形状与 worker 数公式：Partition 换成扁平 chunk 域 `output_chunk`（size token_count·(hidden_size/16)、tile 256），Invariant `route_row`/`route_weight_block` 按 chunk 而非按 2-token 登记为 [{chunk: 256}, {route: route_count}]，Iteration `route_result_rows` 与 Target `output_block` 改为 [{chunk: 256}, {hidden: 16}]，`Worker_count` = ceil_div(token_count·(hidden_size/16), 256)，`Worktile_order` 按 output_chunk 升序。chunk 到输出的映射是 token = floor(c / (hidden_size/16))、通道基址 = 16·(c mod (hidden_size/16))；hidden_size/16 不是 256 的整数倍时一个 worktile 可跨行，末尾 worktile 的多余线程空退。hidden_size = 2048 时 hidden_size/16 = 128，两式等价，退化回 root 的两行登记，分区与数值完全一致。
- 条件与依据：适用于按范围表由 root 加记录承担、而 hidden_size ≠ 2048 因而超出 root `when` 的输入，即 I ∈ {768,1536} 且 Rmax > 256 的 wmode39 带中 H = 4096 的形状（计分 cases 2/3）与 ds-major 带的 H = 7168（case 4）。依据是主机网格公式 (T·(H >> 4) + 255)/256 与内核的 v = block·256 + tid、hw = H >> 4、t = v/hw 映射，二者与上述取值逐字一致；计分样本实测 case 2（T = 512、H = 4096）finalize grid 512、case 4（T = 2048、H = 7168）grid 3584，而 root 的两行公式分别给 256 与 1024。存储提示另按“中间缓冲体量相关的存储提示与 L2 窗口”条目组合（case 2 的 c2 体量即落在 LP2 带，实例为 `finalize_kernel<true>`）。

### 激活的 tanh 近似 sigmoid（参数）

- 基线：[root](root.yaml) 的 Math_reshape Rewrite “Clamped SwiGLU with a tanh-form sigmoid”（sigmoid(x) = 0.5·tanh(0.5·x) + 0.5，`Arithmetic.Approx` 已声明 ~3.2e-4 界）与 `Tile_pipeline.Step.ACT.MAIN` 的 `compute:act_chunk`（源码 `act_kernel2<true>`，bit21 默认开）；并列基线 [split_k_decode](split_k_decode.yaml) 的同名 Rewrite 与 `Tile_pipeline.Step.FIXUP.MAIN` 的 `compute:swiglu`（源码 `moe_fixup<4,true>`，bit25 默认开）同机制：每元素 `fmaf(tanh.approx.f32((alpha*0.5)*y), 0.5, 0.5)`，1 次 MUFU。
- 差异与联动：关掉对应位（ACT 为 bit21、fixup 为 bit25）回到 `__fdividef(1, 1+__expf(-alpha*y))`（2 次 MUFU）。`(al*0.5)*y` 与 `(al*y)*0.5` 按位相同（0.5 是精确二次幂），clamp 次序、QDQ2 的 quant_block 元素组归约（`act_chunk` 为 8 lane × 16 元素，fixup 为 32 lane × 4 元素）、存储模式都不变。数值上两者不等价：源码记录 tanh 形式的 sigmoid 绝对误差 ≤ ~3.2e-4（精确形式 ~2e-7），采用依据是冻结检查器余量（源码记录最终 rel_l2 ≤ ~3e-3，限值 1e-2）。共享 Contract 只规定 bf16 物化与 QDQ 边界，未规定激活的实现精度，故两种取值都在 Contract 内。[mma_sync_fused](mma_sync_fused.yaml) 的融合激活固定 `__expf` 形式（其 Rewrite “Clamped SwiGLU and second QDQ in the tile” 与 `Arithmetic.Approx` 记 ~2e-7），源码没有该开关。同一激活段的两次 QDQ 原语分工也不对称，比较三份设计时不以 root 的形式外推：QDQ2 三链都用近似倒数，QDQ1 则在 root GEMM1 的 `compute:qdq1` 是近似倒数乘、在 split_k FIXUP 的 `compute:qdq1` 与 mma GEMM1 的 `compute:qdq1_codes` 是精确除法，各份 YAML 的 `Arithmetic` 与 `REALIZATION.Require` 已分别登记。
- 条件与依据：bit0（fp16x2 SwiGLU）被源码以余量不足（rel_l2 7.6e-3）排除在默认外；bit31 的 `act_kernel2m`/ACTP 占用率变体非默认；PF 形式还需把 pre_code 读改成 `.cg`（非默认）。

### 全零载荷短路（ZEL）的形式与适用面（局部）

- 基线：[root](root.yaml) 已含默认形式（bit19 + bit22 → zsel = 2）：Math_reshape Rewrite “All-zero payload short-circuit”（zero_flag/effective_rows/effective_row_tiles，Ledger.Cost 保留来源限制）、`Flow.Handoff` 的 zero_flag（producer GEMM1、consumer [ACT, GEMM2, FIN]、initialize: 0）、`Tile_pipeline.Step.GEMM1.MAIN` 的 `compute:zero_scan`（Pipe 中位于 `await:grid_dep` 之前：A 载荷按 uint4 检查低 7 位——e4m3 ±0 当且仅当低 7 位为 0——并检查 sa/scores/w1s/w2s 是否非有限即指数全 1，warp 归约后进 verdict_vote）、`await:verdict`（每 CTA 一次原子到达，最后到达者发布 zero_flag 并自复位两 scratch 字，图重放安全，其余自旋到计数归零）与 FIN 的 `if(zero_flag != 0): store:zero_rows`。判定成立时 effective_rows/effective_row_tiles 为 0：GEMM1/GEMM2 瓦片循环为空、ACT 无工作即返、FIN 直接写 +0.0 而不读 route_result。meta 的固定字 518/519/520 与路由侧写入（≤ 2E+5）在 E = 128/256 下都不冲突；meta 由 `torch.zeros` 分配，未发布该标志的链读到 0（对应 initialize: 0）。
- 差异与联动：zsel = 1（bit22 关）把 `zero_scan` 与打包单原子共识都移到 `await:grid_dep` 之后（即 root Pipe 前两项次序对调）；独立 `zero_detect` 节点形式保留在源码但从不启动（源码记录 ~3-4.5us 节点地板超过该带的税上限）。ZEL 只对 wmode 39/40/36、`hs_stride == T` 且非 RFS/RFT 生效：[split_k_decode](split_k_decode.yaml) 与 [mma_sync_fused](mma_sync_fused.yaml) 的链从不发布 zero_flag，其源码 `meta[ZEL_FLAG] ? 0 : …` 守卫恒取原始总数——这是源码事实，不是可选项；两份 YAML 已按此登记：不引入 zero_flag Handoff，行数与瓦片数直接取原始总数（split_k 的 Rewrite 明记 “no all-zero payload verdict exists here, so both totals are served in full”，其 REALIZATION.Require 另固定该 verdict 字恒 0；mma 的 GEMM 分区以 total_row_tiles 登记，routing_tables 只发布两个总数）。空路由（total_row_tiles = 0）时跳过 `await:verdict` 的到达共识（root Pipe 的 `if(total_row_tiles > 0)` 守卫；zsel = 2 的 pre-wait `zero_scan` 仍执行并投票），zero_flag 可能滞留在上一次调用的值，但源码记录该滞留是良性的：各消费者的零工作路径与短路路径产生同样的精确零组合（root 的 Rewrite 已记录该点）。
- 条件与依据：正确性依据是 Contract 已声明的“全零组反量化恰为零”加 0 × 有限 = 符号零。`zero_scan` 只验证 sa/scores/w1s/w2s 的有限性，不验证 w1/w2 载荷与 alpha/beta/limit：在冻结输入构造下 fp8 载荷由有限值 clamp 到 ±448 后量化（不产生 NaN 码），alpha/beta/limit 由 `input.py` 以有限常数填充（或 None → 不 clamp），故短路在该输入空间内精确；超出该空间不成立（该限制保留在 root 的 Rewrite Math 与 Ledger.Cost）。

### A 操作数装载方式（参数）

- 基线：[root](root.yaml) 的 `Tile_pipeline.Step.GEMM1.MAIN` 的 `load:a_block`（全线程 cp.async 16B 按 row_token 聚集 token 行，每线程每 k 块 4 个任务，覆盖 128 行 × 128B）与 `load:scale_block`（128 行 scale + 2 个列组 scale 进 scale_ring）；`Step.GEMM2.MAIN` 的 `load:a_block`（线程 0 一个 {128,128} TMA bulk box 取 act 连续行，GA2，bit16 默认开）与 `load:b_block`（`expect_tx` 覆盖 A、B 两段字节数，屏障到达计数不变）。
- 差异与联动：bit16 关 → GEMM2 的 `load:a_block` 也回到每 k 块 1024 次 per-thread cp16；bit4（非默认，源码记录 G1 gather4 被否 +35..50%）→ GEMM1 改用 tile::gather4 图、GEMM2 用 {128,128} box；bit1（默认开）→ 主机 `moe_get_bmap` 打开 B 描述符的 256B L2 提升。描述符按 (基址, 行列维度, box, 提升标志) 主机缓存，作为 `__grid_constant__` 实参进 kernel，图重放复用同一份；GA2 的越界 box 行零填充，配合存储侧 valid_rows 行守卫使写出的字节与非 GA2 相同。
- 条件与依据：GA2 只适用 MODE2（源码 static_assert），wmode36 的 n1fast G2 由 bit26 单独打开同一机制的独立实例化；GEMM2 的 A 是 act 连续行故可用 bulk box，GEMM1 的 A 是分散 token 行，默认仍用聚集 cp.async。

### PDL 链与 CUDA 图重放（参数）

- 基线：[root](root.yaml) 的 `Work_schedule.Flow.Launch`（五次提交，start_after 区分 launch_ready 与 kernel_done：GEMM1/ACT/FIN 在前驱 launch_ready 后、GEMM2 在 ACT.kernel_done 后）、各 step MAIN 的 `await:grid_dep` 与 `signal:dependents`（ROUTE 链头只 trigger；ACT 只 wait 不 trigger，其后继的 wait 由 ACT 网格完成时释放）及 REALIZATION.Require 的 PDL 条目。三份设计并列适用的是同一套主机提交框架：PDL 可用时经 `moe_launch_pdl` 以 `cudaLaunchAttributeProgrammaticStreamSerialization` 启动需要提交属性的节点；主机在第二次相同 (shape, 指针) 调用后把整条链录进 CUDA 图，之后按键重放，键含 T/H/I/E/topk/e_offset/hs_stride/device 与全部输入输出指针。设备侧提交形态分两类，各链在自己的 `Work_schedule.Flow` 写实：root（wmode39）与 [split_k_decode](split_k_decode.yaml)（wmode60）的全部节点经 `moe_launch_pdl` 启动并按各自 pdl 实参执行 `griddepcontrol.wait/launch_dependents`。split_k_decode 在 Rmax ≤ 256 时以 SK 为链头（pdl 传 0：既无入口 wait 也无启动授权），FIXUP 的入口 wait 因此由 SK 网格完成释放，对应其 Flow 的 `start_after: SK1.kernel_done`；FIXUP 末尾的 `pdl_trigger` 授权 GEMM2 提前启动（`start_after: FIXUP.launch_ready`），GEMM2 末尾的 `pdl_trigger` 再授权 FIN（`start_after: GEMM2.launch_ready`）；ROUTE 与 SK1 是同一提交的 per_worker 形态，故该链只有四条启动记录。[mma_sync_fused](mma_sync_fused.yaml)（wmode0）的两个 `gemm_kernel` GEMM 节点为普通 `<<<>>>` 启动，签名无 pdl 形参、体内无 griddepcontrol（源码注释明确无 pdl_wait 的 S 路径 kernel 按 plain 启动），提交与启动由流序保证——该链中 routing_fused 仍经 `moe_launch_pdl` 且提前 trigger（pdl 2），但没有带 PSS 属性的后继可提前启动；finalize 仍经 `moe_launch_pdl` 且入口 `pdl_wait`，其 wait 由 GEMM2 网格完成释放（隐式 trigger）。因此该节点的 Flow 不存在 launch_ready 提前边，GEMM1/GEMM2/FIN 三条 start_after 边都按 kernel_done 粒度写实。
- 差异与联动：`MOE_PDL=0` 或 CC < 9 → 全部退回普通启动，kernel 内 `await:grid_dep`/`signal:dependents` 对应的 wait/trigger 不生效，顺序由流序保证；`MOE_DISABLE_GRAPHS=1` 或外层正在捕获 → 只走 eager；出现新 shape 时 `_scratch` 丢弃其他 shape 的缓冲并清空 `_GRAPHS`/`_FAST`（键指向已释放缓冲的图按构造失效），同 shape 重访重新录制；`_FAST` 以 `id(topk_ids)` 为键并强引用全部张量，每次调用仍逐个身份校验后再重放。窗口类启动属性会被图捕获记录为节点属性、每次重放重新生效，而 `ensure_l2pers` 与 persisting 集合复位只能在 eager 下执行——这是 c2 窗口带与图重放之间的既有约束。
- 条件与依据：重放不缓存数据结果，只重放启动序列，每次仍从当前输入内存重算。两条重放快车道都在重放前重新校验配置选择（do_finalize、use_shuffled_weight、weight_layout、gemm1_lora_delta、fp8_quantization_type、activation_type）：`__call__` 的 id 键捷径逐个校验全部张量对象身份，`forward` 的键查表只按 (shape 标量 + 各张量 data_ptr) 命中；两者都跳过 128 对齐、E ≤ 256、dtype/连续性等 eager 守卫，这些守卫在录制该图的那次 eager 调用已经执行过，重放的正确性因此依赖“同一批张量对象、同一布局”这一调用前提。
