# paged_latent_mxfp8_nvfp4

## 范围

**共同 Contract 的范围**（root.yaml 的 CONTRACT，目录不改写）：batch_count 1–32、query_len ∈ {1,3}、head_count ∈ {64,128}、head_dim 512 的 bf16 Q；MXFP8 SWA 分页缓存（record 528）加可选 NVFP4 压缩分页缓存（record 288），选择子宽度 swa_budget 128 与 cmp_budget 512，负值是未选标记；extra 两项成对出现或同为 None；fp32 per-head attn_sink 允许 ±inf；输出是原地写回的 caller bf16 out 与新的 [batch, head, query] fp32 lse；n_sel = 0 时输出全零且 lse = +inf。

**固定实现的实际范围**：host 入口 `plmn_forward`（launch.cu:137-394）逐参数校验后只接受 head_dim = 512、head_count 是 32 的倍数、q/out 连续 bf16 且 shape 相同、两个缓存为连续 uint8 的 [page, row, 1, record] 且 record ∈ {528, 288}、选择子为连续 int32 [batch, query, budget] 且 extra 两项成对、缓存元素数 < 2^31，并要求 ceil(budget / NT) ≤ MAXENT = 4，否则 TORCH_CHECK 直接失败。实现因此比 Contract 宽（任一缓存都可取 528 或 288、head_count 只需是 32 的倍数），本目录记录范围仍按 Contract 域，不把这些额外自由度写成设计前提；tp 不是 ABI 轴。扩展在进程内按 candidate/ 全目录源码与编译 flags 的哈希构建一次并缓存，`Model.forward` 之外没有 host 侧数值。

**当前收录范围**：完整设计含 root 共 2 份，远低于 10 份上限，且均已交付——root（warp 级 mma.sync 方案）与 tcgen05_tmem（tcgen05/TMEM 方案）；没有为提供共享区域而增加的文件，tcgen05_tmem 的三个 Design 区域全部本地定义，无 `from` 边。“变体与组合”的九条正式记录按基线分两组：四条以 root.yaml 中已有对象为基线（HB=64/NT=512 几何、窄 combine 几何、splits = 1 直写、host 的扇出与路径选择规则），覆盖 host 每次调用在三个 launch 分支（`plmn_tc::launch` / `cfg64::launch` / `cfg32::launch`，launch.cu:386-392）之间的选择、两个 mma 几何与两个 combine 几何，其中扇出与路径选择规则一条同时以 tcgen05_tmem.yaml 的对应对象为基线；五条以 tcgen05_tmem.yaml 中已有对象为基线（Heads=128 实例、双 64-head CTA 配对、融合式 split 归并、CUDA 图启动结构、cp.async Q 搬运），变化对象完全落在 tcgen05_tmem 内部，即两个额外实例形态、融合式归并、启动结构与 Q 搬运替代路径，见“变体与组合”。host 另导出 `smem_bytes`、`smem_bytes_hb64`、`use_hb64` 三个诊断绑定，`plmn_forward` 不调用它们，不作为设计收录。没有已研究但未完整展开的独立方案：其余已识别机制都能围绕这两份代表用参数或局部记录说清，其中包括 tcgen 的融合式归并（判定依据见“变体与组合”的“融合式 split 归并”条目）。

**边界与缺口**：最新版原题验证回执缺失、最终题目哈希尚未确认；外部比较器定义及逐输出误差回执未随源包提供，root 的 Tolerance 仍是 source-only 记录，只写明已知判据与缺失项，不采用默认简写解释，也不补造比较器；性能记录为 NCU 6/10 达标，shape 0/1/3/9 超阈值并有 2026-10-25 用户性能例外；随包的性能回执是最终配置的完整测量：ACCEPTANCE.json 给出 metric 身份（NCU gpu__time_duration.sum）、gpu_uuid 与 clock_mhz、每个 shape 的 production 与 candidate 各 20 个 samples_us、by_order（PCCP/CPPC）分解、kernel_count、kernel_sum_us、order_medians_us、ratios 与通过/超限列表，SUMMARY.json 另按 shape 聚合 candidate_us/baseline_us 与比率并说明该指标只统计已启动的 GPU kernel、不含 CPU/编译与 copy-engine DMA；未随包的是源码注释引用的 evidence/online-20261024 机制级 A/B 原始回执与 final-closeout 的逐输出验证回执，因此随包计时只能说明最终配置的整体表现，不能分离单个机制（几何选择、nhb 配对、融合归并等）各自的贡献；正确性验证是 SM103 采样，不是全域证明。`nsm` 与 `smem_per_sm` 由运行时 `cudaDeviceGetAttribute` 查得，源包没有固定值，因此各设计的 `when` 只能写成与该查询值的比较或保守取已核对子域，不能填具体 SM 数；据此，冻结用例中只有极小的 batch_count*query_len（如 shape 8 的 BS=1、10 个 chunk，乘积 10 达不到 (nsm+2)/3 门槛）确定落在 mma 分支，其余用例进入 tcgen 分支，其中 shape 2 的 3*2*10 = 60 属边界情形。两套设计的 16 位操作数格式不同，各自需要在 Math_reshape 单独给出精度论证：root 把 Q（bf16→fp16）与解码后的 KV 都放成 fp16，tcgen05_tmem 三个 tile 统一 bf16；源码的论据是 e4m3×ue8m0 只需 4 位尾数、e2m1×e4m3 只需 7 位，故两种格式的解码都精确，而 bf16 只有 8 位尾数，概率 tile 相对 fp16 少 3 位，且 SM103 对 f16/bf16 混合操作数对会 trap，所以一个 kernel 内三种 tile 必须同格式（kernel_mma.cuh:70-86、kernel_tcgen.cuh:41-56）。Contract 要求的是 FP32 精确值数学，两条论证都须按 source-only 的 atol=0.01/rtol=0.05 判据自行成立，不能把源码注释当作已证明的结论；两种指数近似也都没有版本匹配的误差界：root 的主 kernel 与归并均用 `ex2.approx.f32`（kernel_mma.cuh:159-163），tcgen05_tmem 的主 kernel 用 `ex2.approx.ftz.f32`（kernel_tcgen.cuh:28-32）、其归并复用 cfg32 的 `ex2.approx.f32`；两者的误差界均为 unknown，已分别在两个节点的 Arithmetic.Approx 记录。本目录的阈值与测量数字仅由固定源码文本与随包回执支持，不构成对其他输入或硬件的验证结论。

## 完整设计

| 设计 | 具体机制与保留理由 | 关系 |
| --- | --- | --- |
| [root](root.yaml) | warp 级 mma.sync 方案。实例：`cfg32::launch` → `plmn_kernel_hb32<<<(head_count/32, batch_count*query_len, splits), 256>>>`（HB=32 heads/CTA、NT=256 线程、NC=64 token/chunk、fp16 操作数），splits 固定 > 1，归并用 `plmn_combine_wide_hb32`。机制：两次整块前缀和把 SWA 与压缩两段选择子压缩进 smem（SWA 占 [0,n1)、压缩段接在其后，两段先后与参考一致；段内写入是线程主序，budget 512 > NT 256 使压缩段行序成为参考递增 t 的一个排列，行集合不变、只差求和顺序），slot 再映射为 (来源位, 数据偏移, scale 偏移)；Q 由 bf16 转成精确 fp16 入 smem；每 chunk 把 64 行解码成 fp16 K（单缓冲，lane 选行、tid/NC 选 128 维切片，一次自然对齐加载取回整段 group scale）；ldmatrix + `mma.sync.m16n8k16` 做 QK^T（wm 分 head tile、wn 分 token tile）；base-2 在线 softmax 跨 4 个 token warp 经 smem 求行最大，per-warp 行和与寄存器累加器同乘一个 alpha；P 以 fp16 写回 smem 的 A-operand 布局后做 PV，输出累加器全程在寄存器；尾部写 fp16 part_o 与 (m, l) part_ml，空 chunk 范围发布 merge 的 identity partial（-inf, 0, 0）。MAIN 从不写 attn_out 或 lse，输出只由 COMBINE 产生。保留理由：它是 host 的无条件 fallback 分支（launch.cu:390-392 的最后一个 else），且 host 每次调用都无条件先算出 `cfg32::schedule`，并用它作为 cfg64 是否更优的比较基准（tcgen 分支另有自己的准入判据）；机制全部显式，不需要 TMEM、descriptor 或 TMA 前提，最适合做阅读与比较入口；其 WIDE combine 内核对象被 tcgen05 方案原样启动。 | 阅读入口，保存唯一 Contract |
| [tcgen05_tmem](tcgen05_tmem.yaml) | SM103 tcgen05/TMEM 方案。实例：`plmn_tc::launch_heads<64>(c, splits, po, ml, nullptr, 1)` → `attention<64><<<(batch_count*query_len, splits, 1), 512, 143360>>>`（Heads=64、nhb=1、bf16 操作数、WS 形式 MMA），归并沿用 root 的 `plmn_combine_wide_hb32`，host 以两节点 CUDA 图复用启动结构。机制：不压缩选择子，按 64 个原始槽位为一 chunk 做带 valid 掩码的有序 gather，chunk 数恒为 ceil(listn/64)，split 以 `ci = sp; ci += splits` 循环领取；每线程先把本 chunk 的压缩字节读进寄存器（RawTile），与 barrier 初始化、512 列 TMEM 分配和 Q 的 TMA 搬运重叠；解码成 bf16 写入单缓冲 K smem（SW64 布局）；QK^T 与 PV 都由 tid==0 单线程发 `tcgen05.mma`，累加器常驻 TMEM，用 `tcgen05.commit` + mbarrier parity 等待完成；softmax 在 log2 域，行最大跨 group 经 smem 交换并带“超过 m+2 才抬升”的滞后规则以省去 rescale，alpha 变化时对 TMEM 累加器做 warp 集体 read-modify-write；概率以 bf16 写回 smem；尾部把 TMEM 输出打包成 fp16 存进复用 Q 区的 520-half staging 行并写 (m, l)，随后无条件走 partials → 归并，即使 splits = 1 主 kernel 也从不直接写 out/lse。保留理由：操作数存储（TMEM 而非寄存器）、单线程 MMA 发射与 mbarrier 完成关系、掩码式非压缩 gather、循环领取，以及“输出永远由归并阶段产生”的两段式输出形成，都需要相对 root 重新贯通，不能由 root 加差额说明表达。本设计另有五条以它为基线的变体记录（Heads=128 实例、双 64-head CTA 配对、融合式 split 归并、CUDA 图启动结构、cp.async Q 搬运），见“变体与组合”。 | 与 root 并列的独立完整设计，不派生自 root；源码层面启动与 root 相同的 WIDE combine 内核对象，三个 Design 区域全部本地定义，无 `from` 边 |

## 变体与组合

以下九条正式记录按对象名定位而非行号：前四条以 [root](root.yaml) 中已有对象为基线，后五条以 [tcgen05_tmem](tcgen05_tmem.yaml) 中已有对象为基线；源码锚点用固定版本的文本文件名加行号，不作链接。每条记录分别给出设计成立条件、源码选择条件与实验覆盖，三者不互相替代；精确参数与 `when` 以 YAML 为准。

### HB=64/NT=512 几何（参数）

- 基线：[root](root.yaml) 的 `DESIGN.Math_reshape::Selected-row order and chunking`（压缩宽度 256）、`DESIGN.Work_schedule::MAIN`（`Partition.head_block` 的 size head_count/32、`Mapping.Worker_count`、`Mapping.Strategy` 的 256 线程）、`DESIGN.Tile_pipeline::MAIN`（`Role.MAIN.Info.Member` warp[0:8]、`Storage` 的 q_slot/p_slot/reduce_slot 尺寸、`compute:kd` 的每线程解码切片）与 `REALIZATION::Require` 两条。
- 差异与联动：同一份 kernel_mma.cuh 以 `PLMN_HB=64 / PLMN_NT=512` 第二次包含（launch.cu:55-67），算术与 Pipe 顺序不变；联动为 `head_block` 的 size 变 head_count/64、`Worker_count` 变 (head_count/64)*(batch_count*query_len)*splits、`Member` 变 warp[0:16]（wm 取 0..3，wn 仍是 4 个 token warp）、每线程解码切片从 128 维降到 64 维（NBG 4→8、BLKS 4→2），q_slot 33280→66560、p_slot 4608→9216、reduce_slot 576→1088（k_slot 66560 不变），`Require` 的 smem 由 105024 + 8*(swa_budget+cmp_budget) 变 143424 + 8*(swa_budget+cmp_budget)、每 SM 常驻 CTA 由 2 变 1，每 head 的重复解码从 head_count/32 次降到 head_count/64 次。另一处数值联动：Math 的压缩宽度 256 变 512，每线程选择子条目 per = ceil(budget/NT) 由 2 变 1，写入顺序仍是线程主序，因此压缩段行序由递增 t 的一个排列变成与递增 t 完全一致；两者选出的行集合相同，只差 FP 求和顺序，所以 kernel_mma.cuh:9-12 “两个实例结果逐位相同”的说法只在 budget ≤ NT 时成立，不得写进设计当作保证。
- 条件与依据：设计成立条件是 head_count % 64 == 0 且 ceil(budget/NT) ≤ MAXENT = 4（NT=512 时该上界更宽）。源码选择条件 `use_hb64_shape`（launch.cu:99-110）另要求 nest ≥ listn、`cfg64::best_one_round` 给出非零 splits（即 items*splits 能一波装下 nsm*MINCTA）、其 depth 不超过 `cfg32::schedule` 的 depth，且 5*cfg32 的 SM 数 < 6*cfg64 的 SM 数；不满足时仍走 root 的 HB=32 实例。实验覆盖：源包未附该几何比较的原始回执，只有 kernel_mma.cuh:22-26 与 launch.cu:39-40 的定性说明（同 SM 上 16 warp、重复解码减半、总 smem 流量相同）。

### 窄 combine 几何（局部）

- 基线：[root](root.yaml) 的 `DESIGN.Work_schedule::COMBINE`（`Partition.row_head` 的 tile 4、`Mapping.Worker_count` ceil_div(batch_count*query_len*head_count, 4)、`Mapping.Strategy` 的一 warp 一 head 与一 lane 一 split、`Target.Tile_reduction`）、`DESIGN.Tile_pipeline::COMBINE`（`Role.MAIN.Info.Member` warp[0:4]、`Storage` 的 merge_acc/partial_batch、`compute:merge_stats`/`compute:merged_out`/`store:outputs`）与 `REALIZATION::Prefer`。
- 差异与联动：改由每个 (request row, head) 一个 128 线程 CTA、每线程 4 个输出维（kernel_mma.cuh:872-926），即 `row_head` 的 tile 变 1、`Worker_count` 变 batch_count*query_len*head_count，`Mapping.Strategy` 由“一 warp 一 head、一 lane 一 split”换成“一 CTA 一 head、一线程 4 个输出维、对 splits 串行”（128 线程仍写作 warp[0:4]，但 warp 不再对应 head，`merge_acc` 由每线程 4 维承担）；`merge_stats` 的 mmax/lsum 不再用 32-lane butterfly，而是对 splits 的串行升序循环并跳过 partial_max = -inf 的 split，故 root 中 WIDE 的 Accumulate 措辞不覆盖这条记录；`merged_out` 不再需要 partial_batch 的四 split 批处理，`Prefer` 的“四 split 在飞”随之失效，读取仍是 `__ldcs` 流式；WIDE 把零权 split 也加载并按 0 加权以免每次加载等待自己的权重，窄几何直接跳过。归并算术、per-split 权重、log2 域 sink 重标定与“无 split 见到 token 时输出零、lse = +inf”的规则沿用 root 的 `Split merge and sink normalization`，MAIN、partial 布局与 `Flow.Handoff` 均不变。
- 条件与依据：只适用 mma 家族——cfg32 与上一条的 HB=64 几何共用同一段 launch 代码；tcgen05_tmem 的独立归并恒用 WIDE（kernel_tcgen.cuh:682-684、729-730），没有窄形态。源码选择条件：splits > 1 且 ceil(batch_count*query_len*head_count/4) < nsm（kernel_mma.cuh:1065-1075）。域内可达性：冻结 shape 8（BS=1、head_count=64）的 wgrid = 16，只有 nsm ≤ 16 才会改选 WIDE，而 nsm ≤ 28 时该 shape 会先进 tcgen 分支（BS*nhb*min(16,chunks) = 10），故走 mma 分支的 shape 8 必落窄几何；随包 ACCEPTANCE 记录其 candidate kernel_count = 2，与“主 kernel + 一个 combine”一致。

### splits = 1 直写（参数）

- 基线：[root](root.yaml) 的 `META_DATA.Dispatch.when`（fan-out 大于 1）、`DESIGN.Math_reshape::Split partials` 与 `Split merge and sink normalization`、`DESIGN.Work_schedule::MAIN`（`Partition.split` 的 range [2, 16]、`Flow.Launch`、`Flow.Handoff`）、`DESIGN.Work_schedule::COMBINE` 整步，以及 `DESIGN.Tile_pipeline::MAIN.Role.MAIN` 的 `store:partials` 与 `store:identity_partial`。
- 差异与联动：splits 取 1 时 grid.z = 1，`Partition.split` 的 size 变 1（落在 root 的 `when` 之外，故 root 本体不承担）；`Flow.Launch` 只剩 MAIN 一次提交，`Flow.Handoff` 的三个 partial 键与整个 COMBINE step 不再成立，host 也不分配 part_o/part_ml（launch.cu:324-333）、不启动第二个 kernel（kernel_mma.cuh:1065）；输出生产者由 COMBINE 变回 MAIN——MAIN 自己完成跨 warp 行和、log2 域 sink 重标定 `lae2 = max(lse2, sk2) + log2(1 + 2^-|lse2-sk2|)`、`f = 2^(m - lae2)`，直接写 bf16 out 与自然对数 lse（kernel_mma.cuh:748-769）；空选择的 (r, j) 在这条路径上由 `store:identity_partial` 换成直接写零与 +inf（kernel_mma.cuh:479-485），不再发布 identity partial，`Split merge and sink normalization` 的公式移入 MAIN 尾部，partial_max/partial_sum/partial_out 三个符号随之消失。
- 条件与依据：源码选择条件是 `plan_splits` 在 items ≥ nsm 或 chunk 数很少时可返回 1（kernel_mma.cuh:970-1012）。tcgen05_tmem 没有对应的直写形态：其主 kernel 无论 splits 取值都只写 partials，splits = 1 时输出仍由 WIDE combine 产生（kernel_tcgen.cuh:502-546、682-709）。

### split 扇出与路径选择规则（参数）

- 基线：[root](root.yaml) 的 `DESIGN.Math_reshape::Split partials`（symbol splits）、`DESIGN.Work_schedule::MAIN`（`Partition.split` 的 size 与 range、`Decomposition.Strategy` 的 per_split/c_first/c_last）、`META_DATA.Dispatch.when`；同一条规则也约束 [tcgen05_tmem](tcgen05_tmem.yaml) 的 `DESIGN.Math_reshape::Split partials`（symbol splits）、`DESIGN.Work_schedule::MAIN.Decomposition.Strategy`（ci(c) = sp + c*splits 与 claim_count）、`Partition.split`（range [1, 16]）与 `META_DATA.Dispatch.when`。
- 差异与联动：splits 的具体取值由 host 每次调用从声明的 shape 元数据推出，它不是任何 YAML 的字段值；YAML 只固定 splits 的含义、范围与由它推出的工作划分。mma 路径用 `plan_splits` 的成本模型：items = BS*(head_count/HB) < nsm 时取 ceil(nsm/items) 并按 maxchunk 与 MAXSPLIT=16 封顶，否则在 per = ceil(maxchunk/sp) ≥ MINCHUNK=3 的候选里最小化 rounds*(per*64+39)，rounds 按 cpa = min(MINCTA, smem_per_sm/smem) 折算；cfg64 另用 `best_one_round` 要求一波装下（kernel_mma.cuh:964-1046）。tcgen 路径用 `max_splits = min(16, chunks, max(1, nsm/(BS*nhb)))`，再在能达到最小 depth 的取值里取最大能整除 chunks 的那个，以免留下被合并尾部等待的掉队 CTA（launch.cu:294-305）。路径本身是三级判定：use_tc = head_count ≤ 128 且 listn ≥ 128 且 BS*nhb*min(16,chunks) ≥ (nsm+2)/3，否则 use64，否则 cfg32（launch.cu:279-280、386-392）。maxchunk 与 chunks 的口径不同：mma 用 nest 推出的 chunk 数，tcgen 恒用 ceil(listn/64)，所以短上下文在 tcgen 路径上仍会走完全部 chunk 并对无效槽位做掩码。
- 条件与依据：这些规则只在已收录的配置之间选择，不构成新设计，`when` 也不承担原 selector 的证明职责。来源限制：nest 是 host 用缓存 page 数推出的上界（launch.cu:214-220），依赖 input.py 的 `pages = sum(counts) + 2` 约定（input.py:64），只能高估、只会导致多分；root 的 nchunk 来自真实压缩计数 N（kernel_mma.cuh:468-471），Design 不依赖 nest，所以该上界只影响扇出与几何选择、不影响结果，作为来源限制记在本条而不写进任何 YAML 的保证。nsm 与 smem_per_sm 是运行时查询值（见“范围”）。实验覆盖分两类且不能互替：随包的 ACCEPTANCE.json 与 SUMMARY.json 给出十个冻结 shape 上最终配置的 NCU 计时（production 与 candidate 各 20 个 samples_us、by_order 中位数、kernel_sum_us、ratios、kernel_count 与通过/超限列表），足以核对这些规则在冻结用例上实际选中了哪条路径（kernel_count 就反映是否融合、是否发了第二个 kernel），但它测的是最终配置，不能分离单条规则的贡献；而源码注释中推导这些阈值所用的机制级 A/B 测量（launch.cu:262-293、335-367 引用的 evidence/online-20261024/raw/*）原始回执未随源包提供，故阈值本身只有源码注释的转述、无法独立复核。

### Heads=128 实例（局部）

- 基线：[tcgen05_tmem](tcgen05_tmem.yaml) 的 `DESIGN.Tile_pipeline::MAIN.Storage` 的 `tmem_acc`（qk 视图 [256, 288)、pv 视图 [0, 256)）与 `q_slot`、`p_slot`、`score_acc`（shape [{head: 64}, {slot: nc}]）的尺寸，`DESIGN.Tile_pipeline::MAIN.Role.MAIN` 的 `matmul:q@kd`、`matmul:e16@kd`、`compute:staged_out`，以及 `REALIZATION::Require` 的 q_slot staging 容量条。
- 差异与联动：同一份 kernel_tcgen.cuh 以 Heads = 128 实例化（`launch_heads<128>`）。`matmul:q@kd` 与 `matmul:e16@kd` 由 WS 形式改用非 WS 的 `tcgen05.mma` 形式（kernel_tcgen.cuh:57-71）；`tmem_acc` 的 qk 视图由 [256, 288) 移到 [448, 512)、pv 视图由 [0, 256) 扩为 [0, 448)——TMEM 512 列中输出占 448 列、score 占 64 列，最后 64 个输出维放不进 TMEM，新增每线程的 tail 寄存器存储：16 个 fp32 承载末 64 维（512 线程 × 16 = 128 × 64），随 alpha 一起缩放并在每个 chunk 后从 TMEM 累加进来（kernel_tcgen.cuh:442-445、480-486）；`matmul:e16@kd` 由 2 个 N256 tile 变成 N256 + N192 + N64，且 tail tile 的 accumulate 谓词每 chunk 复位（kernel_tcgen.cuh:464-473）；`compute:staged_out` 增加 col < OutputCols 分支与 tail 的合并（kernel_tcgen.cuh:509-523）；列映射变为 group = tid/128（4 组 × 16 值，kernel_tcgen.cuh:274-279）；`score_acc` 的 shape 扩为 [{head: 128}, {slot: nc}]，`q_slot` 扩为 131072 字节、`p_slot` 扩为 16384 字节，SMEM<128> = 217088 字节；`REALIZATION::Require` 的 q_slot 条 staging 关系变 133120 > 131072。主计算、gather、softmax 滞后规则、输出形成与归并方式均不变。
- 条件与依据：设计成立条件：head_count = 128 且 BS*4 > nsm（此时 tc_nhb = 1，launch.cu:275、kernel_tcgen.cuh:733-740）。域内可达性：冻结 shape 0（16 个请求 × query_len 3 → BS=48、head_count = 128）在 nsm < 192 的机器上属这一形态，随包 ACCEPTANCE 记录该 shape 只有 1 个 kernel，与 128-head 融合形态一致。

### 双 64-head CTA 配对（局部）

- 基线：[tcgen05_tmem](tcgen05_tmem.yaml) 的 `DESIGN.Work_schedule::MAIN.Decomposition.Partition`（row 与 split 两轴）、`Mapping.Worker_count`、`Worktile.Invariant.q`，以及 `DESIGN.Tile_pipeline::MAIN.Role.MAIN` 的 `load:q`、`compute:staged_out`、`store:partials`。
- 差异与联动：`Partition` 新增 head_block 轴（grid 变 (BS, splits, nhb)，grid.z = nhb = 2），一个 head_count = 128 的请求行由两个 64-head CTA 分担；`Mapping.Worker_count` 变为 2 倍；`Worktile.Invariant.q` 的 64 个头成为该行中本 CTA 负责的 block；`load:q` 只搬本 block 的 64 KB Q，只累加自己那一半输出；kernel 内 head 索引变为绝对值 hbase + local，而 smem 索引与 `compute:staged_out`、`store:partials` 的 staging 索引仍是 block-local（kernel_tcgen.cuh:263-271）；融合归并时同行 peer 组变成 bs*nhb + hb，且每 CTA 合并的 head 范围是本 block Heads 的一个切片（kernel_tcgen.cuh:539-546、560-570）。同一行的 CTA 数翻倍，因此一波常驻预算只买得起一半的 splits，partial 数量与归并量随之减半，代价是 gather 重复一次。
- 条件与依据：设计成立条件与源码选择条件：host 仅在 head_count = 128 且 BS*4 ≤ nsm 时取 nhb = 2（launch.cu:275）。实验覆盖：源码注释记录的本机测量为 BS=3/8/12/32 变快、BS=48 变慢，故配对只在还给该行留出两个 split 时使用（launch.cu:262-274），原始回执未随源包提供。

### 融合式 split 归并（局部）

- 基线：[tcgen05_tmem](tcgen05_tmem.yaml) 的 `DESIGN.Work_schedule::COMBINE` 整步、`Flow.Launch`（两次提交）与 `Flow.Handoff`（三个 partial 经 global），`DESIGN.Tile_pipeline::MAIN.Role.MAIN` 的 `store:partials` 与 `compute:staged_out`（其 staging 行复用 q_slot），以及 `DESIGN.Math_reshape::Split merge and sink normalization`。
- 差异与联动：host 传非空 counters 时，`COMBINE` 整步取消，`Flow.Launch` 变为单提交，归并移入主 kernel 尾部（kernel_tcgen.cuh:539-577）：`store:partials` 跳过本 CTA 的自归并段 [h0, h1)，自己那一份 partial 留在 q_slot 的 staging 行、不写 global（`Flow.Handoff` 中 own partial 的存放随之改变），peer 的仍从 global 以 `__ldcs` 流式读入；其后新增尾部动作——每个 (request row, head block) 一组 arrive/done int32 计数器，tid==0 以 `atom.add.release.gpu` 报到后用 `ld.acquire.gpu` 自旋到 splits 个 peer 全部到齐；head 按 `[hbase + sp*Heads/splits, hbase + (sp+1)*Heads/splits)` 在 splits 之间划分，16 个 warp 以 warp-per-head 合并；组内最后一个 CTA 用 `st.release` 把两个计数器归零交回下次 launch（kernel_tcgen.cuh:558-577）。三点联动：输出生产者由第二个 kernel 变为主 kernel 尾部；新增的计数器缓冲（2*BS*nhb 个 int32）是跨调用状态，进入时必须为零，host 只在缓冲增长时 `torch::zeros`、由 kernel 自己归还零（launch.cu:377-383）；q_slot 的 staging 行寿命须覆盖到归并读完。归并算术与基线的 `Split merge and sink normalization` 逐项相同（kernel_tcgen.cuh:164-244 对应 kernel_mma.cuh:806-824：同样的 per-split 权重、log2 域 sink 重标定与零/+inf 规则）；整区不能部分引用，故基线的 Math_reshape 仍本地保留这份定义，目录不复制其内容。判为局部而非独立完整设计：主计算、grid、主循环协作与归并算术逐项不变，变化围绕已有 COMBINE step 的执行者与 own partial 的存放位置，加上上述三点联动。
- 条件与依据：设计成立条件：自旋要求同行全部 split 同时常驻，host 因此重新核对保证而不只依赖启发式——BS*nhb*splits ≤ nsm 且 `SMEM<Heads>*2 > smem_per_sm`（查询值，即每 SM 恰好一个 CTA），Heads=64 时另需 splits*512 ≥ 64*32（launch.cu:368-384、kernel_tcgen.cuh:604-611）。实验覆盖：源码注释记录的本机测量为 128-head 形态各 split 数均受益、64-head 形态只在 splits*16 ≥ Heads 时受益（launch.cu:350-367），原始回执未随源包提供。

### 启动结构：CUDA 图复用与录图时直接双 launch（局部）

- 基线：[tcgen05_tmem](tcgen05_tmem.yaml) 的 `DESIGN.Work_schedule::Flow.Launch`（MAIN → COMBINE 两次提交）与 `REALIZATION::Prefer` 的 CUDA 图条目。
- 差异与联动：非融合且流未在录图时，host 把 `Flow.Launch` 的两次 kernel 提交记成一张两节点图并跨调用复用，主节点收到 `lse = nullptr` 的上下文副本（主 kernel 只写私有 partials），归并节点的 lse 实参在每次新分配地址变化时用 `cudaGraphExecKernelNodeSetParams` 打补丁；流正在录图时不建图、不查图，直接按 host 顺序发两次 launch（kernel_tcgen.cuh:649-731）。已定向核实“记录结构 vs 实际提交”：图的 key 覆盖全部影响地址与形状的字段（q/k1/idx1/k2/idx2/sink/sm_scale/out/H/BS/两个 budget/page/rec/listn）外加 device、stream、splits、nhb、po、ml，任一变化即销毁重建；两个节点每次 `cudaGraphLaunch` 都真实执行且有依赖边，缓存的只是启动结构，不缓存任何计算结果或副作用；TMA descriptor 与 nsm/smem_per_sm 的 thread_local 缓存同理只缓存描述符与设备属性（对应基线的 `REALIZATION::Require` tensor-map 条与 `Prefer` descriptor 缓存条），Q 字节仍在执行时读取。benchmark 的 `preserve_input_storage` 与 `restore_before_each_call` 约定使输入指针跨调用稳定而数值被回卷，正好落在 key 命中且数据仍被重读的语义内。
- 条件与依据：只适用于本设计的独立归并形态（融合形态只有一次 launch，无图）；root 的两个 kernel 始终直接 launch，不建图。

### cp.async Q 搬运（参数）

- 基线：[tcgen05_tmem](tcgen05_tmem.yaml) 的 `DESIGN.Tile_pipeline::MAIN.Role.MAIN` 的 `load:q` 与 `await:q`，以及 `REALIZATION::Require` 的 tensor-map staging 条、`Prefer` 的 descriptor 缓存条。
- 差异与联动：`cuTensorMapEncodeTiled` 的驱动入口查不到或编码失败时 use_tma = false，`load:q` 改用每线程 16 字节的 `cp.async.cg` 把同样的 bf16 字节搬进同一 SW64 布局，超出 head_count 的补齐行由 size predicate 填零；`await:q` 由等待 mbarrier 的 expect_tx 改成 `cp.async.wait_group 0`（kernel_tcgen.cuh:311-336、376-382、490-496）。操作数仍是 bf16，因此 QK 的 A operand 依旧无需转换 pass，数值与 MMA 序列不变。
- 条件与依据：host 侧 thread_local 缓存以 (q 指针, H, BS, device) 为键重新编码（kernel_tcgen.cuh:627-637）；两条路径都由第一个 chunk 的解码与之重叠。
