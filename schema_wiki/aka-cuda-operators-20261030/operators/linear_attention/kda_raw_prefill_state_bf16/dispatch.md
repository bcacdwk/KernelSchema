# kda_raw_prefill_state_bf16

## 范围

实现范围以冻结 host 入口 `candidate/solution.py::Model.forward` 为准；`runtime.py` 只做本地 CUDA 模块的 JIT 编译与按 shape 的工作区缓存，`problem/solution.py` 是生产对照，不在本次提取范围内。入口先做参数归一，再按占用率启发式在两个互斥的实现族之间二选一；两族都在同一 CUDA 流上顺序提交，都独立产出共享 Contract 的全部三个输出，没有第三条可进入的实现路径。

参数归一与固定实参：`output is None` 时新分配 `empty_like(q)`；`beta` 非连续或基址不是 16 字节对齐时，先由 `preprocess.cu::aka_kda_pack_beta`（角色 `beta_pack`，256 线程）值不变地收集到新的连续缓冲，两族都依赖它满足 TMA 描述符对连续性与对齐的要求；`initial_state` 同时作为初值与就地写回目标传入；`use_state_indices` 恒为 0（`state_indices` 是 1 元素占位），`use_initial_state` 与 `store_final_state` 恒为 1；`scale` 按 `scale or 128 ** (-0.5)` 解析，与 Contract 的 `Golden_reference.Gap` 一致；关闭的功能用 1 元素占位缓冲（`unused_indices`、`unused_ckpt`、`unused_ckpt_starts`）满足 ABI。

选择条件是 `solution.py::Model.forward` 中的 `engine` 赋值式：记 `sms` 为设备 SM 数、`parallel_states = request_count * head_count`，则 `engine = cadence % 32 == 0 and (2 * parallel_states > sms or (3 * parallel_states > sms and total_tokens <= 4096 and cadence == 0))`。声明域内 cadence 属于 {0, 32, 64, 128}，恒满足 `% 32 == 0`，因此 cadence > 0 时只取决于 `2 * parallel_states > sms`。取真时进入 root（融合单 kernel），否则进入 [prepare_chain](prepare_chain.yaml)（两段式）。

selector 之外还有一条服务边界：engine host 的 `host_helpers.cuh::EncodeBetaTma` 对 beta TMA 描述符强制 token 维不小于 32（box 为 8 head × 32 token；直绑 beta 的行数 total_tokens 与补齐工作区的行数 max(total_tokens, 16) 都必须 >= 32），因此 engine 路径实际只服务 total_tokens >= 32，root.yaml 的 `when` 已写明该限制。selector 取真而 total_tokens < 32 的输入被冻结 host 校验拒绝（抛错，非数值损坏），两族设计的 `when` 都不覆盖，属已记录的覆盖缺口，Contract 有效域不因此缩小。prepare 侧的 beta 编码（`descriptors.cuh::EncodeBt16NativeBetaTma`）只校验 beta 连续、基址 16 字节对齐与 box 不超过 512 字节，没有这条 32-token box 校验；该路径其余的服务条件只有 `capacity`（即 prepare 的 total_chunks 实参）> 0、prepare 的 CTA 数落在 [head_count, head_count * capacity] 内，以及 chain 的 grid_x == 2 * request_count * head_count，三者在声明域内恒成立。因此 prepare_chain 的 `when` 不设 total_tokens 下界：selector 取假即由该节点承担，与 root 的 32-token 限制互补而不重叠。

拒绝或限制的范围：入口断言 device capability 必须为 `(10, 3)`、`q` 为 CUDA bf16、batch 轴为 1、`key_dim` 为 128、`q/k/v/g/A_log/dt_bias/initial_state/cu_seqlens` 连续、四个布尔标志为真、`lower_bound < 0`、`cadence >= 0` 且为 16 的倍数，`cadence > 0` 时还要求 `state_checkpoints` 与 `checkpoint_cu_starts` 连续且 dtype 正确。selector 的 `cadence % 32 == 0` 一项与 engine 侧 `CheckServingCheckpointInputs` 的 32 token 粒度检查一致，chain 侧只要求 `cadence // 16`，因此声明域外的 cadence = 16 或 48 只可能由 prepare/chain 承担。

root 选择依据：engine 把归一、衰减前缀、三角逆、递推、读出与状态/checkpoint 写全部关在一个计算 CTA 内（此前只有一次 1×128 的 metadata 提交生成请求顺序），状态不出芯片，也不依赖任何跨 kernel 工作区，与 Contract 数学逐步对应，最便于独立阅读并作为比较基线；它无需最复杂或最通用，prepare/chain 也不是它的派生，两者是并列方案。

具体未知边界：

- `sms` 来自 `torch.cuda.get_device_properties(...).multi_processor_count`，是运行时设备属性，固定来源（含 ACCEPTANCE.json 与 SUMMARY.json 的环境记录）没有给出数值，因此两族之间的精确数值分界无法由来源确定。两份设计的 `when` 只能引用该 selector 表达式本身（含 `sms`），不能改写成纯输入域条件。两族在声明域内都真实可达：固定用例 0、1（head_count = 96、request_count = 1）与用例 2（48、16）的 `2 * parallel_states` 分别为 192 与 1536，用例 4、5（head_count = 12、request_count = 1）与用例 8（cadence = 64，12、2）分别为 24 与 48，因此只要 `sms` 落在 48 与 192 之间——SM103 的任何合理取值都满足——前三个用例走 engine、后三个走 prepare/chain，PRECISION.md 记录的采样通过因而覆盖两族（这一覆盖是按形状推得的，来源未逐用例标注所走分支，不得升级为逐用例保证）。去向：root.yaml 的 `when` 已按此约束写成，直接引用 selector 表达式并注明 `sms` 是 host 读取的运行时设备 SM 数；[prepare_chain](prepare_chain.yaml) 的 `when` 以同一 selector 表达式的取假侧写成，并按前述 beta 描述符与 grid 校验不加 total_tokens 下界。
- engine 的 `cu_chunk_offsets` 与 `num_sequences` 实参是 `nullptr` 与 0。读取位置与死亡原因要分开看：compute 角色在**无条件**代码里发出两处加载——主循环前的 `total_chunks = cu_chunk_offsets[num_sequences]`（其唯一使用者 `fallback_head` 全文再无任何引用）与主循环内的 `chunk_global_e = cu_chunk_offsets[seq_idx] + chunk_global_local`（派生出 `tape_ex_base`）；被 `STORE_BACKWARD_TAPE != 0` 守卫（该宏固定为 0，`engine_launch.cu` 有 static_assert）的只是下游消费者，即 tape_e、tape_x、tape_r 的写与第三处 `chunk_global_r` 的加载本身。因此这两处加载不是位于宏守卫内，而是因结果没有活跃消费者才被消除，PRECISION.md 的采样通过与这一读法相容。这是来源限制，不改变设计决定；root.yaml 已按此读法落实——`REALIZATION.Forbid` 把禁用的 ABI 尾部（cu_chunk_offsets、num_sequences、tape 指针、零容量工作区）钉死为 null/0 并记录存活的源文本加载属死代码，二者均未进入 root 的设计输入。
- engine 的残留机械一律未参与工作：`checkpoint_pipe` 的 mbarrier 被初始化、`smem_checkpoint`（偏移 228352，已超出 `SMEM_TOTAL` 227968）与 `smem_short_n32_v` 被声明，但全文从未使用；`work_item_ready` 与 `short_beta_ready` 两组 barrier 同样只初始化不收发，epilogue、aux_mma、mma、prep 四处各声明一个 `_phase_work_item_ready_0*` 相位变量后从未使用；`SPLIT_WORK_ITEMS` 与 `STORE_BACKWARD_TAPE` 都固定为 0；源码标注的 6 个 `Role` 中 beta_prefetch（warp 8）函数体为空、aux_mma（warp 10-11）只声明上述未用相位变量。checkpoint 实际由持有状态的 compute 角色直接写全局。因此 engine 只有一套机制，不存在隐藏的 checkpoint 流水线、split-work 变体或未说明的第二条 beta 预取/辅助 MMA 路径。这些残留已在 root.yaml 落实：`REALIZATION.Forbid` 禁止激活（checkpoint 区超出 227968 B 分配，使用即损坏内存），`REALIZATION.Prefer` 记录 checkpoint 由 COMPUTE 寄存器直写全局，残留区域与空角色均不计入存储账和角色表。

已识别知识的去向：root 侧的三条参数记录见下文“变体与组合”，残留机械与 checkpoint 直写落在 root.yaml 的 `REALIZATION.Forbid` / `REALIZATION.Prefer`，`chunks/mapping/order` 与 beta 补齐工作区由其 ORDER 步、`Flow.Handoff.order` 与“beta TMA 缓冲来源”条目覆盖。prepare_chain 侧的已知机制全部由 [prepare_chain](prepare_chain.yaml) 承担，其三个 Design 区域均为完整本地定义、无整区 `from`，只依赖 root 保存的共享 Contract：

- prepare 的编译期特化（`-DAKA_KDA_HEADS` / `-DAKA_KDA_SEQUENCES`）与 beta 直绑见 `DESIGN.Work_schedule::PREPARE.Schedule` 与 `REALIZATION.Require`；host 估算的 `capacity` 是 `DESIGN.Math_reshape` chunk 编号步登记的上界符号，rank 到全局 chunk 区间的划分、CTA 数与可能为空的 rank 在 `DESIGN.Work_schedule::PREPARE` 的 Decomposition 与 Mapping。
- chain 的 checkpoint 粒度（host 实参 `checkpoint_stride_chunks = cadence // 16`）落在 `DESIGN.Math_reshape` 的 checkpoint 步（`checkpoint_stride` = cadence / chunk_tokens）与 `DESIGN.Tile_pipeline::CHAIN` 两个 compute 角色的条件 `store:checkpoint` 动作；自然请求顺序与 `2 * request_count * head_count` 的 CTA 数在 `DESIGN.Work_schedule::CHAIN` 的 Decomposition 与 Mapping；`qd/kd/w/qk/diag` 五组因子工作区（数学侧即 qd、kd、w、qk_t、gt）的跨 kernel 交接在 `DESIGN.Work_schedule::Flow` 的 Launch 与 Handoff。
- 两族共有的调用边界：`runtime.py::_kda_plan` 按 `(total, heads, sequences, device, stream_id, engine)` 缓存并跨调用复用同一批 host 缓冲，同一流上的顺序提交保证前一个 kernel 写完后一个才读。root 侧由 `DESIGN.Work_schedule::Flow` 的 ORDER -> MAIN（`start_after: ORDER.kernel_done`）与 `Handoff.order` 表达，prepare_chain 侧由 PREPARE -> CHAIN 与五组因子的 Handoff 表达，其 `CHAIN.Schedule` 另记录工作区跨调用复用、槽位恰为 PREPARE 所写因而无需初始化。这些缓冲是内部工作区，不是 Contract 输出。

## 完整设计

| 设计 | 具体机制与保留理由 | 关系 |
| --- | --- | --- |
| [root](root.yaml) | engine 融合单 kernel：先由 `preprocess.cu::aka_kda_packed_metadata`（1×128）按请求长度降序生成 `order`，再由 `engine.cuh::kernel_flashkda_bf16_fused_m128`（grid = request_count * head_count，block = 1024，动态 smem 227968 B，tmem 256 列）以 32 token 为块推进；一个 CTA 承担一个 (request, head) 的全部 128 个 value 行。CTA 内 32 个 warp 中承担稳态工作的是 4 个角色（源码另标注 beta_prefetch(warp 8) 与 aux_mma(warp 10-11) 两个空角色，warp 8-11 统一 dec 到 48 寄存器；启动期设置由 warp 10 初始化 21 组 87 个 mbarrier、warp 0 分配 256 列 tmem，二者不是稳态角色，详见范围小节的残留说明）：prep（warp 12-31，5 个 instance 各绑定一个流水级）用 TMA 载入 q/k/g/beta/v，做 L2 归一、log2 域衰减前缀与 sigmoid(beta)，并用 warp 级 `mma.sync` 求出 32×32 下三角逆 `inv` 与 masked `mqk`；compute（warp 0-3，每线程对应一个 value 行）负责 tmem 中 FP32 状态的读改写：先做 BF16 快照 `state_inp`，再按通道乘 `gt` 衰减写回，并算出 `beta * (v - kd·S)` 残差写回 tmem 供 mma 角色与 `inv` 相乘，checkpoint 与 final_state 也由它直接写全局；mma（warp 9）发四条 tcgen05 MMA——`out = state_inp × qd`、`u_acc = state_inp × kd`、`u = u_raw × inv`，以及一条 N = 160 的融合累加，把 tmem 中相邻的 `state` 与 `out` 当作同一个目标，用 `u` 乘 `[kr, mqk]` 拼接矩阵一次完成状态更新与 intra-chunk 输出项；epilogue（warp 4-7）经 stmatrix 与 TMA 落 32×128 的输出块，尾块改用逐元素写。保留理由：整条数学在一个 CTA 内闭合，中间量不经全局，输出生产者、工作归属与主协作链自成一套完整方案。 | 阅读入口，保存唯一 Contract；已交付的完整基线，`when` 承担 selector 取真且 total_tokens >= 32 的输入（精确写法以 YAML 为准） |
| [prepare_chain](prepare_chain.yaml) | 两段式全局工作区：`prepare.cuh::kernel_flashkda_bf16_bt16_prepare`（grid = ceil(capacity / 4) * head_count，block = 128，smem 44032 B，`__launch_bounds__(128, 5)`）按 (head, 全局 16-token chunk 区间) 分工、每线程固定一个 key 通道，用 warp 级 `mma.sync` 求 16×16 三角逆并把 beta 与逆折叠进因子，把 `qd/kd/w/qk/diag` 五组因子物化到全局工作区；`chain.cuh::kernel_flashkda_bf16_bt16_chain_m64<SaveCheckpoints>`（grid = 2 * request_count * head_count，block = 512，smem 138240 B）每个 CTA 只承担 64 个 value 行，factors warp（14）用 TMA 把因子与 v 送进 8 级环，compute_left/compute_right（warp 4-7、8-11）各负责 tmem 中半个 key 列区间（0-63 与 64-127）的 FP32 状态读改写、BF16 快照 `state_inp`、按通道衰减与 checkpoint/final_state 写，`v - kd·S` 残差（bf16 相减）由 compute_right 追加；mma_state（13）与 mma_q（12）发五条 tcgen05 MMA——`u_acc = state_inp × kd`、`state += u × w_left`、`state += u × w_right`、`out = state_inp × qd` 与 `out += u × qk`，epilogue（warp 0-3）配合 3 个轮转的 tmem 输出累加器与 7 个 smem 输出缓冲，TMA 落 16×64 的输出块。保留理由：intra-chunk 因子的生产者变成独立 kernel 并经全局工作区跨 CTA 共享，value 行被切成两半由两个 CTA 并行，beta 与三角逆已在 prepare 中折叠进因子因而 chain 内不再出现，输出累加与状态更新也各自独立成 MMA（root 则用一条 N = 160 融合），主计算、输出形成、工作归属与主协作都需要重新贯通，无法由 root 加参数或局部差额表达。 | 并列完整设计，与 root 由 host selector 互斥分流；三个 Design 区域均为完整本地定义、无整区 `from`，只依赖 root 保存的共享 Contract；`when` 承担 selector 取假的输入，不设 total_tokens 下界（精确写法以 YAML 为准） |

## 变体与组合

### beta TMA 缓冲来源（参数）

- 基线：[root](root.yaml) engine 启动前 beta TMA 描述符所绑定的缓冲，即 `DESIGN.Work_schedule::MAIN.Schedule` 的 Strategy 记录的直绑取值（beta TMA 描述符绑定连续且对齐的 beta 本身，需 head_count % 8 == 0）；描述符的消费端是 `DESIGN.Tile_pipeline::MAIN.PREP` 的 `load:gate_raw` / `compute:beta` 动作与 `stage_arena` 的 `beta_c(c)` 视图。并列基线：[prepare_chain](prepare_chain.yaml) 的 `DESIGN.Work_schedule::PREPARE.Schedule` Strategy（host 先把跨步或未对齐的 beta 打包成连续缓冲）与 `DESIGN.Tile_pipeline::PREPARE` 的 `load:gate_beta` 动作、`raw_beta` 存储；该节点由 `descriptors.cuh::EncodeBt16NativeBetaTma` 按 head_count 直绑 pair-packed beta。
- 差异与联动：当前取值是 `head_count % 8 == 0 且 total_tokens >= 16` 时直接把 `beta` 当作 `beta_tma`，`PackBetaForTmaIfNeeded` 因指针相同立即返回；另一取值改用 `_kda_plan` 中 `[1, max(total_tokens, 16), ceil(head_count / 8) * 8]` 的 bf16 工作区，并由 `host_helpers.cuh::PackBetaForTmaKernel`（256 线程）按 `beta_token_stride` 收集，同时对 head 与 token 两个方向补齐、越界位置写 0。联动只在描述符侧：kernel 内 prep 角色的 beta TMA 以 8 个 head 为一组解码，再用 `head_idx % 8` 与 `head_idx % 2` 选出本 head 的 logit，因此补齐不改变参与计算的值，PREP 的动作与 `beta_c(c)` 视图在两种取值下不变。prepare_chain 侧不存在这一对取值：其 beta 描述符直绑入口归一后的 beta，没有补齐工作区，两族共用的只有入口的 `aka_kda_pack_beta` 值不变打包。
- 条件与依据：来源选择条件是 `solution.py::Model.forward` 中的 `beta_tma` 选择式（`head_count % 8 == 0 and total_tokens >= 16`）与 `host_helpers.cuh::PackBetaForTmaIfNeeded`；设计成立条件以 root.yaml 的 `when` 为准——`EncodeBetaTma` 的 32-token box 校验使 engine 路径只服务 total_tokens >= 32（见范围小节），选择式中的 `total_tokens >= 16` 一项在该域内恒真，因此声明域（head_count 属于 {8, 12, 16, 24, 32, 48, 64, 96}）内只有 head_count = 12 会走补齐分支，两种取值数值等价。实验覆盖：固定用例中 head_count = 12 的用例 4、5 按形状推得走 prepare/chain，不经过 engine 侧补齐分支；该分支（head_count = 12 且 selector 取真）是否被声明域采样覆盖无法由来源确定，来源未逐样本标注所走分支。此变化只作用于 root：prepare_chain 用 `EncodeBt16NativeBetaTma` 按 head_count 直绑 pair-packed 描述符，不经补齐工作区，head_count = 12 在该节点同样不产生补齐分支；代价是 box 几何随 head_count 变化——head_count = 12 时 432 字节的 box 超出 `raw_beta` 的 256 字节声明槽位，依赖其 `REALIZATION.Require` 钉住的 640 字节布局间隙。

### 请求处理顺序（参数）

- 基线：[root](root.yaml) engine 的 worktile 到 (request, head) 的映射：`DESIGN.Work_schedule::MAIN.Decomposition` 的 `Partition.task` 与 Strategy（task w 映射到 `(order[w / head_count], w % head_count)`）、`MAIN.Schedule.Worktile_order`（按 task 升序），以及 `DESIGN.Work_schedule::ORDER` 步的 `order` 目标（由 `DESIGN.Tile_pipeline::ORDER` 的 `compute:metadata` 按长度降序、等长下标升序生成）。并列基线：[prepare_chain](prepare_chain.yaml) 的 `DESIGN.Work_schedule::CHAIN.Decomposition` Strategy 与 `Worktile_order`——task 升序、task 映射到 `(floor(task / head_count), task % head_count)` 的自然请求顺序；该节点没有 ORDER 步，其 `REALIZATION.Prefer` 记录由每个 CTA 自行重算 chunk 前缀而不增设 metadata 提交。
- 差异与联动：当前取值是 `aka_kda_packed_metadata` 以 `sort_by_length = 1` 生成按请求长度降序、等长时按下标升序的 `order`，engine 用 `seq_order[task_idx / head_count]` 取请求、`task_idx % head_count` 取 head，使最长请求最先开始；另一取值是 `sort_by_length = 0`，即 `order[s] = s` 的自然顺序，此时 `compute:metadata` 的排名循环退化为恒等写入，MAIN 的映射式与全部依赖不变。联动仅限 CTA 到工作的映射，不改变任何数值或依赖。同一 kernel 还产出 `chunks` 与 `chunk_to_seq`，但 engine 启动未消费二者（`capacity` 传 0，`mapping` 是 1 元素占位），root.yaml 的 ORDER 步已把 `chunk_prefix` 目标登记为无消费者。prepare_chain 不消费 `order`，其自然请求顺序由 CHAIN 的映射式固定，不随 `sort_by_length` 变化。
- 条件与依据：来源选择条件是 `preprocess.cu::aka_kda_packed_metadata` 的 `sort_by_length` 分支与 `solution.py::Model.forward` 中传入的 `int(engine)`；engine 路径下该值总为 1，自然顺序这一取值在当前实现中不会进入，属同一机制下的另一参数取值。该参数变化只作用于 root 的 metadata 提交：prepare_chain 无 metadata 提交，`sort_by_length` 的两个取值在该节点都没有对应对象，chain 的 `seq_idx = task_idx / num_heads` 是设计固定而非参数取值。

### 状态槽跨步与索引间接（参数）

- 基线：[root](root.yaml) engine compute 角色的 initial_state / final_state 槽基址计算：`DESIGN.Work_schedule::MAIN.Mapping` 的 Strategy（槽基址 `seq*state_slot_stride + (head*128+row)*128`，host 钉死紧凑跨步 `head_count*128*128`、无索引间接），以及 `DESIGN.Tile_pipeline::MAIN.COMPUTE` 的 `compute:state_init`、`store:checkpoint_entry` / `store:checkpoint` 与 `store:final_state` 动作说明。并列基线：[prepare_chain](prepare_chain.yaml) 的 `DESIGN.Work_schedule::CHAIN.Mapping` Strategy（同一槽基址式与钉死的紧凑跨步，一对 CTA 写不相交的 value 行半）与 `REALIZATION.Forbid`（未用 ABI 实参保持 null/0，kernel 自行解析 state_slot = 请求号），设备侧对应 `DESIGN.Tile_pipeline::CHAIN.COMPUTE_L` / `COMPUTE_R` 的 `compute:state_init`、`store:checkpoint` 与 `store:final_state` 动作。
- 差异与联动：当前取值是 `use_state_indices = 0`、`state_slot_stride = initial_state.stride(0)`，请求 r 的状态基址为 `r * state_slot_stride + (head_idx * 128 + state_row) * 128`，声明域内 `stride(0) = head_count * 128 * 128`；另一取值是 `use_state_indices != 0`，槽号改为 `state_indices[r]`，从而把状态池容量与请求数解耦。联动在 host 校验侧，且两种取值约束不同：`ResolveAndCheckServingStatePoolForDtype` 先要求 `state_slot_stride >= head_count * 128 * 128`，在基线取值 `use_state_indices == 0` 下进一步要求二者**相等**并直接返回池槽数 0；池槽数为 0 又使 `CheckCommonInputs` 的 `active_state_slots` 退回 `request_count`，于是要求 `initial_state.numel() == request_count * head_count * 128 * 128`（`store_final_state != 0` 时对 `final_state` 同样要求），这与共享 Contract 把 initial_state 登记为恰 `request_count` 个槽一致。只有 `use_state_indices != 0` 这一取值才允许更大池的视图：`state_indices` 须为每请求一个 int32 槽号，两个状态张量都须为 `[N_pool, head_count, 128, 128]`、槽内连续、`stride(0) == state_slot_stride`、基址与槽跨步按状态元素大小满足 16 字节对齐，池槽数由 `size(0)` 核定并要求两者相同，`CheckServingAuxiliaryNoOverlap` 也只在这一取值下检查 `state_indices` 与其他张量不重叠。所以 `state_slot_stride` 虽是独立实参，在基线取值下被 host 校验钉死为 `head_count * 128 * 128`，只有启用索引间接时才允许更大池的视图。chain 侧的 host 校验同出一处：`chain_launch.cu::ResolveStatePointerSlots` 调用同一 `ResolveAndCheckServingStatePoolForDtype`，因此上述池容量与对齐约束对两族一致。
- 条件与依据：`engine.cuh::kernel_flashkda_bf16_fused_m128` compute 角色的 `state_slot` / `state_base` 计算与 `host_helpers.cuh::ResolveAndCheckServingStatePool`；本 host 恒传 0 与 1 元素占位，索引间接这一取值不会进入。`chain.cuh` 接收同一 `use_state_indices` 实参但内部固定 `state_slot = seq_idx`、不做间接，两族在当前 host 下行为一致；来源差异在于 chain 的 `state_indices`、`use_state_indices` 与两个 FP32 状态指针只出现在 kernel 签名中、正文从不读取，其 `REALIZATION.Forbid` 已把这四个实参钉死为 null/0，因此索引间接在 prepare_chain 不是可启用的参数取值。
