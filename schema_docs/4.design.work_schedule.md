# 工作调度

本篇从[单个 phase](#单个-phase)的一份工作讲起，再说明[提交与接续](#phase-的提交与接续)和[跨 phase 数据交接](#跨-phase-数据交接)。

## 核心思想

`design.work_schedule` 把上游确定的计算切成可以独立分配的工作，交给具体的执行单元，并安排这些工作怎样排列、分配和接续。它站在算法与硬件之间：向上，把 `math_reshape` 定下的值和索引划成一份份工作，决定哪些数据在一份工作内复用、哪些随局部迭代流过；向下，把这些工作放到设备实际提供的执行单元上，使它们能连续、均衡地推进。

本区不重新定义数学算法，也不展开 warp 分工、逐线程地址、指令、barrier 编号或寄存器布局。它接收 `math_reshape` 给出的值、索引、数学关系、精度和状态初值，并固定其中留给下游绑定的工作参数（分块长度、行集合、遍历映射）；执行单元的名称取自 `contract.hardware_specification`，设备规模这类数值来自它绑定的资料；向 `tile_pipeline` 提供工作边界、worker 身份、执行作用域及必要的交接要求。

### 基本对象

| 对象 | 含义 | 需要避免的混淆 |
| --- | --- | --- |
| `worktile` | 一份可以独立分配的计算工作，可以产生最终结果，也可以产生部分结果 | 不等于输入张量的一块存储，也不等于一次局部循环迭代 |
| `worker` | 承担工作的协作执行单元，可以由一个或多个执行单元组成 | 不等于一个线程；一个 worker 可以连续处理多个 worktile |
| `phase` | 一类具有明确分解、映射和分配规则的工作定义 | 不等于数学步骤、kernel launch 或缓冲槽 |

本区的核心区分是：

> **worktile 的排列不等于 worker 的工作归属；预先获配的工作不等于运行时新领取的工作。**

本区使用 `thesis / flow / phase`：

- `thesis` 概括整体工作组织中最重要的设计选择。
- `phase` 是工作定义的唯一登记处，采用具名映射。
- `flow` 引用这些定义，记录计算 kernel 的边界、同一次提交内的接续方式和跨 phase 数据交接。

`flow.launch` 的一个条目对应一次计算 kernel 提交，可以包含一个 phase，也可以包含由同一批 worker 接续执行、或由不同 worker 同时承担的多个 phase，因此 phase 数量与 kernel 数量没有对应关系。

### phase 粒度

多数算子只有一个 phase。只有当一份分解、映射和分配规则说不清实际的工作组织时，才登记第二个 phase：例如 chunk 先是独立工作维度，进入状态递推后变成 worker 内的顺序迭代，再恢复为独立工作维度，这几段才需要分别登记。

phase 标签本身不产生 launch、全体屏障、全局物化或资源重置，真正发生的这些行为则必须写进相应字段。phase 的多少也不是优化目标：一个 phase 可以包含多种计算，多个 phase 也可以处于同一个 kernel。

### 设计着眼点

上游已经定下算什么，本区决定这些计算怎样摊到设备上。一个 phase 的时长大致是一份工作的时长乘以工作总数、再除以能同时驻留的 worker 数，静态分配时还要向上取整到整波。所以第一个决定是一份工作切多大：它同时决定了一份工作里复用多少数据、占多少片上资源（于是能驻留几个 worker），以及一共切出多少份。随后才是这些工作由谁承担、怎样排列和领取，使最后一波不空、各 worker 不互相等待。字段只是答案的落点。

| 问题 | 要看什么 | 答案落在 |
| --- | --- | --- |
| 并行度够不够 | worktile 总数能否填满设备，最后一波有多空 | `partition` 的 `tile`、`mapping.count` |
| 一份工作内复用了什么 | 哪些数据读进来反复使用，哪些只流过一遍 | `worktile.invariant`、`worktile.iteration` |
| 一份工作要占多少片上资源 | 同时持有的输入块与结果块有多少字节 | 数据块的 `shape / dtype` |
| 一份工作要几个单元一起做 | 合起来能共享什么，分开做会重复搬运什么 | `mapping.worker`、`placement`、`member` |
| 工作量均不均衡 | 各份工作的内部迭代长度是否相近，差距大时靠什么补 | `worktile_order`、`worker_assignment` |
| 中间结果走哪条路 | 写回全局内存再读出，还是留在同一个 worker 的局部资源里 | `flow.launch[].order`、`handoff.storage` |

## 单个 phase

一个 phase 必填 `describe / decomposition / mapping / schedule`，分别说明计算什么、一份工作是什么、由谁执行、怎样排列与分配。它在 `work_schedule.phase` 中以 phase ID 登记；单 phase 的最小提交外壳见[最小 flow](#最小-flow)。

### 结构轮廓

```text
phase.<phase_id>
  describe
  decomposition
    strategy?
    partition: <dimension>: size / tile / range?
    worktile?: invariant? / iteration?
      <value>: shape / dtype / offset? / direction?
    target
      single_tile: <value>: shape / dtype
      tile_reduction?: dimension / input / output / method
  mapping: strategy? / worker / placement? / count / member?
  schedule
    strategy?
    worktile_order[]: by / group? / direction
    worker_assignment: preassigned? / refill / exit
```

phase ID 使用通用标识符，推荐简短的小写名称；数学值、维度与规模的名称沿用上游符号，保留大小写。通用命名与 YAML 写法见[公共约定](0.common.md#通用写法)。

以下两项路径相对于 `work_schedule`：

| 字段路径 | 值的形式 | 填写条件 | 含义与约束 |
| --- | --- | --- | --- |
| `thesis` | 非空英文字符串 | 必填 | 一两句说明整体工作组织最重要的选择、它换来了什么、付出了什么 |
| `phase.<phase_id>.describe` | 非空英文字符串 | 必填 | 说明这类工作计算什么 |

### 工作分解

下表中的路径相对于 `phase.<phase_id>.decomposition`。

| 字段路径 | 值的形式 | 填写条件 | 含义与约束 |
| --- | --- | --- | --- |
| `strategy` | 非空英文字符串 | 结构字段说不清一个必要的分解决定时填写 | 可以写明数学范围或局部遍历关系 |
| `partition` | 维度具名映射 | 必填 | 只登记真正产生独立 worktile 的维度；`{}` 表示整个任务只有一份 worktile |
| `partition.<dimension>.size` | 正整数或数值表达式 | 必填 | 该维度的完整逻辑大小 |
| `partition.<dimension>.tile` | 正整数或数值表达式 | 必填 | 一份 worktile 在该维度覆盖的大小 |
| `partition.<dimension>.range` | 两元素范围列表 | `size` 的取值域未由上游唯一给定时填写 | 约束 `size`，不是本次访问的索引区间 |
| `worktile.invariant` | 数据块具名映射 | 存在局部迭代中保持不变的输入块时填写 | 不表示编译期常量，也不表示跨 worktile 保持不变 |
| `worktile.iteration` | 数据块具名映射 | 存在随局部迭代更换的输入块时填写 | 局部遍历不因此产生独立 worktile |
| `target.single_tile` | 非空数据块具名映射 | 必填 | 一份 worktile 实际产生的结果，可以是部分结果 |
| `target.tile_reduction` | `dimension / input / output / method` 映射 | 本 phase 实际执行跨工作结果的数学合并时填写 | 被合并的维度、合并的输入与输出，以及对上游已确定的合并方法的引用；不在这里重写公式 |

`tile_reduction.input` 与 `output` 各接受单个上游引用或非空引用列表；`dimension` 是一个维度名，`method` 是一个上游合并定义的引用。

本区有两个分块参数：`tile` 决定一份工作有多大，`iteration` 块的 shape 决定局部循环每次推进多少。放大 `tile`，一份工作内的复用随之增加，要同时持有的数据量也增加，而 worktile 总数减少。`invariant` 与 `iteration` 的划分记录的就是这份复用——前者读进来反复使用，后者沿局部索引流过一遍；它和各块的字节量一起决定这份工作的访存量与片上容量需求。

`size` 允许是运行时才确定的表达式。工作数量取决于输入分布时（按专家分组、变长序列），要么取一个能静态算出的上界，并在 `strategy` 中说明多余的工作怎样被判定为空，要么把这部分交给 `refill` 在运行时领取。

### 分解的设计判断

数学上独立的轴可以直接切成独立 worktile。带归约或递推的轴有三条出路：留在一份工作内部顺序推进、写进 `iteration`；切开后产生部分结果，再写清由谁合并（split-K）；或者回到 `math_reshape`，用改写缩短依赖链，例如把 token 递推折成 chunk 递推。选哪条，看切开能换来多少并行度，合并要付出多少流量和额外计算，以及切短之后每份工作的内部迭代是否还够长。

反过来，完整遍历一个维度不等于沿该维度产生独立工作：把本该留在 `iteration` 的维度写进 `partition`，会凭空改变并行度、状态归属和合并需求。

例如，上游已定义 `Nc` 个 chunk。各 chunk 独立计算时，可以按 chunk 分配：

```yaml
partition:
  chunk: {size: Nc, tile: 1}
```

若下一段必须按 chunk 递推，但 value 列之间独立，就改为按列分配、在 worker 内依次读取每个 chunk 的 `U`。以下只展开相关维度：

```yaml
partition:
  dv: {size: DV, tile: 32}
worktile:
  iteration:
    U: {shape: [chunk: 1, token: C, dv: 32], dtype: bf16, direction: ascending}
```

这里 `U` 的类型、`C` 和递推次序均已由上游确定。chunk 从独立工作变成局部循环，不是少写了一个 partition 维度。

### 数据块描述

`invariant`、`iteration` 与 `single_tile` 的条目都用 `shape / dtype` 描述一份 worktile 范围内的那个值，不是单个成员的局部 shape；成员分工由 `mapping.member` 单独表达。`invariant` 可以加 `offset` 区分同一 worktile 内的数学子区域，`iteration` 必须加 `direction`——方向有时由数学递推强制，有时是为了让掩码块或边界块先做完而选，两种情况都要写出来。

| 字段 | 值的形式 | 含义 |
| --- | --- | --- |
| `shape` | 有序的具名维度列表，例如 `[query: 256, head_dim: 128]` | 逻辑维度顺序；partition 已经固定的单个 batch、head 坐标不必作为长度为 1 的维度重复登记 |
| `dtype` | 引用上游已确定的类型 | 精度本身由 `math_reshape` 决定，这里用它和 `shape` 一起算清一份工作的字节量 |
| `offset` | 与 `shape` 顺序对应的数学偏移列表 | 相对当前 worktile，不是字节地址、共享内存偏移或线程地址 |
| `direction` | `ascending / descending` | 该块沿自己的局部迭代索引的访问方向 |

具名轴与整数表达式遵循[公共写法](0.common.md#shape-与整数表达式)，运行时规模的默认有效域见[算法要求](1.contract.algorithm_requirement.md#shape-与规模)。数值表达式引用已定义的符号、本区派生量和数学函数；这里写数学关系，不写设备实现代码。

一个 partition 维度通常产生 `ceil_div(size, tile)` 个工作坐标；最后一份工作的有效数学区域不超出 `size`，线程级 mask 与地址计算不在本区展开。`range` 只约束 `size` 的允许取值域，写成包含端点的下界与上界，上界无固定值时写 `null`；正整数是默认取值，上游已经给出同一约束时不重复填写。

`iteration` 的每个条目描述一个输入块怎样随自己的数学迭代索引更换。迭代范围由上游值的索引域和本份工作的范围确定，可以随工作坐标变化，例如因果可见范围随 query 块移动。两个输入块沿同一个已定义索引变化时使用该索引的同一版本；属于不同局部循环时，不因为同时出现在 `iteration` 中就被解释为同步推进、笛卡尔积或固定先后。局部循环之间必要的先后用 `strategy` 或 `describe` 简明交代，其动作关系由 `tile_pipeline` 展开，不靠映射顺序表达。

### 跨工作结果的合并

生产部分结果的 phase 只登记自己产生的那份结果；`tile_reduction` 写在真正执行合并的 phase 里。独立的合并 phase 有自己的 worktile、mapping 和 schedule，`single_tile` 就是合并后的那份结果；各 worktile 把部分结果直接累加进同一个结果时，执行合并的就是生产它们的 phase，`input` 即本 phase 的 `single_tile`。

`dimension` 是部分结果所沿的那个维度——原地累加时它就在本 phase 的 `partition` 里，独立合并时它只出现在生产 phase 的 `partition` 里；`method` 指向 `math_reshape` 中定义该合并的那一步，不在这里生成另一份隐式工作。累加的机制（如原子加）、部分结果经由哪块存储汇合，以及结果初值由谁、在何时建立，结构字段说不清时写进 `decomposition.strategy`——`handoff` 只登记跨 phase 的交接。只声明部分结果会合并、却没有执行者和依赖，不构成完整的合并设计。

### 执行映射

下表中的路径相对于 `phase.<phase_id>.mapping`。

| 字段路径 | 值的形式 | 填写条件 | 含义与约束 |
| --- | --- | --- | --- |
| `strategy` | 非空英文字符串 | 其他映射字段读不出一个必要决定时填写 | 不用“CTA mapping”这类同义文字重复结构 |
| `worker.unit` | 执行单元名称 | 必填 | 取自 `contract.hardware_specification.execution` 登记的单元，例如 `CTA`；跨类协作的组合由该区登记成一个单元名，本区不自行定义单元 |
| `worker.count` | 正整数或数值表达式 | 必填 | 一个 worker 由多少个该单元组成 |
| `placement` | `unit / count` 映射 | 一个 worker 必须落在特定的物理范围时填写 | 例如占满两个 SM，或落在同一个 cluster 内；不登记无关的物理绑定 |
| `count` | 正整数或数值表达式 | 必填 | 本 phase 提交多少个 worker。同时能驻留多少由 `tile_pipeline` 的资源用量决定，不在这里声明 |
| `member` | 成员列表 | 多成员 worker 的数学分工不能由其他事实唯一确定时填写 | 列表位置对应成员序号；每个成员按维度登记左闭右开的局部区域 |

`worker.count` 是一个 worker 的组成规模，`count` 是实际提交多少个 worker，两者必须分别解释。让多个单元组成一个 worker，总是为了换取某种硬件回报——共享一份搬进来的操作数、共用一条搬运路径，或使用要求成对执行的指令；`member` 写明它们之间怎样分摊这份工作。

本区使用以下派生量，不在案例中重复定义，也不另设工作数量或 worker 数量字段。

| 名称 | 来源 |
| --- | --- |
| `worktile_count` | 当前 phase 的 partition 各维工作数之积；空 partition 取 1 |
| `worker_count` | 当前 phase 的 `mapping.count` |
| `worker_id` | 当前 phase 内从 0 开始的 worker 编号 |

`count` 的两种常见取法代价不同：取 `worktile_count` 时每个 worker 只做一份工作，分配最简单，但每份工作都要重新付一次启动和填流水的开销；取设备能同时驻留的规模时，worker 连续消费多份工作，可以跨工作保留状态和缓冲，代价是要自己安排工作序列和收尾。

`member` 的区域和正文中写出的数学切片使用左闭右开区间，例如 `[0, 128]` 表示局部坐标 `[0, 128)`。

例如，设备已登记 `CTA` 与 `cluster`，一份工作覆盖 256 行、由两个 CTA 平分时，mapping 可以写成：

```yaml
worker: {unit: CTA, count: 2}
placement: {unit: cluster, count: 1}
count: 16
member:
  - {row: [0, 128]}
  - {row: [128, 256]}
```

这是提交 16 个 worker、共 32 个 CTA；每个 worker 的两个 CTA 同处一个 cluster。`member` 使用一份工作的局部行坐标，提交数也不表示 16 个 worker 能同时驻留。

### 工作排列与分配

下表中的路径相对于 `phase.<phase_id>.schedule`。

| 字段路径 | 值的形式 | 填写条件 | 含义与约束 |
| --- | --- | --- | --- |
| `strategy` | 非空英文字符串 | 结构字段尚未表达一个必要的分配决定时填写 | 例如排列键来自运行时排序或分桶时，这个键怎样得到 |
| `worktile_order` | 条目列表 | `partition` 非空时必填 | 从外层到内层排列独立工作，决定逻辑 worktile 编号 |
| `worktile_order[].by` | partition 维度名，或有序维度名列表 | 必填 | 列表表示这些维度先按所写顺序展平成一个排列键 |
| `worktile_order[].group` | 正整数或数值表达式 | 按固定大小的组重排该键时填写 | 每组包含该键的多少个坐标；末组只包含实际存在的坐标 |
| `worktile_order[].direction` | `ascending / descending` | 必填 | 该键的逻辑排列方向 |
| `worker_assignment.preassigned` | `start / step` 或 `start / count` 映射 | 存在预先获配的工作时填写 | 当前 worker 预先得到的整个工作序列；两种写法互斥 |
| `worker_assignment.refill` | `none`，或机制名到规则的映射 | 必填 | 运行时额外取得工作的来源与规则 |
| `worker_assignment.exit` | 条件引用或非空条件引用列表 | 必填 | 这个 worker 结束的条件，例如 `assigned_done` |

`worktile_order`、`preassigned` 与 `refill` 可以独立变化：同一个排列既可以配静态步长分配，也可以配动态领取。`persistent`、`CLC`、`stream-K` 这些名称写进 `strategy` 帮助理解，有约束力的是各字段写下的具体规则。

编号决定哪些工作会同时在设备上跑，也就决定了它们之间能共享多少已经读进 cache 的数据，以及工作量不均时重的工作排在前面还是后面。每个 partition 维度至少在 `worktile_order` 中出现一次；使用 `group` 时，同一个键可以再次出现：带 `group` 的条目排列组，组内次序由后面再次出现的同一个键给出。GEMM 的分组光栅化就写成这种组合：

```yaml
worktile_order:
  - {by: m, group: 8, direction: ascending}
  - {by: n, direction: ascending}
  - {by: m, direction: ascending}
```

最外层按每 8 个 m 坐标一组排列，组内先 n 后 m：连续的八份工作共用同一列 n 的数据，再换下一列，而不是沿整行 m 扫过去。按 KV 工作集分组编号是同一种写法。

`refill` 写 `none` 表示没有运行时额外领取，此时必须用 `preassigned` 给出预分配序列；不由 `mapping` 或 `refill: none` 隐含生成工作归属。写成映射时，键是领取机制的名称，值是这条规则本身——要让读者看出工作从哪里来、一次取多少、计数由谁维护、取不到时怎样结束。

例如，没有预分配工作、所有工作都经同一个全局计数器领取时：

```yaml
refill:
  atomic_counter: |
    Initialize the global counter to 0 before this launch.
    Each worker atomically fetches and increments it by 1.
    Use the returned value as a worktile id if it is below worktile_count; otherwise stop fetching.
```

取消同一 grid 中未启动的 worker 并接管其工作、从共享队列窃取、按桶领取，写法相同。

各份工作的工作量相差较大时（因果掩码、变长序列、按专家分组），排列只能把重的工作提前、缓解尾部，运行时领取才能把空下来的 worker 填上，代价是领取本身的开销，以及要在 `exit` 中为领取失败配一个相应的终止条件。

`worktile_order` 的列表顺序从外层到内层读取；它不是 kernel 提交顺序、跨 worker 完成顺序，也不是内部 reduction 循环。

### 分配序列与退出

按 `worktile_order` 把工作坐标展平为逻辑 worktile 编号。`preassigned: {start: s, step: d}` 表示编号 `s, s+d, s+2d, ...`，直到超出本 phase 的合法工作范围，`d` 为正整数；`preassigned: {start: s, count: n}` 表示连续的 `n` 份工作，`n` 为非负整数且指定编号必须合法。

消费自己预先获得的下一份工作不叫 refill，`refill: none` 不妨碍一个 worker 连续处理多份预分配工作。`assigned_done` 表示该 worker 相关的已分配工作都已完成，不是“已经领取完”；若同一 worker 还要承担同一次提交中的后续 phase，它不能因为当前 phase 的工作耗尽就退出，所有剩余职责与在途操作结束后才允许结束。

## phase 的提交与接续

### 最小 flow

`work_schedule` 的外层组织如下；`phase` 中的每个条目采用上节定义的结构。

```text
work_schedule
  thesis
  phase: <phase_id>
  flow
    launch[]: phase[] / order? / start_after? / protocol?
    handoff?: <value>: producer / consumer[] / storage / initialize? / ready? / wait_at?
```

单 phase 的最小 `flow` 只有一个 `launch` 条目和它的 `phase` 列表：

```yaml
flow:
  launch: [{phase: [attention]}]
```

这已经表达一次计算 kernel 提交，不需要再套一层执行区域。

### 提交身份与字段

每个 phase ID 在 `flow.launch[].phase` 中恰好出现一次，且引用必须在 `phase` 表中解析。因此 phase ID 同时是一次工作提交及其 worker 实例的身份，供下游引用执行作用域；同一类工作需要提交多次时分别登记 phase，可用 YAML anchor 共用字段内容。

一次 phase 提交包含它的完整工作集合：worker 多消费一份 worktile、多走一轮局部循环，都不增加提交次数。下表路径相对于 `work_schedule`：

| 字段路径 | 值的形式 | 填写条件 | 含义与约束 |
| --- | --- | --- | --- |
| `flow.launch[].phase` | 非空 phase ID 列表 | 必填 | 本次提交包含的 phase，只引用不定义 |
| `flow.launch[].order` | 见下表 | 条目包含多个 phase 时必填 | 这些 phase 之间的接续粒度 |
| `flow.launch[].start_after` | 事件引用或非空引用列表 | 整个提交要等某个事件才能开始时填写 | 省略表示不声明额外的启动等待 |
| `flow.launch[].protocol` | 启动协议名，例如 `pdl` | 采用把启动许可与数据可用性分开的协议时填写 | 普通的完成依赖不填 |

`flow.launch` 列表只枚举提交条目，相邻条目之间既没有完成屏障，也没有并发保证；要求前一次完成后才启动时必须写 `start_after`。其事件含义见[事件与启动](#事件与启动)。

### 接续粒度

`order` 的取值：

| 值 | 语义 | 附带要求 |
| --- | --- | --- |
| `per_worktile` | 同一 worker 对当前这份配对工作按列表顺序走完全部 phase，再推进下一份 | 参与 phase 的工作坐标集合与工作归属必须一致 |
| `per_worker` | 每个 worker 完成自己分到的全部前一 phase 工作，再进入下一个 phase | worker 之间不因此互相等待 |
| `all` | 前一个 phase 的全部工作完成后，下一个 phase 才开始 | 同一次提交内采用这种组织，必须有可实现的全体同步 |
| `concurrent` | 这些 phase 由同一次提交中互不相同的 worker 同时承担 | 各 phase 分别给出自己的 `mapping`，相互之间的数据关系写进 `handoff` |

前三个值表示同一批 worker 依次承担这些 phase，因此它们的 `worker`、`count` 及必要的 `placement` 必须一致，`mapping.count` 不相加。

接续粒度决定中间结果要存活多久：`per_worktile` 最省，一份中间结果用完就被下一份覆盖，可以一直留在局部资源里，代价是两段计算在 worker 内串了起来；`per_worker` 放宽到一个 worker 的全部工作；`all` 和拆成两次提交则让中间结果整体留下，通常要落回全局内存。`all` 允许两段采用不同分解，但仍须满足上述共享 worker 的映射约束；拆成两次提交后，才可以分别选择 worker 组成、数量与 placement。这些差别不能藏在 `persistent`、`same worker` 这类名称里。

`order: per_worktile` 要求的是 `A(t0), B(t0), A(t1), B(t1)`，不是 `A(t0), A(t1), B(t0), B(t1)`。使用时，各 phase 的工作坐标集合、逻辑排列和预分配序列必须一致，产物与内部迭代可以不同；生产块与消费块大小不同造成的区域覆盖，不构成这种一一配对。

### 事件与启动

事件引用写成 `<phase_id>.<milestone>`。

| 里程碑 | 含义 |
| --- | --- |
| `kernel_done` | 该 phase 所属计算 kernel 完成，且交出的结果满足后继执行所需的可见性 |
| `launch_ready` | 启动协议定义的后继启动许可事件，针对整个前驱 grid，不是某份 worktile 的数据就绪 |
| 其他名称 | `tile_pipeline` 在该 phase 的 `milestone` 中定义的里程碑，例如某个值第一次被读取的位置；必须能确定作用域、工作索引和相关数据的使用位置 |

同一次提交内的各 phase 共享一个 `kernel_done`：引用其中任何一个 phase 的 `kernel_done`，指的都是这次提交的完成，不是该 phase 的局部完成点。`start_after` 约束设备执行何时可以开始，不要求 host 线程阻塞；一次提交不能等待自己的 `kernel_done`，跨提交的启动依赖也不能形成没有初始事件的循环。

启动许可、数据就绪和真正消费数据是三个可以不同的时点，`start_after` 与 `ready / wait_at` 分别记录它们。存在提前启动的机会不等于已经测得 overlap；跨 worker 消费部分结果，除了数学区域接通，还需要可见性和进展依据。

## 跨 phase 数据交接

### 交接字段

| 字段路径 | 值的形式 | 填写条件 | 含义与约束 |
| --- | --- | --- | --- |
| `flow.handoff` | 非空具名映射 | 存在跨 phase 数据交接时填写 | 键引用上游已定义的数学值，不建立另一个同名对象 |
| `.producer` | phase ID | 必填 | 生产该值的 phase，可以由其中多份 worktile 共同产生 |
| `.consumer` | 非空、无重复的 phase ID 列表 | 必填 | 消费该值的 phase |
| `.storage` | `global`，或 `tile_pipeline.phase.<phase_id>.resource.<resource_id>` 引用 | 必填 | 全局物化，或交接发生在某个已定义的局部资源中 |
| `.initialize` | 数值标量或上游标量引用 | 消费者会读到生产者没有写过的区域时填写 | 省略不表示默认清零，也不能只因为源码调用了分配即清零的 API 就填 |
| `.ready` | 生产者里程碑引用或非空引用列表 | 可消费时点不是生产 worktile 完成时填写 | 覆盖默认的生产就绪时点 |
| `.wait_at` | 消费者里程碑引用或非空引用列表 | 消费者可以先做独立工作、稍后才等待该值时填写 | 覆盖默认的消费入口等待；每条引用自带所属 phase |

省略 `ready` 表示相应生产 worktile 完成、且交出的区域已满足消费者所需的可见性；省略 `wait_at` 表示消费 worktile 开始前该区域必须就绪。这两条是设计约束，不会自动生成发布标志、跨 CTA barrier 或轮询协议，相应机制由 [tile_pipeline](5.design.tile_pipeline.md#跨-phase-交接) 给出。

显式 `wait_at` 通过消费者里程碑定位数据必须就绪的事件：可以是等待动作的 `done`，或真正读取动作的 `issue`。等待本身可以提前开始，其 `issue` 不表示数据已就绪。

`storage` 写 `global` 只规定全局物化，不规定分配 API、物理地址或分配器所有权；写资源引用时，存储空间、所属 worker、容量和槽数由该资源的定义提供，本区不复制。

`consumer`、`start_after` 和 `exit` 的列表都表示共同满足，不表示优先级或任选其一。里程碑名使用通用标识符；里程碑和自定义条件推荐使用简短的小写名称。

### 数学值与区域匹配

`handoff` 的键所引用的那个数学值，生产区域由 `producer` 的 `target` 给出，消费区域由 `consumer` 的 `worktile` 给出。局部名称不同而实际是同一个值时，引用上游已有的数学视图，不能仅凭 shape 相同就认定为同一个对象。

跨 phase 的数据匹配先解析同一个数学值、同一版本和明确的索引关系，再检查生产区域是否覆盖消费区域。索引关系来自上游的数学定义，需要转置、排列、切片或版本视图时引用 `math_reshape` 中已有的视图，不按 shape 猜测。消费区域由多份生产 worktile 覆盖时，要等待全部相关生产结果。

例如，同一值的生产块沿 `dv` 每 32 列一份，消费块每 64 列一份。消费块 `r` 需要 `[64r, 64r+64)`，因此等待生产块 `2r` 和 `2r+1` 的对应区域。这里是同一值的区域覆盖，没有新的数学合并，不因此填写 `tile_reduction`。

### 存续与初始化

一个数据版本的存储至少保留到它的生产访问、全部声明的消费访问及相关在途操作结束；“发出了异步读取”不等于“已经消费完”。这既不要求分配器立即释放，也不要求一律保留到任务结束。

`initialize` 作用于所引用数学值的新存储版本，在相应生产开始前完成，只描述确实需要建立的初值——典型情形是生产者不覆盖、而消费者会读取的区域需要预先为零。它不规定分配 API，也不自动登记额外的 phase 或 launch。

例如，上游把 `T` 定义为下三角矩阵，`solve` 只写下三角，而 `apply` 会读取整个矩阵时，需要保留上三角的零值：

```yaml
handoff:
  T: {producer: solve, consumer: [apply], storage: global, initialize: 0}
```

若生产者本来就完整写出所有被读取的区域，即使实现用了清零分配 API，也不据此添加 `initialize`。

跨 kernel 不保留 worker 局部资源身份：不同 kernel 即使采用相同的 mapping，也建立新的 worker。同一 kernel 内跨 phase 存续的局部资源，必须与 `order`、工作归属和资源定义一致；逐 worktile 接续已经保证前一份数据消费完才覆盖同一个槽时，不再登记一条同义的复用等待。

### 与局部流水线的接口

lane 划分、动作表和缓冲协议由 `tile_pipeline` 决定；交接所在的[局部资源](5.design.tile_pipeline.md#资源)和[具名里程碑](5.design.tile_pipeline.md#跨-phase-交接)也由它在相应的 phase 中定义，本区只引用，不在这里另建一套局部流水线。

## 省略与扩展边界

省略一个可选字段必须具有本节说明的含义，不表示信息尚未填写；`strategy` 的省略表示结构字段与上游引用已经够用，不表示采用了某个隐藏的默认策略。除 `partition: {}` 表示单份整体工作、标量 `shape: []`、以及 `range` 的无界端点外，不用空映射、空列表或 `null` 代替内容；没有可选条目时省略整个字段。

`strategy`、`describe`、`thesis` 是说明字符串，承载结构字段表达不了的那条规则或那句理由，可以包含简短的数学范围；它们不用来把已有字段的内容再复述一遍。

| 位置类型 | 本区位置 | 允许的变化 |
| --- | --- | --- |
| 固定结构 | `work_schedule`、`flow`、launch 条目、handoff 条目、phase 条目，以及 `decomposition / mapping / schedule` 及其子对象 | 只使用本节声明的字段 |
| 具名映射 | `phase`、`handoff`、`partition`、各数据块映射，以及其中的轴名与成员区域维度名 | 可以增加当前设计需要的名称，条目结构不变 |
| 开放取值 | `refill` 的机制、`protocol` 的协议名、`exit` 的条件，以及 `strategy` 与 `describe` 的内容 | 写成能看出规则的具体内容，不只写一个名称 |

增加 phase ID、张量名或维度名是填写实例；新增字段，或新增 `order`、`direction` 的取值遵循[公共扩展规则](0.common.md#结构与扩展)。

全局物化、同一 worker 的延续、完成边界、接续粒度和必要的存储初值都可能改变性能因果，写进正式字段。具体的内存分配调用、普通地址计算、线程布局，以及不影响设计成立的 API 偏好不属于本区；但也不能把确实必要的存储初值随分配细节一起删掉。
