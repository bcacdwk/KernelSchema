# 工作调度

## 核心思想

派生节点可以依[Design 整区引用](0.common.md#design-整区引用)将整个 `work_schedule` 写为 `{from_parent: <直接父ID>}`；root 始终本地定义。下文描述本地或展开后的完整区域。共享的工作参数、launch、step/worker 和 handoff 在使用节点的数学与流水线环境中绑定；不能仅继承 step、覆盖一个参数，或用引用掩盖实际提交集合的差异。

`design.work_schedule` 把上游确定的计算切成可以独立分配的工作，交给具体的执行单元，并安排这些工作怎样排列、分配和接续。它站在算法与硬件之间：向上，把 `math_reshape` 定下的值和索引划成一份份工作，决定哪些数据在一份工作内复用、哪些随局部迭代流过；向下，把这些工作放到设备实际提供的执行单元上，使它们能连续、均衡地推进。

本区不重新定义数学算法，也不展开 warp 分工、逐线程地址、指令、barrier 编号或寄存器布局。它接收 `math_reshape` 给出的值、索引、数学关系、精度和状态初值，并固定其中留给下游绑定的工作参数（分块长度、行集合、遍历映射）；执行单元的名称取自 `contract.hardware_specification`，设备规模这类数值来自它绑定的资料；向 `tile_pipeline` 提供工作边界、worker 身份、执行作用域及必要的交接要求。

### 基本对象

| 对象         | 含义                                                             | 需要避免的混淆                                        |
| ------------ | ---------------------------------------------------------------- | ----------------------------------------------------- |
| `worktile` | 一份可以独立分配的计算工作，可以产生最终结果，也可以产生部分结果 | 不等于输入张量的一块存储，也不等于一次局部循环迭代    |
| `worker`   | 承担工作的协作执行单元，可以由一个或多个执行单元组成             | 不等于一个线程；一个 worker 可以连续处理多个 worktile |
| `step`    | 一类具有明确分解、映射和分配规则的工作定义                       | 不等于数学步骤、kernel launch 或缓冲槽                |

本区的核心区分是：

> **worktile 的排列不等于 worker 的工作归属；预先获配的工作不等于运行时新领取的工作。**

本区使用 `thesis / flow / step`：

- `thesis` 概括整体工作组织中最重要的设计选择。
- `step` 是工作定义的唯一登记处，采用具名映射。
- `flow` 引用这些定义，记录计算 kernel 的边界、同一次提交内的接续方式和跨 step 数据交接。

`flow.launch` 的一个条目对应一次计算 kernel 提交，可以包含一个 step，也可以包含由同一批 worker 接续执行、或由不同 worker 并发承担的多个 step，因此 step 数量与 kernel 数量没有对应关系。

### step 粒度

按工作组织划分 step 时，先判断一份分解、映射和分配规则能否完整表达，不能时再拆分。例如 chunk 先是独立工作维度，进入状态递推后变成 worker 内的顺序迭代，再恢复为独立工作维度。同类工作需要重复提交时，按[提交身份规则](#提交身份与字段)处理。

step 标签本身不产生 launch、全体屏障、全局物化或资源重置，真正发生的这些行为则必须写进相应字段。step 的多少也不是优化目标：一个 step 可以包含多种计算，多个 step 也可以处于同一个 kernel。

### 设计着眼点

上游已经定下算什么，本区决定这些计算怎样摊到设备上。工作耗时近似相同时，可用每份工作的耗时、工作总数与实际并发 worker 数粗估 step 时长，再核对尾部、不均衡和共享资源限制。先比较工作大小对复用、片上容量和工作数量的影响，再安排由谁承担、怎样排列和领取。并发规模需结合硬件与下游资源预算估算，不能直接用提交的 worker 数代替。

| 问题                     | 要看什么                                               | 答案落在                                            |
| ------------------------ | ------------------------------------------------------ | --------------------------------------------------- |
| 并行度够不够             | worktile 总数能否填满设备，最后一波有多空              | `partition` 的 `tile`、`mapping.worker_count` |
| 一份工作内复用了什么     | 哪些数据读进来反复使用，哪些只流过一遍                 | `worktile.invariant`、`worktile.iteration`      |
| 一份工作要占多少片上资源 | 同时持有的输入块与结果块有多少字节                     | 数据块的 `shape / dtype`                          |
| 一份工作要几个单元一起做 | 合起来能共享什么，分开做会重复搬运什么                 | `mapping.worker`、`placement`、`member`       |
| 工作量均不均衡           | 各份工作的内部迭代长度是否相近，差距大时靠什么补       | `worktile_order`、`worker_assignment`           |
| 中间结果走哪条路         | 写回全局内存再读出，还是留在同一个 worker 的局部资源里 | `flow.launch[].order`、`handoff.storage`        |

## 字段定义

### 结构轮廓

下面是字段结构。`[]` 表示列表，`<name>` 表示实例名称，`?` 表示条件可省略。

```text
work_schedule
├─ thesis
├─ step
│  └─ <step_id>
│     ├─ describe
│     ├─ decomposition
│     │  ├─ strategy?
│     │  ├─ partition: <dimension>: meaning / size / tile / range?
│     │  ├─ worktile?: invariant? / iteration?
│     │  │  └─ <value>: meaning / shape / dtype / offset? / direction?
│     │  └─ target
│     │     ├─ single_tile: <value>: meaning / shape / dtype
│     │     └─ tile_reduction?: dimension / input / output / method
│     ├─ mapping: strategy? / worker / placement? / worker_count / member?
│     └─ schedule
│        ├─ strategy?
│        ├─ worktile_order[]: by / group? / direction
│        └─ worker_assignment: preassigned? / refill / exit
└─ flow
   ├─ launch[]: step[] / order? / start_after?
   └─ handoff?: <value>: producer / consumer[] / storage / initialize? / ready? / wait_at?
```

一个 step 必填 `describe / decomposition / mapping / schedule`，分别说明计算什么、一份工作是什么、由谁执行、怎样排列与分配。它在 `work_schedule.step` 中以 step ID 登记；单 step 的最小提交外壳见[step 的提交与接续](#step-的提交与接续)。

### 主体字段

以下两项路径相对于 `work_schedule`：

| 字段路径                      | 值的形式       | 填写条件 | 含义与约束                                                   |
| ----------------------------- | -------------- | -------- | ------------------------------------------------------------ |
| `thesis`                    | 非空英文字符串 | 必填     | 说明整体工作组织的关键选择、依据及收益与代价 |
| `step.<step_id>.describe` | 非空英文字符串 | 必填     | 说明这类工作计算什么                                         |

### 工作分解

下表中的路径相对于 `step.<step_id>.decomposition`。

| 字段路径                        | 值的形式                                     | 填写条件                                    | 含义与约束                                                                         |
| ------------------------------- | -------------------------------------------- | ------------------------------------------- | ---------------------------------------------------------------------------------- |
| `strategy`                    | 非空英文字符串                               | 结构字段说不清一个必要的分解决定时填写      | 补充分块参数、数学范围、局部遍历或结果合并的必要关系                                                     |
| `partition`                   | 维度具名映射                                 | 必填                                        | 只登记真正产生独立 worktile 的维度；`{}` 表示整个任务只有一份 worktile           |
| `partition.<dimension>.meaning` | 非空英文字符串                              | 必填                                        | 用一句话说明该维度的工作坐标选择哪部分计算                                         |
| `partition.<dimension>.size`  | 非负整数或数值表达式                         | 必填                                        | 该维度的完整逻辑大小，可以为 0                                                     |
| `partition.<dimension>.tile`  | 正整数或数值表达式                           | 必填                                        | 一份 worktile 在该维度覆盖的大小                                                   |
| `partition.<dimension>.range` | 两元素范围列表                               | `size` 的取值域未由上游唯一给定时填写     | 约束 `size`，不是本次访问的索引区间                                              |
| `worktile.invariant`          | 数据块具名映射                               | 存在局部迭代中保持不变的输入块时填写        | 不表示编译期常量，也不表示跨 worktile 保持不变                                     |
| `worktile.iteration`          | 数据块具名映射                               | 存在随局部迭代更换的输入块时填写            | 局部遍历不因此产生独立 worktile                                                    |
| `target.single_tile`          | 非空数据块具名映射                           | 必填                                        | 一份 worktile 实际产生的结果，可以是部分结果                                       |
| `target.tile_reduction`       | `dimension / input / output / method` 映射 | 本 step 实际执行跨工作结果的数学合并时填写 | 被合并的维度、合并的输入与输出，以及对上游已确定的合并方法的引用；不在这里重写公式 |

`tile_reduction.input` 与 `output` 各接受单个上游引用或非空引用列表；`dimension` 是一个维度名，`method` 是一个上游合并定义的引用。

本区有两个分块参数：`tile` 决定一份工作有多大，`iteration` 块的 shape 决定局部循环每次推进多少。放大 `tile` 通常减少工作数量，也可能增加复用和同时持有的数据量，是否有益要结合实际访问关系判断。`invariant` 与 `iteration` 分别登记局部迭代中保持不变和随索引更换的输入块，用各块的字节量、复用关系和同时存活状态估算访存量与片上容量。

`size` 允许是运行时才确定的表达式。提交前已经确定实际工作集合时，可以据此预分配；尚不能确定时（如动态分组），可以使用可确定的上界并在 `strategy` 中说明空工作，也可以用 `refill` 在运行时领取。是否需要动态领取，取决于工作集合何时可知，不由“运行时规模”这个名称决定。

#### 分解的设计判断

数学上独立的轴可以直接切成独立 worktile。带归约或递推的轴有三条出路：留在一份工作内部顺序推进、写进 `iteration`；切开后产生部分结果，再写清由谁合并（split-K）；或者回到 `math_reshape`，用改写缩短依赖链，例如把 token 递推折成 chunk 递推。选哪条，看切开能换来多少并行度，合并要付出多少流量和额外计算，以及切短之后每份工作的内部迭代是否还够长。

反过来，完整遍历一个维度不等于沿该维度产生独立工作：把本该留在 `iteration` 的维度写进 `partition`，会凭空改变并行度、状态归属和合并需求。

例如，上游已定义 `Nc` 个 chunk。各 chunk 独立计算时，可以按 chunk 分配：

```yaml
partition:
  chunk: {meaning: Independent chunk, size: Nc, tile: 1}
```

若下一段必须按 chunk 递推，但 value 列之间独立，就改为按列分配、在 worker 内依次读取每个 chunk 的 `U`。以下只展开相关维度：

```yaml
partition:
  dv: {meaning: Block of value columns, size: DV, tile: 32}
worktile:
  iteration:
    U: {meaning: Chunk of U for this worktile's value columns, shape: [chunk: 1, token: C, dv: 32], dtype: bf16, direction: ascending}
```

这里 `U` 的类型、`C` 和递推次序均已由上游确定。chunk 从独立工作变成局部循环，不是少写了一个 partition 维度。

#### 跨工作结果的合并

生产部分结果的 step 只登记自己产生的那份结果；`tile_reduction` 写在真正执行合并的 step 里。独立的合并 step 有自己的 worktile、mapping 和 schedule，`single_tile` 就是合并后的那份结果；各 worktile 把部分结果直接累加进同一个结果时，执行合并的就是生产它们的 step，`input` 即本 step 的 `single_tile`。

`dimension` 是部分结果所沿的那个维度——原地累加时它就在本 step 的 `partition` 里，独立合并时它只出现在生产 step 的 `partition` 里；`method` 指向 `math_reshape` 中定义该合并的那一步，不在这里生成另一份隐式工作。累加的机制（如原子加）、部分结果经由哪块存储汇合，以及结果初值由谁、在何时建立，结构字段说不清时写进 `decomposition.strategy`——`handoff` 只登记跨 step 的交接。只声明部分结果会合并、却没有执行者和依赖，不构成完整的合并设计。

### 执行映射

下表中的路径相对于 `step.<step_id>.mapping`。

| 字段路径              | 值的形式                   | 填写条件                                             | 含义与约束                                                                                                                            |
| --------------------- | -------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `strategy`          | 非空英文字符串             | 其他映射字段读不出一个必要决定时填写                 | 补充工作到执行单元的对应关系、协作条件或有依据的取舍                                                                                               |
| `worker.unit`       | 执行单元名称               | 必填                                                 | 取自 `contract.hardware_specification.execution` 登记的单元，例如 `CTA`；跨类协作的组合由该区登记成一个单元名，本区不自行定义单元 |
| `worker.unit_count` | 正整数或数值表达式         | 必填                                                 | 一个 worker 由多少个该单元组成                                                                                                        |
| `placement`         | `unit / unit_count` 映射 | 一个 worker 必须落在特定的物理范围时填写             | 例如占满两个 SM，或落在同一个 cluster 内；不登记无关的物理绑定                                                                        |
| `worker_count`      | 正整数或数值表达式         | 必填                                                 | 本 step 提交多少个 worker。实际驻留数需结合硬件条件与 `tile_pipeline` 的资源用量估算，不在这里另设字段                             |
| `member`            | 成员列表                   | 多成员 worker 的数学分工不能由其他事实唯一确定时填写 | 列表位置对应成员序号；每个成员按维度登记左闭右开的局部区域                                                                            |

`worker.unit_count` 是每个 worker 内的单元数，`worker_count` 是提交的 worker 总数；总单元数为两者的乘积。让多个单元组成一个 worker，总是为了换取某种硬件回报——共享一份搬进来的操作数、共用一条搬运路径，或使用要求成对执行的指令；`member` 写明它们之间怎样分摊这份工作。

本区使用以下派生量，直接引用已有字段或其计算结果，不在案例中重复登记。

| 名称               | 来源                                                      |
| ------------------ | --------------------------------------------------------- |
| `worktile_count` | 当前 step 的 partition 各维工作数之积；空 partition 取 1 |
| `worker_count`   | 当前 step 的 `mapping.worker_count`                    |
| `worker_id`      | 当前 step 内从 0 开始的 worker 编号                      |

两种常见组合的代价不同：`worker_count` 取 `worktile_count` 并一一预分配时，每个 worker 处理一份工作；选择较少的 worker 并分配连续工作序列时，可以跨工作保留状态和缓冲，但须安排接续与收尾。两者都要在[工作分配](#工作排列与分配)中明确归属，数量本身不隐含分配规则。

`member` 的区域和正文中写出的数学切片使用左闭右开区间，例如 `[0, 128]` 表示局部坐标 `[0, 128)`。

例如，设备已登记 `CTA` 与 `cluster`，一份工作覆盖 256 行、由两个 CTA 平分时，mapping 可以写成：

```yaml
worker: {unit: CTA, unit_count: 2}
placement: {unit: cluster, unit_count: 1}
worker_count: 16
member:
  - {row: [0, 128]}
  - {row: [128, 256]}
```

这是提交 16 个 worker、共 32 个 CTA；每个 worker 的两个 CTA 同处一个 cluster。`member` 使用一份工作的局部行坐标，提交数也不表示 16 个 worker 能同时驻留。

### 工作排列与分配

下表中的路径相对于 `step.<step_id>.schedule`。

| 字段路径                          | 值的形式                                   | 填写条件                                 | 含义与约束                                         |
| --------------------------------- | ------------------------------------------ | ---------------------------------------- | -------------------------------------------------- |
| `strategy`                      | 非空英文字符串                             | 结构字段未表达必要的分配规则或调用前提时填写 | 说明运行时排列键、外部供给或共享状态复用的必要条件 |
| `worktile_order`                | 条目列表                                   | `partition` 非空时必填                 | 从外层到内层排列独立工作，决定逻辑 worktile 编号   |
| `worktile_order[].by`           | partition 维度名，或有序维度名列表         | 必填                                     | 列表表示这些维度先按所写顺序展平成一个排列键       |
| `worktile_order[].group`        | 正整数或数值表达式                         | 按固定大小的组重排该键时填写             | 每组包含该键的多少个坐标；末组只包含实际存在的坐标 |
| `worktile_order[].direction`    | `ascending / descending`                 | 必填                                     | 该键的逻辑排列方向                                 |
| `worker_assignment.preassigned` | `start / stride` 或 `start / count` 映射 | 存在预先获配的工作时填写                 | 当前 worker 预先得到的整个工作序列；两种写法互斥   |
| `worker_assignment.refill`      | `none`，或机制名到规则的映射             | 必填                                     | 运行时额外取得工作的来源与规则                     |
| `worker_assignment.exit`        | 条件引用或非空条件引用列表                 | 必填                                     | 这个 worker 结束的条件，例如 `assigned_done`     |

`worktile_order`、`preassigned` 与 `refill` 可以独立变化：同一个排列既可以配静态步长分配，也可以配动态领取。`persistent`、`CLC`、`stream-K` 这些名称写进 `strategy` 帮助理解，有约束力的是各字段写下的具体规则。

工作编号与分配规则共同影响 cache 复用机会和负载分布，不保证相邻编号的工作同时执行。每个 partition 维度至少在 `worktile_order` 中出现一次；使用 `group` 时，同一个键可以再次出现：带 `group` 的条目排列组，组内次序由后面再次出现的同一个键给出。GEMM 的分组光栅化就写成这种组合：

```yaml
worktile_order:
  - {by: m, group: 8, direction: ascending}
  - {by: n, direction: ascending}
  - {by: m, direction: ascending}
```

最外层按每 8 个 m 坐标一组排列，组内先 n 后 m：连续的八份工作共用同一列 n 的数据，再换下一列，而不是沿整行 m 扫过去。按 KV 工作集分组编号是同一种写法。

`refill` 写 `none` 表示没有运行时额外领取，此时必须用 `preassigned` 给出预分配序列；不由 `mapping` 或 `refill: none` 隐含生成工作归属。写成映射时，键是领取机制的名称，值简明说明工作来源、领取粒度、分配状态的维护者及必要初态与更新规则、领取失败条件；已有字段明确的内容直接沿用。

例如，没有预分配工作、所有工作都经同一个全局计数器领取时：

```yaml
refill:
  atomic_counter: Global counter is 0 before launch; workers atomically add 1 and claim the old value as worktile id if below worktile_count, otherwise stop fetching
```

取消同一 grid 中未启动的 worker 并接管其工作、从共享队列窃取、按桶领取，写法相同。

各份工作的工作量相差较大时（因果掩码、变长序列、按专家分组），排列只能把重的工作提前、缓解尾部，运行时领取才能把空下来的 worker 填上，代价是领取本身的开销，以及要在 `exit` 中为领取失败配一个相应的终止条件。

#### 分配序列与退出

按 `worktile_order` 把工作坐标展平为逻辑 worktile 编号。`preassigned: {start: s, stride: d}` 表示编号 `s, s+d, s+2d, ...`，直到超出本 step 的合法工作范围，`d` 为正整数；`preassigned: {start: s, count: n}` 表示连续的 `n` 份工作，`n` 为非负整数且指定编号必须合法。

消费自己预先获得的下一份工作不叫 refill，`refill: none` 不妨碍一个 worker 连续处理多份预分配工作。`assigned_done` 表示该 worker 相关的已分配工作都已完成，不是“已经领取完”；若同一 worker 还要承担同一次提交中的后续 step，它不能因为当前 step 的工作耗尽就退出，所有剩余职责与在途操作结束后才允许结束。

### step 的提交与接续

单 step 的最小 `flow` 只有一个 `launch` 条目和它的 `step` 列表：

```yaml
flow:
  launch: [{step: [MAIN]}]
```

这已经表达一次计算 kernel 提交，不需要再套一层执行区域。

#### 提交身份与字段

每个 step ID 在 `flow.launch[].step` 中恰好出现一次，且引用必须在 `step` 表中解析。因此 step ID 标识该 [plan](0.common.md#单份-plan-与元数据) 一次计算执行中的工作提交及其 worker 实例，供下游引用执行作用域；同一次计算执行内，同一类工作需要提交多次时分别登记 step，可用 YAML anchor 共用字段内容。同一 plan 用于另一次算子请求时产生新的实例。提交及完成事件以实际计算为准，录图只记录执行结构。

选择条件改变实际提交或交接关系时，依[参数变化与结构变化](0.common.md#参数变化与结构变化)判断节点划分，不以正文取消当前节点已登记的提交或事件。

一次 step 提交包含它的完整工作集合：worker 多消费一份 worktile、多走一轮局部循环，都不增加提交次数。下表路径相对于 `work_schedule`：

| 字段路径                      | 值的形式                 | 填写条件                                   | 含义与约束                         |
| ----------------------------- | ------------------------ | ------------------------------------------ | ---------------------------------- |
| `flow.launch[].step`       | 非空 step ID 列表       | 必填                                       | 本次提交包含的 step，只引用不定义 |
| `flow.launch[].order`       | 见下表                   | 条目包含多个 step 时必填                  | 这些 step 之间的接续粒度          |
| `flow.launch[].start_after` | 事件引用或非空引用列表   | 整个提交要等某个事件才能开始时填写         | 省略表示不声明额外的启动等待       |

`flow.launch` 列表只枚举提交条目，相邻条目之间既没有完成屏障，也没有并发保证；要求前一次完成后才启动时必须写 `start_after`。其事件含义见[事件与启动](#事件与启动)。

#### 调用边界

本次计算的入口提交（无内部启动前驱的提交）在调用者此前已排入的设备工作完成后开始；调用者后续使用输出的设备工作等待对应输出的全部生产区域完成且可见。这些约定不在本次计算的独立提交之间添加顺序，也不要求 host 阻塞等待输出。

外部供给与调用前提在相关 step 的 `schedule.strategy` 中简明说明，只约束实际需要它们的提交。例如，`Geo` 完整上传并可见后才启动 `MAIN`。其准备过程的输入就绪、初态及共享存储复用条件按实际设计给定。具体启动、拷贝与同步机制由 [realization](6.realization.md) 绑定。

#### 接续粒度

`order` 的取值：

| 值               | 语义                                                                 | 附带要求                                                                |
| ---------------- | -------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `per_worktile` | 同一 worker 对当前这份配对工作按列表顺序走完全部 step，再推进下一份 | 参与 step 的工作坐标集合与工作归属必须一致                             |
| `per_worker`   | 每个 worker 完成自己分到的全部前一 step 工作，再进入下一个 step    | worker 之间不因此互相等待                                               |
| `all`          | 前一个 step 的全部工作完成后，下一个 step 才开始                   | 同一次提交内采用这种组织，必须有可实现的全体同步                        |
| `concurrent`   | 这些 step 由同一次提交中互不相同的 worker 承担，可独立推进         | 各 step 分别给出 `mapping`，数据关系写进 `handoff`；不保证同时驻留 |

前三个值表示同一批 worker 依次承担这些 step，因此它们的 `worker`、`worker_count` 及必要的 `placement` 必须一致，`mapping.worker_count` 不相加。

接续粒度决定中间结果要存活多久：`per_worktile` 最省，一份中间结果用完就被下一份覆盖，可以一直留在局部资源里，代价是两段计算在 worker 内串了起来；`per_worker` 放宽到一个 worker 的全部工作；`all` 和拆成两次提交则让中间结果整体留下，通常要落回全局内存。`all` 允许两段采用不同分解，但仍须满足上述共享 worker 的映射约束；拆成两次提交后，才可以分别选择 worker 组成、数量与 placement。这些差别不能藏在 `persistent`、`same worker` 这类名称里。

`order: per_worktile` 要求的是 `A(t0), B(t0), A(t1), B(t1)`，不是 `A(t0), A(t1), B(t0), B(t1)`。使用时，各 step 的工作坐标集合、逻辑排列和预分配序列必须一致，产物与内部迭代可以不同；生产块与消费块大小不同造成的区域覆盖，不构成这种一一配对。

### 跨 step 数据交接

#### 交接字段

| 字段路径         | 值的形式                                                                    | 填写条件                                       | 含义与约束                                                      |
| ---------------- | --------------------------------------------------------------------------- | ---------------------------------------------- | --------------------------------------------------------------- |
| `flow.handoff` | 非空具名映射                                                                | 存在跨 step 数据交接时填写                    | 键引用上游已定义的数学值，不建立另一个同名对象                  |
| `.producer`    | step ID                                                                    | 必填                                           | 生产该值的 step，可以由其中多份 worktile 共同产生              |
| `.consumer`    | 非空、无重复的 step ID 列表                                                | 必填                                           | 消费该值的 step                                                |
| `.storage`     | `global`，或 `tile_pipeline.step.<step_id>.storage.<storage_id>` 引用 | 必填                                           | 全局物化，或交接发生在已定义的片上存储区域中                    |
| `.initialize`  | 数值标量或上游标量引用                                                      | 本次需补足生产者未写、入口或已有状态也未保证的消费初值时填写 | 在相应生产开始前建立；省略不表示清零                    |
| `.ready`       | 生产者事件引用或非空引用列表                                                | 默认就绪点及已有依赖不足以表达所需保证时填写 | 所引用的生产事件全部满足后，该值就绪                            |
| `.wait_at`     | 消费者事件别名引用或非空引用列表                                            | 默认入口及已有依赖不足以表达实际等待位置时填写 | 每条引用属于一个 consumer，覆盖该消费者的默认入口等待         |

省略 `ready` 时，以相关生产 worktile 完成且交出区域满足消费者可见性为就绪点。`wait_at` 按消费者分别覆盖：未被点名的消费者仍在其 worktile 开始前等待；省略整个字段时，全部消费者采用该默认入口。相应交接机制由 [tile_pipeline](5.design.tile_pipeline.md#跨-step-交接) 的实际动作承担。

事件别名按其引用列表展开。`ready` 的前驱必须全部满足；`wait_at` 对其中每个等待动作的 `done` 或读取动作的 `issue` 分别施加就绪约束。等待动作本身可以提前发起。`wait_at` 也可指向循环外的 worker 入口动作；工作集合为空时，仍约束实际存在的入口事件。

`storage` 写 `global` 表示全局物化；写片上区域引用时，位置、所属 worker、容量和槽数取自该 storage 定义。本区不复制区域声明，也不指定分配 API。

#### 数学值与区域匹配

`handoff` 的键引用已定义的数学值，生产区域由 `producer` 的 `target` 给出，消费区域由 `consumer` 的 `worktile` 给出；循环外动作的消费值与范围由该动作的 `describe` 给出。局部名称不同而实际是同一个值时，引用上游已有的数学视图，不能仅凭 shape 相同就认定为同一个对象。

片上交接先按 `storage` 所属的 worker 确定对应副本，各 worker 的同名副本独立匹配。生产与消费按同一个数学值、同一版本和明确的索引关系匹配，并检查生产区域是否覆盖消费区域。索引关系来自上游的数学定义，需要转置、排列、切片或版本视图时引用 `math_reshape` 中已有的视图，不按 shape 猜测。消费区域由多份生产 worktile 覆盖时，要等待全部相关生产结果。

例如，同一值的生产块沿 `dv` 每 32 列一份，消费块每 64 列一份。消费块 `r` 需要 `[64r, 64r+64)`，因此等待生产块 `2r` 和 `2r+1` 的对应区域。这里是同一值的区域覆盖，没有新的数学合并，不因此填写 `tile_reduction`。

#### 存续与初始化

一个数据版本的存储至少保留到它的生产访问、全部声明的消费访问及相关在途操作结束；“发出了异步读取”不等于“已经消费完”。这既不要求分配器立即释放，也不要求一律保留到任务结束。

`initialize` 在相应生产开始前，为本次交接版本补足消费者所需、生产者未写且尚无保证的初值。入口已给定或数学定义保留的初态直接沿用，不重复填写。本字段不指定分配 API，也不生成额外 step 或 launch。

例如，上游把 `T` 定义为下三角矩阵，`solve` 只写下三角，而 `apply` 会读取整个矩阵。上三角尚无初值保证时，在 `solve` 开始前建立零值：

```yaml
handoff:
  T: {producer: solve, consumer: [apply], storage: global, initialize: 0}
```

交接值的数学区域与分配字节范围分别核对。仅预取后丢弃的字节，在读取合法且不影响结果、控制流或后续访问时无需初始化；其实际工作与访问边界仍在流水线或实现交接中说明。

跨 kernel 不保留 worker 局部资源身份：不同 kernel 即使采用相同的 mapping，也建立新的 worker。同一 kernel 内跨 step 存续的局部资源，必须与 `order`、工作归属和资源定义一致；逐 worktile 接续已经保证前一份数据消费完才覆盖同一个槽时，不再登记一条同义的复用等待。

### 固定结构与扩展边界

| 位置类型 | 本区位置                                                                                                                   | 允许的变化                               |
| -------- | -------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| 固定结构 | `work_schedule`、`flow`、launch 条目、handoff 条目、step 条目，以及 `decomposition / mapping / schedule` 及其子对象 | 只使用本节声明的字段                     |
| 具名映射 | `step`、`handoff`、`partition`、各数据块映射，以及其中的轴名与成员区域维度名                                        | 可以增加当前设计需要的名称，条目结构不变 |
| 开放取值 | `refill` 的机制、`exit` 的条件，以及 `meaning`、`strategy` 与 `describe` 的内容                                     | 写成能看出含义或规则的具体内容，不只写一个名称 |

增加 step ID、张量名或维度名是填写实例；新增字段，或新增 `order`、`direction` 的取值遵循[公共扩展规则](0.common.md#结构与扩展)。

## 语法规则

### 名称与顺序

step ID 使用通用标识符，推荐简短的小写名称；整个区域只有一个 step 时，它的 ID 统一写 `MAIN`，不另起算子名。数学值、维度与规模的名称沿用上游符号，保留大小写。通用命名与 YAML 写法见[公共约定](0.common.md#通用写法)。

`worktile_order` 的列表顺序从外层到内层读取；它不是 kernel 提交顺序、跨 worker 完成顺序，也不是内部 reduction 循环。

`consumer`、`start_after` 和 `exit` 的列表都表示共同满足，不表示优先级或任选其一。事件别名与自定义条件的名称使用通用标识符，推荐简短的小写名称。

### 数据块描述

`invariant`、`iteration` 与 `single_tile` 的每个条目必填 `meaning`，用一句简洁英文分别说明一份工作中保持不变的输入片段、每次局部迭代读取的输入片段、以及一份工作产生的结果片段。三类条目都先写 `meaning`，再写 `shape / dtype`；`invariant` 可以随后加 `offset` 区分同一 worktile 内的数学子区域，`iteration` 必须随后加 `direction`——方向有时由数学递推强制，有时是为了让掩码块或边界块先做完而选，两种情况都要写出来。

`shape / dtype` 描述一份 worktile 范围内的那个值，不是单个成员的局部 shape；成员分工由 `mapping.member` 单独表达。

| 字段          | 值的形式                                                 | 含义                                                                                   |
| ------------- | -------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `meaning`   | 非空英文字符串                                           | 必填；说明该输入块或结果块在一份工作中的含义                                             |
| `shape`     | 有序的具名维度列表，例如 `[query: 256, head_dim: 128]` | 逻辑维度顺序；partition 已经固定的单个 batch、head 坐标不必作为长度为 1 的维度重复登记 |
| `dtype`     | 引用上游已确定的类型                                     | 精度本身由 `math_reshape` 决定，这里用它和 `shape` 一起算清一份工作的字节量        |
| `offset`    | 与 `shape` 顺序对应的数学偏移列表                      | 相对当前 worktile，不是字节地址、共享内存偏移或线程地址                                |
| `direction` | `ascending / descending`                               | 该块沿自己的局部迭代索引的访问方向                                                     |

具名轴与整数表达式遵循[公共写法](0.common.md#shape-与整数表达式)，运行时规模的默认有效域见[算法要求](1.contract.algorithm_requirement.md#shape-与规模)。数值表达式引用已定义的符号、本区派生量和数学函数；这里写数学关系，不写设备实现代码。

每个 `partition` 维度条目按 `meaning / size / tile / range?` 排列。一个维度通常产生 `ceil_div(size, tile)` 个工作坐标，最后一份工作的有效数学区域不超出 `size`。任何一个维度的 `size` 为 0 时，本 step 的工作集合为空。`tile` 始终大于 0。线程级 mask 与地址计算在下游描述。

`range` 约束 `size` 的允许取值，有限端点为非负整数或相应表达式，包含两端，上界无固定值时写 `null`。例如所有专家都可能为空时，工作数 `T` 的维度条目可写为 `{meaning: Expert work item, size: T, tile: 1, range: [0, null]}`。上游已给出同一约束时可省略 `range`。

`iteration` 的每个条目描述一个输入块怎样随自己的数学迭代索引更换。迭代范围由上游值的索引域和本份工作的范围确定，可以随工作坐标变化，例如因果可见范围随 query 块移动。两个输入块沿同一个已定义索引变化时使用该索引的同一版本；属于不同局部循环时，不因为同时出现在 `iteration` 中就被解释为同步推进、笛卡尔积或固定先后。局部循环之间必要的先后用 `strategy` 或 `describe` 简明交代，其动作关系由 `tile_pipeline` 展开，不靠映射顺序表达。

### 事件与启动

事件引用写成 `<step_id>.<event_name>`。

| 事件名           | 含义                                                                                           |
| ---------------- | ---------------------------------------------------------------------------------------------- |
| `kernel_done`  | 该 step 所属计算 kernel 完成，且交出的结果满足后继执行所需的可见性                            |
| `launch_ready` | 整个前驱 grid 满足后继启动条件的许可事件；不表示交接数据已就绪                              |
| 其他名称         | `tile_pipeline.step.<step_id>.event` 中定义的局部事件集合，按其形参、worker 与工作实例解析 |

使用 `launch_ready` 时，触发位置、条件与参与范围由 `tile_pipeline` 的动作契约说明；提供启动许可及所需可见性、进展保证的具体机制由 `realization` 绑定。

`start_after` 中的事件集合展开后，所有前驱都须满足；引用范围须覆盖本次启动所需的事件实例。交接事件的工作与索引对应关系遵循上面的[数学值与区域匹配](#数学值与区域匹配)。

同一次提交内的各 step 共享一个 `kernel_done`：引用其中任何一个 step 的 `kernel_done`，指的都是这次提交的完成，不是该 step 的局部完成点。`start_after` 约束设备执行何时可以开始，不要求 host 线程阻塞；一次提交不能等待自己的 `kernel_done`，跨提交的启动依赖也不能形成没有初始事件的循环。

启动许可、数据就绪和真正消费数据是三个可以不同的时点，`start_after` 与 `ready / wait_at` 分别记录它们。`order`、启动前驱和交接约束共同成立，局部时点不取消已有的完成次序。提前启动只保留重叠机会；跨 worker 消费部分结果仍需可见性和进展依据。

### 省略与说明字符串

省略一个可选字段必须具有本节说明的含义，不表示信息尚未填写；`strategy` 的省略表示结构字段与上游引用已经够用，不表示采用了某个隐藏的默认策略。除 `partition: {}` 表示单份整体工作、标量 `shape: []`、以及 `range` 的无界端点外，不用空映射、空列表或 `null` 代替内容；没有可选条目时省略整个字段。

`meaning` 说明条目的工作身份或数据用途，沿用上游数学定义；step 的 `describe` 概括计算职责，`thesis` 说明主要选择的依据与取舍。三个 `strategy` 分别补充分解、映射、分配中结构与上游未表达的关键关系或条件，直接写必要的参数、范围或对应关系。

已有依赖已保证的 `ready / wait_at` 可以省略；完全相同的 handoff 属性可用 YAML anchor/alias 复用，各值仍分别登记。

说明字符串也不提供条件删边或替换生产者的语义；多条路径的合法分组见[公共规则](0.common.md#参数变化与结构变化)。

## 关键原则

### 与微流水线的接口

role 划分、动作表和缓冲协议由 `tile_pipeline` 决定；交接所在的[片上存储](5.design.tile_pipeline.md#片上存储)和[事件别名](5.design.tile_pipeline.md#跨-step-交接)也由它在相应的 step 中定义，本区只引用。

### 影响设计的事实写进正式字段

全局物化、同一 worker 的延续、完成边界、接续粒度和必要的存储初值都可能改变性能因果，写进正式字段。具体的内存分配调用、普通地址计算、线程布局，以及不影响设计成立的 API 偏好不属于本区；但也不能把确实必要的存储初值随分配细节一起删掉。
