#### 核心思想

`design.work_schedule` 把上游已经确定的计算组织成可分配的工作，明确由谁执行、工作怎样分配和接续，以及不同工作之间怎样交接。

本区不重新定义数学算法，也不展开 warp 分工、逐线程地址、指令、barrier 编号或寄存器布局。它接收 `math_reshape` 给出的值、索引、数学关系、精度和状态初值，向 `tile_pipeline` 提供工作边界、worker 身份、执行作用域及必要的交接要求。

**基本对象**

| 对象 | 含义 | 需要避免的混淆 |
| --- | --- | --- |
| `worktile` | 一份可以独立分配的计算工作，可以产生最终结果，也可以产生部分结果 | 不等于输入张量的一块存储，也不等于一次局部循环迭代 |
| `worker` | 承担工作的协作执行单元，可以由一个或多个 CTA 组成 | 不等于一个线程；一个 worker 可以连续处理多个 worktile |
| `phase` | 一类具有明确分解、映射和分配规则的工作定义 | 不等于数学步骤、kernel launch 或缓冲槽 |

本区使用 `thesis / flow / phase`：

- `thesis` 概括整体工作组织中最重要的设计选择。
- `phase` 是工作定义的唯一登记处，采用具名映射。
- `flow` 引用这些定义，记录实际的计算 kernel 边界、同一执行组织内的接续方式和跨 phase 数据交接。

`flow.launch` 中的一个条目对应一次计算 kernel 提交。条目可以包含一个 phase，也可以包含由同一批 worker 接续执行的多个 phase。因此，phase 数量与计算 kernel 数量没有一一对应关系。

`flow.handoff` 以已经定义的数学值命名，说明生产者、消费者和存储位置。它不再复制张量定义、shape、dtype 或数学公式。

**worker 身份与接续粒度分别表达**

同一批 worker 可以采用不同的接续方式：

| 接续方式 | 对一个持久化 worker 的含义 |
| --- | --- |
| 全体接续 | 全部 worker 完成 A 后，才允许开始 B |
| 逐 worker 接续 | 当前 worker 完成自己分配到的全部 A 工作，再执行自己的 B 工作 |
| 逐 worktile 接续 | 当前 worker 对一份配对工作执行 A→B，然后才推进下一份配对工作 |

保留 worker 身份，不自动决定采用哪一种接续方式。这一区别直接影响中间量存续、缓冲容量和是否存在全体等待，不能藏在“persistent”或“same worker”等策略名称中。

**格式不诱导拆分**

不同计算不必登记成不同 phase。能够用一份工作组织和局部流水线准确表达的设计，默认保持单 phase。确实存在多份工作组织时，才分别登记。

增加 phase 标签不自动增加 launch、全量屏障、全局物化或资源重置。真正发生的这些行为则必须记录，不能因为希望格式简短而省略。

#### 字段定义

**结构轮廓**

```text
work_schedule
├─ thesis
├─ flow
│  ├─ launch
│  └─ handoff
└─ phase
   └─ <phase_id>
      ├─ describe
      ├─ decomposition
      ├─ mapping
      └─ schedule
```

`<phase_id>` 和下文的 `<value>`、`<dimension>` 表示实例名称，不是固定字段。

外层结构与 phase 内层组织沿用已确认的边界。`flow` 内部采用当前的简写形式；尚未完成语法收敛的能力在本节明确标为“待确认”，不通过恢复多层执行包装或接受任意字段来补齐。

**外层与执行组织**

| 字段路径 | 值的形式 | 填写条件 | 含义与约束 |
| --- | --- | --- | --- |
| `thesis` | 非空英文字符串 | 必填 | 概括整体工作组织，不承载只能靠猜测才能解析的依赖 |
| `flow` | 固定结构映射 | 必填 | 仅包含 `launch` 和可选的 `handoff` |
| `flow.launch` | 非空列表 | 必填 | 每个条目描述一次计算 kernel 提交，不是 phase 定义表 |
| `flow.launch[].phase` | 非空 phase ID 列表 | 必填 | 引用本次提交包含的 phase，不在此重新定义其含义 |
| `flow.launch[].worker` | `same` | 一个提交包含多个 phase 时必填 | 表示这些 phase 保留同一批实际 worker；不表示任何等待范围 |
| `flow.launch[].order` | `all`、`per_worker`、`per_worktile` | 一个提交包含多个 phase 时必填 | 决定列表内 phase 的接续粒度；单 phase 时省略 |
| `flow.launch[].start_after` | 里程碑引用，或非空引用列表 | 设计要求整个提交在指定事件后才能开始时填写 | 列表中的条件同时满足；省略表示不额外声明整个提交的启动等待 |
| `flow.launch[].protocol` | `pdl` | 采用本节定义的 PDL 提前启动组织时必填 | 指定启动许可与数据可用性分离的协议；普通完成依赖省略 |
| `phase` | 非空具名映射 | 必填 | 键是 phase 的唯一身份声明 |
| `phase.<phase_id>` | 固定结构映射 | 每个 phase 必填 | 仅包含 `describe / decomposition / mapping / schedule` |
| `phase.<phase_id>.describe` | 非空英文字符串 | 必填 | 说明这类工作计算什么；不再同时设置 `name` |
| `phase.<phase_id>.decomposition` | 固定结构映射 | 必填 | 定义一份工作 |
| `phase.<phase_id>.mapping` | 固定结构映射 | 必填 | 定义执行者 |
| `phase.<phase_id>.schedule` | 固定结构映射 | 必填 | 定义工作分配与接续 |

`start_after` 的单引用与单元素列表等价。允许非空列表是对当前字段的最小补充，用于多个前驱的启动汇合，不增加另一张依赖图。

`order` 的三个值是当前的封闭枚举：

| 值 | 语义 | 额外约束 |
| --- | --- | --- |
| `all` | 前一个 phase 的全部工作完成后，下一个 phase 才开始 | 同 kernel 内采用这种组织，必须有可实现的全体同步和进展依据 |
| `per_worker` | 每个 worker 完成前一个 phase 分配给自己的全部工作，再进入下一个 phase | 不同 worker 之间不因此产生等待 |
| `per_worktile` | 对当前配对工作按列表顺序完成全部 phase，再推进下一份配对工作 | 参与 phase 必须具有相同的工作坐标集合和一致的工作归属 |

当前多 phase 单提交形式只完整规定 `worker: same`。共享动态领取池的关系及领取机制尚未形成对应的完整简写，不能仅填写 `worker: shared` 就认为设计已经完整。

**数据交接**

| 字段路径 | 值的形式 | 填写条件 | 含义与约束 |
| --- | --- | --- | --- |
| `flow.handoff` | 非空具名映射 | 存在跨 phase 数据交接时必填 | 键引用上游已定义的数学值；没有交接时整个字段省略 |
| `flow.handoff.<value>.producer` | phase ID | 必填 | 该值的生产 phase；可以由其中多份 worktile 共同产生 |
| `flow.handoff.<value>.consumer` | 非空、无重复的 phase ID 列表 | 必填 | 该值的消费 phase |
| `flow.handoff.<value>.storage` | `global`，或 `tile_pipeline.resource.<resource_id>` 引用 | 必填 | 全局物化，或使用另一区域已经定义的具体资源 |
| `flow.handoff.<value>.initialize` | 数值标量或上游标量引用 | 所选组织需要先建立可被读取的存储初值时填写 | 不是根据分配 API 自动抄写；省略不表示默认清零 |
| `flow.handoff.<value>.ready` | 生产者里程碑引用 | 可消费时点不同于默认生产 worktile 完成时填写 | 覆盖默认的生产就绪时点，不增加另一份数据定义 |
| `flow.handoff.<value>.wait_at` | 消费者里程碑引用 | 消费者可以先执行独立工作、稍后才等待该值时填写 | 覆盖默认的消费 worktile 入口等待 |

当前 `wait_at` 简写只规定单消费者情况下的显式填写。多个消费者使用默认入口等待时，不需要该字段；多个消费者需要不同显式等待点的形式待确认，不能靠列表位置隐式配对。

`storage` 的两种形式不是同义短写：

- `global` 只规定全局物化，不规定分配 API、物理地址或分配器所有权。
- 资源引用指向一个具体设计资源。资源的存储空间、所属 worker、容量和槽数由其定义提供，本区不复制。

默认交接语义如下：

| 项目 | 省略时的含义 |
| --- | --- |
| `ready` | 相应生产 worktile 完成，且交出的区域已经满足消费者所需的可见性 |
| `wait_at` | 相应消费 worktile 开始前，其所需生产区域必须就绪 |
| `initialize` | 本区没有声明预初始化操作；不能据此假定存储已有任何特定值 |

默认语义是设计约束，不会自动生成发布标志、跨 CTA barrier 或轮询协议。需要这些机制的设计，仍须由执行组织和 tile_pipeline 给出可实现的对应关系。

**工作分解**

下表中的路径相对于 `phase.<phase_id>.decomposition`。

| 字段路径 | 值的形式 | 填写条件 | 含义与约束 |
| --- | --- | --- | --- |
| `strategy` | 非空英文字符串 | 结构字段不足以说明一个必要的分解决定时填写 | 可以说明明确的数学范围或局部遍历关系；不重复标题和字段已经表达的事实 |
| `partition` | 维度具名映射 | 必填 | 只登记真正产生独立 worktile 的维度；空映射明确表示整个任务只有一份 worktile |
| `partition.<dimension>.size` | 正整数或受限数值表达式 | 必填 | 该维度的完整逻辑大小 |
| `partition.<dimension>.tile` | 正整数或受限数值表达式 | 必填 | 一份 worktile 在该维度覆盖的大小 |
| `partition.<dimension>.range` | 两元素范围列表 | `size` 的合法取值域未由上游唯一给定时填写 | 约束 `size`，不是选择本次访问的索引区间 |
| `worktile` | 固定结构映射 | 工作读取输入数据块时必填 | 包含 `invariant`、`iteration` 中至少一项 |
| `worktile.invariant` | 数学值具名映射 | 存在局部迭代中保持不变的输入块时填写 | 不表示编译期常量，也不表示跨 worktile 保持不变 |
| `worktile.iteration` | 数学值具名映射 | 存在随局部迭代更换的输入块时填写 | 局部遍历不因此产生独立 worktile |
| `target` | 固定结构映射 | 必填 | 描述实际产物和已有数学合并关系 |
| `target.single_tile` | 非空数学值具名映射 | 必填 | 每份 worktile 实际产生的结果，可以是部分结果 |
| `target.cross_tile` | 数学值具名映射 | 需要说明由多份工作共同构成的结果，且该结果未在实际合并 phase 中登记时填写 | 只描述结果，不隐式创建执行者、归约或额外工作 |
| `target.tile_reduction` | 固定结构映射 | 所属 phase 实际执行跨工作结果的数学合并时填写 | 仅包含 `dimension / input / output / method` |

`tile_reduction` 的条目如下：

| 字段 | 值的形式 | 含义 |
| --- | --- | --- |
| `dimension` | 维度名或非空维度名列表 | 被合并的数学维度 |
| `input` | 数学值引用或非空引用列表 | 合并输入 |
| `output` | 数学值引用或非空引用列表 | 合并输出 |
| `method` | 上游数学方法引用 | 引用已经确定的合并规则，不在这里重写公式 |

独立合并 phase 已经登记最终结果时，生产部分结果的 phase 不再用 `cross_tile` 或 `tile_reduction` 重复登记同一份合并工作。

**数据块描述**

| 使用位置 | 合法字段 | 填写规则 |
| --- | --- | --- |
| `worktile.invariant.<value>` | `shape / dtype / offset` | `shape`、`dtype` 必填；需要区分同一 worktile 内的数学子区域时填写 `offset` |
| `worktile.iteration.<value>` | `shape / dtype / direction` | 三项必填 |
| `target.single_tile.<value>` | `shape / dtype` | 两项必填 |
| `target.cross_tile.<value>` | `shape / dtype` | 两项必填 |

`shape` 使用有序、带名称的维度列表，例如 `[query: 256, head_dim: 128]`。`dtype` 引用上游确定的数据类型；案例使用的 `bf16`、`fp32` 不是本区自行限定的全部类型集合。

`offset` 是与 `shape` 顺序对应的数学偏移列表，相对于当前 worktile，不是字节地址、共享内存偏移或线程地址。

`direction` 当前使用封闭枚举 `ascending / descending`。它描述相应输入块沿其局部迭代索引的访问方向，不表示其他输入块与它之间的先后关系。

**执行映射**

下表中的路径相对于 `phase.<phase_id>.mapping`。

| 字段路径 | 值的形式 | 填写条件 | 含义与约束 |
| --- | --- | --- | --- |
| `strategy` | 非空英文字符串 | 存在无法由其他映射字段直接读出的必要决定时填写 | 不用“CTA mapping”等同义文字重复结构 |
| `worker` | `unit / count` 映射 | 必填 | 一个协作 worker 的组成 |
| `worker.unit` | 执行单元类别名称 | 必填 | 取自 `contract.hardware_specification.execution` 登记的单元，例如 `CTA`；不自行定义单元 |
| `worker.count` | 正整数或受限数值表达式 | 必填 | 一个 worker 包含多少个上述单元 |
| `placement` | `unit / count` 映射 | 设计依赖特定物理资源范围时填写 | 例如一个 worker 需要两个 SM；不登记无关的物理绑定 |
| `count` | 正整数或受限数值表达式 | 必填 | 本执行组织提交的 worker 总数，不等于同时驻留数量 |
| `member` | 成员列表 | 多成员 worker 的数学分工不能从其他事实唯一确定时填写 | 列表位置对应成员序号；每个成员按维度登记左闭右开的局部区域 |

`mapping.worker.count` 与 `mapping.count` 必须分别解释。前者是一个 worker 的组成规模，后者是实际提交多少个 worker。

同一 launch 使用 `worker: same` 时，参与 phase 的 worker 组成、数量及必要的 placement 必须一致。重复引用同一 mapping 不建立第二批 worker，也不应把这些 `mapping.count` 相加。

**工作分配**

下表中的路径相对于 `phase.<phase_id>.schedule`。

| 字段路径 | 值的形式 | 填写条件 | 含义与约束 |
| --- | --- | --- | --- |
| `strategy` | 非空英文字符串 | 存在结构字段尚未表达的必要分配决定时填写 | 策略名称不能替代具体分配规则 |
| `worktile_order` | `by / direction` 条目列表 | `partition` 非空时必填 | 从外层到内层排列独立工作维度；每个 partition 维度出现一次 |
| `worktile_order[].by` | partition 维度名 | 必填 | 引用本 phase 的独立工作维度 |
| `worktile_order[].direction` | `ascending / descending` | 必填 | 该维度的逻辑排列方向 |
| `worker_assignment` | 固定结构映射 | 必填 | 仅包含 `preassigned / refill / exit` |
| `worker_assignment.preassigned` | `start / step` 或 `start / count` 映射 | 静态分配案例必填 | 定义当前 worker 预先获得的工作序列 |
| `worker_assignment.refill` | 当前完整规定的值为 `none` | 必填 | 表示没有运行时额外领取；其他机制需要完成受控扩展 |
| `worker_assignment.exit` | 条件引用或非空条件引用列表 | 必填 | 列表表示同时满足；`assigned_done` 表示该 worker 的已分配工作均已完成 |

`preassigned` 中 `step` 与 `count` 互斥，不能同时填写。当前文档没有把任意字符串、队列名称或 `CLC` 口号登记为完整的 refill 机制。

**固定结构、具名映射与扩展边界**

| 位置类型 | 当前范围 | 规则 |
| --- | --- | --- |
| 固定结构 | 本节各表列出的对象字段 | 未知字段应报告错误，不能默默忽略 |
| 具名映射 | `phase`、`handoff`、`partition`、输入与输出值映射，以及成员区域中的维度名 | 可以增加案例实例名称，但条目内部仍遵守对应固定结构 |
| 受控扩展 | `flow` 内部组织与交接形式，以及既有 `worker_assignment.refill` 的具体机制 | 需要先补充字段或值形式的定义、触发条件和实例；不表示实例可以任意增加键 |

`phase.<phase_id>` 不因下层允许精修而开放第五个并列区域。`decomposition`、`mapping`、`schedule` 也不默认接受任意字段。增加 phase ID、张量名或维度名是增加实例，不是扩展模板。

以下缺口尚未纳入当前简写的固定语法：

| 待确认事项 | 尚缺少的具体约定 |
| --- | --- |
| 同一 phase 的多次引用及循环嵌套 | 调用实例身份、有限索引范围、跨轮版本和首轮初值的简写 |
| 多类工作共享动态领取池 | worker 集合关系、工作项身份、领取规则及全局退出条件 |
| 无直接数据传递的局部复用或协议等待 | 在当前简写中承载 `reuse / sync` 关系的位置及端点形式 |
| 多消费者的不同显式等待点 | `wait_at` 与各消费者之间的无歧义对应 |
| 非默认交接索引关系的引用 | 对已有转置、排列、切片或版本关系的专用引用形式 |

这些需求不能通过伪造数学值、复制 phase 定义、恢复未声明的执行树，或增加 `notes / misc / extra` 来绕过。

#### 语法规则

**命名、定义与引用**

Schema 字段一律使用单数。YAML 字段、说明字符串和自定义里程碑名称使用英文，不允许独立注释或行内注释。

phase ID 在当前 `work_schedule` 内唯一，建议采用小写英文与下划线。数学值名称沿用上游符号，保留大小写。源码路径、函数名及其他外部标识符不得为满足命名风格而修改。

`phase` 的映射键定义身份；`flow.launch[].phase` 只引用身份。引用需要能够在当前 `phase` 表中解析，定义也必须被执行组织引用。

当前无调用别名的简写要求，每个 phase ID 在 `launch` 的 phase 列表中只出现一次。这是当前引用形式的限制，不是“一个 phase 在算法上只能执行一次”的限制。需要重复执行时，应先解决调用实例和版本表示，不能直接重复 ID 后继续使用含糊的交接引用。

`handoff` 的键直接引用数学值，不建立另一个同名对象。例如：

```yaml
handoff:
  P:
    producer: partial
    consumer: [merge]
    storage: global
```

其中 `P` 必须解析到上游同一个数学值。`partial.target.single_tile.P` 给出其生产区域；`merge.worktile.invariant.P` 或 `merge.worktile.iteration.P` 给出其消费区域。

局部名称不同但实际引用同一数学值时，不能仅凭 shape 相同自动认定为同一个对象。应先采用已有明确的数学视图或符号引用；缺少这种关系时报告信息缺失。

YAML anchor 和 alias 只用于复用相同字段内容。它们不创建新的 phase 身份、不表示张量地址相同，也不自动保证 worker 身份相同。每个完整案例是独立的 YAML 文档，不能跨案例引用 anchor。

**列表与映射顺序**

`phase`、`partition`、`handoff`、`invariant`、`iteration` 和结果映射的书写顺序没有执行含义。

`worktile_order` 的列表顺序有含义：从外层到内层读取。它不是 kernel 提交顺序、跨 worker 完成顺序，也不是内部 reduction 循环。

`launch` 列表枚举提交条目，不隐含相邻条目之间的完成屏障。设计要求全体完成后接续时，必须填写 `start_after`。没有依赖关系的条目不因此获得物理并发保证。

同一 launch 的 phase 列表在填写 `order` 后才具有所规定的接续含义。单 phase 条目不填写无意义的 `worker` 或 `order`。

`consumer` 与 `start_after` 引用列表均不表示优先级。多个消费输入、多个启动前提的语义是共同满足，不是任选其一。

**执行事件与接续范围**

事件引用采用 `<phase_id>.<milestone>` 形式。

| 里程碑 | 含义 |
| --- | --- |
| `kernel_done` | 该 phase 所属计算 kernel 完成，且交出的结果满足后继执行所需的可见性 |
| `launch_ready` | PDL 定义的整个前驱 grid 的后继启动许可事件，不是某个 worktile 的数据就绪 |
| 其他名称，例如 `use_P` | tile_pipeline 提供的具名里程碑，必须能确定作用域、工作索引和相关数据使用位置 |

`project.kernel_done` 指的是 project 所属 kernel 的完成。如果 project 与 mix 属于同一 launch，那么 `project.kernel_done` 与 `mix.kernel_done` 指向同一个 kernel 完成事件，不能把它们解释为两个 phase 的局部完成点。

`start_after` 约束设备执行何时可以开始，不要求 host 线程阻塞。实现可以采用适合所选语言和环境的提交依赖，但不能改变等待范围。

同一个 launch 不能等待自己的 `kernel_done` 后才开始。跨 launch 的启动依赖也不能形成无初始事件可触发的循环。

`order: per_worktile` 不只是声明 `A(t)` 必须先于 `B(t)`。它明确要求当前配对组完成后，才推进该 worker 的下一份配对工作：

```text
A(t0), B(t0), A(t1), B(t1)
```

它不允许将同一声明解释为：

```text
A(t0), A(t1), B(t0), B(t1)
```

使用该写法时，各 phase 的 partition 坐标集合、逻辑排列和预分配序列必须一致。产物和内部迭代可以不同，但对应工作必须由同一 worker 承担。不同大小生产块到消费块的区域覆盖，不等于这种一一配对。

**索引、shape 与范围**

<!-- SYNC(1.contract)：1.contract.algorithm_requirement.md 规定运行时规模默认是正整数，并定义了 shape 的具名轴写法和字符串整数表达式。本节 partition.range 的 [1, null] 示例与该默认重复；shape 与表达式的通用部分改为引用该文件，只保留本区特有的规则。改完删除本注释。 -->

对 partition 维度 `d`，`size` 是完整大小，`tile` 是每份工作覆盖的大小。通常该维度产生 `ceil(size / tile)` 个工作坐标。最后一份工作的有效数学区域不能超出 `size`；线程级 mask 和地址计算不在本区展开。

`partition.<dimension>.range` 约束的是 `size` 的允许取值域，使用包含端点的下界、上界。`[1, null]` 表示正值且无固定上界。它不是左闭右开的访问区间，也不是局部循环范围。上游已经给定同一约束时不重复填写。

`member` 的区域与文字中明确写出的数学切片使用左闭右开区间。例如 `[0, 128]` 表示局部坐标 `[0, 128)`。

`shape` 的列表顺序是逻辑维度顺序。partition 已经固定的单个 batch、head 等坐标可以不作为长度为 1 的维度重复登记，但必须能够从上游值的索引关系唯一补回。

输入块和结果块默认描述整个 worktile 范围内的相应值，不是单个 CTA 成员的局部 shape。成员分工由 `mapping.member` 单独表达。

数值表达式可以引用已定义符号及本区派生量，并使用四则运算、括号以及 `min / max / floor / ceil / ceil_div`。它们用于数量和数学索引，不允许任意程序调用、赋值或设备代码。

`strategy`、`describe`、`thesis` 是说明字符串，可以包含简短数学范围，但不能用含糊的自然语言代替已经有固定字段承载的决定。

**局部迭代与数据区域**

`iteration` 中的每个条目描述一个输入块怎样随其数学迭代索引更换。迭代范围必须能够从上游值的索引域及本份工作范围确定。

两个输入块沿同一个已定义索引变化时，使用该索引的同一版本。属于不同局部循环时，不因同时出现在 `iteration` 映射中就被解释为同步推进、笛卡尔积或固定先后。

局部循环之间必要的先后可以用已有 `strategy` 或 `describe` 简明交代，其动作关系由 tile_pipeline 展开。不能依靠 YAML 映射顺序表达。

跨 phase 数据匹配遵循：

> 先解析同一个数学值、同一版本和明确的索引关系，再检查生产区域是否覆盖消费区域。

不能根据 shape 猜测排列、切片、转置或版本。消费区域由多份生产 worktile 覆盖时，必须等待所有相关生产结果。存在覆盖缺口、未解释的重叠写入或索引歧义时，不能宣称交接已经接通。

**分配序列与退出**

本区使用以下派生量，不要求在案例中再次定义：

| 名称 | 来源 |
| --- | --- |
| `worktile_count` | 当前 phase 的 partition 各维工作数之积；空 partition 的乘积为 1 |
| `worker_count` | 当前实际执行组织采用的 `mapping.count` |
| `worker_id` | 当前执行组织内从 0 开始的 worker 编号 |

按 `worktile_order` 将工作坐标展平为逻辑 worktile 编号。

`preassigned: {start: s, step: d}` 表示编号 `s, s+d, s+2d, ...`，直到超出本 phase 的合法工作范围；`d` 必须为正整数。

`preassigned: {start: s, count: n}` 表示连续的 `n` 份工作。`n` 为非负整数，指定编号必须合法，不能未经声明就截断或改成步长序列。

消费自己预先获得的下一份工作不叫 refill。`refill: none` 不妨碍一个 worker 连续处理多份预分配工作。

`assigned_done` 不表示“已经领取完”，而是相关已分配工作已经完成。若同一 worker 还要执行同 launch 中的后续 phase，它不能因为当前 phase 的工作耗尽就物理退出。所有剩余职责及需要收尾的在途操作完成后，才允许结束该 worker。

**存续、初始化与资源复用**

数据版本的存储至少要保留到其生产访问、全部声明的消费访问及相关在途操作结束。没有证据时，不能把“发出了异步读取”当作“已经消费完”。

这种默认存续要求不等于分配器必须立即释放，也不等于一律保留到任务结束。内部函数返回某个中间量，不会自动把它变成 Contract 的外部输出。

`initialize` 只描述所选组织确实需要建立的存储初值。例如生产者没有覆盖、而消费者会读取的区域需要预先为零。它不能仅因为源码调用 `torch.zeros` 就填写，也不能因为最终输出 dtype 已知就推导初始值。

当前初始化简写作用于所引用数学值的新存储版本，在相应生产开始前完成。它不规定分配 API，也不自动登记额外 phase 或额外 launch。需要局部初始化范围而现有字段无法唯一确定时，应报告表达缺口。

跨 kernel 不保留 worker 局部资源身份。不同 kernel 即使采用相同 mapping，也建立新的 worker。单 kernel 中的局部资源跨 phase 存续，则必须与 `worker` 关系、工作归属和资源定义一致。

当逐 worktile 接续已经保证前一份数据消费完后才覆盖同一个槽时，不再登记一条同义复用等待。存在额外的非数据复用依赖而当前格式无法表达时，应明确标为待确认，不能伪造一个用于同步的张量。

**省略、空值与短写**

省略可选字段必须具有本节已经说明的含义，不能表示“重要信息尚未填写”。

`strategy` 的省略表示结构字段及上游引用已经足够，不表示采用某个隐藏默认策略。

除 `partition: {}` 明确表示单份整体工作、标量 `shape: []`、以及 `range` 中的无界端点外，不使用空映射、空列表或 `null` 代替必要内容。没有可选条目时，省略整个字段。

单 phase 的最小 flow 为：

```yaml
flow:
  launch:
    - phase: [attention]
```

它已经表达一次计算 kernel 提交，不需要额外套 `run`、`kernel` 或再次嵌套执行区域。

#### 关键原则

**同一事实只维护一次。**

phase 身份和含义定义在 `phase`；launch 只引用身份。输入输出的数学定义和精度来自上游；handoff 只登记交接。工作数量和执行数量能够推导时，不增加手工计数字段。

| 数量 | 应从哪里获得 |
| --- | --- |
| phase 定义数 | `phase` 的键集合 |
| phase 调用次数 | 执行组织中的调用实例；当前无重复简写中，每个被引用 phase 为一次 |
| 主要计算 kernel 数 | `flow.launch` 条目数 |
| 一次 phase 调用的 worktile 数 | `decomposition.partition` |
| 实际 worker 数 | 所属执行组织采用的 `mapping.count` |

一份 phase 调用包含其完整工作集合。持久化 worker 消费下一份 worktile，不会增加 phase 调用次数。局部 K 循环、chunk 递推和内部归约循环也不增加 phase 调用次数。

初始化、分配、自动调优或包装函数中的其他 GPU 活动，不能未经核对就计入或排除。因此，主要计算 launch 数不能冒充整个包装函数的全部 GPU 活动数。

**区分工作分解与局部遍历。**

完整遍历一个维度，不等于沿该维度产生独立工作。FA4 的 KV 维度属于 iteration；GDN 的 advance 将 chunk 放入 worker 内的顺序迭代。把这些维度同时登记进 partition，会改变并行度、状态归属和合并需求。

**把合并方法放在实际执行合并的工作中。**

部分结果生产者只登记自己产生的部分结果。独立合并 phase 必须有自己的 worktile、mapping 和 schedule，`tile_reduction` 只描述其采用的上游数学方法，不再生成另一份隐式工作。

只有 `cross_tile` 的最终结果描述，没有实际执行者和必要依赖，不构成完整的合并设计。

**只记录影响设计成立的实现条件。**

全局物化、同 worker 延续、完整完成边界、逐 worktile 接续以及必要初始化，都可能改变性能因果关系，应进入正式字段。

具体内存分配调用、普通地址计算、线程布局和没有影响设计成立的 API 偏好，不属于本区。不能逐项抄写源码 API，也不能把确实必要的存储初值随分配细节一起删除。

**允许提前开始，不承诺物理并发。**

启动许可、数据就绪和真正消费数据的时点可以不同。PDL 案例分别记录它们，但不把 PDL 解释成逐 worktile 发布机制，也不把存在提前启动机会等同于已经测得 overlap。

跨 worker 的部分就绪消费不仅需要数学区域接通，还需要可见性和进展依据。字段能表达逻辑等待，不代表硬件实现必然无死锁。

**不以减少 phase 数为优化目标。**

一个 phase 可以包含多种计算；多个 phase 可以处于同一个 kernel。比较方案应关注并行度、计算效率、全局流量、缓冲容量、提交和等待成本，而不是只数 phase 标签。

**与 tile_pipeline 只交换必要接口。**

| 接口 | 本区提供或要求对方对应的内容 |
| --- | --- |
| phase 身份 | 同一组 phase ID，不复制另一份 flow |
| 工作实例 | 数学 worktile 坐标、worker 身份和必要的局部迭代索引 |
| 交接里程碑 | 被引用事件的作用域、区域、可见性和使用完成含义 |
| 执行与资源作用域 | kernel 边界、worker 延续关系及所引用资源的存续约束 |

本区不替 tile_pipeline 设计 lane、动作表或协作字段。遇到尚未统一的资源路径或里程碑接口，应明确接口要求，而不是在 work_schedule 内另建一套局部流水线。

**Case 1：FA4 非因果双 CTA、静态持久化**

固定来源：

| 内容 | 位置 |
| --- | --- |
| 主实现 | `Dao-AILab/flash-attention@ce088ab9:flash_attn/cute/flash_fwd_sm100.py::FlashAttentionForwardSm100` |
| 静态调度器 | `Dao-AILab/flash-attention@ce088ab9:flash_attn/cute/tile_scheduler.py::StaticPersistentTileScheduler` |
| Softmax | `Dao-AILab/flash-attention@ce088ab9:flash_attn/cute/softmax.py` |
| 软件依赖声明 | `Dao-AILab/flash-attention@ce088ab9:flash_attn/cute/pyproject.toml` |

实现语言选择 CuTe DSL，版本选择 `nvidia-cutlass-dsl 4.6.2`。只取非因果、等长、双 CTA、静态持久化分支，不包含 CLC、split-KV、paged KV、varlen 或额外 score/mask 修改。

只读输入为正整数 `BatchCount`，8 个 MHA head，Q/K/V 的序列长度均为 8192、特征维度均为 128。Q/K/V/O 为 BF16，LSE 为 FP32。`SMCount` 来自目标设备资料。Q_high、Q_low 是上游定义的当前查询工作块的两个数学视图。

该案例展示单 phase 的最小外壳；固定步长工作分配和 KV 局部遍历不因加入 flow 而改变。上述调度器源码支持按 cluster 工作编号和固定 grid 步长接续的组织。

```yaml
work_schedule:
  thesis: Share KV across a persistent two-CTA worker.

  flow:
    launch:
      - phase: [attention]

  phase:
    attention:
      describe: Compute attention output and log-sum-exp for each query block.

      decomposition:
        partition:
          batch: {size: BatchCount, tile: 1}
          head: {size: 8, tile: 1}
          query: {size: 8192, tile: 512}
        worktile:
          invariant:
            Q_high:
              shape: [query: 256, head_dim: 128]
              dtype: bf16
              offset: [0, 0]
            Q_low:
              shape: [query: 256, head_dim: 128]
              dtype: bf16
              offset: [256, 0]
          iteration:
            K:
              shape: [kv: 128, head_dim: 128]
              dtype: bf16
              direction: descending
            V:
              shape: [kv: 128, head_dim: 128]
              dtype: bf16
              direction: descending
        target:
          single_tile:
            O: {shape: [query: 512, head_dim: 128], dtype: bf16}
            LSE: {shape: [query: 512], dtype: fp32}

      mapping:
        worker: {unit: CTA, count: 2}
        placement: {unit: SM, count: 2}
        count: "min(worktile_count, floor(SMCount / 2))"
        member:
          - {query: [[0, 128], [256, 384]]}
          - {query: [[128, 256], [384, 512]]}

      schedule:
        worktile_order:
          - {by: batch, direction: ascending}
          - {by: head, direction: ascending}
          - {by: query, direction: ascending}
        worker_assignment:
          preassigned: {start: worker_id, step: worker_count}
          refill: none
          exit: assigned_done
```

本例有一个 phase 定义、一次 phase 调用和一个计算 launch。全部查询工作共 `128 × BatchCount` 份；这是由 partition 得到的数量，不另设计数字段。

**Case 2：GDN 五趟 Triton 分块前向**

固定来源：

| 内容 | 位置 |
| --- | --- |
| 前向组合 | `fla-org/flash-linear-attention@954438d1:fla/ops/gated_delta_rule/chunk.py::chunk_gated_delta_rule_fwd` |
| 块内累计 | `fla-org/flash-linear-attention@954438d1:fla/ops/utils/cumsum.py::chunk_local_cumsum` |
| 系数计算与三角求解 | `fla-org/flash-linear-attention@954438d1:fla/ops/gated_delta_rule/chunk_fwd.py::chunk_gated_delta_rule_fwd_intra` |
| W/U 生成 | `fla-org/flash-linear-attention@954438d1:fla/ops/gated_delta_rule/wy_fast.py::recompute_w_u_fwd` |
| 状态推进 | `fla-org/flash-linear-attention@954438d1:fla/ops/common/chunk_delta_h.py::chunk_gated_delta_rule_fwd_h` |
| 输出 | `fla-org/flash-linear-attention@954438d1:fla/ops/common/chunk_o.py::chunk_fwd_o` |

实现语言选择 Triton，版本选择 `3.6.0`。采用等长序列分支，不启用 FlashQLA、context parallel、额外 Q/K 归一化或 beta 激活。

| 只读输入 | 内容 |
| --- | --- |
| 尺寸 | 正整数 batch 数 `B`，序列长度 4096，head 数 8，dk=dv=128，chunk 长 64，`NT=64` |
| 外部类型 | Q/K/V 为 BF16；单步自然对数衰减 g、已激活的 beta 为 FP32；S_init、S_final 为 FP32 |
| chunk 索引 | `c` 的范围为 `[0, NT)`；块内 token 的范围为 `[0, 64)` |
| 累积衰减 | G 使用上游已定义、与该源码 `RCP_LN2` 和 `exp2` 路径一致的 FP32 表示 |
| 中间值 | T、W、U、S_bar、R_bar 为 BF16；运行中的 S 与 R 为 FP32 |
| 数学视图 | `S_bar(c)` 是进入 chunk c 的状态快照；R_bar 的保存窄化与用于状态更新的加权 R 窄化是两个不同路径 |
| 源码名称对应 | 数学 T 对应源码 A；S_bar 对应 h；R_bar 对应 v_new |

G 的存储表示必须先与上游对齐，不能仅因输入 g 是自然对数，就把源码的底 2 累积表示直接拼接到另一套数学定义中。

下例选择 solve 的 dk 输入块长 64，advance 每 worker 处理 32 个 dv 列，output 每 worktile 处理 64 个 dv 列。它们是本例配置，不是 B200 最优配置声明。

固定源码中，64×64 的求解结果按块下三角写入，而 W/U 生成读取完整矩阵，因此这里保留 T 的零初始化。S_final 的有效区域由状态推进完整写入，不把其分配 API 中的置零升级为本区要求。上述依据分别来自 `chunk_fwd.py`、`wy_fast.py` 和 `chunk_delta_h.py`。

该案例忠实保留五个主要计算 kernel，展示 chunk 从独立工作维度进入 worker 内递推，再恢复为独立工作维度。

```yaml
work_schedule:
  thesis: Keep chunk work independent except during the recurrent state update.

  flow:
    launch:
      - phase: [gate]
      - phase: [solve]
        start_after: gate.kernel_done
      - phase: [prepare]
        start_after: solve.kernel_done
      - phase: [advance]
        start_after: prepare.kernel_done
      - phase: [output]
        start_after: advance.kernel_done

    handoff:
      G:
        producer: gate
        consumer: [solve, prepare, advance, output]
        storage: global
      T:
        producer: solve
        consumer: [prepare]
        storage: global
        initialize: 0
      W:
        producer: prepare
        consumer: [advance]
        storage: global
      U:
        producer: prepare
        consumer: [advance]
        storage: global
      S_bar:
        producer: advance
        consumer: [output]
        storage: global
      R_bar:
        producer: advance
        consumer: [output]
        storage: global

  phase:
    gate:
      describe: Compute chunk-local cumulative decay G.

      decomposition:
        partition: &chunk_partition
          batch: {size: B, tile: 1}
          head: {size: 8, tile: 1}
          chunk: {size: NT, tile: 1}
        worktile:
          invariant:
            g: {shape: [token: 64], dtype: fp32}
        target:
          single_tile:
            G: {shape: [token: 64], dtype: fp32}

      mapping: &single_tile_mapping
        worker: {unit: CTA, count: 1}
        count: worktile_count

      schedule: &chunk_schedule
        worktile_order:
          - {by: batch, direction: ascending}
          - {by: head, direction: ascending}
          - {by: chunk, direction: ascending}
        worker_assignment: &single_tile_assignment
          preassigned: {start: worker_id, count: 1}
          refill: none
          exit: assigned_done

    solve:
      describe: Form and invert the chunk-local triangular matrix.

      decomposition:
        partition: *chunk_partition
        worktile:
          invariant:
            G: {shape: [token: 64], dtype: fp32}
            beta: {shape: [token: 64], dtype: fp32}
          iteration:
            K:
              shape: [token: 64, dk: 64]
              dtype: bf16
              direction: ascending
        target:
          single_tile:
            T: {shape: [token: 64, source_token: 64], dtype: bf16}

      mapping: *single_tile_mapping
      schedule: *chunk_schedule

    prepare:
      describe: Compute U, then W, using T.

      decomposition:
        partition: *chunk_partition
        worktile:
          invariant:
            T: {shape: [token: 64, source_token: 64], dtype: bf16}
            beta: {shape: [token: 64], dtype: fp32}
            G: {shape: [token: 64], dtype: fp32}
          iteration:
            V:
              shape: [token: 64, dv: 64]
              dtype: bf16
              direction: ascending
            K:
              shape: [token: 64, dk: 64]
              dtype: bf16
              direction: ascending
        target:
          single_tile:
            W: {shape: [token: 64, dk: 128], dtype: bf16}
            U: {shape: [token: 64, dv: 128], dtype: bf16}

      mapping: *single_tile_mapping
      schedule: *chunk_schedule

    advance:
      describe: Advance state and save each chunk's snapshot and correction.

      decomposition:
        strategy: Carry FP32 S across chunks and preserve the distinct saved and weighted R casts.
        partition:
          batch: {size: B, tile: 1}
          head: {size: 8, tile: 1}
          dv: {size: 128, tile: 32}
        worktile:
          invariant:
            S_init: {shape: [dk: 128, dv: 32], dtype: fp32}
          iteration:
            G:
              shape: [chunk: 1, token: 64]
              dtype: fp32
              direction: ascending
            K:
              shape: [chunk: 1, token: 64, dk: 128]
              dtype: bf16
              direction: ascending
            W:
              shape: [chunk: 1, token: 64, dk: 128]
              dtype: bf16
              direction: ascending
            U:
              shape: [chunk: 1, token: 64, dv: 32]
              dtype: bf16
              direction: ascending
        target:
          single_tile:
            S_bar: {shape: [chunk: NT, dk: 128, dv: 32], dtype: bf16}
            R_bar: {shape: [chunk: NT, token: 64, dv: 32], dtype: bf16}
            S_final: {shape: [dk: 128, dv: 32], dtype: fp32}

      mapping: *single_tile_mapping

      schedule:
        worktile_order:
          - {by: batch, direction: ascending}
          - {by: head, direction: ascending}
          - {by: dv, direction: ascending}
        worker_assignment: *single_tile_assignment

    output:
      describe: Form output from state snapshots and chunk-local corrections.

      decomposition:
        partition:
          batch: {size: B, tile: 1}
          head: {size: 8, tile: 1}
          chunk: {size: NT, tile: 1}
          dv: {size: 128, tile: 64}
        worktile:
          invariant:
            G: {shape: [token: 64], dtype: fp32}
            R_bar: {shape: [token: 64, dv: 64], dtype: bf16}
          iteration:
            Q:
              shape: [token: 64, dk: 64]
              dtype: bf16
              direction: ascending
            K:
              shape: [token: 64, dk: 64]
              dtype: bf16
              direction: ascending
            S_bar:
              shape: [dk: 64, dv: 64]
              dtype: bf16
              direction: ascending
        target:
          single_tile:
            o: {shape: [token: 64, dv: 64], dtype: bf16}

      mapping: *single_tile_mapping

      schedule:
        worktile_order:
          - {by: batch, direction: ascending}
          - {by: head, direction: ascending}
          - {by: chunk, direction: ascending}
          - {by: dv, direction: ascending}
        worker_assignment: *single_tile_assignment
```

output 的 dv 列块编号为 r 时，其需求区域为 `[64r, 64r+64)`，对应 advance 的两个列块 `2r` 和 `2r+1`。这一对应来自同一数学值的 dv 索引关系，不是由两个 shape 猜测，也不额外产生一次数学合并。

`start_after: advance.kernel_done` 仍要求 advance 全部完成后才启动 output。本例没有改成逐 chunk 或逐列块提前消费。

本例有五个 phase 定义、各一次调用和五个主要计算 launch。T 初始化是显式记录的存储准备要求；未经事件检查，不据此断言整个包装函数只有五次 GPU 活动。

**Case 3：Split-K GEMM，独立合并**

本例是 **B200 设计候选**。组织参考为：

`NVIDIA/cutlass@v4.3.3:include/cutlass/gemm/device/gemm_splitk_parallel.h::GemmSplitKParallel`

该入口采用部分 GEMM 写入 workspace、随后提交独立 reduction 的组织。这里没有确认一份与下述尺寸、tile 和单 CTA 配置完全匹配的 SM100 现成实现，不将该候选声称为已复现实现。

实现目标为 CUDA C++17、CUDA Toolkit 12.9.1，参考库版本固定为 CUTLASS v4.3.3。

只读数学输入为 BF16 A，shape 为 `[m: 512, k: 16384]`；BF16 B，shape 为 `[k: 16384, n: 512]`。上游 P 是按 split 区分的 FP32 部分乘积，最终 D 为 BF16。上游方法引用 `merge_split` 表示按 split 升序以 FP32 合并，再窄化为 D；没有额外加数、激活或原子累加。

本例只选择独立 reduction，不混入最后到达 CTA 合并或其他组织。

```yaml
work_schedule:
  thesis: Compute independent K splits into FP32 workspace, then merge into BF16 output.

  flow:
    launch:
      - phase: [partial]
      - phase: [merge]
        start_after: partial.kernel_done

    handoff:
      P:
        producer: partial
        consumer: [merge]
        storage: global

  phase:
    partial:
      describe: Compute one partial product for one output region and one K split.

      decomposition:
        strategy: "Restrict k to [2048 * split, 2048 * (split + 1))."
        partition:
          m: {size: 512, tile: 128}
          n: {size: 512, tile: 128}
          split: {size: 8, tile: 1}
        worktile:
          iteration:
            A:
              shape: [m: 128, k: 64]
              dtype: bf16
              direction: ascending
            B:
              shape: [k: 64, n: 128]
              dtype: bf16
              direction: ascending
        target:
          single_tile:
            P: {shape: [m: 128, n: 128], dtype: fp32}

      mapping: &single_tile_mapping
        worker: {unit: CTA, count: 1}
        count: worktile_count

      schedule:
        worktile_order:
          - {by: split, direction: ascending}
          - {by: m, direction: ascending}
          - {by: n, direction: ascending}
        worker_assignment: &single_tile_assignment
          preassigned: {start: worker_id, count: 1}
          refill: none
          exit: assigned_done

    merge:
      describe: Reduce all eight split contributions into each final output region.

      decomposition:
        partition:
          m: {size: 512, tile: 32}
          n: {size: 512, tile: 128}
        worktile:
          iteration:
            P:
              shape: [split: 1, m: 32, n: 128]
              dtype: fp32
              direction: ascending
        target:
          single_tile:
            D: {shape: [m: 32, n: 128], dtype: bf16}
          tile_reduction:
            dimension: split
            input: P
            output: D
            method: merge_split

      mapping: *single_tile_mapping

      schedule:
        worktile_order:
          - {by: m, direction: ascending}
          - {by: n, direction: ascending}
        worker_assignment: *single_tile_assignment
```

每份 merge 工作消费其输出区域对应的全部八份 split 贡献。partial 的一个 128×128 区域可以供四份不同 m 子区域的 merge 工作消费，但 P 本身只生产一次。

workspace 的逻辑大小由 P 的 split 维度及完整 m/n 范围确定，为 `8 × 512 × 512` 个 FP32 元素，即 8 MiB。它由 partial 完整写入，不要求预先清零；在相关 merge 消费结束前不能覆盖。

本例的两个 phase 各调用一次，提交两个计算 kernel。合并计算只在 merge 的工作和 `tile_reduction` 中登记，没有另一份隐式执行。

**Case 4：双 GEMM，同一 worker 逐 worktile 接续**

本例是 **B200 设计候选**，用于检验同 kernel、同 worker 的局部接续。结构参考为：

`NVIDIA/cutlass@v4.3.3:examples/13_two_tensor_op_fusion/README.md`

该资料说明同一 threadblock 接续两个 GEMM、在局部存储中交接中间结果的结构与区域约束。它不是下述 SM100 持久化配置的验证依据。

实现目标为 CUDA C++17、CUDA Toolkit 12.9.1。上游定义两个 GEMM：X 与 W1 产生 H，H 与 W2 产生 Y。两次 GEMM 均以 FP32 累加，H 和 Y 按上游规则窄化为 BF16。

| 只读输入或资源接口 | 内容 |
| --- | --- |
| X | BF16，`[row: 65536, input_feature: 128]` |
| W1 | BF16，`[input_feature: 128, hidden_feature: 128]` |
| W2 | BF16，`[hidden_feature: 128, output_feature: 128]` |
| H、Y | 上游分别定义的中间结果与最终输出 |
| `tile_pipeline.resource.hidden_tile` | 本例 tile_pipeline 提供的 worker 独占共享内存资源，容纳一份 H worktile，单槽 |

本区决定逐 worktile 接续，并要求使用该单槽资源。资源内部布局、lane 合作和具体读写动作不在本区展开。

```yaml
work_schedule:
  thesis: Keep H in one worker-local shared-memory tile and finish both GEMMs before advancing.

  flow:
    launch:
      - phase: [project, mix]
        worker: same
        order: per_worktile

    handoff:
      H:
        producer: project
        consumer: [mix]
        storage: tile_pipeline.resource.hidden_tile

  phase:
    project:
      describe: Compute the first GEMM and produce BF16 H.

      decomposition:
        partition: &row_partition
          row: {size: 65536, tile: 128}
        worktile:
          iteration:
            X:
              shape: [row: 128, input_feature: 64]
              dtype: bf16
              direction: ascending
            W1:
              shape: [input_feature: 64, hidden_feature: 128]
              dtype: bf16
              direction: ascending
        target:
          single_tile:
            H: {shape: [row: 128, hidden_feature: 128], dtype: bf16}

      mapping: &persistent_mapping
        worker: {unit: CTA, count: 1}
        count: 128

      schedule: &persistent_schedule
        worktile_order:
          - {by: row, direction: ascending}
        worker_assignment:
          preassigned: {start: worker_id, step: worker_count}
          refill: none
          exit: assigned_done

    mix:
      describe: Compute the second GEMM from H and produce BF16 Y.

      decomposition:
        partition: *row_partition
        worktile:
          iteration:
            H:
              shape: [row: 128, hidden_feature: 64]
              dtype: bf16
              direction: ascending
            W2:
              shape: [hidden_feature: 64, output_feature: 128]
              dtype: bf16
              direction: ascending
        target:
          single_tile:
            Y: {shape: [row: 128, output_feature: 128], dtype: bf16}

      mapping: *persistent_mapping
      schedule: *persistent_schedule
```

对编号为 w 的 worker，执行组织为：

```text
project(w), mix(w),
project(w + 128), mix(w + 128),
project(w + 256), mix(w + 256),
project(w + 384), mix(w + 384)
```

不同 worker 不因此互相等待。当前 mix 对 H 的使用结束后，才进入下一份 project，单槽 H 因而具有明确的覆盖边界。

把 `order` 改成 `per_worker` 会改变中间结果的存续需求，不能视为等价改名。保留两个 phase 也不要求它们必须拆成两个 kernel。

本例有两个 phase 定义、各一次完整工作集合调用、一个计算 launch 和 128 个实际 worker。每个 phase 各包含 512 份 worktile，不能把逐 worktile 接续计成 512 次 phase 调用。

**Case 5：Split-K GEMM，PDL 提前启动合并**

本例是独立的 **B200 设计候选**，实现目标为 CUDA C++17、CUDA Toolkit 12.9.1，参考 CUTLASS v4.3.3。

固定代码参考为：

`NVIDIA/cutlass@v4.3.3:include/cutlass/arch/grid_dependency_control.h`

该入口包含 SM100 的 GDC/PDL 支持。协议语义依据 NVIDIA《CUDA C++ Programming Guide》12.9.1 的“Programmatic Dependent Launch”一节；本例没有声称参考库中的 parallel Split-K 实现已经采用下述组织。

只读数学输入为 BF16 A，shape 为 `[m: 512, k: 16384]`；BF16 B，shape 为 `[k: 16384, n: 512]`。P 是 FP32 部分乘积，D 为 BF16。上游 `merge_split` 定义 split 升序的 FP32 合并和最终窄化，没有额外加数或激活。

本例需要 tile_pipeline 提供以下里程碑接口：

| 里程碑 | 本例要求 |
| --- | --- |
| `partial.launch_ready` | 各 partial worker 在进入 K 循环前提供 PDL 启动许可；引用表示满足协议条件的整个前驱 grid 事件 |
| `partial.kernel_done` | partial 所属 kernel 完成，并满足依赖结果的可见性要求 |
| `merge.use_P` | merge 第一次可能读取 P 的位置；此前仅允许输入无关的准备工作 |

PDL 允许后继提前开始独立准备，但启动许可不代表 P 已经可读。本例在 `use_P` 处等待完整前驱 kernel 的依赖同步；它不是按某个输出 tile 的八份 partial 是否就绪来单独放行。物理 overlap 也不是正确性前提。

```yaml
work_schedule:
  thesis: Allow merge preparation before partial finishes, but wait for the full producer kernel before reading P.

  flow:
    launch:
      - phase: [partial]
      - phase: [merge]
        start_after: partial.launch_ready
        protocol: pdl

    handoff:
      P:
        producer: partial
        consumer: [merge]
        storage: global
        ready: partial.kernel_done
        wait_at: merge.use_P

  phase:
    partial:
      describe: Compute one partial product for one output region and one K split.

      decomposition:
        strategy: "Restrict k to [2048 * split, 2048 * (split + 1))."
        partition:
          m: {size: 512, tile: 128}
          n: {size: 512, tile: 128}
          split: {size: 8, tile: 1}
        worktile:
          iteration:
            A:
              shape: [m: 128, k: 64]
              dtype: bf16
              direction: ascending
            B:
              shape: [k: 64, n: 128]
              dtype: bf16
              direction: ascending
        target:
          single_tile:
            P: {shape: [m: 128, n: 128], dtype: fp32}

      mapping: &single_tile_mapping
        worker: {unit: CTA, count: 1}
        count: worktile_count

      schedule:
        worktile_order:
          - {by: split, direction: ascending}
          - {by: m, direction: ascending}
          - {by: n, direction: ascending}
        worker_assignment: &single_tile_assignment
          preassigned: {start: worker_id, count: 1}
          refill: none
          exit: assigned_done

    merge:
      describe: Reduce all eight split contributions into each final output region.

      decomposition:
        partition:
          m: {size: 512, tile: 32}
          n: {size: 512, tile: 128}
        worktile:
          iteration:
            P:
              shape: [split: 1, m: 32, n: 128]
              dtype: fp32
              direction: ascending
        target:
          single_tile:
            D: {shape: [m: 32, n: 128], dtype: bf16}
          tile_reduction:
            dimension: split
            input: P
            output: D
            method: merge_split

      mapping: *single_tile_mapping

      schedule:
        worktile_order:
          - {by: m, direction: ascending}
          - {by: n, direction: ascending}
        worker_assignment: *single_tile_assignment
```

这里仍然是两个计算 kernel、两批新 worker。`protocol: pdl` 要求前驱和后继建立相应的同 stream 程序化依赖关系，并在 `merge.use_P` 满足对应的数据同步；不能把它实现成没有依赖同步的普通并发提交。

`start_after` 记录启动许可，`ready / wait_at` 记录数据等待，二者不是重复字段。与普通完整完成后启动的组织相比，变化的是等待位置，不是部分乘积的数学定义、合并执行者或 workspace 的覆盖范围。
