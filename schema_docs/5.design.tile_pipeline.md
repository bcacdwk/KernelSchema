# 微流水线

## 核心思想

root 的 `Tile_pipeline` 本地定义；其他设计可以按[Design 整区引用](0.common.md#design-整区引用)写为 `{from: <设计ID>}`。下文约束本地或展开后的完整区域；共享 role、存储、动作及事件须与使用节点当前的 Work_schedule、launch、handoff 和数学值闭合。

`Tile_pipeline` 在已经确定的 worktile 和 worker 内，描述执行角色怎样推进计算、交接数据和复用资源。它接收 `Math_reshape` 给出的值、精度、初值及物化决定，接收 `Work_schedule` 给出的工作归属、执行成员、工作序列与跨 step 关系，再将这些设计转化为 Coder 必须保持的局部执行约束。

本区的基本对象是 **role**。一个 role 是承担一类动作的一组执行单元，在 NVIDIA 上是一个或几个 warp；它不是单个线程，也不一定独占某个硬件引擎。例如，矩阵乘 role 可以只是负责发射异步矩阵乘的一个 warp，矩阵乘本身在 Tensor Core 上执行。执行单元的名称取自 `CONTRACT.Hardware_specification.Execution`，其他设备使用各自登记的单元（如 MI355X 的 `wavefront`、昇腾 950 的 `aic` 与 `aiv`）。

本区保留四类信息：

| 信息       | 回答的问题                                               |
| ---------- | -------------------------------------------------------- |
| 角色与动作 | 哪些执行单元承担什么动作，各自怎样推进                   |
| 索引与控制 | 动作属于哪份工作、哪次局部迭代，在什么条件下存在         |
| 依赖与同步 | 消费者何时可以继续，哪些结果可以提前使用                 |
| 资源与复用 | 值放在哪一级存储、开几个槽，哪些值共用存储，何时可以覆盖 |

动作采用设计级粒度，而非源码调用级粒度。两个连续动作之间，只有出现重要的数据发布、统计量捕获、资源归还、执行角色切换、独立循环或重叠机会，才值得拆开；没有这些边界的内部初始化、转换与计算合成一个动作。

### 设计着眼点

上游已经定下算什么、一份工作多大、由谁来做；本区决定这份工作在 worker 内怎样流动。存在稳定重复段时，先明确每轮的工作，再估计稳态下相邻两轮开始的间隔（pace）。最忙硬件资源的每轮耗时给出其下界；递推依赖、同步和无法重叠的工作可能进一步拉长周期。先比较 Tensor Core、MUFU 与 FMA、搬运与访存、发射等资源的负载，再沿依赖检查可重叠的部分。

| 问题                   | 要看什么                                                                                                             | 落在哪里                                                                               |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| pace 卡在哪一环        | 重复段中各硬件资源各要忙多久，依赖链或同步是否使周期超过资源下界；能否把一部分工作挪到空闲的单元上                   | `Thesis`；pipe 中循环体内的动作，以及 `describe` 中的负载分摊                      |
| 谁和谁重叠             | 同一 role 的异步推进或不同 role 的独立推进，能否在既定依赖下形成有价值的重叠；拆分角色还会增加成员、寄存器与交接需求 | 各 noun 的 `execution_mode`、`Waiting`，以及 role 的划分、`Member`、`Register` |
| 缓冲开多深、放在哪一级 | 生产者要领先几轮才能盖住延迟；加深换来延迟容忍，付出片上容量和每个 SM 能驻留的 worker 数                             | `Storage` 的 `location / depth / shape / total_size`，`Released` 边的距离        |
| 结果多早交出           | 消费者等的是整块还是其中一部分；分段发布让下游提前开始，代价是多一次同步                                             | 动作的切分，`Prepared` 边                                                            |
| 跨工作是否排空         | 持久 worker 的缓冲、状态和在途操作能否直接接续到下一份工作                                                           | `worktile` 与连续序号域，跨工作的边                                                  |

## 字段定义

### 结构轮廓

下面是字段结构。`<name>` 表示实例名称，`?` 表示条件可省略。

```text
Tile_pipeline
├─ Thesis
└─ Step
   └─ <step_id>
      ├─ Index?
      │  └─ <index_name>: meaning / definition
      ├─ Event?: <event_name>
      ├─ Storage?
      │  └─ <storage_id>: meaning / depth / location / shape / dtype / total_size / member? / view?
      │     └─ view.<value>: slot_index? / region?
      └─ Role
         └─ <role_id>
            ├─ Info: Describe / Member / Register? / Using_verb
            │  └─ Using_verb.<verb>.<noun>: execution_mode / describe
            ├─ Pipe: 有序列表（动作字符串、for、if）
            └─ Waiting?: Prepared? / Released? / Allowed?
```

### 主体字段

step 的提交与接续由 `Work_schedule.Flow.Launch` 及其 `order` 确定；动作和等待由各角色的 `Pipe`、`Waiting` 及上游工作组织共同决定。下表路径均相对于 `Tile_pipeline`：

| 字段路径                     | 值的形式                       | 填写条件                                   | 含义与约束                                                                             |
| ---------------------------- | ------------------------------ | ------------------------------------------ | -------------------------------------------------------------------------------------- |
| `Thesis`                   | 非空英文字符串                 | 必填                                       | 说明局部执行的关键取舍、依据与代价；采用流水重叠时，说明主要限制及打算重叠的工作 |
| `Step`                    | 非空具名映射                   | 必填                                       | 键与 `Work_schedule.Step` 一一对应                                                  |
| `Step.<step_id>.Role`    | 非空具名映射                   | 必填                                       | 执行角色，见[Role 字段](#role-字段)                                                     |
| `Step.<step_id>.Storage` | 存储区域具名映射               | 有影响容量、存续或复用的片上区域时填写     | 该 worker 的片上存储账，见[片上存储](#片上存储)                                         |
| `Step.<step_id>.Index`   | 有序索引具名映射               | 索引需共同引用，或需要具名工作序列时填写   | 定义身份、范围和顺序，见[索引](#索引)                                                   |
| `Step.<step_id>.Event`   | 具名映射，值为非空事件引用列表 | 跨 step 需要点名本 step 的局部事件时填写 | 已有事件集合的别名，见[跨 step 交接](#跨-step-交接)                                   |

### Role 字段

单个协作 CTA 可以只有一个 role，没有 `Index`、`Waiting` 和专职异步角色。没有独立执行角色时，不把一段协作计算拆成虚构的 LOAD、COMPUTE 或 EPILOGUE role。

下表路径相对于 `Tile_pipeline.Step.<step_id>.Role.<role_id>`：

| 字段路径            | 值的形式         | 填写条件                               | 含义与约束                                                               |
| ------------------- | ---------------- | -------------------------------------- | ------------------------------------------------------------------------ |
| `Info.Describe`   | 非空英文字符串   | 必填                                   | 一句概括这个角色的总体职责                                               |
| `Info.Member`     | 成员选择字符串   | 必填                                   | 这个角色占用的执行单元，例如 `warp[0:4]`、`cta[0].warp[12:13]`       |
| `Info.Register`   | 正整数           | 设计为不同角色设定不同寄存器预算时填写 | 每线程寄存器数                                                           |
| `Info.Using_verb` | 基础动词具名映射 | 必填                                   | 本 role 使用的全部动作族，见[基础动词与动作声明](#基础动词与动作声明)     |
| `Pipe`            | 非空有序列表     | 必填                                   | 动作发起顺序与控制结构，见[Pipe：有序列表与控制流](#pipe有序列表与控制流) |
| `Waiting`         | 依赖分类映射     | 存在默认依赖之外的前驱时填写           | 见[依赖](#依赖)                                                           |

`Info.Member` 给出该角色的执行单元范围；省略首段 worker 单元时，该 role 在 worker 的每个成员上各有一份。各 role 成员的并集仅统计 worker 内承担已登记动作的执行者（不另设计数，也不为闲置执行单元虚构 role），不能据此推导实际 launch 规模或整体资源成本——例如双 CTA 方案的 role 并集在两个成员上分别只有 11、10 个 warp，而每 CTA 实际启动 12 个 warp。未由成员并集覆盖、但影响驻留或同步的实际启动规模与资源分配条件由 [`REALIZATION`](6.realization.md) 交接。

例如，上游已确定一个 CTA 从契约输入 `x` 协作计算并写出输出 `y`，内部没有需要单独表达的发布或复用边界，该 step 的 role 可以只有：

```yaml
Role:
  MAIN:
    Info:
      Describe: Compute the output y cooperatively
      Member: warp[0:4]
      Using_verb:
        compute: {y: {execution_mode: serial, describe: Compute y from contract input x by the upstream definition and write the output}}
    Pipe:
      - compute:y
```

切出一个 role 的典型理由是让异步发射不必等待同一角色的同步计算，或让不同角色的计算与等待有机会重叠；是否有效还要看依赖和资源争用。`Register` 记录各角色的寄存器预算；在既定总预算内重分配时，计算角色增加的部分需要由其他角色让出，总预算改变则须重新核对驻留。

#### 基础动词与动作声明

动作由一个基础动词和一个 noun 组成，写成：

```text
verb:noun
verb:noun(index)
matmul:a(index)@b(index)
```

基础动词是封闭的八个，分四类二分：

| 类别     | 动作词      | 含义                                                     | `done` 保证                                                      |
| -------- | ----------- | -------------------------------------------------------- | ------------------------------------------------------------------ |
| 数值计算 | `compute` | 按上游定义执行逐元素、归约、转换等非矩阵乘类运算         | 指定结果可供声明的消费者使用                                       |
| 数值计算 | `matmul`  | 执行上游定义的矩阵乘法及其累加；公式与数值路径由上游确定 | 指定矩阵结果可供声明的消费者使用                                   |
| 搬运访存 | `load`    | 从绑定的源读取既有值到指定目标                           | 本次源读取结束，目标数据可用；不自动归还源使用权                   |
| 搬运访存 | `store`   | 把已有值写入绑定的目标                                   | 目标写入完成，并满足声明的消费者所需的可见性                       |
| 顺序同步 | `await`   | 等待其他参与者的已声明通知条件，可涉及多个通知           | 声明的条件及其交接保证已满足                                       |
| 顺序同步 | `signal`  | 向声明的参与者发出指定含义的通知                         | 本方通知义务完成，不表示对方已经继续                               |
| 资源占用 | `acquire` | 取得指定资源本次使用所需的资格                           | 已实际取得使用资格，仅发出请求不算完成                             |
| 资源占用 | `release` | 归还本参与者对指定资源或区域的使用权                     | 本参与者已结束该部分使用；不代表所有参与者完成，也不必物理销毁资源 |

四组对照分别表达非矩阵／矩阵、读取／存储、等待／通知、申请／释放，便于辨认主要作用；数据变化、通知协议与使用资格各有明确归属。具体算法由上游数学定义与动作组合表达，词表只规定基本作用。各平台提供对应能力（NVIDIA PTX 的矩阵、访存与同步指令族，AMD 的 MFMA 与 WMMA，昇腾 Ascend C 的 `Mmad`、`DataCopy`、`SetFlag/WaitFlag`、`AllocTensor/FreeTensor`）；`matmul` 的含义来自上游数学，不绑定某个平台的线程组织、布局或完成方式。

源、目标、访问区域、资源及参与者须能从上游定义和本动作的 `describe` 唯一确定，不能靠词名猜方向。普通读写与结果落位可以包含在计算中；有独立搬运、通知或使用权交接边界时，再拆成相应动作组合。

以下几点容易在选词时出错：

- 「形成值并让其他 role 可读」按实际内容归入 `compute`（算出来并可读）或 `store`（已有值的纯发布写入），不另设发布动词；可见性由该动作的 done 保证承担。
- 「计算并写到物化位置」归入 `compute`；只有当写出本身构成独立的交接或归还边界时，才拆成 `compute` 与 `store` 两个动作。
- 「累加器置零」归入 `compute`，并在 `describe` 中写明它不读输入、不读旧值。
- 多播搬运用 `load`，在 `describe` 中列出目标及完成范围；barrier 的 arrive/wait 用 `signal`/`await`；融合在计算内的 shuffle 不单列动作，独立的重排用 `load`/`store`，swizzle 属于布局实现。
- 搬运的完成协议（如事务字节计数的预告）纳入该搬运动作的完成保证，不单独作为一个 `signal` 动作。
- `store` 的 `done` 要求目标写入完成并满足可见性，「已发射且源已读完」不算 `store` 完成；需要表达源使用权归还早于目标写入完成时，组合 `store` 与有明确原语依据的 `release`，两者不能互相替代。

##### `Using_verb` 与 noun

每个 role 在 `Info.Using_verb.<verb>.<noun>` 登记自己使用的动作族：

```yaml
Info:
  Describe: Compute softmax row statistics and exponentials
  Member: warp[0:4]
  Using_verb:
    compute:
      row_max: {execution_mode: serial, describe: Row maximum of scores(i)}
      exp_value: {execution_mode: serial, describe: Unrounded exponentials from scores(i) and row_max(i) by the softmax formula}
      row_sum: {execution_mode: serial, describe: Sum unrounded exp_value(i) over keys}
Pipe:
  - for(i):
      - compute:row_max(i)
      - compute:exp_value(i)
      - compute:row_sum(i)
```

- `Using_verb` 必填，键只能来自上表的八个基础动词，动词下直接列 noun（每个条目仅含必填的 `execution_mode` 与 `describe`，不接受 `{}`）。它是**精确白名单**：本 role 的 `Pipe`（含空域和未执行分支）中每个动作都必须唯一匹配一个已声明的 `(verb, noun)`，未在 `Pipe` 中出现的动作族不登记；`Waiting` 与 `Event` 引用也须匹配目标 role 已声明的动作族及参数个数。
- 声明键只写基名，如 `p`、`fragment`；实参写在 pipe 和 `Waiting` 中。矩阵乘采用操作数表达时，整个 `a@b` 是一个键，使用处写 `matmul:a(i)@b(j)`，不为 a、b 再建登记层，`describe` 须交代两个操作数及结果。

noun 是这个 role 作用域里的对象名称，不是全局数学值或物理分配的登记。不同 role、不同 verb 可以使用同名 noun；`compute:p` 与 `store:p` 各有自己的模式和说明。同名只有在描述的对象、版本及范围一致时才指同一个东西，不能仅靠拼写认定。

- 同一 `(role, verb, noun)` 基名只允许一种固定参数个数；复合动作分别检查各操作数。`p` 与 `p(i)` 不在同一动作族中混用，不按参数数量或常量索引重载。
- `a(i)@b(j)` 是否允许、是否要求 `i=j`，由实际数学与索引关系决定，不能从声明键推导。声明不建立循环域、不生成动作，也不改变索引作用域。
- 动作实例由 step、worker 实例、成员、role、verb、noun 及实际参数共同确定，展开后必须唯一。重复动作要带足够的真实轮次、版本或区域索引；不能靠源码行、控制块位置或未声明的阶段区分同名事件。

##### `describe` 要说明什么

`describe` 说明动作与数学对象的对应及职责。上游已定义的公式、精度和参数范围直接按对象名或步骤名引用；以下事实不能由上游、基本动作或已声明关系唯一确定时，在本条目补明：

- **跨动作的输入**：本动作读取的每个值，连同它的版本／区域／副本，以及来源动作和成员。入口值和跨 step 输入注明对应来源。本 role 自己的异步产物和控制条件同样要列。
- **存储绑定**：读写已登记存储时点名对应的 `Storage` 及其 `view`（若有）。`view` 只定位值及版本所用的区域，`describe` 绑定本次访问。同一个 p 既在 TMEM 又在寄存器时，各动作须明确使用哪个区域。
- **原语保证**：所依赖的完成或可见性保证本身及其适用范围；提供它的原语由 `REALIZATION` 绑定。
- **协议与资源含义**：通知或使用资格的含义、对象和参与范围；涉及存储时绑定具体区域。

`describe` 不改写上游的公式、精度或物化决定，也不复述上游已经写下的遍历方向、成员切分或数学公式。上游以 `bind:DESIGN.Tile_pipeline::<name>` 交给本区的参数，写在决定它的那个动作的 `describe` 里，并使用同一个名称。

数值类型与转换沿用当前 Design 实际采用的值定义，输入输出沿用 Contract。必要的本地对象由创建或处理它的动作在对应 noun 的 `describe` 中说明；必要的存放格式与 metadata / packing 约定在该说明或 `REALIZATION` 绑定中定义一次，所有使用者一致引用。

下表帮助定位不同名字；数学符号是否登记仍按 DOC3 的判据，本地对象不因跨动作使用就自动成为新的数学符号：

| 名称的用途 | 定义与引用位置 |
| --- | --- |
| 已作为下游数值接口的 `s(t)`、`scores(i)` | 沿用 [Math_reshape 的接口定义](3.design.math_reshape.md#符号属性)及其属性，动作引用所用版本 |
| 工作坐标 `b,c`、循环长度 `iteration_count(b)` | 来自已定义的数学映射或 Work_schedule 关系；动作说明实际读取或恢复方式，不由 `Index` 声明执行查询 |
| 动作内的地址、判定副本或 packing 对象 | 由建立它的动作说明含义、来源及使用者；其他动作或 role 使用时，沿用同一定义并核对就绪 |
| `state_rows` 这样的存储区域 | 在 `Storage` 登记容量与存续，必要时由 `view` 将 `s(t)` 绑定到区域；普通标量临时量不逐项列账 |

例如，上游已定义 `scores(i) = mm32(q, k(i)ᵀ)` 及其 shape、dtype，输入与结果的存储分别登记为 `q_slot`、`k_slot`、`score_slot`；当前由同一 CTA 内的一个 role 同步协作计算。只展开动作声明：

```yaml
matmul: {scores: {execution_mode: serial, describe: Read q in q_slot and k(i) in k_slot into scores(i) in score_slot; done covers participating warps' reads and result visibility within this role}}
```

`scores` 同时作为这个动作的 noun，`score_slot` 则是另行登记的存储区域。同步协作的内部归约与线程同步无须逐项拆开；所依赖的保证仍须由实现提供。`matmul` 不承诺一条矩阵硬件指令，也不由此改变上游选定的乘法精度。

noun 的命名自由不能改变基础 verb 的性质或降低它的 done 保证。`describe` 也不能代替已命名动作之间的必要等待：需要独立引用的部分完成、使用权归还或通知边界，仍使用基础动作与 `Waiting` 表达。

动作保留合理的原语粒度：本 role 内部计算、原语自身的完成或可见性保证，以及实现原语的线程协作，不必逐项拆成 role 或边。实际等待图中另一 role 已命名动作的事件，且不能由默认依赖或其他已声明关系推出时，须用 `Waiting` 显式表达；不能仅以 `describe` 中的「内部条件分支」加入、取消或移动该前驱。条件改变等待位置用 `if`；不同方案按[设计划分原则](0.common.md#参数变化与结构变化)选择记录深度，完整节点仍须表达其实际依赖。

#### 执行模式

每个动作有两个事件：`issue` 表示已经发射或开始执行，`done` 表示它承诺的完成条件已经得到保证。`done` 是设计可以依赖的保证，不是测得的硬件时间戳；几个动作可以共享一次完成通知，只要这次通知确实覆盖它们。

所有动作按 pipe 顺序 `issue`。`execution_mode` 约束的是**完成**与后续发起的关系，它声明在 noun 条目上，作用于同一 step、worker 实例、成员、role 的实际动作序列：

| 模式                | 推进与完成保证                                                                                                |
| ------------------- | ------------------------------------------------------------------------------------------------------------- |
| `serial`          | 自身 `done` 之后，才能发起后续动作；不自动排空此前其他异步动作                                              |
| `async_unordered` | 按 pipe 顺序发起，后续动作不必等自身 `done`；不提供动作之间的完成顺序                                       |
| `async_ordered`   | 按 pipe 顺序发起并允许重叠；采用该模式的动作按发起顺序累积完成，后一个 `done` 覆盖该序列此前动作的 `done` |

这里的成员是 `Mapping.Worker.unit` 成员，见[事件引用](#事件引用)。一个 CTA worker 中，`Member: warp[0:4]` 是同一 role 在该 CTA 内的四个协作 warp，`ROLE[*]` 不会为它们分别建立事件。动作内部跨 warp 的完成与可见性由动作保证及实现承担；`serial` 只在该保证成立后推进，不自动提供 CTA 屏障。

`async_ordered` 中的 ordered **只指 `done` 的累积覆盖**，不指发起顺序——两种异步模式的发起顺序都由 pipe 列表决定。累积完成**跨 noun、跨 verb**，并跨循环与 worktile 接续；中间的 `serial` 动作不重置该序列，其他 `async_unordered` 动作不被纳入。不能为每个 noun 暗中建立一条独立的完成队列。

只有原语确实提供上述共同保证时才采用 `async_ordered`。**两个引擎各自有序不等于共同有序**：同一 role 中若存在互不覆盖的完成机制，使用 `async_unordered`，并通过 `Waiting` 表达需要的先后。完成依据本身不足时按[缺项规则](../schema_template/README.md#1-确认资料与范围)处理，不靠改模式或补等待假定已有实现提供了保证。累积完成本身不提供操作数就绪、别名覆盖安全或提前归还源缓冲的保证。

role 级与 verb 级不设默认或继承模式，noun 条目的模式适用于其全部实例。例如 a、b、c 依次发起，a 与 c 为 `async_ordered`、b 为 `async_unordered`，等待 c 的 `done` 同时覆盖 a 的 `done`，但不覆盖 b 的 `done`。

异步 role 中声明为 `serial` 的动作是同步例外：在 pipe 所在位置发起，完成后该 role 才继续，此前已发起的其他异步动作可继续在途；它等待什么由自身 `describe` 和前驱决定，不默认排空在途异步动作。事件只有 `issue` 与 `done`（不设 `@begin` 或 `@read`），例如归还已读完源槽而全局写入仍在途时：

```yaml
Using_verb:
  store: {o: {execution_mode: async_unordered, describe: Issue a bulk store of the o slot to global memory}}
  release: {o_slot: {execution_mode: serial, describe: Return o_slot after the store has read o}}
```

特定原语的顺序保证可以代替一条显式的边，例如同一 role 中先发起的矩阵乘读完一块存储之后，后发起的矩阵乘才写入它。依赖这种保证时，在 `describe` 中写明保证本身及其适用范围；不能从 `execution_mode`、同一个 role 名或同一个 noun 名推出硬件会处理冲突。

#### Pipe：有序列表与控制流

`Pipe` 记录一个 role 在其职责范围内的动作发起顺序，只采用**有序列表**和两种控制结构 `for` / `if`。

当前不支持 `while`；若未来 Agent 确需该能力，须先声明具体需求并提出 issue，讨论是否纳入规范，在此之前只使用 `for` 和 `if`。

`Pipe` 是非空有序列表。每项是一个动作字符串，或一个只有单个键的控制节点；控制节点的内容直接是同样的非空有序列表。

```yaml
Pipe:
  - load:initial
  - for(i):
      - compute:state(i)
      - store:result(i)
  - store:final
```

最外层列表描述该角色在 worker 整个生命周期内的动作：持久 worker 在最外层按 `worktile` 域循环，只处理一份工作的 worker 直接写这份工作的动作。准备和收尾直接写在循环前后，不设专用段落节点。

列表决定发起顺序；是否等待上一动作完成，由 `execution_mode`、`describe` 和依赖决定。控制节点不自动产生同步、排空、资源重置或额外事件。动作内部的线程分工和协作沿用动作声明。

##### `for`：有序遍历

| 写法                                | 含义                                        |
| ----------------------------------- | ------------------------------------------- |
| `for(i)`                        | 遍历已声明的有序域 i                        |
| `for(i[1:])`                    | 遍历该域的半开切片                          |
| `for(n[t])`、`for(n[t,1:])` | 遍历当前工作的连续序号窗口                  |
| `for(j=0:2)`                    | 局部定义半开范围 `[0,2)`，依次绑定 j=0、1 |
| `for(j=0:min(4,iteration_count))`             | 局部范围的端点使用已定义表达式              |

每次绑定一项，依次发起完整列表中的动作后再进入下一项；完成先后仍按执行模式判断。相邻两个 `for` 是先展开第一批，再展开第二批，不能任意合并成逐项交替。空域产生零项，但不删除后续动作。

`for(t)` 可以遍历上游定义的、运行时才形成的 worktile 序列。领取、确认、发布和终止票处理仍是明确动作，不由循环头代替。不能定义一个「直到成功」的伪域来隐藏局部反馈循环。

例如，上游已定义两组物化值 `u_value(u)`、`w_value(w)` 及其范围 `u_count`、`w_count`，只有后者需要 `g`。同一同步 role 先完成 u_value，再载入 g 并完成 w_value：

```yaml
Pipe:
  - for(u=0:u_count):
      - compute:u_value(u)
  - load:g
  - for(w=0:w_count):
      - compute:w_value(w)
```

一个 role 的两段独立循环写成两个相邻表项，而不是展开成固定索引的动作，也不是新建 kernel。

##### `if`：条件执行

```yaml
Pipe:
  - if(full(t) == 1):
      - release:staging(t)
      - store:output(t)
  - if(full(t) == 0):
      - store:tail(t)
```

每个 `if` 在当前位置判断一次：条件为真时执行内容，为假时不产生其中的动作。条件使用已就绪的布尔值、整数比较及 `and/or/not`；必要的读取或等待由相应动作说明，`if` 不暗中增加这些动作。

两个 `if` 没有隐式配对关系。需要互斥分支时，使用同一个在两段之间不变的判断值及其补条件；不能在第一段改变判定，再把第二个 `if` 当成只判断一次的二选一。需要保存判定时，由有明确 `describe` 的动作建立该值。

`if` 表达动作是否存在或实际的协议选择，不用 0/1 假循环代替。

##### 索引与作用域

- 循环索引只在对应内容中绑定，不泄漏到后续兄弟项。兄弟循环或不同 role 可以独立使用同名索引。
- 内层 `for` 不得重新绑定仍在作用域内的外层索引；局部 `for(j=lower:upper)` 的范围端点在外层作用域求值，新绑定的 `j` 在端点内不可见。
- 遍历 flatten 域会恢复其组成坐标。外层已有的坐标必须与恢复值一致，否则报错，不覆盖或静默筛除冲突项。例如 `for(t)` 内的 `for(n[t])` 可以恢复同一个 `t`；不能由内层 n 将 t 改成另一份工作。

循环域限制循环变量的取值，不限制数学对象的索引范围。例如，上游已定义正整数 `chunk_count`、初值 `s(-1) = s0`、逐 chunk 递推 `s(c)`，以及 `s_final = s(chunk_count-1)`：

```yaml
Pipe:
  - load:s0
  - for(c=0:chunk_count):
      - compute:s(c)
  - store:s_final
```

首轮计算读取初值 `s(-1)`，不需要一次 `c=-1` 的循环；收尾使用已定义的 `s_final`，不借用循环中 `c` 的隐含末值。反过来，一个只在非首轮执行的动作，不会因为 `y(0)` 这个数学值存在，就自动产生 `compute:y(0)`。

「动作不存在」与「动作无数据可处理」不同。空域或为假的 `if` 不产生其中的动作，不能等待这些未产生的动作；已经由 `Pipe` 产生的动作即使在当前条件下为 no-op，仍保留其 `issue / done` 与必要交接，`describe` 应写明它不读写哪些数据，不能因为没有 payload 就删除完成事件。

执行顺序来自 pipe 列表、控制结构、依赖、`describe` 中写明的原语顺序保证，以及上游的工作组织。pipe 中不扩展宏、子程序、跳转或其他控制体系。

### 索引

`Index` 在 step 中为有序索引命名，定义其身份、范围和顺序。每个 `Index.<name>` 是固定映射，`meaning / definition` 两个字段均必填：

| 字段 | 值的形式 | 含义 |
| ---- | -------- | ---- |
| `meaning` | 非空英文字符串 | 一句说明该索引表示的对象或迭代 |
| `definition` | 下表中的域定义 | 定义该索引的有序取值域 |

pipe 和索引表达式按索引名引用其取值域。`definition` 只采用以下三种形式：

| 形式                          | 含义                                                                                                     |
| ----------------------------- | -------------------------------------------------------------------------------------------------------- |
| `[lower, upper]`            | 半开整数域，依次取 `lower` 至 `upper-1`                                                              |
| `worktile`                  | 这个 worker 按处理顺序得到的全部工作，包括预分配的和运行时领取的；取值是本地序号，不是全局 worktile 编号 |
| `{flatten: [outer, inner]}` | 把已定义的有序域积按字典序连续编号，后一个域变化更快；内层范围可以随外层取值变化                         |

跨 role 或条目需要共同引用的索引，以及具名 `worktile` / `flatten` 序列，在 `Index` 中定义一次；只有一个 role 也可以使用。纯局部整数范围直接写 `for(j=0:2)`，条件使用 `if`；普通参数与判断值不登记为索引。

`Index` 定义之间不得循环依赖，`flatten` 各分量恢复的坐标须互不相同。`view` 的形参只参与版本到槽或区域的映射，局部索引作为实参不要求另建公共索引。范围端点引用已有名称，在实际遍历前须已定义并就绪；索引声明不执行读取、领取或等待。多个 role 共用同一索引定义时共享编号含义，各自按 `Pipe` 和依赖独立推进。

整数表达式沿用[公共约定](0.common.md#shape-与整数表达式)，常用 `%` 计算槽位，用 `count(d)`、`last(d)` 查询已声明且外层依赖已绑定的域（`last` 要求非空）。`Refill` 不是 `none` 时，动态 `worktile` 域及含该轴的 `flatten` 域总长在运行时由上游 `Exit` 决定，不能对它们使用 `count` 或 `last`（已绑定当前工作坐标后的有界局部域仍可查询），也不能借用循环退出后的隐含末值；运行时领取与坐标转发本身写成普通动作与依赖。

### 片上存储

`Storage` 登记 worker 内影响容量、存续或复用的片上存储区域。互不重叠的设计区域可以分列，区域如何合并申请由实现决定。下表中的路径相对于 `Storage.<storage_id>`。

| 字段           | 值的形式                 | 填写条件                                                          | 含义与约束                                                                                       |
| -------------- | ------------------------ | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `meaning`    | 非空英文字符串           | 必填                                                              | 一句说明这个存储区域的用途                                                                       |
| `depth`      | 正整数或整数表达式       | 必填                                                              | 每个持有成员的物理槽数；单槽写 1                                                                 |
| `location`   | 存储层级名称             | 必填                                                              | 沿用 `CONTRACT.Hardware_specification` 中的叫法，例如 B200 的 `smem`、`tmem`、`register` |
| `shape`      | 有序的具名维度列表       | 必填                                                              | 一个 `Worker.unit` 成员持有的一个槽的容量                                                      |
| `dtype`      | 环境中已定义的类型名     | 必填                                                              | 容量单元的类型，与 `shape` 一起确定每槽字节数及 `region` 的坐标单位                          |
| `total_size` | 字节数，整数或整数表达式 | 必填                                                              | 该区域在一个 worker 内的总占用，等于 `depth × 单槽字节数 × 持有成员数`                       |
| `member`     | 成员序号或序号列表       | 只有部分成员持有这块存储时填写                                    | 省略表示 worker 的每个成员各有一份                                                               |
| `view`       | 视图具名映射             | 值名与存储名不同、多个值共用、`depth > 1`，或需要子区约束时填写 | 见[视图](#视图)                                                                                   |

`total_size` 统一以字节记，是 `depth`、`shape`、`dtype` 和成员范围的派生值，须满足上述等式；单槽字节数为 `shape` 各维之积乘以 `dtype` 的每元素字节数。父 `dtype` 只作为容量与 `region` 的坐标单位，不规定各值的数值类型。省略 `member` 时按 worker 的全部成员计数，**不是 warp 数**。容量包含设计所依赖的有效分配粒度，`view` 不重复计量。

需要跨动作保留或支持重叠的寄存器副本同样登记；普通标量临时量、指令寄存器名和 barrier 存储不逐项列账。这份账只覆盖已登记区域：影响驻留或同步的额外预留、整块申请与释放或角色寄存器预算由 `REALIZATION` 说明；各存储层级分别核对容量，多 CTA worker 的 `total_size` 不能直接对照单 SM 容量。`register` 区域计入所属 role 的寄存器预算，不再另加一遍。缓冲深度与消费、复用依赖共同限制生产者能领先多少。

`shape` 采用上游的具名轴写法，轴名沿用上游；几种值共用的区域（如 TMEM 中分槽存放 s、p 与 y，或 k 与 v 轮流使用的环）没有统一的逻辑轴，用 `row`、`column`、`element` 这类物理轴名。它描述一个成员持有的容量，所以不一定等于上游按整个 worker 登记的块：两个 CTA 分摊一块 k 时，每个成员只持有一半。物化子集或 packing 由已有设计、动作或实现绑定说明，所需容量不一定等于完整数学值的元素数乘数值类型字节数。

这里的成员来自 `Mapping.Worker`，不是单个线程。`location: register` 的形状同样描述该成员内的逻辑值总量，不表示每个线程各有一个同形状数组。

#### 视图

`view` 将值及版本绑定到槽和占用区域，条目仅允许 `slot_index / region`。键是逻辑值名，可以带版本形参，如 `k(n)`、`s(i,d)`；基名与形参遵循[通用命名](0.common.md#通用写法)。形参只参与该映射，不声明或扩大任何循环，也不捕获 role 的当前循环变量。

| 字段           | 值的形式                 | 填写条件                                         | 含义与约束                                                                 |
| -------------- | ------------------------ | ------------------------------------------------ | -------------------------------------------------------------------------- |
| `slot_index` | 整数或整数表达式         | 父存储区域 `depth` 大于 1 时必填               | 该值的该版本所在的槽，必须落在槽数之内                                     |
| `region`     | 轴名到左闭右开范围的映射 | 设计依赖子区并存、部分数据仍存活或部分覆盖时填写 | 例如 `{column: [64, 128]}`；未列出的轴取整轴，省略以整槽作为保守占用范围 |

**`slot_index` 只写在对应的 view，不设默认推导。** 版本到槽的映射是设计选择，不能从索引名、参数位置或槽数反推。`depth` 只说明有几个槽，`Released` 边只说明何时可以覆盖，两者都不决定哪个版本落在哪个槽。`depth` 为 1 时没有可选的槽，可以省略 `slot_index`。

单槽存储与所存唯一值同名且无子区约束时可省略 `view`；需显式绑定到单槽整槽时写 `view: {x: {}}`（空对象不改变 `x` 的数值定义，无条目的 `view` 直接省略）。省略 `region` 时以整槽作为保守占用与冲突范围，不表示较小的值填满全部字节，也不允许据剩余空间推导额外并发；设计依赖子区并存、部分数据仍存活或部分覆盖时，须用 `region` 保留区域约束或分列独立的 `Storage`，不得因省略改变既定等待或重叠关系。

`slot_index` 与 `region` 的端点可以引用键上的形参及已定义量。`region` 按父存储区域的 `shape / dtype` 选出字节，数值含义来自所绑定的值定义。例如，上游已定义 128×128 的 FP32 值 `s` 和同形状的 BF16 值 `p`，它们共用一个 TMEM 槽：

```yaml
accumulator: {meaning: Shared accumulator for scores and probabilities, depth: 1, location: tmem, shape: [{row: 128}, {column: 128}],
  dtype: fp32, total_size: 65536, view: {s: {}, p: {region: {column: [64, 128]}}}}
```

p 的视图选中每行后 64 个 FP32 容量单元所占的字节，用于存放上游定义的 128 个 BF16 元素，不增加分配。这里选中的是**每行的后半段**，不是整块连续的后 32 KiB；容量相等不证明布局合法，`view` 也不执行数值转换，逻辑值形状仍来自上游。

另一个多槽示例中，上游已定义 128×128 的 FP32 值 `s(i,d)` 和同形状的 `fp8_e4m3fn` 值 `p(i)`；`stats(i)` 保存每行的最大值和未窄化指数和，形状为 128×2、类型为 FP32。存储同时使用 `slot_index` 与 `region`：

```yaml
score_probability: {meaning: 'Shared score, probability and statistics slots', depth: 2, location: tmem, shape: [{row: 128}, {column: 128}],
  dtype: fp32, total_size: 131072, view: {'s(i,d)': {slot_index: i%2}, p(i): {slot_index: i%2, region: {column: [0, 32]}}, stats(i): {slot_index: i%2, region: {column: [32, 34]}}}}
```

**共用字节的值用同一 storage 条目及其 view 表达，容量只计一次。** 覆盖前须保证该区域中旧值的全部必要读取及在途写入已经结束，由依赖或 `describe` 中写明的原语顺序提供保证；view 只声明存储关系。

新分配的存储没有旧读者，不代表内容已经清零；初值来自上游定义和对应动作，例如一个写明不读旧值的 `compute`，或由第一次矩阵乘直接初始化累加器。

### 依赖

`Waiting` 按等待的原因分三类，每类的值是**非空的 YAML 字符串列表**。没有规则的分类省略，没有任何规则时省略 `Waiting`。

| 分类         | 右侧前驱提供什么条件                                       |
| ------------ | ---------------------------------------------------------- |
| `Prepared` | 操作数、计算结果或发布已经就绪，数据可读                   |
| `Released` | 旧内容的全部必要读取已经结束，可以覆盖它的存储             |
| `Allowed`  | 前两类之外的协议放行，例如两个计算角色轮流占用同一硬件单元 |

`Released` 说的是**右侧提供**「已释放」这个条件，不表示左侧动作释放资源，也不要求前驱动词叫 `release`。三类边的约束力相同，分类只保留等待原因。分析依赖环时要合并全部分类以及默认依赖，不能只查复用或协议边；过早覆盖还须沿全部读者与新写入的关系核对。

每条规则写成一个字符串：

```yaml
Waiting:
  Prepared: ['{issue compute:y} ← [{done load:x}, {done load:z}]']
```

- 每条字符串只有一个左侧目标事件，右侧始终是非空前驱列表；单前驱也写成 `[{done a}]`。前驱只在完整事件之间用逗号分项，索引内部的逗号不分项。
- 字段值是 YAML 字符串列表；每条字符串内部的 `{}` 与 `[]` 是依赖记法，不是嵌套的 YAML 数据结构。
- 每个事件写成 `{issue 引用}` 或 `{done 引用}`，花括号同时包住时点与引用。**两端的时点必须显式写出**，不接受裸动作端点，也没有位置默认值。
- 动作引用的完整形式为 `ROLE[member]::verb:noun(indices)`；无索引动作和 `matmul:a(indices)@b(indices)` 沿用原动作记法。可以按[事件引用](#事件引用)省略当前 role，不能省略事件时点。
- `Waiting` 条目的书写顺序不表示执行顺序；同一目标事件命中多条规则或展开出多个有效前驱实例时，前驱取并集（含跨分类规则）。

每条规则表示：**右侧所有前驱先成立，左侧事件才允许成立。** 这是先后约束，不要求两个端点同时发生或紧贴，也不保证动作实际重叠。用 a 表示前驱动作、b 表示目标动作，四种组合如下：

| 规则                         | 这条边要求什么                                          |
| ---------------------------- | ------------------------------------------------------- |
| `{issue b} ← [{done a}]`  | a 的完成保证成立后，b 才能发起                          |
| `{issue b} ← [{issue a}]` | a 已发起，b 才能发起；不必等 a 完成                     |
| `{done b} ← [{done a}]`   | a 的完成保证先成立，b 的完成保证后成立；b 可以提前发起  |
| `{done b} ← [{issue a}]`  | a 已发起，b 才能给出完成保证；这条边不限定 b 的发起位置 |

交换 a、b 会改变约束，两个方向不等价；单条 `done ← done` 也不能自动证明动作内部每一片读写都安全，仍须核对分片与必要依赖。

例如，LOAD 和 COMPUTE 按共享域 `k: {meaning: Iteration shared by loading and computation, definition: [0, iteration_count]}` 推进；LOAD 执行 `load:x(k)`，COMPUTE 的 `compute:y(k)` 读取 x，并保证 done 时已经读完。x 使用两槽缓冲：

```yaml
Storage:
  x: {meaning: Buffer x for overlapping loading and computation, depth: 2, location: smem, shape: [{element: block_size}],
    dtype: fp32, total_size: 2*block_size*4, view: {x(k): {slot_index: k%2}}}
```

COMPUTE 的 `Prepared` 保证值可读：

```yaml
Prepared: ['{issue compute:y(k)} ← [{done LOAD::load:x(k)}]']
```

LOAD 的 `Released` 则保证下一次覆盖同一槽之前，旧值已经读完：

```yaml
Released: ['{issue load:x(k+2)} ← [{done COMPUTE::compute:y(k)}]']
```

这两条边分别保护读取和覆盖，不能互相替代；索引移位在边界处的处理见[依赖的索引窗口](#依赖的索引窗口)。

再如 QSA 的搬运角色：先发起下一片，才允许发布前一片的完成保证，但不要求前一片的物理复制必须晚于下一片发起：

```yaml
Allowed: ['{done load:k_block(n)} ← [{issue load:k_block(n+1)}]']
```

#### 默认的依赖

对于同一 step 内的局部动作，**唯一不写也成立的依赖是：role 内按 pipe 顺序与各动作的 `execution_mode` 推进。** 其余局部依赖都要显式写出，包括操作数就绪、矩阵乘的产物交给谁、动作读了 noun 名字里没有的值、存储何时可以覆盖、协议何时放行。跨 step 数据交接按 [Work_schedule.Flow.Handoff 的默认等待及 `ready / wait_at` 规则](4.design.work_schedule.md#交接字段)执行。

已由 role 顺序、`async_ordered` 的累积完成或其他边传递保证的前驱可以省略——省略的是可推导的重复前驱，不是必要的就绪条件。

输入与前驱按以下要求核对：

- 每个跨动作输入的版本／区域／副本、来源与成员须可唯一确定，上游与已声明关系未决的部分按 [`describe` 的要求](#describe-要说明什么)补明。
- Reviewer 先对照上游数学与 `describe` 核对输入完整性，再逐项核对从就绪到读取结束及覆盖前的安全保证；允许由执行模式、`Waiting` 的传递路径或明确绑定的原语保证覆盖，不要求每项都有直边。

工具对有限事件展开的范围见[微流水线图](../schema_template/README.md#微流水线图)，不以工具已覆盖的部分代替本节语义。

按名称引用要求写法一致：一个值分几次交出，消费者就引用它实际等待的那一部分。例如，动作声明已经定义 p 的 prefix、tail 区域，`matmul:p_prefix(k)@v(k)` 等待的是 `compute:p_prefix(k)`，不必等 tail。区域由 `describe` 定义，不从名称后缀猜测。

### 跨 step 交接

同一次提交中 `order` 不是 `concurrent` 的几个 step 由同一个 worker 实例承担：`Storage` 合成一份账，在其中一个 step 登记一次，其他 step 按名称引用。不同 worker 实例的同名存储分别实例化，片上交接按所属 worker 的对应副本匹配。

两个 role 名称不同，不代表占用不同的物理 warp：物理 warp 按 worker 实例、成员和 warp 编号识别。同一 worker 实例中不同 step 的 role 可以复用同一组 warp；同时活跃的 role 若成员重叠，必须有可实现的执行关系，不能把同一个 warp 当成两份资源。

跨 step 的交接由 [Work_schedule.Flow.Handoff](4.design.work_schedule.md#跨-step-数据交接) 登记。片上交接引用本区的 `Storage`；需要点名局部时点时，在 `Event` 中定义引用名，上游写成 `<step_id>.<event_name>`。默认交接、内建事件或已有依赖已经足够时，不重复登记别名。

`Event` 的每个条目是非空的已有动作事件引用列表。调用时展开列表：用于 `ready / start_after` 时，所有前驱都须满足；用于 `wait_at` 时，就绪约束分别施加到每个等待／申请动作（`await / acquire`）的 `done` 或消费动作（`compute / matmul / load / store`）的 `issue`。通知、可见性与初始化由实际动作及其原语保证承担。

键可以带形参，如 `snapshot_ready(c)`；引用 `snapshot_ready(k)` 时，将 `c=k` 代入列表中的事件。引用只使用这些形参和已定义参数，不捕获某个 role 的当前循环变量。

每个事件须显式写出时点、role 和成员选择，如 `{done MAIN[0]::store:x}`；`ROLE[*]` 选中该 worker 内该 role 的全部成员实例。别名沿用被引用动作的实例身份，跨 step 的 worker、工作及索引匹配遵循 handoff 的值、版本和区域关系。

被实际调用的 `Event` 展开出的事件须由 `Pipe` 实际产生。`wait_at` 可引用循环外的 worker 入口动作；工作序列为空时，这些实际存在的入口事件及其等待约束仍保留。`kernel_done` 与 `launch_ready` 是[第 4 篇的无索引内建事件](4.design.work_schedule.md#事件与启动)，这两个基名不用于本地 event；`launch_ready` 的触发位置、条件与参与范围由对应动作的 `describe` 说明。

例如，上游已定义全局物化值 `x`，`PREPARE` 与 `APPLY` 由两个保证同时驻留的 worker 并发执行，各只处理一份工作。`PREPARE` 发布 x 后还有独立收尾，`APPLY` 先做不依赖 x 的准备，再等待并读取它。工作调度中登记：

```yaml
Flow:
  Launch: [{step: [PREPARE, APPLY], order: concurrent}]
  Handoff: {x: {producer: PREPARE, consumer: [APPLY], storage: global, ready: PREPARE.x_ready, wait_at: APPLY.x_wait}}
```

两侧的同步 role `MAIN` 已有 `store:x` 与 `await:x` 动作：前者写出 x 后以 release 语义发布就绪标志，后者以 acquire 语义读取标志，观察到就绪后才完成；标志在本次提交前初始化为未就绪。本区给这两个动作的完成事件起名：

```yaml
Step:
  PREPARE:
    Event: {x_ready: ['{done MAIN[0]::store:x}']}
  APPLY:
    Event: {x_wait: ['{done MAIN[0]::await:x}']}
```

`ready` 指向发布完成，`wait_at` 指向等待完成；消费者此前的独立准备不受这条交接等待约束。

### 固定结构与扩展边界

没有内容的可选字段直接省略。`Step`、`Role`、`Pipe`、`Info.Using_verb`、`Waiting` 各分类列表与 `Event` 引用列表均须非空。

| 位置类型 | 本区位置                                                                                | 允许的变化                                                 |
| -------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 固定结构 | `Tile_pipeline`、step 条目、index 条目、storage 条目、视图条目、`Info`、noun 条目、`Waiting` | 只使用本节声明的字段                                       |
| 封闭取值 | `Index.<name>.definition` 的域形式、`Using_verb` 的键、`execution_mode`、`Waiting` 的分类键、pipe 的控制结构 | 只使用本篇列出的三种域形式、八个动词、三种模式、三个分类、两种控制结构 |
| 具名映射 | `Step`、`Index`、`Event`、`Storage`、`view`、`Role`、各动词下的 noun       | 可以增加当前设计需要的名称，条目结构不变                   |
| 开放取值 | `location` 的存储名、成员选择中的执行单元名、noun 名、index 与 storage 的 `meaning`、`Info.Describe` 及 noun 的 `describe` | 沿用硬件规格中的名称；noun 自由命名但须唯一匹配；说明按对应字段要求填写 |

增加 role、存储区域、索引、事件别名或 noun 是填写实例。新增字段、域形式、事件种类、动词或边的分类遵循[公共扩展规则](0.common.md#结构与扩展)。

## 语法规则

### 成员与名称

成员选择沿用硬件规格登记的执行单元名，写成路径加下标或半开区间：`cta[0].warp[12:13]` 表示 0 号成员中的 12 号 warp，`warp[0:4]` 表示每个成员中的 0 至 3 号 warp。成员来自上游的 worker 组成，单元编号在一个成员内从 0 计。

索引与区间端点接受非负整数或[已定义的整数表达式](0.common.md#shape-与整数表达式)，不在成员字符串中引入新定义。例如，当前方案已选 `epi=4` 时，`warp[3:3+epi]` 登记实际 epilogue 成员；已确定线程数 `thread_count` 且保证被 32 整除时，可写 `warp[0:thread_count/32]`。各端点在有效域内必须为整数，区间满足 `0 <= lower < upper`，选择不能超出对应执行单元的实际组成。

决定成员的参数须在 worker 执行前确定，在该 worker 的整个 step 中保持不变，不依赖 pipe 的循环变量或动作结果。端点来自当前选定组成或该方案的输入实例化，其他成员配置按[变体规则](0.common.md#参数变化与结构变化)记录。不能用空区间删除 role，也不能登记最大成员范围再由正文取消部分成员或事件。普通检查核对记法及已知数值关系；参数定义、整除条件与当前设计范围内的约束由审阅核实，有限图工具按显式给定的参数展开。

step、role、事件别名、存储区域、索引与 noun 按各自作用域定义和引用，通用大小写与标识符规则见[公共约定](0.common.md#通用写法)；数学值沿用上游名称，一个 step 内只有一个 role 时使用 `MAIN`。

### 事件引用

完整形式为 `ROLE[member]::verb:noun(indices)`，连同时点写成 `{done ROLE[member]::verb:noun(indices)}`。`::` 分隔角色，`@` 只保留在 `matmul:a@b` 的动作内部。省略规则如下：

| 写法                   | 解释                                                       |
| ---------------------- | ---------------------------------------------------------- |
| `verb:noun`          | 当前 role、当前 worker 成员上的动作                        |
| `ROLE::verb:noun`    | 指定 role，仍指当前 worker 成员                            |
| `ROLE[0]::verb:noun` | 该 worker 的 0 号成员上的实例；其他成员编号同理            |
| `ROLE[*]::verb:noun` | 该 role 在当前 worker 的全部成员实例，所选前驱必须全部满足 |

**省略成员下标一律指当前 worker 成员**，带 role 名也一样；当前成员上没有该 role 时，不能自动改取其他成员或全部成员。这里的成员来自 worker 组成，**不是 warp 编号**。跨成员的关系必须写出明确编号或 `[*]`，不根据双方 role 的布局自动改变含义。引用仍须指向所选成员上实际存在的动作。

`Waiting` 左侧必须属于当前 role，右侧可以引用同一 step 的任何 role，包括当前 role；跨 step 的关系经由上游的 `Handoff` 和本区的 `Event` 连接，`::` 不提供跨 step 寻址。

例如，FA4 在两个 CTA 成员各设 LOADQK，矩阵乘位于成员 0，因此明确使用 `[*]`：

```yaml
Waiting:
  Prepared: ['{issue matmul:q(d)@k(i,d)} ← [{done LOADQK[*]::load:qc(d)}, {done LOADQK[*]::load:kc(i,d)}]']
```

源缓冲归还也不必等待目标写入完成。例如，`t` 是 worktile 本地序号，o 只有一个槽；异步 role EPILOGUE 在每份工作中依次执行 `store:o(t)` 和 `release:o_slot(t)`，release 声明为 `serial`，`describe` 保证存储已读完 o 槽。生产者可以这样等待下一次覆盖：

```yaml
Waiting:
  Released: ['{issue compute:o(t+1)} ← [{done EPILOGUE::release:o_slot(t)}]']
```

此时全局写入仍可在途；若只等 `store` 的 `issue`，则得不到源槽可覆盖的保证。

### 跨工作接续与索引边界

#### 跨工作接续

资源默认跨工作接续：同一 worker 的输入环位置、输出缓冲、统计量和在途操作各按自己的使用边界衔接到下一份工作，不在每份工作末尾默认排空。worker 退出及回收局部资源前须保证相关在途操作结束；需要显式排空在途操作、提前释放资源或改变重叠时写成动作，底层释放同步由原语或 `REALIZATION` 承担。

step 和 worktile 都不是资源重建指令。同一 worker 连续处理多份工作时，下一份工作的搬运可以与上一份工作的收尾重叠；在每份工作末尾排空缓冲或插入全量等待，会把持久化换来的这部分重叠丢掉。

#### 连续序号

持久 worker 让缓冲和在途操作跨工作接续时，需要一个跨工作的连续序号。例如，每份工作有 `iteration_count` 次局部迭代时：

```yaml
Index:
  t: {meaning: Local ordinal in this worker's worktile sequence, definition: worktile}
  i: {meaning: Local iteration within one worktile, definition: [0, iteration_count]}
  n: {meaning: Iteration ordinal across worktiles, definition: {flatten: [t, i]}}
```

`t` 是当前 worker 工作序列的本地序号，`i` 是一份工作内的局部迭代，`n` 是 `(t, i)` 的连续编号：此前各份工作的迭代数之和加上 `i`，每份工作的迭代数不同时同样成立。实例只维护 flatten 定义，不手写换算公式。

| 写法         | 含义                                    |
| ------------ | --------------------------------------- |
| `n[t,i]`   | 指定工作和局部迭代对应的连续序号        |
| `n[t]`     | 当前工作包含的完整连续序号切片          |
| `n[t,a:b]` | 当前工作中局部索引落在 `[a,b)` 的切片 |
| `n[t,1:]`  | 当前工作去掉首项后的切片                |
| `n+3`      | 连续序号前进三项，可以跨过工作边界      |

绑定 `n` 时可以唯一恢复其 `t / i` 坐标；`t` 与 `n` 出现在同一个动作或同一条依赖中时，`t` 就是 `n` 所在的工作。`n[t,i+1]` 要求 `i+1` 仍在当前工作的局部域内，越界时不进位到下一份工作；`n+1` 则明确跨过工作边界。前者用于「本份工作中除第一轮以外」这类规则，后者用于跨工作接续的环。

#### 依赖的索引窗口

动作的发生域由 `Pipe` 的控制结构确定；动作族的声明窗口由其所在作用域已声明的索引域确定，不从实际生成了哪些动作倒推。`Waiting` 先核对两端角色、动作族与参数签名，再综合两端引用的已声明索引域与坐标关系展开上下文：

- **右侧独有索引按声明域展开**：仅出现在右侧前驱中的索引（如循环外的 `await:tail` 等待循环内的 `matmul:pv(n,d)`）按已声明域和已有坐标关系展开，不借用循环退出后的隐含末值；落到同一左侧目标实例的全部有效前驱共同约束该目标。
- **目标不存在则无等待实例**：目标动作因自身 `if` 为假、循环切片未选中或所在循环域为空而未产生，或带变量移位的目标越出声明窗口时，不生成等待实例；某份工作内目标的声明发生域为空时，固定索引引用在该工作内也不生成等待，不由此隐含非空假设。角色、动作签名、成员选择及越界侧之外的固定索引错误仍须报错。
- **单前驱移位越界独立跳过**：目标实例存在时，对右侧各前驱及所选成员分别核对窗口；因变量移位落到声明窗口外的单个前驱实例跳过，其余有效前驱继续约束该目标。
- **窗口内缺前驱报错**：目标实例存在，而未移位引用、固定索引引用或声明窗口内的前驱实例不存在（如前驱所在 `if` 为假），属于错误；不能将两端事件集合求交来删掉等待。

例如 `n[t,i+1]` 在每份工作的末轮越过局部域，对应的跨轮项在该轮跳过，末轮由另一条明确规则衔接。折叠写法中的跨轮依赖也不是同轮回边：是否成环，要看展开后的实例及其真实索引关系。

#### 条件等待示例

索引定义如下，其中 `iteration_count>0`：

```yaml
Index:
  t: {meaning: Local ordinal in this worker's worktile sequence, definition: worktile}
  i: {meaning: Local iteration within one worktile, definition: [0, iteration_count]}
  g: {meaning: Matrix product ordinal across worktiles, definition: {flatten: [t, i]}}
```

`MMA` 的矩阵乘采用 `async_ordered`，每个 `g` 依次准备 scale 并执行矩阵乘；`EPILOGUE` 在每个成员上各有一个 `release:accumulator(t)`。当前方案在非首 worktile 准备 scale 前等待前一 worktile 的全部 release，只展开 `MMA` 中与等待位置有关的字段：

```yaml
Info:
  Describe: Prepare scale operands and issue matrix multiplications across worktiles
  Using_verb:
    await: {drain: {execution_mode: serial, describe: Await permission to reuse accumulator(t-1)}}
    compute: {scale_tm: {execution_mode: async_unordered, describe: Stage resident scale operands for g into TMEM}}
    matmul: {payload_a@payload_b: {execution_mode: async_ordered, describe: Accumulate payload_a(g) by payload_b(g) into accumulator(t)}}
Pipe:
  - for(t):
      - if(t > 0):
          - await:drain(t)
      - for(g[t]):
          - compute:scale_tm(g)
          - matmul:payload_a(g)@payload_b(g)
Waiting:
  Released:
    - '{done await:drain(t)} ← [{done EPILOGUE[*]::release:accumulator(t-1)}]'
```

首 worktile 的 `if(t > 0)` 为假，不产生 `await:drain(0)`，该等待也没有实例。后续 worktile 的 `await:drain(t)` 可提前 `issue`，全部成员的 `release` 约束其 `done`；同步的 `await` 再按 `Pipe` 顺序约束随后 `scale_tm` 与首个矩阵乘的 `issue`，无需另写 `release → 首 matmul` 直边（原有操作数就绪等依赖照常成立）。

若局部变体允许独立的 `scale_tm` 提前准备（前提是不覆盖旧工作仍在使用的存储），可取消显式 `drain`，改为 `'{issue matmul:payload_a(g[t,0])@payload_b(g[t,0])} ← [{done EPILOGUE[*]::release:accumulator(t-1)}]'`——此时首 worktile 的矩阵乘存在，其 `t-1` 前驱按声明窗口跳过。实际采用该变化时，按[局部记录规则](0.common.md#局部记录与完整方案)保存相对完整基线的差异。

## 关键原则

### 交付的是约束，不是时间线

本区交付的是依赖和资源约束，不是实测时间线。没有依赖，只表示设计没有禁止重叠，不保证硬件一定同时执行；存在数据边，也不代表存储已经可以覆盖。重叠不另设标记，也不靠书写位置、图中并排或源码相邻来表达；动作仍可能因争用同一硬件单元或编译结果而串行。

### 与上下游的职责边界

数学计算引用 `Math_reshape`；工作分配、成员切分、遍历方向和跨 step 组合引用 `Work_schedule`；具体原语与必要的实现预算由 `REALIZATION` 绑定。本区只声明局部执行与存储设计，不复写上游定义。

`describe` 只保留本区特有且影响设计的内容，不是源码说明书；地址计算、线程级 layout、指令语法、barrier 与寄存器编号等普通实现细节交给 Coder。
