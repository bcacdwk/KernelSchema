#### 核心思想

`tile_pipeline` 在已经确定的 worktile 和 worker 内，描述执行角色怎样推进计算、交接数据和复用资源。它接收 `math_reshape` 给出的值、精度、初值及物化决定，接收 `work_schedule` 给出的工作归属、执行成员、工作序列与跨 phase 关系，再将这些设计转化为 Coder 必须保持的局部执行约束。

本区的基本对象是 **lane**。一个 lane 是承担一类动作的一组执行单元，在 NVIDIA 上是一个或几个 warp；它不是单个线程，也不一定独占某个硬件引擎。例如，MMA lane 可以只是负责发射异步矩阵乘的一个 warp，矩阵乘本身在 Tensor Core 上执行。执行单元的名称取自 `contract.hardware_specification.execution`，其他设备使用各自登记的单元（如 MI355X 的 wavefront、昇腾 950 的 AIC 与 AIV）。

本区保留四类信息：

| 信息 | 回答的问题 |
| --- | --- |
| 角色与动作 | 哪些 warp 承担什么工作，各自怎样推进 |
| 索引与重复 | 动作属于哪份工作、哪次局部迭代 |
| 依赖与发布 | 消费者何时可以继续，哪些结果可以提前使用 |
| 资源与复用 | 值放在哪一级存储、开几个槽，哪些值共用存储，何时可以覆盖 |

本区使用 `thesis / phase`。phase 沿用 `work_schedule` 的 phase ID：每个 ID 就是一次提交及其 worker 实例的身份，本区直接用它作为执行作用域，不复制 `flow`。每个 phase 内，`lane` 登记执行角色，`resource` 是这个 worker 的片上资源账，`domain` 定义多个 lane 共用的索引，`milestone` 给上游交接需要引用的事件组起名。

动作采用设计级粒度，而不是源码调用级粒度。两个连续动作之间，只有出现重要的数据发布、资源归还、执行角色切换、独立循环或重叠机会，才值得拆开。数学内部步骤由上游定义，地址计算、线程级 layout、指令语法及普通原语的实现细节交给 Coder。

本区交付的是依赖和资源约束，不是实测时间线。没有依赖，只表示设计没有禁止重叠，不保证硬件一定同时执行；存在数据边，也不代表存储已经可以覆盖。

**设计着眼点**

上游已经定下算什么、一份工作多大、由谁来做；本区决定这份工作在 worker 内怎样流动。steady 重复一次的时长（一个 pace）由最忙的硬件单元决定——Tensor Core、MUFU 与 FMA、搬运与访存带宽，或发射本身——其余环节只要藏在它下面，就不增加时长。所以先找出瓶颈，再看其余环节能不能被它盖住；字段只是答案的落点。

| 问题 | 要看什么 | 落在哪里 |
| --- | --- | --- |
| pace 卡在哪一环 | steady 中各硬件单元各要忙多久，最慢的一项就是 pace；能否把一部分工作挪到空闲的单元上 | `thesis`；steady 中的动作，以及契约中的负载分摊 |
| 谁和谁重叠 | 想同时进行的动作是否分在不同 lane、之间没有边；多切一个 lane 换来重叠，付出 warp、寄存器和每次交接的握手 | `lane` 的划分，`member`、`register` |
| 缓冲开多深、放在哪一级 | 生产者要领先几轮才能盖住延迟；加深换来延迟容忍，付出片上容量和每个 SM 能驻留的 worker 数 | `resource` 的 `space / slot / shape`，`reuse` 边的距离 |
| 结果多早交出 | 消费者等的是整块还是其中一部分；分段发布让下游提前开始，代价是多一次同步 | 动作的切分，`data` 边 |
| 跨工作是否排空 | 持久 worker 的缓冲、状态和在途操作能否直接接续到下一份工作 | `worktile` 与连续序号域，跨工作的边 |

#### 字段定义

**结构轮廓**

下面是字段结构，不是待填写的 YAML。`?` 表示条件可省略，`<phase_id>`、`<lane_id>` 等表示实例名称。

```text
tile_pipeline
├─ thesis
└─ phase
   └─ <phase_id>
      ├─ domain?: <index>
      ├─ milestone?: <milestone>
      ├─ resource?
      │  └─ <resource_id>: space / shape / dtype / slot? / member? / view?
      │     └─ view.<value>: slot? / part? / dtype?
      └─ lane
         └─ <lane_id>
            ├─ info: member / mode? / register? / verb?
            ├─ pipe: repeat? / prologue? / steady? / epilogue?
            └─ edge?: data? / reuse? / sync?
```

**外层与 phase**

下表中的路径均相对于 `tile_pipeline`。

| 字段路径 | 值的形式 | 填写条件 | 含义与约束 |
| --- | --- | --- | --- |
| `thesis` | 非空英文字符串 | 必填 | 一两句说明 pace 卡在哪一环、靠什么把其余环节藏到它下面，以及付出了什么 |
| `phase` | 非空具名映射 | 必填 | 键与 `work_schedule.phase` 一一对应 |
| `phase.<phase_id>.lane` | 非空具名映射 | 必填 | 执行角色，见“lane” |
| `phase.<phase_id>.resource` | 资源具名映射 | 有需要登记的片上存储时填写 | 该 worker 的片上资源账，见“资源” |
| `phase.<phase_id>.domain` | 索引域具名映射 | 多个 lane 共用一个索引，或资源视图要用到它时填写 | 统一索引的身份与边界，不要求各 lane 锁步推进 |
| `phase.<phase_id>.milestone` | 具名映射，值为非空事件引用列表 | 上游交接引用本 phase 的局部事件时填写 | 所列事件全部发生时，该里程碑成立 |

同一次提交中 `order` 不是 `concurrent` 的几个 phase 由同一个 worker 实例承担：它们的 lane 使用同一组物理 warp，资源合成一份账，在其中一个 phase 定义一次，其他 phase 直接按名称使用。不同 worker 实例中的同名资源互不相干。

**资源**

下表中的路径相对于 `resource.<resource_id>`。

| 字段 | 值的形式 | 填写条件 | 含义与约束 |
| --- | --- | --- | --- |
| `space` | 存储层级名称 | 必填 | 沿用 `contract.hardware_specification` 中的叫法，例如 B200 的 `SMEM`、`TMEM`、`register` |
| `shape` | 有序的具名维度列表 | 必填 | 一个成员持有的一个槽的容量 |
| `dtype` | 上游已定义的数值格式 | 必填 | 与 `shape` 一起确定每槽的大小 |
| `slot` | 正整数或整数表达式 | 多于一个槽时填写 | 物理槽数；省略为 1 |
| `member` | 成员序号或序号列表 | 只有部分成员持有这块存储时填写 | 省略表示 worker 的每个成员各有一份 |
| `view` | 视图具名映射 | 一块存储要放多个值、按索引轮转槽位、与别的值共用空间，或只占一部分时填写 | 见“视图” |

资源名与上游的某个值同名、又没有写 `view` 时，这块单槽存储就存放该值，它的各个版本依次覆盖，例如跨 chunk 原地更新的状态。只登记设计层面的存储，即存放上游值或局部状态的缓冲；barrier 存储、对齐余量和编译器临时量属于实现，不登记。

这份账回答两个问题。一是容量：同一 worker 实例的全部资源，加上各 lane 的寄存器预算，决定一个 SM 能同时驻留几个 worker，`work_schedule` 把这个数交给本区决定。二是深度：`slot` 决定生产者最多能领先消费者几轮。`space` 决定值停在哪一级存储；放在 `register` 中的状态不占共享存储，但计入所属 lane 的寄存器预算。

`shape` 采用上游的具名轴写法，轴名沿用上游；几种值共用的资源（如 TMEM 中分槽存放 S、P 与 Y，或 K 与 V 轮流使用的环）没有统一的逻辑轴，用 `row`、`column`、`element` 这类物理轴名。它描述一个成员持有的容量，所以不一定等于上游按整个 worker 登记的块：两个 CTA 分摊一块 K 时，每个成员只持有一半。

**视图**

`view` 的键是逻辑值名，可以带索引模式，如 `K(n)`。模式中的索引是形参，只用来把值的版本映射到槽，不声明或扩大任何循环。

| 字段 | 值的形式 | 填写条件 | 含义与约束 |
| --- | --- | --- | --- |
| `slot` | 整数或整数表达式 | 父资源多于一个槽时必填 | 该值（该版本）所在的槽，必须落在槽数之内 |
| `part` | 轴名到左闭右开范围的映射 | 只占一个槽的一部分时填写 | 例如 `{column: [64, 128]}`；未列出的轴取整轴，省略表示整槽 |
| `dtype` | 数值格式 | 解释方式不同于父资源时填写 | 省略时继承父资源，不产生新分配 |

`part` 先按父资源的形状和数据类型选出物理区域，再按视图的类型解释：在 FP32 槽中，`{column: [64, 128]}` 选中后一半存储，将其解释为 BF16 不增加容量。逻辑值的形状仍来自上游，不能凭 dtype 换算去猜。

**lane**

下表中的路径相对于 `lane.<lane_id>`。

| 字段路径 | 值的形式 | 填写条件 | 含义与约束 |
| --- | --- | --- | --- |
| `info.member` | 成员选择字符串 | 必填 | 这个角色占用的执行单元，例如 `warp[0:4]`、`CTA[0].warp[12:13]` |
| `info.mode` | `sync / async / ordered` | 不是 `sync` 时填写 | 动作之间的默认推进方式，见“lane 内的顺序” |
| `info.register` | 正整数 | 设计为不同角色设定不同寄存器预算时填写 | 每线程寄存器数 |
| `info.verb` | 动作词到契约的具名映射 | 动作含义超出或需要收紧通用动词表时填写 | 见“动作与契约” |
| `pipe` | pipe 块 | 必填 | 动作序列与重复结构 |
| `edge` | 依赖分类映射 | 存在默认依赖之外的前驱时填写 | 见“依赖与里程碑” |

`member` 同时给出角色的规模：一个 worker 用多少 warp，就是各 lane 成员的并集，不另设计数；不承担动作的 warp 不登记。成员选择省略第一段时，这个 lane 在 worker 的每个成员上各有一份。

切出一个 lane 的典型理由：异步发射者（搬运、矩阵乘）单独占一个 warp，发射就不会被计算拖住；同一类计算交给两个 lane 轮流承担（FA4 的两个 Softmax），一个 lane 的计算就能盖住另一个 lane 的等待。`register` 在角色之间重新分配寄存器：一个成员的寄存器总量固定，计算角色多拿的部分，要从搬运和发射角色那里让出来。

`info.verb` 的值是一句契约；某个动作的推进方式不同于所在 lane 的 `mode` 时，改用只含 `meaning` 与 `mode` 的长形式：

```yaml
verb:
  store: Issue a bulk store of O to global memory.
  release:
    mode: sync
    meaning: Wait until the store has read the O slot, then return the slot.
```

**pipe 与域**

每个 pipe 块由 `repeat / prologue / steady / epilogue` 组成，子块结构相同。lane 的顶层 pipe 描述这个角色在 worker 整个生命周期内的动作：持久 worker 在顶层按 `worktile` 域重复，只处理一份工作的 worker 直接写这份工作的动作。

| 字段 | 值的形式 | 填写条件 | 含义与约束 |
| --- | --- | --- | --- |
| `repeat` | 域名、域切片，或单项局部域映射 | 块中有重复主体时填写 | 不填写时，三个区域各执行一次 |
| `prologue` | 动作或子块的有序列表 | 有一次性开头动作时填写 | 在块开始时执行一次 |
| `steady` | 动作或子块的有序列表 | 有主体动作时填写 | 按 `repeat` 的域逐项执行，没有 `repeat` 时执行一次 |
| `epilogue` | 动作或子块的有序列表 | 有一次性收尾动作时填写 | 在全部主体之后执行一次 |

域定义采用以下三种形式：

| 形式 | 含义 |
| --- | --- |
| `[lower, upper]` | 半开整数域，依次取 `lower` 至 `upper-1` |
| `worktile` | 这个 worker 按处理顺序得到的全部工作，包括预分配的和运行时领取的；取值是本地序号，不是全局 worktile 编号 |
| `{flatten: [outer, inner]}` | 把已定义的有序域积按字典序连续编号，后一个域变化更快；内层范围可以随外层取值变化 |

局部域短写如 `repeat: {k: [0, 8]}`，只在当前 lane 的这个块中定义 `k`。多个 lane 需要共同解释一个索引，或资源视图要用到它时，在 `domain` 中定义一次，各 lane 写 `repeat: k`。域的边界能用上游名称表达时就引用名称（如 GDN 的 chunk 数 `Nc`、FA4 每份工作要遍历的 KV 块数 `N`），不写算好的数字：换一个分支，名称仍然成立，数字就不一定。

`worktile` 的长度可能到运行时才知道：`refill` 不是 `none` 时，worker 何时停止由上游的 `exit` 决定，此时不对它使用 `last` 或 `count`。运行时领取本身（例如查询下一份工作，再把坐标交给其他 lane）是某个 lane 的普通动作，其他 lane 进入下一份工作前对它的等待是普通的依赖。

**依赖与里程碑**

`edge` 按等待的原因分三类，每类都写成 `等待的动作 → 非空前驱事件引用列表`：

| 字段 | 等待什么 |
| --- | --- |
| `data` | 操作数、计算结果或发布已经就绪 |
| `reuse` | 旧内容的全部必要读取已经结束，可以覆盖它的存储 |
| `sync` | 数据与复用之外的协议放行，例如两个计算角色轮流占用同一硬件单元 |

三类边的约束力相同，分类只保留原因，也让读者能直接找到最要紧的部分：流水里的环几乎都要经过一条从消费者指回生产者的边，也就是 `reuse` 或 `sync`，死锁和过早覆盖都出在这里。哪些依赖不写也成立，见“默认的依赖”。

`milestone` 只给已有的事件组起一个对外名称，不产生数据可见性、跨 CTA 通知或轮询；这些机制由 lane 中的实际动作承担，见“跨 phase 交接”。

**固定结构与扩展边界**

| 位置类型 | 本区位置 | 允许的变化 |
| --- | --- | --- |
| 固定结构 | `tile_pipeline`、phase 条目、资源条目、视图条目、`info`、pipe 块、`edge` | 只使用本节声明的字段 |
| 具名映射 | `phase`、`domain`、`milestone`、`resource`、`view`、`lane`、`verb` | 可以增加当前设计需要的名称，条目结构不变 |
| 开放取值 | `space` 的存储名、成员选择中的执行单元名、动作词及其契约 | 沿用硬件规格中的名称；通用表之外的动作词写明契约 |

增加 lane、资源、索引、里程碑或动作词是填写实例。新增字段、域形式、事件种类或边的分类属于结构修改，须另行确认其含义、填写条件和真实案例。

#### 语法规则

**名称与顺序**

通用写法（单数字段名、英文、真实仓库路径与函数名原样、实例不写注释、不用 `null` 或空字符串占位）见 `contract.algorithm_requirement` 的语法规则。phase ID 与里程碑名沿用 `work_schedule` 的写法（小写英文与下划线）；lane、资源与索引采用英文标识符，数学值的名称沿用上游，保留大小写。

映射的书写顺序没有执行含义。执行顺序只来自 pipe 列表、`repeat`、依赖、契约中写明的原语顺序保证，以及上游的工作组织；`flatten` 中域列表的顺序有含义，它决定编号方式。

YAML anchor 只复用相同的字段内容，例如两个对称角色共用一份动作契约；它不创建共享存储或新角色，也不跨案例使用。

没有内容的可选字段直接省略。`phase`、`lane` 与 `pipe` 必须非空，没有动作的 warp 不建 lane；edge 规则与里程碑必须有非空引用列表，没有前驱就省略该条目。

**动作与契约**

动作写成：

```text
verb:object
verb:object(index)
mma:A(index)@B(index)
```

动作名同时是引用身份：重复展开后，同一 worker 实例、同一成员、同一 lane 内的动作名必须唯一，不能在多轮 repeat 中重复一个不带索引的固定动作。对象可以是上游的值、局部状态或协议对象；合写的名称（如 `State_Local`）要能从契约知道它包含什么，不能靠拆分下划线去猜。

通用动词如下：

| 动作词 | 通用含义 |
| --- | --- |
| `load` | 把已定义的值搬进本 phase 的存储 |
| `publish` | 形成目标值，并让其他 lane 可以读取 |
| `store` | 把已有结果写到上游规定的物化位置 |
| `compute` | 执行上游定义的计算，结果只供本 lane 使用 |
| `produce` | 执行上游定义的计算，并写到上游规定的物化位置 |
| `zero` | 把目标累加状态置零 |
| `mma` | 以所写操作数做矩阵乘累加；累加器何时初始化、分段消费哪一部分，由契约写明 |
| `wait` | 等到目标可用，本身不计算；等什么由它的前驱给出 |
| `release` | 本 lane 对目标的读取已经结束，它的存储可以被覆盖 |

通用表之外的动作词（如 `update`、`rescale`、`scan`、`advance`）必须在 `info.verb` 中写明契约，通用词的契约也可以在那里收紧。`info.verb` 是补充，不是白名单：没有写进去的通用词照常使用通用含义。

契约写名称与上游推不出来的东西：动作还读了什么、分几次交出结果、在哪里初始化、依赖哪条原语顺序保证。它可以合并内部计算，但不改写上游的公式、精度或物化决定，也不复述上游已经写下的遍历方向、成员切分或数学公式。上游以 `bind:design.tile_pipeline::<name>` 交给本区的参数（如 FA4 中决定哪些元素走多项式路径的 `use_poly`），写在决定它的那个动作的契约里，并使用同一个名称。

特定原语的顺序保证可以代替一条显式的边，例如同一 lane 中先发射的矩阵乘读完一块存储之后，后发射的矩阵乘才写入它。依赖这种保证时，在契约中写明保证本身及其适用范围，提供它的原语由 `realization` 绑定；不能从 `mode`、同一个 lane 名或同一个对象名推出硬件会处理冲突。

**lane 内的顺序**

每个动作有两个事件：`issue` 表示已经发射或开始执行，`done` 表示它承诺的完成条件已经得到保证。`done` 是设计可以依赖的保证，不是测得的硬件时间戳；几个动作可以共享一次完成通知，只要这次通知确实覆盖它们。

| `mode` | lane 内的推进 |
| --- | --- |
| `sync`（省略时） | 当前动作 done 之后，才推进到下一个动作 |
| `async` | 按 pipe 顺序发射，不保证完成顺序 |
| `ordered` | 按 pipe 顺序发射，完成也按发射顺序：某个动作 done，就意味着此前发射的动作都已 done |

`ordered` 让等待者只需等最后一个动作，省掉对前面各个动作的边；只在原语确实提供累积完成时使用，例如一次提交就能覆盖此前全部矩阵乘的完成。拿不准时写 `async`：多写几条边只是啰嗦，误用 `ordered` 则会省掉必要的边。

异步 lane 中的长形式 `mode: sync` 是同步例外：该动作在 pipe 中的位置发射，完成后 lane 才继续，已经发射的其他异步动作可以继续在途。它等待什么由自己的契约和前驱决定，不默认排空此前的全部异步动作；`ordered` 的完成顺序也只在异步动作之间成立。

没有通用的 `@begin` 或 `@read` 事件。需要表达“源存储已经可以归还、目标写入尚未完成”时，用一个有明确原语依据的 `release` 动作，它不能冒充整个写入完成。

**默认的依赖**

以下依赖不写也成立：

- lane 内按 `mode` 推进；
- 引用某个 `load` 或 `publish` 的对象、且名称与索引完全相同的动作，发射前等待该动作 done。

`load` 与 `publish` 的作用本来就是把一个对象交给别的动作使用，名称就是接口，所以可以默认。其余依赖都要显式写出：矩阵乘的产物交给谁、动作读了名字里没有的值、存储何时可以覆盖、协议何时放行。默认依赖与显式依赖一起进入展开后的事件图和环检查。

按名称匹配要求写法一致：一个值分几次发布，消费者就引用它实际等待的那一部分；生产者写 `Q_high(t)`、消费者只写 `Q_high`，两者不会匹配。

已由 lane 顺序、`ordered` 的完成顺序或其他边传递保证的前驱可以省略。省略的是可推导的重复前驱，不是必要的就绪条件。

**事件引用**

完整形式为 `Lane[member]/action@event`，省略规则如下：

| 写法 | 解释 |
| --- | --- |
| `action` | 当前 lane、当前成员上的动作 |
| `Lane/action` | 两个 lane 在 worker 的每个成员上各有一份时，指同一成员上的实例；否则指对方的全部实例 |
| `Lane[0]/action` | 0 号成员上的实例 |
| `Lane[*]/action` | 对方的全部实例，用于两边都在每个成员上、却要等全部成员的情形 |
| 等待方省略事件 | 使用 `issue` |
| 前驱或里程碑省略事件 | 使用 `done` |

成员的默认覆盖了最常见的两种关系：每个成员上的角色只和本成员的对应角色交接；只在一个成员上的角色（如成对 CTA 共用的 MMA）与每个成员上的角色交接时，等待全部实例。偏离这两种关系时才写具体成员，例如一个成员的搬运多播到另一个成员。

动作末尾的 `@issue`、`@done` 是事件后缀，矩阵乘中间的 `@` 属于动作名。edge 的左侧必须属于当前 lane，右侧可以引用同一 phase 的任何 lane；跨 phase 的关系经由上游的 `handoff` 和本区的 `milestone` 连接。同一事件匹配多条规则时，前驱取并集，包括不同分类的规则。

**域、重复与边界**

`[lower, upper]` 一律是半开区间，`[0, 8]` 表示八次迭代，不包含 8。一个块按以下顺序展开：

```text
prologue 一次
steady 对域中每个索引执行一次
epilogue 一次
```

嵌套块按所在列表位置执行。一个 lane 的两段独立循环写成两个相邻子块，而不是展开成固定索引的动作，也不是新建 kernel。

当前循环变量只在其 steady 中绑定。prologue 和 epilogue 可以使用外层已绑定的变量、常量及域查询 `count(d)`、`last(d)`，不能使用当前循环变量的某个隐含“最后值”。空域使 steady 执行零次，但不删除 prologue 与 epilogue；`last` 只用于非空域。

多个 lane 使用同一个域，不代表它们同时进入同一轮：每个 lane 独立推进，只受自己的顺序和依赖约束。

整数表达式沿用 `contract.algorithm_requirement` 与 `work_schedule` 的约定，另可使用取模 `%` 与域查询 `count(d)`、`last(d)`。

**连续序号**

持久 worker 让缓冲和在途操作跨工作接续时，需要一个跨工作的连续序号。FA4 使用：

```yaml
domain:
  t: worktile
  i: [0, N]
  n: {flatten: [t, i]}
```

`t` 是当前 worker 工作序列的本地序号，`i` 是一份工作内的局部迭代，`n` 是 `(t, i)` 的连续编号：此前各份工作的迭代数之和加上 `i`，每份工作的迭代数不同时同样成立。实例只维护 flatten 定义，不手写换算公式。

| 写法 | 含义 |
| --- | --- |
| `n[t,i]` | 指定工作和局部迭代对应的连续序号 |
| `n[t]` | 当前工作包含的完整连续序号切片 |
| `n[t,a:b]` | 当前工作中局部索引落在 `[a,b)` 的切片 |
| `n[t,1:]` | 当前工作去掉首项后的切片 |
| `n+3` | 连续序号前进三项，可以跨过工作边界 |

绑定 `n` 时可以唯一恢复其 `t / i` 坐标；`t` 与 `n` 出现在同一个动作或同一条依赖中时，`t` 就是 `n` 所在的工作。`n[t,i+1]` 要求 `i+1` 仍在当前工作的局部域内，越界时不进位到下一份工作；`n+1` 则明确跨过工作边界。前者用于“本份工作中除第一轮以外”这类规则，后者用于跨工作接续的环。

**执行索引与数学值索引**

循环域限制循环变量的取值，不限制数学对象的索引范围。GDN 的 `c` 从 0 开始，上游状态却从初值 `S(-1)` 开始，因此首轮读到的 `S(c-1)` 合法，并不代表执行了一次 `c=-1` 的循环。反过来，一个只在非首轮执行的 `rescale` 动作，不会因为 `Y(0)` 这个数学值存在，就自动产生 `rescale:Y(0)`。

**依赖的索引窗口**

pipe 和 edge 的边界规则不同。pipe 严格按 `repeat` 的域展开，不会因为某个动作越界就删掉一整轮。edge 中带变量移位的规则按声明的索引窗口逐项实例化，移位后落在域外的那一项跳过；固定索引的引用和窗口内的引用都必须指向实际存在的动作——拼错动作名、漏掉合法域内的一次发布，都不是边界情况。

窗口来自已经声明的循环域或数学值域，不从实际生成了哪些动作去倒推。例如 FA4 的 `n[t,i+1]` 在每份工作的末轮越过局部域，相应的跨轮规则不在该轮生成，末轮由另一条明确的规则连接。折叠写法中的跨轮依赖也不是同轮回边：是否成环，要看展开后的实例及其真实索引关系。

**成员、别名与存续**

成员选择沿用硬件规格登记的执行单元名，写成路径加半开区间：`CTA[0].warp[12:13]` 表示 0 号成员中的 12 号 warp，`warp[0:4]` 表示每个成员中的 0 至 3 号 warp。成员来自上游的 worker 组成，warp 编号在一个成员内从 0 计。

两个 lane 名称不同，不代表占用不同的物理 warp：物理 warp 按 worker 实例、成员和 warp 编号识别。同一 worker 实例中不同 phase 的 lane 可以复用同一组 warp；同时活跃的 lane 若成员重叠，必须有可实现的执行关系，不能把同一个 warp 当成两份资源。

物理存储的共用通过一个资源及其视图表达。视图只说明存储关系，不产生数据边、发布或同步：两个值落在同一块存储里，旧值的全部必要读者和新值的写入时刻都要由依赖表达，或由契约中写明的原语顺序保证。

新分配的存储没有旧读者，不代表内容已经清零；初值来自上游定义和对应动作，例如 `zero`，或由第一次矩阵乘直接初始化累加器。

资源默认跨工作接续：同一 worker 的输入环位置、输出缓冲、统计量和在途操作，各按自己的使用边界衔接到下一份工作，不在每份工作末尾排空。worker 结束前的安全回收由资源与原语承担；只有提前释放，或回收本身改变重叠时，才写成动作。

**跨 phase 交接**

跨 phase 的交接由 `work_schedule.flow.handoff` 登记。省略 `ready` 与 `wait_at` 时，交接点是生产工作完成与消费工作开始，本区不必为它们提供名称；只有上游要求提前交出或推迟等待时，才在相应 phase 中定义 `milestone`，上游以 `<phase_id>.<milestone>` 引用。交接发生在片上资源中时，上游引用的是这里定义的资源。

里程碑的键可以带索引，如 `snapshot_ready(c)`，索引与所引用事件中的同名索引对应。生产侧的里程碑绑定真实的完成或发布事件；消费侧的里程碑落在实际执行等待的动作上，例如轮询标志、或等待前一个 kernel 完成的 `wait`。数据可见性、通知方式和消费方的驻留条件都由这些动作承担，不能由一个名称产生。

#### 关键原则

**按外部边界决定动作粒度。**

内部初始化、转换和计算若没有被其他角色利用的中间边界，可以合成一个已定义的动作。提前发布、统计量捕获、源缓冲归还等边界不能因为源码连续而被合并掉。

**同一事实只维护一次。**

数学计算引用 `math_reshape`；工作分配、成员切分、遍历方向和跨 phase 组合引用 `work_schedule`；原语选择交给 `realization`。本区只增加局部组织：能由 lane 成员、资源的 shape 与槽数、域定义推出的数量不另设字段，契约也不复述上游已经写下的事实。

**发布与复用分别检查。**

生产者发布只说明消费者可以读取。覆盖存储还必须等待全部必要的读者结束，或依赖契约中写明的原语保证。一个读者读完不代表所有读者读完，源缓冲可以归还也不代表目标写入完成。

**没有依赖不等于已经实现 overlap。**

重叠是依赖图允许的机会，不是一项可以声明的属性：不另设 overlap 标记，也不依靠书写位置、图中并排或源码相邻来表达同时执行。两个动作即使没有边，也可能因为争用同一硬件单元或编译结果而串行。

**持久 worker 的收益在于接续。**

phase 和 worktile 都不是资源重建指令。同一 worker 连续处理多份工作时，下一份工作的搬运可以与上一份工作的收尾重叠；在每份工作末尾排空缓冲或插入全量等待，会把持久化换来的这部分重叠丢掉。

**简单工作应保持简单。**

单个协作 CTA 可以只有一个 lane，没有 `domain`、`edge` 和专职异步角色。不能为套用 FA4 的形式，把 Triton 的一段协作计算拆成虚构的 Load、Softmax 或 Epilogue lane。

**说明密度与实例密度分开。**

通用规则放在本节，案例只保留特有且影响设计的契约。`info.verb` 不是源码说明书；精确的 barrier 编号、寄存器编号、线程地址和普通 lowering 细节不进入本区。

#### 具体案例

以下两个案例的目标硬件均为 B200 / SM100，只展开 `tile_pipeline`；名称与记号沿用 `contract.algorithm_requirement` 和 `design.math_reshape`，工作组织沿用 `design.work_schedule` 的同名案例，设备、实现栈与工具链版本由 `contract.hardware_specification` 固定。两例一繁一简：FA4 用到本区的大部分结构——多个 lane、跨工作接续的环、分段发布与存储别名；GDN 的每个 phase 只有一个协作 lane，示范简单工作应当写得多简单。

**Case 1：FA4 非因果双 CTA、静态持久化**

固定来源：

| 内容 | 位置 |
| --- | --- |
| 主实现与角色划分 | `Dao-AILab/flash-attention@ce088ab9:flash_attn/cute/flash_fwd_sm100.py::FlashAttentionForwardSm100` |
| Softmax 与 P 的分段发布 | `Dao-AILab/flash-attention@ce088ab9:flash_attn/cute/softmax.py` |
| 分段矩阵乘 | `Dao-AILab/flash-attention@ce088ab9:flash_attn/cute/blackwell_helpers.py` |

分支与工作组织同 `work_schedule` 的 FA4 案例：每份工作是 512 行 Q，分为各 256 行的 Q_high 与 Q_low；两个 CTA 组成一个 worker，各承担两块中的 128 行；KV 按块降序流过，每块 128 行，每份工作遍历 `N` 块（本例 KV 长 8192，`N = 64`）。S、P、Y、alpha 与 Lsum 的定义和精度来自 `math_reshape`：S 与 Y 为 FP32，P 为 BF16。

```yaml
            steady:
              - repeat: "n[t,1:]"
                prologue: ["wait:alpha_high(n[t,0])", "wait:alpha_low(n[t,0])"]
                steady: ["rescale:Y_high(n)", "rescale:Y_low(n)"]
                epilogue:
                  - "release:statistic_low(t)"
                  - "read:final_high(t)"
                  - "publish:O_high(t)"
                  - "read:final_low(t)"
                  - "publish:O_low(t)"
                  - "produce:LSE(t)"
          edge:
            data:
              "rescale:Y_high(n[t,i+1])": ["Softmax_high/publish:alpha_high(n[t,i+1])"]
              "rescale:Y_low(n[t,i+1])": ["Softmax_low/publish:alpha_low(n[t,i+1])"]
              "publish:O_high(t)": ["MMA/mma:P_high_tail(n[t,last(i)])@V(n[t,last(i)])"]
              "publish:O_low(t)": ["MMA/mma:P_low_tail(n[t,last(i)])@V(n[t,last(i)])"]
            reuse:
              "publish:O_high(t+1)": ["Epilogue/release:O_high(t)"]
              "publish:O_low(t+1)": ["Epilogue/release:O_low(t)"]

        Epilogue:
          info:
            member: "warp[13:14]"
            mode: async
            verb:
              release:
                mode: sync
                meaning: >
                  Wait until the store has read the O slot, then return the slot;
                  the global write may still be in flight.
          pipe:
            repeat: t
            steady: ["store:O_high(t)", "store:O_low(t)", "release:O_high(t)", "release:O_low(t)"]
```

显式的数据边只剩名字里看不出来的交接：MMA 产出的 S 交给 Softmax，Correction 用 alpha 改写 Y，下一段 PV 要等 Y 改写完成，最后一段 PV 之后才能归一化 Y。Q、K、V、P、O 与最终统计量的交接都由 `load`、`publish` 的名称默认给出；`reuse` 边逐一对应会被覆盖的存储：KV 环、Q、TMEM 中的 Y、统计量与 O。

MMA 是 `ordered`：稳态的 `rescale` 等本轮 alpha，alpha 又等本轮 QK 完成，这已经覆盖了此前发射的 PV，所以 `rescale` 不再单独等 PV；归一化 Y 之前没有后续的 QK 可以依靠，仍显式等待最后一段 PV。

`release:O_high(t)` 只等存储读完 O 槽，不等全局写入完成；下一份工作的 `publish:O_high(t+1)` 等的是它，所以输出的写回可以和下一份工作重叠。

资源账：每个成员的 SMEM 合计 226 KiB（Q 64、KV 96、O 64、统计量 2），TMEM 用四个 128 列的槽，共 512 列。

**Case 2：GDN 五趟 Triton 分块前向**

来源与分支同 `work_schedule` 的 GDN 案例：五个 kernel 依次提交，中间量都经全局内存交接，每份工作由一个 CTA 承担。状态的记法沿用 `math_reshape`：`S(c)` 是处理完 chunk `c` 之后的 FP32 状态，`S(-1)` 即初值 `S0`；`Nc` 为 chunk 数。

本例展示单 lane phase 的最短写法：没有 `domain`、`edge` 和异步角色，动作大多直接使用通用动词；常驻寄存器的值登记为与上游同名的资源，advance 的状态在整个 chunk 循环中留在寄存器里。

```yaml
tile_pipeline:
  thesis: >
    With one cooperative lane per phase nothing overlaps inside a worker, so latency is
    hidden only across co-resident CTAs; advance runs the serial chunk chain and keeps the
    FP32 state in registers throughout, so the state itself never round-trips through memory.

  phase:
    gate:
      lane:
        Main:
          info: {member: "warp[0:1]"}
          pipe:
            steady: ["produce:G"]

    solve:
      resource:
        Gram: {space: register, shape: [block: 10, token: 16, source_token: 16], dtype: fp32}
      lane:
        Main:
          info:
            member: "warp[0:4]"
            verb:
              accumulate: Accumulate the lower Ctri-by-Ctri blocks of K·Kᵀ over one dk slice into Gram.
              solve: Apply the upstream solve to Gram and store the lower blocks of BF16 T.
          pipe:
            repeat: {k: [0, 2]}
            prologue: ["load:G", "load:beta", "zero:Gram"]
            steady: ["accumulate:Gram(k)"]
            epilogue: ["solve:T"]

    prepare:
      resource:
        T: {space: register, shape: [token: 64, source_token: 64], dtype: bf16}
        beta: {space: register, shape: [token: 64], dtype: fp32}
      lane:
        Main:
          info: {member: "warp[0:4]"}
          pipe:
            prologue: ["load:T", "load:beta"]
            steady:
              - repeat: {u: [0, 2]}
                steady: ["produce:U(u)"]
              - "load:G"
              - repeat: {w: [0, 2]}
                steady: ["produce:W(w)"]

    advance:
      resource:
        S: {space: register, shape: [dk: 128, dv: 32], dtype: fp32}
        R: {space: register, shape: [token: 64, dv: 32], dtype: fp32}
      lane:
        Main:
          info: {member: "warp[0:2]"}
          pipe:
            repeat: {c: [0, Nc]}
            prologue: ["load:S0"]
            steady: ["produce:S_bar(c)", "compute:R(c)", "produce:R_bar(c)", "compute:S(c)"]
            epilogue: ["store:S_final"]

    output:
      resource:
        State_term: {space: register, shape: [token: 64, dv: 64], dtype: fp32}
        Local_term: {space: register, shape: [token: 64, source_token: 64], dtype: fp32}
      lane:
        Main:
          info:
            member: "warp[0:4]"
            verb:
              accumulate: Accumulate Q·S_bar into State_term and Q·Kᵀ into Local_term over one dk slice.
          pipe:
            repeat: {k: [0, 2]}
            prologue: ["zero:State_term", "zero:Local_term"]
            steady: ["accumulate:State_Local(k)"]
            epilogue: ["produce:o"]
```

五趟之间的交接由上游 `handoff` 登记，本区不再串联。`solve` 的求解内部步骤没有被其他角色利用的边界，合成一个动作；`prepare` 的 U、W 两段循环是同一 lane 的两个相邻子块。

advance 首轮的 `produce:S_bar(0)` 读到的是初值 `S(-1)`，并不对应一次 `c=-1` 的循环；末轮的 `compute:S(Nc-1)` 得到的就是随后写出的 `S_final`。
