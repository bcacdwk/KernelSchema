#### 核心思想

`contract.hardware_specific` 固定目标设备、关键硬件能力和当前任务的资料入口。它接收任务已选定的卡型与实现栈，向 Planner 和 Coder 提供共同的硬件依据、编程依据和查询位置；双方可以决定怎样利用这些条件，但不能自行更换设备、语言或资料版本。

本区区分两类内容：`device / arch / feature` 描述设备事实，`wiki` 绑定设备及已选软件栈的资料。同一卡型的能力摘要不因算子或语言改变；语言、模板库及相应编程资料则按任务分别绑定。

`feature` 只保留会改变计算、存储或协作可行性的关键行为与限制，完整规格和操作细节留在资料中。`wiki` 每类只绑定一个入口，由入口内部组织材料，避免 Plan 复制手册、测量表和工具清单。

本区不决定数学改写、工作划分、角色分工、缓冲配置或流水顺序，也不记录本次运行的资源配置、profiler 输出或性能结论。硬件支持、软件能否表达、具体实现的实测表现必须分别判断。

#### 字段定义

以下轮廓只展示固定字段；`feature` 内的能力名称属于具名映射，不在轮廓中枚举。

```text
hardware_specific
├── device
├── arch
├── feature
└── wiki
    ├── hardware
    ├── programming
    │   ├── language
    │   ├── template
    │   ├── virtual_isa
    │   └── machine_isa
    ├── microbench
    ├── sota
    │   ├── kernel
    │   └── schema
    └── profile
```

下表路径均相对于 `contract.hardware_specific`。“引用”指后文定义的单个字符串，不是嵌套对象或列表。

| 字段路径 | 值的形式 | 填写条件 | 含义与约束 |
| --- | --- | --- | --- |
| `device` | 非空字符串 | 必填 | 具体物理卡型，不以代际名称代替。本组案例固定为 `NVIDIA B200`。 |
| `arch` | 非空字符串 | 必填 | 设备的架构身份。本组案例固定为 `SM100`，不代替具体编译目标参数。 |
| `feature` | 非空具名映射 | 必填 | 键为能力名称，值为一句非空英文摘要，说明关键行为、作用域或限制。 |
| `wiki` | 固定结构映射 | 必填 | 资料入口集合，仅包含轮廓中声明的字段。 |
| `wiki.hardware` | 引用 | 必填 | 具体卡型的完整资料文件，覆盖计算、存储、访存、通信、同步、执行组织及必要边界。不能只绑定代际目录。 |
| `wiki.programming` | 固定结构映射 | 必填 | 当前任务已选实现栈的编程资料。 |
| `wiki.programming.language` | 引用 | 必填 | 一种已选语言或 DSL 的语法、编程模型、接口、编译与使用规则，不是候选语言菜单。 |
| `wiki.programming.template` | 引用 | 条件必填 | 任务独立采用模板库或抽象接口时填写；没有这种独立采用关系时省略。 |
| `wiki.programming.virtual_isa` | 引用 | 必填 | 虚拟指令集的语义、操作数、类型与形状约束、支持条件及同步规则。 |
| `wiki.programming.machine_isa` | 引用 | 必填 | 目标架构的机器指令与反汇编资料。资料内部应区分官方定义与观察结果。 |
| `wiki.microbench` | 引用 | 必填 | 操作及组合执行的测量知识入口，不是本次 benchmark 配置或输出文件。 |
| `wiki.sota` | 固定结构映射 | 必填 | 当前卡型的实现与设计案例入口。 |
| `wiki.sota.kernel` | 引用 | 必填 | 当前卡型上的算子实现与参考库索引，不保证其中每项都是最优实现。 |
| `wiki.sota.schema` | 引用 | 必填 | 当前卡型的设计案例集合，不自动承诺案例已通过验收。 |
| `wiki.profile` | 引用 | 必填 | 工具使用、数据采集、报告与 dump 解释，以及分析定位方法。始终只有一个入口。 |

**固定结构**

`hardware_specific`、`wiki`、`wiki.programming` 和 `wiki.sota` 只允许轮廓中声明的同级字段。未知字段应作为格式错误处理，不能静默忽略，也不能通过 `notes`、`misc` 或 `extra` 接纳。

除 `template` 外，全部字段必填。没有资料时保留相应入口并明确占位，不通过删字段表达资料缺失。

**具名映射**

`feature` 允许增加有依据的硬件能力名称。名称在本区内唯一，优先使用官方标识或简短、明确的英文名称；每项的值始终是摘要字符串，不能改成任意嵌套对象。

案例中的六个能力名称不是所有设备的封闭枚举。增加一个能力条目属于增加映射实例，不是增加模板字段；该条目仍须描述设备事实，并与同卡型的其他实例保持一致。

**扩展边界**

本区没有另外开放的模板字段扩展位置。新的资料分类或同级结构需要另行确认，不能在填写案例时自行加入。

各 wiki 仓库内部可以组织目录、索引和正文，但这些内部结构不成为 Plan 的新增字段，本节也不规定其数据 schema。

#### 语法规则

**基本写法**

YAML 使用英文，所有自定义字段使用单数；真实仓库路径、指令名称和外部标识保持原样。禁止独立注释和行内注释。

本区只使用映射和字符串，不使用列表。映射顺序不表示优先级、执行顺序或覆盖关系；重复键不合法。

所有字符串必须非空。`null`、空字符串、空列表、空映射、数值 `NaN` 和横杠都不能代替缺失信息。`device`、`arch` 和已登记的能力摘要没有隐式默认值；`feature` 至少包含一项有依据的能力。

`feature` 的键按完整字符串识别。例如，`tcgen05.mma` 中的点和 `L1/SMEM` 中的斜杠都是名称的一部分，不表示嵌套路径。摘要是供阅读和审查的说明，不是调度指令，也不据此自动生成同步或资源配置。

**引用格式**

每个 wiki 叶子统一填写一个带引号的引用字符串：

`"repository@ref:path"`

| 部分 | 含义 |
| --- | --- |
| `repository` | 项目中可唯一识别的仓库标识；不要求仓库名称带有 `wiki-` 前缀。 |
| `ref` | 所引用资料的 tag、branch 或 commit。 |
| `path` | 该修订下的仓库内相对路径，保持真实大小写和名称。 |

普通入口可以指向一个文件或目录；`wiki.hardware` 必须指向具体卡型文件，例如 B200 的独立资料文件，而不是泛泛的 Blackwell 介绍。

一个叶子不能拼接多个引用、使用通配符或填写公共网址列表。需要多份材料时，由所绑定入口组织。已核对的上游资料目录可以直接作为入口，不必为了统一仓库名称再复制一份文档。

引用只定位外部资料，不是 Plan 内部字段别名，也不会从其他案例继承内容。正式引用必须能解析到实际存在的对象；格式正确本身不证明资料存在、版本匹配或结论有效。

**省略与占位**

`template` 的省略只有一个含义：本任务没有独立采用需要另行绑定的模板库或抽象接口。语言自身接口、编译器内部依赖，不自动构成独立模板库。已经采用某个库但资料尚未整理时，必须保留 `template` 并占位。

占位统一使用带尖括号的完整字符串：

```yaml
hardware: "<wiki-hardware@pending:Blackwell/B200.md>"
```

整个 `<...>` 表示该入口尚未形成正式绑定。其中的仓库名和路径是预期位置，不是仓库或文件已存在的声明；`@pending` 表示资料修订尚未绑定，不是真实分支。

已知的软件或 ISA 版本必须实填。确实尚未核定的版本位置使用 `pending`，例如：

```yaml
virtual_isa: "<wiki-virtual-isa@pending:PTX/pending/>"
```

这里的 `@pending` 表示入口未绑定，`PTX/pending/` 表示所需 PTX 资料版本也未核定。两者不能被解释为“不支持 PTX”，更不能授权 Coder 自行选择最新版。

占位可以让缺口在结构中可见，但不等于资料已就绪。在依赖该入口作出设计或实现判断之前，应补齐对应资料；不能把带占位的示例称为资料绑定已完成。

**版本匹配与追溯**

`ref` 固定资料修订，不要求所有软件组件共用一个版本号，也不增加独立 `version` 字段。

语言和模板资料的头部应说明其覆盖的软件身份、发布版本及必要的编译链条件。直接绑定上游仓库时，可以由同一提交中的发布说明和依赖文件提供对应关系；仅凭 tag 名称不能断定每个页面都已同步更新。

准备阶段可以用 tag 或 branch 定位资料。任务冻结时，将其解析到的 commit 填回同一个 `ref`，使后续分支移动不会改变既有任务的依据。更新引用形成明确的 Plan 修订，不静默追随 `latest`；影响判断的依赖资料也应可追溯。

硬件文件可以纠错和补全。资料修订不表示设备本身发生变化；若纠错影响能力摘要，应同步修正同卡型的相关实例，而不是只修改某个软件栈案例。

#### 关键原则

**摘要记录能力，不记录采用方式**

判断一项内容是否进入 `feature`，应看它是否改变可行的计算、存储或协作方式。“支持 CTA-pair MMA”属于能力；“本例使用双 CTA”属于 Design。当前算子的瓶颈、缓冲槽数、近似策略或性能收益不属于能力摘要。

一句话可以用分号合写紧密相关的行为和边界，但不能删掉会改变理解的限定词，例如异步操作的完成条件、协作作用域或取消操作可能失败。某项摘要中的“单线程”或“异步”只限定该项所述操作，不能推广到其他指令。

**同卡同事实，资料按栈绑定**

同一卡型采用同一份硬件文件和一致的能力摘要。换语言不能删去暂时无法使用的硬件能力，也不能复制一份随工具链变化的硬件规格。摘要没有列出的能力，不据此判为“不支持”。

工具链是否提供接口、能否正确编译，应查 `programming` 资料。发现版本或支持缺口时，应指出具体缺口，不能通过改写硬件事实、更换语言或静默降级设计来解决。

某次运行的可用资源、时钟或功耗限制不是物理卡型规格；本区不为它们增加运行环境表。实测结果也不能替代规格。使用测量知识时，应核对其设备、软件与运行条件是否适用。

**资料入口不承担其他区域的证明责任**

| 位置 | 回答的问题 |
| --- | --- |
| `meta_data.source` | 这份设计依据什么实现或材料？ |
| `contract.algorithm_requirement.pytorch_reference` | 本任务与哪个对照实现建立输入、输出和数值关系？ |
| `wiki.sota` | 可以查阅哪些实现或设计案例？ |
| `wiki.microbench` | 已有哪些操作与硬件表现之间的测量知识？ |
| `wiki.profile` | 如何采集、解释和定位问题？ |
| `realization` 中的 `feedback.evidence` | 某次替代实现实际做了什么实验，得到了什么证据？ |

`profile` 可以在入口内部组织 NCU、NSYS、Sanitizer 和 PyTorch Profiler 等材料，但不拆成新的 Plan 子字段。`sota` 不等于数值对照，也不要求照抄；源码采用某种实现，只能证明该源码的选择，不能自动证明硬件必需、数值独立或性能最优。

#### 具体案例

以下是三个独立的 B200 / SM100 任务，不是同一任务可随意切换的语言菜单。三例使用相同的硬件事实，仅改变已选软件栈及对应资料绑定。

能力摘要依据 NVIDIA 的 [PTX ISA 9.0 归档资料](https://docs.nvidia.com/cuda/archive/13.0.0/parallel-thread-execution/index.html)和 [Blackwell Tuning Guide 13.0](https://docs.nvidia.com/cuda/archive/13.0.0/blackwell-tuning-guide/index.html)。案例中 CTA 指线程块，cluster 指线程块集群，GMEM 和 SMEM 分别指全局内存和共享内存。

所有带 `<...>` 的入口仍是占位，未声明相应 wiki 已建立。以下案例用于说明填写方式，未执行编译、GPU 数值或性能测试，也未进行独立盲重建。

**Case 1：B200 + CUDA C++ + CUTLASS/CuTe**

本例选择 CUDA Toolkit 13.0.0，并独立采用 CUTLASS 4.2.1 的 C++/CuTe 接口，因此同时填写 `language` 和 `template`。模板提交的版本身份可由其[发布说明](https://github.com/NVIDIA/cutlass/blob/f3fde58372d33e9a5650ba7b80fc48b3b49d40c8/README.md)核对；虚拟 ISA 入口对应 [CUDA 13.0.0 归档中的 PTX ISA 9.0](https://docs.nvidia.com/cuda/archive/13.0.0/parallel-thread-execution/index.html)。

这是明确的软件选择与资料绑定，不是该组合已经编译验证的声明。

```yaml
hardware_specific:
  device: NVIDIA B200
  arch: SM100
  feature:
    tcgen05.mma: Single-thread asynchronous issue; TMEM accumulators; one CTA or a same-cluster CTA pair whose ranks differ only in the lowest bit.
    TMEM: Tensor Core memory separate from SMEM, with explicit allocation and dedicated access instructions.
    TMA: Asynchronous tensor-map transfers between GMEM and SMEM; GMEM-to-SMEM multicast within a cluster.
    cluster: Co-scheduled CTAs can synchronize and access peer SMEM through loads, stores, and atomics while that SMEM exists.
    CLC: Asynchronously attempts to cancel an unstarted CTA or cluster in the same grid; returns its first CTA's grid index on success.
    L1/SMEM: L1, texture cache, and SMEM share physical capacity.
  wiki:
    hardware: "<wiki-hardware@pending:Blackwell/B200.md>"
    programming:
      language: "<wiki-language@pending:CUDA-Cpp/13.0.0/>"
      template: "NVIDIA/cutlass@f3fde58372d33e9a5650ba7b80fc48b3b49d40c8:media/docs/cpp/"
      virtual_isa: "<wiki-virtual-isa@pending:PTX/9.0/>"
      machine_isa: "<wiki-machine-isa@pending:SASS/SM100/>"
    microbench: "<wiki-microbench@pending:B200/>"
    sota:
      kernel: "<wiki-sota-kernel@pending:B200/>"
      schema: "<wiki-sota-schema@pending:B200/>"
    profile: "<wiki-profile@pending:NVIDIA/>"
```

**Case 2：B200 + CuTe DSL**

本例选择 CuTe DSL，绑定 [CUTLASS 4.0.0 发布提交](https://github.com/NVIDIA/cutlass/blob/b995f933179c22d3fe0d871c3a53d11e4681950f/README.md)中的 DSL 资料。没有独立采用 C++ CUTLASS/CuTe 模板接口，因此省略 `template`，不因名称中同有 CuTe 就补入 C++ 文档。
