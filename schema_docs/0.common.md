# 公共约定

本篇定义各区共用的写法与 plan 身份；各分区的字段语义由第 1–6 篇分别说明。角色权限见 [README 分区总览](../README.md#2-schema-是什么)，创建、提取与修改文件的操作流程见[模板说明](../schema_template/README.md#填写与检查)。

按当前需要查阅：[单份 plan 与元数据](#单份-plan-与元数据)、[通用写法](#通用写法)、[shape 与整数表达式](#shape-与整数表达式)、[来源与证据](#来源与证据)、[选择条件与索引](#选择条件与索引)。需要多条并存设计时，再读[派生节点与 dispatch](#派生节点与-dispatch)。

## 单份 plan 与元数据

一个任务一个目录，沿用题目名，没有时取 `meta_data.name`。默认只有一份 YAML：`root.yaml`，保存完整 Contract 与核心 Design；节点 ID 缺省为 `root`，通常省略 `meta_data.dispatch`，表示覆盖整个契约有效域。每个 YAML 文件恰有一个映射文档。

`meta_data` 位于 plan 的最前面，用于识别任务与路径、记录设计出处与版本，不属于 Contract。它与其中的 `dispatch` 都是固定结构，只使用本篇声明的字段。

```text
meta_data
  name
  describe
  source?
  version
  dispatch?   # 存在派生节点时填写，规则见后文
```

上图和各章结构轮廓中的 `?` 表示可省略，`<name>` 表示实例自行命名的映射键，`[]` 表示列表条目。这些轮廓记号不写入 YAML。

各章的 YAML 片段只展开当前讲解的字段，必要前提随示例给出；未展示的必填字段仍需填写。各处示例独立，不跨章拼接为同一份 plan。

| 字段路径 | 值的形式 | 填写条件 | 含义与约束 |
| --- | --- | --- | --- |
| `meta_data.name` | 非空字符串 | 必填 | 计算任务的通用名称，不含 tile、CTA、架构或实现分支。 |
| `meta_data.describe` | 非空字符串 | 必填 | 一句话说明任务，不写优化理由或性能结论。 |
| `meta_data.source` | 来源字符串 | 设计有实际依据时必填；没有时省略 | 设计所依据的一项主要实现或材料。省略只说明没有设计依据，`compute` 和 `golden_reference` 照常必填。 |
| `meta_data.version` | 正整数 | 必填 | 这份 plan 的修订号，从 1 开始，数据内容变化时递增；各节点分别计数。 |

`meta_data.source` 的代码来源使用[来源格式](#来源与证据)，需要定位入口时加 `::function`；`ref` 必须固定版本，使用 commit 或不可变的 tag。论文等非代码材料写真实、可定位的出处，不伪装成仓库路径。

`source` 只记录实际依据：从现有实现提取设计时填写该实现；独立优化或自创的方案仍以某份材料为依据时照实填写；不为填满字段编造来源。任务进度和实验结果不写在这里，版本由 `version` 承担。

`version` 只标识这份 plan 修订的先后，按数据实际改动的文件独立递增，不是源码的版本号；只修改共用 Contract 时，只递增 root 的版本，纯排版变化无需递增。修订操作与实验追溯见[模板说明](../schema_template/README.md#3-填写与修订)。

### plan 与计算执行实例

plan 是静态计算设计，工作与事件身份绑定一次算子请求的实际执行：即时调用，或外层图中已录制的那次算子请求被执行。同一请求因 fallback 等实际提交多组计算时，这些工作都属于该次执行，不能将其另算逻辑调用来消除重复工作或副作用。

纯录图或实例化步骤不执行所记录的计算，也不产生这些计算的 GPU 完成事件。可以根据录制结构描述将来执行所用的 plan，但未回放不表示已经执行；每次真正执行已录制的算子请求，才产生该次执行的工作与事件实例。录图相关调用若另在非 capture 的 stream 上实际提交初始化或其他 kernel，这些实际前缀仍须保留，不能把整条路径视为零执行。

录图时已固定的 host 选择、按值标量和张量绑定，以录制或显式更新后的值为准；执行时由设备读取的张量内容，以当次读取为准，不能沿用录图时的内容。路径覆盖仍核对范围内的录图、回放和失败分支；纯录图步骤没有计算执行实例，不要求另造空计算 plan，也不是删去该 host 路径或收窄 Contract 的理由。实际提交与事件按[工作调度](4.design.work_schedule.md#提交身份与字段)表达，不能因后续失败或 fallback 抹去已经提交的工作。

## 通用写法

Schema 字段名使用一到三个英文词，结合所在层级直接说明对象、数量、索引或关系；不用同一个短名同时表示数量和编号。字段名使用单数，YAML 中的名称和文本使用英文；真实的仓库路径、函数名、指令名等外部标识保留原样。实例中不写 YAML 注释：通用约定在文档中说明，实例特有且影响结果的事实写进正式字段。

通用标识符由英文字母、数字和下划线组成，不以数字开头。节点 ID 等位置的进一步约定，以及硬件单元名称等开放字符串的写法，由对应字段规定。

YAML 的行内映射 `{...}`、行内列表 `[...]` 与展开写法都合法，检查器按解析后的数据结构校验，不规定换行样式。推荐把输入输出、symbol、分块参数等短条目写成紧凑记录，例如 `Q: {meaning: Query, shape: [token: T, d: D], dtype: bf16}`；较大的结构保持层次，数学正文保留多行。紧凑排版不放宽字段、类型或引用约束。

映射中的书写顺序没有执行或覆盖含义；列表的顺序与组合含义由各区定义。YAML anchor 与 alias 只复用相同的字段内容，不创建对象身份、共享存储或执行关系，也不跨 YAML 文档使用。`ref:`、`bind:` 等字符串是 plan 的语义引用，不是 YAML alias，允许的位置与目标范围见各区规则。

没有内容的可选字段直接省略，不以空映射、空列表、`null`、空字符串、`-` 或 NaN 代替缺失信息。具有明确含义的空结构或 `null` 只在对应字段允许时使用，例如标量 `shape: []`。wiki 入口占位与 `unknown:` 也只在各区明确允许的位置使用，不能推广成通用缺省值。

### 结构与扩展

固定结构只使用已声明字段；具名映射允许增加实例名称，但条目结构不变；封闭词汇与开放取值由对应字段区分。各章的“扩展边界”列出本区的具体位置。

当前规范、模板和检查器只维护这一套字段及取值。更名时同步修改现行实例、规则与测试，不保留字段别名、旧名回退或自动转换；归档材料保留其历史写法，不作为当前输入。YAML anchor/alias 的内容复用仍遵循上文规则，与字段版本兼容无关。

增加映射条目或填写开放取值属于填写实例。新增固定字段、封闭取值或记法属于语言结构变更，须另行确认其含义、值形式、填写条件与真实案例；维护要求见[维护说明](../schema_template/tools/README.md#回归与修改)。

## shape 与整数表达式

shape 是有序的具名维度列表，每个元素是一个“轴名: 大小”的单项映射，同一 shape 内轴名唯一。列表顺序是轴顺序；标量写 `[]`。具体描述的是完整逻辑值、工作块还是单成员容量，由所在区域规定。

大小可以是非负整数、规模名、常量名，或写成字符串的整数表达式，例如 `"2*I/G"`。表达式引用已定义的量，常用四则运算及 `min / max / floor / ceil / ceil_div`；其他函数或记号在使用处说明含义。表达式在有效域内必须得到整数：依赖整除时写明条件，需要取整或补齐时写出 `ceil` 等运算，不能隐含截断。

已知数值直接写成 YAML 数值，整数表达式写成字符串；校验不执行表达式或代入运行时规模。表达式和公式正文都供阅读，不要求符合 Python 等编程语言的语法；定义是否完整、结果是否为整数由设计审阅核对。运行时规模的引入与默认有效域见[算法要求](1.contract.algorithm_requirement.md#shape-与规模)。

## 来源与证据

仓库引用的共同形式为 `repository@ref:path`，需要定位仓库内的入口或符号时加 `::function` 或相应名称。

| 部分 | 含义 |
| --- | --- |
| `repository` | 项目中可唯一识别的仓库标识；不要求仓库名称带有 `wiki-` 前缀。 |
| `ref` | 所引用资料的 tag、branch 或 commit。 |
| `path` | 该修订下的仓库内相对路径，保持真实大小写和名称。 |

具体字段规定是否必须固定 commit、是否允许目录，以及如何标记尚未形成的绑定：设计来源见[元数据](#单份-plan-与元数据)，参考入口见[算法要求](1.contract.algorithm_requirement.md#golden_reference)，资料入口见[硬件规格](2.contract.hardware_specification.md#引用格式)，实验记录见[实现反馈](6.realization.md#有证据的替代反馈)。

| 位置 | 回答的问题 |
| --- | --- |
| `meta_data.source` | 这份设计依据什么实现或材料？ |
| `meta_data.dispatch.when` | 当前设计负责契约有效域中的哪些输入？ |
| `contract.algorithm_requirement.compute` | 调用者要求计算什么？ |
| `contract.algorithm_requirement.golden_reference` | 以哪个参考入口为标准答案、允许多大误差，与契约有哪些已知差异？ |
| `contract.hardware_specification.wiki.sota` | 可以查阅哪些实现或设计案例？ |
| `contract.hardware_specification.wiki.microbench` | 已有哪些操作与硬件表现之间的测量知识？ |
| `contract.hardware_specification.wiki.profile` | 如何采集、解释和定位问题？ |
| `realization.prefer[].feedback.evidence` | 某次替代实现实际做了什么实验，得到了什么证据？ |

源码路径只能说明原实现怎样做，不能证明它是硬件必需、数值独立或最优的。不同用途的引用即使来自同一仓库，也不能互相替代；正式引用必须能定位实际对象，格式合法不表示已经核对过内容。

## 派生节点与 dispatch

### 派生关系的含义

派生节点表示不同 workload 所需的并存设计，不表示同一路径的历史版本。`parent` 记录设计来源，不提供 Design 继承；创建与修订的方法见[模板说明](../schema_template/README.md#2-创建文件或进入已有任务)。

### 节点字段

以下路径均位于 `meta_data`，在结构轮廓中表现为 `dispatch?: id? / parent? / when`。

| 字段路径 | 值的形式 | 填写条件 | 含义与约束 |
| --- | --- | --- | --- |
| `meta_data.dispatch` | 包含 `id?`、`parent?`、`when` 的映射 | 存在派生节点时各节点填写；单份 root 通常省略 | 记录节点身份、派生关系与选择条件。省略时表示覆盖整个契约有效域的 root。 |
| `meta_data.dispatch.id` | 节点名 | 派生节点必填；root 可省略 | 在任务目录内唯一，缺省为 `root`；不改变 `meta_data.name` 的任务名称。 |
| `meta_data.dispatch.parent` | 同目录的节点 ID | 派生节点可填写，缺省为 `root`；root 不填写 | 这份设计从哪个节点派生。 |
| `meta_data.dispatch.when` | 非空英文字符串，通常为多行文本 | 使用 dispatch 时必填 | 当前节点的设计被选中的充要条件，在 root 的契约有效域内求值。 |

### 文件与共享 Contract

核心文件为 `root.yaml`，其余为 `<id>.yaml`；也接受 `.yml` 扩展名，但不能用两种扩展名重复声明同一 ID。ID 在目录内唯一，用小写字母、数字和下划线概括 workload 与设计特征，不以数字开头，例如 `q1_cluster`。派生节点显式填写与文件名一致的 `dispatch.id`；同一路径的修订沿用 ID，名称中不放随 workload 变化的 split 数等参数。

root 选用任务中较通用、能作为其他设计起点的实际 plan。派生节点用 `parent` 指向直接的设计来源，最终都连到 root。整棵树只有 root 保存 `contract.algorithm_requirement` 和 `contract.hardware_specification`；其他 YAML 省略 `contract`，其中的 Contract 名称和引用统一解析到同目录 `root.yaml`。各节点完整填写自己的 `meta_data`、Design 和必要的 `realization`，不通过父节点拼接设计片段。

同一任务各节点显式填写相同的 `name`、`describe`。参考入口和误差判据随 root 的 Contract 共用，派生节点不复制或收窄契约。共用契约的修改仍遵守 [README 的修改权限](../README.md#2-schema-是什么)。

### 单文件阅读视图

需要单个文件独立阅读时，由[正式生成工具](../schema_extract/README.md#单文件阅读视图)将指定节点与当前 root 的完整 Contract 合成一个阅读视图。创作目录仍采用上面的共享规则，worker 不手动复制多份 Contract；视图写入独立目录，不混入创作任务。

视图保留节点的元数据、完整 Design、适用的 Realization 和实际选择条件，只补入共享 Contract。`dispatch.id` 仍是原节点身份，`parent` 只记派生出处，不从该节点读取或继承内容；独立阅读与检查不需要父文件或兄弟文件。视图文件名不提供额外语义；`version` 保留原节点修订号，生成回执另绑定节点及共享 Contract 的实际字节身份。

单文件模式必须显式使用 `check_yaml.py --standalone`。它要求文件自身包含 Contract，检查内部结构和已有的关联；普通检查仍按整个创作目录执行。视图中的 `when` 保持原节点范围，不因此承诺覆盖其他路径。生成视图不修改设计、不产生新的语义批准，也不修复原产物已经存在的表达问题；需要修订时回到创作节点，经审阅后重新生成。

### 选择条件与索引

`when` 通常用 `Let … Select exactly when …` 表达，派生量和必要的运行时事实在本节点中说明，不复述 root 已给出的 shape、dtype 等约束。包含 root 和中间节点在内，各节点的条件在完整契约域内独立求值，应互斥并共同覆盖全域；`parent` 只表达设计派生关系，不把父节点的 `when` 叠加到子节点。只有一份 root 时通常省略 `meta_data.dispatch`；若显式保留，`when` 说明覆盖整个契约有效域，例如 `Select for every input in the contract domain.`，不要求固定句式。

`dispatch.md` 是每个任务的必要入口，包括只有 root 的任务。用中文展示以 root 为起点的派生树，并链接各节点，简述其 workload 与相对父节点的设计变化；只有 root 时，链接 root 并简述其 workload 与核心设计。树与 YAML 的 `parent` 对应；精确选择条件与修订号以 YAML 为准，不在索引中重复。

### 参数变化与结构变化

在节点的选择范围内，同一套合法的参数、公式与索引规则能完整表达实际设计时，数量变化保留在同一节点，不按每个 shape、tile 或成员数复制设计。实际提交集合、生产者、物化或事件关系的变化若不能由这些既有规则表达，则用 `dispatch` 分成各自完整的节点；不能把多条路径的结构并集写进一份 YAML，再用正文删除条目或改接依赖。

`when` 描述当前调用实际选择的设计，可以引用本节点已说明来源与含义的运行时事实，例如一次 probe 的返回值。它不代替 probe 执行，也不表示执行中才产生的结果能提前预测；节点仍须包含真实发生的探测与后续提交。已经提交但读取结果超时，与根本未提交是不同情形，完成事件及接续依据实际提交和协议表达。
