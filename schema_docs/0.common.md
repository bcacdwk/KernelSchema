# 公共约定

## 核心思想

本篇定义共用写法、完整设计身份、变体记录与共享规则；适用于从已有实现提取和没有源码的新设计。各分区的字段语义由第 1–6 篇说明。角色权限见 [README 分区总览](../README.md#2-schema-是什么)，文件操作见[模板说明](../schema_template/README.md#填写与检查)。

### 单份 plan 与元数据

一个任务一个目录，沿用题目名，没有时取 `meta_data.name`。从 `root.yaml` 开始，保存唯一 Contract 与一份实际完整 Design。每份完整 YAML 称为一个 plan 或设计节点，恰有一个映射文档，表达一套具体已选方案；完整性由本地定义与显式整区引用构成。其他配置、局部变化及完整方案按下文的 dispatch 规则组织。

`meta_data` 位于 plan 的最前面，用于识别任务与路径、记录设计出处与版本，不属于 Contract。它与其中的 `dispatch` 都是固定结构，只使用本篇声明的字段。

## 字段定义

### 结构轮廓

下面是 `meta_data` 的字段结构。本篇与各章结构轮廓中，`?` 表示可省略，`<name>` 表示实例自行命名的映射键，`[]` 表示列表条目。

```text
meta_data
├─ name
├─ describe
├─ source?
├─ version
└─ dispatch?
   ├─ id?
   └─ when
```

### 元数据字段

| 字段路径               | 值的形式   | 填写条件                         | 含义与约束                                                                                             |
| ---------------------- | ---------- | -------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `meta_data.name`     | 非空字符串 | 必填                             | 计算任务的通用名称，不含 tile、CTA、架构或实现分支。                                                   |
| `meta_data.describe` | 非空字符串 | 必填                             | 一句话说明任务，不写优化理由或性能结论。                                                               |
| `meta_data.source`   | 来源字符串 | 有实际外部设计来源时必填；没有时省略 | 设计所依据的一项主要实现或材料。省略只说明没有可记录的外部设计来源，`compute` 和 `golden_reference` 照常必填。 |
| `meta_data.version`  | 正整数     | 必填                             | 这份 plan 的修订号，从 1 开始，数据内容变化时递增；各节点分别计数。                                    |

`meta_data.source` 的代码来源使用[来源格式](#来源与证据)，需要定位入口时加 `::function`；`ref` 必须固定版本，使用 commit 或不可变的 tag。

`source` 只记录实际依据：从现有实现提取设计时填写该实现；独立优化或自创的方案仍以某份材料为依据时照实填写。没有源码的设计可以给出自身推导，不为填满字段编造来源。任务进度和实验结果不写在这里，版本由 `version` 承担。

`version` 按本文件的数据改动独立递增，不是源码版本号；纯排版变化无需递增。只修改共用 Contract 时，只递增 root 的版本。引用的定义改变而本文件未改时，有效 Design 可以变化，本文件版本不因此递增；追溯同时保留实际内容来源。修订操作见[模板说明](../schema_template/README.md#3-填写与修订)。

### 节点字段

`meta_data.dispatch` 只含 `id? / when`，说明完整设计的身份与承担范围。

| 字段路径                      | 值的形式                                   | 填写条件                                     | 含义与约束                                                                |
| ----------------------------- | ------------------------------------------ | -------------------------------------------- | ------------------------------------------------------------------------- |
| `meta_data.dispatch`        | 包含 `id?`、`when` 的映射 | 多个完整设计时各自填写；单份 root 有额外范围限制时填写 | 省略表示唯一的 root 设计承担整个 Contract 有效域。 |
| `meta_data.dispatch.id`     | 节点名 | 非 root 必填；root 可省略 | 在任务目录内唯一，缺省为 `root`；不改变任务名称。 |
| `meta_data.dispatch.when`   | 非空英文字符串 | 使用 dispatch 时必填 | 本份 Design 承担的输入与必要调用条件，在共享 Contract 内描述。 |

## 语法规则

### 通用写法

Schema 字段名使用一到三个英文词，结合所在层级直接说明对象、数量、索引或关系；不用同一个短名同时表示数量和编号。字段名使用单数，YAML 中的名称和文本使用英文；真实的仓库路径、函数名、指令名等外部标识保留原样。实例中不写 YAML 注释：通用约定在文档中说明，实例特有且影响结果的事实写进正式字段。

说明文字直接写对象、作用或设计依据，尽量一句读懂。使用常见术语和明确名称，不自造缩写；已有字段、公式或引用表达的内容不再复述。设计成立所需的映射、版本、初态和保证写在对应字段中。

通用标识符由英文字母、数字和下划线组成，不以数字开头。节点 ID 等位置的进一步约定，以及硬件单元名称等开放字符串的写法，由对应字段规定。

普通字符串直接书写，需保持字符串类型或避免 YAML 歧义时使用引号或块文本。YAML 的行内映射 `{...}`、行内列表 `[...]` 与展开写法都合法，检查器按解析后的数据结构校验，不规定换行样式。推荐把输入输出、symbol、分块参数等短条目写成紧凑记录，例如 `Q: {meaning: Query, shape: [token: T, d: D], dtype: bf16}`；较大的结构保持层次，数学正文保留多行。紧凑排版不放宽字段、类型或引用约束。

映射中的书写顺序没有执行或覆盖含义；列表的顺序与组合含义由各区定义。YAML anchor 与 alias 只复用相同的字段内容，不创建对象身份、共享存储或执行关系，也不跨 YAML 文档使用。`ref:`、`bind:` 等字符串是 plan 的语义引用，不是 YAML alias，允许的位置与目标范围见各区规则。

没有内容的可选字段直接省略，不以空映射、空列表、`null`、空字符串、`-` 或 NaN 代替缺失信息。具有明确含义的空结构或 `null` 只在对应字段允许时使用，例如标量 `shape: []`。wiki 入口占位与 `unknown:` 也只在各区明确允许的位置使用，不能推广成通用缺省值。

### shape 与整数表达式

shape 是有序的具名维度列表，每个元素是一个“轴名: 大小”的单项映射，同一 shape 内轴名唯一。列表顺序是轴顺序；标量写 `[]`。具体描述的是完整逻辑值、工作块还是单成员容量，由所在区域规定。

大小可以是非负整数、规模名、常量名，或写成字符串的整数表达式，例如 `2*I/G`。表达式引用已定义的量，常用四则运算及 `min / max / floor / ceil / ceil_div`；其他函数或记号在使用处说明含义。表达式在有效域内必须得到整数：依赖整除时写明条件，需要取整或补齐时写出 `ceil` 等运算，不能隐含截断。

已知数值直接写成 YAML 数值，整数表达式写成字符串；校验不执行表达式或代入运行时规模。表达式和公式正文都供阅读，不要求符合 Python 等编程语言的语法；定义是否完整、结果是否为整数由设计审阅核对。运行时规模的引入与默认有效域见[算法要求](1.contract.algorithm_requirement.md#shape-与规模)。

### 来源与证据

仓库引用的共同形式为 `repository@ref:path`，需要定位仓库内的入口或符号时加 `::function` 或相应名称。

| 部分           | 含义                                                            |
| -------------- | --------------------------------------------------------------- |
| `repository` | 项目中可唯一识别的仓库标识；不要求仓库名称带有 `wiki-` 前缀。 |
| `ref`        | 所引用资料的 tag、branch 或 commit。                            |
| `path`       | 该修订下的仓库内相对路径，保持真实大小写和名称。                |

具体字段规定是否必须固定 commit、是否允许目录，以及如何标记尚未形成的绑定：设计来源见[元数据](#单份-plan-与元数据)，参考入口见[算法要求](1.contract.algorithm_requirement.md#golden_reference)，资料入口见[硬件规格](2.contract.hardware_specification.md#引用格式)，实验记录见[实现反馈](6.realization.md#有证据的替代反馈)。

| 位置                                                | 回答的问题                                                     |
| --------------------------------------------------- | -------------------------------------------------------------- |
| `meta_data.source`                                | 这份设计依据什么实现或材料？                                   |
| `meta_data.dispatch.when`                         | 当前设计负责契约有效域中的哪些输入？                           |
| `contract.algorithm_requirement.compute`          | 调用者要求计算什么？                                           |
| `contract.algorithm_requirement.golden_reference` | 以哪个参考入口为标准答案、允许多大误差，与契约有哪些已知差异？ |
| `contract.hardware_specification.wiki.sota`       | 可以查阅哪些实现或设计案例？                                   |
| `contract.hardware_specification.wiki.microbench` | 已有哪些操作与硬件表现之间的测量知识？                         |
| `contract.hardware_specification.wiki.profile`    | 如何采集、解释和定位问题？                                     |
| `realization.feedback[].evidence`                 | 某次替代实现实际做了什么实验，得到了什么证据？                 |

源码路径只能说明原实现怎样做，不能证明它是硬件必需、数值独立或最优的。不同用途的引用即使来自同一仓库，也不能互相替代；正式引用必须能定位实际对象，格式合法不表示已经核对过内容。

## 派生节点与 dispatch

Dispatch 用少量完整设计和一次性的变体记录保存核心设计决定。完整 YAML 交代一套具体的端到端方案，`dispatch.md` 组织其范围、关系和其他配置的变化；源码的选择分支不逐一对应设计节点。

### 参数变化与结构变化

本份 YAML 明确选定自己的分块、worker 组成、缓冲和机制，定义这些参数及其关系。其他取值、模式或组合写入 `dispatch.md`，不以开关、枚举、选择公式、查表或自然语言选路留在 YAML 中；把配置选择改写为 `min` 等表达式也不改变其性质。

当前方案随输入产生的尺寸、索引、有效区域和工作量仍在 Design 中定义，不能移到目录作为正文唯一依据。算法的有效分支和当前机制所需的循环、尾块、空工作、队列领取与终止、验证状态判断照常保留。例如，固定分块后用 `ceil_div` 计算工作数、用 `min` 截取尾块，或根据本次产生的 `Clean` 决定必要动作，都属于当前方案的执行；根据输入在三槽与四槽之间选择缓冲配置，则属于其他配置的选择。区别在决定的对象，不在编译期、运行期或公式写法。

例如，已选自适应尾块搬运机制、槽容量固定为 128 行时，按本块有效行数向上取整到 16、32、64 或 128 行，是本次传输范围；正文交代各范围的有效数据、实际搬运与完成计数。是否采用这种自适应机制则是配置选择，其他选择记入目录。离散取值或选择不同 descriptor 本身不决定分类。

| 差异 | 判断依据 | 记录方式 |
| --- | --- | --- |
| 同规则参数变化 | 同一机制下的其他取值，所需联动可以明确说明 | 当前取值留在 YAML，其他取值及联动在目录记录一次 |
| 局部新决定 | 能围绕基线已有值、step、role 或存储说清改变及必要联动，边界外的主体组织继续成立 | 在目录记录一次变化，直接引用完整基线及已有对象 |
| 新的整体设计 | 需要重新贯通解释主要计算、输出形成、工作归属或主协作组织 | 作为独立候选；选定完整交付时保留一份有独特价值的 YAML |
| 已有决定的组合 | 具体接口相容，组合没有引入新的整体组织 | 说明必要的组合关系与局部联动，不按配对新建节点 |
| 实现细节 | 不改变所选设计的结果、性能取舍或必要保证 | 留给实现；必要的来源行为简述一次 |

判断新增信息的价值，看省去它是否会误解计算、性能原因或协作关系；改动行数、分区数和提交次数不决定记录深度。判断局部闭合时，沿基线已有对象说明变化的输入、输出及必要联动，再核对边界外哪些主要计算、工作归属和协作仍可直接沿用。能列出改动对象并不等于局部：把新的主计算、主要领取与退出或整条主循环协作包成一个对象，仍需按整体设计判断。

例如，只重排输入 cache 后交给原 attention，可围绕既有输入视图记录准备、物化、交接和读取变化，原 attention 的工作归属、递推及输出仍成立。若把独立的逐 chunk 输出工作移入状态递推，取消全部入口快照与中间量交接，则输出的独立工作轴、生产者和主执行链都改变，需要重新贯通为整体候选；不能仅因差额写得短就称为局部。原主计算仍执行、但结果已不再供最终输出使用时，也要沿实际输出来源判断。

split-KV 的部分结果与跨 kernel 归并需要完整方案；相同数学下，持久 worker 的补领、提前预取及跨工作寿命也可能形成独特完整设计，不能只概括为给单工作方案增加队列。Softmax 计算一份 alpha 供自身与 Correction 复用，则可以记录载荷、数值与生产消费的必要联动，不按每种调度重复整份 attention。

同一决定只记一次。同名同 shape 不证明可组合，需核对值含义、精度、有效区域、生产消费与完成关系。必须保留的信息可以成为完整设计、变体记录或未展开的独立候选说明，不因此都取得完整 YAML 身份。

### 文件与共享 Contract

root 选择一份便于理解和比较的实际完整设计，作为默认阅读入口。其他设计可以独立并列，也可以由已有设计派生或组合；共同 Contract 的归属不要求共同的设计祖先。

同一算子的当前完整设计集合含 root 最多 10 份，这是硬上限；保留关键设计信息的前提下越少越好，每份都须有独特的完整设计价值。发现或研究的候选可以更多，选定的完整集合仍遵守此上限。已研究但未选定完整展开的独立方案在目录范围中诚实说明，不改称参数或局部变化，不以拆目录、复制 Contract、另藏完整 schema 或保留“历史”名义继续交付额外完整设计。

核心文件为 `root.yaml`，其余为 `<id>.yaml`；也接受 `.yml`，同一 ID 只使用一种扩展名。ID 在目录内唯一，用小写字母、数字和下划线概括稳定的设计特征，不以数字开头，例如 `split_kv`。非 root 节点显式填写与文件名一致的 `dispatch.id`；同一设计的修订沿用 ID，不把随 workload 变化的参数放进名称。

只有 root 保存 `contract.algorithm_requirement` 和 `contract.hardware_specification`，其他 YAML 省略 `contract`；所有 Contract 引用统一解析到同目录 root。各设计填写相同的任务 `name / describe`，自己的其他元数据与必要的 `realization`；三个 Design 区域分别本地定义或显式引用。每个完整节点在自身范围内从 Contract 输入定义到全部输出。

范围较窄不改变共同的输入域、参考入口、误差或硬件要求。共用 Contract 的修改遵守 [README 的修改权限](../README.md#2-schema-是什么)。

### 选择条件与索引

`when` 只表示本份设计承担的输入和必要调用条件。范围可重叠，也可未覆盖整个 Contract；目录不规定隐式优先级，root 不自动承担未记录的情况。单份 root 有额外限制时也须显式填写 `when`。

范围依据设计的参数、容量和接口条件确定，可保守采用已核对的子域；不复述 Contract 已有约束。原实现的选择阈值、已验证样本与最大可行域是不同事实，`when` 不承担原 selector 或验证证明的职责。动态条件须有明确来源；所需的初态、就绪、版本与资源存续保证仍在对应字段表达，不能由范围文字补造。

`dispatch.md` 是每个任务的中文入口，包括只有 root 的任务。以下是唯一的最小格式：“范围”和“完整设计”必需；有实际变体内容时才写“变体与组合”。

```markdown
# <任务名称>

## 范围

当前收录范围，以及影响理解或使用的边界。

## 完整设计

| 设计 | 具体机制与保留理由 | 关系 |
| --- | --- | --- |
| [root](root.yaml) | 本份具体方案的主要机制与保留理由 | 阅读入口，保存唯一 Contract |

## 变体与组合

### <有意义的名称>（<类型>）

- 基线：当前完整 YAML 链接及其中已有对象；多基线直接并列。
- 差异与联动：相对这些基线的变化及必要配套，已有定义直接引用。
- 条件与依据：适用的接口或范围、已有依据及影响使用的缺口。
```

完整设计表列出全部当前完整 YAML，摘要足以辨认各自的机制与保留理由；独立方案可并列，来源或组合关系按实际内容说明。精确参数、`when` 与修订号以 YAML 为准。范围中确有已研究但未完整展开的独立候选时，简述其名称、独特机制、范围或出处及取舍理由，明确没有交付完整 schema；没有此类候选不增设空小节。共同 Contract、任务要求实现的范围与目录实际收录的范围分别说明；记录缺口不解除任务要求的完整交付义务。

每条变体的标题从“参数”“局部”“组合”中选定一种类型，正文包含基线、差异与联动、条件与依据三个信息项；短条目可合成一句，不要求额外子表或空字段。源码事实使用固定来源；原创设计可给出推导及待验证判断。设计成立条件、原实现选择条件和实验覆盖按实际已有事实区分，不补造来源或验证。

### 局部记录与完整方案

最终每条参数、局部或组合记录都直接定位至少一个当前完整 YAML 及其中已有对象。用数学符号、step、role、存储或唯一的 rewrite 名称定位，不以易漂移的行号和列表序号作为修改地址；源码证据仍可使用固定版本的行链接。同一变化适用于多个基线时并列链接，说明各自对象对应及必要区别，共同差额只写一次。

组合可以链接原始参数或局部条目，但仍直接列出完整基线，只补已知相容关系和新增限制，不层层把组合当作新基线。基线已有的数学、资源和协议直接引用；不逐主线、后端或参数配对复制记录，不默认任意组合都成立。条目的排列和引用不产生 patch 应用顺序，也不修改基线的参数或 `when`。

变体记录没有完整 plan 的 ID、版本或独立交付身份。它可以讨论基线范围外的变化，但须说明自己的条件和依据；未完整展开的独立候选不能假借局部基线或变体记录冒充完整交付。完整 YAML 的内容只由本地定义和整区引用确定，目录不能补齐其中缺少的定义。

数值舍入、输出生产者、初始化与资源退休等变化必须说清。准备或错误前缀可以按设计意义概括，但在途访问不会因调用失败或未列为节点而消失；记录的保证要覆盖其实际依赖的状态。已知来源限制在受影响的定义或局部记录中说明，不补造等待、隔离或有效域保证。

实施当前 YAML 时遵守其完整有效 Design，目录中的变化不会自动应用。任务选择某项参数、局部变化或组合时，应明确本次具体选择、必要联动及适用范围。只有任务要求交付该方案的完整 schema 时，才整理实际选定的完整设计，并遵守数量与独特价值规则；目录笔记本身不产生新建或重写完整算子的义务。

### Design 整区引用

`design.math_reshape`、`design.work_schedule`、`design.tile_pipeline` 各自填写完整本地映射，或恰好只有 `from` 一个字段的映射。root 的三个区域全部本地定义；其他设计中相同的完整区域直接使用 `from`，三区可以分别选择来源，例如：

```yaml
design:
  math_reshape: {from: reshape_plan}
  work_schedule: {from: schedule_plan}
  tile_pipeline: {from: pipeline_plan}
```

`from` 的值是同任务目录中另一个完整设计的 ID，引用其同名整区，不依赖文件排列顺序。目标可以继续引用，最终落到本地完整定义；该节点称为实际 provider。任一区域的引用都构成使用节点到来源节点的边，整个节点引用图须无环，包括跨区相互引用。

本地与引用二选一，不附加覆盖字段，不引用片段、局部记录或其他目录。完整设计中某区需要任何内容修改时，该区须完整本地定义，其余相同区继续共享。共享区内部已固定的选择不能由目录覆盖，也不能为了复用改成可选配置容器。`from`、对象属性的 `ref:`、符号的 `bind:` 和单文件 YAML alias 各按自己的作用域使用。

引入的定义在**使用节点**的完整上下文中绑定：root Contract、当前数学符号与调度参数、step/worker、流水线存储及事件均按本节点解析。例如 `bind:design.work_schedule::Bk` 取使用节点已选的 Bk，不要求来源节点的外部 Bk 同值；整个共享区的公式、值含义、精度、有效域、边界和接口仍须在当前上下文成立。整区共享仍需审阅当前三区与必要 Realization 的接合。

引用不携带来源设计的 `when`、元数据、版本或 `realization`。三区全部引用也遵循上文的设计划分原则，引用来源不同本身不构成新设计；不能创建只有 provider 用途、没有自身独特完整设计价值的节点。设计间的借鉴关系在目录说明，不产生共同设计父或运行依赖，实际内容来源由 `from` 唯一确定。

创作文件称为 raw，展开三区后的内容称为 effective。有效内容来源包括本节点、root 与所有实际中间引用及 provider；审阅和实验追溯固定这些文件的版本与内容身份。共用定义改变时，复核实际引用者的当前接口及依赖该定义解释差额的局部记录；纯来源说明不产生内容继承。

### 单文件阅读视图

单文件阅读视图补入当前 root 的完整 Contract，展开目标节点的三个 Design 区域，保留该节点的元数据、`when`、修订号与 Realization。视图可独立阅读，仍是原设计的内容视图，不产生新的节点身份或覆盖范围。

视图与创作目录分开保存，记录原节点、root、全部实际引用链及 provider 的内容摘要。生成前核对完整有效 Design，修订回到原定义进行；来源改变后重新生成。展开本身不构成正确性或适用性验证。

## 关键原则

### 结构与扩展

固定结构只使用已声明字段；具名映射允许增加实例名称，但条目结构不变；封闭词汇与开放取值由对应字段区分。各章的“扩展边界”列出本区的具体位置。

正式 schema 只使用本规范声明的字段与取值。结构更名直接替换定义与使用位置，不设置同义字段或自动转换；归档材料不作为当前输入。YAML anchor/alias 只按上文规则复用内容。

增加映射条目或填写开放取值属于填写实例。新增固定字段、封闭取值或记法属于语言结构变更，须另行确认其含义、值形式、填写条件与真实案例；维护要求见[维护说明](../schema_template/tools/README.md#回归与修改)。
