# 硬件规格

## 核心思想

`contract.hardware_specification` 固定目标设备、关键硬件能力和当前任务的资料入口。它接收任务已选定的设备与实现栈，向 Designer 和 Coder 提供共同的硬件依据、编程依据和查询位置；双方可以决定怎样利用这些条件，但不能自行更换设备、实现栈或资料版本。

本区分三类内容：`device / arch / execution / feature` 是设备事实，同一设备的这几项不因算子、语言或设计改变；`stack` 是本任务已选的实现栈；`wiki` 把设备与实现栈绑定到固定版本的资料。

`execution` 声明这台设备有哪些执行单元、怎样分层，是下游 worker 与 lane 的词汇来源。`feature` 只保留会改变设计空间的机制与关键缺项，完整规格、指令列表和数值细节留在资料中。`wiki` 每类只绑定一个入口，由入口内部组织材料，避免 Plan 复制手册、测量表和工具清单。

本区不决定数学改写、工作划分、角色分工、缓冲配置或流水顺序，也不记录本次运行的资源配置、profiler 输出或性能结论。硬件支持、软件能否表达、具体实现的实测表现必须分别判断。

对应 CUE 定义为 [schema.cue](../schema_template/schema.cue) 中的 `#HardwareSpecification`。

## 字段定义

以下是本区的字段结构。`?` 表示条件可省略，`<unit>` 与 `<name>` 表示实例自行登记的映射键；这些记号不写入实例。

```text
hardware_specification
├── device
├── arch
├── execution
│   └── <unit>
├── feature
│   └── <name>
├── stack
│   ├── language
│   ├── template?
│   └── toolchain
└── wiki
    ├── hardware
    ├── programming
    │   ├── language
    │   ├── template?
    │   ├── virtual_isa?
    │   └── machine_isa?
    ├── microbench
    ├── sota
    │   ├── kernel
    │   └── schema
    └── profile
```

下表路径均相对于 `contract.hardware_specification`。“引用”指后文定义的单个字符串，不是嵌套对象或列表。

| 字段路径 | 值的形式 | 填写条件 | 含义与约束 |
| --- | --- | --- | --- |
| `device` | 非空字符串 | 必填 | 执行本任务的具体型号，不以代际或系列名代替。封装、存储容量或分区模式改变可见资源时，分别视为不同设备。 |
| `arch` | 非空字符串 | 必填 | 厂商用来选择指令集与资料的架构标识。具体的编译目标参数属于实现选择，需要固定时写进 `realization.require`。 |
| `execution` | 非空具名映射 | 必填 | 键是本设备的执行单元名称，值是一句英文摘要，说明该单元由什么组成、嵌在哪一层、占用什么物理资源。 |
| `feature` | 非空具名映射 | 必填 | 键是机制或缺项名称，值是一句英文摘要，写清机制本身及会改变判断的边界。 |
| `stack` | 固定结构映射 | 必填 | 本任务已选实现栈的身份，与下面绑定的资料修订是两回事。 |
| `stack.language` | 非空字符串 | 必填 | 已选语言或 DSL 及其版本，只有一项；语言没有独立版本号时，版本身份由 `toolchain` 承担。 |
| `stack.template` | 非空字符串 | 任务独立采用模板库或抽象接口时填写 | 该库或接口的身份与版本。 |
| `stack.toolchain` | 非空字符串 | 必填 | 把该语言降到目标 ISA 的编译工具链及版本；由语言发行版自带时，写该发行版提供的工具链身份。 |
| `wiki` | 固定结构映射 | 必填 | 资料入口集合，仅包含轮廓中声明的字段。 |
| `wiki.hardware` | 引用 | 必填 | 具体型号的完整资料文件，覆盖计算、存储、访存、通信、同步、执行组织、数值格式与精度行为及必要边界。不能只绑定代际目录。 |
| `wiki.programming` | 固定结构映射 | 必填 | 已选实现栈的编程资料：语言与模板各自对应 `stack` 中的同名项，指令层资料对应 `stack.toolchain` 实际生成的指令集。 |
| `wiki.programming.language` | 引用 | 必填 | `stack.language` 的语法、编程模型、接口、编译与使用规则，不是候选语言菜单。 |
| `wiki.programming.template` | 引用 | 与 `stack.template` 同时出现 | 该模板库或抽象接口的资料。 |
| `wiki.programming.virtual_isa` | 引用 | 该栈存在虚拟指令层时必填 | 虚拟指令集的语义、操作数、类型与形状约束、支持条件及同步规则。 |
| `wiki.programming.machine_isa` | 引用 | 该栈存在可查的机器指令层时必填 | 目标架构的机器指令与反汇编资料。资料内部应区分官方定义与观察结果。 |
| `wiki.microbench` | 引用 | 必填 | 操作及组合执行的测量知识入口，不是本次 benchmark 配置或输出文件。 |
| `wiki.sota` | 固定结构映射 | 必填 | 实现与设计案例入口。 |
| `wiki.sota.kernel` | 引用 | 必填 | 面向本设备的算子实现与参考库索引，不保证其中每项都是最优实现。 |
| `wiki.sota.schema` | 引用 | 必填 | 可借鉴的设计案例集合，不自动承诺案例已通过验收。 |
| `wiki.profile` | 引用 | 必填 | 工具使用、数据采集、报告与 dump 解释，以及分析定位方法。始终只有一个入口。 |

### 固定结构

`hardware_specification`、`stack`、`wiki`、`wiki.programming` 和 `wiki.sota` 只允许轮廓中声明的同级字段。

条件字段的省略与资料缺口的占位分别见[省略与占位](#省略与占位)；其余字段必填。

### 具名映射

`execution` 与 `feature` 的键由实例登记，优先使用官方标识或简短、明确的英文名称。键分别在各自映射中标识条目；两个映射可以同名，不设跨表唯一性限制，因为字段路径已经区分执行单元与机制。每项的值始终是摘要字符串，不能改成任意嵌套对象。

`execution` 只登记设备实际存在、且设计需要称呼的层级：能承担一份工作、一类动作，或共同受限于同一份物理资源的单元。比下游动作粒度更细的层级不单独登记。规模数值只在限定单元组成时出现，例如一个单元最多容纳多少下层单元；设备级的数量与容量属于 `wiki.hardware`。

`feature` 的条目受删除测试和条数约束，见“关键原则”。案例中的名称不是任何设备的封闭枚举；增加一个条目属于增加映射实例，不是增加模板字段，该条目仍须描述设备事实，并与同设备的其他实例保持一致。

### 扩展边界

本区没有另外开放的模板字段扩展位置；新的资料分类或同级结构遵循[公共扩展规则](0.common.md#结构与扩展)。

各 wiki 仓库内部可以组织目录、索引和正文，但这些内部结构不成为 Plan 的新增字段，本节也不规定其数据 schema。

## 语法规则

### 基本写法

通用命名与 YAML 写法见[公共约定](0.common.md#通用写法)；本区特有且影响判断的事实写进正式字段。

本区只使用映射和字符串，不使用列表。映射顺序不表示优先级、执行顺序或覆盖关系，`execution` 的嵌套关系写在各自的摘要里，不靠书写顺序表达。

本区没有隐式默认值；所有字符串必须非空，`execution` 与 `feature` 各至少包含一项有依据的条目。资料缺口使用下文规定的入口占位。

`execution` 与 `feature` 的键按完整字符串识别。例如，`tcgen05.mma` 中的点和 `L1/SMEM` 中的斜杠都是名称的一部分，不表示嵌套路径。

### 引用格式

每个 wiki 叶子统一填写一个带引号的 `"repository@ref:path"` 字符串；各部分含义见[来源与证据](0.common.md#来源与证据)。

普通入口可以指向一个文件或目录；`wiki.hardware` 必须指向具体型号的资料文件，而不是代际或系列介绍。

一个叶子不能拼接多个引用、使用通配符或填写公共网址列表。需要多份材料时，由所绑定入口组织。已核对的上游资料目录可以直接作为入口，不必为了统一仓库名称再复制一份文档。

引用只定位外部资料，不是 Plan 内部字段别名，也不会从其他案例继承内容。正式引用必须能解析到实际存在的对象。

### 省略与占位

省略表示这一层在本任务或本实现栈中不存在：没有独立采用模板库时不写 `template`，没有虚拟指令层的栈不写 `virtual_isa`。语言自身的接口和编译器内部依赖不构成独立的模板库；语言名称里出现某个库的名字，也不等于采用了该库的接口。

这一层确实存在、只是资料尚未整理时，保留入口并占位。占位统一使用带尖括号的完整字符串：

```yaml
hardware: "<wiki-hardware@pending:Blackwell/B200.md>"
virtual_isa: "<wiki-virtual-isa@pending:PTX/pending/>"
```

整个 `<...>` 表示该入口尚未形成正式绑定。其中的仓库名和路径是预期位置，不是仓库或文件已存在的声明；`@pending` 表示资料修订尚未绑定，不是真实分支。已知的资料版本必须实填，确实尚未核定的版本位置同样写 `pending`，如上面的 `PTX/pending/`。它表示所需的 PTX 资料版本待定，不能被解释为“不支持 PTX”，更不能授权 Coder 自行选择版本。

占位让缺口在结构中可见，但不等于资料已就绪。在依赖该入口作出设计或实现判断之前，应补齐对应资料；不能把带占位的示例称为资料绑定已完成。

### 版本匹配与追溯

`stack` 记录软件身份与版本，`ref` 固定资料修订，两者是不同的事实：同一份资料修订可以服务多个软件版本，更新 `ref` 也不表示实现栈变了。版本不另设字段，软件组件之间也不要求共用一个版本号。

语言和模板资料的头部应说明其覆盖的软件身份、发布版本及必要的编译链条件，使 `stack` 与资料的对应关系可核对。直接绑定上游仓库时，可以由同一提交中的发布说明和依赖文件提供对应关系。

准备阶段可以用 tag 或 branch 定位资料。任务冻结时，将其解析到的 commit 填回同一个 `ref`，使后续分支移动不会改变既有任务的依据。更新引用形成明确的 Plan 修订，递增 `meta_data.version`，不静默追随 `latest`；影响判断的依赖资料也应可追溯。

硬件文件可以纠错和补全。资料修订不表示设备本身发生变化；若纠错影响 `execution` 或 `feature`，应同步修正同一设备的相关实例，而不是只修改某个实现栈的案例。

## 关键原则

### `feature` 记录会改变设计空间的机制，不是功能清单

判据是删除测试：删掉这一条，读者会不会做出一个不可实现的设计，或者错误地排除一个本来可行的设计？会，才写。“支持 CTA-pair MMA”属于机制；“本例使用双 CTA”“当前瓶颈在某个单元”属于 Design，不进入本区。缓冲槽数、近似策略和性能收益同样不属于这里。

因此，“本代新增”不是入选理由，“由来已久”也不是排除理由。一项能力即使是新增的，不改变设计空间就不写；一项机制即使存在了几代，只要读者容易默认它不存在、或默认它没有限制，就要写。关键缺项可以显式写明不支持并指出替代路径，用来阻止跨设备的默认继承；摘要没有列出的能力，不据此判为“不支持”。

条目数量有限，通常不超过十条。需要更多条目时，多半是在复述资料：具体数值、完整指令列表和参数组合属于 `wiki`。

一句话可以用分号合写紧密相关的行为和边界，但不能删掉会改变理解的限定词，例如异步操作的完成条件、协作作用域或取消操作可能失败。某项摘要中的“单线程”或“异步”只限定该项所述操作，不能推广到其他指令。

### 同一设备同一套事实，实现栈只改变资料绑定

同一设备采用同一份硬件文件，以及一致的 `execution` 与 `feature`。换语言不能删去暂时无法使用的硬件能力，也不能复制一份随工具链变化的硬件规格。

执行单元的名称与层级只在本区声明一次：`execution` 写单元由什么组成、嵌在哪一层、占用什么物理资源，`feature` 写这些单元之间能做什么，同一事实不写两遍。下游只能使用本区登记的单元名称；目标设备没有某个层级时，按这里登记的单元重新表达设计，而不是借用其他设备的形近名称。

工具链是否提供接口、能否正确编译，应查 `programming` 资料。发现版本或支持缺口时，应指出具体缺口，不能通过改写硬件事实、更换实现栈或静默降级设计来解决。

某次运行的可用资源、时钟或功耗限制不是设备规格；本区不为它们增加运行环境表。实测结果也不能替代规格。使用测量知识时，应核对其设备、软件与运行条件是否适用。

### 资料入口的职责

wiki 与设计来源、参考入口、实验记录的区别见[来源与证据](0.common.md#来源与证据)。`profile` 可以在入口内部组织 NCU、NSYS、Sanitizer 和 PyTorch Profiler 等材料，但不拆成新的 plan 子字段；`sota` 提供可借鉴的案例，不要求照抄。

## 具体案例

以下三例分别是 NVIDIA、AMD 与昇腾上的独立任务，用来说明同一组字段怎样容纳不同的设备身份、执行模型与资料层次：case 1 的实现栈有完整的四层编程资料，case 2 所在的栈没有对外的虚拟指令层，case 3 还没有独立采用模板库。换实现栈只改变 `stack` 与 `wiki.programming`，同一设备的 `device / arch / execution / feature` 不随之变化。

各例的事实依据在相应段落中给出。

### Case 1：B200 + CUDA C++ + CUTLASS/CuTe

本例选择 CUDA Toolkit 13.0.0，并独立采用 CUTLASS 4.2.1 的 C++/CuTe 接口，因此 `stack.template` 与 `wiki.programming.template` 同时出现。模板提交的版本身份可由其[发布说明](https://github.com/NVIDIA/cutlass/blob/f3fde58372d33e9a5650ba7b80fc48b3b49d40c8/README.md)核对。虚拟 ISA 对应 [CUDA 13.0.0 归档中的 PTX ISA 9.0](https://docs.nvidia.com/cuda/archive/13.0.0/parallel-thread-execution/index.html)，机器 ISA 按架构绑定：两层资料的版本轴不同，所以是两个入口。

执行层级与能力摘要依据上述 PTX ISA 9.0 与 [Blackwell Tuning Guide 13.0](https://docs.nvidia.com/cuda/archive/13.0.0/blackwell-tuning-guide/index.html)。`mbarrier` 与 `setmaxnreg` 都不是本代新增，但按通用模型推理时容易漏掉，缺了它们会误判可行的 warp 分工与异步重叠。

```yaml
hardware_specification:
  device: NVIDIA B200
  arch: SM100
  execution:
    warp: 32 threads that issue as one instruction stream; the smallest scope of a collective instruction.
    CTA: Warps resident on one SM, sharing its SMEM allocation and barriers.
    cluster: CTAs co-scheduled on SMs of one GPU processing cluster; the size is fixed at launch.
  feature:
    tcgen05.mma: Single-thread asynchronous issue; TMEM accumulators; one CTA or a same-cluster CTA pair whose ranks differ only in the lowest bit.
    TMEM: Tensor Core memory separate from SMEM, with explicit allocation and dedicated access instructions.
    TMA: Asynchronous tensor-map transfers between GMEM and SMEM; GMEM-to-SMEM multicast within a cluster.
    mbarrier: Asynchronous copies and MMA report completion by arriving at an SMEM barrier; issue order does not imply completion order.
    setmaxnreg: A warp group can release or claim per-thread registers at runtime, so roles in one CTA can hold asymmetric budgets within its total.
    cluster: Peer SMEM in the same cluster is addressable by load, store and atomic while that SMEM exists.
    CLC: Asynchronously attempts to cancel an unstarted CTA or cluster in the same grid; returns its first CTA's grid index on success.
    L1/SMEM: L1, texture cache, and SMEM share physical capacity.
  stack:
    language: CUDA C++17
    template: CUTLASS 4.2.1
    toolchain: CUDA Toolkit 13.0.0
  wiki:
    hardware: "<wiki-hardware@pending:Blackwell/B200.md>"
    programming:
      language: "<wiki-language@pending:CUDA-Cpp/13.0.0/>"
      template: "NVIDIA/cutlass@f3fde58372d33e9a5650ba7b80fc48b3b49d40c8:media/docs/cpp/"
      virtual_isa: "<wiki-virtual-isa@pending:PTX/9.0/>"
      machine_isa: "<wiki-machine-isa@pending:SASS/SM100/>"
    microbench: "<wiki-microbench@pending:B200/>"
    sota:
      kernel: "<wiki-sota-kernel@pending:B200/>"
      schema: "<wiki-sota-schema@pending:B200/>"
    profile: "<wiki-profile@pending:NVIDIA/>"
```

### Case 2：MI355X + HIP + Composable Kernel

本例选择 ROCm 7.2.4，并独立采用同一发布的 [Composable Kernel](https://github.com/ROCm/composable_kernel/releases)，资料入口绑定该发布标签；该库的开发主线已迁入 `ROCm/rocm-libraries`。HIP 直接编译到 gfx950 机器指令，这一栈没有 PTX 式的对外虚拟指令层，因此省略 `virtual_isa`；`machine_isa` 对应厂商正式发布的 [CDNA4 指令集手册](https://www.amd.com/content/dam/amd/en/documents/instinct-tech-docs/instruction-set-architectures/amd-instinct-cdna4-instruction-set-architecture.pdf)，是官方定义而不是反汇编观察。

设备身份与执行层级依据 [ROCm 的硬件规格表](https://rocm.docs.amd.com/en/docs-7.0.0/reference/gpu-arch-specs.html)与 [MI350 系列微架构说明](https://rocmdocs.amd.com/en/latest/reference/gpu-arch/mi350.html)，指令语义、搬运宽度与转置读取依据上述手册。`tensor_map_transfer` 与 `TF32` 写成显式缺项，用来挡住从其他架构继承过来的默认假设。

```yaml
hardware_specification:
  device: AMD Instinct MI355X
  arch: gfx950
  execution:
    wavefront: 64 work-items that issue as one instruction stream; operands sit in per-lane VGPRs, matrix accumulators in AccVGPRs.
    workgroup: Wavefronts resident on one CU, sharing that CU's LDS allocation.
    XCD: 32 active CUs with their own L2 slice; one device carries eight of them.
  feature:
    v_mfma: Matrix instructions issued by a whole wavefront; a result becomes readable only after enough independent instructions, which the program must supply.
    v_mfma_scale: One instruction loads E8M0 block scales and applies them to an FP8, FP6 or FP4 product; the scales do not carry over to later MFMA.
    global_load_lds: Loads up to 128 bits per lane from global memory straight into LDS without staging in VGPRs; addressing stays per-lane.
    ds_read_tr: Reads LDS while transposing 4-, 6-, 8- or 16-bit matrix elements into VGPRs.
    s_waitcnt: Outstanding memory operations are tracked by counters rather than per-buffer barriers, and different instruction types return out of order.
    tensor_map_transfer: Not available; there is no descriptor-driven transfer engine, so multi-dimensional movement is expressed as per-lane addressing.
    TF32: Not available in this matrix core.
  stack:
    language: HIP C++17
    template: Composable Kernel rocm-7.2.4
    toolchain: ROCm 7.2.4
  wiki:
```

### Case 3：昇腾 950PR + Ascend C

本例的设备身份精确到 SoC 版本：950PR 有多个核数配置，CANN 的[平台配置](https://gitcode.com/cann/runtime/blob/6cce8b2417de63cfb5726489fa894199dc8a77e1/src/platform/platform_config/cann-dev/Ascend950PR_9579.ini)把 `Ascend950PR_9579` 解析为 28 个 Cube Core 与 56 个 Vector Core，且 `cube_vector_combine=split`，两类核分别领取工作。

本任务直接使用 Ascend C 的核级接口，没有独立采用算子模板库，因此省略 `template`；该栈不提供面向用户的虚拟指令层，`virtual_isa` 一并省略。机器指令层存在，只是本项目尚未整理资料，所以 `machine_isa` 保留入口并占位——省略与占位在这里是两件不同的事。Ascend C 随 CANN 发行，没有独立版本号，版本身份由 `toolchain` 承担。

执行层级与能力摘要依据[昇腾 950 NPU 架构白皮书](https://public-download.obs.cn-east-2.myhuaweicloud.com/ascend/%E6%98%87%E8%85%BE950%20NPU%E6%9E%B6%E6%9E%84%E7%99%BD%E7%9A%AE%E4%B9%A6.pdf)与 [950 新增特性导航](https://gitcode.com/cann/asc-devkit/blob/64a39deed2dabe9bacac58ac4a09607ee03fbf59/docs/asc_950_feature_guide.md)。
