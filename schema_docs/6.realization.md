# 实现交接

本篇先判断[一条实现选择是否需要交接](#选择一条实现约束)，再说明[实现自由的边界](#实现自由的边界)。需要记录实验替代时，查阅[反馈规则](#有证据的替代反馈)。

## 核心思想

`realization` 是 Planner 与 Coder 之间的最小实现交接区。它只记录 Contract 和 Design 尚未表达、但双方确实需要共享的实现条件，以及少数有具体理由优先尝试的选择。

本区的基本单位是一条**指向上游对象的实现选择**：`item` 说明约束谁，`choice` 说明选择什么，`reason` 说明为什么需要交接。条目按 `require / prefer / forbid` 分组。`require` 把 Design 刻意留在抽象层的依赖落到具体原语或条件上：tile_pipeline 的动作契约只写所依赖的保证，math_reshape 只写数值路径，提供这些保证、实现这些路径的原语在本区固定。`prefer` 是有具体成本理由的优先实现，`forbid` 是已经排除、值得避免重试的弯路。

本区不重新决定数学、精度、工作组织、角色、缓冲或依赖，也不重复固定设备、语言和库版本。设计主张已经属于 Design，因此不设置 `thesis`；单项选择的理由由 `reason` 承担。

不影响既定数值与执行语义的代码组织、地址计算、barrier 编号和精确线程 layout，默认留给 Coder。调试日志、待办事项和完整实验报告不进入本区。

**空区是合法的完整结果。** 没有新增交接信息时，省略 `realization`。这不会取消任何上游约束。

## 选择一条实现约束

### 先做删除测试，再判断强度

| 判断结果 | 处理 |
| --- | --- |
| 上游已经完整表达同一约束，删掉本条不会丢信息 | 删除，不为保险重复。 |
| 替换选择会破坏已确定的角色、数据路径或交接方式，而上游尚未表达所需的实现兼容条件 | 写入 `require`。 |
| 替换后设计仍成立，但有具体成本理由优先尝试当前选择 | 写入 `prefer`。 |
| 某条路径未被上游自然排除，但 Planner 已明确排除，且值得避免重复尝试 | 写入 `forbid`。 |
| 只是在源码中出现，没有约束必要性或具体优先理由 | 留给 Coder。 |
| 无法判断，是因为上游角色、精度或依赖尚未明确 | 返回上游补齐，不用本区代替设计。 |

删除测试只删上游已经覆盖的冗余条目；通过测试的硬条件即使让本区变长也必须保留。本区偏长，说明设计把本应定下来的细节留了出来，应回到对应 Design 区收束，而不是靠省略必要条件显短。

`forbid` 不机械罗列 `require` 的反面，也不收集所有错误实现。已经违反 Contract 或 Design 的路径，本来就不合法。

### 结构与字段

```text
realization?
  require[]?: item / choice / reason
  prefer[]?: item / choice / reason / feedback?
  forbid[]?: item / choice / reason
```

`feedback` 的字段与证据条件见[替代反馈](#有证据的替代反馈)。

下表中的 `<kind>` 仅代指 `require`、`prefer` 或 `forbid`，不是新增字段。

| 字段路径 | 值的形式 | 填写条件 | 含义与约束 |
| --- | --- | --- | --- |
| `realization` | 映射 | 可省略 | 仅包含本区新增的实现条件与建议。 |
| `realization.require` | 条目列表 | 有额外硬条件时填写 | 设计依赖、但上游留在抽象层的实现条件，如提供某条动作契约保证的原语。Coder 不得自行替换或降级。 |
| `realization.prefer` | 条目列表 | 有具体优先理由时填写 | 在不改变 Contract 和 Design 的前提下，值得优先尝试的实现选择。 |
| `realization.forbid` | 条目列表 | 有明确排除结论需要保留时填写 | 排除容易重复尝试、且未被上游约束自然排除的路径。 |
| `realization.<kind>[].item` | 非空引用字符串，或非空引用列表 | 每条必填 | 指向上游已有对象或计算；不在本区定义对象。 |
| `realization.<kind>[].choice` | 非空英文字符串 | 每条必填 | 具体原语、实现选择或兼容性要求。不是封闭枚举。 |
| `realization.<kind>[].reason` | 非空英文字符串 | 每条必填 | 说明选择与既定前提、数据流或具体成本的关系。 |

### `item` 的引用与作用域

`item` 只引用上游已经定义的对象或计算，不建立别名或本地对象表。

名称在整份 Plan 中能够唯一解析时直接填写；需要限定作用域时写成：

```text
<owner>::<name>
```

`owner` 是上游已有的区域或具名作用域，`name` 是其中已有的名称，例如 `design.math_reshape::P`。引用 phase 内的对象时，名称以 phase ID 开头，再接上游自己的写法，例如 tile_pipeline 的角色写 `design.tile_pipeline::attention.MMA`。引用 Contract 时，数学与验收指向 `contract.algorithm_requirement` 及其 `golden_reference`，设备与实现环境指向 `contract.hardware_specification`，例如固定编译目标参数时 `item` 指向它的 `arch`。

更深的路径跟随上游自己发布的对象结构，本区不预设内部字段，也不用列表下标充当长期身份。裸名称与限定名称只在解析到同一个上游定义时等价；名称不唯一，或上游还没有给出身份时，先回上游解决，不靠读源码猜测，也不在本区临时造名。

### 单个引用与引用列表

单个引用与仅包含该引用的列表含义相同。多个对象只有在共享同一 `choice` 和 `reason` 时才合写；否则拆成独立条目。

引用列表不表示计算顺序、依赖关系或新的对象组合。不得重复填写同一对象来表达执行次数。

当 `item` 指向值而不是具名操作时，`choice` 必须说明约束该值的哪一段计算。例如，指向 `P` 时，可以限定为“计算 P 的多项式求值”，不能笼统约束所有与 P 相关的操作。

### `choice` 与 `reason`

`choice` 写选择本身，约束强度由所在分组表达，不必重复写“必须”“优先”或“禁止”。在 `forbid` 中，`choice` 直接写被排除的路径，避免双重否定。

原语名可以保持简短，但不足以限定作用位置或数值行为时，必须补充必要条件。`reason` 应指出具体依赖或成本，不能只写“更快”“更好”或“源码如此实现”。

`reason` 可以引用已有设计前提，但不能借理由补入新的角色、搬运、状态或执行关系。

例如，上游 `main.MMA` lane 已约定写入 TMEM，并依赖“先读完旧操作数，后续乘积才覆盖共用槽”的顺序保证，在支持该原语的任务环境中可以把实现绑定写成：

```yaml
require:
  - item: "design.tile_pipeline::main.MMA"
    choice: tcgen05.mma for the products defined by this lane.
    reason: The lane writes TMEM and relies on each product reading the old operand before a later product overwrites the shared slot.
```

另一种情况是：上游已经定义了 P 的逐元素多项式求值，同一 lane 中有可配对的独立 FP32 FMA，环境也支持成对指令。保持每个元素的运算与舍入不变时，减少指令数只是优先理由：

```yaml
prefer:
  - item: "design.math_reshape::P"
    choice: Use paired FP32 FMA for the existing independent polynomial pairs, preserving per-element operations and rounding.
    reason: Reduce FMA instruction count.
```

两个片段分别依赖各自已说明的上游条件；不能仅从值名 P 或原语名推导这些条件。

### 顺序、重复与冲突

映射顺序和条目列表顺序均不表示执行顺序，也不构成覆盖或优先级规则。

所有适用的 `require` 和 `forbid` 都必须同时满足；`prefer` 不能与它们或上游约束冲突。同一对象可以有多条约束，但应针对不同问题，且作用范围明确。重复条目应合并或删除；冲突属于 Plan 问题，不按“后写覆盖前写”处理。

明确的重复计算成本可以支持一个 `prefer`，但不能写成已经获得的性能收益。源码出处的证明范围见[来源与证据](0.common.md#来源与证据)；来源代码使用某种语言，也不会自动将它变成本区的硬条件。

## 实现自由的边界

替换是否属于 Coder 自由，取决于是否保持全部既定数学与执行条件，而不是指令名称是否相近，或一次测试的局部误差是否较小。

| 变化 | 处理边界 |
| --- | --- |
| 更换 API 封装、代码组织或指令表达，同时保持既定逐元素运算、舍入、角色和依赖 | 属于 Coder 可比较的实现选择。 |
| 改变舍入点、近似方法、量化顺序、换底计算位置或已声明的精度路径 | 返回 `design.math_reshape`。 |
| 改变物化、重算或逻辑状态保留方式 | 返回 `design.math_reshape`，并检查相关执行设计。 |
| 增加设计层可见的搬运，改变 lane、buffer 生命周期或 overlap | 返回 `design.tile_pipeline`；涉及工作分配时还需返回 `design.work_schedule`。 |
| 改变黑盒数学、量化规则、输出或验收要求 | 涉及 `contract.algorithm_requirement`，Planner 与 Coder 均不得自行修改。 |
| 更换已选设备、语言、库或接口环境 | 涉及 `contract.hardware_specification` 的 `device / arch / stack`，不能由本区覆盖。 |

`ex2.approx`、`rcp.approx` 等名称不隐式授权额外的数值行为；使用近似原语不等于允许增加 FTZ、改变参数计算或放宽验收要求。同样，将标量计算改成 packed 指令，也不自动允许改变融合舍入点或 lane 分工。

例如，`math_reshape` 只写了 `exp2`、尚未允许主动近似时，不能在 `prefer` 中加一条“在允许范围内使用 `ex2.approx`”来补出许可。先在数学区明确需要的近似方法、适用范围与误差依据或缺口，再讨论实现选择；没有新增交接条件时，直接省略 `realization`。

无法实现 `require` 时，应报告阻碍，不能自行降为 `prefer`。更快或更准确的结果都不构成修改上游的权限。

## 有证据的替代反馈

Coder 直接修改 `prefer[].feedback`，保留原来的 `choice` 与 `reason`；反馈也不为 `require` 或 `forbid` 提供豁免。字段与证据要求如下，修订及检查流程见[模板说明](../schema_template/README.md#3-填写与修订)。

| 字段路径 | 值的形式 | 填写条件 | 含义与约束 |
| --- | --- | --- | --- |
| `realization.prefer[].feedback` | 映射 | 记录有真实实验依据的替代选择时填写 | 仅允许出现在 `prefer` 条目下，不覆盖原始选择。 |
| `realization.prefer[].feedback.choice` | 非空英文字符串 | `feedback` 出现时必填 | Coder 提出的替代选择。 |
| `realization.prefer[].feedback.evidence` | 单个固定版本记录引用 | `feedback` 出现时必填 | 指向支持该替代的真实实验记录。 |

`feedback` 省略只表示本区没有记录有证据的替代，不代表替代已经通过或已经被否定。

`feedback.evidence` 使用公共的 [`repository@ref:path` 格式](0.common.md#来源与证据)。

`ref` 必须锁定支持当前结论的记录版本，`path` 指向真实实验记录。完整配置、结果和报告留在该记录中。

没有真实证据时省略 `feedback`，不填写假路径、假版本或占位反馈。设计源码出处不能代替实验记录；`meta_data.source` 也不是数值验收 oracle。

实验记录至少应支持以下判断：

| 判断 | 记录需要提供的内容 |
| --- | --- |
| 对比对象明确 | 原始与替代实现、它们对应的 Plan 与环境（按 `repository@ref:path` 固定版本引用），以及实际 workload。 |
| 替代符合要求 | 按原有要求检查契约输出及相关设计约束，不能只报告局部原语误差。 |
| 比较成立 | 在相同 workload 和可比较的测量范围下给出结果，并限定结论适用范围。 |

例如，用两条标量 FMA 替代一次 packed FMA，只有在逐元素运算、舍入和角色不变时，才可作为本区的替代反馈。实验细节留在记录中，无需增加 benchmark 表或审批字段。

一次更快的实验不能覆盖错误输出、遗漏最终状态、更换量化分支或改变计时范围的事实。多个历史实验也不应扩展成这里的新列表。

## 省略与扩展边界

本区的通用命名、YAML 写法与缺项规则见[公共约定](0.common.md#通用写法)。没有内容的分组和整个区域都直接省略。

本区所有映射都是固定结构，只使用结构轮廓中的字段，没有具名映射，也没有可以自行扩展的位置。增加条目、引用新的上游对象或填写新的实现选择都是填写实例；新增字段遵循[公共扩展规则](0.common.md#结构与扩展)。

条目不按算子名、phase 名或原语名另建并列区域，也不设 `notes` 一类的兜底字段；现有字段确实表达不了的需求，先指出结构缺口。
