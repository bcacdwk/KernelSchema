## D1：KernelSchema 的独立 implement 承诺

**推荐：保留一个不依赖 AKA 运行后端的真实参考 implement，并让 AKA 提供增强实现能力。**

参考 implement 首期只承诺一个明确支持范围：单任务、单实现栈、串行、有上限的 coder 调用，任务提供构建/验证/测量能力。它保存准确代码并支持从未完成代码继续，不复制 AKA 的全套调度、晋升、隔离和后台维护。

备选：KernelSchema 提供自己的四流程入口，但 implement 必须调用外部 AKA。维护的执行能力更少，公开产品则需要明确说明 AKA 是实现与验证的运行依赖。

需要判断：是否接受推荐的独立程度，并承担维护这一小块真实执行能力的成本？独立不等于自带模型或 GPU；两种方案都需要相应运行条件。

## D2：首发范围与推进顺序

**推荐：工程先验证固定 schema 的实现与续写；公开 demo 尽早加入 design 和一次 optimize；一个现有复杂算子的材料预审同步提前。**

顺序建议：一个资料闭合的小任务/单栈 → 固定设计实现、代码续写与真实验收 → 同任务 design/optimize 演示；同时选一份既有 schema 核对硬件、比较器、必要 dispatch 和资料可取得性，随后做真实复杂实现。

这一区分意味着独立 demo 不等 AKA 动态循环全部完工，教学案例成功也不被当成复杂 Schema 有效性的证明。

备选：以一个现有复杂算子直接作为首个真实实现目标。它与当前资产更贴近，但实现、材料缺口、语义审查和 AKA 适配的问题更容易交织，首个独立 demo 可能更晚。

需要判断：先采用推荐的分期，还是优先把既有复杂算子作为第一目标？具体 GPU、实现栈、模型、任务 evaluator（含是否首期使用 Agate）在方向确认后按所选案例和现有环境确定，不在本页擅自固定或删除 Agate 需求。

## D3：Planner 何时接管设计迭代

**推荐：按一次固定设计的实现阶段交接，不把每个 AKA episode 结束都当作 optimize 触发器。**

同一 schema 可以跨多个 coder episode。满足本次范围的实现与验收后，或出现有证据的设计阻碍，再交 planner；编译错误、尚未写完、资源超时分别处理，不自动归因为设计失败。正确且符合设计但较慢的代码可以作为已实现结果交付，性能目标是否达到单独记录。

备选：每个或每隔固定数量的 coder episode 都调用 planner 检查，可作 keep/revise 判断。这可以更早纠偏，但增加模型成本和设计变动，仍须保留未完成代码、累计预算和准确版本绑定；不能强制每次改 YAML。

需要判断：首期采用推荐的实现阶段边界，还是希望 planner 按固定 episode 周期介入？如果选周期介入，可稍后再确定间隔。

## 建议知会项（不是追加决策问卷）

- 三仓分工：KS 持有语言与四流程；AKA 可选适配持有其 coder/执行接入；EXP 管实验与固定版本消费。依赖方向建议 AKA 适配 fork → 可选 KS submodule，KS 核心不反嵌 AKA。当前未执行 fork、分支切换或迁移。
- AKA 的具体驱动方式以窄验证定型。单 episode façade、有限原循环接口、保留或替换 V1 的必要职责，均不能仅凭现有代码片段认定已经可用。
- 正确性、设计符合性、性能分别记录。首期符合性可采用有限、可追踪的检查与独立审阅；证据不足保留 unknown，不冒充完整通过。
- extract 内部保持现行流程；进入 implement 前补齐并固定本次任务条件，兼容自动提取、人工审修、手写与新设计来源。
- 首期独立闭环是有范围与预算的演示；长期无人值守、复杂远端故障恢复、多 provider 等按后续阶段逐步扩展。
