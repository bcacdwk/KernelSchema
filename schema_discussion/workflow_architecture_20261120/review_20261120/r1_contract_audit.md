## 一、确定的矛盾或规范缺口

### C-01：恢复从 result 进入，无法覆盖第一份 result 尚不存在的边界

- **定位**：P:89、99 只规定 `implement --continue …/result.json`；C:195–209 同样要求从保留结果定位后端状态。另一方面 P:130–132、C:266、281、291 要求先持久操作事实、产物和资格，并将 result 定义为可重建投影。
- **反例**：首次 implement 已经持久化 operation、准确 C、执行/用量收据，在第一次写出 `result.json` 前进程退出。`.runtime/` 与 artifacts 完整，公开恢复命令要求的文件却不存在。这不是跨机迁移，也不是远端不可知问题。
- **缺失之处**：计划没有要求在首次收费前发布一个 durable 恢复入口，也没有定义 `--request 原请求 --out 已存在运行根` 是重放恢复还是错误，更没有另一个按运行根进入的恢复命令。不能用“result 可重建”代替用户如何调用重建。
- **同类边界**：design/optimize 也使用公共 recovery/continuation、收费收据与发布协议（P:79、82；C:137–139、169），但列出的 CLI 只有 implement 能 continue。写作调用未知或发布完成但结果丢失时，其 settle/replay 能力必须明确；可以明确不支持继续写作，但仍需能吸收已经发生的事实。
- **后果**：已有进度和费用虽然保存在磁盘上，公开入口仍不能取回；调用者很容易另开请求重新付费。V09 的发布中断和“返回丢失不重新开 e”也缺少可调用的验收入口。
- **最小修正**：选一种即可：在首次收费前持久一个始终可用的恢复锚点；或让续接接受运行根并按原 operation 分派；或明确同请求/同 out 的幂等恢复语义。把“首份 result 尚不存在”加入现有 V08/V09，并说明三个新入口各自允许的恢复动作。无须新建 checkpoint 服务。
- **归属/首期**：KS-02 定入口，KS-05/07 实现各操作，AKA-08/09 映射。影响首期；不阻止 KS-01 材料准备。

### C-02：Q、一次运行与重放的边界没有分开，私有状态无法实现跨输出目录的去重承诺

- **定位**：P:67 用 Q 标识请求；P:99 将 token 绑定运行根；P:106、C:265 只规划每个运行根的少量私有状态。C:220 又说“重放请求不能增加模型调用”，C:272 说历史费用“不能因新输出目录/新会话重新归零”；CLI 则允许 `--request … --out …`（P:89）。
- **可核对反例**：同一个 `parent=null` 请求 Q，先执行到 `runs/a`，再将原始输入 bundle 交给 `--out runs/b`。b 中没有 a 的私有账目，命令也未给原 token/owner。对 b 的实现而言，“这是首次执行”与“a 已花完额度后的重复执行”具有相同可见输入。仅凭 Q 和 b 的私有状态不能区别二者。
- **这不是要求阻止恶意复制**：问题是普通用户重跑公开 demo、网络重试与恢复究竟属于哪一种操作。若这些句子原意只是“同一 run/父 owner 内不能归零”，应写出这个限制；不能把它保留成跨任意输出目录的保证。
- **后果**：两个实现者会分别选择“相同 Q 永不再执行”或“新 out 总是新余额”，导致重复收费、无法合法重复实验，或汇总时将两个真实运行当同收据去重。request_id 已在 Q 中，但未定义它在运行/重复实验中的唯一性范围。
- **最小修正**：明确恢复/幂等域为同一个 durable run/预算 owner，区分输入身份 Q 与一次实际运行身份；原 run 的恢复必须定位其账目。明确新 run 的显式启动及历史费用归属，禁止把它当 continuation。删除超出该边界的“换目录仍保证全局去重”读法，优先不要增加全局请求注册服务。
- **验收**：在 V08 中并列验证同 run 重放不新增费用、明确的新 run 产生新的真实调用记录、丢失 owner 的旧 run 不被当成有新余额的恢复。
- **归属/首期**：KS-02/05/09、AKA-08/09，EXP-01 的重复实验也消费该定义。影响首期预算与重跑语义。

### C-03：unknown 检查与 unknown 在途操作混用，导致合法补证永远不能准入

- **定位**：P:52、131 将“pause/耗尽/unknown”统一设 fence，且“只可查询吸收原事实”；C:300 对执行身份/费用/终态不明规定 settle_only，但 C:301 明确允许 fidelity 证据不足在有具体动作和余额时 continue；P:97 也将 settle_only 限定为“未知在途操作”。
- **反例**：reviewer 已正常终止、用量已结算，对一项源码关系给出 unknown，同时指出需要一份可取得的编译报告。余额足够。按 C:301 可新增这次验证；按优先级更高的 P:131，unknown 已经建立禁止任何新调用的 fence，补证永远不能发生。
- **后果**：KS 与 AKA 可能对同一结果给出不同恢复行为；也可能把“证据尚不能证明”错误变成“旧执行尚未结算”。前者应保留不合格状态，却不当然禁止同 R 的有据补证，更不能因此触发 planner。
- **最小修正**：只把**已准入操作的身份/终态/计费结算不明**列为此类 durable fence。已结算的检查 unknown 单独按 C:301 处理；必需检查仍不能签 qualified。补一句状态优先级：尚有未结算操作时，即使另有合格 C，也不能用 completed 掩盖该恢复责任。
- **验收**：V07 留未知远端 job 的零重提；V02/V08 另保留“review 已结算、检查 unknown、余额充足、有具体补证”的不同轨迹，不扩成所有 unknown 的排列组合。
- **归属/首期**：KS-05/06、AKA-07/09。直接影响首期可恢复性，只需改清规则而非增加状态枚举。

### C-04：完整 artifacts 导入会把无关私有历史变成公开复用的硬依赖

- **定位**：P:105–108 要求所有 Ref 可取得、旧路径/字节不可改，且导入单位是来源的**完整** artifacts 子树，包括所有历史 request/result/原始报告；P:183、V:235–237 又要求公开包只含授权材料，原日志可能必须脱敏，并保留与原件摘要的关联。
- **条件反例**：某个原 usage 收据 U 用 Ref 指向日志 L，L 含不能公开的个人路径。公开包删除 L，或只保留脱敏 L'。前者产生缺引用；后者的字节不匹配旧 Ref。旧 U 又不能改路径后沿用摘要。按完整树规则，即使新请求只需要可公开 Schema 和 C，也必须拒绝这份公开包。
- **判断范围**：这是上述条件下的逻辑冲突，不断言本次 demo 一定含私有日志。原件只保留在作者机器、给出原摘要，也不能满足第三方的“实际文件可读取并核对”。AKA 原生测量产物确有 host-private 内容边界，见 `AKA:src/aka/contracts/evaluation.py:60–67`，不能默认全部历史均可公开。
- **后果**：公开“查看证据”包、可导入的 v1 bundle 与私有完整归档混成一个对象；第三方可能可以读 README，却无法按规范消费其中 Schema/代码。完整树规则还把无关历史的缺项传播给每次下游导入。
- **最小修正**：至少明确两者不同：可导入 bundle 必须满足它实际声称的完整闭包；脱敏证据展示不能冒充原 v1 的完整可导入归档。首发可只发布从一开始就可分发的闭合运行记录。若需要从私有历史复用公开 Schema/C，优先考虑删除“必须复制全部无关历史”的要求，采用选定产物的真实引用闭包；仍保留原路径、摘要与来源说明，不发明改标签豁免。
- **归属/首期**：KS-02/08/14、AKA-02/10。P2；只在使用不可公开原件的公开发行/组合路径成立，不应阻塞纯本地 fixed 工程。

## 二、合理实现可以解决，但计划尚未明确的选择

以下不判定现设计必错，也不把它们与技术 spike 失败混为一谈。建议裁决轮决定是否用一两句补齐，而非新增工作包。

### C-05：优化目标究竟属于 Task，还是属于这一次写作请求

- **定位**：P:43 将“目标”列为 optimize 输入，C:137 的具体请求字段只有 Task/rules/materials/scope/budget/backend/schema/feedback/evidence；P:66、C:47 又拒绝未知核心字段。`KS:OPTIMIZE_SCHEMA.md:3、9`、`KS:DESIGN_SCHEMA.md:13` 明确依赖当轮目标/优先 workload，且不能在 Contract 中自增字段。
- **场景**：同一合法 Task/Schema/覆盖范围，调用者分别希望优先降低 M=1 延迟、或以已有反馈修复某个设计瓶颈。当前协议没有说明该指令放 Task.acceptance/workload、约定的 Materials 条目，还是独立 Ref；后端也无法从 Materials 中区分当前授权目标与普通参考文字。
- **后果**：实现者容易用未绑定的 CLI/prompt 临时指令，或者为一次优化意图改动整个 Task 身份；双方的请求模板未必可互操作。
- **最小修正**：明确一种已有文档的权威位置与可见角色即可；若目标随 Task 固定，写明从哪个 Task 字段读取；若同 Task 可换当轮目标，给它确定的请求承载位置并纳入 Q。不要为这一点新增通用目标 DSL。
- **归属/首期**：KS-02/07/09。P2，首个 demo 的固定目标可以推知，不据此断言 demo 不能运行；在对外发布请求模板前应消除歧义。

### C-06：R0 条目表不能自动成为新设计的 fidelity 门，交接责任应补清

- **定位**：W:41–45 的具体交付是 R0 条目/方法 manifest；W:47–51 生成新 Schema/scope。C:235、258 要求必需条目在规则/请求闭包内固定；V:86 允许设计输出 Rd 与 R0 不同，V:96 明说新分工需要新的 fidelity 条目。W:59–63 的 demo 又直接消费 Rd/R'。
- **场景**：合法的 Rd 或 optimize 输出把“一 program 一行”改为“一 program 多行”。若下一 implement 仍投递 R0 的具体验收条目，会拒绝一个符合 Rd 的 C；若直接删掉旧条目，又没有建立 Rd 的新必需项，可能错误 qualified。单纯把收据上的 schema_sha256 换成 Rd 不解决语义问题。
- **尚未证错的原因**：KS-06 完全可以使用按当前 Schema 解释的通用有限条目模板；并不必然要新增一个模型调用或让 planner 自行定义合格标准。但计划没有明确采用这个办法，也没有把新条目形成、固定和核对交给某个包。
- **最小修正**：把“给任一首发支持的 Rd/R' 建立与其对应的必需检查”列入 KS-06，并说明 KS-07/09 在构造下一固定请求前如何取得它；允许通用 Schema 相对模板。明确不会只替换收据 hash，也不会让生成设计的 planner 单方面删掉必要验收项。
- **验收/首期**：将一个改变 work ownership 的 synthetic Rd 放入现有 V02/V09，验证正确新实现可被审查、旧设计实现不会因重新贴标签而通过。影响 design/optimize 的首期闭环，不阻塞手审 R0 的 fixed 开发。AKA-07 消费同一接口，不另维护清单生成器。
