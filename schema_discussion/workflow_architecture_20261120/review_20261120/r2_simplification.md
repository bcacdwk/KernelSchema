# R2：全局删减与合并建议

日期：2026-11-20。只提出精简方案，供第三轮裁决；不修改正式计划或代码。
已读 AGENTS、用户简报、D1–D3、主计划、工作包、复审说明、两份 R1 和正式采用的两份 R5 附录。
定位简称：P=`../04_implementation_plan.md`，W=`../05_work_packages.md`，C=`../planning/r5_contract_execution_review.md`，V=`../planning/r5_validation_delivery_plan.md`。行号对应审查前版本。

我的判断：主要负担来自完整历史复制、重复入口/规范/验收归属，以及把一个实现事务拆成过多交接包；不是有限正确性和恢复要求本身太多。
建议直接撤销若干义务，再合并其实现与验证责任。无需更换首题，也不应靠取消独立 implement、准确续写、planner demo、复杂题预审或 AKA off 来缩短计划。
下列方案不以减少到某个包数为目标；后面的 18 个交付单元只是可执行的合并草案，不是新的强制数字。

## S-01 — 只导入选定产物的真实引用闭包

- **原位置/内容：** P:104–110；W KS-02/07/08/13、AKA-02/10。每次组合必须复制来源 bundle 的完整 `artifacts/`，连带历史 request/result、日志、用量和以前的全部导入。
- **明确删法：** 删除“完整 artifacts 子树”为导入单位。调用者选择 Schema、source 或所需证据作为根，导入这些根实际引用到的文件；未引用的旧调用日志、旧结果和无关候选不进入新请求。
- **保留形态：** 保留稳定 publication 前缀、原路径/字节/摘要、普通文件检查、暂存后发布与同路径异字节拒绝。真实 Ref 必须递归闭合；不能截断 Schema.parent 等现有引用，不能把脱敏件冒充原件。
- **必要区分：** 一份可复用 Schema/C 不必附赠整个运行档案；公开完整证据时，则检查所选择的证据根自身闭包。只展示摘要的脱敏说明不声称是可导入原证据。
- **为何不伤目标：** D1–D3 需要固定当前输入与可核对证据，没有要求每次 implement 携带所有祖先的私有日志。已有 Ref 结构足以决定闭包，无需 artifact 服务、全局索引或新的导出协议。
- **代价：** 导入器需按已支持对象的引用字段遍历，并区分外层 Ref 与原生报告文本；比目录全拷多一点解析，但免掉持续增长的复制、许可和缺项传播负担。已有逐 Ref 核验本就需要识别这些边。
- **关系：** 直接采用 C-04 的较小修正。V06/V09 只需验证选定闭包移动后可读、缺真实依赖拒绝、无关历史缺失不影响导入；不用增添公开档案平台。

## S-02 — 恢复只定位原 run；不承诺全局去重

- **原位置/内容：** P:89、99、106；C:195–209、220、265–272。一方面只有 run 私有状态，另一方面要求换 out 不归零；公开恢复又必须先找到 result 和 opaque token。
- **明确删法：** 删除跨任意新输出目录保证不新增费用/调用的文字。Q 是输入身份；幂等与累计预算只在同一 durable run/父 owner 内成立。显式新 run 是新运行，有自己的真实费用，不冒称 continuation。
- **首期入口：** 三个新操作统一接受 `--continue <run目录>`；先核目录内首次收费前持久化的 request/后端定位/准入状态，再重建结果或结算。`result.json` 是输出，不是恢复的唯一门票。
- **可再删除：** 首发只承诺本地运行根恢复，公共 `{backend,token}` 可取消；若 AKA 驱动确实需要 token，将其留在宿主私有状态。调用者持有 run 目录即可，不再同时维护结果路径、token 和运行根三种定位物。
- **保留形态：** operation、Q、后端版本与账目必须匹配；损坏/丢失 owner 不得恢复成新余额。同 run 重放只吸收旧事实；需要新调用时仍过原累计预算。`recovery` 的动作提示可以保留。
- **为何不伤目标：** 准确 C 可以显式作为新请求 seed；这与从原 run 继续结算是两件事。计划本来就不承诺可移植 checkpoint、隐藏会话搬家或跨机恢复。
- **代价：** 不能只带一个 result 文件恢复；但现方案也依赖原运行根私有状态。外部后端若必须暴露独立恢复凭据，可保留该凭据，不必因此恢复全局去重承诺。
- **关系：** 同时闭合 C-01/C-02。只补“首次 result 尚未发布”的恢复 fixture，以及同 run 重放/明确新 run 两条轨迹；不新增注册中心或公共 run 身份服务。

## S-03 — 四项能力保留，重复可执行入口直接删除

- **原位置/内容：** P:29–30、89；C:344–346；W KS-02/14。统一 CLI、Python API 外，三个能力目录还各有 `tools/run.py`、配置和 README。
- **明确删法：** 删除三个 `tools/run.py` 和目录专属配置模板。统一 `kernelschema {design|optimize|implement}` 是新能力的命令入口，Python API 是同一实现的调用接口；extract 保留原命令及已计划的兼容透传。
- **目录形态：** 如需保留用户可发现的 `schema_design/` 等目录，只放简短 README，链接唯一 CLI 的具体命令、角色方法和同一组可运行 examples；不复制参数表、安装说明或请求样例。
- **为何不伤目标：** 可调用四流程由真实命令和 demo 兑现，目录数量和脚本数量不是能力数量。C:24 记述的能力目录诉求仍满足，不把它降为无实现的 TODO 门面。
- **代价：** 不再支持 `python schema_design/tools/run.py` 这类尚未发行的别名；没有兼容迁移成本，用户只需学习一套请求/恢复规则。
- **关系：** 不涉及 R1 的正确性问题；减少 C-01 恢复入口需要同步维护的副本。

## S-04 — 删掉重复的有效规范，而不是继续增加附录

- **原位置/内容：** P §§3–7、W 开头/末尾、C §§2–8、V §§2–8。字段、恢复表、工作 DAG、spike、发行门、README 更新点多处同时有效，C 的示例路径又被 P §4 全局覆盖。
- **明确并法：** P 只保留方向、所有权、阶段交接、首发范围及发布门；W 只保留交付单元、依赖和验收 ID。公共字段/身份/恢复规则只在 C；Task 细则、V01–V15 与实验规则只在 V。
- **直接删除：** C §7 的第二份工作包 DAG、C §8 与 P 重复的 spike/目录表、V §7 的第二份阶段发行门/逐门 README 更新表，以及 P 中逐项重述完整 Task/计时参数的段落。相关内容由唯一主表的链接替代。
- **样例处理：** C 中被正式发布规则否定的旧路径样例必须改成一份一致的最小实例，或删除重复大块 JSON；不要继续要求读者先读样例再应用优先级覆盖。后续实现产生的 fixture 可成为可执行示例，不另建文档生成平台。
- **历史边界：** R4/R5 的研究推导留历史身份，不再要求开工者逐个判定哪句仍有效。现有两个采用附录可就地收敛，无需新造更多“最终版”文件。
- **为何不伤目标：** 每条真实义务仍有一个权威位置；删除的是多份同步义务。C-03 正是重复恢复文字已产生不同结论的例子。
- **代价：** 实施者需要一次跳转；换来无需比较三份同名规则。第四轮应按内容核查迁移，不能仅删整节而漏掉其中唯一规则。

## S-05 — 按可交付行为合并工作包

- **原位置/内容：** W 34 包，尤其 KS-05/06、KS-09/14、AKA-05/06、AKA-07/08/09、MIG-04/05。多包共同修改同一 source、准入状态、结果投影或发行根，又分别复述同一验收。
- **明确并法：** 固定实现与合格投影由一个包负责；demo 与源码发行收尾由一个包负责；AKA bootstrap/seed 由一个包负责；AKA 资格/预算/恢复/公共返回由一个固定事务集成包负责。
- **不能省的阶段：** 这些包内部仍区分接口稳定、CPU fixture、真实资格三个完成记录；合并不意味着接口开发要等待真实 GPU，也不把全部修改变成一次大提交。
- **迁移简化：** MIG-01 的隔离/重读状态变成开工前检查及一份基线记录，不是独立产品里程碑。MIG-03 的依赖固定与安装分别归可选模块建设和 AKA 发行；MIG-04/05 合成一次 EXP 消费迁移。
- **为何不伤目标：** E-02 的 native baseline 与 coder seed 本就必须一起设计；资格先落盘再晋升、用量吸收与 result 投影也不能靠包间口头假设拼接。合并减少这些交接缝。
- **代价：** 某些包较大，需要内部检查清单；但无需再为每个小清单维护一套依赖/完成/公开说明。后文给全量原 ID 映射，正式工作表不必留下删除包的墓碑。
- **关系：** C-01/C-03、E-02 的修正都落入已有合并包；R1 没发现 DAG 环，不应借精简重新制造“所有资格先完成才可写接口”的串行门。

## S-06 — 跨后端验收用已有真实记录汇合

- **原位置/内容：** W KS-13、AKA-02/11；V:136–146、197–210。KS-13 再列双方模型/完整 evaluator/fidelity/性能和多组负例，容易被执行成第三轮资格项目。
- **明确并法：** 删除独立 KS-13 工作包。共同 fixture 和映射对照归 AKA-02 对接工作；跨后端文档和结论在 AKA-11 发行时，索引 KS 与 AKA 已有适用记录。
- **明确的免重跑规则：** 精确 Task/C/evaluator/profile/adapter 版本与方法均匹配时，已有 V01/V03/V04/V06 记录可同时满足本侧发行与配对验收；仅缺对接点或版本变动时补测受影响路径。
- **保留形态：** 两侧仍分别需要真实通道证据；三个关键坏候选必须在实际 adapter 上被拒绝；新增的跨请求导入和能力拒绝仍需 CPU 对接证据。不能拿 KS pass 代签 AKA。
- **为何不伤目标：** “证据相互独立”要求后端各自实际运行，不要求同一后端为两个发布表重复运行同一 qualification。单独的成对结论仍可清楚给出。
- **代价：** 需要一个简短配对索引说明复用哪份记录及适用性；这比独立测试活动和重复证据包小得多。
- **关系：** 保留 E-01/E-02 对 AKA 实际适配的要求；不把原生 hook 的未知伪装成已验证。

## S-07 — 首期预算使用一个 owner 的准入器和活动时钟

- **原位置/内容：** P:127–131；C:270–290；W AKA-09。公共活动时间写为父子活动区间并集，用量行又含自己的 active_ms，容易导向通用区间合并、递归预算树和多份余额状态。
- **明确简化：** 首期允许一个顶层 owner 串行调子请求；同进程调用和恢复都通过它持久化的准入器。公共 active_ms 由 owner 的活动/静止转换累积，子操作只引用账户和操作 ID，不另汇总成第二份公共时间。
- **实际删项与边界：** 删除 C:286 每条 usage 行必有 active_ms 的字段义务；公共时间只在账户汇总给出。任意深度父账户调度和分布式区间合并则明确不在首期范围，并非断言原文已经要求这些平台。子请求的用量可以投影；父余额不靠求和 child totals 或 native totals 推算。
- **保留形态：** pause 后已在途工作仍算活动；确认静止才暂停计时；崩溃间隔无法证明静止则保守计入。calls/jobs/token 的真实明细、父/请求/native 最紧限额、未知费用与收尾预留全部保留。
- **为何不伤目标：** D1 明确单任务串行，P:25 又禁止双顶层循环；现阶段没有多 owner 并发结算需求。单 owner 时钟本身实现了所需活动区间并集语义。
- **代价：** 以后真正需要并发子任务时必须重新资格化计时/额度实现；当前没有承诺这种能力。不改成“暂停也耗光 deadline”来人为缩减续写能力。
- **关系：** C-02 的 owner 边界使本方案可实现；C-03 只需区分未结算操作与已结算检查 unknown，无须增加一套 unknown 状态机。

## S-08 — fidelity 补闭环，采用固定方法读取当前 Schema

- **原位置/内容：** W KS-06/07/09；C:235–258；V:86–98。R0 特定条目与新 Rd/R' 的交接缺项，容易被修成“每次生成并发布一套新验收清单”。
- **明确形态：** 首期固定一个有限审阅方法，按当前完整 Schema 检查数值路径、work ownership、存储/寿命、Require/Forbid 和 scope；每个结果列出实际审查的设计义务、代码位置与理由。
- **不用新增：** 不增加 planner 生成测试清单、第二个清单 planner、清单发布服务或单独的清单审批工作包。R0 专属例子是该方法的 fixture，不是后续所有 R 的固定“一 program 一行”要求。
- **保留形态：** reviewer 独立只读，方法版本和当前 R/C 等绑定固定；无法覆盖新设计的义务就 unknown/partial，不能通过泛泛的几个 pass 标签漏掉它。planner/coder 无权删必要义务。
- **验证：** 在已有 V02/V09 加“一行一 program”与“多行一 program”的正反配对，证明同一 C 对不同 R 得到正确 verdict；不要求真实 optimize 强行 revise。
- **为何不伤目标/代价：** 仍检验设计符合性，且可用当前 Schema 解释合法新设计；代价是 reviewer 必须明确逐条解释，复杂同步仍可能 unknown。本方案不声称通用语义证明。
- **关系：** 采纳 C-06/E-03 的第一种最小修正，拒绝为它们新增清单生成架构。E-01 另补 out 原 storage/view 守卫，E-02 另区分 baseline 与 seed；两者也不需新平台或新包。

## S-09 — pilot 不按最快观测选终态，不预建额外实验臂

- **原位置/内容：** V:267–274、288、308–310；W EXP-01/02。历史候选按计时最优选择，又用同一数据报告结果；另预留 F1 第二批及 P/C 额外对比。
- **明确替换：** 首个 pilot 预登记与速度无关的选择规则，例如选预算内最后一份完成 Task 和其所属 R 必需检查的 C；同次序冲突用固定序号。不得依据速度选择回退候选。
- **为何选“最后”示例：** 不建议默认最早合格 C；D 组往往先完成 R0 再 optimize，永远选最早者会把动态改进排除出交付结果。末次合格规则可自然容纳真实 R'。
- **边界保留：** 新 R 未完成时，可按预登记规则展示最后合格历史 C，但注明所属 R；不能把它冒充当前 R 的公共 qualified。所有历史测量、latest/qualified/G 与失败仍保留。
- **明确删除：** 删除 best-of-budget 选择义务，首期无需为它另建“选定后独立复测”的额外预算/流程；删除 P/C 实验臂和“F1 再来同样九次”的预排任务，不转成长期 TODO。
- **为何不伤目标：** B/F/D 仍能检验固定设计与一次动态策略的完成、成本和交付结果。当前并未承诺证明结构化文本优于普通计划，或压缩 Schema 优于传原码；没有这些主张就无需对应实验设施。
- **代价：** 不再估计“预算内最优候选”的效果；应把实验结论写成预登记交付策略的效果。若将来明确研究最优搜索，届时另设计独立终态测量。
- **关系：** 修 E-04 采用删除选择偏差来源的较小路线，而不是自动增加一轮 GPU。保留完整 Task 的正常性能测量；本项不影响 KS/AKA 首发。

## S-10 — 一份审阅证据同时承载 coverage 与 fidelity

- **原位置/内容：** C:152–160、234–258；W KS-06、AKA-07/08。coverage receipt、fidelity receipt、结果覆盖映射容易分别生成、保存、校验三份相同的范围→代码关系。
- **明确并法：** fidelity 审阅报告同时保留 coverage_id→节点/变体/代码位置映射、task_uncovered 与设计条目结论；结果中的 coverage/fidelity 检查引用同一报告，各自状态仍分开。
- **保留形态：** scope/when 的准入核对仍在调用前完成；缺 dispatch、覆盖不全、设计违规分别可诊断。执行报告继续统一承载 build/correctness/performance，原生原始证据不重编码。
- **为何不伤目标：** 删除独立文件和重复投影，不删除覆盖检查；Check 本就允许多项指向同一收据，写作四检查也无需拆四份报告。
- **代价：** 审阅报告稍长，schema-on 的投影器要明确取各项状态。没有必要发明通用报告引擎或更宽的多态协议。

## S-11 — 撤销没有当前交付对象的长期工程包

## 看似复杂但不能删的内容

- 独立真实 coder/evaluator、实际模型与 GPU 资格；fake/历史回放不能代签 D1 的真实能力。
- 准确 source 字节、稳定 C 与 draft 的区别、latest/qualified/G/HEAD 的必要分离；否则“继续实现”会退回旧源码或错绑证据。
- 角色材料边界、固定 assignment、Task/evaluator 不可由 planner/coder 改动、当前 Schema 的有限独立 fidelity；它们直接决定是不是实现指定设计。
- 原输出 storage/view 与副作用检查、完整比较式、原生 V0 baseline 与 partial seed 分离；E-01/E-02 是真实缺口，不能拿“简化”免掉。
- 未知在途操作不重提、费用不归零、seed 不覆盖已准入 draft、资格先持久再晋升及三种 audit；这些对应已存在的执行/恢复边界。
- fixed 零 planner、普通代码失败不自动改设计、keep 无行动即停止；以及暂停/父预算控制所有新调用。这些是 D3 的产品语义。
- AKA off 无 KS 依赖/调用，EXP 固定消费和旧 capture 不迁写；以及 FA4 root 子域不代表全任务、必要 dispatch 与原栈限制。
- JCS/Ref/source codec 等已有明确方案暂不另改。移除历史复制和重复入口的收益更大；为省一个确定的序列化规则重写身份体系，当前缺少足够收益证据。
