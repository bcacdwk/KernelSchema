# nvfp4_fused_moe

## 范围

### 实现范围与入口

固定实现是 AKA 候选，`problem/solution.py` 只是生产对照，不在提取范围内。入口 `candidate/solution.py::Model.forward` 只承担 host 工作：从张量 shape 推导规模（`T`、`K` 取自 ids，`E` 取自 gemm1_weights 第 0 维，`I = N1/2`，`H = packed 轴 * 2`），校验三个权重与 scale 的形状一致，要求调用者提供结果缓冲（Contract 的 Input `output_buffer`；Output `output` 就是这同一对象，被覆写后放进单元素列表返回），选择 rung，按 rung 分配 workspace，组装 `MoEABI` 后调用 `candidate/nvfp4_moe.cu` 的 `moe_run`。全部数值工作在 `nvfp4_moe.cu`；`nvfp4_fast.c` 只把已发布的 identity 校验搬到 C 层，不绑定任何数值。按 CONVENTIONS，整个 `candidate/` 一起复用。

实现门槛属于设计范围而非 Contract：`E <= 256`、`H % 128 == 0`、`I % 64 == 0`、`N1 % 128 == 0`，packed-NVFP4 家族另需 `_rung7_ok`，即 `H % 256 == 0` 且 `I % 256 == 0`。声明域的四组几何 (2048,768,128)、(4096,768,128)、(4096,1536,128)、(7168,256,256) 全部满足，因此本目录的设计在声明域内不因这些门槛再收窄；`when` 只需承担 rung 选择条件，不需要复述门槛。root.yaml 已按此把门槛留在目录、把工具链与拒绝条件写进 `REALIZATION`，Contract 内没有任何门槛。

### 声明域内实际可达的配置

`_pick_cfg` 的 106 级 rung 阶梯在声明域内只会给 GEMM1 返回 97 或 99：`R = T*K <= 1536` 走 99，否则走 97（`R` 即 root.yaml 的 `route_capacity`，不是有效路由数 `route_count`）。返回 43 的分支要求 `min(E,R) <= 32` 且 `R > 4*min(E,R)`，即 `E <= 32`，在 `E ∈ {128,256}` 下不可达。GEMM2 由 `cfg2` 独立选择（97 与 99 都在同一张 `cfg2` 配对表里），可达 81（WS3 + TSTORE）、57（WS3）、44（单体 + SFCP）、23（flat-stream，只在 `I == 256` 配对）。MEGA rung 92 在 `K == 8`、`R <= 8192`、`R*H <= 32e6` 且 capture-time 路由直方图为空时替换整条链；zero-capture 前缀在 capture-time 零探针接受、`cfg ∈ {74,78,97,99}` 且 `cfg2 ∈ {23,44,57,81}` 时叠加。对照十个固定用例：0/1/2 走 99，3/4/5/6/7/9 走 97，8（empty routing）走 MEGA 92，9 另叠加零前缀。

`NVFP4_MOE_CFG` / `NVFP4_MOE_CFG2` 能强制任意 rung，属实验开关，不构成声明域内的调用条件，也不为其建立设计身份。host 侧还有三处一致性修复：rung 不合法时重选，两个 GEMM 的中间表示家族（`fam`）不一致且含 fam-2 时强制 `cfg = cfg2 = 7`，`>= 4` 与 `< 4` 混用时退到 rung 0；声明域内三条都不触发。

device 侧 `launch_gemm` 的 cp.async 回落只覆盖非 WS3 的 fam-2 mono rung（落到 8 或 10）与 flat-23：后者的 map 被拒时把 cfg 改成 12，而 `wide` 按 12 重新判定为真，于是经链尾的 `fc = wide ? 8 : 10` 最终落到 rung 8 的 cp.async 形式。WS3 全部 rung（含 97/99）在操作数图不可编码时返回 733，REDF 返回 732，mono split-K 返回 731，都没有回落——因为它们的流水契约包含 TMA box 与 fp32 部分和；rung 80/81 另有 drain map，缺失时返回 738（同样不回落）。所以走 `launch_gemm` 的两份设计——[root](root.yaml) 与 [split_k](split_k.yaml)——都要求 TMA 图可编码：权重侧每行 payload 字节 `H/2`（GEMM1）或 `I/2`（GEMM2）须 16 字节对齐且 `>= 128`，行数 `(2I 或 H)*E` 须是 32 的倍数；GEMM2 的 act 行 `I/2` 同样须 `>= 128`；rung 81 的 drain map 另需 `H >= 64` 且 `Rmax >= 32`，后者与 host 的 `tstore_ok = T*K >= 32` 是同一条件，所以 81 不会在 drain map 不可编码时被选中。声明域内 `I >= 256`、`H >= 2048`、`E ∈ {128,256}`，这些条件全部成立；唯一剩下的前提是 `cuTensorMapEncodeTiled` 能经 cudart 取到（`encode_entry`），root.yaml 已把它连同"图不可编码即拒绝、不回落"写进 `REALIZATION.Require`；split_k.yaml 的 `REALIZATION` 照实登记了同一前提的三处具体形式：两个 GEMM 的多维 TMA box（行代数等于 Contract 的 `prepared_row`，不可编码即拒绝）、A 侧换成 `hidden_states` 上的 2-D UINT8 `tile::gather4` map（`hidden_dim/2` 不是 16 的倍数或不足 128 字节即拒绝，同样没有 cp.async 回落）、以及 GEMM2 `EPI` 的 rout bulk store map（需 `hidden_dim >= 64` 与 `route_capacity >= 32`，缺失即拒绝），733/738 一类硬失败因此都写在正文里。MEGA 不在此列：cfg=91/92 分支不经 `launch_gemm`、不取 `tma_set`/`tma_d_set`，`k_mega_body<false>` 用普通 gmem 载入取 w1/w2 payload、用 `__ldg` 查 `g_e4m3_f32` 表取 scale，全函数没有任何 tensor map 或 `cp.async.bulk`（`cp_async16` 只出现在 `STAGED=true` 的 rung 91 分支），因此 733/732/731/738 与上述对齐、行数、drain map 条件都与它无关。mega.yaml 的 `REALIZATION` 登记的是另一组必要实现条件：`__launch_bounds__(512, 2)` 与落在 48KB 默认预算内、不申请 opt-in 属性的动态 shared `(hidden_dim + hidden_dim/8 + 96)*4 + 64`；`acc32`/`cnt` 的分配时清零加每次 finalize 自清构成初态保证，因此没有 memset 提交；ticket 前后各有一次 device 级 release/acquire 栅栏。它的 Design 不取任何 tensor map，`Flow.Launch` 只有一条无 `start_after` 的提交，因此也没有 PDL 链。`cfg >= 84` 落到链尾会返回 734/735 而不是静默跑错 kernel。

### 主要机制与依据

以下按 root.yaml 的实际对象命名：step 是 `COUNT`、`SCAN_TILES`、`SCATTER`、`GATHER`、`GEMM1`、`GEMM2`、`FINALIZE`，两个 GEMM 的角色是 `PRODA`、`PRODB`、`MMA`、`EPI`，其余 step 只有 `MAIN`；数学值用 `DESIGN.Math_reshape` 的符号名（`counts`、`offs`、`tile_offsets`、`tile_expert`、`tile_first`、`route_of`、`gathered_payload`、`gathered_scale`、`act_payload`、`act_scale`、`rout`、`acc`），源码缓冲名只在需要定位固定来源时并列。规模符号也沿用 root.yaml：`route_count` 只指有效路由数，`route_capacity = token_count*slot_count` 才是源码 host 侧的 `R = T*K`；下文一切 host 门槛（97/99 分带、MEGA-92、`small_thresh`、SELFPREP、finalize 宽度）都以 `route_capacity` 为量，`route_count` 只用于"哪些行是 padding"这类有效性判断。

1. 一条七节点流水线，按 route-tile 分组。`Work_schedule.Flow.Launch` 依次提交 `COUNT`、`SCAN_TILES`、`SCATTER`、`GATHER`、`GEMM1`、`GEMM2`、`FINALIZE`，每条以 `start_after` 前驱的 `launch_ready` 相接（PDL 开启形式），而 `Flow.Handoff` 的每个值另给 `ready: kernel_done`；`counts` 的清零是交接上的 `initialize: 0`，不是第八次提交。工作单元是 (route tile, n-tile)：`COUNT` 与 `SCAN_TILES` 由 per-expert 计数生成 `tile_expert[j]` 与 `tile_first[j]`，每专家 `ceil(counts[e]/bm)` 个 128 行 tile；GEMM 网格是 `capped_grid_tc(n_tiles, max_tiles)`，kernel 以 `item = blockIdx.y*gridDim.x + blockIdx.x` 起、按 `gridDim.x*gridDim.y` 步进持久遍历 `tile_count * n_tiles`（split-K 再乘 SK）。`tile_bound = ceil_div(route_capacity,bm) + min(expert_count,route_capacity)` 只是 host 上界，真实 tile 数在 device 的 `tile_offsets[expert_count]`，没被领取的 item 直接返回，网格上限把空转 CTA 压到 2 CTA/SM（自动 296）。

2. block-scaled NVFP4 tcgen05 GEMM，两个操作数都保持 packed（`Math_reshape` 的 `bsprod`）。一个 stage 是 256 个 FP4（每行 128 payload 字节，`F4_ROWB`）与 4 个 kset（`F4_NK`）；E4M3 scale 先落 shared（`sfa_ring`/`sfb_ring` 的 `f4_sf_off` 布局），再由 `MMA` 的 `compute:sf_tmem`（`tcgen05.cp.cta_group::1.32x128b.warpx4`）搬进 `sf_tmem`，MMA 是 `tcgen05.mma kind::mxf4nvf4 block_scale scale_vec::4X`，累加器在 TMEM 的 `accumulator`。因此不存在 fp4→bf16 解码步骤，`hid_bf` 与 `fc1` 都不分配。prepared 权重布局（gate/up 交织、32 行置换、128×4 scale swizzle）由 TMA 多维 box 的坐标代数直接吸收，与 Contract 的 `prepared_row` 逐项相符，GEMM1 的 up/gate 两个 64 行半区在 NPAIR 下合成一条 n128 MMA 的两个 box。

3. WS3 七 warp 角色分工。224 线程、2 CTA/SM，TCOLS 192 → TALLOC 256。`PRODA`（warp0）是 A-scale producer：LDG.128 的 `sf_prefetch` ping-pong 寄存器加 `compute:sfa_stage` 的 STS.32；`PRODB`（warp1）是 B producer：`load:a_payload`/`load:b_payload` 的 TMA box 加 `load:b_scale` 的 4 字节 cp.async（`cp.async.mbarrier.arrive.noinc`）；`MMA`（warp2）发 `compute:sf_tmem`、`matmul:a_payload@b_payload` 与两次 commit；`EPI`（warps3–6）按 `warp & 3` 绑定 TMEM lane quadrant 排空。同步全走 mbarrier：stage barrier 收 34 次 arrival（tx 字节 + warp0 + 32 个 warp1 cp.async），`signal:stage_retired` 释放环槽，`signal:accumulator_full`/`await:accumulator_free` 承担 item 边界的累加器交接，主循环里没有 block 级会合。DEEP 把 payload 环（`a_ring`/`b_ring`，深 3）与 scale 环（`sfa_ring`/`sfb_ring`，深 2）的等待拆成 `await:payload_slot_free` 与 `await:scale_slot_free`，否则第三个 payload buffer 是死 shared。

4. clamp、activation 与 NVFP4 QDQ 融进 GEMM1 的 `EPI`。该角色每 32 列 chunk 从 `accumulator` 取 up/gate 各 32 个 fp32，做 clamp（up 双侧、gate 只上界）、activation（type 3 与 type 10 两式共用 `activation2`）、每 16 通道一组的 QDQ（pair 最大值树 → `f32_to_e4m3(min(amax/6,448))` → `__frcp_rn` 反乘 → 硬件 `cvt.rn.satfinite.e2m1x2` 打包），由 `store:act_payload` 与 `store:act_scale` 直接写出 packed `act_payload`/`act_scale`；lane mask（`token_local < rows_valid`）丢弃 tile 的 padding 行。SK=1 时没有独立 activation 节点。

5. GEMM2 物化 per-route BF16，`FINALIZE` 做路由加权和。GEMM2 的 A 是连续 route 序的 packed act，`EPI` 的 `compute:rout_bf16` 把每 route 的 fp32 结果 `__floats2bfloat162_rn` 后写进 `rout`；TSTORE 时整 32 行 quadrant 先落 `sink` 的 2KB 槽，由 lane0 发一次 `store:rout_bulk`（`cp.async.bulk.tensor.2d`），部分 quadrant 保留 `store:rout_masked`（其 padding 行属于下一个专家的 rout 区间）。`FINALIZE.MAIN` 的 `compute:weighted_sum` 按 (token, h-chunk) 沿 slot 升序把 `route_of[t,s]` 指向的 rout 行乘 `scores[t,s]` 累加成 fp32，`store:output` 做最后一次 bf16 RNE 并无条件写满 `output_buffer` 的每个元素。

6. CUDA graph 捕获与 host identity 缓存属于调用边界，不改提交身份。`moe_run` 把 ABI 全字段（除 `stream`）连同所有进程级 knob 哈希成 key，同 key 第二次出现时把整条 launch 序列捕获成图并重放；重放执行同一批 kernel、读同一批指针上的当前字节，不 memoize 任何数值。host 侧 `_hot` 用 15 个对象/标量的 identity 校验命中预建 ABI，`_fast` 是 37 项 id-tuple 的 dict，`nvfp4_fast.c` 在 C 层做同一校验。任何不匹配都回落到完整校验的慢路径并重建 ABI、重捕图；`_c()` 产生拷贝时不发布缓存。PDL 属性默认开启，`nroutes >= 49152` 时关闭。

7. capture-time 统计只选 kernel，不改数值。G2GATE 在 shape 上界与下界跨越 3072 阈值时把 `ids` 读回 host 数真实 route tile，用于在 WS3 与单体 GEMM2 叶子之间选择；MEGA-92 的 empty 判据与 zero-capture 探针同理，且都只在慢路径 publish 时算一次。三者的正确性都不依赖统计：GEMM2 各叶子写同一批字节，MEGA 的 unit 循环每次读真实 ids 并做 CTA 级 census，零前缀每次重放由 `k_zero_verify` 从当前字节重判。因此 root.yaml 的 `Dispatch.when` 用输入条件（含"payload 幅值非全零"）而不是统计结果或用例编号来划范围。

### 未收范围与已知缺口

rungs 0–6（warp-mma 阶梯与 tcgen05 bf16 家族，配 `k_decode_hidden` 解出 bf16 激活、GEMM1 写 fp32 `fc1`、`k_act` 再写 bf16 `act`）的中间表示与 fam-2 确实不同，但只在 `_rung7_ok` 失败时可达，声明域内永不选中；本次不交付完整 schema，也不改称参数或局部变化，按域外 fallback 家族如实记录。一批 override-only 探针同样不交付：82/83（PFTMA）、89/90/93/94（NIPRE）、95（SK4）、98（NPAIR 的 AMODE 2 SK2 形式）、100（PP）、101/102（MBH）、103/104、105（EPI8）、88（FUSE）、96（SELFPREP），源码逐条记录了实测判定（多为 REJECTED 或等待配对 A/B）；其中机制上值得留的差额已按下面的记录表达。`nvfp4_moe_base.cu`、`_d81.cu`、`_j18.cu`、`_t80.cu` 与 `solution_base_host.py`、`solution_d81.py`、`solution_j18.py`、`solution_t80.py` 是历史 A/B 快照：四个 host 的 `_SRC` 都仍指向 `nvfp4_moe.cu`，而它们的 `_ABI_FIELDS` 比当前 `MoEABI` 短（缺 `small_thresh`、`zflag`、`zflag_host`，46 项对 49 项），因此不与当前 device ABI 相容，不能作为独立实现入口，只用于 lineage。

P2 交 P3 定向核实的调用边界已全部核实并落在 root.yaml：graph 重放与 identity 缓存只改 host 路径，`moe_run` 要么重放已捕获的节点集、要么 eager 直发同一序列，两图 clean 分支需要非零 `zflag_host` 而 root 的 `when` 已排除，故任何缓存命中都不改变提交身份；A 操作数图只按 `Rmax` 行编码，越界 box 被裁剪并零填充而非越界读，`GATHER` 从不写 `r >= route_count` 的行，E2M1 与 E4M3 都不 trap，这正是 `Math_reshape` 声明的 padding 契约；`tma_set` 以指针与几何为 key 并缓存 refused，故 in-place 变更安全、被拒几何每次响亮失败；GEMM2 `EPI` 每 warp 在 retire 会合前的 `await:stores_drained`（`cp.async.bulk.wait_group 0`）使 `GEMM2.kernel_done` 蕴含 `rout` 全局可见，正是 `FINALIZE` 的 `await:predecessor` 所消费的。

沿用 P1 的两项来源缺口：activation 域矛盾（`shape_range.json` 写死 'situ'，`shape_cases.json` 的九个用例构造 type-3）由 Contract 的并集回答，两式在同一 `EPI` 内、不改变任何机制识别或代表选择；验收比较器公式缺失只影响外部通过边界，`Golden_reference.Tolerance` 照实记为 source-only。另有两项本目录照实保留：`Hardware_specification` 除 `Execution` 的 thread/warp/cta/sm/grid 登记外仍是占位，root.yaml 的 `resident_cap`、2 CTA/SM 与 TMEM、shared 预算按源码常量手工核对而非由硬件登记推出；源码自述的 rung 间 bit-exact 论断本次未独立验证，Design 未依赖它，只在记录中作为源码已述的取舍依据出现。

MEGA 侧另有两条来源限制照实保留。其一，host 的 `rung_ok(92)` 只检查 `hidden_dim % 256 == 0`，而 `k_mega_body` 的 FC1 块循环迭代 `hidden_dim >> 9` 次、每次由 32 个 lane 各覆盖 16 个 hidden 通道即共 512 个，因此实际需要 `hidden_dim % 512 == 0`：256 的奇数倍会让尾部通道静默不进点积。声明域的三值 2048/4096/7168 都是 512 的倍数，故该缺口在本目录范围内不可达；mega.yaml 的 `Block-factored SIMT FP32 FC1 slice` 已把 512 倍数写成声明域事实，来源本身没有把它登记成门槛，本目录也不代为补造。其二，mega 的 ticket finalize 只 stage 8 个 slot 的 route 与分数（shared 数组 8 项，staging 循环是 `k < slot_count && k < 8`），而 ticket 目标 `nvt*chunk_count` 与 finalize 的 route 循环用的 `nvt` 都按全部 `slot_count` 个数统计，因此它依赖 Contract 声明域的 `slot_count = 8`（`shape_range.json` 把 topk 固定为 8），与 host 的 `K == 8` 门同源；`slot_count > 8` 会让 finalize 迭代到未 stage 的槽位、读过期 shared 值。

## 完整设计

当前完整设计集合含 root 共三份，未超十份上限。三份的 `when` 按 host 的 promoted 选择互斥——fused 带 `route_capacity > 1536`、SK 带 `route_capacity <= 1536` 且保留带 bulk drain 的 WS3 GEMM2 叶子、MEGA 的 capture-time 空路由带——但都不是最大成立域：root 只承认 host 无需回读真实 route tile 就能判定的形状上界，SK 带里 `ws_g2` 为假的配对与 payload 全零的输入都落在三份 `when` 之外。这些差额由下面的记录承担：GEMM2 的 57/44/23 三条叶子记录加组合轴记录承担 `ws_g2` 为假的配对（固定用例 0 与 1 属此），零输入验证前缀记录承担 payload 全零（固定用例 9 属此），路由准备、finalize 宽度、ACT 切片形式等记录承担同一带内的其余已选与对照形式。域外与未 promoted 的内容——rungs 0–6 家族、一批 override-only 探针、四份历史 A/B 快照——按"未收范围与已知缺口"如实说明，不交付完整 schema，也不改称参数或局部变化。精确参数、`when` 与修订号以各 YAML 为准，本表摘要只用于辨认机制与保留理由。

## 变体与组合

### GEMM2 WS3 排水与等待旋钮（参数）

- 基线：并列两份。[root](root.yaml) 的 `DESIGN.Tile_pipeline::GEMM2`（`EPI` 的 `sink` 区域、`store:rout_bulk`、`await:sink_free`、`await:stores_drained`，`PRODB` 的两条环等待）与 `DESIGN.Work_schedule::GEMM2`，相关前提是 `REALIZATION` 的 drain map 一条；[split_k](split_k.yaml) 的 `DESIGN.Tile_pipeline::GEMM2` 与 `DESIGN.Work_schedule::GEMM2`。两份的 GEMM2 整区对象逐项同名、shape 与表达式一致（`PRODA`/`PRODB`/`MMA`/`EPI` 四个角色、`sink` 与各环存储、`Index` 的 `t`/`ks`/`g`、`Worker_count = (hidden_dim/128)*min(tile_bound, ...)`、`Math_reshape` 的"Fc2 product and per-route BF16"与 `rout`；split_k 的 `Schedule.Strategy` 另注明叶子由定住 launch 集那次调用的 ids 决定），实质区别只在 act 的生产者——root 是 GEMM1 的 `EPI`，split_k 是 `ACT` step——而两者写出的 `act_payload`/`act_scale` 接口逐字相同，因此下面每处替换在两份设计里指向同一个对象。
- 差异与联动：rung 57 是同一 `f4_body_ws` 主体（`k_gemm_f4_ws2<128,false,3,2,0>`）关掉 TSTORE/DEEP/EPITB/CPHOIST/EARLYDONE：`rout` 全部走 `store:rout_masked`，`sink` 的 4×2048B 连同 `await:sink_free` 与 grid-exit 的 `await:stores_drained` 都不再需要，动态 shared 从 114960 降到 106640，drain map 的 `hidden_dim >= 64` 与 `route_capacity >= 32` 前提随之消失；DEEP 关掉后 `PRODB` 的 `await:payload_slot_free` 与 `await:scale_slot_free` 合并回一条等待。staged image（`a_ring`/`b_ring` 深 3、`sfa_ring`/`sfb_ring` 深 2）、MMA 序列与 epilogue 算术不变。组合到 split_k 时另有一处联动：57 不用 bulk drain，因此 split_k `REALIZATION` 中 GEMM2 `EPI` 的 bulk store map 一条（连同 `hidden_dim >= 64` 与 `route_capacity >= 32`）不再适用，其 `when` 里 `route_capacity >= 32` 那一项也失去依据——host 在 `ws_g2` 为假时根本不检查 `tstore_ok`。
- 条件与依据：`ws_g2` 为真但 `route_capacity = token_count*slot_count < 32` 时选 57，与 drain map 的 `Rmax >= 32` 是同一条件（源码在 map 缺失时返回 738 而不回落）。源码记录 arm-b 的 TSTORE 与 DEEPxTSTORE 两次独立预注册实测，并称 57 与 44 bit-identical（源码自述，本次未独立验证）。

### GEMM2 单体 128 线程叶子（局部）

- 基线：并列两份，对象对应同上一条。[root](root.yaml) 的 `DESIGN.Tile_pipeline::GEMM2` 全部四个角色（`PRODA`/`PRODB`/`MMA`/`EPI`）与其 `Storage`，`DESIGN.Work_schedule::GEMM2` 与 `Math_reshape` 的"Fc2 product and per-route BF16"不变；[split_k](split_k.yaml) 的同名 `DESIGN.Tile_pipeline::GEMM2`、`DESIGN.Work_schedule::GEMM2` 与同名 `Math_reshape` rewrite 亦然。
- 差异与联动：rung 44 用 `f4_body`（`k_gemm_f4_tma<128,false,3,0,3,0,1,false,false,true>`，即 BN=128、STAGES=3、AMODE=0、SFS=3、SK=1、SFCP）：128 线程 4 warp 的同质角色取代七 warp 分工，一个 `MAIN` 角色承担 staging、MMA 与 TMEM 排空，每 stage 两次 block 级会合取代 mbarrier 环；scale 走 cp.async（SFCP）且 `sfa`/`sfb` 环深 3 而非 2，`sf_prefetch` 寄存器环消失。tiling（`bm=128`、BN=128、STAGES=3）、staged image、MMA 序列、TMEM 排空与 `rout` 输出都不变，`minBlocks` 仍是 2，item 编号与 `Worker_count` 表达式与两份基线相同。组合到 split_k 时同样去掉 bulk drain：split_k `REALIZATION` 的 drain map 一条与 `when` 的 `route_capacity >= 32` 不再适用；44 的 128 线程同质主体取代 split_k GEMM2 的七 warp 角色分工，而 `ACT` 产出的 `act_payload`/`act_scale` 接口与 `rout` 输出不变。
- 条件与依据：`ws_g2` 为假且 `intermediate_dim != 256` 时选中（fixed 0/1 一类小工作空间，角色分工的启动成本摊不平）——这两个用例的 `route_capacity` 分别是 8 与 256，都在 split_k 的 `when` 之外，故由本条与组合轴记录一起承担；源码记录约 128 items 0.915x、约 2048 items +1.2%、4096 items 以上 +3–6% 的实测边界。

### GEMM2 flat-stream 叶子（局部）

- 基线：[root](root.yaml) 的 `DESIGN.Tile_pipeline::GEMM2`（Index 的 `t`/`ks`/`g` 与四个角色的 Pipe），并列 [split_k](split_k.yaml) 的同名 GEMM2 整区（对象对应同前两条），并与上一条单体记录组合（同为非 WS3 主体）。
- 差异与联动：rung 23 `f4_flat_g2` 取消 per-item 的环 prime 与 drain，让一条 stage 流跨 item 边界，`g` 不再按 item 复位（stage `g+2` 的 box 在迭代 `g` 发出，两级 TMA 延迟始终在途）；item 元数据放在 3 槽寄存器环里（按 `t % 3` 取槽，两份基线的 GEMM2 `Storage` 中都没有对应区域，需新增一份寄存器存储），由所有线程做相同的广播加载、在下一次 MMA 之前提交；item `t-1` 的排空移到 item `t` 第一次迭代的开头、前一次 MMA 的 retire 屏障之后、下一个 MMA 发射之前，因此累加器交接不再是 `MMA` 与 `EPI` 之间的一对跨角色事件，而是同一角色 pipe 内的 block 级会合，TMEM 复用的原有次序保持不变。NK1 特化把 `t`/`ks` 折叠成常量，只在 `nk == 1` 时精确。23 也不取 drain map，与 split_k 组合同时去掉其 drain map `Require` 与 `when` 的 `route_capacity >= 32`。
- 条件与依据：只在 `intermediate_dim == 256` 且 `ws_g2` 为假时配对（deepseek 几何的小 R）；源码依据是 `nk == 1` 时每个 stage 都是 item 边界，shape 4 的 GEMM2 曾测得 172–177us 对 85us 的流量下限。源码另记录生产只经 NK1=true 特化启动，generic `nk > 1` 的步进 cursor 形式曾触发 illegal access，故该叶子不得推广到 `nk > 1`。

### GEMM1 与 GEMM2 叶子的组合轴（组合）

- 基线：[root](root.yaml) 的 `DESIGN.Work_schedule::GEMM1` 与 `GEMM2`，并列 [split_k](split_k.yaml) 的 `DESIGN.Work_schedule::GEMM1`、`ACT` 与 `GEMM2`；并链接上面三条 GEMM2 叶子记录。对象对应：两份设计共享 `Math_reshape` 的 `act_payload`/`act_scale` 符号与字节布局（root 由 GEMM1 的 `EPI` 生产，split_k 由 `ACT` 生产），也共享同一 route-tile 图（`counts`/`offs`/`tile_offsets`/`tile_expert`/`tile_first`，`bm` 都是 128；root 由 `COUNT` 与 `SCAN_TILES` 生产，split_k 由单块 `PREPARE` 生产），源码要求两个 GEMM 就 `bm` 达成一致。
- 差异与联动：GEMM1 叶子（97/99）与 GEMM2 叶子（81/57/44/23）是互不作用的轴：GEMM1 侧的变化只改 act 的生产者（root 的 `EPI` 或 split_k 的 `ACT`），GEMM2 侧的变化只改 `rout` 的生产者，因此上面三条叶子记录可与任一份基线的 GEMM1 按需组合；组合后的具体选择仍须写明各自前提（81 需 drain map 及其 `hidden_dim >= 64`、`route_capacity >= 32`，44 需 SFCP 主体，23 需 `nk == 1`），本目录不按配对新建节点或复制记录。固定用例 0 与 1 就是 99 配 44 的实际组合：`ws_g2` 为假使它们落在 split_k 的 `when` 之外，用的却正是 split_k 的 `PREPARE`/GEMM1/`ACT` 正文加 44 叶子与 4 元素 finalize。
- 条件与依据：源码逐对组合——host 的 `cfg2` 块对 97 与 99 用同一张配对表，device 的 `launch_gemm<false>` 只按 `cfg2` 分派；组合不引入新的整体组织。

### 路由准备的两条路径（局部）

- 基线：并列两份。[root](root.yaml) 的 `DESIGN.Work_schedule::COUNT`、`SCAN_TILES`、`SCATTER` 三个 step 与 `Tile_pipeline` 中对应的 `MAIN` 角色，`counts` 交接上的 `initialize: 0` 表达那次同时清零 `counts` 与 fill 计数器的 memset，不是独立提交；[split_k](split_k.yaml) 的 `DESIGN.Work_schedule::PREPARE` 与 `DESIGN.Tile_pipeline::PREPARE.MAIN`（`compute:stage_ids`/`histogram`/`expert_scan`/`scatter`/`tile_map` 五段）。本条的小路径相对 root 是变化，相对 split_k 则是已选正文，这里说明它各自的适用条件。
- 差异与联动：小路径 `k_prepare_small` 把三个 step 合成一次提交——一个 1024 线程 block 完成 stage ids → warp-private 直方图 → 跨 warp 前缀 → `scanNW<32>` 专家扫描 → scatter → tile 图，并顺带清零 fused split-K 计数器；root 的大路径把它拆成 memset 加 `COUNT`（shared 两级直方图，每 block 每专家一次全局 atomic）加 `SCAN_TILES`（扫描与 tile 图合并进一个 block）加 `SCATTER`（`k_scatter_agg`）。两条路径写同一组 `counts`、`offs`、`tile_offsets`、`tile_expert`、`tile_first`、`route_of`、`route_token`、`route_slot`、`route_expert`，专家内 route 顺序都是任意置换，下游只读这个元组。
- 条件与依据：`small_thresh` 默认 6500，`route_capacity` 落在 (3000,6500] 且 capture-time 直方图非空时取 3000；root 的 `when` 带内固定用例 3/9（R=4096、skewed 非空）因此走大路径，4/5/6/7 超过 6500 也走大路径，所以 root.yaml 以大路径为正文；这个判断不变。但 root 的 `when` 带内 `1536 < route_capacity <= 3000`（以及 (3000,6500] 且直方图为空、又因 `route_capacity*hidden_dim > 32e6` 没被 MEGA 接走）仍走小路径，这部分差额由本记录承担。SK 带则恒走小路径：`route_capacity <= 1536` 小于 `small_thresh` 的任何可达取值（3000 或 6500，或 env 覆盖），而 device 侧的判据就是 `route_capacity <= small_thresh`，因此 `k_prepare_small` 正是 [split_k](split_k.yaml) `DESIGN.Work_schedule::PREPARE` 的正文而非备选——root 的三个 step 合成一条提交，`Flow.Launch` 只剩五条，`Handoff` 里的路由元组（`counts`/`offs`/`tile_offsets`/`tile_expert`/`tile_first`/`route_of`/`route_token`/`route_expert`）生产者都是 `PREPARE`，`counts` 上也没有 `initialize: 0`（单块 shared 直方图不需要那次全局清零 memset）。两条路径确定性地产出相同的 `counts`、`offs`、`tile_offsets`、`tile_expert`、`tile_first`——整数求和、`scanNW` 扫描与 `ceil(counts[e]/bm)` 的 tile 图都与顺序无关。但 `route_of`/`route_token`/`route_slot`/`route_expert` 只保证专家内置换等价，不逐字节相同：小路径的位置是跨 warp 前缀基址加 warp 内 shared `atomicAdd` 的到达序，大路径的 `SCATTER` 先以全局 `atomicAdd(&fill[x])` 按 block 到达序为每 block-专家预留连续区间、再用 shared rank 取块内槽位，所以其置换连 run-to-run 都不保证可复现（`k_scatter` 同理）。输出字节仍不变：每条 route 的 GEMM 值与它占的槽位无关，`FINALIZE` 经 `route_of` 按固定 slot 升序求和，重排专家内位置改不了任何输出。因此 `small_thresh` 只是性能旋钮，不能当作确定性或可复现开关，专家内 route 序也不能用于任何顺序论证（含 split-K 的切片序，那是按 `part` 的切片下标升序，与此无关）。源码注释称两条 prep 路径 bit-identical，本目录按上述更强的事实记录。

### 准备与聚集的等价实现选择（参数）

- 基线：[root](root.yaml) 的 `DESIGN.Work_schedule::SCATTER`（叶子 `k_scatter_agg`）与 `GATHER`（叶子 `k_gather_f`，`Worker_count` 的 cap 1184、128 线程），以及 `Math_reshape` 的"Route-ordered activation operand"（`gathered_payload`/`gathered_scale`）；其中"小路径可换 `k_prepare_small2`"一项的基线是 [split_k](split_k.yaml) 的 `DESIGN.Work_schedule::PREPARE`，其余两项只适用于 root——split_k 没有 `GATHER` step，也没有 `gathered_payload`/`gathered_scale`。
- 差异与联动：`SCATTER` 可换 `k_scatter`（每 warp 每专家一次全局 fill atomic）；小路径可换 `k_prepare_small2`（PREP2，默认关）；`GATHER` 可换 `k_gather_t`（token-major，cap 2368 × 64 线程）或 `k_gather_a`（route-major，cap 1184 × 128）。三者只改划分与 launch 形状，即 `Partition` 的 tile 大小与 `Worker_count` 表达式，`Single_tile` 目标与 `Worktile_order` 不变。给定同一 `route_of`，三者写出的 `gathered_payload`/`gathered_scale` 图像逐字节相同——每个 (route 行, 16B chunk) 目标都由恰好一个线程写入同一份 token 字节，与划分无关；这与上一条的路由元组不同，这里的目标地址是 route 下标的确定函数，不含 atomic 到达序。PREP2 的 `k_prepare_small2` 换掉的是小路径本身：per-warp 融合的清零/staging/直方图前段，加按活跃 warp 数收窄的跨 warp 前缀；step 的划分、`Worker_count`（仍是单块 1024 线程）与产出的元组都不变，只有块内前段的分工与前缀宽度变。
- 条件与依据：这些 knob 都混进 graph key（网格与 kernel 身份烘进捕获）；`r >= route_count` 的行三种实现都不写（`Math_reshape` 已声明这些行保持原值），由 GEMM1 `EPI` 的 lane mask 丢弃。PREP2 默认关（`NVFP4_MOE_PREP2=1` 启用），源码称其 route map 与 v1 bit-identical——整数求和精确，被跳过的全零 warp 行本来贡献 0——本次未独立验证。

### finalize 的每线程宽度（参数）

- 基线：并列两份，方向相反。[root](root.yaml) 的 `DESIGN.Work_schedule::FINALIZE`（`Partition` 的 `token`/`hidden_block` tile 1024、`Worker_count = token_count * ceil_div(hidden_dim,1024)`）与 `Tile_pipeline::FINALIZE.MAIN`（`compute:weighted_sum` 读八个 rout 值、`store:output` 写 16 字节 chunk），正文是 8 元素/线程的 `k_finalize`；[split_k](split_k.yaml) 的 `DESIGN.Work_schedule::FINALIZE`（`hidden_block` tile 512、`Worker_count = token_count * ceil_div(hidden_dim,512)`）与 `Tile_pipeline::FINALIZE.MAIN`（四个 rout 值、8 字节 chunk），正文是 4 元素/线程的 `k_finalize4`。两份的 `Math_reshape`"Routing-weighted output reduction"相同。
- 差异与联动：三个宽度是同一机制的不同取值——`k_finalize4`（4 元素/线程，`hidden_block` 变 512、块数翻倍）、`k_finalize`（8 元素/线程，1024）、`k_finalize16`（16 元素/线程，`hidden_block` 变 2048、store 用 streaming `.cs`）。每元素算术与沿 slot 升序的 route 顺序不变，只是 (token, hidden) 到线程的映射、`Partition` 的 tile 大小与网格宽度变；三者都按 `dim3(ceil(nfin/128), token_count)` × 128 线程启动，`nfin` 分别是 `hidden_dim/4`、`hidden_dim/8`、`hidden_dim/16`。
- 条件与依据：选择门是 `route_capacity*hidden_dim*2 >= fin16_mb()<<20`（默认 40MB）取 16，否则 `fin_wide()`（默认开）且 `token_count <= fin_tmax()`（默认 128）取 4，否则取 8。相对 root 基线：16 在带内可达（固定用例 4/5/6/7 的 `route_capacity*hidden_dim*2` 分别约 117MB/67MB/268MB/50MB，fixed 4 的 ncu 剖面末节点确实是 `k_finalize16`），4 不可达（root 的 `when` 要求 `route_capacity > 1536` 且声明域 `slot_count = 8`，迫使 `token_count > 192`），所以 root.yaml 取未加门的 8 元素形式为正文——fixed 3 的剖面末节点正是 `k_finalize`。相对 split_k 基线：4 元素是正文（其 `when` 的 `token_count <= 128` 正是 fin4 的门，fixed 0/1/2 的剖面末节点都是 `k_finalize4`），8 元素是 SK 带里 `128 < token_count <= 192` 的变化（`route_capacity <= 1536` 仍成立，例如 `token_count = 192`、`slot_count = 8` 给 `route_capacity = 1536`），16 元素在带内不可达，因为 `route_capacity*hidden_dim*2 <= 1536*7168*2 ≈ 22MB < 40MB`。三个 knob（`fin16_mb`、`fin_wide`、`fin_tmax`）都混进 graph key。

### GEMM 环深与 scale 通路旋钮（参数）

- 基线：并列两份。[root](root.yaml) 的 `DESIGN.Tile_pipeline::GEMM1` 与 `GEMM2` 的 `Storage`（`a_ring`/`b_ring` 深 3、`sfa_ring`/`sfb_ring` 深 2、`sf_tmem`、`accumulator`、`sf_prefetch`，GEMM2 另有 `sink`）、四个角色的等待拓扑，以及 `REALIZATION` 的 fused m128n128k64 一条与 `Forbid` 的 item-parity 第二累加器；[split_k](split_k.yaml) 的同名 `Storage` 与角色等待拓扑。这些旋钮是两份设计共用的 `k_gemm_f4_ws2`/`k_gemm_f4_ws2d` 主体的模板参数，存储对象名与环深逐项对应；区别是 split_k 的 GEMM1 已选形式本身带 SFCH+SFPF=2、NPAIR 与 DEEP，而 CPHOIST 与 EARLYDONE 在编译期就是假。`Forbid` 的 item-parity 第二累加器只在 root 登记。
- 差异与联动：STAGES/SFS 改 `a_ring`/`b_ring` 与 `sfa_ring`/`sfb_ring` 的 `depth` 与 `total_size`；DEEP 关掉则 `PRODB` 的 `await:payload_slot_free` 与 `await:scale_slot_free` 合并为一条；SFCH 把 B-scale staging 改成每 warp 指令读一段连续 128B（`load:b_scale` 的划分变，(src,dst,half) 多重集不变）；SFPF 只改 L2 预取距离，不对应任何 YAML 对象；NPAIR 把 up/gate 两个 64 行半区合成单一 128 行 SFB 块并令 `MMA` 发一条 m128n128k64（即 root.yaml 已选形式，TCOLS 224→192）；CPHOIST 是 `MMA` 的 `hoist_enabled` 运行时门；EARLYDONE 是 `EPI` 在 `c == 1` 提前 `signal:accumulator_free`；EPITB 是 GEMM2 `EPI` 的成对排空（`for(cp)` 两次 `load:tmem_chunk` 共用一次 `await:tmem_drain`）。payload 的 staged image 与每列的 k-chain 次序不变，NPAIR 是其中唯一改动 B-SF 图像者；源码逐条论证这些改动 bit-exact（本次未独立验证，也未用于任何设计判断）。
- 条件与依据：`hoist_enabled = route_capacity >= 16*expert_count` 已写在 `MMA` 的 Describe 里，是同一机制内的两条互补条件而非配置开关；NPAIR 只允许 GEMM1 BN=64、SK ∈ {1,2}、AMODE ∈ {2,3}、EPI=4（源码 static_assert）；PP（双累加器）与 NPAIR 互斥、override-only，已作为 root.yaml 的 `Forbid` 记录并附源码自测的 0.906x。split_k 带内 CPHOIST 的运行时门恒假：`hoist_enabled` 要求 `route_capacity >= 16*expert_count`，声明域 `expert_count ∈ {128,256}` 使门槛至少 2048，而 SK 带 `route_capacity <= 1536` 永远够不到；cfg 99 更在编译期就关掉 CPHOIST 与 EARLYDONE，所以 split_k 的 GEMM1 `MMA` 把 hoist 写成 off。它的 GEMM2 仍是 rung 81（CPHOIST/EARLYDONE 编译期为真，`EPI` 保留成对排空里提前的 `signal:accumulator_free`），但同一运行时门在该带内恒假，hoist 实际不发生，split_k.yaml 的 GEMM2 `MMA` Describe 已照此写明。

### ACT 的切片归约形式（参数）

- 基线：[split_k](split_k.yaml) 的 `DESIGN.Work_schedule::ACT`（`Partition` 的 `act_item`、`Target.Tile_reduction` 沿 `k_slice`）、`DESIGN.Tile_pipeline::ACT.MAIN`（`load:partials`、`load:route_expert`、`compute:act_qdq` 与其 `Waiting.Prepared`），以及 `DESIGN.Math_reshape` 的"Slice reduction of the FC1 partials"与符号 `part`。
- 差异与联动：已选形式是编译期切片数的 load hoist（`k_act_packed<true,2>`，即 SKT=2）：切片地址不依赖 `route_expert`，所以全部切片 load 先发，`route_expert`/alpha/beta/limit 在其在途时才解析，把原本两次串行的 DRAM 往返重叠——这正是 `ACT.MAIN` 的 `Waiting.Prepared` 中 `{issue compute:act_qdq} ← [{done load:partials}]` 与 `Pipe` 里 `load:partials` 先于 `load:route_expert` 所表达的。对照形式 SKT=0（`NVFP4_MOE_ACTV2=0` 恢复）用运行时循环按 `split_count` 逐切片加载：归约方法、切片升序与每切片先 up 后 gate 的次序、`part` 的 shape 与 dtype、`act_payload`/`act_scale` 的输出都不变，源码称两者 bit-identical（本次未独立验证），改变的只是 `load:partials` 的发射位置与它相对 `load:route_expert` 的次序。
- 条件与依据：`act_v2()` 在 `NVFP4_MOE_ACTV2` 未设时返回 1，函数体内注释记为 PROMOTED on this tree（dv_b39fedfe0b3e，配对同 job、各 shape bit-exact：fixed_0 0.956、fixed_1 0.926、fixed_2 0.978、domain_5 0.994，never worse）；`k_act_packed` 与该函数上方各留有一句"Knob default OFF"是残留注释，以代码默认值与 PROMOTED 注释为准。SKT 按 `sk` 取 2/4/8、其他值落回 0，split_k 的 `split_count = 2` 故取 2；旋钮混进 graph key。

### SK 带内已研究的其余 split-K 形式（局部）

- 基线：[split_k](split_k.yaml) 的 `DESIGN.Work_schedule::GEMM1`（`Partition` 的 `k_slice`、`Schedule.Strategy` 的 item 编号、`Mapping.Worker_count`）、`DESIGN.Tile_pipeline::GEMM1`（`Index.ks`、各环 `Storage`、`EPI` 的 `store:part`）、`DESIGN.Work_schedule::ACT`，以及 `DESIGN.Math_reshape` 的 `part`、"Block-scaled packed product in two slices"与"Slice reduction of the FC1 partials"。
- 差异与联动：FUSE（rung 88）把切片归约移进 GEMM1 `EPI` 的每 (tile, n-tile) 组最后到达者：`ACT` step 与它那条提交、`Flow.Launch` 的一条边、`Handoff` 的 `part` 都消失，`act_payload`/`act_scale` 改由 `EPI` 生产，`Math_reshape` 的切片归约从独立节点变成 epilogue 内的一段。rung 95 把 `split_count` 由 2 改到 4：`Partition.k_slice` 的 size、`Index.ks` 上界（`hidden_dim/(256*4)`）、网格 x 维的乘数、`part` 的第一维与每元素多一次 fp32 加法随之变；此时 `hidden_dim = 2048` 只剩 `nk = 2` 个 stage，低于环深 3。rung 98 保留 root 的预聚集 A（AMODE=2，即保留 `GATHER` 节点与 `gathered_payload`/`gathered_scale`）而只取 SK=2 与 NPAIR，等于把 split_k 的"Direct clipped activation operand"换回 root 的"Route-ordered activation operand"，`PRODB` 的 `load:a_payload` 从 `nbox` 条四行 gather box 变回一条 128 行 box。
- 条件与依据：三者都是 override-only 探针（`NVFP4_MOE_CFG=88/95/98`）。源码记录 FUSE 在 8 个 SK 带 shape 上全部 REJECTED（1.02-1.27x，归约尾巴压在 epilogue warp 上），rung 95 在 6 个 SK 带 shape 上 REJECTED（1.007-1.099x），rung 98 尚无配对 A/B。控制关系按源码逐条：78↔99 与 75↔98 各只差 NPAIR，75↔78 只差 clipped gather4 加 SFCH/SFPF=2，78↔95 只差 SK，78↔88 只差 FUSE；单体家族里 76↔43 只差 clipped gather4、77↔76 只差 clipped/unclipped（源码的定价路径是 43→77 算删掉预聚集节点、77→76 算裁剪）。99 相对其控制 78 的实测为 fixed_2 1.013/1.012、domain_5 1.019/1.020、domain_7 1.020/1.010，fixed_1/domain_1 中性，全部 bit-exact（源码自述，本次未独立验证）。

### MEGA 的权重 staging 形式与网格上限（局部）

- 基线：[mega](mega.yaml) 的 `DESIGN.Tile_pipeline::MAIN` 的 `Storage`（`x_image`/`ug_image`/`aq_image`/`cta_scratch`/`ticket_scores`，没有任何权重 staging 区）与 `Role.MAIN` 的 `compute:fc1_slice`/`compute:fc2_partial`，以及 `DESIGN.Work_schedule::MAIN` 的 `Mapping`（`Worker_count = min(worktile_count, resident_cap)`）与 `Schedule.Worker_assignment.Preassigned`。
- 差异与联动：STAGED=true（rung 91，`k_mega_decode`）在同一 `Storage` 里增加两块权重区——每 unit 的 64 行 w1 payload（`64*hidden_dim/2` 字节）与每 hidden 行的 16 字节 w2 切片（`hidden_dim*16`），合计 `48*hidden_dim` 字节，用 cp.async 一次 commit group 搬入、一次 CTA 会合后从 shared 计算；`fc1_slice` 与 `fc2_partial` 的读端由 gmem 换成这两块 shared 图像，unit 划分、unit 序、ticket 协议、finalize 与全部算术都不变，差别只在操作数来源。`mega_grid_cap`（`NVFP4_MOE_MEGA_GRID`，默认 0 即取 296）只改 `Mapping.Worker_count` 的上限与 `Preassigned` 的连续段长度：unit 循环与 pass 0 都按 gridDim 跨步，所以只改划分、不改哪些 unit 执行；网格烘进 graph key。
- 条件与依据：rung 91 由 `NVFP4_MOE_MEGA=2` 启用（默认 1 不启用），host 门另加 `route_capacity <= 64` 与 `min(expert_count,route_capacity)*3*intermediate_dim*hidden_dim <= 96e6`；`rung_ok(91)` 还要求 `48*hidden_dim + (hidden_dim + hidden_dim/8 + 96)*4 + 64 <= 227KB` 的 opt-in 预算（`hidden_dim=2048` 约 105KB、4096 约 211KB，7168 被排除），因此它要 `cudaFuncSetAttribute` 而 mega.yaml 登记的 direct 形式不要。源码记录它在 tiny 非空工作上仍输给张量流水（fixed_0 1.4455、domain_0 1.8955，NCU 判为 L1TEX-scoreboard-bound 的 SIMT 解码链），故为 override/experiment-only，本目录不交付完整 schema。

### 零输入验证前缀与两图重放（局部）

- 基线：并列两份。[root](root.yaml) 的 `DESIGN.Work_schedule::Flow.Launch` 整条提交序列与调用边界（入口提交 `COUNT` 无内部前驱）；[split_k](split_k.yaml) 的 `DESIGN.Work_schedule::Flow.Launch`（五条提交，入口提交 `PREPARE`）与其各 step 角色的 `await:predecessor`。MEGA 不在此列：host 的零前缀门要求 `cfg ∈ {74,78,97,99}` 且 `cfg2 ∈ {23,44,57,81}`，92 不在其中。
- 差异与联动：publish 时 `moe_zero_probe` 一次性扫描当前字节（payload 幅值全零、scale/scores/alpha/beta/limit 有限、两个权重 scale 张量无 NaN）并同步；接受则分配 `zflag`（4 个 int32，初值 0）并在链首加 `k_zero_verify` 提交。每次重放该节点都从当前字节重新判定，无条件把零写进 `output_buffer`，再用 atomicOr 与 arrival ticket 把 `zflag[0]` 置 1（clean）或 0（dirty）并复位 `zflag[1]`/`[2]`；链上每个 kernel 的 ZGUARD 在自己的 `pdl_wait` 之后读 `zflag[0]`，为 1 就返回——即在两份基线中每个角色于 `await:predecessor` 之后多一条早退判断（split_k 的 `PREPARE.MAIN` 与 `ACT.MAIN` 同样带 `await:predecessor`）。clean 重放下 `output` 的唯一生产者是 `k_zero_verify`，其余提交已发生但没有工作；dirty 重放下完整链重算并覆盖 `output`。ZERO2（默认模式）再拆成两张图：先重放只含 verify 的 clean 图，host 在 pinned 镜像上自旋，dirty 或超时（2e8 次）才发完整链图；处于外层 host 捕获时跳过自旋并按序记录两张图。
- 条件与依据：数值依据是声明域内没有 bias，`hidden_states = 0` 推出 fc1、act、`rout`、`output` 全为零且零是精确值，与路由（含 empty 与 masked）无关；`token_count*hidden_dim >= 2^20` 才启用 mode 2（host 往返只在链足够贵时划算）。root.yaml 的 `when` 已用"payload 幅值非全零"排除该前缀，split_k.yaml 的 `when` 同样排除，正确性不依赖 capture-time 统计。固定用例 9（payload 全零，host 选 97 加 81）因此落在两份 `when` 之外，只由本记录承担其差额；零前缀的 cfg 白名单含 99，所以 SK 带内 payload 全零的输入也会叠加它。

### REDF 融合路由归约（局部）

- 基线：并列两份，对象对应同 GEMM2 叶子各条。[root](root.yaml) 的 `Math_reshape`"Fc2 product and per-route BF16"（`rout`）与"Routing-weighted output reduction"，`Work_schedule::GEMM2`/`FINALIZE` 与 `Tile_pipeline::GEMM2.EPI`；[split_k](split_k.yaml) 的同名两条 `Math_reshape` rewrite 与同名 `GEMM2`/`FINALIZE` step、`Tile_pipeline::GEMM2.EPI`。并与"GEMM2 单体 128 线程叶子"记录组合（rung 46 = 44 + REDF，47 = 19 + REDF）。
- 差异与联动：GEMM2 `EPI` 不再写 `rout`，而是把每 route 的 bf16 RNE 结果乘 routing 权重后以 `red.global.add.v4.f32` 累进 `acc32[token,hidden]`（该缓冲每次调用在侧流分支上 memset，在 GEMM2 之前 rejoin，图捕获下成为并行分支），`FINALIZE` 换成 `k_convert` 只做最后一次 bf16 舍入，`Flow.Handoff` 的 `rout` 由 `acc32` 取代。声明的数值边界（per-route BF16 物化、fp32 路由求和）保留，但 fp32 求和顺序从 slot 升序变成 atomic 顺序——Contract 本就把该顺序留为未指定，reference 自己也是 atomic `index_add_`。`rout` 缓冲与 `FINALIZE` 的散射读消失。
- 条件与依据：env `NVFP4_MOE_REDF` 门控、默认关，源码记录尚未完成配对 A/B；选中时 `ws_g2` 分支被跳过，因此它只与单体 GEMM2 相容，且 46/47 在 map 被拒时故意硬失败（732）而不回落到写 `rout` 的 kernel。host 的 `cfg2` 块对 97 与 99 用同一张表，所以 SK 带的 99 配 46 同样成立。

### SELFPREP 网格内路由准备（局部）

- 基线：并列两份。[root](root.yaml) 的 `DESIGN.Work_schedule::COUNT`/`SCAN_TILES`/`SCATTER`（三者不再提交）与 `GEMM1`（`Tile_pipeline::GEMM1` 各角色在 `await:predecessor` 之前多一段 `self_prep`）；[split_k](split_k.yaml) 的 `DESIGN.Work_schedule::PREPARE`（这条提交不再出现）与其 `DESIGN.Tile_pipeline::GEMM1` 各角色。rung 96 实际长在 SK 带的 78 上，所以 split_k 才是它本来的宿主，root 一侧按同名机制对应。
- 差异与联动：rung 96 在 GEMM1 grid 内用 `self_prep` 重算整张路由图（在 `pdl_wait` 之前，因为只读输入 ids），从而不提交 prep 节点；每个 CTA 都算一遍，属并发同值写，CTA 自己的读由收尾 block 会合后的自身写满足，下游 kernel 靠 stream 序观察。它产出的 `counts`/`offs`/`tile_offsets`/`tile_expert`/`tile_first` 与 `k_prepare_small` 相同，但 route 元组用的是规范序——chunk-major、专家内按 route 下标升序，rank 由确定性的 shfl 扫描加 chunk 内前缀得出——而 root 的 `SCATTER` 用 block 到达序加 shared rank，小路径用 warp 内 atomic 到达序，三者一般不是同一置换；源码的保证停在输出层面（专家内 route 序按契约任意，消费者只认元组，故每条 route 的输出位置不变）。
- 条件与依据：正确性范围 `route_capacity <= 256`（`self_prep` 内 `R = p.T*p.K`，`chist` 只有 4 个 64-route chunk）且 SK2 整除；env `NVFP4_MOE_SELFPREP` 门控、默认关，等待配对 A/B。host 门还要求默认 GEMM1 叶子是 78，而当前 promoted 叶子是 99，所以声明域内实际不可达。

### 网格上限、PDL 与 eager/图重放（参数）

- 基线：并列两份。[root](root.yaml) 的 `DESIGN.Work_schedule::GEMM1`/`GEMM2` 的 `Mapping`（`resident_cap` 与 `Worker_count` 的 `min(tile_bound, ...)` 形式、`Preassigned` 的 start/stride）、`Flow.Launch` 的 `start_after: launch_ready` 与 `Flow.Handoff` 的 `ready: kernel_done`，以及调用边界；[split_k](split_k.yaml) 的 `DESIGN.Work_schedule::GEMM1`/`GEMM2` 的 `Mapping` 与 `Preassigned`（同一 capped 持久网格，只是 GEMM1 的 item 数乘了 `split_count`）、`Flow.Launch` 的五条 `start_after: launch_ready`，其 `REALIZATION` 也登记了 griddepcontrol 一条。MEGA 不在此列：它只有一条不经 `launch_pdl` 的提交，网格上限由上面的 MEGA 记录承担。
- 差异与联动：持久网格上限（自动 2 CTA/SM = 296，`capped_grid_tc3` 给三 CTA 的 rung 用 1.5 倍）只改 `gridDim.y`，item 循环按 `gridDim.x*gridDim.y` 步进，因此只改划分、不改哪些 item 执行；PDL 属性默认开、`nroutes >= 49152` 时关，kernel 内的 `griddepcontrol.wait`/`trigger` 保证可见性（`REALIZATION` 已绑定），值不变——root.yaml 的 `Flow` 取的是 PDL-on 形式，摘掉属性后同一 `Flow` 在更强的流序下仍成立；`NVFP4_MOE_NO_GRAPH=1` 或 key 未连续命中两次时走 eager 直发同一提交序列。
- 条件与依据：这些 knob 全部混进 graph key；warp-mma 阶梯不加网格上限（其 CTA 小、网格是唯一并行度），但该家族在声明域内不可达。

### host 调用缓存层级（参数）

- 基线：[root](root.yaml) 的调用边界与 `DESIGN.Work_schedule::Flow.Launch` 的提交序列——三层缓存都不改变它。这条记录对 [split_k](split_k.yaml) 与 [mega](mega.yaml) 的调用边界同样成立：缓存层在 `moe_run` 之上，与选中哪个 rung、链上有几条提交无关。
- 差异与联动：`_hot` 单条 identity 校验（15 个对象/标量加 env 快照）→ `_fast` 的 37 项 id-tuple dict → `nvfp4_fast.c` 在 C 层做同一校验并经 raw 地址调 `moe_run`（CFAST2 再省掉 ctypes marshalling 与 per-call setattr）。三层都只减少 host 时间，设备字节、捕获图与 digest 不变；任何不匹配、位置参数、缺 key、流变化或未发布的 entry 都回落到完整校验的慢路径，`_c()` 产生拷贝时不发布缓存也不保留旧 entry。
- 条件与依据：未被校验的 21 个参数没有 ABI 字段，且在 `solution.py` 中除签名、key 与部分 keepalive 之外别处不读，因此不可能影响任何计算值；这一不变式由源码在 `_HOT_KEYS` 处登记。
