# fp8_scaled_grouped_gemm

## 范围

**实现范围与入口。** 固定实现入口是 `candidate/solution.py::Model.forward`。Python 侧只做公开元数据检查、编译加载与 ABI 绑定，不含数值逻辑：拒绝 `scale_granularity_mnk != (1,128,128)` 或 `scale_major_mode != 'MN'`（ValueError），忽略 `mma_sm / backend / segment_alignment`，`out=None` 时按 `out_dtype`（缺省 bf16）新建 (m,n) 输出——冻结调用总是传入 out，该分支不进入；身份缓存未命中时，`_validate` 复核 dtype、shape、numel 与连续性；forward 提交所选引擎后返回调用者给的同一个 out 对象。设计本体在 `candidate/fp8gg_umma.cu`：一个 ABI（`fp8umma_run`）后面挂三个 kernel 实例，由 host 按 shape 派生几何择一提交；`candidate/fp8gg_bind.cpp` 是纯绑定胶水（METH_FASTCALL 加 weakref 身份 memo），`candidate/fp8gg.cu` 是非 Blackwell 回退模块。

**实际可进入与不可进入的实现。** `_Engines` 按 `torch.cuda.get_device_properties(0)` 的 cc 分派：`cc[0] == 10` 时编译并只用 `fp8gg_umma.cu`（gencode `compute_10{minor}a`），否则编译 `fp8gg.cu`。冻结环境是 NVIDIA L20D、build target `10.3a`（`performance/SELECTION.json` 的 ncu environment），即 cc = (10, 3)，所以本次实际可进入的实现只有 umma 模块的三个实例：`umma_gemm<0>`、`umma_wide<4,32768,0>`、`umma_wide<3,65536,1>`。`umma_gemm<1>` 只在诊断宏 `FP8GG_FORCE_SAREG` 构建下进入（host 策略已把 sareg 恒置 0）。`fp8gg.cu` 在冻结设备上既不编译也不进入：`fp8gg_bind.cpp` 只用 `#pragma weak` 声明 `fp8gg_run`，bind 模块的编译单元里没有它（`launch_sync` 会报 NotImplementedError），只有 umma 编译失败才落到该回退，属构建环境失败路径而非输入条件。

**host 拒绝与限制范围。** `fp8umma_run` 在 `m/n/k/G <= 0` 时直接返回 0 不提交；`n % 128 != 0 || k % 128 != 0` 返回 1001；`G > 116` 返回 1004（schedule smem 尾部 1024B 上界，Contract 的 group_count 最大 64）；smem 预算不足返回 1003；tensormap 编码失败返回 1002，其中 A 的缩小 box 编码失败时降级 `abox=0` 继续。冻结 Contract 的形状约束排除了非正尺寸、n/k 不整除和 G 过大三类返回；smem 容量、tensormap 编码和 CUDA API 仍可能失败，不能由合法形状排除。`sched_policy` 对每个 (indptr, G, m, n, k) 身份做一次 m_indptr 的 D2H 并 `cudaStreamSynchronize`，命中时只比较指针；D2H 或同步失败则退回 engine 0，并把这个结果写进同一身份缓存。CUDA graph 与两侧身份 memo 的任何失败都只降级 host 路径（永久直接提交、逐次 validate + launch），不改变设备侧工作。

**host 引擎选择属源码配置，不进 YAML。** `sched_policy` 在一次 indptr D2H 后算出 ne（非空组数）与 mtiles（各组 `ceil(rows/128)` 之和），sareg 恒为 0；在 `n % 256 == 0 && ne > 0 && nSM > 0` 前提下，engine 由六条“实测获胜类”门限的析取决定（`items256 = mtiles * (n/256)`、`kb = k/128`）：`kb >= 32 且 items256 >= 4nSM 且 mtiles >= 4ne`；或 `kb ∈ [32,48] 且 2*items256 >= 5nSM 且 mtiles >= ne`；或 `kb >= 16 且 items256 >= 8nSM 且 mtiles >= 2ne`；或 `kb ∈ [8,12] 且 items256 >= 10nSM 且 mtiles >= ne`；或 `kb >= 16 且 items256 >= 8nSM 且 mtiles == ne`；或 `kb ∈ [8,20] 且 items256 >= 4nSM 且 mtiles >= 2ne`。命中后若 `kb <= 20 且 2*mtiles >= 3*ne` 改判 engine 2。`pp = (mtiles == ne)` 供 B 的 L2 evict_first 提示，同一个值同时作为 V0 的 `Params.bstream` 与 wide 的 `ParamsW.bstream`。这些是原实现的 selector 与实测覆盖，既不写进任何 YAML，也不由节点的 `when` 承担；两份完整设计各自固定一个实例，root 的 `when` 只把选择器指向本节作为源码配置记录。`performance/ncu/result.json` 的 kernel 名直接记录了 10 个固定用例的实例归属：用例 0/1/6/7 提交 `umma_gemm<0>`，2/5 提交 `umma_wide<4,32768,0>`，3/4/8/9 提交 `umma_wide<3,65536,1>`，三个实例在冻结域内都被实际提交。`performance/ncu/0.csv` 至 `9.csv` 的 `device__attribute_multiprocessor_count` 和 `launch__sm_count` 均为 148；这给出该采样环境的实际 nSM。dual/bstream 等运行参数仍须按源码门限与固定输入推导，NCU kernel 名本身不记录它们；Design 中 grid 保留符号 `sm_count`。

**域外与降级分支。** 冻结域的五组 (n,k) 使 `kb_count ∈ {12,16,32,56}` 全为偶数，奇数 kb_count 的尾对分支（`has1 == false`：预告字节数减半、只发 kb0 的四个 UMMA、epilogue 用 `sc1 = 0` 并提前 arrive）是源码支持但域外的路径，两份设计都不承担，也不作为缺陷记录。`abox=0` 是 tensormap 编码失败时的降级取值，见“固定 128 行 A box”。跨引擎数值一致性源码有两种说法：`candidate/solution.py` 顶部称两引擎 “produce bitwise-equal outputs (A/B-verified)”，`fp8gg_umma.cu` 的 V1 合并注释称 “cross-engine outputs within <=1 bf16 ulp on eval inputs”；本目录与两份设计都不采用较强的逐位相同说法，各自只声明与参考无逐位一致保证。

**已研究但未完整展开的独立方案。** `candidate/fp8gg.cu::fp8gg_bm64` 是源码里另一套完整实现，机制与 umma 两引擎完全不同：BM=64 / BN=128 / BK=128，3 级 cp.async 环，256 线程按 2(m) × 4(n) 划分 warp，全部 warp 同时承担 `mma.sync.aligned.m16n8k32.row.col.f32.e4m3.e4m3.f32` 与 epilogue——没有 warp 专职化、没有 tmem、没有 TMA；每 128-K 块先在寄存器 fragment 内累加，再用 `a_scale[row,kb] * b_scale[e,kb,nt]` 提升进主 fp32 累加器，最后 `stmatrix` 写 smem、以 uint4 直接写全局；grid = min((ceil(m/64) + G) * n/128, 2*nSM)，`__launch_bounds__(256, 2)`。它面向非 Blackwell 目标，在冻结设备 sm_103a 上不可进入，其承担范围无法落在本任务共享 Contract 的硬件要求之内，因此本次不交付完整 YAML，也不改称参数或局部变化。若将来任务硬件改成 sm_89 一类目标，它需要作为独立完整设计另行提取。

**本次收录范围。** 三者分别说明：共同 Contract 的有效域是 P1 已冻结的输入域（五组 (n,k)、group_count ∈ {8,16,32,64}、m 为 4 的倍数且 1 ≤ m ≤ 65536）；任务要求实现的范围就是这一整个域；本目录收录 2 份完整设计——root（V0 pair-batched 引擎的具体实例 `umma_gemm<0>`）与并列的 wide（`umma_wide<4,32768,0>`）。root 的工作分解覆盖整个形状域，数值与 host 调用边界见下文；wide 另有 `n % 256 == 0` 的硬接口条件（冻结域的 n ∈ {1536, 3072, 4096, 7168} 全满足），两者范围重叠、不设隐式优先级。engine 2（w1g）与其余取值差额按局部或参数记录，见“变体与组合”。两份设计在冻结域内都被实际提交，没有为凑数保留的配置族。

## 完整设计

| 设计 | 具体机制与保留理由 | 关系 |
| --- | --- | --- |
| [root](root.yaml) | V0 pair-batched 引擎的具体实例 `umma_gemm<0>`（`fp8umma_run` 的 engine==0 提交路径）。数学区把每个 128-K 块先在精确 e4m3 上收缩成 `blk(kb)`，再用 `sc(kb) = a_scale[kb,row] * b_scale[g,kb,nt]` 一次 FFMA 提升进 `acc`，最后一次性收窄成 bf16；调度区只有一个 MAIN step，工作维度 `item` 是 (组内 128 行块, 128 列块) 的紧凑枚举，持久网格按 `min((ceil_div(m,128)+group_count)*(n/128), sm_count)` 领取；流水线区 warp0 = PRODUCER 把 K 块对搬进 3 深的 `a_ring`/`b_ring`（每 pair-stage 64 KiB，实际按 A0/B0/A1/B1 四个 16 KiB 区排列），warp1 = ISSUER 每对发 8 个 k32 UMMA 写 `acc_pair` 该对的两个 128 列块 `blk(n,0)`、`blk(n,1)`、并以一次 `tcgen05.commit`（`signal:pair_done`）同时释放 stage 与发布两个累加器，warp4–7 = EPILOGUE 以 thread == tile 行做 x16 旋转排空、逐块提升进线程局部 `row_acc`；`compute:promote` 退休全部 TMEM 读取后先 `signal:acc_free`，再由 `compute:promote_tail` 完成最后 32 列的 FFMA，整块经 `staging` 走 2 次 TMA bulk store、残块谓词直写；设备侧 `sched_table` 前缀调度，无需全局设备工作区。保留理由：host 的默认引擎与源码自身认证的基线路径（“gate-off reproduces the V0 path exactly”），接口最清楚（一个 step、一次提交、128×128 tile、单组 epilogue、每对一次 commit），且冻结用例 6 正以这套取值（abox=1、dual=0、bstream=0、sareg=0）提交 | 阅读入口，保存唯一 Contract；与 wide 并列而非父子，范围重叠、不设隐式优先级 |
| [wide](wide.yaml) | wide 引擎的具体实例 `umma_wide<4,32768,0>`（`fp8umma_run` 的 engine==1 提交路径）。调度区同样只有一个 MAIN step，工作维度 `item` 是 (组内 128 行块, 256 列块) 的紧凑枚举，`Worker_count` 为 `min((ceil_div(m,128)+group_count)*(n/256), sm_count)`，设备侧 `sched_table` 前缀调度、无需全局设备工作区；数学区把每个 128-K 块先在精确 e4m3 上收缩成 256 列的 `blk(kb)`，再用 `sc(kb,h) = a_scale[kb,row] * b_scale[g,kb,2*nt+h]`（h 为列半块）一次 FFMA 提升进 `acc`，最后一次性收窄成 bf16；流水线区 warp8 lane0 = PRODUCER，每轮把一个 128 行 A box 与一个 256 行 B box 搬进 4 深的 `a_ring`/`b_ring`（每轮一个 16KB A 槽加一个 32KB B 槽），warp9 lane0 = ISSUER，每轮先等 `stage_full` 与 `acc_free`、再发 4 个 k32 UMMA（128×256 描述符）写 `acc_pair` 槽 `n%2` 的 `blk(n)`，并以一次 `tcgen05.commit`（`signal:round_done`）同时释放 stage 与发布累加器，warp0–7 共 256 线程 = EPILOGUE 按 `grp = warp >> 2` 分成两个 128 列组，`compute:scale` 算出本轮的 `sc`、`compute:promote` 以 x16 旋转排空，全部 TMEM 读退休后由 256 线程各一次 `signal:acc_free` 释放槽，`compute:promote_tail` 再从 `drain_regs` 完成各半块最后 32 列的 FFMA，a_scale 与 b_scale 都走 `sa_regs`/`sb_regs` 的寄存器 kb-ahead 预取（没有 root 的 `sa_ring` cp.async 环）；PREPARE 的 Member 是全部 10 个 warp（320 线程），负责 `sched_table`、barrier 初态与 tmem 分配；整块写回按两个半块顺序复用同一个 32KB `staging`（`release:staging` → `store:staged_half` → `store:half_out`，每项 4 次 epilogue barrier、1–2 次 bulk 读完成等待与 2 组 store），残块走 `store:tile_direct` 谓词直写。保留理由：工作项与 B box 几何（256 行 × 128 列）、同步轮粒度为单个 128-K 块而不是 K 块对、4×48KB 环、128×256 UMMA 描述符与 2×256 列 tmem 槽、320 线程两列组 epilogue、scale 全寄存器预取、两个半块顺序复用同一 32KB 暂存都与 root 不同，commit 粒度与 epilogue 分栏都不由 “BN 取 256” 推出，三个 Design 区域都要重新贯通，不能用基线加目录差额表达；源码本身把它作为并列引擎交付并给出同类实测依据（c5 类 −7.5%），冻结用例 2、5 由它承担 | 与 root 并列而非父子，范围重叠、不设隐式优先级；Math_reshape、Work_schedule、Tile_pipeline 三区已判定全部本地定义，未使用 `from` |

## 变体与组合

以下条目按当前完整基线的真实对象定位；精确参数、`when` 与修订号以 YAML 为准，条目不修改基线，也不产生 patch 应用顺序。数值与门限均来自固定源码。

### 寄存器 a_scale 预取（局部）

- 基线：[root](root.yaml) 的 `DESIGN.Tile_pipeline::MAIN.EPILOGUE` 中 `load:a_scale` 与 `Storage.sa_ring`（2KB、depth 2、slot `j%2` 的行私有 cp.async 环），以及 `REALIZATION.Require` 中“谓词 4 字节 cp.async、每对迭代提交一个组、一组在飞等待”那条。
- 差异与联动：a_scale 改为每线程寄存器两深预取——当前对 `sa_c0/sa_c1`、下一对 `sa_n0/sa_n1`，循环内为 pair j+2 补两个 kb 值，越界行谓词置 0 且不解引用；`load:a_scale` 由异步 cp.async（async_unordered）变为同步 `__ldg` 寄存器读，`sa_ring` 连同其 `cp.async.wait_group 1`、每对末尾的补发与无条件提交一起闲置不用。这不节省 smem：布局把 sa 区固定在 `staging` 之后、barrier 尾部再 +2048，且这段在 SAREG 分支之外；host 又为 `umma_gemm<1>` 与 `umma_gemm<0>` 设置相同的 MaxDynamicSharedMemorySize 并以同一 smem 表达式提交，故 2KB 在 SAREG=1 中是预留未用，启动 smem 与 barrier 偏移对两个实例完全一致。b_scale 的一对提前寄存器 `__ldg`（`sb_regs`）两条路径相同、不变；`row_acc`、排空顺序、逐元素 FFMA 序、`signal:acc_free` 时点与写回全不变，源码称两路径逐位相同。对应实例 `umma_gemm<1>`。
- 条件与依据：host 自 V2.0/X33 起把 `Params.sareg` 恒置 0（注释：sareg0 在每个受测 V0 形状上胜或平——c6 −7.7%、d7 −7.2%、c0/d6 1.000、零实测损失），该取值只在诊断宏 `FP8GG_FORCE_SAREG` 构建中进入，冻结 10 个用例都不提交它；作为已研究取值保留，不是当前交付路径。

### kb1 双发射（局部）

- 基线：[root](root.yaml) 的 `DESIGN.Tile_pipeline::MAIN.ISSUER`（`Member: warp[1:2]`、`matmul:a_pair@b_pair`、`signal:pair_done`）、`Waiting.Released` 的 `stage_free(n) ← pair_done(n-3)` 边，以及 `REALIZATION.Require` 中“每对一次 `tcgen05.commit`”与“operand-full 与 pair-done barrier 各一次到达”两条。
- 差异与联动：warp2 lane0 成为第二个发射者（ISSUER 的 Member 扩为 `warp[1:3]`），warp1 只发 kb0 的四个 k32 步写 `blk(n,0)`、warp2 发 kb1 的四个步写 `blk(n,1)`，两者各自 `tcgen05.commit` 到同一 stage 的 `pair_done`，因此该事件的到达计数由 1 变 2，两次 commit 都落地才算该对完成；两个 warp 各自等 `stage_full` 与 `acc_free`，stage/phase 与跨项延续的 pair 序号记账不变，`acc_pair` 中 `blk(n,0)` 与 `blk(n,1)` 两个 128 列块的归属也不变（源码 tmem 偏移 `pb*2` 与 `pb*2 + 1`）。warp2 由 root 中的闲置 warp 变为专职。数学、工作分解、PRODUCER、EPILOGUE 与写回不变；实施时上述两条 Require 相应改为“每对两次 commit / 两次到达”。
- 条件与依据：host 按 `pairs_ub = wub * ceil(kb_count/2) >= 48 * grid` 置 `Params.dual`（运行期形状派生，不进 `when`）；源码称门限关闭时逐位复现 V0 路径，实测依据 c0 dual0 +3.4%。按门限与 nSM = 148 反推，冻结 engine-0 用例 0/1/7 以 dual=1 提交、用例 6 以 dual=0 提交，因此这是常发路径而非假设情形；root 固定 dual=0。

### B 载入的 L2 evict_first 提示（参数）

- 基线：并列两份完整设计——[root](root.yaml) 的 `DESIGN.Tile_pipeline::MAIN.PRODUCER` 中 `load:b_pair`，与 [wide](wide.yaml) 的 `DESIGN.Tile_pipeline::MAIN.PRODUCER` 中 `load:b_block`；host 用同一个 `pp` 分别赋 `Params.bstream` 与 `ParamsW.bstream`，两份设计都固定 bstream=0，所以下面这条差额对两个对象同时成立。
- 差异与联动：B 的 `cp.async.bulk.tensor.2d` 加 `.L2::cache_hint`，policy 由 `createpolicy.fractional.L2::evict_first.b64 1.0` 生成；A 载入（root 的 `load:a_pair`、wide 的 `load:a_block`）、`stage_full` 的预告字节数（root 的域外尾对减半，wide 每轮只有一个 128-K 块、无尾对）、写回与全部 barrier 不变，属纯缓存提示，不改变 stage 内容与完成语义。
- 条件与依据：host 的 `pp = (mtiles == ne)`，即每个非空组恰好一个 m-tile、B 只被读一次时打开；源码实测 c1 −9.7%、c7 −8.5%、d9 −2.4%，而任何 B 复用形状回退（c4 +4.4%、c8 +1.0%）。冻结 engine-0 用例中 1 与 7 恰好 mtiles == ne，故实际以 bstream=1 提交；root 固定 bstream=0。

### 固定 128 行 A box（参数）

- 基线：并列两份完整设计——[root](root.yaml) 的 `DESIGN.Tile_pipeline::MAIN.PRODUCER` 中 `load:a_pair` 与其 `REALIZATION.Require` 中“A box 高度取自匹配的 tensormap、预告字节数与实际搬运一致”那条，以及 [wide](wide.yaml) 的 `DESIGN.Tile_pipeline::MAIN.PRODUCER` 中 `load:a_block` 与其 `REALIZATION.Require` 中“A box 高度取自匹配的 tensormap、B box 为 256 行 128 列、每轮预告字节数为两者之和”那条。两侧的自适应 box 都按本块有效行数向上取整到 16/32/64/128，对应同一套 `tA/tA64/tA32/tA16` 四个预编码 tensormap，host 分别以 `Params.abox` 与 `ParamsW.abox` 传入，两份设计都固定 abox=1。
- 差异与联动：只用 128 行 box 的 tensormap（host 把四个 map 指针都指向 `tA`），root 的 `load:a_pair` 每个 k 块恒搬 128 行、每对预告字节数恒为 `2*16384 + 2*16384`（域外尾对为 `16384 + 16384`），wide 的 `load:a_block` 恒搬 128 行、每轮预告字节数恒为 `16384 + 32768`；残块时 box 以上的行改由本次载入填入（相邻组的行，或超出 m 时由 TMA 的 OOB 零填充），它们仍只喂给 EPILOGUE 的 `valid` 谓词与整块/残块写回二分所排除的行，有效输出、`staging` 与直写路径不变。
- 条件与依据：host 在三个缩小 box 的 tensormap 编码失败时置 `abox = 0` 并继续，属降级路径而非性能选择；abox 取决于本次编码结果而不是输入条件，因此不进 `when`。

### 8 warp 分栏 epilogue（局部）

- 基线：[root](root.yaml) 的 `DESIGN.Tile_pipeline::MAIN.EPILOGUE`（`Member: warp[4:8]`、`compute:promote` 的 x16 旋转排空、`signal:acc_free` 的 128 次到达、`store:staged_tile`）、`Storage.staging` 与 `Storage.row_acc`，以及 `REALIZATION.Require` 中“256 线程”与“accumulator-release barrier 128 次到达”两条。
- 差异与联动：NEPI=8 使每 worker 384 线程（12 warp），EPILOGUE 的 Member 变 `warp[4:12]` 共 256 线程，按 `grp = (warp - 4) >> 2` 分两个列组、`coloff = grp*64`，每线程 `row_acc` 的列数由 128 变 64（CTA 内逻辑总量仍是 128 行 × 128 列）；因每线程列数不再是 128，x16 旋转排空改回 x32 两深批（每次 wait 前发 2 个 x32，每个 kb 只需一批即覆盖本线程的 64 列），`signal:acc_free` 的到达计数与 `bar.sync 1` 的参与线程数由 128 变 256；`store:staged_tile` 的暂存 box 索引按 `(coloff + col) >> 6` 得出，两个列组各写一个 16KB box，issuer 仍发 2 次 TMA store 到 `nt*128` 与 `nt*128 + 64`，残块直写每线程 8 个 uint4；PREPARE 的 Member 相应扩为 `warp[0:12]`（m_indptr 拷贝与两次 rendezvous 由全部 384 线程参与）。数学、工作分解、PRODUCER/ISSUER 与 `acc_pair` 几何不变。
- 条件与依据：需要诊断宏 `FP8GG_V0_8EPI` 构建，认证配置未采用、冻结用例都不提交它；源码依据是 x7 诊断（每对排空 506–608 cyc、发射者 pe_wait 394–602 cyc），目的是缩短每对的排空跨度。

### wide 的单遍整块写回（局部）

- 基线：[wide](wide.yaml) 的 `DESIGN.Tile_pipeline::MAIN.EPILOGUE` 中 `release:staging(t,h)`、`store:staged_half(t,h)`、`store:half_out(t,h)` 与 `Storage.staging`，即整块写回按两个半块顺序复用同一个 32KB 暂存（源码 `umma_wide<4,32768,0>` 的 GSTORE == 0 分支；固定版本 `candidate/fp8gg_umma.cu` 的 1316–1347 行是基线、1348–1378 行是本变体）。
- 差异与联动：实例 `umma_wide<3,65536,1>`（engine 2，源码称 w1g）与基线是同一个 kernel 模板，模板参数 GSTAGES 4→3、GSTAGB 32768→65536、GSTORE 0→1，只改整块写回：每项一次 `cp.async.bulk.wait_group.read`（等上一项的 store 读完暂存）、一次 256 线程具名 barrier，两个列组各把自己那 128 列打包成 `q = 2*grp + (c >> 3)` 的两个象限写进 64KB `staging`，一次 `fence.proxy.async` 加一次 bar，issuer 一次发 4 个 box（`nt2*256 + {0,64,128,192}`）并 commit 一组，即每项由基线的 4 次 barrier、1–2 次读完成等待、2 组 store 变为 2 次 barrier、1 次读完成等待、1 组 store（两者的首次读等待都只在已有未决 store 时发生）。必要联动：`a_ring` 的 depth 4→3（`total_size` 65536→49152）、`b_ring` 的 depth 4→3（131072→98304）、`staging` 的 `total_size` 32768→65536、`shape` 由 `[{row:128},{col:128}]` 改为 `[{row:128},{col:256}]`、`view` 由每半块一项改为整块一项、启动 smem 230400→`3*49152 + 65536 + 1024 = 214016` 字节、`REALIZATION.Require` 中“每半块一个 bulk group、每半块一次 `cp.async.bulk.wait_group.read`”改为“每项一个、每项一次”、EPILOGUE 的 `for(h=0:2)` 三段变单段。残块谓词直写（`store:tile_direct`）、`Math_reshape`、`Work_schedule` 的 `item` 与项数 W = `s_pref[G] * n2_tiles`、320 线程与两个 128 列 epilogue 组、2×256 列 `acc_pair` 槽与 256 次 `signal:acc_free` 到达全部沿用基线，源码称只改写回、数值逐位相同（store-only）。
- 条件与依据：门限 `engine == 1 且 kb_count <= 20 且 2*mtiles >= 3*ne`；源码实测 c9 −3.3%、d2 −3.9%、d4 −3.9%、c4 −2.8%、c8 −1.8%、c3 −1.6%，流式类（mtiles ≈ ne：c7 +1.9%、d9 +2.3%）在浅环上回退，故由 `2*mtiles >= 3*ne` 排除，kb > 20 亦排除（c2 1.000、c5 1.010）；engine 2 提交失败永久回退 engine 1（`g_w1g_off`）。冻结用例 3/4/8/9 由它承担，是域内常发路径。按局部记录而不另立完整设计：它没有新的主计算、输出形成方式、工作归属或主协作组织，只围绕既有写回动作改变协议与两项容量。

## 来源与当前限制

- **来源身份。** YAML 的实现和参考入口固定到 `KernelSchema@24d2b3d3ca9d4907c4e7efd9607cf78cfb1a52b2`。`performance/SELECTION.json` 的 candidate/contract 文件摘要对应此处的固定源码。`CERTIFIED_BEST.json` 的 fixed/domain pass 是所列样本、种子与外部检查器的来源记录；metadata 的 atol=.01、rtol=.05、max_mismatch_fraction=0 没有随附完整比较器公式、相对误差基准或非有限值路由，YAML 因而保留 Source only，不套用默认比较器。性能目标是固定 shape speedup 的几何平均，NCU kernel-sum 计量排除 CPU、编译和 copy-engine DMA，不能推出首次 selector D2H 或端到端开销。
- **算术边界。** 四个 k32 `tcgen05.mma` 步以 FP32 accumulator 形成每个 128-K block；有限 e4m3 的单项数学乘积可由 FP32 精确表示，不等于已知硬件内部归约舍入或全域逐位一致。后置 scale 乘法及 FFMA 与参考先分别反量化的结合次序不同，来源没有全域误差界。当前 Contract 未给 scale 设额外上界：例如 a、b 全零且两个 scale 均为有限的 2^100 时，参考反量化仍为零，而后置 scale 产品在 FP32 溢出后与零块相乘可产生 NaN。这是现有数值路径的限制，不能靠收窄 Schema 输入域消去，也没有 GPU 实测该例。
- **片上账目。** root 的 `sb_regs` 是 128 个 epilogue 线程各持有当前/下一对的两个 scale，共 2048 B；wide 的 `sa_regs` 和 `sb_regs` 各为 256 个线程的两深预取，各 2048 B。`drain_regs` 记录每线程两批 32 个 FP32 值：root 32768 B、wide 65536 B；末批在 `acc_free` 后供 `promote_tail` 使用。`row_acc` 分别为 65536/131072 B。三者描述源码级缓冲容量，不是编译器实际分配、同时活跃寄存器数或无 spill 承诺。root 的 1 KiB 控制尾区占用 68+8(G+1) B，wide 为 84+8(G+1) B；G=64 时分别 588/604 B，均不与 ring/staging 重叠。
- **资源采样。** 原 NCU CSV 记录 root/wide/w1g 的动态 smem 为 232448/230400/214016 B，另有每 CTA 1024 B driver 预留；设备每 SM shared-memory 上限为 233472 B，样本的 shared-memory occupancy limit 为 1 CTA。该资源事实支持采样构建的一 CTA 驻留上限，不证明所有设备、构建或任意调用均成功；YAML 仍保留硬件占位。
- **host 缓存限制。** Python/C weakref memo 只比较六个张量的对象身份，不重新读取 data_ptr、shape、stride、dtype 或 device；原注释所称这些属性构造后不可改变并不是 PyTorch 对象保证。复用同一对象期间若用 `set_`/`resize_` 等改变其 storage/metadata，缓存可继续使用旧参数。当前缓存路径依赖其不变，源码缺少失效检测。`sched_policy` 也按指针和尺寸缓存由 m_indptr 内容推导的 engine/pp，不检测内容变化；device 每次仍重读 m_indptr 来枚举当前工作，因此应区分缓存选择可能陈旧与数值结果缓存。源码的设备查询、stream getter 和多个进程全局缓存固定以 device 0 为基点，不提供任意多设备切换保证。
