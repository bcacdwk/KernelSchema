接受的判断：完整执行路径分区与核心设计记录是不同职责；整区共享能减少重复定义，但不自行减少组合身份。实际结构变化值得分析，不应自动升级为新的完整算子设计。

要求后续检验的边界：

- alpha、FSCAN、REDF、ready-only 等局部改变有真实数据/协议含义，不能按字段少就省略
- 同 shape 不证明同接口；组合须保留表示、有效索引、生产者和完成边界的必要配套条件
- MoE 的验证既是计算捷径又含源码版本竞态；不能全当包装删除，也不能补造来源没有的安全保证
- 整区相等与真实共享适用性不同，扩大引用范围必须有实际样本支持

## 第二轮：研究要求的收束

主代理向两个新 MAX 代理明确：

1. 适用范围、原实现选择集合、已验证样本和最大可行域分开理解；记录范围不自动构成正确性证明
2. 局部变化只写新增决定和必要联动，不能另建必须填齐的迷你 schema
3. 完整设计的判据不能机械采用改动分区数、launch 数或固定节点上限
4. 比较引用方案时，区分减少节点、减少正文、理清来源三种收益，不以其中一个冒充另一个

主代理再次独立展开较新 MoE 的 96 份批准稿：math/schedule/pipeline 的不同内容数为 76/84/83，现有整区引用为 20/12/13。按逐字相同内容复用，扩大来源范围在这个快照中额外可省 **0 区**。FA4 两份 shared-rescale 的数学区确实相等，直接父不同；这里有跨父共享的具体价值。两项事实均支持把“共享方式”与“减少组合身份”分开讨论。

同时收窄一个案例用途：QSA 的 Contract 本身已经固定请求数和索引模式，不能用它证明现状存在“宽 Contract、窄 root Design”的分离。单份设计允许只记录 Contract 的一部分，是待讨论的规则能力，而非该 QSA 案例已经实现的事实。

下一轮要比较 `parent` 是否还有独立价值：保留主要来源字段会不会与 Markdown 中的多来源关系重复；移除它是否能让 Contract 归属、内容引用与设计来源各有清楚职责。字段名和具体方案尚未敲定。

## 第三轮：反例审阅与试写

两个新 MAX 代理分别审计候选规则和试写 MoE/FA4 目录；主代理独立阅读两份目录草稿，并要求修正以下问题：

| 问题 | 判断与处理 |
| --- | --- |
| FA4 `folded_static` 被列为第四条完整主线，但主要是已有映射与单工作生命周期的组合 | 降为组合参考；源稿确有新增 WorkCoord 发布与首次 Q/K/V 加载等待，另作局部说明，不能假称 pipeline 与 root 全等 |
| MoE `format_tables` 被列为独立局部决定，所选 packed 主干却不消费它 | 不再独立命名；必要冷准备事实归入一次 ABI/来源条件说明 |
| `serial_handoff` 要求删掉入口 griddep 协议 | 源码 helper 无条件保留，普通提交下无效；改为普通 stream 的前驱完成接续，不要求删除指令 |
| FC2 cp 回落的文字笼统排除“split” | 区分 split-K FC1 的拒绝与可配套 FC2 的回落，不能否定已有 `split_cp` 组合 |
| 推断验证需要权重内容不可变 | 两个第三轮代理独立发现当前 Contract 已限定权重 scale 有限；不新增该要求，也不把越出 Contract 的 NaN 当成合同内反例 |
| 把同 stream 或本次成功当成隔离保证 | 不成立。host mirror 没有调用代次；失败遗留的私有流访问也不会因后次成功而消失。集中保留必要来源限制，不恢复全部错误路径矩阵 |
| 任何实际实施都被要求生成完整新 schema | 收束为仅在需要完整 schema 交付时整理已选方案，避免另增普遍流程义务 |
