# 正式规则落地与独立审阅

本页记录上一轮落地。用户随后进一步明确具体配置、十份上限与提取职责，最新方案及验收见[本轮结果](../concrete_design/README.md)；以下历史审阅不作为另一套现行规范。

用户确认研究方案后，主代理亲自修改 DOC0 与相关 DOC1、3–6，并更新 CHANGELOG。提取流程、模板、工具与既有 YAML 留待后续对齐。

## 实施内容

- common 新增独立的 dispatch 部分：从源码识别设计决定、划分完整方案与局部变化、选择 root、维护来源与组合关系
- `when` 只描述当前设计承担范围；共同 Contract 不变；局部记录也以条件或已核实例界定范围
- 删除 `parent`，三个 Design 区域采用同任务同名整区 `from`；root 全部本地，内容引用图无环
- 更新当前节点的绑定、有效内容来源、修订影响与单文件阅读视图；保留完整设计中的值、工作、存储与依赖约束

## 审阅方法

## 主代理已采纳的实质补充

局部变化没有独立的 `when`，所以其定义本身必须说明适用边界。common 的局部记录段现已明确：用条件或所指的已核实例界定范围，不增加字段、小表或逐配对清单。

主代理复读了固定来源 FA4 的请求数分支与 `is_persistent` 定义。四项排序实现的范围不能套到整个基线；当前来源未采用 split+persistent 也不能被解释为一般设计禁止该组合。此补充限定的是已有记录的结论，不限制在明确条件下设计新方案。

## 没有扩充规则的判断

MoE 审阅稿最初把首用格式表初始化列成局部设计，并认为常规 packed root 需要表就绪。主代理质疑其消费关系，审阅者复核后确认 cfg97/cfg81 不读这些表，`e4m3_val` 直接算术解码；这是源码依赖判断错误，已修正演练，不为此增添通用条款。回退禁令也已明确针对被拒绝的当次 GEMM，不能误禁整条 split-K 主线配套 FC2 cp。

数值、生产者或等待发生局部变化，并不自动要求完整节点；两个审阅者对具体代表的选择可以不同，只要能按规范说清记录范围、基线和必要联动。无需规定唯一划分或硬性数量。

## 验收结论

两位审阅者均确认当前 docs 可据以开始源码分析，无剩余必改项。主代理阅读并验收两份报告，仅采纳局部记录适用范围这一项规范补充。

47 个正式 YAML 示例均可解析，相比修改前只有 common 的整区引用示例发生预期变化；DOC0–6 的 79 个本地链接有效。修改保留既有 changelog 历史，正式正文不加入研究过程或迁移兼容说明。提取流程、模板、检查器与既有算子仍未改动。
