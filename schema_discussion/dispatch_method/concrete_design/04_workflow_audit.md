# 第 2 轮：六阶段工作流审计

本报告先独立核对了第 1 轮两份研究、当前阶段页、REVIEW、作者入口和实际 Python 协议，再与[本轮规则审计](03_rule_audit.md)交换结论。依据 [BRIEF](BRIEF.md)，只写本报告与 [PLAN](PLAN.md)，没有修改正式规范、代码、状态、输入或旧 YAML，没有启动提取、运行检查器或进行 GPU 验证。

**结论是保留六个关口，修正其批准对象与回转边界。** P2 解决“已有材料中哪些机制会影响代表选择”，P4 解决“已知知识怎样落到实际基线、有限完整集合及记录计划”。P4 的计划批准不能成为未来正文的批准；P5 不获得目录编辑权；P6 负责最终全部当前设计和记录的独立验收。新方法与冻结执行协议必须分开说明。

## 1. 第 1 轮中需要改正的结论

| 原建议中的缺口 | 本轮决定 |
| --- | --- |
| P2 写“完整代表候选集合含 root 至多 10” | 发现候选可以多于 10，否则会在研究前截断。限额作用于选定的拟完整交付集合。未选中的独立机制仍可有真实的范围、价值与取舍记录。 |
| P2 把“可能另有主机制”列为继续研究条件，但没有限定疑点来源 | 只有入口、调用、数值表示、工作分配或协作线索实际支持这个疑点，才继续定向深入。不能因尚有未读代码，推定还必须发现一个设计。 |
| P4 可依赖未来节点，但没说明正式记录与计划描述的区别 | 基于真实完整 YAML 的条目可以按 common 格式审定；未来节点只列拟议身份、源码事实、预期接口和待落实位置，不虚构已有对象、链接、共享或批准。 |
| P5 发现都等到 P6 更新目录 | 记录增补或纠正可集中收尾，但若影响代表集合、其他节点的成立前提或后续派发安排，须先定点处理。自身设计问题仍由当前 P5 修正并独立审阅。 |
| 一切 from 调整都先回 P4 | P4 的共享意向不是冻结写法。仅影响本节点的完整本地化，或改用已存在已审且确实相同的整区，由当前 P5 独立审阅，汇集实际引用事实。只有产生集合、名额、未来依赖/派发或其他节点前提的改变才回 P4。 |
| dispatch 强制三个章节，无变体也写空声明 | 最终必需范围和完整设计表；有参数、局部、组合记录才出现相应章节，不制造空节。 |
| 实施任一目录变体前都要求 Planner 补完整 schema | 这是超出任务的普遍义务。明确本次选择和权限即可；只有任务要求交付该具体组合的完整 schema 时才完成相应完整表达。目录本身仍不能自动改写 YAML 或授权 Coder 改 Design。 |

以上修正不降低完整节点的审阅深度，也不增加常设审批角色。

## 2. P2 的全局认识应当是什么

P2 不需要先做一遍所有路径的 P3。它需要一个足以支持当前选择的机制概览，调查单位是给定范围内的入口族、选择轴及影响设计的接口，不是 selector 取值的笛卡尔积。

### 2.1 可停止的调查顺序

1. 从固定任务材料和 host 入口确认本次实现范围、参数归一、可实际进入的主要实现族，以及源实现拒绝或限制的范围。共同 Contract、来源实现可达范围、此次记录选择是三件不同的事。
2. 看每个有区分性线索的实现族：从输入到输出的主要值与物化、输出或归并负责者、主工作分配，以及必要的跨工作或跨调用接续。只沿能回答当前区分问题的调用深入；同名函数、同 shape 和同 launch 数均不足以归并。
3. 对源码已提示的相互作用追一个实际代表。例如两个算子部分使用了不同 Act 表示，或一个前缀改变输出生产者、状态版本、在途访问或完成关系。这些疑点必须核实；互不作用的 tile 轴和后端轴不生成配对表。
4. 给已识别的机制一个去处判断：拟完整代表、参数/局部/组合记录、已研究但本轮不完整展开、来源限制，或尚须解决的具体疑点。判断允许修订，但不能把未读机制直接写成“只是参数”。
5. 选择有实际源码实例、主要接口明确且便于比较的具体 root。root 无需最复杂、最优、最通用或充当所有其他设计的祖先；它不能是拼接多种模式的虚构 baseline。

P2 的充分性来自上述判断有证据，不来自阅读行数或“所有代码已看完”。已知材料没有提示影响选择的新机制时，可以停止；参数的每个数值、每条 host 阈值、所有 action 名称和完整缓冲细节不必提前完成。

### 2.2 必须解决与可以保留的未知

| 已有线索指向的未知 | P2 处理 |
| --- | --- |
| 另一条链可能改变主要数值路径、输出形成、工作领取或主协作；可能使现有代表丢失核心知识 | 定向追查，直到可以据实选择、归类或说明来源确实不足；不能用普通“未覆盖”通过当前选型。 |
| 某个重要源文件根本未提供，而当前 root 或已承诺记录的成立依赖它 | 阻塞受影响的判断，说明缺少什么和为何必需；继续不依赖它的工作。 |
| 已核主机制一致，剩余某个普通参数取值或实现细节未研究，不影响本次主张 | 如实限制当前记录，允许后续按需要补充；不假称全范围可用，也不阻止写 root。 |
| 已研究的另一独立设计不在当前完整交付选择中 | 保存名称、独特机制、范围与出处，以及暂不完整展开的理由；不能改称参数来躲上限。 |

这里没有“理论上可能还有设计，所以永远不能放行”的要求。超过十个发现候选也不自动要求提问：先按任务价值与重叠程度选定至多十份真实完整代表，保留未选机制的诚实记录。只有用户明确点名必须逐套完整交付的独立方案确实超过十份，才构成不能自行解决的目标冲突。

### 2.3 P2 与 P4 的独立产物

| 关口 | 必须产物 | 放行所解决的问题 | 不在本次批准中 |
| --- | --- | --- | --- |
| P2 | dispatch 草案中的实现范围、主要机制与依据、选定 root、拟完整集合及价值、已知轻量记录线索和具体未知边界；root 的身份/初步承担范围 | root 及代表选择没有依赖尚未核实的重要机制前提；拟完整集合含 root 不超过 10；没有把配置排列当设计身份 | root 的完整 Design、所有参数明细、未来非 root 的完整定义及其引用可用性 |
| P4 | 基于真实 root 的正式记录；有限完整目录计划；非 root 的具体实例、差异、预期共享与待落实位置；P3 发现的去处 | 每份完整文件有独特价值，轻量记录有据且不重复，未来写作任务明确，必要引用顺序可成立，已知知识没有无主去处 | 尚未产生的非 root 正文、未来 provider 的定义同一性，以及所有未展开组合的完整性 |

P4 必须独立读懂当前完整 root 及相关实际依赖，仍要反馈 root 的问题；它不另发一份 P3 root 批准，也不重复 P2 的全路由调查。仅当 P3 新证据动摇选型时回 P2。

## 3. P4 如何写尚未存在的基线

最终 common 格式只接受真实完整 YAML 的基线及其中已有对象。P2/P4 是过程草案，可以含明确的拟议计划；这项阶段事实不能反过来放宽最终格式。

- 已存在的完整 root 和其他当前完整设计正常链接；正式参数/局部/组合条目指向真实值、rewrite、step、role 或存储等对象。
- 未写节点用拟议 ID/文件名和“仅计划”标记，不能用可点击链接假装文件已存在。描述源码中的具体机制、拟相对哪套设计、哪些区预计本地或共享、哪些具体命名/接口需要其作者落实。
- 依赖未来基线的条目也是记录计划。已知的差异、来源与约束先保留；若暂缺的是实际对象名，明确待绑定，不能预先宣布某对象已经定义。若欠缺的其实是必要值、生产者或完成条件等语义依据，则继续研究，不能把它作为单纯命名问题递延。
- 拟共享只是有根据的写作与依赖计划，不是整区相等的证明。P5 只能引用实际存在并已独立审过的完整来源；仍须在本节点上下文验证整区同一性、绑定与接口。
- P5 将已落实对象和计划偏差交回既有工作记录。P6 用最终正文核对条目；未生成的链接、尚未绑定的对象及“将来相同”的承诺不能混入完成交付。

不新增 plan JSON 字段、组件 ID、片段地址或状态机。草案中的计划描述与最终目录分清即可，不要求另建一份永久知识表。

## 4. P5 新事实由谁处理，以及何时返回

P5 Worker 始终只改自己的完整 YAML；Reviewer 始终独立审本节点有效全文、共享 Contract 和实际内容依赖。两者可以报告新事实，但不并发写共享 dispatch，也不借一条记录修改兄弟或上游。

普通发现通过既有交接/问题记录说明：事实和来源、对应基线与对象、建议记录位置、对当前完整集合及其他节点前提/安排的影响。这里规定的是交接应包含的语义，不是新增机器字段。P4 的预期共享不是必须复刻的写法；本节点调整后仍完整成立、实际来源已存在并独立审过、引用图无环，且无需改变其他节点的前提或安排时，由当前 P5 审阅即可，实际引用和相关摘要在收尾时对齐。

| 发现 | 先处理哪里 | 更新与审阅 |
| --- | --- | --- |
| 参数、局部或组合记录增补/纠正，不影响完整集合及其他节点前提/安排 | 保留 P5 当前节点工作；转 P6 收尾 | P6 新 Reviewer 核对交接和最终文件，明确需补记录时派按需 Worker 集中更新 dispatch；再审最终全文。无需重选 root 或重开全部目录。 |
| 仅调整本节点的共享写法：完整本地化，或改用已存在已审的相同整区 | 当前 P5 | 独立审阅新的有效全文及实际来源，汇集真实引用和目录摘要变化；不为一次普通共享选择增加 P4 往返。 |
| 完整节点增删、替换、名额重分配，或需要改变其他节点的前提/安排、新增未计划的未来依赖 | 先回 P4 | 修相关集合、依赖与记录，重新核对总数和每份价值，再由节点作者完成本地改稿及独立审阅。未受影响稿件不重写；依赖新前提的工作等待解决。 |
| 有据的新主机制使代表选择失当，或 root 不能再承担原定代表作用 | 先回 P2，再按需要 P3/P4 | 重新判断相应机制与选择；不因发现另一种有价值设计就必然换 root，也不把新机制与全部旧轴相乘。 |
| 当前节点细节或自身 when 错误，仍是同一选定机制 | 当前 P3/P5 | 修本节点并独立复审，按实际变化核对依赖它的内容和目录事实。若修正已改变代表选择前提，再回 P2。 |
| 实际 provider 的本地定义本身有误 | 定义所在 P3 或 P5 | 定义作者修复并重新独立审阅；复核真实引用者及依赖该基线的记录。叙述“借鉴它”不等于内容依赖。 |
| provider 正确，但不适用于当前使用上下文 | 依上面的普通共享边界，在当前 P5 完整本地化，或改用真正相同的已存在整区 | 不能为迁就一个使用者反改 provider；不能以 dispatch 差额覆盖被引用区域。若产生其他计划影响，再回 P4。 |
| 共享 Contract 的已知事实有误 | P1 | 修唯一定义，评估全部当前设计受影响的前提并独立复审；保留未受影响正文。真实任务或来源发生改变沿既有新任务边界处理。 |

这些是目标方法的职责与影响判断，**不是当前 Runner 已实现的自动重开、失效或调度路径**。现有预算、历史、身份和权限不能被文档建议重置；未来工具对接须保留 raw、独立审阅和真实冻结身份。

## 5. P6 验收的是完整集合与记录去向

P6 使用新的 Reviewer，读全部最终完整设计的有效全文和全部正式记录。当前共用定义按实际文件读一次，每个使用上下文的范围、绑定、数值、接口、资源与必要 Realization 仍分别核对；这不是只看差异的抽查。

1. 实有完整集合、目录和当前计划一致，root 唯一且总数不超过十，每份可从共同输入贯通到全部输出。相同完整区域使用 from，共享图无环；不存在只有共享作用而无独立设计价值的额外节点。
2. 逐份核实独特价值。删除它究竟丢掉哪项主体解释；参数、局部、组合记录是否足以保存该差额。在保留关键设计信息前提下越少越好，10 为硬上限；不得为守数合并不相容的主机制。
3. 从 P2/P4 的已识别机制和 P5 新事实反查最终去处：已在完整 YAML、已在有明确基线的记录、或作为独立未展开方案/真实来源边界得到说明。这个反查是审阅工作，不要求追加永久报告或每行源码的索引。
4. 核对每条记录与实际基线一致：对象仍存在，差异范围和联动成立，原 selector、设计可用范围和实际实验范围没有混为一谈；组合不默认全配对合法，也不声称组合本身已成完整 schema。
5. 区分没有被某份 YAML 覆盖的合法输入、源实现不能覆盖的输入、目录未完整记录的实现方案。when 可重叠，root 无隐式兜底；任务原本明确要求的交付范围仍须满足。

第十一种重要设计不能靠名称转移通过：如果它需要重新贯通主输出形成、工作分配或主协作，就仍是独立设计候选；不能改称“参数”，也不能拆目录、复制 Contract、换扩展名、藏完整 YAML 于 Markdown，或把仍在交付的方案叫作历史。可以在范围中诚实记录它为何未完整展开，或替换一个价值重复的已选代表；不能宣称十份已经无损覆盖全部设计。

## 6. 普通作者规则与流程应共用什么

dispatch 格式只在 common 主定义：范围和当前完整设计表必需；变体与组合按需出现；每条用基线、差异与联动、条件与依据三个信息项，简短条目可在一句合写。提取证据怎样取得属于 P2–P5；原创设计可以使用推导及待验证判断，不伪造源码。

“当前完整 YAML 自足”不等于“每条笔记独立实现整个算子”。笔记借助明确基线表达差额，保留影响理解的数值、初始化、有效区域和完成保证即可。记录顺序不构成 patch 顺序，目录不覆盖 YAML，也不自动授权实施全部组合。

参数仍须定义，但一份 YAML 固定已选方案：具体 Bk、槽数、split 数及模式与随输入变化的块数、尾部、空工作要分开。DOC5 的 EPI=4/8 与 Hoist=0/1 配置对照应固定一个选择；必要的 if(t>0)、尾块和队列条件继续保留。DOC3/DOC4 的绑定及整数公式没有因此需要整体重写。

格式、数量与身份准入不在 EXTRACT_SCHEMA、P4、REVIEW 再各造一份；这些文件分别定义流程、阶段职责和审阅判断。普通实现与优化入口引用同一规则，不采用提取的 GPU 豁免来降低自身任务验收要求。

## 7. 实际执行器边界

只读代码已经足以确定本轮不能宣称端到端支持：

| 当前事实 | 依据 |
| --- | --- |
| P4 精确接受七字段 plan，并要求单父可达树；dispatch 开头必须逐字匹配确定性父表及固定覆盖缺口节 | [artifacts.py](../../../schema_extract/tools/artifacts.py) 的 validate_plan、index_prefix、validate_index |
| 解析与字段检查识别 parent/from_parent；引用必须指同名直接父区域 | [design_resolution.py](../../../schema_template/tools/design_resolution.py) 的 resolve_documents；[structure.py](../../../schema_template/tools/rules/structure.py) 的整区检查 |
| P5 当前按直接父批准解锁，影响集合沿 parent 扩展 | [stages.py](../../../schema_extract/tools/stages.py) 的 next_calls、affected_nodes |
| P5 产物证据包括本节点、直接父及双方来源闭包 | [receipts.py](../../../schema_extract/tools/receipts.py) 的 required_artifact_evidence |
| starter 也未同步当前全部文字语法，仍含 phase、pipe.steady 等结构 | [starter.yaml](../../../schema_template/starter.yaml)；本轮不改此文件 |

因此新增一个 [执行器对齐说明的计划位置](PLAN.md#执行器对齐入口) schema_extract/EXECUTOR_ALIGNMENT.md，集中说明目标方法、当前实现、冻结旧运行和待对接能力。它不新增运行命令或状态格式。EXTRACT_SCHEMA、Supervisor README、模板入口及仓库导航短链至它；阶段正文只写新方法；两个 tools README 保留真实旧协议并明确适用范围。

已有 tools 文档已经完整说明的回执、引用证据、直接父模板、迁移、provider 修复、合入和预算，不从阶段页再复制一遍。确实只在阶段页定义的 P1 comparisons、P4 确定性索引格式、P6 字段授权细节，迁入旧协议小节后删除“按新阶段页填写旧字段”的悬空指引。旧 run 只按其实际冻结材料解释，不能拿新阶段文字静默替换。

本轮完成标准是文字规范一致、职责明确、链接可用且边界诚实。新 from 解析、有限目录计划、按实际依赖调度和失效、记录增补的派发/证据、冻结能力与旧 run 接续，均是后续代码工作；本轮不以旧检查器通过证明新方法已实现。
