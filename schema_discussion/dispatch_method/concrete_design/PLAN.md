# 具体设计与提取方法：第 3 轮实施方案

本方案已由主代理审定并完成文档实施，第四轮两个新代理独立验收均无剩余必改项，结果见[落地记录](README.md)。依据 [BRIEF](BRIEF.md)、[第 1 轮作者规则](01_schema_rules.md)、[第 1 轮流程研究](02_extract_method.md)、[第 2 轮规则审计](03_rule_audit.md)和[第 2 轮工作流审计](04_workflow_audit.md)，已收敛最小格式、未来基线、P5 普通共享调整和实现义务；无需追加用户决定。执行器对接仍是后续工作。

本轮只修改下表中的 Markdown/README。阶段文件名、稳定导航和有效规则尽量保留；不修改 Python、检查器、starter、算子 YAML、PNG、运行状态、输入范围、归档或历史回执，不运行提取或 GPU 验证。方法文档完成与工具完成是两个不同结论。

## 已确定的决定

1. 同一算子的当前完整设计集合含 root 最多 10 份。在保留关键设计信息前提下越少越好，10 为硬上限。每份必须有独特的完整设计价值，完整性由本地定义及显式整区引用构成。
2. 一份 YAML 只描述一套具体已选方案。它保留自己的参数定义、输入引起的尺寸/工作量变化、必要的条件、循环和退出；不保存其他配置的开关、枚举或选择公式。
3. 其他配置的参数差异、有边界的局部变化与已知组合进入 dispatch。必要信息必须保留，不等于每条信息都取得完整 YAML 身份。
4. 判定局部或整体看新增机制和差异能否在明确接口处闭合，不看改了几个区域、多少行或是否数学相同。改变主输出形成、主要工作分配或主协作组织可以支持新的完整代表。
5. 相同完整 Design 区域直接 from；三区可分别采用不同来源，root 三区全本地。整个实际内容引用图无环；引用不带入来源 when、元数据或 Realization。借鉴关系在 dispatch 说明，既不产生共同设计父，也不产生运行依赖。
6. when 表示当前具体 Design 承担的输入与必要调用条件。可重叠、可留范围空白，root 没有兜底或优先级；实现范围、记录范围和共同 Contract 不混淆。
7. 发现候选可以超过十个，选定的拟完整交付集合必须不超过十个。已研究的未选独立机制诚实记在范围中，不能改称参数、拆目录、复制 Contract、另藏完整 schema 或借“历史”继续交付第十一份。
8. common 只定义面向所有作者的文件、身份、记录与共享规则；源码分析、读深、阶段顺序与提取验收属于 extract。dispatch 最小格式只有一个正式主定义。
9. 保留 P1–P6、Worker/Reviewer 分离和独立全文审阅。不增加默认的新审批角色，也不要求每条目录笔记都变成可独立实现的完整算子。
10. P5 只改自己的完整 YAML。本节点共享选择由当前 P5 独立审阅，普通记录增补/纠正交 P6 写作与审阅；改变完整集合、名额、未来依赖/派发或其他节点成立前提，才先返回相应阶段。换用已存在已审的相同整区或完整本地化，本身不构成回 P4 的理由。
11. 当前冻结 Runner/checker 的 parent/from_parent、七字段计划、直接父依赖等协议仍按实际版本记录。纯文档改动不授予新调用、回执或调度能力，也不改变既有状态、批准、预算及来源身份。
12. 本轮没有需要追加用户决定的分歧。只有实际发现用户明确要求逐套完整交付的独立方案超过十份，或真实任务/来源目标存在不能从材料推断的冲突，才提出具体问题；不预设确认步骤。

## dispatch 格式的唯一主定义

主定义放在 [schema_docs/0.common.md 的“选择条件与索引”](../../../schema_docs/0.common.md#选择条件与索引)，局部、组合及完整方案的语义继续放相邻的“局部记录与完整方案”。保留这些锚点。EXTRACT_SCHEMA、P4、REVIEW 和作者入口只链接并定义本角色怎样使用，不复制一套竞争模板。

最终文件采用以下最小结构：

- “范围”：简短说明当前收录范围与影响理解的边界；确有已研究但未完整展开的独立方案时，在这里按需说明名称、独特机制、范围/出处与取舍理由。没有缺口不强制空小节。
- “完整设计”：列全部当前完整 YAML。表格使用“设计／具体机制与保留理由／关系”三列；root 说明阅读入口和共同 Contract，独立方案可以并列。精确参数与 when 以正文为准。
- “变体与组合”：有实际内容才出现。每条以有意义的标题标明参数、局部或组合，并包含“基线／差异与联动／条件与依据”三个信息项。短条目可以合成一句，不强制额外子表或空字段。

最终每条变体都直接定位至少一个当前完整 YAML 及其已有对象；多基线可以并列，指出差异分别作用在哪里。组合可以链接原始参数/局部条目，但仍直指完整基线，不把组合层层当作派生基线，也不默认条目顺序、任意积组合或 patch 语义。源码选择条件、设计成立条件、实验覆盖范围按实际已有事实区分，不补造不存在的来源或验证。

以上是最终交付格式。P2/P4 的工作草案允许明确的拟议计划：未来文件用普通文本文件名并标“仅计划”，未来对象和共享明确待落实；不得以可点击的假文件或语气冒充现有完整定义。P6 必须用实际正文完成绑定并清理临时计划内容。common 不引入 P2/P4 特殊状态字段。

实现入口只要求任务的具体选择和权限明确。涉及 Design 改变仍由 Planner 决定，Coder 不因目录存在某条变体就能自行套用；只有任务要求交付该选定方案的完整 schema 时，才把它整理成符合上限和准入规则的完整 YAML。不要写成“每条目录笔记实施前都要新建或重写完整算子”。

下表定义目标方法。实际机器字段、可调用命令、代际和冻结行为由执行器对齐入口及 tools 文档说明，不能直接照此表宣称现有 Runner 已能派发。

| --- | --- | --- | --- |
| P1 共享 Contract，01_contract.md | root 的任务元数据与共享算法 Contract；硬件占位原样保留。建立文件不代表选定 root Design。 | 当前已完成 Contract 全文及固定 IO/reference/验收材料，外部数学、有效域、全部输出、数值与副作用完整；已知验收事实不丢，非阻塞缺口如实记录。 | 进入 P2。真实外部任务/来源变更沿既有新任务边界处理，不能用缩小 Contract 降节点数。 |

P3 完善自身 when 是把已选具体方案的真实范围写全，不授权将其他机制塞回 root 或更改共同 Contract。P2/P3 的上述方法职责与当前 Python 写权限可能不同，这正属于后续代码对接，不在旧运行中静默采用。

### P2 的调查止点

把识别方法写进 P2，保持方法紧凑：固定本次实现范围与主要入口族；按有证据的机制区别追代表到关键接口；仅对会改变值、输出归属、主要分配、完成或跨工作寿命的真实线索继续深入；判断参数、局部、组合和完整代表；再选 root。

P2 不按函数、文件、配置编号或所有 selector 路径计数。源码已提示可能改变代表选择的重要机制不能放进泛泛的“未覆盖”；普通未读细节不构成无限追索理由。机制发现可以超过十项；被选为完整交付的集合才受十份限额。P2 的草案无需另一份固定报告，临时阅读进度留既有工作记录。

涉及录图、缓存、验证/拒绝前缀时，核对实际提交及已发生的副作用，而非仅靠 host 顺序猜执行。通用提交含义链接 DOC4 的“提交身份与字段／调用边界”，源码如何判定写在 P2/P3，不恢复 common 中已删的提取步骤。

### P4 的完成标准

P4 对已存在完整基线的正式记录负责，也对未来任务是否明确负责。未来节点只缺正文命名/落实时，可给完整计划并标明待绑定位置；若实际差异、生产者或完成条件还靠猜测，应补研究，不能伪装成待命名事项。

拟共享必须区分“计划采用这个区域”与“该区域已证明相同”。P5 检查已完成来源后可以完整本地化，或选择已存在已审的真正相同整区；仅影响本节点且引用图仍合法时，由当前 P5 独立审阅并汇集实际引用事实，不必回 P4。只有改变集合/名额、需要未计划的未来来源或重排其他节点、改变其成立前提时，才回 P4 修相关计划。P4 不创建未来 YAML，不改 root 或现有节点正文，也不为当 provider 建无独立设计价值的完整文件。

### P5 发现与目录收尾的顺序

P5 提交新事实、来源、涉及基线与对象、建议落点及影响判断，使用已有交接/问题承载，不定义新的回执字段。

| 影响 | 处理顺序 |
| --- | --- |
| 补充或纠正参数、局部、组合记录，不改变完整集合或其他节点前提/安排 | P5 继续当前节点；P6 新 Reviewer 把交接与最终产物一起核对，明确补项后由 P6 按需 Worker 集中更新，再审最终内容。 |
| 仅把本节点某区完整本地化，或换为已存在已审的真正相同整区 | 当前 P5 检查实际来源、引用图与完整有效设计并独立审阅；汇集真实引用和目录摘要，在 P6 对齐，不新增 P4 往返。 |
| 增删/替换完整节点、重分配名额，或改变其他节点的前提/安排、增加未计划的未来依赖 | 先 P4 修相关目录、依赖和数量判断，再由相应 P3/P5 作者改本地完整正文及独立审阅；依赖新前提的工作等待解决，未受影响的代表不重选。 |
| 新机制推翻已选代表或 root 的代表作用 | 先 P2 重看这项识别，再按需要 P3/P4/P5；普通有价值新发现不自动触发换 root。 |
| 共享定义错误，或 Contract 错误 | 回真正的定义位置修复，复核实际受影响者及记录；不沿虚构 parent 树重做无关稿件。 |

P6 完成前，每项已交接的重要新事实必须已有去处或有据说明为何不进入当前交付；不能因为 P5 没有 dispatch 写权限而丢失。该去处核对不要求新增永久台账。旧稿保留与旧批准仍然适用是两件事，最终审阅覆盖当前真实内容。

- 共享 Contract 不为实现限制、名额或某个候选改写。外部验收器缺失按已有来源记录边界处理；已提供的基准、阈值、输出与副作用不能丢。必须靠猜测的设计事实阻塞具体受影响范围，已知事实写错则退修。

## 实施顺序与检查方法

### 文字与链接检查

1. 对本轮文件执行 diff 阅读及 git diff --check，核对只有 Markdown/README 改动；对照本轮开始快照区分既有修改，禁止重置或格式化无关文件。
2. 用 rg 定向检查旧术语：from_parent、直接父、parent、互斥、完整契约域覆盖、七字段、路径树、所有路径、参数化、Hoist、EPI。逐个判断语境：工具实际协议和历史示例说明可以保留；新作者/阶段方法不得继续用它们施加旧义务。不可机械全局替换。
3. 检查变更 Markdown 的相对文件链接与小节锚点。保留 common 的派生节点与 dispatch、参数变化与结构变化、选择条件与索引、局部记录与完整方案、Design 整区引用等现有锚点；保留 P3 节点逐段方法及第 4–7 段、P1 硬件占位、模板操作节和 REVIEW 的主要锚点。
4. 修掉阶段/REVIEW 指向已不存在 common“plan 与计算执行实例”的链接；通用提交规则转 DOC4 实际锚点，提取特有的源码识别转 P2。文件名不用跟随标题改名。
5. 核对 dispatch 格式只在 common 正式定义，其他新方法页没有自造表头、必填空节、JSON 字段或组件 ID。工具页中的旧格式必须有清楚适用范围。
6. 核对执行器对齐页在根导航、提取总览/手册、模板检查入口和两个工具页均可到达；没有“新语法已经支持”“新阶段已自动派发”“旧实例已合规”的无证据声明。
