# 第 1 轮：具体设计、变体目录与作者规则

## 明确推荐

推荐采用“每算子至多 10 份具体完整设计 + 一个规范化 dispatch.md”，含 root，目标始终是足够表达时更少。**必要设计信息必须保留，不等于每项必要信息都要取得完整 YAML 身份。** 一份 YAML 固定当前选定的配置与机制，保留该机制随输入变化的实例数量、尺寸和必要控制；其他配置的参数变化、局部协议与组合统一在 Markdown 登记。

完整设计的准入采用可复核的“主体与局部闭合”判断，不按区域数、代码量或泛称“重要”裁决。数学不变而主调度、主循环协作不同，同样可成为完整设计。确有十份以上独立方案时，必须选择当前任务要完整交付的方案，并明示其余方案未完整展开；不能伪装成参数、拆目录或伪造不同 Contract 来回避取舍。

保留现有 `when` 的范围语义及整区 `from`，取消作者入口中的 `parent/from_parent` 和互斥穷举要求。不增加字段、局部 patch 语言或可执行的 Markdown 配置系统。**没有必须追加询问用户的决定。** 用户已授权上述取舍；具体选哪些代表由任务目标、已有证据和独立审阅决定。本报告只提出规则与试写，未改正式规范、源码、检查器、运行状态或实例，也未重新批准历史设计。

## 1. 可直接采用的规范草案

### 1.1 完整设计的身份

每个完整 YAML 表达在其声明范围内，从共同 Contract 输入到全部输出的一套具体设计。完整性由本地内容和显式整区引用共同形成；不能依靠“再应用 dispatch.md 的若干条目”补全。

判定差异时先回答两个不同的问题：

1. **该信息是否必须记录？** 删除它会否误解实际求值、精度、数据与状态归属、性能代价，或必要的就绪、复用、完成保证？会误解就必须保留，不能以“局部优化”删掉。
2. **它是否需要完整设计身份？** 对照最近的已有完整设计，能否指明已有对象及接口，用若干独立的差异说明全部联动，并在这些接口之外继续采用基线的主体组织？能做到时，优先在 dispatch.md 记录。若必须重新贯通解释主计算、主工作分配或主协作机制，才作为另一份完整设计候选。

“局部”由差异的边界决定：

- 指明入口、出口和涉及的已有值、step、role、存储或事件。
- 说明改变的定义、必要联动及其正确性条件；差异传播到边界后，既有后继能继续使用明示的值与保证。
- 不要求变更只出现在一个区。相反，把整条主流水线写成“替换 tile_pipeline”也不构成局部说明。
- “其余相同”须能核对，不能由同名、同 shape、同数学式或源码函数名推定。

以下变化可以成为完整设计的正面理由：改变输出形成或主要中间量路径；改变主状态递推或归属；改变主工作分配、领取与退出；改变主循环生产者、消费者和资源生命周期的组织。须说明**哪项原有主体解释已不够，以及新机制如何成立、有何收益与代价**，而不是只报出 static、persistent、WS 等名称。

这不是能机械计算的最小设计数定理。审阅的可复核依据是上述对照、边界和新增机制；不得以“我觉得很重要”“改了两区”“超过几行”替代。符合准入只是有理由保留的候选，还要按当前任务和十份上限选择。

### 1.2 当前设计的参数与其他配置

YAML 应固定本份方案已选择的分块、并行组成、缓冲深度、数值策略和协议模式。需要多处引用时仍使用现有参数、公式、`ref:` 与 `bind:`；不把参数消除成重复常量。

| 内容 | 放置 |
| --- | --- |
| 当前选择，例如 Bk=128、四槽输入环、EPI=4 | YAML 中决定该值的原有字段 |
| 给定上述选择后，由输入确定的块数、索引、有效长度、容量及工作实例 | YAML 的公式、shape、工作分解或索引 |
| 同一已选机制的尾块、空工作、递推分情形、掩码、就绪状态与必要协议条件 | 对应数学或 pipe 中的现有条件与循环 |
| Bk=64/128、三槽/四槽、EPI=4/8 等其他配置及它们的联动 | dispatch.md 参数条目 |
| joint/dual loader、是否启用 scale hoist、可选合并方式等机制选择 | dispatch.md 局部/组合条目，或经准入选择另一份完整设计 |
| 原 selector 的 shape 阈值、调优预算和配置选择公式 | dispatch.md 中一次说明其有用含义并固定来源；不作为 YAML 配置选路 |

**判断依据是该表达式在做什么，不是有没有 if、min、ceil_div，也不是在运行时还是编译时求值。** 已选 tile 下的 `ceil_div(L,Bk)` 是工作量；根据长度、并行预算和 scratch 上限再挑一个 split 数，属于配置选择。把多选一从 if 改写成 min/max、查表或文字公式，不改变它的性质。

这条规则也不要求冻结整个 workload。已选 persistent 方案用固定规则产生当前 worktile 序列，或者将 worker 数约束为现有工作数与已选驻留上限的较小值，仍是该方案的实例化。输入张量、Contract 参数、实际队列结果和已声明的协议状态可以动态变化。

真正选定的自适应算法或协作机制可以保留自身的条件：例如从当前数据计算 Clean 后清零或执行其既定计算链，或队列为空时发布终止描述符。必须定义判断值的产生、可见性和全部后果；不能把“从几个现成配置中选一个”的外部 selector 改名为自适应机制后塞回 YAML。

### 1.3 dispatch.md 的最小格式

每个任务都维护一个中文 dispatch.md。必需三个部分：范围、完整设计、变体与组合。没有变体时写明“当前未记录其他变体”即可，不制造条目。来源可使用文末链接避免重复长路径。

~~~markdown
# <任务名称>

## 范围

说明当前保留什么，以及主要未完整记录的范围。
完整 YAML 的适用条件和当前配置以文件正文为准。

## 完整设计

| 设计 | 本份具体机制与保留理由 | 与已有设计的关系 |
| --- | --- | --- |
| [root](root.yaml) | ... | 阅读入口，保存共同 Contract |
| [other](other.yaml) | ... | 独立方案，或说明借鉴的设计及差异 |

## 变体与组合

### <有意义的名称>（参数 / 局部 / 组合，选其一）

- 基线：链接完整 YAML，并以已有符号、rewrite 名称、step、role 等定位。
- 差异与联动：相对基线的变化、理由，以及所有必要的配套变化。
- 条件与依据：本项适用范围；已有实现用固定来源，原创设计用推导与待验证判断。
~~~

最少规则：

1. 完整设计表列出全部当前 YAML；不要求派生树。一个设计可以借鉴多个来源，独立设计直接并列。精确配置、`when`、版本和全文定义仍以 YAML 为准，目录只给辨识所需的摘要。
2. 参数、局部、组合条目统一使用上面三项。参数条目可在“差异与联动”中用短表列同一轴的若干值及关系；不为每个数值新建标题或全文。
3. 基线最终定位到一个或多个完整 YAML。标题与普通 Markdown 锚点供人引用，不新增组件 ID、版本、patch 地址或继承规则。不要以行号、列表序号或“上一条”作为改变的对象；源码证据可使用固定版本行链接。
4. “差异与联动”须保留新增数值路径、生产者、有效区域、初始化、就绪与资源退休等实际影响。已有定义直接链接，不重抄基线。只有参数名或“相同但更快”不构成条目。
5. “条件与依据”区分本项成立条件、原实现何时选择它、实验实际覆盖什么。三种事实有几种就写几种，不要求补造其余；原创方案可以只有推导依据及尚待验证的部分。
6. 同一变体轴只定义一次，并列明已知适用的基线或接口。多个轴可组合时，用一条组合关系说明适用集合和共同条件；只有组合产生新的限制或联动，才追加相应内容。不得默认笛卡尔积合法，也不逐配对列全套文字。
7. 条目排列没有应用顺序，Markdown 不修改 YAML。完整设计的 `when`、字段定义或审阅身份不会因一个条目自动改变。“来源存在这种组合”也不等于已交付、已审阅或已验证该组合的完整 schema。

可另加一个很短的“未完整展开”小节，登记确实独立而本轮未选中的方案。它不是第四种伪装的局部变体，见上限规则。

### 1.4 when 与目录的分工

保留现有 `meta_data.dispatch.when`：说明**当前这份具体 Design** 承担的输入和必要调用条件，可取已有依据支持的保守子域。它不选择 YAML 内部的备选配置，不重演源码 selector，也不自动声称最优或已验证。

多个完整设计的范围可以重叠，也可以没有覆盖全部 Contract。root 不隐含兜底，目录顺序不产生优先级；任务确实要求完整实现整个有效域时，仍须交代未覆盖部分如何完成，不能把记录压缩当作解除任务要求。

dispatch.md 负责设计目录、其他配置的差异条件、原实现选择依据和已知组合。引用 YAML 的 when，不复制一份长条件另行维护。变体若改变基线的容量或适用范围，须在条目中说明新的条件及其依据；不能宣称基线 YAML 的 when 已随之扩大，也不能机械继承基线原 selector 条件。

### 1.5 from 的同一性与边界

完整设计选定以后，再决定如何共用正文。某一区域的完整定义可以原样承担使用节点的该区时，直接写 `{from: <设计ID>}`，不复制共同正文。检查的是全部规范内容与使用上下文，不只检查数学结果或字段外形。

- 来源区的固定值、值含义、精度、物化、工作/角色、有效区域、事件与生命周期保证全部被使用节点接受。
- 仅已显式交给外区的 `bind:/ref:` 在使用节点环境中解析；绑定对象的语义和接口必须吻合。相同公式引用使用节点的 Bk 是允许的，不因此要求 provider 和使用者的外部 Bk 取值相同。
- 区域内已经固定的 Bk、槽数或协议不能在目录里覆写。也不为共享而新造未定配置参数、选路开关或宽泛约束，消除“具体方案”。
- 任何本区规范定义确需不同，就不能引用该区后声称另改一行。要完整交付已选方案时，该区落为完整本地定义；未变的其他整区仍直接 from。

“避免微调复制整区”的第一手段是**不为微调另建完整 YAML**，而把其他取值记入 dispatch.md。若本次实际选择了该微调作为当前设计，修订原节点；只在已决定保留另一完整设计时接受必要的不同区域正文。整区引用的粒度确有复制代价，本轮明确接受这个代价，不引入片段 patch 来掩盖。

沿用同任务目录、三个区域分别选来源、root 全本地、跨区整体引用图无环的规则。来源的元数据、when、版本与 realization 不随 from 进入使用节点。三区引用同一套现有决定本身不产生新设计身份；不允许只为当 provider 新建没有独立设计价值的完整节点。

### 1.6 十份上限与设计演进

十份是当前同一算子/任务的完整设计上限，含 root，不是推荐数量。仅换扩展名、子目录、根名、重复 Contract、独立导出或把完整 YAML 放入 Markdown 附件，都不能产生额外名额。历史版本与同一设计的阅读视图不作为新的在用设计；不得借“历史”名义继续向使用者交付第十一份当前方案。

初筛超过十份时：

1. 先核实是否混入配置枚举、局部变化、已有决定组合、恢复历史及相同内容。它们按规则移到目录；有价值的差异和调用保证继续保留。
2. 对剩余候选逐一给出最近基线、不能局部闭合的主体变化和当前任务需要。数学相同不是排除理由；冷门也不自动无价值。
3. 选择当前要实现、比较或沉淀的关键方案，优先留下不能由已选方案及局部记录说明的重要机制。证据是否充分、当前任务是否需要、与已选方案是否重复，均可构成取舍依据；不根据文件易写程度凑到十份。
4. 仍有独立方案不能入选时，在 dispatch.md “未完整展开”列出名称、独特机制、已知范围与出处，以及为何本轮暂不完整化。没有合适基线就写“独立方案”，不能硬改称局部变体。记录已核事实和缺口，不宣称无损或全组合覆盖。

同一设计的发展在原 ID 上修订，参数选择的旧值与理由可进入目录，历史正文由版本管理保存。新机制需要并存时才竞争一个完整节点；也允许在同一 workload 上并列比较根本不同的方案，不限定“必须不同 workload 才能并存”。

当前任务转向新方案时，可以替换旧代表，而非只增不减。替换前检查全部实际 from 使用者：它们仍需旧定义时先迁移到保留的真实完整设计，或将所需区域落为本地；不得悄悄让来源变化改写其他设计。更新目录、范围、出处与旧实验的适用性。root 始终保存共同 Contract 和一份真实 Design；换 root 内容不改变共同 Contract，也不产生假祖先要求。

确需实现某个目录变体时，Planner 先选定配置并落实为当前完整设计，再交 Coder；通常是修订现有设计，确有独立价值和并存必要才增加文件。目录不授权 Coder 自动套用差异，也不自动把所有记载组合变成待实现目标。

## 2. 两个真实的参数/控制边界

### 2.1 FA4：选 split 数与执行一个 split 是两件事

当前 [prefill split 稿](../../../schema_template/examples/fa4_prefill/splitkv_dual_load.yaml) 在 work_schedule 中用

~~~text
Ssplit=min(floor(G/C),floor(Kblocks/2),
           floor(24000000/(TotalQ*Hq*D*4)),64)
~~~

选择 split 数。这是并行度、每 split 工作量与 workspace 预算之间的配置选择。新规范应先选一个实际取值，例如一个有源实例支持的 Ssplit，作为该完整 split+combine 设计的当前配置；原选择公式与已知其他取值进入参数条目。这里没有宣布任意取值都可行，也未替现有稿指定一个未经核对的新值。

固定该选择以后，下列关系仍须在 YAML：

~~~text
span=ceil(ceil(L(b)/Bk)/Ssplit)
lo=s*span
hi=min((s+1)*span,ceil(L(b)/Bk),Nfull)
N=max(0,hi-lo)
sigma(i)=lo+i
~~~

它们决定当前请求和 split 的实际工作。N=0 时只产生空 split 的 LSE，不执行 operand traffic 和不应存在的等待；这属于所选算法的空工作路径，不能移走后留下错误的无条件读取。online softmax 的 keep、safe、alpha 分情形与 causal mask 也继续留在数学正文。对应源稿有旧 repeat 写法，不以其历史语法作为当前规范模板。

[decode cluster 稿](../../../schema_template/examples/fa4_decode/q4_cluster.yaml) 给出第二个同类佐证：SplitCount 根据 L、B 和预算 96 在 4/8/16 等配置间选择，属于目录；已选 SplitCount 后的条带索引、N_r 和空成员参与统计交换，属于当前完整方案。不能因二者都可写成整数公式，就统一保留或统一删除。

### 2.2 MoE：选 TSTORE 配置后仍需要完整块/尾块分支

[实际 FC2 源码](../../../kernel_wiki/aka-cuda-operators-20261030/operators/moe/nvfp4_fused_moe/candidate/nvfp4_moe.cu) 的 f4_body_ws 模板与静态断言（4210–4240 行）表明：TSTORE 是配置选择，限定 GEMM2、BN=128、EPI=4、非 PP。EPI=8 的其他配置不能塞进该 YAML 的同一套角色范围；TSTORE 关闭的写回方式作为局部变体说明。

**但已选 TSTORE=true 的具体方案本身必须保留** 5210–5254 行的运行条件：当前 warp 的完整 32 行 quadrant 才能 bulk store；尾块只对有效 route 作 masked STG，否则会覆盖下一专家的输出。此处 rows_valid 来自当前工作，选择是该写回协议的必要边界行为。

同样必须保留 source-read 完成与 global-write 完成的区别：wait_group.read 允许复用共享源缓冲，最终 wait_group 0 才保证 finalize 所需的输出完成。调参变化进入 MD 不会取消真实条件动作、for 循环、完成事件和复用保证。

这是只读源码结论，不是 GPU 故障复现或所有配置可达性证明。

## 3. FA4 dispatch.md 短试写

以下演示目标格式，**不是当前 11 份实例已完成精简的声明**。三个完整设计只展示合理的起点；实际选定参数、when 和完整正文仍要分别落实。尤其不把 11→3 说成已证明的最小数或同等覆盖。

~~~markdown
# FA4 prefill

## 范围

记录 FP8 paged causal attention 的主要设计与已知变体。
本目录保留 static、folded persistent、split+combine 三份具体代表。
完整 YAML 的当前参数和适用条件以其正文为准；其他配置仅在下面登记。

## 完整设计

| 设计 | 本份具体机制与保留理由 | 与已有设计的关系 |
| --- | --- | --- |
| [root](root.yaml) | 矩形 static 工作网格、双加载、lagged-max online attention | 保存共同 Contract |
| [packed_persistent](packed_persistent.yaml) | 请求 query 工作折叠，worker 接续多份工作并维护跨工作资源寿命 | math_reshape 整区与 root 相同，直接 from；调度与流水线本地 |
| [splitkv_dual_load](splitkv_dual_load.yaml) | KV 分段产生 FP32 partial/LSE，再独立 combine | 新的部分结果与输出形成路径 |

## 变体与组合

### split 数与 combine 容量（参数）

- 基线：[splitkv_dual_load](splitkv_dual_load.yaml) 的 Ssplit、span 与 combine。
- 差异与联动：其他 Ssplit 取值仍采用同一 partial/LSE 接口；同时重算分段边界、workspace 和 combine 容量。源实现取 Smax=32（Ssplit≤32）或 64，不能只改分段提交数量。
- 条件与依据：各取值受至少两个 split、每段工作量和 workspace 约束；来源的预算选择公式只在本条定位一次，见[固定源实现][source]。当前 YAML 只保留其选定值。

### 请求按 KV 长度排序（局部）

- 基线：[packed_persistent](packed_persistent.yaml) 的请求映射；也适用于源实现已记录的 folded static 变体。
- 差异与联动：按 L(b) 降序建立 request-id/prefix 映射，并保持每项回到原请求的索引；CTA 内发布后相关 role 才使用。源 compare-swap 相等时不能假定稳定。
- 条件与依据：这里只记录来源中相应小 batch 排序实现，不把固定比较网络推广到任意 batch。实际映射和已知入口见[固定源实现][source]。

### 共享 alpha（局部）

- 基线：[root](root.yaml) 与 [packed_persistent](packed_persistent.yaml) 的 Stats、Softmax 和 Correction。
- 差异与联动：Stats 从两列 old maximum/base 改为一列 FP32 alpha，由 Softmax 计算并供自身分母更新及 Correction 复用。Stats 复用仍等 Correction capture，Y rescale 仍等前一 PV 完成；首块保留原确认关系。收益是少一次 alpha 重算与一列交接。
- 条件与依据：已知来源是 B=4、TotalQ=16384 的两种小 batch 调度；见[alpha 生产][alpha]与[alpha 消费][consume]，未声称已适用于 split 或 joint loader。

### 排序与共享 alpha（组合）

- 基线：[packed_persistent](packed_persistent.yaml) 及其已记录的 folded static 变体，同时采用“请求按 KV 长度排序”与“共享 alpha”两项。
- 差异与联动：排序改变工作访问顺序，共享 alpha 改变每份工作的 Stats 通路；保留 RequestMap 发布、每工作状态重置和各自资源协议。
- 条件与依据：源实现分别有 small_static_shared_rescale 与 small_persistent_shared_rescale 实例。两项各定义一次，不再为两种调度重写 alpha，也不推导其他轴可任意组合。
~~~

## 5. common、extract 与普通作者入口的职责

### 5.1 从 common 移出的具体内容

当前 common 110 行的：

> 分析既有实现时，先确认共同 Contract 与本次保留的实现范围，再沿输入到输出比较各路径的数学求值、物化、工作归属和协作协议。先归纳整体方案与共享的局部决定，再选择 root 和需要完整记录的设计……

这是**源码提取的方法与先后顺序**，移到 EXTRACT_SCHEMA / 阶段入口。common 改写为本报告的通用身份判据，不出现“先读哪些源码、如何枚举调用分支、哪个阶段锁分组”等步骤。

以下原则继续属于 common，不应随提取步骤一起移走：

- 代码文件、函数、配置编号与设计数量没有对应关系。
- 参数/局部/组合与完整设计的记录深度、上限、格式及范围职责。
- 当前方案完整闭合；已发生的副作用和在途访问不能被记录形式抹去。
- 来源证据不能证明硬件必需、数值独立、最优或未获得的保证。
- 不补造等待、隔离、版本和有效域；共享接口、from 绑定与变更传播需要审阅。

common 中对准备/错误前缀的具体提取口吻可收成“记录差异不省略受影响的初态、副作用、完成和生命周期条件”；如何跟踪已提交前缀、源码回落、缓存及 selector，放 extract。原则留 common，提取操作不留。
