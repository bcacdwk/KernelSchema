# 提取方法：先识别机制，再完成少量具体设计

本稿只研究提取职责与文档分工，依据本轮 [BRIEF](BRIEF.md)。不改正式规范、Python、运行状态或既有 YAML，不启动提取。下述阶段为建议的方法规范，当前执行器的差异单列在文末；保留 P1–P6 的名称不表示现有工具已经支持这些职责。

**推荐保留六个关口，但重新划清 P2、P4、P5 的对象。** P2 在写 root Design 前识别主要机制、确定代表集合；P3 写一套具体 root；P4 把已识别的知识整理为至多 10 份完整设计的目录，以及参数、局部与组合记录；P5 只完成目录中的其他完整代表；P6 审完整设计与记录是否忠实、充分、无重复。六个关口分别解决任务、识别、具体基线、记录计划、其他代表、交付六种不同问题。

减少数量不能依靠把配置选择藏回 YAML。完整 YAML 表达一套闭合设计；同规则配置差异进入 `dispatch.md`，root 仍定义自身参数及随输入变化的尺寸、索引、边界和工作量。`from` 只复用相同整区；它既不决定哪份设计值得存在，也不代替组合接口的审阅。

## 1. 现行六阶段中的职责冲突

以下引用的是本轮开始时的正式阶段文字。当前 common 已有非树目录、`from` 与允许范围重叠的修改，因此现状本身存在规则与阶段页、工具之间的不一致，不能笼统称它们为一套已经工作的“新流程”。

| 位置与当前条款 | 对新目标的影响 | 应改变的职责 |
| --- | --- | --- |
| [P1](../../../schema_extract/phases/01_contract.md) 建立 `root.yaml`，但“此时不展开各路径的 Design”，代表路径留 P2 | **创建 root 文件本身不是过早选设计。** 文件先承载共享 Contract 是合理的；问题在于后续选择前掌握什么 | 保留 Contract 先行。明确 P1 不批准 root 的 Design 方向，也不默认共同入口就是最后选中的具体方案 |
| [P2](../../../schema_extract/phases/02_dispatch_draft.md) 第 1 步“在共享 Contract 的完整有效域内列出真实 host 路径及选择依据”；第 2 步选“较通用且便于派生的 root” | 识别单位仍是完整路由；“只深入到足以区分设计”没有具体止点，容易只看 host 就选 root，或为确定 root 先展开全部路由。“便于派生”还把 root 与强制共同设计祖先绑定 | 先按机制、输入输出与接口比较代表，说明何时足以选 root；扫描选择轴，不枚举轴的全部配对。root 以实际、清楚、有代表性为准 |
| P2 先核实提交、物化、生产者、完成关系；[P4](../../../schema_extract/phases/04_dispatch_plan.md) 又“据真实 root 设计和 host 路由重审分组”，并说“树和节点数由固定源码决定” | P2/P4 都承担全路由分组；前者计划不够实，后者再做一次识别。实际差异被自然推成完整节点差异 | P2 决定“有什么值得保留”；P4 决定“已知知识准确落在哪份完整设计或哪条记录”。P4 只补有新证据的识别，不重做 selector 全图 |
| P4 第 1 步允许“真实设计、实现或选择差异”支持并存路径，要求每项直接父、相对父差异；第 3–4 步把目录固定投影成七字段计划 | 缓存状态、初始化前缀、配置阈值等即使不产生独特完整设计，也可能获得计划身份；树形复用把多来源设计迫成一父 | 完整文件只由独立设计价值支持。设计出处、局部组合与实际内容引用分别说明，不以 parent 组织设计目录 |
| [P5](../../../schema_extract/phases/05_branch.md) 每个计划项独立创作、贯通、审阅；首次从直接父建立三区引用 | 若 P4 已列出组合，每个组合即成为完整交付单位；整区共享只减少一部分正文，不消除这些单位 | P5 只接至多 9 个非 root 完整代表。不同来源不必有共同设计父；只在相同整区使用 `from` |
| [P6](../../../schema_extract/phases/06_final.md) 第 2 项要求检查 `when`“互斥与完整契约域覆盖” | 把算子来源的路由覆盖继续等同于完整 YAML 覆盖；会否决有意保留少量代表的目录 | 检查每份设计自身的范围和局部记录的适用条件。范围允许重叠、允许未收录范围，最终不证明原 selector 被完整复刻 |
| [REVIEW](../../../schema_extract/REVIEW.md) 对每个变化提交/成员/物化/事件的条件展开；差异只在“参数化或拆完整节点”之间判断 | 独立审阅有价值，但审阅对象缺少“已在 dispatch 充分记录”的第三种结果；读懂完整 root 仍不能替代记录审阅 | 保留四项文档判断、独立角色和对当前有效内容及依赖上下文的理解；增加记录相对基线的完整性审阅。P4 从当前完整 root 建立理解，批准对象是目录与计划，不另做一次 P3 root 批准 |

**不能由这些条款推出“历史 root 都选错了”。** 已有复盘主要证明首审遗漏了边界、来源限制或数值验收事实，不是对 root 代表选择质量的对照实验。这里修的是选择前的识别方法和交付单位，不承诺靠前期扫描消灭所有后续发现。

### 少量真实例子及其限度

- **MoE 的重复完整身份有直接内容证据。** `no_scan_fused_small_flat` 相对 `fused_small_flat` 的三个有效 Design 区域全部相等，新增的是 ABI 重建、workspace 初态及服务寿命等条件；这些知识不能丢，但不应因此再交一份完整算子。初始 60 中有 10 种 FC1 × 5 种 FC2 的 50 个命名配对；后续 154 则大量来自默认主干与调用前缀的组合，两个范围不同。见 [MoE 证据第 2、3、6 节](../01_moe_evidence.md)。这说明改为默认范围或增加整区引用，都不足以单独解决组合数。
- **FMHA 的 43 项计划不等于 43 个已证明不可约的设计。** 其中 D128 的 24 项来自三种 scan × 两种搬运 × 两种部分和写回 × 两种归并。segmented 增加 segmax 物化、FSCAN 改统计与归并接口，这些事实值得保留；不能据乘积就认定每个配对都要一份完整 YAML。见 [BRANCH_DERIVATION 第 3 节](../../../schema_extract/archive/six-operators/20261109-methodology-review/BRANCH_DERIVATION.md)。
- **也确有应当完整保留的组合。** Sparse `probe_hidden_mma` 同时决定 packed 前缀与 MMA 余段的输出区间、side probe、观察后的余段提交及 caller join；两个原方案的链接不能交代新的输出归属和接续。MoE REDF 同时改变 BF16 舍入后的权重乘法、Acc32 归并、旁流清零/join 和 finalize，不能降成“FC2 微调”。见 [组合试写的 Sparse 反例](../06_case_trials.md#强耦合反例sparse-hidden_mma) 与 [MoE 第 5 节](../01_moe_evidence.md)。
- **后期修 root 有独立根因。** MLA 在 P4 发现首轮 reuse 边界错误，GEMM 在 P6 补 root 的 TMEM 来源限制，FMHA 在 P5 发现 P1 遗漏比较基准。它们分别是设计边界、来源限制、共享验收事实问题，不由节点数直接导致。见 [ROOT_ANALYSIS](../../../schema_extract/archive/six-operators/20261109-usage-review/ROOT_ANALYSIS.md) 及 [分支复盘第 4 节](../../../schema_extract/archive/six-operators/20261109-methodology-review/BRANCH_DERIVATION.md)。

方法决定完整交付单位；执行器的祖先失效传播、旧稿是否保留、失败续跑、证据回执拒收和长会话读写，是另外的成本来源。本轮不重算历史费用，不把历史全部回修费用当成可删除开销，也不承诺“节点减少几成，费用就减少几成”。

## 2. 六关口与更简方案的比较

可行的四阶段替代是：A 任务与机制识别，合并 P1/P2；B root 与目录，合并 P3/P4；C 其他完整代表；D 全目录终审。Worker/Reviewer 独立关系保持，每阶段内部仍须先解决前提再写后续内容。

| 取舍 | 调整后的六关口 | 四阶段替代 |
| --- | --- | --- |
| root 前识别 | P1 已审 Contract，P2 独立检验机制与代表选择；进入 Design 前有明确止点 | A 可完成相同识别，但 Contract 错误与选型错误到同一大产物审阅时才一起反馈 |
| root 与记录的关系 | P3 先给出可引用的真实基线，P4 用真实名称、接口、边界整理差异 | B 作者同时写 root 与差异，少一次交接；复杂 root 反复变化时记录容易跟着漂移 |
| 避免重复 | P4 从当前完整 root 理解目录/记录，重点核对差额与接口，不重新展开 selector 全图或全路由分组 | 自然少两个外部关口，但不能省掉阶段内部的同样判断 |
| 有难度的既有实现 | 能分别退回 Contract、识别、具体设计或目录，不把小发现都变为整阶段重做 | 范围较大；要有相同的局部返修边界，否则容易把合并阶段整体重开 |
| 简单单设计 | P2 与 P4 可各为一段短结论；P5 跳过，不为阶段凑目录或记录 | 更紧凑，适用于来源与设计均已非常清楚的手工任务 |

**本轮推荐六关口。** 理由是既有实现的两种未知需要分别消除：写 root 前不知道主要设计机制，写完 root 前还不知道可可靠引用的具体基线。P2 和 P4 分别对这两者负责，便可保留一次早期选型检查和一次具体记录检查，且不会再重复全路由划分。四阶段可作为以后已有质量证据时的简化方案；不需要为了“阶段少”把现在最需要加强的前期识别藏回大写作阶段。

这不是建议六个固定篇幅的报告或更多评审角色。仍使用现有 Worker/Reviewer；只交付任务 YAML 与 `dispatch.md`，过程判断和问题进入已有回执。阶段文件名可以保留，标题和职责必须改。

| 阶段 | 输入 | Worker 必须解决与产物 | Reviewer 独立审阅 | 可进入下一步的条件 |
| --- | --- | --- | --- | --- |
| **P1 任务与共享 Contract** | 固定 IO、输入构造、reference、验收资料、实现入口及已给定的实现选择范围 | 分清任务与实现限制；在 root 填元数据、共享算法 Contract，保留硬件占位。Design 未写；不选具体主线 | 当前 Contract 全文与固定任务材料；数学、数值、输出、副作用、有效域、参考与已知验收事实 | 能独立理解外部任务；阻碍任务定义的未知已解决，其他缺口有据说明。root 文件存在不等于 Design 已选 |
| **P2 机制识别与代表选择** | 已审 Contract、固定 host/实际调用入口、实现族和 workload | 按第 4 节读代表；写 `dispatch.md` 草案：实现范围、主要机制、拟完整代表及理由、参数/局部/组合线索、未研究或不收录范围。选一套具体 root，并说明自身范围与来源 | 独立理解当前 Contract 与草案，核实主干、最有区分力的替代及关键接口；判断是否遗漏可能改变 root 或代表集合的核心机制。源码核对围绕本阶段判断与疑点深入 | root 是有据的真实设计；拟完整集合含 root 至多 10；每项有独立价值；会推翻当前选型的来源未知不能留到大量 P5 后才看 |
| **P3 完成具体 root** | P2 的代表选择、当前 root、相关固定源码、规范 | 沿数学→调度→流水线→必要 Realization 完成一套具体设计。定义自己的参数和输入相关规律；不将其他配置塞进开关、公式选择表或可选结构并集。新增识别事实记入回执 | root 有效全文；从输入到全部输出贯通，核实所选设计的首轮、稳态、尾部、空工作及跨工作寿命等实际边界；同一设计的输入行为不能漏审 | root 自身闭合，范围与参数一致，来源忠实；规定结构检查与独立语义审阅均通过。发现选型前提失效时先定点回 P2 |
| **P4 设计目录与变体记录** | 完整已审 root、P2 草案、P3 发现、必要的其他代表源码 | 将已识别知识落实到规范 `dispatch.md`：至多 10 个完整设计入口及独立价值；参数差异、局部变化、必要组合关系各写一次；为非 root 明确具体实例、待写差异和必要内容来源。只补新的关键识别，不扫全路由配对 | 独立理解当前完整 root、目录与实际依赖上下文；审每项记录、基线、证据、条件和接口，审拟完整集合是否可以更少、是否遗漏核心设计。发现 root 问题仍须反馈；P4 不另产生 P3 的 root 批准 | 计划内每份 YAML 都值得独立存在；记录足以交接，不把配置差异留作“以后 P5 各写一份”；已知核心知识均有明确去处；未来文件仅获计划批准 |
| **P5 完成其他具体代表** | 当前有限目录、本节点真实实例、root Contract、已存在的实际 `from` 来源与固定源码 | 每次完成一份完整 YAML。相同整区显式共享，不同区域完整本地写；自己的范围和 Realization 独立成立。报告影响目录/记录的新事实，不产生局部变体 YAML | 本节点完整有效 Design 和实际引用闭包；审每个使用上下文的参数、名称、数值、生产消费、事件、寿命与 Realization。比较有意义的基线，不能以引用来源或旧批准代替差异依据 | 当前节点闭合并获独立批准；其实际内容依赖可核实。最多 9 个非 root；没有则跳过。完整依赖就绪即可，不要求共同设计父 |
| **P6 全目录终审与必要收尾** | 最终完整 YAML 集合、`dispatch.md`、固定来源、P5 新发现和未决项 | 先由新 Reviewer 审；需要时 Worker 在明确范围补记录、修具体节点或修链接。未改内容保留；修订后独立审阅 | 所有完整设计的有效全文及全部正式参数/局部/组合记录；共享定义按当前来源读一次，各上下文仍审。核对数量、独立价值、记录去向、链接、真实范围和缺口，不重建所有源码路径 | 实有完整集合与目录一致且含 root ≤10；没有配置容器或无价值重复；重要机制没有以“未覆盖”偷掉；记录与最终基线一致；完整检查和独立终审完成，才能交付 |

各阶段仍须独立理解当前产物的有效内容及实际依赖上下文，不能只读目录名称或以旧批准替代当前定义。P4 必须读懂当前完整 root；本轮收束的是全路由重新分组和批准对象，不以省成本为由另行削弱独立审阅政策。P3/P5 对完整节点的独立审阅和 P6 对最终全文的独立审阅保持。P1 外部验收缺项、硬件占位和不安排 GPU 的现有边界无需重建一套。

## 4. P2 在写 root 前究竟读到哪里

应先有机制总览，再选 root；不先写一份深度 root 后靠分支逐渐发现全局结构，也不要求先完成所有路径的 Design。

1. **沿任务到实际入口确认范围。** 看 host 参数归一、入口绑定、配置族及实际 kernel 提交入口；区分本次选择的实现族与共同 Contract。这里检查选择轴与入口清单，不产生每种轴取值组合的路径表。排除手动配置等必须来自已给定范围或明确的记录选择，不能悄悄改任务域。
2. **为不同机制各追一条足以区分的真实链。** 至少知道从哪些输入得到哪些输出、主要中间值是否物化、谁负责输出或归并、工作怎样分配，以及是否存在跨工作/跨调用的接续。涉及分工差异时读到必要角色与完成协议，不能只凭同名 API、同 shape 或 launch 数量归类。
3. **围绕区分性问题深入。** 例如“split 结果由谁归并”“零验证是否是输出生产者”“缓存状态是否只改入口服务”“static 与 persistent 是否共享同一映射”“两个计算族的 Act 表示是否相同”。看清这些差别即可归类，不需先写每条链的完整缓冲与 action 清单。
4. **区分代表、参数、局部、组合、来源限制。** 对已经识别的轴各留一个有据结论；若两个轴交互会改变值、输出归属、接口或完成关系，只追这一交互的代表。互不影响的 FC1/FC2 或加载/归并组合不生成积表；同样接口也不能自动证明全部组合可行。
5. **再选 root。** 优先实际承载主要工作、主要接口清楚、便于读者比较的一套具体方案。不能人为造一个“包含所有可选分支”的通用 baseline，也不必选最复杂、性能最好或对所有设计都是共同祖先的实现。记录自己的参数选择与承担范围，其余不同配置有后续记录位置。

P2 的最小充分结果，是读者能回答：“这里有哪些主要计算/执行机制；为何这些代表能保存核心知识；root 是哪一套；剩下哪些只是已知差异，哪些还不清楚。”以下任一事实仍不清楚，就应继续定向读源码：可能另有输出产生方式、不同中间表示或归并、另一工作领取/协作机制，或可能使候选超过 10 的独立设计族。未知的某个普通 tile 配置细节、完整 action 命名、每个 host 阈值则不应阻止选 root。

“已经读过两个分支”不是充分性的标准，“每个 if 都追到底”也不是要求。止点由这些设计问题是否已有证据决定。识别记录不需要单独新文件，可在 dispatch 草案用一行一种机制；暂时的阅读进度和待查位置留回执，最终目录只保留实际范围与必要未研究边界。

例如 MoE 先区别融合 packed、split-K+激活、direct、验证输出，再看扩展范围中的 last-arriver、selfprep、BF16、REDF；无需先生成“ABI 前缀 × FC1 × FC2”的清单。这个例子是识别顺序，不是未经源码审阅就认定所有 MoE 只能有四份或九份 YAML。

## 5. dispatch 的写作、审阅与上限落地

### 参数、局部、组合分别何时完成

**P2 找事实与去处，P4 写可供使用的记录，P5 提交新增事实，P6 对最终记录负责。** P4 的依据应是实际 root 中已存在的值、step、role、存储及其他稳定对象，不能再用“相对父少一个 kernel”代替设计差额。精确记录形式由 common 统一；extract 只补源码如何确认和阶段何时完成，不另设一份竞争格式。

记录的审阅对象分三类：

| 记录 | P4 应写与审的新增内容 | 不能要求的工作 |
| --- | --- | --- |
| 同规则配置参数 | 指向具体基线，指出哪个设计参数改变、适用约束及来源；读者能辨认它仍沿用相同计算、索引与协议。当前 YAML 仍只定义自己的方案参数 | 把来源配置表全部抄进 YAML；为每个 tile/成员数创建节点；把全部配置证明成一个新的通用方案 |
| 局部变化 | 用稳定对象说明真实改动与必要联动、适用条件、结果/数值/依赖的影响及来源；相同决定只记一次 | 每个分区重新填完整小 schema；只以改了几个字段判断局部；为方便审阅强制升成完整节点 |
| 已有决定的组合 | 明确参与的设计或局部记录、已核接口及必要相容/不相容条件；新联动补一处。遇到新整体组织再考虑一个具体完整代表 | 枚举所有已知轴的配对；从形状相同推断任意组合；把记录顺序或链接解释成可执行 patch |

P4 的“定稿”应改成“目录与变体记录”，避免误解为未来绝不再变。依赖尚未写出的完整节点时，可先说明相对哪个拟定代表及新增机制；它只获得记录/计划层面的批准。P5 落实真实名称和内容后，P6 必须核实链接、对象与接口，不能把先前计划当成实际定义。

P5 仍只写自己获派的完整 YAML，不让多个节点 Worker 并发编辑同一 `dispatch.md`。发现一项新的参数约束、局部联动或记录错误时，在已有回执给出对应记录、事实与源码依据；P6 按需 Worker 汇总到该记录并由 Reviewer 审阅，不为每条小发现全量重开 P4。**完整节点集合、实际引用关系或名额分配变化，必须提前回 P4 修相应计划与依赖，不能等 P6 清理。** root 选择或其他节点成立条件被推翻，也须立即交相应职责处理。只是不影响这些项的记录事实，才可汇集到 P6。

### 不把 dispatch 变成另一种穷举清单

记录的准入仍是“省去此信息会误解结果、主要性能原因或必要协作关系”。同一规则的参数变化可按范围或一组有据配置概括；无设计影响的 API 差别、查表实现和普通错误码不逐项列。局部记录按决定组织，组合只写新增的相容条件与耦合，不登记全部出现过的配对。即使有十个 tile 值和五个启动阈值，也不是 50 项 dispatch 记录。

反向边界同样明确：为了避免展开而删除真正的第二次验证、probe 已提交的前缀、REDF 的初始化，仍然是错误。完整代表自身需要的事实留在自己的字段；其他已保留变体的必要事实留在其一次记录中。

### ≤10 是三次明确检查，不是目标数量

| 时点 | 必须做的选择 |
| --- | --- |
| P2 识别 | 机制线索可多于 10 项，但进入完整代表候选的集合含 root 必须 ≤10。先去掉配置/包装身份，再把局部与组合改为一次记录；选择能同时承载相关机制的真实具体实例。不得为了省数拼出源码不存在的通用方案 |
| P4 计划 | 每份文件都要说出不能只用参数/局部记录替代的独立价值；能少一份且不丢该价值就少一份，不为整区共享另造没有独立设计价值的 provider 节点。局部记录不占文件名额，但不能实质写成藏在 Markdown 中的第 11 份全算子 YAML。不得靠拆子目录、同算子改名或视图文件规避上限 |
| P6 终审 | 核对最终实有集合及独立价值，包含 root 且 ≤10；旧计划 8、后来暗增到 11 也不合格。核对识别到的重要机制各自的记录去向，及所有轻量记录与当前基线是否相符；不统计所有源码分支是否各有 YAML |

若超过候选上限，优先换掉只能重复展示已知机制的代表，或选能自然承载多项已知决定的实际组合；相同整区 `from` 只用于文本共享，不能为第 11 个文件开例外。也不能为了守数把本应完整说明的新输出/协作组织标成“参数”。若经过比较仍有超过 10 套不可约、且用户明确要求逐套完整交付的核心设计，才形成真实的目标冲突；此时列出具体取舍证据交用户决定，不擅自收窄 Contract。本轮现有案例没有证明存在这一冲突，因此不应预先追加确认步骤。

### 研究状态、收录选择与错误行为应区分

这些是需要如实说明的事实类别，不是给 Runner 新增的状态机。

| 情况 | 可以如何交付 | 不能怎样表述 |
| --- | --- | --- |
| 已研究，已写完整代表 | 给出具体 YAML 及自身 `when`，完整贯通全部输出 | 代表已经审过，所以未写组合也全都正确 |
| 已研究，轻量记录 | 参数、局部或组合记录有明确基线、变化、条件和必要接口；承诺只及已说明内容 | 只有一句“同 root”就算保存，或把局部记录当完整 schema |
| 已研究，刻意不收录 | 说明范围与理由，例如无设计影响的包装、目标外的强制实验族；知道何物被排除 | 为省名额把主要新计算/协作机制无理由排除；把不收录说成源实现不存在 |
| 来源尚未研究或不足 | 明示具体边界，判断是否影响代表选择、已声称记录或当前设计成立；影响者须先解决 | 未读就称“只有参数差异”“无价值”或“已覆盖”。不影响当前声明的未研究范围可随目录保留，不要求全源码无未知 |
| 拒绝、失败或源缺陷 | 这是源码行为，可同时属于上面某种研究状态。区分提交前拒绝、已提交后失败、落到另一正常实现；在受影响设计或记录中保留必要副作用、在途访问、版本和寿命，详细缺陷沿用 issue | 用“错误路径”统一抹掉已发生的工作；为每个错误码创造完整算法；补造 fallback、等待或资源隔离保证 |

“实现不能覆盖某些合法输入”和“本目录选择不完整记录某些实现设计”也不是同一件事。前者是来源实现限制，后者是设计知识目录的范围；两者都不改变共同 Contract。`when` 表示当前具体设计的承担范围，不要求互斥，不由父条件叠加，也不默认 root 补齐目录空白。

## 6. 后续发现与修订只回到必要位置

`from` 表示当前内容依赖。一个设计可以有多个区域来源，也可全部本地定义而只共享 root Contract；叙述“受 A 启发”不产生内容依赖，目录也不要求所有设计通过一条 parent 链连到 root。P5/P6 审当前原文及实际来源链，不审一个虚构父亲的全部设计来证明本节点。

| 新发现 | 方法上由谁处理 | 需要复核的范围 |
| --- | --- | --- |
| 本节点细节、边界或 `when` 错误 | 当前 P3/P5 作者修自己的定义，独立复审 | 当前完整节点及真的依赖该变化的记录/引用者 |
| 新参数约束、局部变化或组合联动，未改变完整集合 | P5 提报，P6 的按需 Worker 更新对应 dispatch 记录；必要时先修受影响节点 | 该记录、使用它解释差额的关系、实际受影响的完整设计；不因一个记录增补重选 root |
| 发现新的整体机制，现有代表未保存 | 回 P2 的识别判断；确认需要完整代表后，P4 只修相关目录项并重新核对 ≤10，P5 写该具体代表 | 相关选择和记录；已有无关完整稿保留。新机制不与已知所有轴相乘 |
| 节点增删/替换、完整名额重分配或实际 `from` 引用关系变化 | 提前回 P4 核对相应集合、内容依赖和当前记录；不靠 P6 临时加文件或改依赖 | 改动项及真实依赖闭包，保留无关完整稿；引用变化本身不支持新增完整身份 |
| 整区 provider 的本地定义本身错误 | 修实际定义所在 P3/P5，独立审 provider | 实际引用链的消费者及依赖该基线的局部记录；不是叙述派生树的所有后代 |
| 共享定义本身正确，只是不适合当前组合 | 在当前节点把该整区完整本地化并修订，或选择已有确实相同的整区；改变已定实际引用关系时，同步按上行提前更新 P4 的依赖判断 | 当前使用上下文及改变的实际依赖；不能反过来修改 provider 使其他设计错误，也不因此重做全部机制识别 |
| root 的代表选择真的失效 | 回 P2，必要时重写 P3 并更新 P4 | root 和依赖其实际内容/目录基线的部分。仅发现另一种有价值设计不构成换 root 的理由 |
| 共享 Contract 的已知事实写错 | 回 P1，复核所有完整设计是否仍适用 | 全部使用者的受影响前提，最终仍有完整 P6；已有完整稿可先独立评估是否需改，不能无条件覆盖重写 |

每次指出新事实、受影响定义和依据；不为了请求重开寻找无关新源码行。已有 raw 应保留，批准则只对当前定义、来源和适用范围有效。方法上的影响分析应按真实内容和引用传播，P6 最终仍独立审阅全部不超过 10 份设计与正式记录。这里没有规定 generation、fence、回执字段或自动失效算法，也不声称现有 Runner 已能做到这一传播范围。
