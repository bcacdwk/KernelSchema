# 问题定义与判断标准

主代理的初步整理，供各轮研究检验；下面的假设不是既定结论。

## 我们要解决什么

Schema 的产物应是一组值得理解、复用和实施的设计，不必逐项复刻原实现的全部选路。共同的数学 Contract 和硬件要求保持一致；变化可以涉及数学改写、工作调度和微流水线。

本轮的目标有两个，不能相互替代：减少需要独立理解、维护的设计数量；减少不同设计之间的重复定义。整区引用主要帮助后者，不能自行消除组合节点。

用户希望真正的基础设计只有少量。研究应识别新增的设计信息和组合关系，不能为了得到小于十的数字而随意合并，也不能把源码分支数直接当成设计数。

## 已核对的现状

| 事实 | 含义与边界 |
| --- | --- |
| DOC0 要求每个节点的 `when` 独立求值，互斥且共同覆盖 Contract 全域 | 节点同时承担设计载体与完整运行时选路分区两种职责 |
| DOC0 以无法参数化的提交、生产者、物化或事件差异作为拆节点依据 | 局部结构变化容易升级为一整份完整设计，但是否应升级仍需讨论 |
| 每个节点只有一个直接父；三个 Design 区域只能引用直接父的同名整区 | 设计来源、目录组织与内容共享的选择互相约束，独立组合很难直接表达 |
| FA4 prefill 现有 11 个 YAML 节点 | static/persistent、K/V 加载分工、长度排序、alpha 共享、split-KV 在多条路径重复出现；不能仅因重复出现就断言能自由组合 |
| 首批 MoE 交付 60 节点，暂停时计划 154、批准 96 | 时间点和提取范围均不同；较新稿限定默认实现控制，154 不是 154 份已审定设计，也不是初始 60 的同范围扩张 |
| MoE 索引中，多种 FC1 组织各自重复配对同样的 FC2 组织 | 提示组合放大，仍需源码检查各维度是否独立、有无新的跨区耦合 |
| 单 root 也存在漏项回修和较高上下文成本 | 不能把全部成本和错误归因于节点划分，也不能承诺引用或少分支能等比例省钱 |

## 要分开判断的四件事

1. **设计身份**：这条变化是否增加了值得单独理解的算法、分解、数据通路、分工或同步方案？这和某个参数取值、源码入口、提交列表不同不是同一问题。
2. **适用范围**：设计依赖哪些输入或调用条件才能成立？这和原实现恰好用什么阈值选择它不同。需要判断两者各自应保留多少，是否仍须互斥穷举。
3. **共享内容**：哪些定义实际相同、在新上下文也成立？这和设计从谁启发或派生不同。共享不应默认证明组合正确。
4. **记录深度**：哪些值得完整 YAML，哪些只需记录变化，哪些没有新增设计信息？简记是设计说明还是可展开的机器补丁，必须说清楚。

## 初步假设

- 主要矛盾可能是把“完整路由覆盖”当成“完整设计知识”，使局部变化与独立组合不断增加完整节点
- 单父树可能混合了三种不同关系：共同 Contract 的归属、设计派生来源、内容引用；多来源组合会暴露这个限制
- 不能只放宽继承语法，也不能把几十份 YAML 搬成几十条同样难维护的说明；真正要减少的是重复的设计决策
- 有限 `for/if` 能表达单份设计内部的规律，但不应为消除节点把全部方案塞进巨大的条件结构

## 证据如何支持取舍

每个建议至少回答：现有哪个案例有问题；新增或删去什么设计信息；读者还能否理解留下的计算、物化、分工和依赖；记录与维护的工作是否真的减少。

提议合并时检查四个反例：数值语义改变、跨 kernel 物化改变、资源寿命或事件协议改变、组合后新增接口约束。出现这些差异并不自动要求完整 YAML，但不能以“微调”二字抹掉必要解释。

完整 YAML 应在声明范围内自洽；简记不冒充已完整展开、已验证的独立方案。使用字段或对象名称定位差异，比依赖易漂移的文件行号更适合作为维护规则。

- 分支保留、共享、简记、省略的推荐标准与反例
