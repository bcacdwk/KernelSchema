# 第一轮 Design 评审

结论：现有流程已经能支持 Planner 从 Contract 和案例形成原创设计，数学 → 调度 → 流水线的顺序应保留。需要补强的是一处衔接：在起点明确本轮先落实具体 root，在后段明确如何从已发现的候选中选出确需并存的少数完整方案。建议只改第 1、5 节的相关段落，不增加调查阶段、批准关口或固定报告。

“先形成 root”是集中设计精力，不要求先证明 root 最优、完成实验、覆盖整个 Contract，也不禁止为了选定它而比较少数有依据的整体路线。普通 Design 没有一份必须忠实收录的既有实现，不能照搬 Extract 的主要机制调查与独立选型审定。

## 建议修改：把一条工作线首尾接起来

**第 1 节点明 root 与本次任务范围。** 将 L13 的“一套具体方案”明确为先围绕主要 workload 形成的 root；先确认任务要求覆盖什么，再逐层落实本份设计自身承担的范围。root 选择便于理解和比较的实际方案，不需要为充当全域基线而加入多套机制。比较时发现的其他有据路线可先保留差异和理由，不在这里展开全部 dispatch。

实际影响：读者不会等到交付时才把已经写好的主方案理解为 root，也不会把“契约有效域”“本次要求实现的范围”“root 自身范围”合成一个义务。现有 L55 才提任务范围另行核对，前移这个认识有助于正常选择首条路线；并未改变 common 的范围语义。

**第 5 节突出先取舍、再展开。** root 的计算、工作归属与主要协作清楚后，依据本轮已经发现的差异，判断是否还需要独特完整方案并存；给出它增加的整体设计价值及本次保留理由后，再逐层完成选定方案。当前选择落实在正文，其余参数、局部变化和已知组合按 common 记录；未完整展开的方案仍按独立候选说明。相同整区按现有规则 `from`，不是每条路线都从头重写三区。

实际影响：把完整展开的投入放在明确选择之后，不因参考目录列出许多节点便逐个复制，也不因变化重要便自动提升为完整 YAML。这是把 L55 已有原则转成下一步动作，不需额外发起一轮全局调查。若没有新的并存需要，一份 root 即可；有据的整体路线比较可发生在前面的推导中，不能把本段变成“完成 root 验证后才准考虑其他路线”的门槛。

这两处之外，普通改名、展开、本地化或相同整区引用调整沿当前工作完成；只有具体事实推翻前提时才按 L7 返回最早受影响层。无须再加一套回退表。

## 明确无需修改

- **案例与原创的边界已经足够。** L17 和 common L102 不让源码替代硬件、正确性或最优性依据。引用来源不等于沿用所有机制；从 Contract 自行推导也不需要伪造来源。无需给普通 Design 增加固定源码调查或 Extract 式审阅。
- **有限比较已有可执行方法。** L21–25 先建参照、估算差额、选择主路线，L37–41 与 L45–49 再解决工作组织和局部约束。不宜另设候选数量、穷举表或先完成所有方案再比较的要求。
- **推进条件与回退无需收紧。** L7、L29–31 已要求先处理可分析且能推翻方案的问题，也允许把剩余的数值、驻留或性能判断交给后续验证。不能把“尚未实测”统一改成阻塞，也不能把“路线还没选”当作普通待验证项。
- **缺少输入不等于方法缺陷。** [模板 L9–17](../../../schema_template/README.md#1-确认资料与范围) 已要求任务提供目标、workload、Contract 和硬件依据，允许继续不受影响的部分。FA4 示例的 wiki 占位、快速数学误差缺项属于材料状态；未给 workload 权重也不能通过增加流程文字凭空补出。DOC3 的 `bind` 与既有未知说明已能交接下游选值，无需新状态字段。
- **common 不应复制进本页。** 数量上限、局部闭合、组合相容、最终真实基线及 `from` 使用上下文均已有定义。Design 只需指明何时作判断，继续链接唯一规则。

## 供第二轮 medium 使用的普通任务

以下是有限文字推演任务，不预设要选哪个案例或交付几份设计。

> 你是 Planner，要为 paged causal GQA 设计首版方案。读 `DESIGN_SCHEMA.md`、`schema_docs/0.common.md` 和按需的 DOC3/4/5；仅写文字推演，不写 YAML、不运行脚本、提取或实验。
>
> 本次算法输入采用 `schema_template/examples/fa4_prefill/root.yaml` L14–67 给出的 Contract：FP8 Q/K/V、Hq=16、Hkv=1、D=256、Page=64，右对齐 causal attention，保持 out 的更新与返回别名，以及原有 reference 和容差。这个 Contract 由任务给定；旧 Design、旧 `when` 和节点树不是本次要求。
>
> 本次要求支持两组 workload：主组 BatchCount=32，每请求 Qlen=128、L=8192；次组 BatchCount=1、Qlen=1、L=131072。两组均按 Contract 构造合法页表和前缀边界，数据仍采用 Contract 的值域。每次调用有 64 MiB 可用 scratch；本轮讨论隔离调用，不设计跨调用缓存。目标是降低完整 callable 的延迟，首先照顾主组，同时给次组明确的可用路径；准备、额外物化、提交和归并成本都算在内。
>
> 目标设备与栈沿用该 Contract 的 L20D/SM103、CuTe DSL 4.6.1。可用事实是 L68–82 的执行层级、存储和异步能力摘要；完整 wiki 绑定和精确吞吐尚缺，材料状态见 `schema_template/examples/README.md`。此次停点不要求完成资源验收：工作数量与逻辑流量可直接推导，容量、并发与相对代价可用有明确来源的数值或约束式，不虚构峰值、驻留或实测结论。
>
> 先从计算和主要成本出发，比较足以作当前选择的少数路线，选一条作为 root 方向，并说明它自己的范围。需要案例时，可读上述 `root.yaml`，按当前疑点再看同目录的 `splitkv_dual_load.yaml`、`packed_persistent.yaml` 或 `small_persistent_shared_rescale.yaml`；不要求把四份都读完或复现旧分组。采用案例中的数值近似或组织方式时，解释本任务为何适用；可以作不同选择。
>
> 将已选方向推进到向调度和流水线的交接：输入到输出的计算、状态与物化；工作边界、结果归属及必要归并；下一层必须实现的生产消费和资源复用关系。给出已经能选定的内容，明确仍由下一层选值或待验证的条件。root 的主要组织清楚后，再说明是否值得保留其他完整方向，以及实际遇到的参数、局部或组合知识应放哪里。不要求凑出第二份完整设计或写完动作表。
>
> 到这里停止，简述正式流程在哪些地方帮助你推进；若有卡住，只定位具体决定、缺少的输入或规则，不把未完成的全文、缺硬件 wiki 或未做实验直接判作流程失败。本轮输出不是完整 schema 或验收结果。

本任务能观察有限比较、root 聚焦、少量完整方案与轻量记录的关系，也能观察在不假装完成硬件验证的前提下能否继续交接。它不以特殊数值反例或缺少材料来测试作者是否“失败”。
