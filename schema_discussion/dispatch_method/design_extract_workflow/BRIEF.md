# Design 与 Extract 流程改进

本轮只完善文字流程：Design 从给定任务与可参考的 schema wiki 形成新设计；Extract 将固定 Kernel wiki 实现整理为 schema wiki。Optimize、Implement、执行器、检查脚本和真实提取均不在范围内。

## 目标

- 让作者先形成清楚的 root，再决定确有独特价值且需要并存的少数完整方案；参数变化、局部变化与已知组合用目录记录。
- 让 Extract 的 P2 充分研究并独立审定主要机制、代表与轻量记录去处，后续阶段沿已定判断完成正文和目录。
- 保留必要纠错：具体事实推翻前提时返回受影响阶段，普通命名、展开、局部引用调整不触发重复选型。
- 文档直接说明当前工作与推进条件，精简客观；不增加审批、固定报告或防御性清单。
- 以协作改进为目标。角色试读用于观察未来作者能否顺利推进，不刻意制造反例或要求推翻现有设计。

## 既定边界

common 已定义：当前完整 YAML 含 root 最多十份，越少越好；每份表达一套具体设计，相同整区可用 `from`；完整身份依独特整体设计价值判断，目录按参数、局部、组合记录其他变化。root 是真实设计与共享 Contract 的阅读入口，不要求覆盖整个 Contract 或成为所有设计的祖先。

字段、取值、结构及语义的实质改变只记录 issue。本轮可直接修改流程与说明文字；既有字段议题见 [FIELD_ISSUES](../../role_prompt_trial/FIELD_ISSUES.md)，不借本轮处理 F1/F2。

## 四轮分工

每轮两名新代理，模型 `gpt-6-astra`；主代理阅读关键规则、审定建议、协调边界并验收。

| 轮次 | Effort | 工作 |
| --- | --- | --- |
| 1 | max | 分别从 Design 与 Extract 全链路评审当前方法，区分真实流程缺口、已有规则和输入缺项 |
| 2 | medium | 分别代入未来 Planner 与提取 Worker/Reviewer，依据正式文档和真实参考材料作有限文字推演 |
| 3 | max | 结合角色反馈，独立复核两条流程及交接，给出可直接实施的精简修改意见 |
| 4 | xhigh | 按主代理审定意见分别修改 Design 与 Extract 文案，核对相关导航与一致性 |

不计入此前任务的代理；不复用旧代理。本轮所有判断记录在本目录。
