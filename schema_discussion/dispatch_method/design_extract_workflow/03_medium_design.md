## 2. 先确定计算方向

直接求值参照是逐 query/head 计算全部可见 score，再 softmax 与 PV。主要组共有 65,536 个 query/head 行；按完整矩形计算，一个 FP32 score 矩阵约 2 GiB，score 与 probability 两份约 4 GiB。causal 尾部只略微减少这个量。因此先选分页流式计算，避免全局物化这两份矩阵；这项容量收益成立，但不能据此宣称 callable 已经更快。

我保留 head packing：行 r 对应局部 query `floor(r/16)` 与 head `r%16`，同一组行共享 K/V。K/V 仍通过 block_tables 取得，不能假定逻辑相邻页在物理上相邻。主要组全量 FP8 K/V 重排也要 `32*8192*2*256 = 128 MiB`，超出 scratch。次要组全量重排恰为 64 MiB，未留下 split 部分结果空间。因此首版不选全量重排；这不排除以后研究逐请求或局部重排。

对每个有效行，保留在线三元组 `(m,l,Y)`，初态 `(-inf,0,0)`。本块有有效 key 时，以缩放后的 FP32 score 更新 `m_new=max(m,max(score))`，令 `alpha=0`（旧状态为空）或 `exp(m-m_new)`，`E=exp(score-m_new)`；被掩码位置直接为零，然后：

```text
l_new = alpha*l + sum(E)
Y_new = alpha*Y + sum_j(E[j]*V[j,:])
out = bf16(Y/l)
```

QK、E、l、Y、重缩放及 PV 采用明确的 FP32 求值起点，最终才转 BF16；不引入案例中的 lag、指数 offset、FP8 P 或默认 fast-exp2。QK/PV 的实际乘法与累加行为需要在实现交接前落实；“FP32 累加”不能授权隐含 TF32 或额外操作数窄化。数学上选 FP32 PV 也意味着不能直接沿用案例的 FP8 PV Tensor Core 代价，这是这条保守路线的重要成本。

这里已能做的数值自检不能全部推给实验。按 E4M3FN 有限值上界 448，QK 原始绝对值至多 `256*448^2=51,380,224`，缩放后至多 3,211,264，FP32 不会因这个量级溢出。普通最大值更新使 E、alpha 在精确关系上均不大于 1；这两组长度下 l 不超过 131,072，Y 每通道的绝对值粗界约为 `448*131072=58,720,256`，也没有 FP32 溢出问题。第一块显式处理空旧状态，整块无可见 key 时跳过更新，避免 `-inf-(-inf)`。输出沿 Contract 索引写回 out，完全忽略 out 初值。

这些范围界不是原容差证明。尤其大幅抵消的 QK、接近的 score、长序列累计和最终接近零的输出，仍可能放大归约顺序与指数误差。因为没有收窄 Q/K/V 值域，不能用“随机 FP8 输入一般通过”代替这部分判断。当前先固定上述路线，再补实际算术语义和有针对性的分析；若发现它不满足原验收，回到数学层修改，不能交给 Coder 自选近似路径。

次要组在同样的在线关系上切分 KV。每个 split 产生 `(m_s,l_s,Y_s)`，完整物化供归并使用。归并取 `m*=max_s(m_s)`，计算 `w_s=exp(m_s-m*)`，再以 `sum_s(w_s*Y_s)/sum_s(w_s*l_s)` 形成最终输出。空 split 约定为 `(-inf,0,0)` 并不参与无效指数运算。本次固定次要 shape 可以让所有 split 非空；仍须在实际公式中明确这一事实。选择直接合并三元组，避免为了复刻案例再引入 log/LSE 路径。

## 3. 再安排工作，交给流水的是什么

主要组先取 `Bq=4`、`M=64`、`Bk=64` 作为可继续核实的具体起点，一份 worktile 是一个请求的四个 query、全部 16 heads，遍历其可见 KV 页。共 `32*ceil(128/4)=1024` 份工作，先按一 CTA 一份工作、静态预分配、完成即退出组织。尾页仍按每行的右对齐 causal 条件处理，不把 query 块最大可见位置当成所有行都可见。

这给了较多独立工作，无需先切 KV 来增加并行度；但 1024 份工作是否足够、是否驻留合适，仍取决于实际设备。代价也要带回上层：每请求有 32 个 query 块，忽略缓存与 causal 尾部削减时，逻辑 K/V 读取可接近 4 GiB。head packing 的复用不能被写成所有 query 块共享一次 DRAM 读取。将 Bq 增大到 8 会减半这一重复量，却加大行状态，值得后续作为参数变化比较。

一份主工作若保留 FP8 Q/K/V 块、FP32 score 或 E 单槽、FP32 Y 和两个行标量，粗算分别约 16、16、16、16、64 和 0.5 KiB。这是约 128.5 KiB 的逻辑同时存活预算起点，不是全部属于 SMEM，也不是已经证明单 CTA 放得下。实际累加布局、score 与 E 能否安全复用、转换临时量、分配粒度及寄存器数量尚未计全；下一步必须把它们分配到具体存储层级，再复查容量和驻留。

次要组若仍由一个 CTA 承担全部 16 heads，就有很长的串行 KV 遍历。我先选择 128 个固定连续 split，每段 1024 keys，`Bk=64` 时各 16 轮，128 个部分结果 worker。这个 128 是本轮待资源/性能核实的选择，不沿用旧 selector，也不写成依 SM 数自动选方案的公式。部分三元组占 `128*16*(256+2)*4 = 2,113,536` 字节，约 2.02 MiB；写后再读约 4.03 MiB 的逻辑传输，另有 Q 重复读和归并计算。相对于不 split，收益条件是并行执行缩短的延迟超过额外提交、部分结果传输和归并的总成本。

归并按 head、输出通道块分配工作，每个最终输出元素只有一个归并生产者；各工作读取其需要的全部 split，不依赖原子累加。初版用两次提交，归并明确等待部分结果 kernel 完成并可见，不引入跨 kernel 提前消费或全 grid 自旋等待。

向微流水线交接的关键内容是：

- Q 的行映射与保留范围、页表 K/V 视图、每行 mask，已经确定的 FP32 求值路径和 `(m,l,Y)` 更新；Bq/Bk/split 由调度唯一绑定，不能由流水或 Coder 再挑一套。
- 主方案的 `MAIN` 独占其输出区域；split 方案的 partial/merge 分别生产三元组和最终输出，handoff 的数学值、索引范围、global 物化和完成前驱必须齐全。
- 局部依赖是 Q/K 就绪后 QK，score 与旧状态就绪后 softmax，V 与 E 就绪且旧 Y 的缩放完成后 PV；最终状态完成后写输出。复用 K 槽要等最后 QK 读取结束，V/E 槽要等最后 PV 读取结束；发起异步操作不算完成。
- scratch 的所有消费元素都由本次生产者写出；调用隔离不能代替本次初始化。部分结果要留到归并全部读取结束，局部状态则按每份工作重新初始化。

首版倾向单槽、简单 role 协作，把语义和存储生命周期先做完整；只有确认搬运或计算重叠值得容量与同步代价后再增加缓冲。此处尚未决定完整成员范围、动作粒度及存储位置，所以还没达到 DOC 5 完整交付条件。
