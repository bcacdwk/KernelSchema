# 微流水线

## 核心思想

派生节点可以依[Design 整区引用](0.common.md#design-整区引用)将整个 `tile_pipeline` 写为 `{from_parent: <直接父ID>}`；root 始终本地定义。下文描述本地或展开后的完整区域。共享 role、资源、动作及事件仍须与使用节点当前的 work_schedule、launch、handoff 和数学值闭合；引用不继承 provider 的选择条件，也不允许局部 role/phase patch 或取消实际存在的生产消费与事件。

`tile_pipeline` 在已经确定的 worktile 和 worker 内，描述执行角色怎样推进计算、交接数据和复用资源。它接收 `math_reshape` 给出的值、精度、初值及物化决定，接收 `work_schedule` 给出的工作归属、执行成员、工作序列与跨 phase 关系，再将这些设计转化为 Coder 必须保持的局部执行约束。

本区的基本对象是 **role**。一个 role 是承担一类动作的一组执行单元，在 NVIDIA 上是一个或几个 warp；它不是单个线程，也不一定独占某个硬件引擎。例如，矩阵乘 role 可以只是负责发射异步矩阵乘的一个 warp，矩阵乘本身在 Tensor Core 上执行。执行单元的名称取自 `contract.hardware_specification.execution`，其他设备使用各自登记的单元（如 MI355X 的 wavefront、昇腾 950 的 AIC 与 AIV）。

本区保留四类信息：

| 信息       | 回答的问题                                               |
| ---------- | -------------------------------------------------------- |
| 角色与动作 | 哪些 warp 承担什么工作，各自怎样推进                     |
| 索引与控制 | 动作属于哪份工作、哪次局部迭代，在什么条件下存在         |
| 依赖与同步 | 消费者何时可以继续，哪些结果可以提前使用                 |
| 资源与复用 | 值放在哪一级存储、开几个槽，哪些值共用存储，何时可以覆盖 |

动作采用设计级粒度，而不是源码调用级粒度。两个连续动作之间，只有出现重要的数据发布、统计量捕获、资源归还、执行角色切换、独立循环或重叠机会，才值得拆开；没有这些边界的内部初始化、转换与计算可以合成一个已定义的动作。数学内部步骤由上游定义，地址计算、线程级 layout、指令语法及普通原语的实现细节交给 Coder。

### 设计着眼点

上游已经定下算什么、一份工作多大、由谁来做；本区决定这份工作在 worker 内怎样流动。存在稳定重复段时，先明确每轮的工作，再估计稳态下相邻两轮开始的间隔（pace）。最忙硬件资源的每轮耗时给出其下界；递推依赖、同步和无法重叠的工作可能进一步拉长周期。先比较 Tensor Core、MUFU 与 FMA、搬运与访存、发射等资源的负载，再沿依赖检查可重叠的部分。

| 问题                   | 要看什么                                                                                                             | 落在哪里                                                                               |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| pace 卡在哪一环        | 重复段中各硬件资源各要忙多久，依赖链或同步是否使周期超过资源下界；能否把一部分工作挪到空闲的单元上                   | `thesis`；pipe 中循环体内的动作，以及 `describe` 中的负载分摊                      |
| 谁和谁重叠             | 同一 role 的异步推进或不同 role 的独立推进，能否在既定依赖下形成有价值的重叠；拆分角色还会增加成员、寄存器与交接需求 | 各 noun 的 `execution_mode`、`waiting`，以及 role 的划分、`member`、`register` |
| 缓冲开多深、放在哪一级 | 生产者要领先几轮才能盖住延迟；加深换来延迟容忍，付出片上容量和每个 SM 能驻留的 worker 数                             | `storage` 的 `location / depth / shape / total_size`，`released` 边的距离        |
| 结果多早交出           | 消费者等的是整块还是其中一部分；分段发布让下游提前开始，代价是多一次同步                                             | 动作的切分，`prepared` 边                                                            |
| 跨工作是否排空         | 持久 worker 的缓冲、状态和在途操作能否直接接续到下一份工作                                                           | `worktile` 与连续序号域，跨工作的边                                                  |

## 字段定义

### 结构轮廓

下面是字段结构。`<name>` 表示实例名称，`?` 表示条件可省略。

```text
tile_pipeline
├─ thesis
└─ phase
   └─ <phase_id>
      ├─ index?
      │  └─ <index_name>: meaning / definition
      ├─ event?: <event_name>
      ├─ storage?
      │  └─ <storage_id>: meaning / depth / location / shape / dtype / total_size / member? / view?
      │     └─ view.<value>: slot_index? / region?
      └─ role
         └─ <role_id>
            ├─ info: describe / member / register? / using_verb
            │  └─ using_verb.<verb>.<noun>: execution_mode / describe
            ├─ pipe: 有序列表（动作字符串、for、if）
            └─ waiting?: prepared? / released? / allowed?
```

### 主体字段

本区使用 `thesis / phase`。phase ID 沿用 `work_schedule` 中的工作定义；提交与接续由 `flow.launch` 及其 `order` 确定。每个 phase 内，`role` 登记执行角色，`storage` 登记 worker 的片上存储区域与占用，`index` 定义有序索引，`event` 为跨 phase 引用的已有事件集合命名。后三项按需登记；动作和等待由 pipe、依赖及上游工作组织决定。

下表中的路径均相对于 `tile_pipeline`。

| 字段路径                     | 值的形式                       | 填写条件                                   | 含义与约束                                                                             |
| ---------------------------- | ------------------------------ | ------------------------------------------ | -------------------------------------------------------------------------------------- |
| `thesis`                   | 非空英文字符串                 | 必填                                       | 一两句说明局部执行的主要安排、依据与代价；采用流水重叠时，说明主要限制及打算重叠的工作 |
| `phase`                    | 非空具名映射                   | 必填                                       | 键与 `work_schedule.phase` 一一对应                                                  |
| `phase.<phase_id>.role`    | 非空具名映射                   | 必填                                       | 执行角色，见[role 字段](#role-字段)                                                     |
| `phase.<phase_id>.storage` | 存储区域具名映射               | 有影响容量、存续或复用的片上区域时填写     | 该 worker 的片上存储账，见[片上存储](#片上存储)                                         |
| `phase.<phase_id>.index`   | 有序索引具名映射               | 索引需共同引用，或需要具名工作序列时填写   | 定义身份、范围和顺序，见[索引](#索引)                                                   |
| `phase.<phase_id>.event`   | 具名映射，值为非空事件引用列表 | 跨 phase 需要点名本 phase 的局部事件时填写 | 已有事件集合的别名，见[跨 phase 交接](#跨-phase-交接)                                   |

### role 字段

单个协作 CTA 可以只有一个 role，没有 `index`、`waiting` 和专职异步角色。没有独立执行角色时，不把一段协作计算拆成虚构的 Load、Compute 或 Epilogue role。

下表中的路径相对于 `tile_pipeline.phase.<phase_id>.role.<role_id>`。phase ID 沿用 `work_schedule`，每个 role 登记一个执行角色。

| 字段路径            | 值的形式         | 填写条件                               | 含义与约束                                                               |
| ------------------- | ---------------- | -------------------------------------- | ------------------------------------------------------------------------ |
| `info.describe`   | 非空英文字符串   | 必填                                   | 一句概括这个角色的总体职责                                               |
| `info.member`     | 成员选择字符串   | 必填                                   | 这个角色占用的执行单元，例如 `warp[0:4]`、`CTA[0].warp[12:13]`       |
| `info.register`   | 正整数           | 设计为不同角色设定不同寄存器预算时填写 | 每线程寄存器数                                                           |
| `info.using_verb` | 基础动词具名映射 | 必填                                   | 本 role 使用的全部动作族，见[基础动词与动作声明](#基础动词与动作声明)     |
| `pipe`            | 非空有序列表     | 必填                                   | 动作发起顺序与控制结构，见[pipe：有序列表与控制流](#pipe有序列表与控制流) |
| `waiting`         | 依赖分类映射     | 存在默认依赖之外的前驱时填写           | 见[依赖](#依赖)                                                           |

`info` 按 `describe / member / register? / using_verb` 的顺序书写。`info.describe` 说明角色总体职责，各 noun 的 `describe` 说明具体动作。

`member` 同时给出角色的规模：一个 worker 用多少 warp，就是各 role 成员的并集，不另设计数；不承担动作的 warp 不登记。成员选择省略第一段时，这个 role 在 worker 的每个成员上各有一份。

例如，上游已确定一个 CTA 协作计算并写出 `Y`，内部没有需要单独表达的发布或复用边界，该 phase 的 role 可以只有：

```yaml
role:
  MAIN:
    info:
      describe: "Compute and write the output Y cooperatively."
      member: "warp[0:4]"
      using_verb:
        compute:
          Y:
            execution_mode: serial
            describe: "Form Y from the inputs defined upstream and write it to the materialized destination."
    pipe:
      - "compute:Y"
```

切出一个 role 的典型理由是让异步发射不必等待同一角色的同步计算，或让不同角色的计算与等待有机会重叠；是否有效还要看依赖和资源争用。`register` 记录各角色的寄存器预算；在既定总预算内重分配时，计算角色增加的部分需要由其他角色让出，总预算改变则须重新核对驻留。

#### 基础动词与动作声明

动作由一个基础动词和一个 noun 组成，写成：

```text
verb:noun
verb:noun(index)
matmul:A(index)@B(index)
```

基础动词是封闭的八个，分四类二分：

| 类别     | 动作词      | 含义                                                     | `done` 保证                                                      |
| -------- | ----------- | -------------------------------------------------------- | ------------------------------------------------------------------ |
| 数值计算 | `compute` | 按上游定义执行逐元素、归约、转换等非矩阵乘类运算         | 指定结果可供声明的消费者使用                                       |
| 数值计算 | `matmul`  | 执行上游定义的矩阵乘法及其累加；公式与数值路径由上游确定 | 指定矩阵结果可供声明的消费者使用                                   |
| 搬运访存 | `load`    | 从绑定的源读取既有值到指定目标                           | 本次源读取结束，目标数据可用；不自动归还源使用权                   |
| 搬运访存 | `store`   | 把已有值写入绑定的目标                                   | 目标写入完成，并满足声明的消费者所需的可见性                       |
| 顺序同步 | `await`   | 等待其他参与者的已声明通知条件，可涉及多个通知           | 声明的条件及其交接保证已满足                                       |
| 顺序同步 | `signal`  | 向声明的参与者发出指定含义的通知                         | 本方通知义务完成，不表示对方已经继续                               |
| 资源占用 | `acquire` | 取得指定资源本次使用所需的资格                           | 已实际取得使用资格，仅发出请求不算完成                             |
| 资源占用 | `release` | 归还本参与者对指定资源或区域的使用权                     | 本参与者已结束该部分使用；不代表所有参与者完成，也不必物理销毁资源 |

四组对照分别表达非矩阵／矩阵、读取／存储、等待／通知、申请／释放，便于辨认主要作用；数据变化、通知协议与使用资格各有明确归属。具体算法由上游数学定义与动作组合表达，词表只规定基本作用。各平台提供对应能力（NVIDIA PTX 的矩阵、访存与同步指令族，AMD 的 MFMA 与 WMMA，昇腾 Ascend C 的 `Mmad`、`DataCopy`、`SetFlag/WaitFlag`、`AllocTensor/FreeTensor`）；`matmul` 的含义来自上游数学，不绑定某个平台的线程组织、布局或完成方式。

源、目标、访问区域、资源及参与者须能从上游定义和本动作的 `describe` 唯一确定，不能靠词名猜方向。普通读写与结果落位可以包含在计算中，不必把每次计算拆成多个动作；有独立搬运、通知或使用权交接边界时，再组合相应动作。`release` 的 done 与 `store` 的 done 分别描述源使用权归还和目标写入完成，两者不能互相替代。

以下几点容易在选词时出错：

- 「形成值并让其他 role 可读」按实际内容归入 `compute`（算出来并可读）或 `store`（已有值的纯发布写入），不另设发布动词；可见性由该动作的 done 保证承担。
- 「计算并写到物化位置」归入 `compute`；只有当写出本身构成独立的交接或归还边界时，才拆成 `compute` 与 `store` 两个动作。
- 「累加器置零」归入 `compute`，并在 `describe` 中写明它不读输入、不读旧值。
- 多播搬运用 `load`，在 `describe` 中列出目标及完成范围；barrier 的 arrive/wait 用 `signal`/`await`；融合在计算内的 shuffle 不单列动作，独立的重排用 `load`/`store`，swizzle 属于布局实现。
- 搬运的完成协议（如事务字节计数的预告）纳入该搬运动作的完成保证，不单独作为一个 `signal` 动作。
- 「已发射且源已读完」不是 `store` 的 done：`store` 的 done 要求目标写入完成并满足可见性。需要表达源已读完而目标未写完时，用 `store` 加一个有明确原语依据的 `release`。

##### `using_verb` 与 noun

每个 role 在 `info.using_verb.<verb>.<noun>` 登记自己使用的动作族：

```yaml
info:
  describe: "Compute the row statistics and exponentials for softmax."
  member: "warp[0:4]"
  using_verb:
    compute:
      RowMax:
        execution_mode: serial
        describe: "Compute the row maximum of Scores(i)."
      Exp:
        execution_mode: serial
        describe: "Form the unrounded exponentials from Scores(i) and RowMax(i), following the softmax formula."
      RowSum:
        execution_mode: serial
        describe: "Sum the unrounded Exp(i) values along the key dimension."
pipe:
  - "for(i)":
      - "compute:RowMax(i)"
      - "compute:Exp(i)"
      - "compute:RowSum(i)"
```

- `using_verb` 必填，键只能来自上表的八个基础动词；动词下面直接列 noun，不套额外层级。它是**白名单**：pipe 中每个动作必须唯一匹配一个已声明的 `(verb, noun)`，没有声明的动作不成立。
- 只登记本 role 使用的动作族。每个 noun 条目仅有 `execution_mode`、`describe` 两个字段，固定先写前者，二者均必填，不接受 `{}`。
- 声明键只写基名，如 `P`、`Fragment`；实参写在 pipe 和 `waiting` 中。矩阵乘采用操作数表达时，整个 `A@B` 是一个键，使用处写 `matmul:A(i)@B(j)`，不为 A、B 再建登记层，`describe` 须交代两个操作数及结果。

noun 是这个 role 作用域里的对象名称，不是全局数学值或物理分配的登记。不同 role、不同 verb 可以使用同名 noun；`compute:P` 与 `store:P` 各有自己的模式和说明。同名只有在描述的对象、版本及范围一致时才指同一个东西，不能仅靠拼写认定。

- 同一 `(role, verb, noun)` 基名只允许一种固定参数个数；复合动作分别检查各操作数。`P` 与 `P(i)` 不在同一动作族中混用，不按参数数量或常量索引重载。
- 从 pipe 核对全部调用，包括空域和未执行分支中的动作；`waiting` 的引用必须匹配相同动作族及参数个数。
- `A(i)@B(j)` 是否允许、是否要求 `i=j`，由实际数学与索引关系决定，不能从声明键推导。声明不建立循环域、不生成动作，也不改变索引作用域。
- 动作实例由 phase、worker 实例、成员、role、verb、noun 及实际参数共同确定，展开后必须唯一。重复动作要带足够的真实轮次、版本或区域索引；不能靠源码行、控制块位置或未声明的阶段区分同名事件。

##### `describe` 要说明什么

最少要让读者确定「对象是什么、本动作做什么」。上游已经明确的公式、精度、工作范围直接沿用，用普通对象名和步骤名说明对应关系，不重抄整份算法。以下几项无法唯一确定，必须在本条目写清：

- **跨动作的输入**：本动作读取的每个值，连同它的版本／区域／副本，以及来源动作和成员。入口值和跨 phase 输入注明对应来源。本 role 自己的异步产物和控制条件同样要列。
- **存储绑定**：读写已登记存储时点名对应的 `storage` 及其 `view`（若有）。`view` 只定位值及版本所用的区域，`describe` 绑定本次访问。同一个 P 既在 TMEM 又在寄存器时，各动作须明确使用哪个区域。
- **原语保证**：所依赖的完成或可见性保证本身及其适用范围；提供它的原语由 `realization` 绑定。
- **协议与资源含义**：通知或使用资格的含义、对象和参与范围；涉及存储时绑定具体区域。

`describe` 不改写上游的公式、精度或物化决定，也不复述上游已经写下的遍历方向、成员切分或数学公式。上游以 `bind:design.tile_pipeline::<name>` 交给本区的参数，写在决定它的那个动作的 `describe` 里，并使用同一个名称。

数值类型与转换沿用当前 Design 实际采用的值定义，输入输出沿用 Contract。必要的本地对象由创建或处理它的动作在对应 noun 的 `describe` 中说明；必要的存放格式与 metadata / packing 约定在该说明或 `realization` 绑定中定义一次，所有使用者一致引用。

noun 的命名自由不能改变基础 verb 的性质或降低它的 done 保证。`describe` 也不能代替已命名动作之间的必要等待：需要独立引用的部分完成、使用权归还或通知边界，仍使用基础动作与 `waiting` 表达。

动作保留合理的原语粒度：本 role 内部计算、原语自身的完成或可见性保证，以及实现原语的线程协作，不必逐项拆成 role 或边。实际等待图中另一 role 已命名动作的事件，且不能由默认依赖或其他已声明关系推出时，须用 `waiting` 显式表达；不能仅以 `describe` 中的「内部条件分支」加入、取消或移动该前驱。条件改变等待位置用 `if`，不能合法参数化时再按公共规则拆分 dispatch。

#### 执行模式

每个动作有两个事件：`issue` 表示已经发射或开始执行，`done` 表示它承诺的完成条件已经得到保证。`done` 是设计可以依赖的保证，不是测得的硬件时间戳；几个动作可以共享一次完成通知，只要这次通知确实覆盖它们。

所有动作按 pipe 顺序 `issue`。`execution_mode` 约束的是**完成**与后续发起的关系，它声明在 noun 条目上，作用于同一 phase、worker 实例、成员、role 的实际动作序列：

| 模式                | 推进与完成保证                                                                                                |
| ------------------- | ------------------------------------------------------------------------------------------------------------- |
| `serial`          | 自身 `done` 之后，才能发起后续动作；不自动排空此前其他异步动作                                              |
| `async_unordered` | 按 pipe 顺序发起，后续动作不必等自身 `done`；不提供动作之间的完成顺序                                       |
| `async_ordered`   | 按 pipe 顺序发起并允许重叠；采用该模式的动作按发起顺序累积完成，后一个 `done` 覆盖该序列此前动作的 `done` |

`async_ordered` 中的 ordered **只指 `done` 的累积覆盖**，不指发起顺序——两种异步模式的发起顺序都由 pipe 列表决定。累积完成**跨 noun、跨 verb**，并跨循环与 worktile 接续；中间的 `serial` 动作不重置该序列，其他 `async_unordered` 动作不被纳入。不能为每个 noun 暗中建立一条独立的完成队列。

只有原语确实提供上述共同保证时才采用 `async_ordered`。**两个引擎各自有序不等于共同有序**：同一 role 中若存在互不覆盖的完成机制，使用 `async_unordered`，并通过 `waiting` 表达需要的先后。完成依据本身不足时按[缺项规则](../schema_template/README.md#1-确认资料与范围)处理，不靠改模式或补等待假定已有实现提供了保证。累积完成本身不提供操作数就绪、别名覆盖安全或提前归还源缓冲的保证。

role 级与 verb 级都不设模式，也没有默认或继承；本条目的模式适用于它的全部实例。例如 A、B、C 依次发起，A 与 C 为 `async_ordered`、B 为 `async_unordered`，等待 C 的 `done` 也保证 A 的 `done`，但不保证 B 的 `done`；需要 B 完成时仍须有相应依赖。

异步 role 中声明为 `serial` 的动作是同步例外：该动作在 pipe 中的位置发起，完成后 role 才继续，已经发起的其他异步动作可以继续在途。它等待什么由自己的 `describe` 和前驱决定，不默认排空此前的全部异步动作。

```yaml
using_verb:
  store:
    O:
      execution_mode: async_unordered
      describe: "Issue a bulk store of the O slot to global memory."
  release:
    OSlot:
      execution_mode: serial
      describe: "Wait until the store has read the O slot, then return the slot."
```

没有通用的 `@begin` 或 `@read` 事件。需要表达「源存储已经可以归还、目标写入尚未完成」时，用一个有明确原语依据的 `release` 动作，它不能冒充整个写入完成。

特定原语的顺序保证可以代替一条显式的边，例如同一 role 中先发起的矩阵乘读完一块存储之后，后发起的矩阵乘才写入它。依赖这种保证时，在 `describe` 中写明保证本身及其适用范围；不能从 `execution_mode`、同一个 role 名或同一个 noun 名推出硬件会处理冲突。

#### pipe：有序列表与控制流

`pipe` 记录一个 role 在其职责范围内的动作发起顺序，只采用**有序列表**和两种控制结构 `for` / `if`。

当前不支持 `while`；若未来 Agent 确需该能力，须先声明具体需求并提出 issue，讨论是否纳入规范，在此之前只使用 `for` 和 `if`。

`pipe` 是非空有序列表。每项是一个动作字符串，或一个只有单个键的控制节点；控制节点的内容直接是同样的非空有序列表。

```yaml
pipe:
  - "load:Initial"
  - "for(i)":
      - "compute:State(i)"
      - "store:Result(i)"
  - "store:Final"
```

最外层列表描述该角色在 worker 整个生命周期内的动作：持久 worker 在最外层按 `worktile` 域循环，只处理一份工作的 worker 直接写这份工作的动作。准备和收尾直接写在循环前后，不设专用段落节点。

列表决定发起顺序；是否等待上一动作完成，由 `execution_mode`、`describe` 和依赖决定。控制节点不自动产生同步、排空、资源重置或额外事件。动作内部的线程分工和协作沿用动作声明。

##### `for`：有序遍历

| 写法                                | 含义                                        |
| ----------------------------------- | ------------------------------------------- |
| `"for(i)"`                        | 遍历已声明的有序域 i                        |
| `"for(i[1:])"`                    | 遍历该域的半开切片                          |
| `"for(n[t])"`、`"for(n[t,1:])"` | 遍历当前工作的连续序号窗口                  |
| `"for(j=0:2)"`                    | 局部定义半开范围 `[0,2)`，依次绑定 j=0、1 |
| `"for(j=0:min(4,N))"`             | 局部范围的端点使用已定义表达式              |

每次绑定一项，依次发起完整列表中的动作后再进入下一项；完成先后仍按执行模式判断。相邻两个 `for` 是先展开第一批，再展开第二批，不能任意合并成逐项交替。空域产生零项，但不删除后续动作。

`for(t)` 可以遍历上游定义的、运行时才形成的 worktile 序列。领取、确认、发布和终止票处理仍是明确动作，不由循环头代替。不能定义一个「直到成功」的伪域来隐藏局部反馈循环。

例如，上游已定义两组物化值 `U(u)`、`W(w)` 及其范围 `Nu`、`Nw`，只有后者需要 `G`。同一同步 role 先完成 U，再载入 G 并完成 W：

```yaml
pipe:
  - "for(u=0:Nu)":
      - "compute:U(u)"
  - "load:G"
  - "for(w=0:Nw)":
      - "compute:W(w)"
```

一个 role 的两段独立循环写成两个相邻表项，而不是展开成固定索引的动作，也不是新建 kernel。

##### `if`：条件执行

```yaml
pipe:
  - "if(Full(t) == 1)":
      - "release:Staging(t)"
      - "store:Output(t)"
  - "if(Full(t) == 0)":
      - "store:Tail(t)"
```

每个 `if` 在当前位置判断一次：条件为真时执行内容，为假时不产生其中的动作。条件使用已就绪的布尔值、整数比较及 `and/or/not`；必要的读取或等待由相应动作说明，`if` 不暗中增加这些动作。

两个 `if` 没有隐式配对关系。需要互斥分支时，使用同一个在两段之间不变的判断值及其补条件；不能在第一段改变判定，再把第二个 `if` 当成只判断一次的二选一。需要保存判定时，由有明确 `describe` 的动作建立该值。

`if` 表达动作是否存在或实际的协议选择，不用 0/1 假循环代替。已有动作即使没有 payload，仍保留它承诺的 `issue`/`done`；不能因此删除整个动作及必要交接。

##### 索引与作用域

- 循环索引只在对应内容中绑定，不泄漏到后续兄弟项。兄弟循环或不同 role 可以独立使用同名索引。
- 内层 `for` 不得重新绑定仍在作用域内的外层索引。局部范围的索引名也遵守这一限制。
- 遍历 flatten 域会恢复其组成坐标。外层已有的坐标必须与恢复值一致，否则报错，不覆盖或静默筛除冲突项。例如 `for(t)` 内的 `for(n[t])` 可以恢复同一个 `t`；不能由内层 n 将 t 改成另一份工作。
- `count(d)`、`last(d)` 只查询适用的已声明域，`last` 要求非空。动态 worktile 序列没有可预先查询的总长，不能借用循环退出后的隐含末值。

循环域限制循环变量的取值，不限制数学对象的索引范围。例如，上游已定义正整数 `Nc`、初值 `S(-1) = S0`、逐 chunk 递推 `S(c)`，以及 `S_final = S(Nc-1)`：

```yaml
pipe:
  - "load:S0"
  - "for(c=0:Nc)":
      - "compute:S(c)"
  - "store:S_final"
```

首轮计算读取初值 `S(-1)`，不需要一次 `c=-1` 的循环；收尾使用已定义的 `S_final`，不借用循环中 `c` 的隐含末值。反过来，一个只在非首轮执行的动作，不会因为 `Y(0)` 这个数学值存在，就自动产生 `compute:Y(0)`。

「动作不存在」与「动作无数据可处理」不同。空域不产生其内容中的动作；已经由 pipe 列出的动作即使在当前条件下为 no-op，仍有 `issue/done`，`describe` 应写明它不读写哪些数据。不能因为没有 payload 就自行删除其完成事件，也不能等待空域中没有产生的动作。

执行顺序来自 pipe 列表、控制结构、依赖、`describe` 中写明的原语顺序保证，以及上游的工作组织。pipe 中不扩展宏、子程序、跳转或其他控制体系。

### 索引

`index` 在 phase 中为有序索引命名，定义其身份、范围和顺序。每个 `index.<name>` 是固定映射，按 `meaning / definition` 的顺序书写，两个字段均必填：

| 字段 | 值的形式 | 含义 |
| ---- | -------- | ---- |
| `meaning` | 非空英文字符串 | 一句说明该索引表示的对象或迭代 |
| `definition` | 下表中的域定义 | 定义该索引的有序取值域 |

pipe 和索引表达式按索引名引用其取值域。`definition` 只采用以下三种形式：

| 形式                          | 含义                                                                                                     |
| ----------------------------- | -------------------------------------------------------------------------------------------------------- |
| `[lower, upper]`            | 半开整数域，依次取 `lower` 至 `upper-1`                                                              |
| `worktile`                  | 这个 worker 按处理顺序得到的全部工作，包括预分配的和运行时领取的；取值是本地序号，不是全局 worktile 编号 |
| `{flatten: [outer, inner]}` | 把已定义的有序域积按字典序连续编号，后一个域变化更快；内层范围可以随外层取值变化                         |

跨 role 或条目需要共同引用的索引，以及具名 `worktile` / `flatten` 序列，在 `index` 中定义一次；只有一个 role 也可以使用。纯局部整数范围直接写 `for(j=0:2)`，条件使用 `if`；普通参数与判断值不登记为索引。

`view` 的形参只参与版本到槽或区域的映射，局部索引作为实参不要求另建公共索引。范围端点引用已有名称，在实际遍历前须已定义并就绪；索引声明不执行读取、领取或等待。

`worktile` 的长度可能到运行时才知道：`refill` 不是 `none` 时，worker 何时停止由上游的 `exit` 决定，此时不对它使用 `last` 或 `count`。运行时领取本身（例如查询下一份工作，再把坐标交给其他 role）是某个 role 的普通动作，其他 role 进入下一份工作前对它的等待是普通的依赖。

多个 role 使用同一索引定义时，共享编号含义，各自按 pipe 和依赖独立推进。

整数表达式沿用[公共约定](0.common.md#shape-与整数表达式)。本区常用取模 `%` 计算槽位，使用 `count(d)`、`last(d)` 查询已定义的域。

### 片上存储

`storage` 登记 worker 内影响容量、存续或复用的片上存储区域。互不重叠的设计区域可以分列，区域如何合并申请由实现决定。下表中的路径相对于 `storage.<storage_id>`；六个必填字段按 `meaning / depth / location / shape / dtype / total_size` 的顺序书写，没有 `view` 时整条写成一行。

| 字段           | 值的形式                 | 填写条件                                                          | 含义与约束                                                                                       |
| -------------- | ------------------------ | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `meaning`    | 非空英文字符串           | 必填                                                              | 一句说明这个存储区域的用途                                                                       |
| `depth`      | 正整数或整数表达式       | 必填                                                              | 每个持有成员的物理槽数；单槽写 1                                                                 |
| `location`   | 存储层级名称             | 必填                                                              | 沿用 `contract.hardware_specification` 中的叫法，例如 B200 的 `SMEM`、`TMEM`、`register` |
| `shape`      | 有序的具名维度列表       | 必填                                                              | 一个 `worker.unit` 成员持有的一个槽的容量                                                      |
| `dtype`      | 环境中已定义的类型名     | 必填                                                              | 容量单元的类型，与 `shape` 一起确定每槽字节数及 `region` 的坐标单位                          |
| `total_size` | 字节数，整数或整数表达式 | 必填                                                              | 该区域在一个 worker 内的总占用，等于 `depth × 单槽字节数 × 持有成员数`                       |
| `member`     | 成员序号或序号列表       | 只有部分成员持有这块存储时填写                                    | 省略表示 worker 的每个成员各有一份                                                               |
| `view`       | 视图具名映射             | 值名与存储名不同、多个值共用、`depth > 1`，或需要子区约束时填写 | 见[视图](#视图)                                                                                   |

`total_size` 统一以字节记，是 `depth`、`shape`、`dtype` 和成员范围的派生值，须满足上述等式；单槽字节数为 `shape` 各维之积乘以 `dtype` 的每元素字节数。父 `dtype` 只作为容量与 `region` 的坐标单位，不规定各值的数值类型。省略 `member` 时按 worker 的全部成员计数，**不是 warp 数**。容量包含设计所依赖的有效分配粒度，`view` 不重复计量。

单槽存储与所存的单个值同名且无需子区约束时，可以省略 `view`，以整槽作为保守占用范围，各版本依次覆盖。需要跨动作保留或支持重叠的寄存器副本同样登记；普通标量临时量、指令寄存器名和 barrier 存储不逐项列账。

这份账只覆盖已登记区域。影响驻留的额外预留、对齐或实际申请量由 `realization` 说明；各存储层级分别核对容量，多 CTA 的合计不能直接对照单 SM。`register` 区域计入所属 role 的寄存器预算，不再另加一遍。缓冲深度与消费、复用依赖共同限制生产者能领先多少。

`shape` 采用上游的具名轴写法，轴名沿用上游；几种值共用的区域（如 TMEM 中分槽存放 S、P 与 Y，或 K 与 V 轮流使用的环）没有统一的逻辑轴，用 `row`、`column`、`element` 这类物理轴名。它描述一个成员持有的容量，所以不一定等于上游按整个 worker 登记的块：两个 CTA 分摊一块 K 时，每个成员只持有一半。物化子集或 packing 由已有设计、动作或实现绑定说明，所需容量不一定等于完整数学值的元素数乘数值类型字节数。

这里的成员来自 `mapping.worker`，不是单个线程。`location: register` 的形状同样描述该成员内的逻辑值总量，不表示每个线程各有一个同形状数组。

#### 视图

`view` 将值及版本绑定到槽和占用区域，条目仅允许 `slot_index / region`。键是逻辑值名，可以带版本形参，如 `K(n)`、`S(i,d)`。形参只参与该映射，不声明或扩大任何循环，也不捕获 role 的当前循环变量。

| 字段           | 值的形式                 | 填写条件                                         | 含义与约束                                                                 |
| -------------- | ------------------------ | ------------------------------------------------ | -------------------------------------------------------------------------- |
| `slot_index` | 整数或整数表达式         | 父存储区域 `depth` 大于 1 时必填               | 该值的该版本所在的槽，必须落在槽数之内                                     |
| `region`     | 轴名到左闭右开范围的映射 | 设计依赖子区并存、部分数据仍存活或部分覆盖时填写 | 例如 `{column: [64, 128]}`；未列出的轴取整轴，省略以整槽作为保守占用范围 |

**`slot_index` 只写在对应的 view，不设默认推导。** 版本到槽的映射是设计选择，不能从索引名、参数位置或槽数反推。`depth` 只说明有几个槽，`released` 边只说明何时可以覆盖，两者都不决定哪个版本落在哪个槽。`depth` 为 1 时没有可选的槽，可以省略 `slot_index`。

省略 `region` 时，整个槽是该用途的保守占用与冲突范围；不表示较小的值填满或访问全部字节，也不允许据未使用的空间推导额外并发。已有交接保证冲突的读者及在途写者都已结束时，整槽先后复用可以省略精确位置。设计依赖子区同时存活、部分数据仍存活或部分覆盖时，须用 `region` 保留区域约束，或将真正独立的区域分列为 `storage`；省略不得增加全组等待或改变既定的重叠关系。

`slot_index` 与 `region` 的端点可以引用键上的形参及已定义量。`region` 按父存储区域的 `shape / dtype` 选出字节，数值含义来自所绑定的值定义。例如，上游已定义 128×128 的 FP32 值 `S` 和同形状的 BF16 值 `P`，它们共用一个 TMEM 槽：

```yaml
Accumulator:
  meaning: "Hold scores and probabilities in a shared accumulator slot."
  depth: 1
  location: TMEM
  shape: [row: 128, column: 128]
  dtype: fp32
  total_size: 65536
  view:
    S: {}
    P: {region: {column: [64, 128]}}
```

P 的视图选中每行后 64 个 FP32 容量单元所占的字节，用于存放上游定义的 128 个 BF16 元素，不增加分配。这里选中的是**每行的后半段**，不是整块连续的后 32 KiB；容量相等不证明布局合法，`view` 也不执行数值转换。逻辑值的形状仍来自上游；该区域中 S 的必要读取及在途写入结束后才能写入 P。

另一个多槽示例中，上游已定义 128×128 的 FP32 值 `S(i,d)` 和同形状的 `fp8_e4m3fn` 值 `P(i)`；`Stats(i)` 保存每行的最大值和未窄化指数和，形状为 128×2、类型为 FP32。存储同时使用 `slot_index` 与 `region`：

```yaml
ScoreProbability:
  meaning: "Buffer scores, probabilities, and row statistics across iterations."
  depth: 2
  location: TMEM
  shape: [row: 128, column: 128]
  dtype: fp32
  total_size: 131072
  view:
    "S(i,d)": {slot_index: "i%2"}
    "P(i)": {slot_index: "i%2", region: {column: [0, 32]}}
    "Stats(i)": {slot_index: "i%2", region: {column: [32, 34]}}
```

在单槽存储中，`view: {X: {}}` 将 X 绑定到整槽的保守占用范围；空对象不改变 X 的数值定义。没有条目的 `view` 则省略。

**共用字节的值用同一 storage 条目及其 view 表达，容量只计一次。** 覆盖前须保证该区域中旧值的全部必要读取及在途写入已经结束，由依赖或 `describe` 中写明的原语顺序提供保证；view 只声明存储关系。

新分配的存储没有旧读者，不代表内容已经清零；初值来自上游定义和对应动作，例如一个写明不读旧值的 `compute`，或由第一次矩阵乘直接初始化累加器。

### 依赖

`waiting` 按等待的原因分三类，每类的值是**非空的 YAML 字符串列表**。没有规则的分类省略，没有任何规则时省略 `waiting`。

| 分类         | 右侧前驱提供什么条件                                       |
| ------------ | ---------------------------------------------------------- |
| `prepared` | 操作数、计算结果或发布已经就绪，数据可读                   |
| `released` | 旧内容的全部必要读取已经结束，可以覆盖它的存储             |
| `allowed`  | 前两类之外的协议放行，例如两个计算角色轮流占用同一硬件单元 |

`released` 说的是**右侧提供**「已释放」这个条件，不表示左侧动作释放资源，也不要求前驱动词叫 `release`。三类边的约束力相同，分类只保留等待原因。分析依赖环时要合并全部分类以及默认依赖，不能只查复用或协议边；过早覆盖还须沿全部读者与新写入的关系核对。

每条规则写成一个字符串：

```yaml
waiting:
  prepared:
    - "{issue B} ← [{done A}, {done C}]"
```

- 每条字符串只有一个左侧目标事件，右侧始终是非空前驱列表；单前驱也写成 `[{done A}]`。前驱只在完整事件之间用逗号分项，索引内部的逗号不分项。
- 外层 `-` 是 YAML 列表，字符串内部的 `{}` 与 `[]` 是依赖记法。实例须使用 YAML 引号或合规块标量，不能把花括号误写成 YAML 映射。
- 每个事件写成 `{issue 引用}` 或 `{done 引用}`，花括号同时包住时点与引用。**两端的时点必须显式写出**，不接受裸动作端点，也没有位置默认值。
- 动作引用的完整形式为 `Role[member]::verb:noun(indices)`；无索引动作和 `matmul:A(indices)@B(indices)` 沿用原动作记法。可以按[事件引用](#事件引用)省略当前 role，不能省略事件时点。
- `waiting` 条目的书写顺序不表示执行顺序；同一目标事件命中多条规则时，前驱取并集，包括跨分类的规则。

每条规则表示：**右侧所有前驱先成立，左侧事件才允许成立。** 这是先后约束，不要求两个端点同时发生或紧贴，也不保证动作实际重叠。用 A 表示前驱动作、B 表示目标动作，四种组合如下：

| 规则                         | 这条边要求什么                                          |
| ---------------------------- | ------------------------------------------------------- |
| `{issue B} ← [{done A}]`  | A 的完成保证成立后，B 才能发起                          |
| `{issue B} ← [{issue A}]` | A 已发起，B 才能发起；不必等 A 完成                     |
| `{done B} ← [{done A}]`   | A 的完成保证先成立，B 的完成保证后成立；B 可以提前发起  |
| `{done B} ← [{issue A}]`  | A 已发起，B 才能给出完成保证；这条边不限定 B 的发起位置 |

交换 A、B 会改变约束，不表示两个方向等价。需要中间读完、归还或发布边界时，使用有真实 `describe` 的 `release`、`signal`、`store` 等动作，不新增通用的 read/ready 事件。单条 `done ← done` 不能证明动作内部每一片读写都安全，仍须核对分片与必要依赖。

例如，Load 和 Compute 按共享域 `k: {meaning: "Iteration shared by loading and computation.", definition: [0, N]}` 推进；Load 执行 `load:X(k)`，Compute 的 `compute:Y(k)` 读取 X，并保证 done 时已经读完。X 使用两槽缓冲：

```yaml
storage:
  X: {meaning: "Buffer X for overlapping loading and computation.", depth: 2, location: SMEM, shape: [element: B], dtype: fp32, total_size: "2*B*4",
      view: {"X(k)": {slot_index: "k%2"}}}
```

Compute 的 `prepared` 保证值可读：

```yaml
prepared:
  - "{issue compute:Y(k)} ← [{done Load::load:X(k)}]"
```

Load 的 `released` 则保证下一次覆盖同一槽之前，旧值已经读完：

```yaml
released:
  - "{issue load:X(k+2)} ← [{done Compute::compute:Y(k)}]"
```

这两条边分别保护读取和覆盖，不能互相替代；索引移位在边界处的处理见[依赖的索引窗口](#依赖的索引窗口)。

再如 QSA 的搬运角色：先发起下一片，才允许发布前一片的完成保证，但不要求前一片的物理复制必须晚于下一片发起：

```yaml
allowed:
  - "{done load:Kblk(n)} ← [{issue load:Kblk(n+1)}]"
```

#### 默认的依赖

对于同一 phase 内的局部动作，**唯一不写也成立的依赖是：role 内按 pipe 顺序与各动作的 `execution_mode` 推进。** 其余局部依赖都要显式写出，包括操作数就绪、矩阵乘的产物交给谁、动作读了 noun 名字里没有的值、存储何时可以覆盖、协议何时放行。跨 phase 数据交接按 [work_schedule.flow.handoff 的默认等待及 `ready / wait_at` 规则](4.design.work_schedule.md#交接字段)执行。

已由 role 顺序、`async_ordered` 的累积完成或其他边传递保证的前驱可以省略——省略的是可推导的重复前驱，不是必要的就绪条件。

输入与前驱按以下要求核对：

- 每个 noun 的 `describe` 必须逐项列明本动作的跨动作输入，连同版本／区域／副本及来源动作和成员；入口值与跨 phase 输入注明对应来源，本 role 自己的异步产物和控制条件同样要列。
- Reviewer 先对照上游数学与 `describe` 核对输入完整性，再逐项核对从就绪到实际读取的安全保证。允许由执行模式、`waiting` 的传递路径或明确绑定的原语保证覆盖，不要求每一项都有一条直边。

工具对有限事件展开的范围见[微流水线图](../schema_template/README.md#微流水线图)，不以工具已覆盖的部分代替本节语义。

按名称引用要求写法一致：一个值分几次交出，消费者就引用它实际等待的那一部分。例如，动作声明已经定义 P 的 prefix、tail 区域，`matmul:P_prefix(k)@V(k)` 等待的是 `compute:P_prefix(k)`，不必等 tail。区域由 `describe` 定义，不从名称后缀猜测。

### 跨 phase 交接

同一次提交中 `order` 不是 `concurrent` 的几个 phase 由同一个 worker 实例承担：`storage` 合成一份账，在其中一个 phase 登记一次，其他 phase 按名称引用。不同 worker 实例的同名存储分别实例化，片上交接按所属 worker 的对应副本匹配。

两个 role 名称不同，不代表占用不同的物理 warp：物理 warp 按 worker 实例、成员和 warp 编号识别。同一 worker 实例中不同 phase 的 role 可以复用同一组 warp；同时活跃的 role 若成员重叠，必须有可实现的执行关系，不能把同一个 warp 当成两份资源。

跨 phase 的交接由 [work_schedule.flow.handoff](4.design.work_schedule.md#跨-phase-数据交接) 登记。片上交接引用本区的 `storage`；需要点名局部时点时，在 `event` 中定义引用名，上游写成 `<phase_id>.<event_name>`。默认交接、内建事件或已有依赖已经足够时，不重复登记别名。

`event` 的每个条目是一个非空的已有动作事件引用列表。引用时展开列表：用于 `ready / start_after` 时，所有前驱都须满足；用于 `wait_at` 时，就绪约束分别施加到每个等待完成或读取发起事件。通知、可见性与初始化由实际动作及其原语保证承担。

键可以带形参，如 `snapshot_ready(c)`；引用 `snapshot_ready(k)` 时，将 `c=k` 代入列表中的事件。引用只使用这些形参和已定义参数，不捕获某个 role 的当前循环变量。

每个事件须显式写出时点、role 和成员选择，如 `{done MAIN[0]::store:X}`；`Role[*]` 选中该 worker 内该 role 的全部成员实例。别名沿用被引用动作的实例身份，跨 phase 的 worker、工作及索引匹配遵循 handoff 的值、版本和区域关系。

被引用的事件须由 pipe 实际产生。`wait_at` 可引用循环外的 worker 入口动作；工作序列为空时，这些实际存在的入口事件及其等待约束仍保留。`kernel_done` 与 `launch_ready` 是[第 4 篇的无索引内建事件](4.design.work_schedule.md#事件与启动)，这两个基名不用于本地 event；`launch_ready` 的触发位置、条件与参与范围由对应动作的 `describe` 说明。

例如，上游已定义全局物化值 `X`，`prepare` 与 `apply` 由两个保证同时驻留的 worker 并发执行，各只处理一份工作。`prepare` 发布 X 后还有独立收尾，`apply` 先做不依赖 X 的准备，再等待并读取它。工作调度中登记：

```yaml
flow:
  launch: [{phase: [prepare, apply], order: concurrent}]
  handoff:
    X: {producer: prepare, consumer: [apply], storage: global,
        ready: prepare.x_ready, wait_at: apply.x_wait}
```

两侧的同步 role `MAIN` 已有 `store:X` 与 `await:X` 动作：前者写出 X 后以 release 语义发布就绪标志，后者以 acquire 语义读取标志，观察到就绪后才完成；标志在本次提交前初始化为未就绪。本区给这两个动作的完成事件起名：

```yaml
phase:
  prepare:
    event:
      x_ready: ["{done MAIN[0]::store:X}"]
  apply:
    event:
      x_wait: ["{done MAIN[0]::await:X}"]
```

`ready` 指向发布完成，`wait_at` 指向等待完成；消费者此前的独立准备不受这条交接等待约束。

### 固定结构与扩展边界

没有内容的可选字段直接省略。`phase`、`role`、`pipe` 与 `info.using_verb` 必须非空，没有动作的 warp 不建 role；`waiting` 的前驱列表与 `event` 的引用列表均须非空。

| 位置类型 | 本区位置                                                                                | 允许的变化                                                 |
| -------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 固定结构 | `tile_pipeline`、phase 条目、index 条目、storage 条目、视图条目、`info`、noun 条目、`waiting` | 只使用本节声明的字段                                       |
| 封闭取值 | `index.<name>.definition` 的域形式、`using_verb` 的键、`execution_mode`、`waiting` 的分类键、pipe 的控制结构 | 只使用本篇列出的三种域形式、八个动词、三种模式、三个分类、两种控制结构 |
| 具名映射 | `phase`、`index`、`event`、`storage`、`view`、`role`、各动词下的 noun       | 可以增加当前设计需要的名称，条目结构不变                   |
| 开放取值 | `location` 的存储名、成员选择中的执行单元名、noun 名、index 与 storage 的 `meaning`、`info.describe` 及 noun 的 `describe` | 沿用硬件规格中的名称；noun 自由命名但须唯一匹配；说明按对应字段要求填写 |

增加 role、存储区域、索引、事件别名或 noun 是填写实例。新增字段、域形式、事件种类、动词或边的分类遵循[公共扩展规则](0.common.md#结构与扩展)。

## 语法规则

### 成员与名称

成员选择沿用硬件规格登记的执行单元名，写成路径加半开区间：`CTA[0].warp[12:13]` 表示 0 号成员中的 12 号 warp，`warp[0:4]` 表示每个成员中的 0 至 3 号 warp。成员来自上游的 worker 组成，warp 编号在一个成员内从 0 计。

索引与区间端点接受非负整数或[已定义的整数表达式](0.common.md#shape-与整数表达式)，不在成员字符串中引入新定义。例如，当前 phase 的参数已确定 `EPI` 为 4 或 8 时，`warp[3:3+EPI]` 登记实际 epilogue 成员；已确定线程数 `Nt` 且保证被 32 整除时，可写 `warp[0:Nt/32]`。各端点在有效域内必须为整数，区间满足 `0 <= lower < upper`，选择不能超出对应执行单元的实际组成。

决定成员的参数须在 worker 执行前确定，在该 worker 的整个 phase 中保持不变，不依赖 pipe 的循环变量或动作结果。数量变化可以沿用同一份参数化设计，但不能用空区间删除 role，也不能登记最大成员范围再由正文取消部分成员或事件。普通检查核对记法及已知数值关系；参数定义、整除条件与全域约束由审阅核实，有限图工具按显式给定的参数展开。

phase、事件别名、role、存储区域、索引与普通 noun 基名均采用[通用标识符](0.common.md#通用写法)；矩阵乘复合键由两个符合该规则的操作数基名以 `@` 连接，实参写在 pipe 或事件引用中。数学值的名称沿用上游，保留大小写。一个 phase 内只有一个 role 时，它的 ID 统一写 `MAIN`；phase ID 沿用 `work_schedule`，整份设计只有一个 phase 时同样是 `MAIN`。

### 事件引用

完整形式为 `Role[member]::verb:noun(indices)`，连同时点写成 `{done Role[member]::verb:noun(indices)}`。`::` 分隔角色，`@` 只保留在 `matmul:A@B` 的动作内部。省略规则如下：

| 写法                   | 解释                                                       |
| ---------------------- | ---------------------------------------------------------- |
| `verb:noun`          | 当前 role、当前 worker 成员上的动作                        |
| `Role::verb:noun`    | 指定 role，仍指当前 worker 成员                            |
| `Role[0]::verb:noun` | 该 worker 的 0 号成员上的实例；其他成员编号同理            |
| `Role[*]::verb:noun` | 该 role 在当前 worker 的全部成员实例，所选前驱必须全部满足 |

**省略成员下标一律指当前 worker 成员**，带 role 名也一样；当前成员上没有该 role 时，不能自动改取其他成员或全部成员。这里的成员来自 worker 组成，**不是 warp 编号**。跨成员的关系必须写出明确编号或 `[*]`，不根据双方 role 的布局自动改变含义。引用仍须指向所选成员上实际存在的动作。

`waiting` 左侧必须属于当前 role，右侧可以引用同一 phase 的任何 role，包括当前 role；跨 phase 的关系经由上游的 `handoff` 和本区的 `event` 连接，`::` 不提供跨 phase 寻址。

例如，FA4 在两个 CTA 成员各设 LoadQK，矩阵乘位于成员 0，因此明确使用 `[*]`：

```yaml
waiting:
  prepared:
    - "{issue matmul:Q(d)@K(i,d)} ← [{done LoadQK[*]::load:Qc(d)}, {done LoadQK[*]::load:Kc(i,d)}]"
```

源缓冲归还也不必等待目标写入完成。例如，`t` 是 worktile 本地序号，O 只有一个槽；异步 role Epilogue 在每份工作中依次执行 `store:O(t)` 和 `release:OSlot(t)`，release 声明为 `serial`，`describe` 保证存储已读完 O 槽。生产者可以这样等待下一次覆盖：

```yaml
waiting:
  released:
    - "{issue compute:O(t+1)} ← [{done Epilogue::release:OSlot(t)}]"
```

全局写入此时仍可在途。若省掉 release，却只等 store 的 issue，就没有得到源槽可以覆盖的保证。

### 跨工作接续与索引边界

#### 跨工作接续

资源默认跨工作接续：同一 worker 的输入环位置、输出缓冲、统计量和在途操作，各按自己的使用边界衔接到下一份工作，不在每份工作末尾排空。worker 结束前的安全回收由资源与原语承担；只有提前释放，或回收本身改变重叠时，才写成动作。

phase 和 worktile 都不是资源重建指令。同一 worker 连续处理多份工作时，下一份工作的搬运可以与上一份工作的收尾重叠；在每份工作末尾排空缓冲或插入全量等待，会把持久化换来的这部分重叠丢掉。

#### 连续序号

持久 worker 让缓冲和在途操作跨工作接续时，需要一个跨工作的连续序号。例如，每份工作有 `N` 次局部迭代时：

```yaml
index:
  t: {meaning: "Local ordinal in this worker's worktile sequence.", definition: worktile}
  i: {meaning: "Local iteration within one worktile.", definition: [0, N]}
  n: {meaning: "Continuous iteration ordinal across worktiles.", definition: {flatten: [t, i]}}
```

`t` 是当前 worker 工作序列的本地序号，`i` 是一份工作内的局部迭代，`n` 是 `(t, i)` 的连续编号：此前各份工作的迭代数之和加上 `i`，每份工作的迭代数不同时同样成立。实例只维护 flatten 定义，不手写换算公式。

| 写法         | 含义                                    |
| ------------ | --------------------------------------- |
| `n[t,i]`   | 指定工作和局部迭代对应的连续序号        |
| `n[t]`     | 当前工作包含的完整连续序号切片          |
| `n[t,a:b]` | 当前工作中局部索引落在 `[a,b)` 的切片 |
| `n[t,1:]`  | 当前工作去掉首项后的切片                |
| `n+3`      | 连续序号前进三项，可以跨过工作边界      |

绑定 `n` 时可以唯一恢复其 `t / i` 坐标；`t` 与 `n` 出现在同一个动作或同一条依赖中时，`t` 就是 `n` 所在的工作。`n[t,i+1]` 要求 `i+1` 仍在当前工作的局部域内，越界时不进位到下一份工作；`n+1` 则明确跨过工作边界。前者用于「本份工作中除第一轮以外」这类规则，后者用于跨工作接续的环。

#### 依赖的索引窗口

动作的发生域由 pipe 的控制结构确定。依赖先解析两端的角色、动作名称和签名，再对左侧目标动作的发生域实例化：

- 目标因自己的 `if` 为假或循环没有相应项而不存在，该等待没有实例。
- 目标存在，而声明窗口内所需的前驱不存在，是错误；不能通过两端事件集合求交来删掉等待。
- 拼错角色、动作名或签名仍是错误。发生域来自控制声明，不从完成日志倒推。
- 带变量移位的规则按声明的索引窗口逐项实例化，移位后落在域外的那一项跳过；固定索引的引用和窗口内的引用都必须指向实际存在的动作。

窗口来自已经声明的循环域或数学值域，不从实际生成了哪些动作去倒推。例如 `n[t,i+1]` 在每份工作的末轮越过局部域，相应的跨轮规则不在该轮生成，末轮由另一条明确的规则连接。折叠写法中的跨轮依赖也不是同轮回边：是否成环，要看展开后的实例及其真实索引关系。

#### 条件等待示例

索引定义如下，其中 `N>0`：

```yaml
index:
  t: {meaning: "Local ordinal in this worker's worktile sequence.", definition: worktile}
  i: {meaning: "Local iteration within one worktile.", definition: [0, N]}
  g: {meaning: "Continuous matrix multiplication iteration across worktiles.", definition: {flatten: [t, i]}}
```

MMA role 的矩阵乘采用 `async_ordered`，每个 g 依次准备 scale 并执行矩阵乘；Epilogue role 在每个成员上各有一个 `release:Accumulator(t)`。已定义的 `Hoist` 为 0 或 1：为 0 时，非首 worktile 在准备 scale 前等待前一 worktile 的全部 release；为 1 时可先准备 scale，但其首个矩阵乘仍须等待 release。只展开 MMA 中与等待位置有关的字段：

```yaml
info:
  describe: "Prepare scale operands and issue matrix multiplications across worktiles."
  using_verb:
    await:
      Drain:
        execution_mode: serial
        describe: "Drain(t) completes once the accumulator of worktile t-1 has been released by every epilogue member."
    compute:
      ScaleTM:
        execution_mode: async_unordered
        describe: "Stage the scale operands for g into TMEM; reads only values already resident."
    matmul:
      "PayloadA@PayloadB":
        execution_mode: async_ordered
        describe: "Accumulate PayloadA(g) by PayloadB(g) into Accumulator(t)."
pipe:
  - "for(t)":
      - "if(t > 0 and Hoist == 0)":
          - "await:Drain(t)"
      - "for(g[t])":
          - "compute:ScaleTM(g)"
          - "matmul:PayloadA(g)@PayloadB(g)"
waiting:
  released:
    - "{done await:Drain(t)} ← [{done Epilogue[*]::release:Accumulator(t-1)}]"
    - "{issue matmul:PayloadA(g[t,0])@PayloadB(g[t,0])} ← [{done Epilogue[*]::release:Accumulator(t-1)}]"
```

首 worktile 或 `Hoist=1` 时 `if` 为假，不产生 `await:Drain(t)`，它的等待也没有实例；首个矩阵乘的 `t-1` 前驱由声明窗口排除。等待可以提前 issue，release 约束的是 `await` 的 done；同步的 `await` 再约束随后 `compute` 的 issue。`Hoist=1` 保留 release→matmul，不增加 release→compute。原有操作数就绪等依赖及动作声明照常保留。

## 关键原则

### 交付的是约束，不是时间线

本区交付的是依赖和资源约束，不是实测时间线。没有依赖，只表示设计没有禁止重叠，不保证硬件一定同时执行；存在数据边，也不代表存储已经可以覆盖。重叠不另设标记，也不靠书写位置、图中并排或源码相邻来表达；动作仍可能因争用同一硬件单元或编译结果而串行。

### 与上下游的职责边界

数学计算引用 `math_reshape`；工作分配、成员切分、遍历方向和跨 phase 组合引用 `work_schedule`；具体原语与必要的实现预算由 `realization` 绑定。本区只声明局部执行与存储设计，不复写上游定义。

`describe` 只保留特有且影响设计的内容，不是源码说明书；精确的 barrier 编号、寄存器编号、线程地址和普通 lowering 细节不进入本区。
