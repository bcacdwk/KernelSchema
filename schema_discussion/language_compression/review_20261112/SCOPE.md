# 语言精简三项建议的必要性复核

只讨论当前 schema 自身的规则与字段，不修改正式 docs、算子、模板、检查器或提取流程。

用户要求：增加内容须证明它影响设计；删除内容须证明不会丢掉重要设计。目标是在少量语言规则中保存尽可能重要的设计事实。原表中的“不加新模块”是待检验建议，不是预设结论。

## 范围

原表来自 `schema_discussion/language_compression/README.md` 的最后四行。本轮处理其中三项：

| 轮次 | 主题 | 原建议需要接受的检验 |
| --- | --- | --- |
| 1 | 外部等待 | 是否只需在既有 strategy 中保留外部条件、启动/消费点和输出交接；哪些 host 过程能删，哪些等待位置不能改变。 |
| 2 | 组内分工 | member 与短动作契约是否够用；什么分工应留在高层动作，什么独立推进、发布或复用边界确实需要拆开。 |
| 3 | 跨调用状态 | 输入输出、已有状态定义和短复用前提是否够用；删除缓存容量、替换与分配过程是否有反例。 |

**分支复用、局部继承、root/dispatch 设计不在本轮范围内。** 可以读已有分支作为不同算子设计的证据，不评估如何组织、继承或压缩这些分支。

每轮两位新的 `gpt-6-astra / max` 代理独立判断，三轮共六位。主代理只负责指路、组织、整合与材料检查；设计必要性及反证由子代理完成。

## 权威与来源

- `rules/` 是本轮捕获的最新 `schema_docs/0–6`，用于判断现行能力。外部调用边界、flow、storage/index/event、逐 noun 动作声明和新增 meaning/describe 均已有近期修改；旧报告中的缺口不能不经对照就沿用。
- `inputs/proposal.md` 冻结用户当前建议表，保留已划掉的行；它们不重新进入本轮范围。
- 首要证据入口是 `schema_extract/archive/six-operators/20261109-methodology-review/SCHEMA_VERBOSITY.md`。
- 定位具体文字和源码可用 `schema_extract/archive/20261109-ten-operator-text-audit/README.md`、`SCHEMA_DISCUSSION.md`、`SCHEMA_LANGUAGE_GAPS.md`、`gap_review/` 和逐算子报告。
- `inputs.json` 记录当前规则、建议表、调查来源及复用的 corpus。十算子的固定输入与源码路径取自 `schema_discussion/flow_review/corpus.json`；其中旧规则快照不能用作本轮现行规范。
- FMHA、MoE 使用暂停时的 working 输入，不用早期 wiki 稿冒充；已批准、候选、未完成和骨架分别看待。
- 可参考既有 flow/phase/view 研究来定位；新增、删减和“已解决”的关键结论仍须核当前规则及具体 YAML，必要时核固定源码。

## 每份报告的交付

控制在约 120–160 行。开头直接回答原建议是保留、修改、撤回还是已经落实。

1. 逐项区分：当前规则已有能力、实例没用好、仍需短定义、真实结构缺口、来源缺陷、实现细节。
2. 给出具体字段路径及最小修改建议；可以建议零新增字段，也可以在反例支持时提出小量结构，不追求预设立场。
3. 每项增加或删除建议附设计影响与依据。比较前后是否改变工作量、数值/版本、存储身份或范围、执行参与者、必要先后、重叠机会、初始化和复用条件。
4. 至少给一处可安全缩短的真实文字，以及一处不能删除或不能按原表一刀切处理的事实；每项附文件路径、行号和简短解释。证据不足时直接说明，不编造反例。
5. 解释不足不能只靠搬到另一个自由字段解决；判断短说明还是结构更好，要同时计算规则复杂度与实例成本。
6. 可以指出由本主题牵出的邻近字段问题，但不得转向分支复用/dispatch，也不要把完整 runtime 或源码缺同步当成新语言的必然要求。

各代理只写自己编号的报告、证据和必要草图；不读同轮搭档的结论，不再派子代理。记录实际阅读范围，不把机械搜索量当作语义审计量。报告引用当前规则时链接 `rules/`，引用实例与代码时使用固定来源路径。
