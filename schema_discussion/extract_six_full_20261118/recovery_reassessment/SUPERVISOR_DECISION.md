# Supervisor 为何把工具故障推成从 P1 重跑

2026-11-19，独立只读复盘。只新增本报告；未改工具、生产说明、运行状态、冻结材料、稿件或批准，未执行模型、恢复或测试。技术续接机制由另一份独立调查负责。用户授权与当时委派范围按主代理本轮交接理解；以下仓库文档用于核对实现和决策，不把规划文档当作用户逐字指令。

**结论：选择新 run 有真实的实现依据；选择全部从 P1 重做缺少充分依据。** 当前工具确实不能给旧 run 换执行器，普通 resume 也确实会再次撞到同一个 gate。问题是把这一限制直接升级成内容与全部阶段批准必须重建，并在比较方案前用“仅现有公开接口”排除了轻量保进度修复。更早的精简又把当前长任务的执行器修复接续与旧版本兼容一起撤掉，旧 issue 没同步这一能力退化。

## 1. 此次真正失效的是什么

| 已核实事实 | 能推出的处理范围 | 不能推出的结论 |
| --- | --- | --- |
| P6 reviewer 无写入，完整五文件与 checkpoint 一致；gate 用仅含 root 的局部解析集合检查非 root 授权，误拒合法 scope | 修正工具的清单使用，重新满足正式采纳与终审门禁 | P1 的 Contract、P2 的选型、全部 Design 因而不可信或必须重写 |
| 原 `approve` 尚未进入正式 receipt 校验，没有 P6 正式批准 | 保留原 response/result/rejection；后续形成真实当前批准 | 直接补写旧 receipt、清 scope 或把模型原话当作交付批准 |
| root 把三个主数组的 208 个 32 位槽小计写成实际总寄存器数和无 spilling 保证 | 修正 root 的几句局部表述，独立审其完整相关范围并核实际依赖影响，最终新的 P6 | 208 完全无来源，或共享 Contract、代表选择和所有非 root 正文均须重新生成 |
| 源码 31 个文件逐字节一致，原四份完整 YAML 与目录均在 | 完整稿、来源证据、已接受阶段记录是可评估承接的工作 | 只要换执行身份，这些工作就仅能充当无批准意义的阅读资料 |

依据：[P6_APPROVE_SCOPE.md](../P6_APPROVE_SCOPE.md):7–23、38–64；[REGISTER_CLAIM_TRIAGE.md](../REGISTER_CLAIM_TRIAGE.md):15–48；[SPARSE_SUCCESSOR_START.md](../SPARSE_SUCCESSOR_START.md) 的输入核验。

因此，不能把恢复缩成“修 gate 后直接发布”；root 问题真实存在，P6 的原 approve 也没有正确解决它。但目前没有证据要求回到 P1/P2 重新建立任务与选择。具体依赖复核范围由真实定义、批准对象和使用关系决定，不能在此预许“一定只需两三次调用”。

## 2. 当时哪些考虑合理，哪些被扩大了

**合理的部分。** 冻结执行器确有缺陷且公开 resume 无法修复；没有证据时不能把当前整个工作树当作等价旧执行器，其他改动也须纳入实际差异。保留旧快照和原始回执、禁止手改状态冒充成功、保持 Runner 单写者与独立审阅，均有必要。新 run 使用真实新身份、旧稿明示来源、其余五项继续，也是在当时限定接口内可执行的办法。子代理交付的不是虚假恢复方案。

**扩大解释发生在选择候选之前。** [SPARSE_SUCCESSOR_PLAN.md](../SPARSE_SUCCESSOR_PLAN.md):3 把选择组织成“现成新 run”与“只有必须保留 UUID/批准才需迁移”，:86–95 随后要求 P1–P6 全部新建。这遗漏了真正应比较的目标：保留可用工作并完成剩余部分，UUID 是否延续只是实现选择。

| 约束来源 | 实际含义 | 不应扩大为 |
| --- | --- | --- |
| 用户要完成六项、允许修工具/流程，重视简洁、不建旧兼容或庞大系统 | 比较剩余工作与维护成本，选最小可行修复 | 只能调用已有 CLI；任何新接续能力均超授权 |
| 历史证据必须真实、旧快照不可偷换 | 原执行与原审批记录保持原义，新执行记录真实身份 | 新执行身份必须取消所有未受影响审批适用性 |
| 当前 README 要求执行器变化另建 run | 现行产品限制，需要遵守或正式改变实现 | 用户的长期产品要求就是工具每修一次便重跑 |
| 主代理当时要求“仅用现成公共接口，不热改/不造迁移系统” | 子代理在该有限方案空间做选择 | 该方案已与轻量保进度修复比较并证明总成本最小 |
| Reviewer 每次审本阶段有效全文 | 一旦需要派审，不能只看改动几行 | 每次工具修复必须重新派发所有历史阶段的 reviewer 和 worker |

这也解释了为何“仅重做一个算子、其余五项保留”不足以回答效率问题：被忽略的是同一个 Sparse 内部未受影响的阶段、节点和批准。

**成本比较缺了一半。** 原计划详细核对了新资料包、来源身份、输出注册、export、monitor 换 UUID，却没有同等评估修复续接入口与必要复核的成本。对四份设计，标准无返工新路径已有 P1–P4 四对 worker/reviewer、P5 三对和 P6 reviewer，即 15 次阶段调用；续写、回执修复和退修还会增加调用。这是按标准流程估算，非本次实际用量。旧稿作为 source 附件还会形成新 source identity，要求转写引用、重建选择及批准。

上述操作可能是现有接口下的正确执行步骤，但“没有新增代码”不能代表总工作量最小。应比较接下来需要的工程、模型与验收成本；现有完整稿和可保留的有效结论能够减少剩余工作，不只是已经花掉的成本。

## 3. 以前专门设计的续接为何没挡住这次重跑

这不是简单的“忘读一个旧文件”。能力曾存在，后来被明确删除；原则也没有在当前 Supervisor 入口保留下来。

1. **原问题正是本次问题。** [progress-preserving-continuation](../../../schema_extract/issues/archive/extract_workflow/progress-preserving-continuation.json):4 直接批评把“执行器升级、旧结论是否有效、是否重写产物”捆绑；:9–19 记录 2.4.0 已实现默认保进度。旧[连续修订设计](../../../schema_extract/archive/designs/2.4.0-continuous-revision.md)明确“未知不自动回 P1”，并把回执/检查 gate 变化列为定向复核，不先派重写 worker。
2. **20261117 精简确实移除了该能力。** [BRIEF.md](../../extract_execution_20261117/BRIEF.md):8 要保留有价值的恢复、直接更新当前实现、不建旧版本兼容层；[PLAN.md](../../extract_execution_20261117/PLAN.md):36–42 进一步删执行器换绑、continue/revise、predecessor/successor 和旧批准 adoption；[R3_B.md](../../extract_execution_20261117/implementation/R3_B.md):10、36–38 证实实现和执行绑定切换测试均退出。剩余 maintain 仅在同一冻结身份内修稿。不能把旧设计里的命令当当前可用。
3. **产品边界没有分清。** 当时重写 schema/父关系/后端协议，删除旧格式和跨产品版本兼容有合理目的。但“旧格式无需兼容”和“当前格式长任务遭遇执行器 bug 后仍可续接”是两个需求。规划保留了固定执行器内的恢复，却未另列后者的最低能力与验收结果。仅凭这些记录，不能断言用户专门决定放弃后者。
4. **现行文字反而强化了新建。** [Supervisor 手册](../../../schema_extract/README.md):46–54 把 source/config、rules、executor 全固定并写“来源、任务、规则或执行器改变时另建 run”；[tools/README](../../../schema_extract/tools/README.md):94 明确 maintain 不换执行器。给工程调查实际投递的 [monitor_handoff.md](../../../schema_extract/prompt/operations/monitor_handoff.md):3 要求冻结规则或源码变化新建，:5 只强调保留“未受影响任务”；装配点是 `monitor.py:142–147`。这些提示缺少同 run 内保进度与重复成本的决策规则。
5. **看似有恢复提示，实际到不了这一决策。** [recovery.md](../../../schema_extract/prompt/operations/recovery.md) 和 retry/receipt_repair 要保稿，只约束已获准恢复的阶段角色；它们不能改变 Supervisor 是否另建 run，也不能让被冻结的 Python 采用已修工具。[REVIEW.md](../../../schema_extract/REVIEW.md):97 已支持完整候选先审、核批准适用性，但同样受固定身份和实际工具能力限制。
6. **问题台账没有反映当前能力。** 原 issue 仍写 resolved，TRIAGE 也仍列同 run 执行器登记已采纳。归档保留历史决定是对的，但现行入口指向当前手册后，缺少“该能力已随重构退出、当前仍有这一需求缺口”的说明。源码工具 bug 虽 resolved，并不表示这条恢复能力或受阻 run 已恢复。

直接触发是委派与采纳时的方案过窄；长期原因是把冻结身份当作整条 run 的不可调整产品边界，又没有留下正式承接已完成工作的轻量入口。独立全文审阅本身不是问题，也无需为省成本放宽它。

## 4. 最小默认规则与文字修改建议

不新增大 SOP。把唯一决策规则放在 Supervisor 手册；工程交接引用它，阶段角色继续沿已有职责。以下仅为待采纳文本，尚未修改生产文件。

**A. `schema_extract/README.md`，在“恢复与交付”命令表前加一小段：**

> 先区分调用/回执错误、工具缺陷、产物问题与任务或来源变化，保留 checkpoint、证据、有效批准和已用调用账。按实际受影响范围优先续接修复；未知先复核，已完成内容不默认重写。缺少恢复入口时先评估最小工具改动；另建 run 也先判断可承接的稿件和结论，只有具体不可恢复、任务改变或证据失效才扩大重做范围。重复多个已完成阶段前，说明失效依据、拟重复工作及相对续接修复的成本，不另设用户审批步骤。

**B. 同手册“输入与输出”第 54 行的全称新建规则改为准确能力说明：**

> 冻结记录保留当时真实身份，不回写。当前命令不能替换 run 的执行器或导入跨 run 进度；遇到工具修复按“恢复与交付”评估续接能力缺口。需要新 run 身份不代表已有内容和全部阶段结论失效。

来源/任务变化的现有分流仍在总览与 REVIEW。工具补齐接续能力后再更新此处的实际命令，不提前写成已经支持。

**C. `prompt/operations/monitor_handoff.md` 前两句替换并收窄已有重复说明：**

> 定位错误属于调用/回执、工具、产物还是任务变化，核实执行身份与未结调用。按 Supervisor 手册保留进度、判定影响并优先续接修复；没有现成入口时评估最小工具改动，不直接推成从 P1 重跑。
>
> 结论引用具体证据，说明保留和复核哪些阶段、节点与任务，以及恢复或重做的剩余成本。终止未确认继续保持 fence；阶段恢复与 queue 提醒分别处理。

这里改“未受影响任务”为具体的阶段、节点、任务，正好补上本次遗漏，不需要新增报告格式。

**D. 原 issue 沿同一 ID 补正当前决定。** 在 `progress-preserving-continuation` 追加 20261117 删除事实和本次反例，明确目前保留的是固定身份内保稿/维护，工具修复后换执行器续接仍缺。当前 outcome 不宜继续笼统宣称全部 resolved；可用 partially_adopted 保留 2.4.0 历史采纳与验证，remaining 写清现有缺口。本次复盘不是实现修复，不新增“已解决版本”、不另建同根因 issue。

无需在 EXTRACT_SCHEMA、REVIEW、每个阶段页重复整套规则。总览现有恢复导航足够；若后续仍出现把全文审阅等同全阶段重跑的误读，只需在 REVIEW:97 补一句：“先按影响决定是否需要重派审阅；一旦派审，仍覆盖本阶段有效全文。”

## 5. 不能靠 prompt 补上的工具职责

最少需要一种真实的保进度入口：在保留原证据的前提下，让已结清的当前格式任务采用修复执行器并接回实际剩余工作。它可以保留 run ID，也可以建立明确后继身份；选择由技术报告比较，不能预先把它归为庞大跨版本迁移系统。

这个入口须由现有 Runner/冻结身份/批准检查共同实现三件事：记录实际执行器差异；逐范围区分原批准证据、当前适用性与尚未批准稿件；沿已有 checkpoint、维护、依赖核验及调用账继续。未受影响结论有依据才保留，有疑问先审，有实际内容错误才修；新身份不授予额外预算或掩盖旧成本。原被拒 P6 结果不能由 Supervisor 回填成成功。

提示文字只能改变下一次决策顺序，不能让旧 frozen resume 执行新代码，不能让 starter-only 的新 run 自动获得现有阶段进度，也不能使不存在的批准有效。应补当前格式、此次类型故障所需的小能力，不复活旧字段兼容、通用迁移框架或全套旧测试矩阵。

对本次 Sparse，合理待比较的基线是：保留完整四稿与目录、真实来源和调用记录，修 gate 与 root 证据范围，按实际影响完成必要独立复核及新的 P6。扩大重做须有具体不可恢复范围、任务变化或证据失效，并比较剩余修复与重做成本；“当前没有入口”本身不够。当前记录尚未提供全流程重做所需的依据。
