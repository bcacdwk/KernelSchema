# 用户决定：工具故障续接，先完成并留下待审计标记

2026-11-19。以下为用户在 issue 讨论后的明确决定，取代此前等待讨论及前置额外审计的方案；此前调查和候选报告保留为历史。

1. **范围仅为 extract 流程工具自身故障的修复续接。** 本轮不扩展到源码、任务或语义规则改变后的承接。
2. **沿已有前提与进度先走完。** 遇到这类中途工具问题，不因潜在的批准适用性疑问而重新停下来向用户决策，也不默认重跑或前置额外独立语义审计。原稿、原证据、历史批准及已用调用账保留；失败结果不能伪造为已接受，正常流程仍产生真实的当前结果和交付凭据。
3. **留下随 schema 交付的标记。** 明确记录哪个阶段发生什么问题、何处可能需要独立审计，以及继续使用已有进度的事实。标记是未完成审计的知会，不能写成问题已修完或所有旧批准已重新验证。使用交付元数据记录，不增加固定 YAML 字段或改写已审正文。
4. **完成后再汇报，由用户决定是否额外检查或重来。** 暂不执行因 Supervisor 额外调查而增加的 P3/P5 维护或重审；正常流程自身的退修按实际结果处理。Sparse 的寄存器表述疑点等已知待查项明确留在标记中。
5. **其他所有 issue 的后续修改等用户另外指挥。** 现有修复和历史记录保留，不顺手增加新的改动。
6. **立即继续尚未完成的 Sparse 与 FMHA。** 原技术子代理继续负责旧 Sparse 至交付，主代理负责 FMHA 和整体监督；已取消的 Sparse successor 不恢复，不从 P1 另起重跑。

用户原话要点：

> 支持的是工具修复，也就是 extract 流程工具本身发生问题的续接。
>
> 先继续走完，但是给这个 schema 留下一个标记，就是明确说清楚这里之前在 XX 的阶段有 XX 的问题，有一个需要潜在独立审计的地方。
>
> 等结束之后，作为需要知会的事件汇报让用户决定是否再检查＋重来。
>
> 把没跑完的继续走完即可。先走完，有问题打标记，再额外检查，最省事。

执行标记至少包含：算子与运行身份、问题阶段和具体问题、对应证据/issue、沿用的进度和需要知会的审计点、`pending_user_decision_after_completion` 状态。用户这项决定本身是真实续接依据；不得为了满足早先候选接口而编造“已独立审计、确定兼容”的结论。
