# M07 原始使用反馈

## 实际进度

从 AGENTS、DESIGN_SCHEMA 和给定 Contract 开始，阅读 common 的参数/结构变化、DOC 3 的数学接口/绑定/数值、DOC 4 的工作分解/排列/映射/flow、DOC 5 的动作/索引/存储/等待以及模板作者入口。第一次批量读取输出过长被截断，随后按章节重读；这是我的查阅操作问题，不归为规范缺陷。

形成一条实际主路线：一 query 的 16 个头由一个 CTA 在线处理；全局 token 直接分配，页内复用，双槽搬运与计算重叠。写了数学关系、work_schedule 与部分 tile_pipeline；比较了 split-KV、增加 query 复用、head 分组、持久领取与单角色变化。没有读取旧方案，没有任何执行实验；没有完成全域数值验收、硬件原语绑定或完整 YAML。以下问题保留第一理解，不是都已经证明规则错误。

## M07-01：已给 Contract 的硬件词汇足够，能力/容量不足

- 分类：输入问题；尚未解决。
- 场景：想选 FP8 QK、较快 PV 和异步页搬运，并核对 CTA 能否驻留。
- 材料：输入 `hardware_specification.wiki` 全部 pending；DESIGN_SCHEMA §1 要分别核实“能力存在、资源够用与工具链支持”；DOC 2 强调 feature 不代替完整资料。
- 第一理解：SM103、TMEM、异步 MMA 已列出，似乎可以直接设计具体快速矩阵流水。再读后意识到这不提供 dtype/shape、容量、完成原语或 CuTe 接口保证。
- 尝试：用符号工作量和 72 KiB SMEM / 16 KiB 累加器粗预算继续；两个 matmul 暂按 FP32 SIMT 数学路径，原语绑定标为未完成，不推断 FP8 指令存在。
- 影响：路线可以讨论，不能声称可驻留、吞吐改善或实际双槽重叠成立；性能方案停在较保守的数值路径。
- 需要：设备容量、相关算术/搬运原语、CuTe 4.6.1 支持与大致相对代价。未要求本实验补齐调查。

## M07-02：FP8 输入的 NaN 域与 tolerance 接口不清

- 分类：输入问题；未解决。
- 场景：在线最大值和指数递推的有限精度自检。
- 材料：给定 query/kv_cache 只有 fp8_e4m3fn，无 range；out 特意允许任何 BF16 bit pattern；DOC 1 默认 FP32，DOC 3 要按有效分支检查，DESIGN_SCHEMA §2 不允许用“输出有界”替代分析。
- 第一理解：FP8 数据可按有限 ±448 检查。写到中间范围时才意识到 e4m3fn 的 fn 不代表没有 NaN。
- 疑问：Contract 的数学 max/exp 在 NaN 输入上的输出、golden 的传播行为，以及 atol/rtol 对 NaN 的接受方式是什么？仅有引用入口与 tolerance 字符串没有说明。
- 尝试：完成有限子域的界和首轮空状态处理；没有把 finite 限制写进 when 冒充 Contract，也没有读旧 Design 补语义。
- 影响：不能把主路线描述为全 Contract 数值正确；输入缺口不妨碍继续工作划分与槽位依赖草稿。
- 需要：任务方确认有限输入保证，或给出 NaN 语义/验收规则；若确需 golden 细节，也应只读 reference 而不是借旧 Design 决定。

## M07-03：有少/多请求、长/短序列方向，却没有主 workload 权重

- 分类：输入问题；通过明确假设暂时推进。
- 材料：任务要求考虑四类情景；schema_template/README §1：“还需从任务说明取得实际 workload 和优化目标；当前规范尚未确定它们的字段格式”。
- 场景：一 query/CTA 的 KV 复用和少 query 的并行度明显冲突。
- 第一理解：应给四类 shape 设计分支。读 DESIGN_SCHEMA §1“先围绕主要 workload 形成一套具体方案，不急于按 shape 拆节点”后，不知道何者优先才算遵循流程。
- 尝试：明确优先“独立 query 行较多”只是本次自选设计焦点，写四类候选和成本，不发明 shape 阈值，不声称最优。
- 影响：能够选主路线；不能判断应先完整展开 split-KV 还是更大 query tile，也不能定 dispatch 的性能范围。
- 需要：代表 shapes、长度偏斜、吞吐/延迟目标和权重；或者明确允许 Planner 自选主 workload（本实验事实上允许）。

## M07-04：把一 query 改两 query，何时超出“参数变化”

- 分类：文字流程/自身没懂；部分解决，边界未定。
- 材料：common“同规则参数变化”“局部新决定”“新的整体设计”；DOC 4 partition 只登记独立工作维度，允许空工作上界；DESIGN_SCHEMA §5 用独特整体设计判断节点。
- 场景：我的主方案按全局 token tile=1，可直接二分找请求；tile=2 有跨请求的块，不能继续假定共享 KV。
- 第一理解：Bq 从 1 到 2 是最普通参数变化。实际落笔后发现必须改成请求内任务集合，可能需矩形上界+空 CTA，或准备紧凑任务表，工作计数/映射也随之改变。
- 尝试：把“不会跨请求的两 query 工作”保留为候选，未自动分类为参数；如果用矩形空工作，主体递推/协作仍能保留，可能是局部；如果引入任务生成和新领取，可能成为整体方案。
- 影响：数学思路清楚，目录应该记几份完整方案仍拿不准。不是要求现在新增字段。
- 需要：一例明确包含 ragged 工作域变更、且说明局部/整体判定理由的正式例子，或审阅反馈。已有定义能指导，但对我这个边界例子仍需判断。

## M07-05：动作是数学 matmul 还是实现 primitive；可以保守到哪一级

- 分类：文字流程/自身没懂；语义部分解决，实现保证未解决。
- 材料：DOC 5“matmul 的含义来自上游数学，不绑定某个平台的线程组织、布局或完成方式”；同时要求“动作保留合理的原语粒度”，describe 需给出完成/可见性保证。
- 场景：不敢假设 Tensor Core 支持与概率窄化，却要写 QK/PV 的 pipe。
- 第一理解：写 `matmul` 就是在承诺一条硬件矩阵指令；若用 SIMT，就应写 compute。查到上述句子后改用 matmul，说明其 FP32 数学路径与 serial 完成。
- 尝试：没有替 QK/PV 捏造异步执行；保留显式 matmul 以关联数学乘积。Load 的 async_unordered 是设计要求，不是已证实实现能力，已标为待绑定。
- 剩余疑问：一个跨七个 warp 的 SIMT 乘积作为 serial 动作是否已足够“合理原语粒度”，还是必须进一步写协作归约和内部同步？文档说内部协作可不展开，我据此暂认为可，但没有 implementation evidence。
- 影响：片段能表达依赖，尚不等于可实现交付。
- 需要：一个“数学 matmul 由同步协作实现”的简短作者例子，会比再列指令名称更有帮助。

## M07-06：字符串里的名字、局部值和寄存器账写到什么程度

- 分类：固定字段使用/自身没懂；部分解决。
- 材料：DOC 3 symbol 的下游接口必须 shape/dtype；DOC 4 Bk 示例把固定值写入 strategy；DOC 5 describe 要唯一确定跨动作输入、版本、存储绑定，但本地对象允许在 describe 说明。
- 场景：`a/b/q/C/N` 在工作映射中定义，两个 role 各自计算；`m/l/alpha/Uscaled` 来自数学递推；Output 寄存器只是输出写回暂存。
- 第一理解：所有名字都得注册为 symbol/storage/index，导致还没确定流水就似乎要填一串字段；又担心把完整意义塞 describe 会遗漏关键约束。
- 尝试：Bk 按正式示例用 bind→strategy；N 用已定义数学函数作 index 域；为 Locate/Initialize 说明各自读 metadata，不假定 invisible 的共享生产者。对关键 Q/KV/Score/U 写 storage；m/l 与输出寄存器账未补全，明确是片段。
- 实際落笔还把 Q 的 `offset` 误写成源切片字符串 `query[a,:,:]`；回查 DOC 4 数据块属性才发现它是相对 worktile 的数学偏移列表。我删除该 offset，把来源放进 meaning/动作绑定。这处已自行解决，说明只读结构轮廓容易对可选字段作错误直觉解释。
- 仍不确定：哪些 purely local 的中间值可只由动作 describe 建立、哪些既然被另一动作读就必须加 symbol？DOC 3 的“被其他区引用”与 DOC 5 的“本地对象”边界我还需二次审阅。本次未把这种犹豫隐藏为完成。
- 影响：写一个可读片段不难，写到所有名字可唯一解析、同时避免机械重述需要较多往返阅读。
- 需要：对一段完整短 pipeline 标注“此名数学接口/此名局部对象/此名物理存储”的作者示例；未主张新增字段。

## M07-07：split-KV scratch 与调用计量不能从输入推出来

- 分类：输入问题；未解决，未阻断主方案。
- 场景：少 query 长 KV 的独立候选需要跨 kernel 部分结果。
- 材料：workspace_buffer 只有 WorkspaceBytes 与“zeroed before first isolated use”；Contract 计时为完整 standalone callable。
- 第一理解：既然给了 workspace，应能放部分结果。计算每 query `4*S*16*(256+2)` 字节后，没有任何 WorkspaceBytes 下界可证明能容纳。
- 尝试：记出容量公式及读写、launch 成本；主方案完全不用 scratch。没有给候选添加隐式零初始化假设，也没有假定调用可免费分配其他显存。
- 影响：候选能进行数学/分支判断，但尚不能定实现范围或 claiming 容量足够。
- 需要：可用 workspace 下界、允许内部申请的策略或候选调用条件；不能由我缩小原 Contract 来解决。

## M07-08：顺序、覆盖与首尾边界——查阅后自行解决的困惑

- 分类：文字流程；已在当前片段解决，保留阅读轨迹。
- 场景：KV 两槽，Load 超前 Calc；第一次准备写“Load 下一页等上一页计算完成”，又担心把重叠全部串行化。
- 材料：DOC 5 prepared/released 示例、默认依赖、依赖的索引窗口；serial 不排空此前异步动作。
- 第一理解：同名 K/V 或 pipe 顺序可能自动足够；以及 `i+2` 末尾不存在会不会让规则非法。
- 尝试：明确值就绪为 `QK(i) <- loadKV(i)`，槽归还为 `loadKV(i+2) <- PV(i)`；依赖按声明索引窗口实例化，首两页无旧值，末尾超域不生效。Calc 串行顺序已经覆盖 ScoreSlot 的下一轮覆盖，不增加重复边。
- 结果：能手工走 N=1、N=2、N=3 的首/稳/尾关系；没有工具执行。`allowed` 没有真实协议需要，省略，不为了覆盖所有分类而发明动作。
