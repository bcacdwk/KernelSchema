# M08：Reviewer 使用提示时的实际问题

仅记录本次读提示、审当前 M06 DRAFT 和定向查源码的经历。没有读 worker 的 ISSUES；不把下面全部项目称作规则缺陷。

## M08-01：P2 的正式前提与这次手工输入不一致

- 分类：输入不足／任务特例，已按本次授权解决。
- 场景与位置：P2「准入与应读材料」写“P1 的任务元数据和共享 Contract 已通过”；REVIEW「各阶段覆盖范围」要求 P2 独立审 P1 已完成内容。M06 DRAFT 开头却说没有完成或通过任何阶段，且只有事实摘要。
- 当时理解/尝试：最初不能把自己当正式阶段 reviewer 放行，但也不能因 P1 未通过就停止本实验。我回看委派中“不要求补做完整 P1/P3”的范围，用 reference/input 的有限核对支持候选判断，并明确没有正式 P2 批准。
- 后果：不能把本次意见转录成正式 approve。建议实验结果显式标注“候选评议”；这是当前输入与正式流程不同，不要求改 schema 固定字段。
- 工具要求检查：P2 明文说“不因它尚未完成要求完整 YAML 检查通过”；EXECUTOR_ALIGNMENT 明文说当前 CLI 不能端到端运行新方法。我没有遇到仍必须先运行 checker 才能手工审候选的现行要求。

## M08-02：REDF 的“局部差额足够”与“新输出主体”仍需要人工裁量

- 分类：自身最初未明／文字判据的裁量边界；不据此断言规则漏洞。
- 场景与位置：M06「拟代表」对 REDF 犹豫；common:114–126 允许围绕已有值/step/role/storage 记录局部联动，也说重新贯通主要输出形成应作整体；REVIEW「完整设计的保留与降级」要求说明为什么差额不够。
- 当时理解/尝试：我最初看到“epilogue 替换 + memset + convert”，确实可以用很短差额说完，不能用长度决定。随后只读 C:3948–3987、8234–8262、9164–9192、9329–9338、1687–1703，确认原子前 BF16 边界、共享 accumulator 的 token 归属、清零汇合和最终生产者。
- 结论与影响：选择完整保留，因为替换了 route 归并的主体协作，不能靠给新 epilogue 对象命名隐藏全部输出收集关系；相对最近 cfg99/44 基线评价，避免把 G2 WS→mono 混算成 REDF 价值。现有规则提供方向，但“短差额也能文字说清”不等于“局部”，这一实际边界容易令 reviewer 反复犹豫。
- 最小建议：若增补示例，可用本例展示“接口外主体是否仍成立”的反事实判断；无需先增加字段。

## M08-03：ZERO2 的本次 host 条件提交找不到现有表达

- 分类：可能固定字段/语义变化；尚未找到现行解法。
- 场景与位置：C:9471–9491 实际先 launch clean，host spin，只有观察非 1 才 launch full；outer capture 只记录两图。DOC4:243–259 只有 step/order/start_after 且每 step 一次，DOC4:395 禁止说明字符串条件删边；common:112 允许本次 Clean 控制必要动作；DOC5:286–301 的 if 仅作用于 role pipe。
- 当时理解/尝试：我先怀疑草稿把“启动依赖”与“条件存在”混淆；重读字段表、调用边界和 if 后，确认 start_after 只能表达等待，不能表达不提交。也考虑只列 full 并给零工作，或拆 clean-only/full 若干 when；前者不忠实实际提交，后者没有承载 host 本次 verdict/timeout 决策，而且 when 不是隐式调度优先级。
- 后果：无法独立批准草稿 ZERO2 完整表示，也不能伪造 host CUDA worker 或自添 guard。这个疑点已超过单纯 worker 不会写的泛泛抱怨：有具体源码反例和字段限制。但我没有穷尽证明所有合法表示不可能。
- 最小需求：由规范维护者给现有字段的可审表达，或讨论具条件存在性及其事件/交接含义的提交表达；仅添加一个未定义语义的布尔字段并不够。本次只报告，不修改规范。

## M08-04：候选标签掩盖已经选中的混合机制

- 分类：worker 草稿缺项／评审输入组织问题。
- 场景与位置：M06 选“packed WS split-K 主链 cfg99/44”，又把“单体 FP4、BF16/warp MMA 族”整行列作未充分研究。C:8234 附近 cfg44 直接实例化 mono f4_body，cfg99 的 WS G1 与其配对。
- 当时理解/尝试：初读名称容易把 split-K 当作整链都 WS，进而认为 mono 是全新未收录机制。我沿 G2 cfg44 追到 C:3053、3531–3718 的 CTA 同步主循环，才区分“G2 mono 已有候选承载”和“整条 mono/BF16 方案还未审”。
- 后果：若按族名计数，会重复增加完整候选；反过来若只看 root→split-K 的 K 轴，则会漏掉另一个主协作机制。需把每个真实实例的 G1/G2 与输出组织分别说明，最终仍按端到端方案决定文件，不要求新固定字段。

## M08-05：正确的两条 pipe 边容易被扩大解释为关键关系都已交代

- 分类：片段输入的能力边界／自身最初不确定，现行规则有解。
- 场景与位置：M06「可表达的普通局部依赖」仅两个 released 等待；DOC5:326–350、610–652 定义 worktile/flatten/窗口，DOC5:185–216 定义动作完成与跨 noun 累积保证。
- 当时理解/尝试：最初想判“缺整个角色和动作表，所以不可审”，但草稿明示这是局部示范，本次不是 P3。我改为逐条核 C:4628–4660、4950–4968，只判断它解释的 operand ring 复用。flatten 跨 item 的写法正确，不能要求退回每 item 的 i。
- 后果或缺口：这不证明 prepared、accumulator→epilogue→下一 item、CPHOIST、TSTORE sink 等关系完整。把“P2 可理解”与“P3 正式定义足够”分开，既不误批，也不无端补做 P3。无需规则新增字段。

## M08-06：调查止点不能只继承 worker 列出的下一步

- 分类：worker 机制概览缺项；现行调查规则能够处理。
- 场景与位置：M06 末尾下一步只有 REDF、单体/WS 与 ZERO2；但 C:9299 的 `cfg != 31 && cfg != 32 && cfg != 88` 已提示部分 SK 不提交独立 act，C:8031–8062 给真实 cfg88 入口，C:5270–5309 给 last-arriver 归并。
- 当时理解/尝试：我本来只准备解决草稿显式留下的 REDF；读 run_pipeline 时发现这个排除条件，于是定向追 FUSE epilogue，看到它在 s_epidone 后 fence/ticket/归并，作用到跨 item 进展。
- 后果：不能宣布 P2 的重要疑点只剩草稿三个清单项。新增 cfg88 的机制与去处待决，不因此展开所有分支或强制再造完整文件。P2「调查止点」的“实际入口、输出归属、完成、跨工作寿命”已给出充分继续依据，问题不在缺少规则。

## M08-07：root 示例的 selector 算术与设计保证容易混读

- 分类：自身阅读边界／草稿范围待落实。
- 场景与位置：M06 用 fixed_3 的 G2 下界算术支持 cfg81 可达，并提醒 P3 固定 when；S:1250 附近先用 R 的界判断是否 host readback，common「选择条件与索引」区分 selector 阈值、样本与设计范围。
- 当时理解/尝试：最初容易把 `ceil(R/128)` 看作整个 Contract（含 masked/empty route）的实际非空 M tile 下界。回看 S 中行为与草稿的“非零、skewed 可达说明”，它最多支撑特定 selector 决策，实际 counts/map 仍按当前有效路由生成。
- 后果：本次不因示例非完整 when 而要求补 P3，但不批准该算式是所有输入的工作量保证；后续需固定机制与必要条件。common 已有区分规则，不是新增字段需求。
