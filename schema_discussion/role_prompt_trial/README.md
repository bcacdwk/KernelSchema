## 采集对象与边界

- 设计者从 DESIGN_SCHEMA 与给定 Contract 开始，尝试形成方案、调度/微流水线片段及分支判断
- 提取者从 EXTRACT_SCHEMA 和源码开始，做到 P2 机制识别与代表判断；最后一个样本由新 reviewer 独立评审前一份 MoE 草稿
- 不要求完整提取或完整设计交付，不运行 Python 提取器、checker、GPU 或正式测试
- 鼓励记录不理解、找不到、两种读法、输入缺口及临时假设；不要求 medium 代理先证明规则错误
- 固定字段的增删、类型、封闭取值、必填/默认、引用或执行语义等实质变更只列 issue，交用户决定
- 文字、导航、已有语义的解释、流程与职责说明可以由后续 MAX 代理直接修订，不改代码、原算子 YAML、输入数据或运行状态

## 每人的交付

在各自目录保存两份短文件：

- `DRAFT.md`：当前实际做出的方案/机制判断、拟保留和降级的分支、必要的小段调度或 pipe 试写；可以不完整，明确未解决处，不冒充可交付完整 schema
- `ISSUES.md`：阅读起点、读过的材料、做到哪里；逐项记录实际卡点及最终仍不明白的事情，保留最初误读与后续自查结果

每项原始问题使用本人的前缀编号，例如 `M01-01`，尽量包含：发生在什么具体选择/字段；相关文档位置和短片段；当时的两种理解或无法继续的原因；已经尝试怎样查清；暂用什么假设；需要说明、材料或字段变化中的哪一种。不懂本身可以登记，不能为凑数凭空发明问题。

已有工具尚未实现新规范是实验前提；如果文字仍迫使角色必须先运行未适配工具才能思考，应记录具体阻碍。输入信息不足与文档缺口可以暂时分不清，后续核实，不偷改给定 Contract。

## 两轮 MAX 处理

第一轮两个代理分别负责作者/schema 侧和提取侧，均读取全部 8 份原始观察，核实、去重并在互斥文件范围内修订文字。每个原始编号须有去处：已修、现有规则可解释、输入问题、未证实，或固定字段待用户决定。

第二轮一个 MAX 代理对合并后的问题与实际改动作独立复核，处理交界重复和剩余文字问题。最终汇总统一列出已改内容、未采纳理由、保留的字段议题与适用边界，不以“medium 代理理解错了”自动否定其暴露的说明问题。
