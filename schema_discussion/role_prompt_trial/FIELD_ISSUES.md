# 固定字段与语义核实

本页区分“已有字段怎样填写”和“改变规范接受内容或解释结果”。原始编号、归因及证据入口见 [ISSUE_REGISTER](ISSUE_REGISTER.md)；A/B 的独立意见仍分别保留。**本轮没有实施下面两项规则变更候选**，也未新增字段、封闭值、默认值、条件事件或引用豁免。

P1 在已有 `hardware_specification.execution` 中最小登记有据执行单元，属于本轮已明确授权的流程修订，已落地文案，无须再次批准。它没有同时解决设备规模来源。其他能按现有结构表达的事项列在后半部分，不要求用户重复批准正常填写。

## F1：固定实现中的动态设备规模能否直接以源码查询为来源

原始编号：**M02-04**。C 另在 MLA 的现有草稿及源码核到同类用法，作为影响范围的佐证，不追加原始编号。

### 当前规则与案例

- [DOC2 具名映射](../../schema_docs/2.contract.hardware_specification.md#具名映射)只让 execution 记录执行层级、组成及资源作用域；设备级数量和容量属于 `wiki.hardware`。
- [DOC2 引用格式](../../schema_docs/2.contract.hardware_specification.md#引用格式)要求 wiki.hardware 绑定具体型号的完整资料文件，使用能解析的 `repository@ref:path`；pending 不构成绑定。其完整资料要求没有因字段值是字符串而消失。
- [DOC4 核心思想](../../schema_docs/4.design.work_schedule.md#核心思想)规定设备规模这类数值来自 hardware 绑定的资料。`mapping.strategy` 可说明映射关系，并未豁免这项来源要求。
- [P1](../../schema_extract/phases/01_contract.md#第-3-段硬件占位)现在只最小登记 execution，其余字段仍保留 starter 占位、不展开硬件资料。C 补明既有引用/来源规则仍有效；已有源码事实无法合规表达时按框架问题定位受影响范围。

实际 [GEMM solution.py](../../kernel_wiki/aka-cuda-operators-20261030/operators/gemm/grouped/fp8_scaled_grouped_gemm/candidate/solution.py):126–129 在 `_Engines.__init__` 调用 `torch.cuda.get_device_properties(0)`，将 `multi_processor_count` 缓存为 `self.nsm`；[fp8gg.cu](../../kernel_wiki/aka-cuda-operators-20261030/operators/gemm/grouped/fp8_scaled_grouped_gemm/candidate/fp8gg.cu):340–344 用它把 grid 限制为不超过 `2*nSM`，且至少一个 CTA。查询发生于初始化，不能描述成每次 launch 都重新读取。

MLA [solution.py](../../kernel_wiki/aka-cuda-operators-20261030/operators/mla/mla_expanded_fp8/candidate/solution.py):2001–2008 也查询 `cudaDevAttrMultiProcessorCount`，据 nsm_l 选择 grid；源码另含 fallback=148。这个常量只是来源行为，不是本规范已给的设备数量或默认值。

### 核实判断

**已有字段能表达查询方法与动态值关系，但当前材料/流程没有提供合规绑定。** 如果一个符合 DOC2 要求、已固定版本的具体设备资料文件说明相应数量或合法查询方法，并能核对设备身份、查询含义与软件接口，那么 mapping 可引用该资料，在既有 strategy 中定义 nSM 的关系；不必增加数值表、`device_query` 或新的硬件字段。动态查询不必被改成硬编码常量。

当前却没有这样的硬件资料绑定。单把源码赋值写进 strategy、用 math 的外部 binding 指向源码，或把 `multi_processor_count` 称为“方法名”，都不能绕过 DOC4 的设备规模来源约束。将一个只有查询代码的文件冒称具体型号的完整硬件资料，同样不满足原规则。最小 execution 登记与 `--skip-hardware` 均不补齐这条依据。

### 候选方案与取舍

| 方案 | 具体做法 | 影响 |
| --- | --- | --- |
| A．保持来源语义，补齐既有资料绑定 | 取得符合 DOC2 完整性要求的具体设备资料，必要时在其中补充数量/查询方法和对应接口依据，填入现有 wiki.hardware，再由 mapping 引用；提取流程仅对实际提供的材料作相应调整。 | 不新增字段或改变来源语义；但当前“不展开硬件资料、其余入口占位”的提取流程没有该材料，不能将此方案写成已经完成。不是只补一个孤立 nSM 摘要即可。 |
| B．为固定实现提取开放受限的源码查询来源 | 允许 mapping 在既有说明字段中按固定源码声明设备查询、被查询对象、发生时点/缓存寿命及数值使用位置；只保留该实现实际使用的表达，不由它推断容量、ISA 支持或驻留保证。 | 无须新增固定字段，但须明确修订 DOC4 的来源约束和提取政策，是语义选择。其关联审阅与未来工具支持也需同步，不能先靠说明或 skip 参数临时采用。 |

**推荐：**若继续维持“不展开整套硬件资料”的固定实现提取目标，讨论采用 B；已有完整且匹配的硬件资料时 A 足够。字段名称和类型本身不构成缺口，不推荐仅为 nSM 增加一套结构化查询字段。

影响范围是依赖这些数量的完整 `mapping.worker_count`、相关 selector 事实及其来源闭合；GEMM 与 MLA 已有具体案例。执行名登记、独立数学事实和限域候选评议可继续，不能因此声称整个 work_schedule 已完成，也不将问题扩大为必须补查全部硬件能力。

## F2：是否让单份完整 Plan 表达 host 观察后的条件提交

原始编号：**M06-01、M08-03**。这是 worker 与独立 reviewer 的两个原始观察，合并后仍保留各自来源。

### 当前规则与实际反例

[DOC4](../../schema_docs/4.design.work_schedule.md#提交身份与字段)的 `flow.launch` 枚举实际计算 kernel 提交，每个 step ID 在一次计算执行中恰出现一次；`start_after` 只约束启动时点，说明字符串不能删除工作或替换生产者。[DOC5 的 if](../../schema_docs/5.design.tile_pipeline.md#if条件执行)控制 role 内动作，不控制 host 的图提交。common 允许本次验证状态控制必要动作，但没有据此定义 flow 级分支；`when` 也只限定某份设计的范围，不执行整个选路算法。

MoE [nvfp4_moe.cu](../../kernel_wiki/aka-cuda-operators-20261030/operators/moe/nvfp4_fused_moe/candidate/nvfp4_moe.cu):9471–9491 的 ZERO2 路径将 pinned verdict 设为 -1，先提交 clean 图，host 有界轮询；只有观察值不是 1 时才再提交 full 图。full 自身带另一次 verify（9157–9159），两次求值不能共用同一个 step 身份。`cudaGraphLaunch` 是图提交调用，一个 full 图内部仍有多次实际计算 kernel 提交，不能把整个图冒称一个任意 flow.launch 条目。

| 情形 | 实际提交事实 |
| --- | --- |
| host 观察为 1 | 只提交 clean 图中的 verify；它扫描并写出零结果。 |
| host 观察为 0 | clean 图后再提交 full 图；full 中的第二次 verify 与后续链实际存在。 |
| host timeout | 同样提交 full 图。即使随后验证为 clean、链内动作按 ZGUARD 退出，也不等于这些 kernel 未提交。 |
| outer capture | 当场记录 clean 和 full，不等待 verdict；之后重放这个外层图时是固定的两图结构。录图不能记作当场已完成计算。 |

固定列出 full 会多报观察为 1 的路径，省略则漏报 dirty/timeout；提交零工作与根本未提交也不同。把 host 冒充 CUDA role、用 start_after 代替是否存在，或让 when 隐含完成本次轮询选择，均没有既有依据。这里确有一层尚未定义的控制能力，不能仅用字段名看似足够来宣布解决。

### 当前目录分工能保存什么

现行规则并未要求把所有有价值机制都丢掉，或先为每条路径新建一份 YAML：

1. 选定的固定 full 图、固定外层重放结构等，在各自完整、来源可核的范围内，可按现有 flow 表达；源中 verify 的输出、副作用与 ZGUARD 必须保留。
2. 目录可以说明 clean 图与 full 图各自工作、两者的实际组合/调用关系、观察/timeout 触发和成本；有当前完整基线时直接定位它，只有未来正文时仍标为计划。
3. ZERO2 的 host 决策改变实际工作和输出形成，是有价值的独立机制。若未完整展开，可在 common 规定的“范围”中作为已研究但未完整展开的独立候选说明，保留真实原因；不能为凑数量改称无关包装或普通参数。只有确实由既有相容决定构成的差额才按“组合”正式记录。

这条目录路径可以满足保存选定固定方案及其他设计知识的目标，**不能声称一份 YAML 已完整表达整个 ZERO2 数据相关提交算法**。目录也不能补齐完整 YAML 缺失的控制语义。若任务明确要求 ZERO2 本身作为完整 Plan，现行路径仍不满足该要求；若只要求有限完整集合与有价值候选去处，则无需为使用已有目录能力再次批准。

### 候选方案与取舍

| 方案 | 具体做法 | 影响 |
| --- | --- | --- |
| A．保留当前语言范围 | 完整展开选定、可表达的固定方案；目录保留 ZERO2 两图关系、独特控制价值与未展开限制，继续遵守十份上限及真实完整身份。 | 无字段变化，不把所有候选都变成完整 YAML 义务；无法满足“单份完整 Plan 覆盖整个 ZERO2 host 算法”的额外目标。 |
| B．增加有明确语义的条件提交 | 讨论 flow 中的条件 launch 或受限分支区域，用于本例的固定前缀加有条件后续提交；与现有 role if 分层。 | 扩充固定结构或控制解释。需同时定义条件的生产/host 读取/稳定版本、求值时点和 timeout、未提交时的 step/事件实例、输出覆盖、handoff 与等待，以及 capture/replay 身份。仅增加一个布尔 guard 不足以形成完整语言。 |

**推荐：**当前有限设计目录可以先采用 A，保存有价值的控制事实；只有确定要把整个 host 提交算法作为一份完整 Plan 的表达目标时，再采用 B 并设计相应事件与数据语义。现有反例没有要求引入任意 host 程序、无界 while 或通用控制流语言。

### 源码 mirror 风险与语言能力分开

verify 会写同一个 `zflag_host`（1707–1793），full 图的第二次 verify 也拿到该指针；dirty/timeout 后，host 提交 full 即可返回（9471–9491），未在这里等待其 mirror 写入结束。若调用上下文允许前一 replay 的迟到写入发生于下一次 host 重置 -1 之后，下一次轮询可能读到旧 verdict。源码的“重置发生在 launch 前，所以永不陈旧”注释本身没有排除该次序。

本轮没有完整核实固定调用环境是否排除了这种跨调用次序，也没有运行竞态复现。这里保留具体的版本/复用风险及所需证据，不能宣称源 kernel 已被证实在全部调用中错误或正确。即使未来新增条件提交字段，也只是能够描述选择；它不会自动给 mirror 添加代际身份、等待或隔离，不能作为源码正确性修复。

## 采用边界

所有现有字段的具名实例填写、普通文字修订、参数/局部/组合记录和已授权的 P1 最小登记都可按当前规则继续。本轮仅把 F1 的来源放宽与 F2 的新增控制能力留为规则选择；不把输入确认、算法设计或未完成源码调查混成字段变更审批，也不预先实施任何候选。
