# While 必要性研究方法

本研究判断的是设计级 pipe 是否需要 while，而非源码能否出现 while。当前规则仍在上级 README；本研究不直接修改它，也不迁移算子。

## 核心问题

1. 现有 Kernel 的 while 分别是有限遍历、工作领取、原语等待／重试，还是动作之间的反馈？
2. 对合理、语义明确的算子，是否存在必须在 role 的多个设计动作间表达的反馈循环？
3. 删除 while 后，for/if 能否保持动作发起、完成与交接关系，并保持描述自然、简短？
4. 当前样本无需 while，能否支持当前语法删除；它与“所有合理算子都不需要 while”有什么区别？

## 统一判据

- `for` 可遍历输入／元数据定义的有序域，也可遍历上游工作调度实际提供的动态 worktile 序列。不能凭空定义“直到成功的所有轮次”来把本地反馈藏进域定义。
- 条件必须已经可用；读取、计算、通知、等待不能隐藏在 while/if 条件求值中。
- 原语内部轮询、CAS 重试、线程级算法步骤不自动变成 pipe 动作。反过来，已经独立发布、交接、释放或跨 role 协作的设计边界，也不能为了删循环塞进一个不透明大动作。
- 区分：有自然有限域、有真实迭代上限但提前停止、没有可用的有限上限。硬件有限状态空间或任意巨大的 cap 不算有意义的消去方法。
- 比较改写时分别判断：算子结果与退出行为；设计动作及事件轨迹；额外状态、重复条件求值、跨角色交接；可读性与实际控制开销。只证明有限样例轨迹相同不能声称一般等价。
- while 的存在本身既不证明死锁／设计缺陷，也不证明该语法应该进 pipe。每个例子须给出所在抽象层、进展依据和正常退出条件。
- 允许提出移到 work_schedule 或动作契约的解释，但须证明这是该职责本来所在的层，不能只是挪走未解决的反馈。

## 材料与交付

首先分析十个 trial 的固定源码、对应 baseline 与现有算子分支；再从更广的合理算子与公开实现寻找强反例。逐例记录路径、位置、循环控制来源、循环体关键动作、结束／进展依据、替代表述、结论及证据限制。

前四份报告分别调查四模板、六提取算子、正向反例及 for/if 消去能力；后续用新的代理做独立复核与取舍。最多两个子代理并行，均使用新窗口、max effort。没有运行 GPU 的计划。

新文件全部放在本目录。原始 Kernel、正式 schema、既有 trial、上级 README 和已确认 verb／waiting 规则保持现状；主代理最后提供入口与精炼结论。
