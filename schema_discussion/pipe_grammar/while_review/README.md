# Pipe 中 while 的必要性研究

**决定已采纳：当前核心 pipe 只保留有序列表、`for`、`if`，`while` 不属于规范语法，本研究单独保留作为重审依据。** 已核对的实际路径没有形成必须保留它的需求；几个最强的跨动作反馈候选，也找到了有根据的有限表述。

**不能据此说“良好定义的算子不应该有 while”。** 源码中的等待、哈希探测、调度和求解反馈都可以合理。这里取舍的是设计级 pipe 的控制形式，不是禁止 Kernel 源码使用 while。

研究阶段只交付材料与建议；后续已按用户决定更新[正式语法](../../../schema_docs/5.design.tile_pipeline.md#pipe有序列表与控制流)。未来 Agent 如确需 while，须先声明具体需求并提出 issue，再讨论是否纳入；此前只使用 for/if。本次未迁移旧 trial、检查器或 Kernel 源码。研究期间仓库另有文档提交，版本边界见末节。

## 结论依据

| 实际情况 | 判断与证据 |
| --- | --- |
| 输入长度、KV 块、chunk、分量与状态递推 | 轮次来自已有输入域，状态依赖前一轮不等于继续条件也依赖计算结果；用 for。四模板与六提取 root 的实际选择路径已回查。 |
| QSA／MLA 票据、MoE scheduler、CLC 工作接管 | 有真正的运行时领取和跨角色反馈，但任务单位、分配器与终止协议本来就属于工作调度。可用动态 for；领取、确认、归还和终止票不能省掉。 |
| barrier 轮询、Sparse 位置发布等待、Hash 探测 | 等待可能没有有限次数上界，不能用固定重试次数代替；它们属于 await/acquire 或已有局部协作算法。没有因此要求 pipe 展开每次轮询。 |
| CUDA cooperative CG | 每轮有 SpMV、归约、grid 同步和残差反馈，属于真实设计边界；源码本来有 10000 次 cap。缓存残差稳定后，for+if 可保持活跃动作与原有成功／失败判断。 |
| Galois persistent BFS | 下一 frontier 由当前计算产生，不能假称它是事先给定的轮次域；但有包含末次排空的顶点数上界，可用 for(V)+if。 |
| Galois persistent SSSP | 专项证明在列明的算法执行契约下，outer≤V、每个 inner≤V，均包含末次通知排空。保持原 frontier、三队列、双 counter slot、屏障及 delta 更新，不换成另一种算法，也不需要 Wmax 扫描。 |
| PyTorch Gamma 拒绝采样 | 没有接受次数 cap，但反馈在线程局部计算内；自然属于 compute。它反驳“无 cap 就是坏算法”，不构成 pipe 必须暴露 while 的实证。 |
| Galois Delaunay／MIS | 已核对实现的外层反馈位于 host 的多次 kernel 提交之间，不是单个 role 的 pipe。加一个 pipe while 也不能替代跨 kernel 编排。 |

十个 root 的结论有源码控制来源与动作边界依据，不只是“现有试写没有 while”。更广 Wiki 的筛查和公开候选也没有被当成全世界算子的穷尽证明。CG／图算法的跨 grid 控制投影还要求明确联合 worker 的成员范围；若把各 CTA 视为独立 worker，添加 while 本身不能提供跨 worker 事件寻址。

## 最强未决项得到的补充：SSSP

[第三份报告](reports/03_counterexamples.md)最初没有证明 SSSP 的精确双队列调度上界，因此没有把它计入 for/if 已覆盖。之后专门交由第七位代理研究，并再次交回独立终审：

- **out 在下一个外层立即处理，并不等待距离进入某个阈值。** 外层每轮至少完成一次以入口距离为依据的松弛传播；V−1 轮后距离稳定，再一轮处理剩余通知。
- 内层用阈值截断后的距离及通知不变量证明传播；不假设 atomicMin 每次成功，也不假设 re 里全是低于阈值的节点。V−1 波后相关距离稳定，再一波不再产生 re。
- 因而只需已有的 `graph.nnodes`，可以保留两层原动作列表，分别使用 for(V)+if。两个界各自可达到，但不声称总 V² 界同时紧致。

完整证明与反例见 [07 专项报告](reports/07_sssp_bound.md)，复核见 [06 终审](reports/06_final_audit.md)。这些是**有前提的算法层结论**：固定扫描边域、非负权、完整波次、相应读取与屏障可见性、算术和队列有效。没有证明旧 CUDA 源满足任意编译、内存模型或固定 2E 容量下的所有执行，也没有证明其 degree 配置覆盖任意输入图。那些是实现／输入契约核验，不能由循环语法代替。

## for/if 的替代有前提

有真实 MaxIter 或自然上界，还必须同时满足：

1. 条件由明确动作建立，判断时已经可用；不在 if 里暗中加载、计算或等待。
2. 停止后不会再次激活。常见做法是继续读取最后一次动作留下的稳定缓存状态；不能盲目查询一个从未生成的未来轮次条件。
3. 活跃 body 保持原动作、索引、完成约束和全部交接；空尾不执行 body 的 barrier、队列交换、计数推进或释放。
4. 最终状态与退出结果照原契约判断。用满预算不自动表示成功，也不自动表示失败；初始零轮、恰好在最后一轮完成和异常出口都要区分。

[04 理论报告](reports/04_for_if_limits.md)给出了条件证明和四类错误见证：false 后重新为 true、未来条件未定义、人为 cap 冒充成功、反复执行 Final／release。它们说明不能把 while 机械替成 for+if。

比较也须区分三个层次：**动作事件是否相同、描述是否自然、实际实现是否增加开销**。纯条件的空尾在朴素实现中可能增加检查，但 pipe 不要求 Coder 逐条执行这些静默步骤；只要保持设计动作和约束，源码仍可使用 while/break 跳过它们。本研究没有 GPU 性能测量，也不宣称删除 while 会使 Kernel 更快。

## 这项决定的范围

本次采用决定所依据的核心范围为：

> 描述已定义有序域、真实调度器提供的 worktile 流，以及能保留条件就绪、停止状态、动作身份与交接的有限反馈／门控。原语内部等待和没有独立设计交接的局部算法由动作契约承担。核心不承诺表示任意无自然有限上界的本地跨动作反馈。

不能用任意巨大 cap、事后构造“直到成功的轮次域”，或吞并原有独立交接的大动作，冒充已经具备最后那种能力。把一段反馈移到 work_schedule，必须有真实任务单位、调度职责、领取和终止接口，不能只是改名字。

方法上可以构造合法的无 cap 跨角色拒绝采样：生成候选、发布、验证、确认和归还均是独立边界，在每轮独立、固定接受概率为 p（0<p<1）的模型下，它几乎必然终止，但任意长的有限拒绝前缀都有正概率。保留这一协议时，有限 cap 会增加失败结果或改变采样行为；将整段塞进 compute 会隐藏交接。**这是对普遍消去命题的构造性反例，不是本次已核实的 GPU 实现需求。**

重审门槛不必是“证明 for/if 在数学上绝对无法表达”。只要新增一个实际要描述的 Kernel，其本轮结果决定多个有用动作的再次发起，而自然 for/if 写法需要虚构域／上限、复杂锁存，或使设计明显难以审阅，就应重新评估 while。应提交固定源码及同粒度对照，保留退出、失败、在途工作和资源归还；不应先判它是坏设计。

删除 while 也不会自动得到终止性、静态全展开或无死锁保证：动态 worktile 流和 await 仍依赖各自的进展协议。
