# 04：有序 for + if 的能力与 while 的边界

**建议：当前核心可以先只保留有序列表、for、if，把现有 while 严格语义留作候选扩展；必须同时声明覆盖范围。** 这项取舍的依据是：本报告核对的真实设计中，工作遍历、有限扫描、原语内部重试及具有真实 MaxIter 的反馈，都有自然的分工或有界表述。它不支持“所有良好定义算子都不需要 while”。如果目标包括没有可用有限上界、且跨多个可引用动作或 role 的本地反馈，当前 while 确实补充了 for/if 没有提供的控制能力。

**不能把“有上界”直接当成“机械消去等价”。** 正确消去还需要已经可用的条件、停止后不再激活的状态、合法的最终结果与交接、完整的事件身份。`C=[true,false,true]` 和“下一轮条件仅由本轮动作产生”已经足以反驳最常见的直接改写，完全不必诉诸任意程序终止性。

本报告先独立推理，再核对原材料；没有通过阅读 01/02/03 报告的结论建立判断。[方法](../METHOD.md)、[当前 pipe 规则](../../README.md#pipe-规则)、[最新八词与动作粒度](../../../verb_vocabulary/README.md)是约束来源。报告引用旧 schema 时仅把它们当作设计锚点，示意动作采用最新基础词。所有固定来源、文件散列及 CPU 见证结果在 [04_for_if_limits.json](../data/04_for_if_limits.json)。没有运行 GPU、修改 Kernel、正式 schema、既有 trial 或 manifest。

**讨论的语言范围。** `for` 遍历已经定义的有序域：长度可以来自运行时输入，可以在进入内层循环之前由一个有意义的动作算出，也可以是 `work_schedule` 真正提供的动态 worktile 流。它不是只能编译期展开的 for。反过来，当前语义不包含 `break/continue/else`、赋值节点、递归、任意生成器或“循环体往自己的未知域不断追加轮次”的新控制机制。`while(r,C)` 先判断已经就绪的 C，只在成功进入一轮后递增 r；首次 false 即永久离开该循环。两种控制都只决定动作的存在与发起顺序，不自动生成读取、等待、排空、完成、通知或资源释放事件。

| 情况 | for/if 能力与必要前提 | 对 while 的判断 |
| --- | --- | --- |
| 1. 次数来自输入或元数据 | `for(i=0:N)`，N 可以是运行时长度。上游动作算好子范围后再进入内层 for 也成立。 | 没有额外表达力需求；“数据相关”本身不是理由。 |
| 2. 算法本来有 MaxIter，但会提前退出 | 对真实 `[0,MaxIter)` 使用稳定终态门控；保留提前退出、上限耗尽、数值失败等结果。 | 常见情形能消去，但可能增加判定、终态状态与书写负担。不能仅因有 MaxIter 就宣布任意改写等价。 |
| 3. 自然单调 ranking 导出有限上界 | 例如非负整数 R 每成功一轮至少减 1，且 R=0 时不能继续，则 B=R0。需要有效输入前提与各步契约成立。 | 可用自然 B；大而松的 B 仍可能使门控表述不合算。 |
| 4. 本地反馈，没有可用自然上界 | 如果下一次设计动作是否存在只由本轮结果决定，有限既有域不能凭空提供任意长的后继序列。 | 在保留这些动作与接口的范围内，while 有真实作用；“单个 compute 什么都能做”不是等价消去证明。 |
| 5. 等待外部通知、原语内部重试 | 用 `await` 表达已声明通知，用 `acquire` 表达最终取得资源；轮询/CAS 可以是原语实现。 | 通常不应提升为 pipe while。去掉 pipe while 也没有因此证明 await/acquire 一定终止。 |
| 6a. 外部调度实际提供动态 worktile | 用 `for(t)`；领取、发布、确认、终止票和末项排空仍是可引用动作。 | 不因总长度不能预先查询就需要 while。 |
| 6b. 本轮结果生成新工作或重试 | 若已有真实动态任务调度职责、入队接口和终止检测，可以归入调度；否则不能把成功轮次事后命名为 worktile 域。 | 取决于职责与接口，不能靠给循环换索引名解决。 |

“良好定义”至少有三个不同含义。数学目标、输入域与失败结果清楚，不等于迭代次数预先可用；在某些进展前提下终止，也不等于存在可供这个 pipe 使用的自然上界；具有有限输入张量，更不等于其所有协议步骤都受张量长度直接控制。另一方面，如果项目明确只描述有限工作分解和少量有真实预算的迭代，这个受限集合确实可以不需要核心 while。应把后一条写成覆盖承诺，而非普遍的算法质量定律。

**一个正确的有界消去模板。** 设下列动作已经是原设计的真实动作，`compute:Feedback(r)` 做本来就需要的状态推进与停止判定；它维护一个当前状态对象，其中 `Continue` 已经可读。这里不是增加 `compute:SetActive` 来模拟赋值。各动作的具体数学、对象绑定、通知对象及等待仍需声明；本片段不是完整 schema。

```yaml
pipe:
  - "load:InitialState"
  - "while(r, Continue)":
      - "compute:Candidate(r)"
      - "store:Candidate(r)"
      - "signal:CandidateReady(r)"
      - "await:VerdictReady(r)"
      - "load:Verdict(r)"
      - "compute:Feedback(r)"
  - "store:Outcome"
  - "release:Workspace"
```

如果 B 已经可用，并且满足下列前提，可以改成：

```yaml
pipe:
  - "load:InitialState"
  - "for(r=0:B)":
      - "if(Continue)":
          - "compute:Candidate(r)"
          - "store:Candidate(r)"
          - "signal:CandidateReady(r)"
          - "await:VerdictReady(r)"
          - "load:Verdict(r)"
          - "compute:Feedback(r)"
  - "store:Outcome"
  - "release:Workspace"
```

1. **B 有来源。** 它是原算法的真实 MaxIter，或能从已定义输入/状态及进展不变量证明的上界。前一种情况的原循环条件应包含 `r < B`，上限耗尽保持原有结果；后一种情况必须保证最多 B 轮后原条件为 false。检查器预算、硬件有限状态数、随意大的 cap 和事后收集成功轮次都不满足这一条。
2. **条件在合法位置就绪。** 初始动作建立 Continue；每轮已有动作建立下一次判定，并通过 serial 或实际依赖保证届时可用。异步计算刚被 issue 不表示判定已可读；if/while 头也不会帮它等待。
3. **停止后稳定。** Continue 读取的是已经存在的当前状态，只有实际执行的循环体更新它。停止后没有动作或其他 role 把它重新变为 true。无需证明活跃阶段的残差数值单调：只要退出后状态不再变，门控已经吸收终态。
4. **不是读取不存在的版本。** 对 `Continue(r)` 这种逐轮产出的不可变版本，不能假设 `Continue(K+1)` 在 r=K 的判定 false 后仍存在。使用当前状态的表述必须已由对象与动作契约支持；否则是额外状态/接口改造，不能宣称纯语法消去。
5. **判定可重复而无外部影响。** 条件只观察已就绪值，不在求值中读取设备内存、轮询、产生随机数或通知。即便判定纯净，如果它随 for 的 r 变化、观察可由其他角色改变的值，仍需另证停止后的稳定性。
6. **终态与事件接口完整保留。** Outcome 读取原设计的退出状态，区分成功、耗尽、取消、数值异常等；它不借用离开作用域的 r，也不把 `last([0,B))` 当作最后活跃轮。原有零轮处理、异步在途动作、必要通知和归还依赖不能少。

条件 3 是最常见、最廉价的正确实现，不是“所有循环条件天然单调”的假设。若首次 false 只是一个瞬时或按索引变化的观察，while 自身记住“已经离开”；for/if 需要某种等效记忆。这个锁存必须来自有契约的真实状态动作，不能在报告里悄悄加一行 `active = active && C`，再把没有赋值节点的语言称为已经足够。

**为什么模板成立。** 令原循环实际进入 K 轮。对 `r=0..K-1` 归纳，两种表述看到相同状态，发起相同动作实例，使用相同操作数、模式与 waiting。若 K<B，r=K 的判定为 false，之后当前 Continue 保持 false，所以 for 的其余迭代不产生动作；若 K=B，二者按真实上限或保证的停止条件结束。最终状态与 Final 动作相同。零轮、B=0 和恰好用满 B 轮也要包含在前提与证明中。

在这些前提下，可保持**去掉控制内部静默步骤后的动作/issue-done 事件结构**：原有发起顺序、完成约束、跨 role 交接边以及实际事件身份不变。它不是逐条机器控制指令、每次 predicate 观察或实际时间的等价证明。多角色系统还要求其他角色的条件发布、事件存在域和停止协议满足同一不变量；不能单独改一个消费者就假设全系统成立。

| 比较对象 | 正确模板能保证什么 | 仍需分开报告什么 |
| --- | --- | --- |
| 数值结果与退出结果 | 相同实际轮次、原有类型/舍入/状态更新与最终结果契约 | `false` 不等于成功；达到 MaxIter、NaN 或取消可能也是退出原因。 |
| 动作及 issue/done | 活跃前缀的实例、发起顺序和既有完成约束保持 | 控制不自动产生 done，不把无 payload 动作删掉，也不自动排空。 |
| predicate 观察 | 在稳定、纯条件上，额外 false 观察不增加设计动作 | while 通常观察 K+1 次；for/if 观察 B 次。K=B 时还可能省掉原循环末次 false 判定。 |
| 条件值的定义域 | 当前状态在 inactive 尾段仍定义 | 逐轮版本可能只定义到 K；不能继续索引 K+1。 |
| Final 与资源归还 | Final 所需状态与前驱相同，仍显式执行 | 放在 for 后的 Final 要经过 inactive 控制尾段才能发起。无 GPU 时间结论。 |
| 实际控制开销 | 可证明的静默尾段允许实现进一步优化 | 直接解释/降低会访问 B 次门控；编译器可能跳过尾段，不能从语法直接推断 GPU 慢多少。 |
| 描述与检查成本 | 有真实小 B、现成终态时很简短 | 大 B、额外锁存、跨 role 终止、初始/耗尽特殊路径可能使表达反而更难审阅。 |

例如 B=5、实际一轮时，本报告 CPU 见证的动作序列完全一致，而 predicate 观察是 2 次与 5 次。这个数字只说明模型中的控制访问数量。它不代表 3 次 GPU 指令，也不证明编译器不能把尾段消掉。

`pipe` 约束设计动作序列，源码负责实现这些约束。**去掉 pipe while 不要求 Coder 把源码 while/break 改成低效的固定 for。** 如果 inactive 尾段只有已经稳定的纯条件、没有设计动作，源码可以直接用 while/break 跳过它，保持允许的动作事件行为。因此，“语义上能否消去”“描述是否自然”“最终实现是否增加开销”是三个独立判断。需要额外读取/同步才能维持判定，或者未来状态尚未定义时，上述优化前提并不成立，不能把这些工作当成免费。

把 Final 移到终态首次形成的位置可以提前发起资源释放，但并非无条件的简化：还需覆盖初始 false、恰好用满 B、失败状态和单次执行，并维持原前驱。放进当前活跃分支、使用已稳定的终态判定，在某些设计中合法；在 for 的两个兄弟 if 中反复检查 `not Continue` 则会多次 Final。即使提前完成 Final，worker 退出或后继 phase 仍可能经过 inactive 尾段。没有 break 的语法本身不保证这些控制成本消失。

**四个错误消去见证。** [CPU 脚本](../scripts/04_for_if_event_traces.py)只模拟有明确状态契约的串行 issue/done，不解析正式 schema、不运行外部代码，也不模拟 GPU 并发。

| 见证 | 原语义 | 错误改写及后果 |
| --- | --- | --- |
| W1：false 后再次 true | 输入已经提供 `C=[true,false,true,false]`。`while(r,C(r))` 只发起 `compute:State(0)`。 | `for(r=0:3)` 内 `if(C(r))` 还发起 `compute:State(2)`。条件没有副作用、没有未就绪读取，仍然不等价。 |
| W2：未来条件未定义 | 初始只有 C(0)=true；State(0) 产生 C(1)=false。while 此时退出并写 Outcome。 | 三轮 for 到 r=2 要求 C(2)，但 State(1) 从未发生。正确行为是未定义条件错误，不能把它默认为 false。 |
| W3：人为 cap 冒充成功 | 一个三轮才完成的反馈，原循环执行三轮并写成功结果。 | cap=2 的 for 执行两轮后仍写 Success，后置条件为假。改成返回 Exhausted 可以避免谎报，但改变了原算子契约，仍不是等价消去。 |
| W4：错误提前 Final | 原设计在第一次停止后执行一次 Outcome 与 release。 | 每次 for 都分别 `if(Continue)` 做工作、`if(not Continue)` 做 Final，B=3、一轮停止时重复 release 三次，也违反事件实例唯一性。 |

W1 反驳的是机械改写，不是声称输入 flags 的任何算法都必须用 while。若已有上游元数据给出“第一个 false 位置”，for 那个前缀当然成立；若另加扫描来取得这个位置，则须承认新增计算及其事件。W2 同理：已有的当前状态接口可以解决它，不能凭一个未执行动作产出未来状态。

脚本核对了 72 个原算法自带 MaxIter 的小规模状态例子（包含预算耗尽），以及其中 45 个具有保证上界的例子；所比较的动作轨迹与 Outcome 均相同，并验证以上四种错误。有限见证补充条件证明，不把几十个例子升级为一般等价定理。脚本中的 Python 更新只是实现命名 compute 的状态契约，没有向 pipe 增加赋值节点。

还有两种无须脚本就应拒绝的改法：其一，每轮在 if 外 `load:Condition(r)` 来保证判定“刷新”，会增加读取/issue-done 事件，而且停止后的新观察可能再激活工作；其二，Final 固定等待 `{done Compute(B-1)}`，但实际只活跃一轮。后者引用了不存在的必要前驱，按当前 waiting 规则应报错，不能通过对事件日志求交把等待删掉。

**三个真实来源锚点。**

1. **QSA：同一源码里有调度 while，也有 hash while，两者不是同一个层级问题。** 固定 KernelSchema commit `01fff90d714abc6e84904ea9c44523ba66d34a0e`。快照 [qsa_kernel.py](../../trial_roots/sources/template_qsa_prefill/qwen38_core_qsa_cutedsl/qsa_kernel.py) 320–335 行，调度角色原子领票、存票、通知、等待确认后检查终止；673 行及 762 行的消费者 while 处理领到的有限 worktile。源 [work_schedule](../../../../schema_template/examples/qsa_prefill/root.yaml) 149–193 行已经定义工作分解、原子票分发、终止票确认及排空；[trial](../../trial_roots/template_qsa_prefill.yaml) 的 `for(t)` 保留 Ticket0、Next(t)、accept、drain 边界。这是有真实外部调度契约的动态有序流，不能用“次数运行时才知道”证明必须保留 pipe while。

   同一固定版本 [qsa_preprocess.py](../../trial_roots/sources/template_qsa_prefill/qwen38_core_qsa_cutedsl/qsa_preprocess.py) 37–65 行给出 16384 槽及 `maxe < slot_count` 前提；221–236 行和 346–359 行是 CAS 插入与线性探测。若 maxe 确实是支持输入内同时插入条目的有效上界、表在此阶段只插入不删除、原子语义成立，则每次失败走到下一槽；一次全表探测均失败将意味着所有槽已被占，和容量前提矛盾。这是自然有限上界，不是从有限硬件状态空间编造的巨大 cap。**assert 一个常量不等于已经证明异常输入或不一致 packing 也满足有效条目上界。** 更关键的是，既有 [preprocess 契约](../../../../schema_template/examples/qsa_prefill/root.yaml) 208–214 行已经把探测放在 build 的线程级构建流程，跨动作边界是 Hash 构建完成到 compaction；最新词表允许这类本地算法属于 compute。没有必要逐次 probe 建立 pipe 事件。

2. **FMHA segmented scan：当前数据决定后续范围，仍然可有限遍历。** 固定 KernelSchema commit `6e4ca91bd91d998cac99e8dadd83838e153c679d`，快照 [fmha_tc.cuh](../../trial_roots/sources/extract_fmha/fmha_tc.cuh) 1406–1495 行。外层按 nseg 走有限 chunk；加载当前 16 个 segment maxima，用进入 chunk 的 m 计算 jmp；如果 jmp=0，填充 `[t0,t1)` 的常量；否则由首个置位位算出 tp，先填 `[t0,tp)`，再精确走 `[tp,t1)`。m 的单调性质支持跳过前缀的正确性，tp 在后续 for 进入前已算出，t1 受输入 T 限制。B1 的 1503–1568 行也采用先算 f、后遍历 `[f,send)` 的有限范围。

   所以“本轮数值改变了后面执行多少工作”仍不足以推出 while 必需。若这层扫描在 pipe 显式展开，已有 compute 可以产出 jmp/tp，再用两个基于稳定 jmp 的互补 if 和有限 for；若没有独立交接，整个局部 scan 属于 compute 也自然。源码中的局部 break 可以通过输入定义的有效 chunk 域或单调越界门控处理。这里不声称源码每个 load、标量比较都应提升为设计动作，也没有把该优化换成另一种扫描算法。

   同版本 [fmha_tcg.cuh](../../trial_roots/sources/extract_fmha/fmha_tcg.cuh) 2608–2645 行还有一个特别有用的边界例：`gs_wait_wd` 超过 100000 次 poll 就设置 latch 并直接返回，后续等待也提前返回；2609–2611 行注释明确承认这是让 kernel 携错误数值尽快退出来取得诊断日志。1656–1657 行显示该 watchdog 默认关闭，正常分支调用 `mbar_wait`。这是诊断中有意放弃正常完成保证的分支，不能把这个 cap 当作生产 await 的自然成功上限，更不能据此把超时当作依赖满足。

3. **CUDA cooperative-grid CG：是合理反馈的强证据，是“严格不能消去”的弱证据。** NVIDIA CUDA Samples v12.5 解析为固定 commit `9c688d7ff78455ed42e345124d1495aad6bf66de`，公开源码 [conjugateGradientMultiBlockCG.cu](https://github.com/NVIDIA/cuda-samples/blob/9c688d7ff78455ed42e345124d1495aad6bf66de/Samples/4_CUDA_Libraries/conjugateGradientMultiBlockCG/conjugateGradientMultiBlockCG.cu#L242)。249 行 `max_iter=10000`；270–309 行在 GPU 内重复向量推进、SpMV、dot、解/残差更新、残差 dot，并用 `cg::sync(grid)` 交接。初始残差与每轮末尾残差分别在同步后加载，下一轮依赖本轮的计算结果。

   在保留全 grid 动作边界与同步的前提下，用 `for(r=0:10000)` 门控已经就绪的当前残差即可表达这一**有界**反馈，实际步骤 k 对应 r+1。达到阈值后 body 不再执行，残差保持，不需要额外锁存；达到 cap 则保留最后近似解与失败判定。不能假定浮点 CG 必在 N 轮收敛来另造更小 cap。源码 489–491 行实际按 `sqrt(r1) < tol` 输出 PASSED/FAILED 与进程退出码；原 while 的 `r1 > tol*tol` 为 false 不应直接翻译为“成功”，等号与 NaN 的判断也不能混用。

   该来源说明良好算法可以包含真实数值反馈与跨 CTA 协作；它不证明这个关键词在核心不可删除，也不证明这些源码同步已经完整映射成符合当前成员/phase 规则的 KernelSchema。这里只读了固定源码，没有运行它。文件 SHA256 为 `1e6f89447b28529e9458d0c491bcbdcf4da24e4c8ff97d590b7617225e68ab39`。

**自然 ranking 的限度。** 非负整数剩余项数、尚未访问的表槽、有限图中不重复推进的层数，只有在每个设计轮确实消耗这个量时才给出 B。仅说某个实数误差严格下降不够：`R(r)=2^-r` 可以永不等于零；若有已知收缩率与正容差，才可能算出有意义的步数。无容量约束的字典序状态、期望迭代次数、平均性能和“通常很快”也不是有限上界证明。原语公平性或完成保证控制每一步能否完成，与轮数上界是不同问题。

**while 仍有严格作用的一个契约构造。** 考虑分批拒绝采样：Proposal role 用真实 compute/matmul 生成候选，store/signal 发布候选缓冲；另一个 Validation role 验证并通知；Proposal 显式 await/load 判定、释放本轮缓冲，然后在拒绝时生成下一批。每轮有可引用的候选交接、验证通知和资源复用边界，下一轮存在与否来自本轮结果，没有上游预先提供的轮次域。

取每轮独立、接受概率恒为 `p∈(0,1)` 的构造，则连续 k 轮仍未接受的概率恰为 `(1-p)^k`，因此几乎必然终止，但任意有限 B 都有正概率仍未接受。有限 cap 加 Exhausted 会增加原来没有的失败结果；把未验证候选当结果会破坏正确性；改用另一种直接采样算法则是算法更换，不能证明原 while 设计有漏洞。在保留这些明确交接边界的要求下，一个 compute 不能吞掉整个协议；把“直到接受的全部轮次”称为 for 域也不满足当前规则。

这是**合成的设计契约反例，不是本库或公开 GPU 实现的事实证明**。如果拒绝采样完全在线程局部、只有最终样本被外界消费，将整个算法放入一个 compute 正当，源码内的 while 不支持 pipe while。这里的进展承诺是几乎必然终止；若用户把“良好定义”特指每条随机轨迹都有限结束，就应把本例排除出那个更窄的承诺。它仍准确指出随机算子常见的数学定义与一个固定 cap 不等价。对确定性反馈，本报告只主张“没有当前可用上界时不能宣称已有消去”，没有把未找到上界升级为所有此类程序必定不可有界的定理。

**封装/分层的最强反方，应当认真接受。** 当前粒度的目标是设计动作而非线程程序；普通读写可以随 compute，原语自旋可以随 await/acquire，真实工作领取属于调度。不能因为源码出现多个循环或原子指令，就要求 pipe 有相同层数。`compute:Hash`、`compute:LocalSample`、`await:Ready` 都可能是正确边界；一个原语内部没有独立消费者的失败探测一般不需要命名事件。真实 MaxIter 也往往足够，尤其初始条件、当前状态和最终成功检查已经存在时。

但这种解释至少要通过下面的职责检查：

- **封装后的 done 到底保证什么。** `await` 只等待他人的已声明通知，不能暗中反复产生候选或推进本地算法；`acquire.done` 表示已经取得资格，超时/申请失败不能伪装成完成。compute 可以做本地数学与普通读写，不能让原本可单独被依赖的发布、读取结束、通知或归还边界失去地址。
- **谁拥有中间动作。** 若一个大 compute 跨过另一个 role 的独立工作、资源复用或消费，而外围仍需要等待这些中间事件，封装不合法。即使“最终数值一样”，原来可引用的协议已被删掉。若本来就是一个合作计算集体、所有内部步骤都只有一个对外完成边界，则该粒度可能完全合理；不能仅因使用了多线程或 barrier 就判定必须拆。
- **动态 worktile 是真实工作还是轮次化名。** 真正的任务队列可以接收本轮生成的子任务；若 task 的输入、目标、身份、入队/领取与终止检测已经属于调度接口，worker 用 for(t) 合法。全系统仍存在反馈，只是反馈本来由调度负责。若没有这样的接口，把尝试 r 叫 worktile、再让域提供者替同一 role 计算下一次候选和判定，只是把算法循环移到未定义的地方。
- **退出不能依赖事后知识。** 空队列不代表没有在途生产者或重试；终止票、发布、确认、失败和资源归还要保留。只有“调度完成时可回看得到一个列表”不足以定义运行中的 for 域。QSA 已有明确票据与终止规则，是合法例子；任意局部反馈没有自动继承这个资格。

反过来，不能把所有跨 role 往返都硬判成 pipe while：假如本轮结果确实成为已声明 scheduler 的真实输入，且调度器承担再分发/重试/终止，这可能就是正确分层。应该查工作目标、接口与责任，而非规定“数据依赖只能放在 pipe”或“反馈都应放在 scheduler”。

**关于有限展开和替换算法。** 对编译期已知的小 B，嵌套 `if(C0) { Body0; if(C1) { Body1; ... } }` 可以保留第一次 false 即停止的结构，不必锁存；代价是 B 份动作/控制文本。运行时 B 不能靠固定深度语法树普遍获得这种表述。把 B 设成硬件状态空间大小、写无限 for、预先跑完原算法以得到成功轮次域，都不构成自然消去。更换为直接算法、批量求所有候选或在 host 重新发起，也可能是优秀实现选择，但会改变动作序列、工作分配或算法，不能据此否定原反馈设计。

**给当前规则的明确取舍。** 我建议把 while 从当前核心移入候选扩展，保留现在的严格定义及上述使用条件，原因是目前三个源码锚点都没有建立“无自然上界且必须暴露在 pipe 的反馈”的实际迁移需求；当前词表本来也不追求完整线程程序表达。此建议不是按关键词数量越少越好：强迫有界反馈塞入不自然的锁存/终态契约，会把控制复杂度转移到 describe；for(t) 和 await 也意味着删掉 while 不会自动获得静态有限展开或终止性。

若采用删除，能力范围可直接写为：

> 核心 pipe 描述已定义有序工作域、真实调度器提供的 worktile 流，以及具有可用有限域、已就绪条件和明确停止状态的动作门控。原语内部等待/重试和没有独立设计交接的局部算法由动作契约承担。当前核心不承诺在保留所有设计动作与交接边界的同时，表示任意无自然有限上界的本地反馈循环；不得用无限域、事后成功轮次域、任意 cap 或不透明大动作冒充该能力。检查预算耗尽是未验证，不是正常退出或算法失败。

建议在出现下列任一情况时重审，而非要求证明任意程序终止：新增真实算子必须根据本轮结果反复发起多个可引用动作且没有可用自然上界；具有真实 MaxIter 的新增设计为了 for/if 需要专用锁存、复杂终止协议或难以接受的 inactive 尾段；动态任务调度接口无法自然容纳反馈且保留中间 role 交接是核心价值。届时应完成至少一份源码固定、粒度一致的多 role while 试写，逐一核对零轮、提前停止、预算耗尽/失败、条件就绪、事件存在域和最终资源释放；有限展开检查的结论仍只限于已验证范围。

如果项目现在就承诺一般迭代算子和这种跨动作反馈，那么应保留当前 while，且继续限制条件纯净、轮次身份明确与真实动作边界。两种工程选择都能自洽；**“所有良好定义算子不应有 while”不能作为其中任何一种的证明。**
