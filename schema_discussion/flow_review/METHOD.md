# Flow 规则评估

本轮只评估 `design.work_schedule.flow`，不修改正式规则、算子、模板或检查器。目标是保留影响工作组织、数据交接与并行机会的设计事实，去掉无助于设计的实现过程。

## 材料

- 规则以本轮捕获的 `rules/` 为准，原文件来自当前 `schema_docs`；不把旧 YAML 的语法当成现行规范。
- 十个算子来自既有文本审计的固定输入：四个模板与六个提取算子。四个模板 root 已与当前模板逐字节核对一致。
- 六个算子采用 2026-11-09 暂停时的工作稿；FMHA、MoE 尚未完成整树，不以更早 wiki 发布稿代替。当前 wiki 归档仅作来源及版本对照。
- `corpus.json` 保存输入路径、状态和哈希。基础范围是十个 root；分支用于补充不同 flow 拓扑，不把占位稿、未开始节点或重复继承计作独立设计证据。
- 优先复用两个既有调查：`SCHEMA_DISCUSSION.md` 和 `SCHEMA_VERBOSITY.md`。涉及新增/删除能力的关键判断须回看 YAML，必要时核对对应 Kernel 源代码。

## 独立调查

五位新的 `gpt-6-astra` 子代理，`effort=max`，最多两位同时运行。分别考察：

1. 字段语义、默认值和最小表达能力。
2. 六算子的实际 flow 与源代码支持的关系。
3. 说明字符串中隐藏的关系、外部调用与跨次复用边界。
4. 四个模板与 phase 组合方式，尤其融合、拆分和工作粒度。
5. 最小方案的独立反证、命名与阅读成本。

各自先独立判断，不阅读其他子代理的建议。主代理复核具体证据，区分共识、分歧与仍需决定的范围。

## 每项结论的要求

- 说明该事实影响什么设计决定；有无字段不等于有无表达能力。
- 区分：现行能力已够、实例填写错误、文字归属不当、真实表达缺口、实现细节。
- 删除建议需要指出保留该事实的去处；新增建议需要实际反例及最小写法。
- 不为穷尽任意程序引入通用 host/stream/graph 语言；也不以抽象为由改变已有先后、存续或重叠关系。
- 区分启动许可、可消费时点、等待位置；区分逻辑数据值与物理存储、单次调用与跨次状态。
- 记录原文路径与行号。试写片段标明是现行语法还是讨论提案，不改原始算子。

统计只用于观察字段使用，不代替语义判断；没有出现的能力不因此可删。全部检查为静态阅读或有限 CPU 核对，不作 GPU 正确性和性能结论。
