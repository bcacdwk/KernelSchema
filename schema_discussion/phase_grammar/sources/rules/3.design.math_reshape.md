# 数学改写

## 核心思想

派生节点可以依[Design 整区引用](0.common.md#design-整区引用)将整个 `math_reshape` 写为 `{from_parent: <直接父ID>}`；root 始终本地定义。下文描述本地定义及引用展开后的内容，不允许只引用某个 rewrite 或附加局部覆盖。共享公式、符号和 `bind:` 在当前使用节点的 Contract 与工作参数中理解，仍须核对其适用性和下游关系。

`math_reshape` 在不改变 Contract 的前提下，决定实际算出哪些值、这些值怎样定义、以什么精度存在、存在多久。它做的是算法与硬件的 co-design：动机来自硬件——哪类单元更快、哪一级存储放得下、哪条依赖链太长——而改写本身是纯数学的，与流水线无关。本区接收 Contract 的输入输出、数学要求和硬件条件，可以引用由下游绑定的工作参数，向下游交付可审阅的数学设计；它不决定 CTA、warp、role、物理布局、缓冲槽位、屏障或流水重叠。

本区使用 `thesis / rewrite`：

- `thesis` 概括这次改写最重要的主张、动机与主要代价。
- `rewrite` 是本区唯一的计算定义处，从 Contract 输入写到全部输出。
- `rewrite[].ledger` 不定义任何值，只对照一个明确的 baseline 记录这一步造成的差额。

`rewrite` 以数学决定为单位：一个步骤应当能被单独审阅、替换或否决，步骤之间只通过值的依赖相连。物化值产生处与迭代结构改变处通常就是步骤的边界；精度分叉不单独成步，在同一步里用两个名字表达。步骤不是 phase：一个数学步骤可以由多个工作实例完成，多个步骤也可以融合在同一份工作中。

### 设计着眼点

改写可以重新考虑算子边界、数据表示和融合方式，前提是保持 Contract。结合硬件相对代价与计算依赖，比较减少计算或物化、缩短依赖链、转移执行资源等机会，并说明收益成立的条件；没有值得采用的改写时可以保留原计算。提取既有实现时，先从实际求值与数据依赖还原数学决定，再核对它的收益和代价，不从代码名称推定优化效果。

| 问题                 | 要看什么                                                                                                     | 落在哪里                                                       |
| -------------------- | ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------- |
| 主要成本在哪一项     | 硬件规格与 microbench 给出的相对代价，以及直接求值的计算量、传输量和依赖。                                   | 对应步骤 `ledger` 的 `gain` / `cost` 及其成立条件。                      |
| 哪些量其实不必存在   | 随输入规模增长、或物化后只被读一两次的中间量：能否由固定大小的状态逐块吸收，或换一种结合顺序就根本不必算出。 | `symbol.retention`，以及 `ledger` 中物化量与访存量的变化。 |
| 串行链能不能变短     | 链上的合并是否满足结合律，递推是否对状态线性：满足时可以分段计算再合并，或把若干步合成一次块运算。           | 递推的 `math`，以及 `ledger` 中依赖链长度的变化。                                   |
| 能不能换更便宜的单元 | 同一份计算能否交给吞吐更高的单元，或拼成它的原生形状，例如把零散的行聚成稠密块。                             | `math` 中的计算形式，以及 `ledger` 里两类单元的此消彼长。      |
| 精度能不能换吞吐     | 哪些乘法输入可以窄化、哪些函数可以近似、哪些量必须留在 FP32；`tolerance` 的预算还剩多少。                  | 公式中的 cast，`arithmetic`，以及 `ledger.cost` 中的新增误差。                     |

## 字段定义

### 结构轮廓

下面是字段结构。`[]` 表示列表，`<name>` 表示实例名称，`?` 表示条件可省略。

```text
math_reshape
├─ thesis
└─ rewrite[]
   ├─ name
   ├─ math
   ├─ symbol?                 named map
   │  └─ <name>: meaning / shape? / dtype? / retention? / binding? / value?
   ├─ arithmetic?
   │  ├─ approx?
   │  └─ accumulate?
   └─ ledger?
      ├─ baseline
      ├─ gain?
      └─ cost?
```

### 主体字段

下表中的路径均相对于 `math_reshape`。

| 字段路径                            | 值的形式         | 填写条件                                                       | 含义与约束                                                                                               |
| ----------------------------------- | ---------------- | -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `thesis`                          | 非空字符串       | 必填                                                           | 一两句说明采用或保留的计算方式及其依据；有改写时概括主要收益与代价，不写泛泛的性能口号。                 |
| `rewrite`                         | 非空步骤列表     | 必填                                                           | 从 Contract 输入写到全部输出。                                                                           |
| `rewrite[].name`                  | 非空字符串       | 必填                                                           | 简短说明该步骤的数学决定。                                                                               |
| `rewrite[].math`                  | 非空多行字符串   | 必填                                                           | 定义、递推、分情形、索引范围和显式 cast。                                                                |
| `rewrite[].symbol`                | 具名映射         | 该步骤首次引入必须登记的符号时必填                             | 每个符号只登记一次；没有新增登记对象时省略。                                                             |
| `rewrite[].arithmetic`            | 固定结构映射     | 存在公式未完整表达的精度例外时必填                             | 只允许 `approx`、`accumulate`，至少填写一项。                                                        |
| `rewrite[].arithmetic.approx`     | 非空字符串       | 存在公式未完整表达的主动近似时填写                             | 说明近似方法、适用域和误差界；没有可靠误差界时明确写 `unknown:`。                                      |
| `rewrite[].arithmetic.accumulate` | 非空字符串       | 累加方式、归约分组或乘法输入精度不能从公式及默认规则确定时填写 | 不重复已经由 `mm32`、`mma32` 或显式 cast 表达的事实。                                                |
| `rewrite[].ledger`                | 固定结构映射     | 该步骤相对 baseline 有值得记录的收益或代价时填写               | 只允许 `baseline`、`gain`、`cost`；每项写成一行，不超过 150 字符。                                       |
| `rewrite[].ledger.baseline`       | 非空字符串       | `ledger` 出现时必填                                            | 写明这一步拿来对照的求值方式及其物化取法；共用的计量口径见“账本”，这里只写与它不同的部分。             |
| `rewrite[].ledger.gain`           | 非空字符串       | 该步骤有可计量的收益时填写                                     | 相对 baseline 减少的量，带单位和范围；其中的符号必须已由 `math` 定义。                                   |
| `rewrite[].ledger.cost`           | 非空字符串       | 该步骤有可计量的代价时填写                                     | 相对 baseline 增加的量或新增的误差来源，写法同 `gain`；缺少某项不是零变化的证明。                        |

### 符号属性

登记的判据只有一条：符号是否带着公式表达不了的信息——保留方式（`carry_forward`、`keep_value`）、外部提供者（`binding`）、本层固定值（`value`），或者是其他区要取用、必须写明 `shape` 与 `dtype` 的接口。不满足的量即使跨步骤使用、即使是精度分叉的源头，也只在公式中定义。

登记之后，属性要填到下游够用为止。物化结果应说明后续用途；从已有实现提取时，未被消费的结果也如实保留并说明。不能为了避开属性检查，把关键状态移出 `symbol`；也不应为了表格完整，把每一个数学临时变量都扩展成条目。

`symbol.<name>` 的合法字段为 `meaning / shape / dtype / retention / binding / value`，按需填写。

| 字段          | 值的形式                             | 填写条件                               | 含义与约束                                                     |
| ------------- | ------------------------------------ | -------------------------------------- | -------------------------------------------------------------- |
| `meaning`   | 非空字符串                           | 必填                                   | 一句话说明符号是什么；不重复整段公式，也不承担缺项占位。       |
| `shape`     | 具名维度列表，或属性引用、待绑定标记 | 公式不能确定，或该值要被下游取用时必填 | 描述一个逻辑实例的值形状，不描述线程 fragment。                |
| `dtype`     | 类型名字符串，或属性引用、待绑定标记 | 同 `shape`                           | 描述数值表示。类型名必须在任务环境中有定义；不是任意自造标签。 |
| `retention` | 保留方式与实例范围字符串             | 值跨迭代携带，或选择物化时必填         | 描述哪些值保留供后续使用，不指定物理驻留位置或写入次数。       |
| `binding`   | `ref:` 或 `bind:` 引用字符串     | 整个符号由本区之外提供时必填           | 指定符号的定义来源或待绑定的提供者。                           |
| `value`     | 已知标量或数组字面值                 | 本层选择一个固定值时填写               | 是该固定值的唯一来源；不用于装未知值或外部参数。               |

“被下游取用”指 `carry_forward`、`keep_value` 或被其他区引用的值：它们是下游的接口，`shape` 与 `dtype` 必须填全。公式已经定死、又只在本步使用的属性不再复写一遍——`dot32` 的结果是 FP32，`0 <= u < Bk` 已经给出长度。

集合、映射、函数，以及只作参数使用的数学整数没有数值表示，省略 `shape` 与 `dtype`，也不写 `not_applicable`；它们由 `math` 定义，或由 `value`、`binding` 给出。`value` 与外部 `binding` 不同时承担同一符号的定义权：外部已经固定的量使用引用，不在本区再维护一份数值。

查询行集合、访问映射不必存在对应张量，也不必有 dtype。下游若物化索引数组，应为那个实际数组说明形状、dtype 和生命周期，而不是倒过来把本区的数学映射解释为已经存在的数组。

### 值的保留

`retention` 写成 `"<carry_forward|keep_value> <实例>"`，括号中的每一组下标是一个实例；存在递推时在分号后给出迭代范围。

| 写法                                                | 含义                                                                                                  |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 省略                                                | 不跨迭代携带，也不物化：在产生它的那一轮计算中用完，可以被同一轮里后续步骤的公式使用。                |
| `"carry_forward (b,h,q); i=-1..N-1"`              | 在给定迭代范围内携带的递推状态；换到新实例（这里是新的查询行）就按公式重新初始化。                    |
| `"keep_value (b,h)"`、`"keep_value invocation"` | 在该实例范围内保留已有或算出的值，供后续复用，而不是在用处重算；`invocation` 表示整个调用只有一份。 |

`retention` 描述逻辑用途，不是内存空间枚举：递推状态一律写 `carry_forward`，它是否需要在某处保存到全局内存不由这个词决定；`keep_value` 也不表示全局内存、独立 kernel 或屏障，值放在哪一级存储由下游决定（跨 phase 交接时见 `work_schedule` 的 `handoff.storage`）。初值、重置位置、有效迭代范围、消费者和最终输出关系都由 `math` 给出，本区不另设初始化、重置或终点字段；`retention` 必须与这些公式一致。

这里的“迭代”以 `math` 定义的计算和逻辑实例为准。例如，输入的切片或排列视图可以在一份 worktile 中保持不变，由下游缓存供多轮计算使用；单凭这种物理驻留不能判定新增了逻辑物化。若数学设计要求保留非递推的值，供后续迭代或步骤复用而不重算，则按该逻辑实例填写 `keep_value`。

`keep_value` 不要求每个元素恰好写一次，也不要求本次调用覆盖所有槽。某个空分支保留已有 scratch 内容时，由 `math` 写明哪些元素保持不变，不能从保留方式推导额外写入。

例如，已定义每个 batch、head 独立的递推，共 `Nc` 个 chunk：`S(-1) = S0`，`S(c)` 是 chunk 末状态，后续计算需要每个 chunk 的入口快照 `S_bar[c] = bf16(S(c-1))`。登记的区别是：

```yaml
symbol:
  S: {meaning: State after chunk c, shape: [dk: DK, dv: DV], dtype: fp32,
      retention: "carry_forward (b,h); c=-1..Nc-1"}
  S_bar: {meaning: Incoming-state snapshot for each chunk,
          shape: [chunk: Nc, dk: DK, dv: DV], dtype: bf16, retention: "keep_value (b,h)"}
```

`S` 的 shape 描述一份当前状态，`S_bar` 则真的保存了 `Nc` 份快照，所以多出 chunk 轴。二者的实际存储位置仍由下游决定。

### 固定结构与扩展边界

| 位置类型     | 本区位置                                                                     | 允许的变化                             |
| ------------ | ---------------------------------------------------------------------------- | -------------------------------------- |
| 固定结构     | `math_reshape`、`rewrite[]`、`symbol.<name>`、`arithmetic`、`ledger` | 只使用本节声明的字段。                 |
| 具名映射     | `symbol`                                                                   | 可以增加当前设计需要的符号名。         |

增加步骤、数学符号或辅助函数属于填写内容；新增 `retention` 取值或固定字段遵循[公共扩展规则](0.common.md#结构与扩展)。

## 语法规则

### 名称、ID 与定义范围

通用命名与 YAML 写法见[公共约定](0.common.md#通用写法)。本区的符号名区分大小写，可以用简短的英文或数学惯用名称，如 `alpha`、`tau`。

Contract 的常量、规模、输入与输出直接用原名，不另起别名；Contract `compute` 中的中间量只用来定义要求，本区按自己的改写重新定义需要的量，沿用同一个名称时必须仍是同一个数学对象，例如 chunk 末状态应明确对应 Contract 中哪个 token 的状态。本区内一个名称只有一份定义，后续步骤和下游直接使用；未登记的名称只在 `math` 中定义，其范围必须能从公式确定。

`rewrite` 列表按先定义、后使用排列，这一顺序只表示定义关系；列表与映射的顺序都不表示执行顺序，执行先后只来自公式中的数据依赖、递推和下游安排。

### 引用与缺项

本节的对象/属性 `ref:` 与下游符号 `bind:` 不承担整区继承；区域共享仅使用上述 `from_parent`。继承数学区中的 `bind:design.work_schedule::Bk` 指向使用节点当前的 Bk 定义，不携带 provider 的参数取值或选择条件。

属性引用沿用[Contract 的 `"ref:"` 写法](1.contract.algorithm_requirement.md#symbol-与属性引用)，跨区目标写成 `<area>::<name>[.<attribute>]`，例如 `contract.algorithm_requirement::V.dtype`、`design.work_schedule::Bk`，本区内部的符号省略区名；指向固定版本材料时写 `repository@ref:path::symbol`。`::` 后的名称是语义定位，不要求目标区域新增同名字段，但接入完整 Plan 时必须解析到实际定义。

| 写法                   | 含义                                                                    |
| ---------------------- | ----------------------------------------------------------------------- |
| `"ref:<target>"`     | 目标已由上游或本区定义，且唯一可解析。                                  |
| `"bind:<target>"`    | 提供者明确，取值由目标所在的下游区固定，不是留给 Coder 自由替换的空位。 |
| `"unknown:<reason>"` | 尚未确定或缺少依据；必须说明缺口。                                      |

`binding` 引用整个对象，`shape`、`dtype` 中的引用只引用相应属性，语义必须一致。外部绑定的符号仍可填写已知属性，它们是对绑定结果的约束，不是第二份定义；冲突时报告问题，不由某一处静默覆盖另一处。

显式的 `ref:contract.algorithm_requirement::<对象>.<属性>` 在所有节点中都指向 root 的共享 Contract。属性目标必须是其中已登记的对象，且确有对应属性；校验器对这类结构化引用检查存在性，不要求派生节点复制 Contract。仅在公式、strategy 或动作契约中定义的其他语义目标仍需审阅解析。

源码中计算某个量的函数不是它的数学定义。映射由下游负责、且提供者已经明确时才使用 `bind:`；属于本层的数学定义仍须在 `math` 中完成，不能用绑定或源码函数引用代替。`unknown:` 用于连属性值或有效依据都尚未确定的情况，不出现在 `ledger` 中。

例如，数学改写使用块长 `Bk`，但把选值交给工作调度：

```yaml
symbol:
  Bk: {meaning: Reduction block length, binding: "bind:design.work_schedule::Bk"}
```

对应 phase 的 `decomposition` 可以这样固定它；这里假设 Contract 已定义形状为 `[reduction: L, feature: D]` 的输入 `K`：

```yaml
strategy: Bk = 64; each local iteration consumes one K block.
worktile:
  iteration:
    K: {shape: [reduction: Bk, feature: D], dtype: "ref:contract.algorithm_requirement::K.dtype", direction: ascending}
```

`Bk` 只有下游这一处数值定义，不新增 schema 字段；数学区也不同时填写 `value: 64`。这段绑定说明应随设计写明，不能只在实现源码中出现。

### 数学表达与 shape

`math` 只写实际求值的计算：定义、递推、分情形和显式转换。等价性证明、不变量和解释性文字不写在这里。改写与 Contract 的关系及精度路径依据固定源码和任务定义审阅。

记号沿用[算法要求](1.contract.algorithm_requirement.md#数学表达与参考精度)，集合写成 `{j in integers | ...}`、`j in visible_key(q)` 这样的英文形式；不使用 LaTeX 源码、线程视图操作或实现代码。本区补充下表：

| 记号                   | 含义                                   |
| ---------------------- | -------------------------------------- |
| `Aᵀ`                | 转置。                                 |
| `A ⊙ B`             | 逐元素乘法；广播轴必须明确。           |
| `X[:,None]`          | 数学上的单例轴插入，不指定物理布局。   |
| `count(S)`           | 集合的元素个数。                       |
| `dtype(X)`           | 已定义对象的 dtype，不是重新选择类型。 |
| `bytesize(dtype(X))` | 该 dtype 的每元素字节数。              |

矩阵乘一律用下一节的精度记号写出，`*` 只用于标量乘与缩放，`⊙` 只用于逐元素乘。辅助函数（如自行选择的多项式近似）没有全局定义，在使用它的计划中给出；`exp2_native` 这类带实现含义的函数，由公式、`arithmetic` 或绑定说明来源，后缀 `native` 本身不定义算法或误差界。

未被改写的计算直接引用 Contract 的定义，不重抄；改写发生在某个计算内部时，必须展开到能看见改动的粒度——per-tensor scale 的 GEMM 可以不展开，把 block scale 提到内积之外就必须展开。

shape 写成[具名维度列表](0.common.md#shape-与整数表达式)，例如 `[kv: Bk]`、`[dk: DK, dv: DV]`；沿用 Contract 对象的轴时保持同名。它描述一个实例的完整值，只列方括号下标对应的轴：圆括号中的递推下标，以及公式省略或逐个处理的下标（如 `b`、`h`），都不列入。这一点与 Contract 的 symbol 不同。

分情形只要求在有效分支上求值。不能把越界读取、`0/0` 或 `-inf-(-inf)` 当成无条件计算，再假设掩码会消除影响。空和为零，空最大值为 `-inf`；递推是否允许空范围，还必须有明确的最终关系。

### 精度与辅助运算

默认 FP32 与 RNE、`<dtype>(x)` 转换、窄化必须写出而加宽不写，都由[算法要求](1.contract.algorithm_requirement.md#数学表达与参考精度)给出。窄化与量化不能只靠 `symbol.dtype` 暗示：填写的 `dtype` 是对公式结果的断言，`P = bf16(E)` 与 `dtype: bf16` 必须一致，不能由两处分别调参。本区补充下表：

| 记号                          | 数值含义                                                   |
| ----------------------------- | ---------------------------------------------------------- |
| `cast(dtype(X),Z)`          | 将 `Z` 转为 `X` 已定义的 dtype。                       |
| `fma32(A,B,C)`              | FP32 融合乘加，乘加结果一次舍入。                          |
| `dot32(A,B)`、`mm32(A,B)` | 所示 dtype 输入的内积或矩阵乘，零初始累加器和结果为 FP32。 |
| `mma32(A,B,C)`              | 以 FP32 `C` 为初始累加器的矩阵乘加。                     |
| `mm_tf32(A,B)`              | TF32 乘法输入路径，FP32 累加与结果；不表示 TF32 存储张量。 |
| `sum32`                     | FP32 归约。未另行固定时，不由记号指定归约树。              |

这些是数学记法，不要求实现提供同名 API。FP32 累加器也不代表乘法输入、乘积内部处理和全部舍入都具有 FP32 精度，更不构成逐位一致性保证；影响设计的输入截断、累加分组和近似必须另外表达，并以目标架构为依据，另一架构上的累加行为不能直接搬过来。

`arithmetic` 只补充当前步骤。跨步骤沿用同一例外时必须引用其定义，不能把一个步骤的精度说明默认为整份 Plan 的覆盖规则。

例如，已定义的 FP32 值 `R` 与同形状的 FP32 权重 `decay` 分成两条数值路径，且两次窄化的输入均在 BF16 范围内时，公式直接写出各自的舍入点：

```yaml
math: |
  R_saved = bf16(R)
  R_weighted = bf16(decay ⊙ R)
```

两条路径都从 FP32 `R` 出发，不能把第二条改成先取 `R_saved` 再加权。仅有这类显式窄化时无需再用 `arithmetic` 重述；若还选择了公式未表达的近似方法，则另写对应例外。

### 账本

账本不是成本模型：计算量与访存量由 `math` 的公式和形状决定，账本只把“跟谁比、这一步动了什么”这个论证固定下来，让读者不必重新推导。它因此有入选判据——删掉这份账本，读者还能不能看出这一步的收益或代价？不能，才写。

`baseline`、`gain`、`cost` 各写一行，每行不超过 150 字符。`baseline` 写用来对照的求值方式，`gain` 写相对它减少的量，`cost` 写增加的量以及新增的误差来源。一类变化只记一项，低阶项并入主项；工作从一类单元换到另一类时，减少的记进 `gain`、增加的记进 `cost`，并用同一个计量对象对上。一行里有多项时用分号分隔，写到能判断方向与量级即可，不必展开全部低阶项。某一侧没有值得记录的变化就省略该字段；省略不是零变化的证明。

默认计量口径是：一个 MAC 是一次乘加，不换算成两个 FLOP；字节按逻辑读写的有效载荷计，既不是峰值分配，也不是实测 DRAM 流量；元素按本区公式实际求值的个数计，被掩码或补齐的位置只要仍然求值就计入；物化量计总量，同时存活量与峰值分配另行写明；遍历趟数要指明遍历的对象。下游分块造成的重复计算与重复读取、cache 行为、launch 开销、流水重叠和编译器结果都不计入；确需纳入其中某项时，必须同时给出依据。

`gain` 与 `cost` 先写计量对象，再写变化：采用“前值 -> 后值”或带正负号的增减，并在末尾给出计量范围。依赖下游参数时保留公式与绑定关系，不在本区抄一份调度配置；只在特定输入区域成立时，把条件写进同一行。

新增的误差来源及其已知误差界记在 `cost`，例如哪一次窄化进入了哪个乘法、近似覆盖哪些元素。实现与参考实现的最终输出差异由 `contract.algorithm_requirement.golden_reference` 回答，不在账本里预测。

账本分别记录各项变化，不把某项下降直接等同于整体收益。没有可核对的收益时，不能把改写称为已证实的优化；提取已有实现时同样如实记录它的代价。

例如，某一步已把 `T` 次 token 状态推进改成 `Nc` 次 chunk 推进，并选择保存 `Nc` 份、每份 `D` 个 BF16 元素的快照。收益与代价写在这一步自己的账本里：

```yaml
ledger:
  baseline: Token recurrence with a D-element FP32 state and no snapshots.
  gain: "State chain: T -> Nc state transitions per sequence"
  cost: "Saved snapshots: 0 -> 2*Nc*D bytes per sequence"
```

`T`、`Nc`、`D` 都来自已有定义；账本没有重新选参数，也没有把链长下降直接写成性能收益。

## 关键原则

### 参数的定义归属

Contract 对象直接沿用或引用，不在本区改变其名称、shape、语义或量化规则。块长这类参数按它改变了什么来归属，而不是按名字：改变三角系统与跨块递推的 chunk 长度是本层选择；只决定工作分块的长度由下游绑定；直接决定输入量化语义的组长由 Contract 固定。

### 精度是可以设计的，但每条数值路径都要留下痕迹

在哪里窄化、在哪里保持 FP32、哪里用带误差界的近似换吞吐，都是本层的决定，预算是 `contract.algorithm_requirement.golden_reference.tolerance`。每条数值路径都要由公式及必要的精度例外表达，不能被一句“FP32 累加”替代。跳过不可见项与近似本来必须计算的项是不同的决定，必须分别说明。

本区不另立误差标准，局部的多项式误差界也不是最终输出误差界。实现替换是否可接受，取决于它是否改变已声明的路径或 Contract 要求，而不是能否用“小于一个 ULP”概括。需要改动这些决定时返回设计或 Contract 讨论，不能移到 realization 后自行放宽。
